# Dynamic Workflow Engine — Deep Dive

## 1. Executive Summary

The Dynamic Workflow Engine is Lyra's execution substrate for code-driven, background, resumable multi-agent orchestration. It is the third primitive of the ultracode replication plan (Primitive 3) and sits at the center of Lyra's effort-driven orchestration stack: the `AutoOrchestrator` decides when a task warrants a workflow; the `WorkflowEngine` executes the workflow script; and the `AdversarialVerifier` (AVP) cross-checks every mutating action through a 3-critic panel from different providers.

The engine solves a fundamental architectural tension in conversational LLM applications: turn-by-turn agent loops fill the context window with intermediate results, limiting the scope of any complex task. The workflow engine breaks this pattern by executing orchestration scripts in a separate runtime. Intermediate results live in script variables (not the context window), agents run in background worker threads, and the user's session remains responsive throughout.

Key numbers:
- **16** concurrent agent cap (matches Claude Code's default)
- **1,000** total agents per workflow run
- **48** backpressure queue depth threshold
- **3** critics per claim in the AVP panel
- **6** trust dimensions in the A-Trust weighting system (Quality, Quantity, Relevance, Manner, Sincerity, Competence)
- **4** distinct providers supported (Anthropic, DeepSeek, OpenAI, Google), each with its own adapter

The breakthrough differentiator from Claude Code: Lyra's engine can assign different workflow stages to different providers. Bulk discovery work runs on cheap DeepSeek, verification on reliable Claude Sonnet, and synthesis on deep-reasoning Opus. This provider-aware multi-model orchestration is architecturally impossible in Claude Code (which is Anthropic-only).

## 2. The Engine Architecture

### 2.1 Script Format (JS-Based Orchestration)

Workflow scripts are authored in a JavaScript-like DSL that compiles to Lyra's internal `WorkflowScript` data model. Unlike Claude Code's JavaScript runtime, Lyra's engine uses a Python-native representation (dataclass-based) that can be generated by any LLM provider -- not just Anthropic models.

The core data model for script representation:

```python
@dataclass
class WorkflowScript:
    name: str
    description: str = ""
    phases: list[WorkflowPhase] = field(default_factory=list)
    providers: dict[str, str] = field(default_factory=dict)
    estimated_cost_usd: float = 0.0

@dataclass
class WorkflowPhase:
    name: str
    tasks: list[AgentTask] = field(default_factory=list)
    status: WorkflowStatus = WorkflowStatus.PENDING
    started_at: float = 0.0
    completed_at: float = 0.0
```

The `providers` dict maps logical roles to concrete model names (e.g., `{"default": "deepseek-flash", "verify": "claude-sonnet", "synthesize": "claude-opus"}`). This is the seam for provider-aware orchestration: a single workflow can dispatch tasks to multiple model families without any code changes.

A workflow script in practice reads like:

```
Phase 1: Discover (8 parallel agents on deepseek-flash)
  ├─ Audit auth submodule
  ├─ Audit encryption submodule
  ├─ Audit storage submodule
  ├─ Audit logging submodule
  ├─ Audit api-gateway submodule
  ├─ Audit session-mgmt submodule
  ├─ Audit input-validation submodule
  └─ Audit key-mgmt submodule

Phase 2: Verify (3 critics per finding on claude-sonnet + claude-opus)
  └─ For each finding: CriticA (Refutation), CriticB (Consistency), CriticC (Evidence)

Phase 3: Report (1 synthesis agent on claude-opus)
  └─ Synthesize 17 confirmed + 8 flagged findings into structured report
```

### 2.2 Runtime Environment (Sandboxed)

Before any workflow script executes, it passes through the `ScriptVM` -- a static analyzer that enforces safety constraints. The VM does NOT execute the script; execution is delegated to the `WorkflowEngine`'s scheduler, which dispatches individual `AgentTask` instances through the provider adapter layer.

The ScriptVM checks for two categories of violations:

**Denied globals** -- functions that could execute arbitrary code or access the host system:
```
eval, exec, Function, require, import, __import__, open, compile
```

**Denied modules** -- Python modules that provide filesystem or network access:
```
fs, child_process, os, subprocess, sys, shutil, socket, http, urllib
```

The VM performs simple substring matching (not AST parsing) because:
1. The workflow DSL has no import mechanism -- all providers, schemas, and utilities are injected by the engine
2. The surface area for injection is well-defined: only the `agent()` function and `parallel()`/`pipeline()` combinators
3. Any denied keyword that appears in a script is a hard violation -- false positives (e.g., "classify" containing "class") are acceptable because the DSL vocabulary is controlled

This is a defense-in-depth approach. Even if a script passes the static analyzer, individual agent tasks execute inside the provider API's output-format constraints (structured schemas, JSON modes where available), providing a second layer of isolation.

### 2.3 Phase Model

The workflow engine organizes execution into a two-level hierarchy: **workflows** contain **phases**, and **phases** contain **tasks** (individual agent calls).

```
Workflow
  ├── Phase 1 (e.g., "Discover")
  │     ├── AgentTask (prompt, model, schema, status)
  │     ├── AgentTask
  │     └── AgentTask ...
  ├── Phase 2 (e.g., "Verify")
  │     ├── AgentTask
  │     └── AgentTask ...
  └── Phase 3 (e.g., "Report")
        └── AgentTask
```

**Phase progression is strictly sequential**: Phase 2 does not begin until Phase 1 completes. Within a phase, tasks execute in parallel batches, but phases never overlap. This guarantees that the output of one phase is available as input to the next, without requiring the user to manage inter-phase dependencies.

Each `AgentTask` carries detailed metadata for tracking:
```python
@dataclass
class AgentTask:
    id: str                  # 8-char hex UUID
    prompt: str              # The agent's instruction
    model: str               # Model identifier (e.g., "deepseek-flash")
    phase: str               # Phase name (for post-hoc analysis)
    schema: dict | None      # JSON schema for structured output validation
    status: AgentTaskStatus  # QUEUED → RUNNING → COMPLETED / FAILED
    result: Any              # The agent's output
    error: str | None        # Error message if failed
    retries: int             # Current retry count
    max_retries: int         # Maximum retries before marking failed
    started_at: float        # Unix timestamp
    completed_at: float      # Unix timestamp
    tokens_used: int         # Token consumption
    cost_usd: float          # Computed cost
```

The engine tracks aggregate metrics per workflow: total agents dispatched, total tokens consumed across all agents, cumulative cost (computed from provider-specific pricing), and elapsed wall-clock time.

### 2.4 Progress View in /workflows TUI

The workflow engine exposes a `get_status()` API that the TUI (`/workflows` view) consumes to render live progress. The status payload is:

```python
{
    "workflow_id": str,
    "status": "running" | "paused" | "completed" | "failed" | "cancelled",
    "current_phase": str,
    "total_tasks": int,
    "completed_tasks": int,
    "failed_tasks": int,
    "agent_count": int,
    "total_tokens": int,
    "total_cost_usd": float,
    "elapsed_seconds": float,
    "backpressure": bool
}
```

A visual progress bar per phase renders as `[███████░░░] 71/93`, showing completed vs total tasks. The backpressure flag lights up yellow when the queue depth exceeds 48, signaling the user to pause or review concurrency. Active agents are shown by model type (e.g., "Active: 14 agents (12 sonnet + 2 opus)"), giving the user visibility into which providers have running tasks.

Interactive controls in the TUI allow the user to pause (serialize state to JSON snapshot), stop (cancel all pending and running tasks), or view verbose per-task details including individual token counts and cost breakdowns.

## 3. Execution Model

### 3.1 Background Execution

The `WorkflowEngine` executes workflows in **dedicated daemon threads**, not the main event loop. When a workflow is started via `engine.start(script)`, the method:

1. Validates the script has not exceeded the total agent cap (1,000)
2. Inserts the workflow into the internal tracking dictionaries under a lock
3. Spawns a `threading.Thread(target=self._execute, args=(workflow_id,), daemon=True)`
4. Returns the workflow ID immediately

The `_execute` method runs on the background thread and iterates through phases synchronously. Within each phase, it collects queued tasks, dispatches them in batches of up to `MAX_CONCURRENT` (16), and awaits their completion before moving to the next batch.

Because the workflow engine uses `threading` rather than `asyncio`, it can bridge the sync-to-async boundary cleanly: individual agent tasks call `AbstractProvider.chat()` which is an async method. The engine uses `asyncio.run()` in a thread pool executor to call async provider code from the sync background thread:

```python
@staticmethod
def _run_async(coro):
    try:
        loop = asyncio.get_running_loop()
    except RuntimeError:
        return asyncio.run(coro)
    # If we're already in an event loop, use a thread
    with concurrent.futures.ThreadPoolExecutor(max_workers=1) as executor:
        future = executor.submit(asyncio.run, coro)
        return future.result()
```

This design ensures the user's interactive session remains responsive: the main thread never blocks on LLM responses. The user can issue new commands, check workflow status, pause execution, or start additional workflows while the background engine continues processing.

### 3.2 Intermediate Results

A key architectural decision: intermediate results live in **script variables**, not the context window. Each `AgentTask.result` stores the complete provider response (content, tokens, cost). These results accumulate in memory during execution but do NOT flow back into the conversational context unless explicitly retrieved via `get_status()` or when the workflow completes.

This is the fundamental scalability advantage over turn-by-turn orchestration. In a traditional agent loop:
- Each agent's output is added to the conversation history
- The context window fills proportionally with the number of agents
- A 100-agent task would overflow any model's context window

In the workflow engine:
- Agent outputs are stored in a Python `dict` keyed by `task_id`
- The context window contains only the workflow script and the current task's prompt
- 1,000 agents produce the same context footprint as 1 agent -- only the storage grows, not the context window

The trade-off is that agent outputs cannot reference each other's results mid-stream (no inter-agent conversation within the same model context). However, the `pipeline()` combinator mitigates this by feeding one agent's output as the next agent's input in a controlled chain, with intermediate results still stored outside the context window.

### 3.3 Subagent Caps

Two hard caps govern subagent dispatch:

**Concurrency cap** (`MAX_CONCURRENT = 16`): The maximum number of agent tasks running simultaneously. Matches Claude Code's default and reflects a practical limit on provider API parallelism, thread pool sizing, and useful output consumption. When a phase has 93 tasks (e.g., 31 findings x 3 critics), the engine dispatches them in batches of 16 until all are complete.

**Total agent cap** (`MAX_TOTAL_AGENTS = 1000`): The maximum cumulative agents across all workflows in a single engine instance. This prevents runaway workflows from exhausting system memory. The cap is checked at `start()` time with a mutex lock:

```python
with self._lock:
    if self._agent_count >= self.MAX_TOTAL_AGENTS:
        raise RuntimeError(
            f"Agent cap reached: {self._agent_count}/{self.MAX_TOTAL_AGENTS}"
        )
```

The `_agent_count` counter is incremented in batch (not per-task) during phase execution to reduce lock contention: `self._agent_count += len(batch)`.

### 3.4 Backpressure

The engine implements a single backpressure signal: when the total `_agent_count` exceeds `BACKPRESSURE_QUEUE_DEPTH` (48), the `get_status()` response sets `backpressure: True`. This signal propagates to the TUI as a visual indicator and to the `AutoOrchestrator` as a throttle hint.

The threshold of 48 is chosen deliberately: with 16 concurrent agents, 48 total means approximately 3 full batches worth of agents have been dispatched. This gives the engine room to finish existing work while signaling that new workflows should not be started until the count drops below 48.

At the script level, the `parallel()` combinator can check backpressure before dispatching new tasks, but the current implementation leaves this decision to the caller (the LLM that wrote the script or the user who accepted it). This is a deliberate simplicity choice: the engine enforces bounds at dispatch time, and the backpressure signal is informational rather than blocking.

## 4. Resumability

### 4.1 Pause/Resume/Stop/Restart

The engine supports four lifecycle controls per workflow:

| Operation | Effect | Implementation |
|-----------|--------|---------------|
| `pause(id)` | Halts execution, returns serializable snapshot | Sets status to PAUSED, removes from `_running` set, calls `PauseResumeSerializer.serialize()` |
| `resume(snapshot)` | Restarts from saved state | Deserializes via `PauseResumeSerializer.deserialize()`, resets in-progress tasks to QUEUED, calls `start()` |
| `cancel(id)` | Terminates unconditionally | Sets status to CANCELLED, removes from `_running` set -- any running phase checks `_running` membership before dispatching the next batch |

The `_execute` method checks the running set at two granularity levels:
- **Between phases**: Before starting each phase, it checks `self._statuses.get(workflow_id) != WorkflowStatus.RUNNING`. If paused or cancelled, it returns immediately.
- **Between batches**: Before dispatching each batch within a phase, it performs the same check. This means a pause can take effect mid-phase, after the current batch of agents completes.

The `return` from `_execute` is clean -- no exception, no corruption. Completed phases retain their results; in-progress tasks within the last batch are lost (they were in-flight when the pause occurred) and are re-queued on resume.

### 4.2 Workflow State Persistence

The `PauseResumeSerializer` converts the entire workflow state to a JSON-serializable dict. The snapshot includes:

```python
{
    "workflow_name": str,
    "phases": [
        {
            "name": str,
            "status": str,
            "tasks": [
                {
                    "id": str,
                    "prompt": str,
                    "model": str,
                    "status": str,          # COMPLETED / QUEUED / RUNNING / FAILED
                    "result": Any,
                    "error": str | None,
                    "retries": int,
                    "tokens_used": int,
                    "cost_usd": float,
                },
                ...
            ],
        },
        ...
    ],
    "providers": dict,       # Role → model mapping
    "engine_state": dict,    # Aggregate counters (agent_count, total_tokens, total_cost)
    "serialized_at": float,  # Unix timestamp
    "version": 1,            # Schema version for forward compatibility
}
```

On resume, the serializer:
1. Restores the `WorkflowScript` with all phases and tasks
2. Preserves `COMPLETED` task results in full (completed work is not lost)
3. Resets `QUEUED` and `RUNNING` tasks back to `QUEUED` with `result = None`
4. Calls `engine.start(script)` which re-enters the execution loop

The engine state (aggregate counters) is restored from `engine_state` but this is informational only -- the resume re-dispatches queued tasks and the counters accumulate from zero on top of the restored values.

### 4.3 Crash Recovery

Crash recovery is currently **manual**: if the Lyra process terminates while a workflow is running, the in-memory state is lost. The JSON snapshot from a prior `pause()` call is the only recovery mechanism. The design intentionally does not implement automatic checkpointing (which would require filesystem writes on every batch completion) to avoid I/O latency inside the hot execution path.

The recovery protocol is:
1. User checks their workflow status file (stored by the TUI when the workflow was created)
2. If a snapshot was saved before the crash, user calls `engine.resume(snapshot)`
3. Completed task results are preserved; in-flight tasks are re-dispatched
4. If no snapshot exists, the workflow must be restarted from scratch

This is an area for future improvement: periodic auto-snapshots at phase boundaries (phase start and phase completion) would provide coarse-grained checkpointing with minimal I/O overhead. Phase boundaries are natural checkpoint points because phase transitions are strictly sequential and no in-flight tasks exist at those moments.

## 5. Agent Pool

### 5.1 Subagent Lifecycle

The subagent lifecycle inside the workflow engine follows a strict spawn-execute-return cycle:

```
1.  QUEUED      Task created, added to phase's task list
2.  RUNNING     Engine dispatches to provider via _run_task()
3a. COMPLETED   Provider returned successfully → result + tokens + cost recorded
3b. RETRYING    Provider returned error → retries < max_retries → requeued
3c. FAILED      Provider returned error → retries exhausted → error recorded
```

The lifecycle is entirely managed by the engine's `_run_task` method:

```python
def _run_task(self, task: AgentTask) -> None:
    task.status = AgentTaskStatus.RUNNING
    task.started_at = time.time()
    try:
        provider = self._resolve_provider(task.model)
        request = ChatRequest(
            messages=[Message(role=MessageRole.USER, content=task.prompt)],
            model=task.model,
            max_tokens=self._default_max_tokens,
            temperature=self._default_temperature,
        )
        response = self._run_async(provider.chat(request))
        task.result = response.content
        task.tokens_used = (
            response.usage.input_tokens + response.usage.output_tokens
            if response.usage else 0
        )
        task.cost_usd = self._estimate_cost(...)
        task.status = AgentTaskStatus.COMPLETED
        task.completed_at = time.time()
    except ProviderError as e:
        task.error = str(e)
        if task.retries < task.max_retries:
            task.status = AgentTaskStatus.RETRYING
            task.retries += 1
        else:
            task.status = AgentTaskStatus.FAILED
    except Exception as e:
        task.error = f"{type(e).__name__}: {e}"
        # Same retry logic
```

There is no agent pooling or reuse. Every agent task is ephemeral: it is created, dispatched once (or up to max_retries+1 times), and its result is stored. This is by design -- agents in a workflow are stateless function calls, not persistent conversational entities. Each call has its own prompt, its own schema, and its own model assignment. The only state is the result.

### 5.2 Model Routing per Subagent

Each `AgentTask` specifies a `model` string. The engine resolves this to a concrete provider via `_resolve_provider()`:

```python
def _resolve_provider(self, model: str) -> AbstractProvider:
    if self._provider_registry:
        return self._provider_registry.resolve(model)
    if self._default_provider:
        return self._default_provider
    raise RuntimeError(
        f"No provider configured for model '{model}'. "
        "Pass providers= to WorkflowEngine or set a default provider."
    )
```

The resolution follows a two-tier strategy:
1. If a `ProviderRegistry` is configured (from `lyra-router`), it handles the model-to-provider mapping with capabilities-aware routing
2. Otherwise, the engine falls back to a single default provider

This means a workflow script can assign models freely:
- `model: "deepseek-flash"` for bulk discovery (cheap, fast)
- `model: "claude-sonnet"` for verification (reliable, good at structured output)
- `model: "claude-opus"` for synthesis (best reasoning, highest quality)

And the registry handles the actual API dispatch -- resolving model aliases, checking capability requirements (e.g., DeepSeek does not support JSON mode or vision), and applying provider-specific fallbacks.

### 5.3 Provider-Aware Concurrency Caps

While the engine has a global concurrency cap of 16, the individual provider adapters enforce their own limits defined in the `CapabilityMatrix`:

| Provider | Concurrent Limit (provider-enforced) |
|----------|-------------------------------------|
| Anthropic | 50 |
| DeepSeek | 60 |
| OpenAI | 60 |
| Google | 30 |
| OpenRouter | 200 |
| OpenWeights | 10 |

The engine's 16-cap is a **local scheduler cap** -- it limits how many tasks the engine dispatches simultaneously. The provider's cap is enforced at the API level. If an adapter exceeds its concurrency limit, it receives rate-limit errors (model `ErrorCode.RATE_LIMIT`) and the task retries with exponential backoff.

The engine does not currently implement per-provider scheduling windows (e.g., "only send 5 to DeepSeek at a time"). Because provider rate limits (50-60) exceed the engine's concurrency cap (16), the engine is always the bottleneck -- it never dispatches more tasks than any single provider can handle. This is a pragmatic optimization that avoids the complexity of per-provider scheduler queues.

## 6. AVP Middleware Integration

### 6.1 Adversarial Verification Protocol

The AVP is the fourth ultracode primitive and integrates with the workflow engine as a middleware layer. Every claim produced by a workflow agent (a finding, a conclusion, a recommendation) can optionally pass through the AVP before being included in the final output.

The AVP core algorithm:

```
1. Anonymize claim (strip identity markers) — DEFAULT ON
2. Classify action via MutationGate
3. If mutating: route to 3 critics from different providers
4. Apply DecisionMatrix for consensus
5. Return verified result with critic annotations
```

The `AdversarialVerifier` class sits above the engine's provider dispatch. When a workflow script includes verification steps (as in the PCI compliance audit example), it calls three critic agents independently, collects their `CriticVerdict` instances, and runs the `DecisionMatrix`:

```python
class AdversarialVerifier:
    def verify(self, claim, critics_fn, agent_id=""):
        # Step 1: Anonymize
        review_claim = self._anonymizer.anonymize(claim)

        # Step 2: Get 3 critic verdicts from different providers
        verdicts = critics_fn(review_claim)

        # Step 3: Run decision matrix
        consensus = self._matrix.resolve(verdicts)

        return {"consensus": consensus, "verified": consensus == ACCEPT, ...}
```

Critics are expected to come from different providers (Anthropic, DeepSeek, OpenAI) to maximize architectural diversity. This is based on findings that cross-model error correlation is approximately 14.6 times worse than same-model correlation for error detection -- meaning diverse critics catch errors that homogeneous critics systematically miss.

### 6.2 Critique-Before-Execute for Mutating Actions

The AVP's `MutationGate` pre-classifies every action before it reaches the critic panel. Only mutating actions trigger the full 3-critic panel. Non-mutating actions pass through without verification overhead.

```python
class MutationGate:
    _MUTATING_KEYWORDS = frozenset({
        "write", "edit", "delete", "remove", "create", "update",
        "replace", "commit", "push", "deploy", "execute", "run",
        "install", "uninstall", "move", "rename", "copy", "chmod", "chown",
    })
    _NON_MUTATING_KEYWORDS = frozenset({
        "read", "view", "list", "show", "search", "find", "grep",
        "cat", "head", "tail", "ls", "stat", "diff", "log", "status",
        "describe", "get", "fetch", "query", "check", "validate",
        "inspect", "audit",
    })
```

The classification is keyword-based (not LLM-based) for speed -- it runs in microseconds and never blocks the execution thread. When both mutating and non-mutating keywords are present, the conservative default is MUTATING (trigger full verification). When no keywords match, the default is UNCERTAIN, which is also treated as MUTATING.

This SABER-inspired optimization means that in practice, most workflow phases (which are predominantly read-discover-analyze) skip verification entirely, and only write/edit/delete actions trigger the 3-critic panel. For a typical 3-phase workflow (Discover-Verify-Report), only the Verify phase's mutating conclusions would trigger AVP.

### 6.3 SABER Mutation-Gating and the Consensus Decision Matrix

The `DecisionMatrix` maps 3-critic vote combinations to final outcomes:

| Critic A | Critic B | Critic C | Outcome |
|----------|----------|----------|---------|
| ACCEPT | ACCEPT | ACCEPT | CONFIRMED |
| ACCEPT | ACCEPT | FLAG | CONFIRMED |
| ACCEPT | ACCEPT | REJECT | CONFIRMED (≥2 ACCEPT wins) |
| ACCEPT | FLAG | FLAG | FLAGGED |
| ACCEPT | REJECT | REJECT | REJECTED |
| REJECT | REJECT | REJECT | REJECTED |
| ACCEPT | REJECT | FLAG | ESCALATE (1-1-1 split) |

The rule is simple and deterministic: ≥2 ACCEPT votes means the claim passes, ≥2 REJECT votes means it is dropped, and the 1-1-1 split case is escalated (flagged for human review or held in a separate "uncertain" section).

This is complemented by the **ReviewAnonymizer** which strips identity markers from claims before they reach critics. This mitigates two documented failure modes from multi-agent debate research:

- **Identity-driven sycophancy** (Choi/Zhu/Li, ACL 2026): Agents uncritically adopt peer views when they know who wrote what. Fix: strip agent IDs, normalize formatting.
- **Actor-Observer Asymmetry** (Li et al., ACL 2026): Same agent reviewing own output blames external factors; reviewing others blames internal faults -- a >20% attribution flip on perspective swap. Fix: randomize critic-to-claim assignment; never let critics review their own output.

Additionally, the **RogueAgentMonitor** tracks per-agent confidence trajectories and flags agents that show signs of confusion (sudden confidence drops >0.3, sustained low confidence <0.4 over 5 steps, negative trend >0.2, or >2 early termination attempts). This prevents a single confused agent (from the "Preventing Rogue Agents" ACL 2025 findings) from sinking the entire task.

## 8. Trade-Off Analysis

### 8.1 Thread-Based vs Async Background Execution

**Choice**: The engine uses `threading.Thread` with `asyncio.run()` bridges for each task, rather than pure-async or process-based execution.

**Trade-offs**:

| Dimension | Thread-based | Pure async | Subprocess |
|-----------|-------------|------------|------------|
| Simplicity | High -- straightforward imperative code | Medium -- careful with blocking calls | Low -- IPC, serialization |
| Isolation | Low -- shared GIL, shared memory | Low -- same event loop | High -- process boundary |
| Provider call overhead | Medium -- asyncio.run() per call | Zero -- native async | High -- serialization |
| Crash isolation | None -- threads crash the process | None | Full -- subprocess dies independently |
| State sharing | Trivial -- shared in-memory dicts | Shared via asyncio.Queue | Complex -- RPC or shared storage |

The thread-based approach was chosen for simplicity and speed of implementation. The practical limitation is the Python GIL: CPU-bound operations within a task (e.g., JSON parsing, schema validation) do not parallelize. However, LLM provider calls are I/O-bound (network waits dominate), and each task's `asyncio.run()` releases the GIL while waiting on the network. For the workflow engine's I/O-dominated workload, threads are sufficient.

The subprocess approach would be necessary for full crash isolation (one workflow crash cannot bring down the engine), but this is a future enhancement.

### 8.2 Static Text Analysis vs AST Parsing

**Choice**: The ScriptVM uses substring matching for safety analysis, not AST parsing.

**Trade-offs**:

| Dimension | Substring matching | AST parser |
|-----------|-------------------|------------|
| Speed | Microseconds | Milliseconds |
| False positives | Possible ("classify" contains "class") | None |
| False negatives | Misses obfuscated code | Comprehensive |
| Implementation complexity | ~40 lines | ~200+ lines (parser + visitor) |

Substring matching was chosen because the workflow DSL is a controlled vocabulary: there is no import mechanism, no module system, and no way to obfuscate code within the DSL. The DSL only provides `agent()`, `parallel()`, `pipeline()`, and schema validators. If a script contains `eval` or `require('fs')` anywhere, it is blocked -- there is no legitimate use for these tokens within the DSL.

False positives are acceptable because the LLM that generates the script will receive the violation list and regenerate without the offending tokens. The cost of a false positive is one regeneration cycle; the cost of a false negative (obfuscated code passing through) could be arbitrary code execution.

### 8.3 In-Memory State vs Persistent Checkpointing

**Choice**: Workflow state lives entirely in memory. Persistent snapshots are only created when the user explicitly pauses.

**Trade-offs**:

| Dimension | In-memory (current) | Phase-boundary checkpoint | Every-batch checkpoint |
|-----------|-------------------|--------------------------|----------------------|
| Recovery granularity | Crash = full loss | Lose current phase only | Lose current batch only |
| I/O overhead | Zero | 2 writes per phase | 2 writes per batch |
| Complexity | Minimal | Medium (auto-serialize before phase start) | High (track dirty state) |
| File storage | None | ~files/hour | ~files/minute |

The in-memory approach was chosen for simplicity and performance. Phase-boundary checkpointing is the most natural extension and would provide reasonable recovery granularity (losing at most one phase's worth of work) with minimal implementation complexity -- the `_execute` method already has clear phase-boundary hooks where a checkpoint write could be inserted.

### 8.4 Keyword-Based Mutation Gate vs LLM-Based Classification

**Choice**: The MutationGate uses keyword matching, not an LLM call.

**Trade-offs**:

| Dimension | Keyword-based | LLM-based |
|-----------|--------------|-----------|
| Latency | <1 microsecond | ~500ms-2s |
| Cost | Zero | ~$0.01-0.05 per classification |
| Accuracy | ~95% for well-defined keywords | Variable |
| Handling ambiguity | Returns UNCERTAIN (conservative) | Can reason through ambiguous cases |

The keyword approach wins decisively because the MutationGate is called for every single action a workflow agent might take. With potentially hundreds of actions per workflow, an LLM-based gate would dominate both cost and latency. The SABER insight is that the gate does not need to be perfect -- it only needs to be fast and conservative. If UNCERTAIN (conservative/mutating) is returned for the 5% of ambiguous cases, those actions simply trigger the full AVP panel, which is the correct behavior anyway.

### 8.5 No Agent Pooling

**Choice**: Agents are created and destroyed per-task. No reuse.

**Trade-offs**:

| Dimension | No pooling | Agent pool |
|-----------|-----------|------------|
| State complexity | None -- tasks are stateless | Significant -- context management, session affinity |
| Resource usage | Provider API calls are the only cost | Memory per pooled agent |
| Warm-start | No -- each call starts cold | Yes -- pooled agents retain conversation history |
| Cross-task context | Manual via script variables | Automatic via conversation history |

The stateless design is intentional: workflow agents are function calls, not conversational partners. Each `agent()` call has a self-contained prompt that describes exactly what the agent should do. There is no benefit to retaining conversation history between calls because the workflow script already manages inter-agent data flow through variables and combinators.

The one scenario where pooling would help is if multiple agents need to reason over the same large context (e.g., a 100,000 token codebase that must be re-sent for every agent). Prompt caching (supported by Anthropic's API) mitigates this without pooling: the cached prompt is reused across calls, reducing token consumption by approximately 90% for the cached prefix.

## 9. (B) Breakthrough: Provider-Aware Orchestration

Claude Code's ultracode is Anthropic-only. Lyra's workflow engine operates across all configured providers. This section documents the breakthrough capabilities that this enables and the design decisions that make it work.

### 9.1 Multi-Provider Model Routing

The `WorkflowScript.providers` dict maps logical roles to specific models:

```python
script = WorkflowScript(
    name="pci-audit",
    phases=[...],
    providers={
        "default": "deepseek-flash",    # Bulk discovery — $0.27/MTok
        "verify": "claude-sonnet",       # Verification — $3.00/MTok
        "synthesize": "claude-opus",     # Synthesis — $15.00/MTok
    }
)
```

Individual tasks within phases reference these roles or direct model names:

```python
task1 = AgentTask(prompt="...", model="deepseek-flash")   # Uses "default" role
task2 = AgentTask(prompt="...", model="claude-sonnet")    # Verification role
task3 = AgentTask(prompt="...", model="claude-opus")      # Synthesis role
```

The `_resolve_provider()` method routes each task to the correct adapter based on the model name. The engine does not care which provider serves which model -- it only cares that the provider adapter conforms to the `AbstractProvider` interface.

### 9.2 Provider-Aware Auto-Orchestration

The `AutoOrchestrator.evaluate()` method includes provider-aware degradation logic:

```python
if provider == "openweights":
    # Open-weights: keyword trigger only, no auto-trigger reliability
    if should:
        should = False
        provider_fallback = True
elif provider == "deepseek":
    # DeepSeek: less reliable auto-trigger → attach explicit prompt fallback
    if should:
        reasoning += " | Prompt fallback: proposal attached"

elif provider in ("anthropic", "openai"):
    # Full auto-trigger reliability
    pass  # No degradation needed
```

This ensures that the orchestration tier's behavior adapts to the capabilities of the provider generating the workflow script. Open-weights models do not reliably auto-trigger workflows (they tend to produce malformed scripts), so the orchestrator falls back to keyword-only mode. DeepSeek gets the benefit of auto-triggering but with an explicit fallback prompt attached.

### 9.3 Cost-Optimized Provider Mixing

The practical cost savings from provider-aware orchestration are substantial. For the PCI compliance audit example:

| Phase | Provider | Agents | Cost |
|-------|----------|--------|------|
| Discover (8 parallel) | DeepSeek Flash ($0.27/MTok) | 8 | ~$0.94 |
| Verify (93 tasks) | Claude Sonnet ($3.00/MTok) + Claude Opus ($15.00/MTok) | 93 | ~$1.50 |
| Report (1 synthesis) | Claude Opus ($15.00/MTok) | 1 | ~$0.98 |
| **Total** | | **~102 agents** | **~$3.42** |

If all 102 agents ran on Claude Opus (Claude Code's default, since it is Anthropic-only), the cost would be approximately 5-10x higher. The provider-aware approach runs 93% of agents (85/93 verification + 8 discovery) on cheaper providers and reserves expensive deep-reasoning models for the 7% of tasks that genuinely need them.

### 9.4 Capability Awareness

The `CapabilityMatrix` ensures that provider routing respects each provider's feature set:

- **Anthropic**: tool calling, prompt caching (90% cost reduction for repeated prefixes), reasoning budget
- **DeepSeek**: tool calling, no JSON mode (uses prompt instructions instead), no vision
- **OpenAI**: tool calling, JSON mode, vision, reasoning effort parameter
- **Google**: largest context window (1M tokens), tool calling, vision
- **OpenWeights**: limited context (32K), no tool calling (prompt-based only), variable quality

The workflow engine consults this matrix when resolving providers, ensuring that tasks requiring specific capabilities (e.g., JSON output for schema validation, vision for screenshot analysis) are routed to providers that support them. This happens transparently: the script author specifies the model, and the engine ensures the provider can handle the task.

### 9.5 Future Directions

1. **Speculative execution**: Run cheap models in parallel with expensive ones; use cheap results unless expensive model disagrees (reduces latency without sacrificing quality).

2. **Adaptive provider selection**: Use historical trust scores from A-Trust to adjust provider routing based on observed reliability for specific task types.

3. **Provider-aware pricing transparency**: Show per-provider cost breakdowns in the `/workflows` TUI before execution, so users can optimize the provider mix based on their budget constraints.

4. **Graceful provider degradation**: If a provider becomes unavailable mid-workflow, fail over to an alternative provider with equivalent capabilities rather than failing the entire workflow.
