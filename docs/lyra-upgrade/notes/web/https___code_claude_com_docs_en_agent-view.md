# Manage multiple agents with agent view (code.claude.com — Anthropic / Claude Code)

**Source:** https://code.claude.com/docs/en/agent-view  
**Version/release:** Claude Code v2.1.139+ (research preview as of this documentation version, noted as potentially changing). Minimum version requirements documented: v2.1.140 for agent view, v2.1.141 for `--cwd` scoping, v2.1.142 for `--permission-mode`/`--model`/`--effort` flags, v2.1.143 for `worktree.bgIsolation` setting, v2.1.145 for voice dictation in agent view, v2.1.157 for `--agent` flag and honoring `agent` setting.  
**Type:** Product documentation (Claude Code feature)

## Key Technical Claims

1. **Supervisor daemon as per-user background process.** All background sessions are hosted by a single per-user supervisor process that is separate from the terminal and from agent view itself. The supervisor starts automatically on first backgrounded session or `claude agents` invocation, and exits when all sessions finish and no terminal is connected.

2. **Two-axis session state model.** Sessions carry both a *state* (Working, Needs input, Idle, Completed, Failed, Stopped) and a *process shape* (alive/`✻`, exited/`∙`, loop-sleeping/`✢`). This separates logical progress from process lifecycle — important for surviving detach/reattach cycles.

3. **Cheap-model glanceability.** Each row's one-line summary is generated by a **Haiku-class model**, not the session's main model. Summary refreshes at most once every 15 seconds, plus once when each turn ends. Each refresh is one short Haiku-class API request billed through the normal provider.

4. **Auto-worktree isolation.** Before editing files, every background session (whether started from agent view, `/bg`, or `claude --bg`) moves into an isolated git worktree under `.claude/worktrees/` so parallel sessions can read the same checkout but each writes to its own working tree. This isolation is skipped when already inside a linked worktree, not in a git repo, or writing outside the working directory.

5. **Idle process reaping.** Once a session finishes and sits unattached for about an hour, the supervisor stops its process to free resources. Pinned sessions (`Ctrl+T`) are exempt. The next attach, peek, or reply starts a fresh process from saved state. Empty rows (from `<-` with no prompt) are removed after about 5 minutes.

6. **Memory-pressure eviction.** When the host runs low on memory, the supervisor stops idle non-pinned sessions first, then idle pinned ones only if needed.

7. **Configuration persistence across process restart.** Permission mode, model, effort, and configuration flags all persist when the supervisor stops and restarts a session's process. `--dangerously-skip-permissions` and `--permission-mode bypassPermissions` survive restart instead of falling back to the directory's `defaultMode`.

8. **Session state survives sleep and supervisor restart.** State is stored to disk (`~/.claude/jobs/<id>/state.json`). Auto-updates and supervisor restarts are transparent to session state.

## Architecture/Mechanism Details

### Supervisor Process

- Background sessions are hosted by a **per-user supervisor process** (daemon), not tied to any terminal.
- Authenticates same credentials as interactive sessions; makes no additional network connections beyond the model API.
- Each background session is its **own Claude Code process**, managed by the supervisor.
- A session that is actively working, waiting for input, pinned, running a subagent/monitor/background command keeps its process alive.
- The supervisor watches the installed Claude Code binary for auto-updates (local file watch, not network check). Background sessions are detached processes, so they keep running through the supervisor restart, and the new supervisor reconnects to them.
- Stopped with `claude daemon stop --any` (with `--keep-workers` to preserve sessions through restart).

### State Storage

| Path | Contents |
|------|----------|
| `~/.claude/daemon.log` | Supervisor log |
| `~/.claude/daemon/roster.json` | List of running sessions (for reconnect after restart) |
| `~/.claude/jobs/<id>/state.json` | Per-session state shown in agent view |
| `~/.claude/jobs/<id>/tmp/` | Per-session scratch directory (writes here don't need permission) |

Each session gets `CLAUDE_JOB_DIR` env var pointing to its `~/.claude/jobs/<id>` directory, enabling coll-free temporary file writes across parallel sessions.

### Dispatch Mechanisms

Three ways to start a background session:
1. **From agent view** — type prompt in dispatch input, Enter dispatches. Supports subagent prefix matching, `@repo` for directory targeting, `! <command>` for raw shell jobs, image pasting.
2. **From inside a session** — `/bg` or `<-` on empty prompt backgrounds the current session. Configuration flags from original launch carry through.
3. **From shell** — `claude --bg "<prompt>"` starts a session straight to the background.
   - `claude --agent code-reviewer --bg` runs a specific subagent as the session's main agent.
   - `claude --bg --exec 'pytest -x'` runs a shell command as a background job.

### Row Summaries

- Generated by Haiku-class model (configurable via `ANTHROPIC_DEFAULT_HAIKU_MODEL` env var).
- Refreshed at most every 15 seconds + once per turn end.
- From v2.1.161, running parallel work items shows `done/total` count (e.g. `2/5`).
- Peek panel shows recent output, what the session needs, and pull requests opened.
- Multiple-choice questions in peek panel: press number key to pick an option.
- From v2.1.145: voice dictation in peek reply and dispatch input.

### Shell Management Commands

| Command | Purpose |
|---------|---------|
| `claude agents --cwd <path>` | Open agent view scoped to sessions under path |
| `claude agents --json` | Print live sessions as JSON array (pid, cwd, kind, startedAt, sessionId, name, status, waitingFor) |
| `claude attach <id>` | Attach to session |
| `claude logs <id>` | Print recent output |
| `claude stop <id>` | Stop session |
| `claude respawn <id>` / `--all` | Restart with conversation intact |
| `claude rm <id>` | Remove session (keeps worktree with uncommitted changes) |
| `claude daemon status` | Print supervisor state, version, socket directory, worker count |
| `claude daemon stop --any` | Stop supervisor (with `--keep-workers` to preserve sessions) |

### Subagent Dispatch

- First word of dispatch prompt matching a custom subagent name runs that subagent as the session's main agent.
- `@<agent-name>` explicitly mentions a subagent anywhere in the prompt.
- Subagent isolation: spawned subagents inherit the session's worktree. Set `isolation: worktree` in subagent frontmatter for separate worktree.

### Worktree Isolation Control

- Default: worktree isolation is always on for background sessions.
- Disable with `"worktree": { "bgIsolation": "none" }` in `.claude/settings.json` (requires v2.1.143+).
- Deleting a session in agent view (`Ctrl+X` twice) removes the worktree including uncommitted changes.
- `claude rm <id>` from shell keeps worktree with uncommitted changes and prints path.

### Permission Mode, Model, Effort

- Background session reads settings from its directory (same as interactive `claude`).
- `/bg` or `<-` keeps the current permission mode (so `acceptEdits` or `auto` persists through detach).
- `claude agents --permission-mode plan --model opus --effort high` sets defaults for every dispatched session.
- `--allow-dangerously-skip-permissions` makes `bypassPermissions` available in the mode cycle without starting in it.
- These settings persist through supervisor-initiated process restarts.

### Limiting Quota Use

- Background sessions consume subscription quota independently. Running ten agents in parallel uses quota roughly ten times as fast as one.
- Sessions are local (preserved across sleep, stop on shutdown).
- Claude-created worktrees are deleted with the session in agent view.

## Numbers & Benchmarks

- **Summary refresh rate:** At most once every 15 seconds, plus once per turn end.
- **Idle process reaping:** ~1 hour of unattached idle before process stopped.
- **Empty row cleanup:** ~5 minutes.
- **Haiku-class model** for summaries (not the session's main model).
- **Minimum prompts:** 4 characters (shorter prompts rejected with "Too short" hint).
- **Worktree isolation:** Auto-triggered for background sessions, see `.claude/worktrees/` for path.
- **`--json` output:** Structured machine-readable format for scripting integration.
- **Session ID:** Short alphanumeric ID, also the directory name under `~/.claude/jobs/`.
- **Permission mode acceptance:** `bypassPermissions` and `auto` require one-time interactive acceptance before any session can use them (even in background).

## Transfer to Lyra

**The One Idea:** Supervisor daemon with cheap-model session row summaries for glanceable fleet management.

Lyra's architecture debate (ARCHITECTURE-DEBATE.md) converged on Candidate B (Fleet-Centric) with a supervisor daemon as its core. The Claude Code Agent View is the reference implementation of this concept. The single most transferable mechanism is the **Haiku-class model for row summaries** — using a cheap model to generate glanceable one-line status updates for every session row, refreshed at bounded intervals (15s), decoupling the summary generation cost from the session's main model cost.

This solves the fundamental scaling tension in Lyra's fleet view: as the fleet grows to tens of concurrent sessions, you need visibility into each session without paying the full model cost for each row. By routing summary generation to a cheap model (Haiku-class or equivalent), Lyra can display meaningful session progress for arbitrarily large fleets at negligible marginal cost per row.

Additional transferable patterns:

1. **Two-axis state model** (state x process shape) — Lyra's fleet view should track both logical progress and process lifecycle independently.
2. **Shell-accessible management commands** — `claude attach/logs/stop/respawn/rm/daemon` from shell enables scripting, CI integration, and power-user workflows without the TUI.
3. **Auto-worktree isolation** — Lyra already plans worktree isolation (EnterWorktree tool); Agent View confirms the pattern of auto-isolation before any write as both correct and necessary for safe parallel background sessions.
4. **Memory-pressure eviction of idle sessions** — An important production concern that Lyra's supervisor should implement from day one.
5. **Configuration persistence across process restart** — A background session that was re-pinned, re-modeled, or switched to bypass mode should not lose those settings when the supervisor reaps and restarts its process.

**Workstream route:** §4.13 (Fleet/Swarm — supervisor daemon, fleet view, background sessions)

**Impact:** 5 — The supervisor daemon is the architectural spine of Lyra's fleet-centric design (Candidate B winner). The cheap-model summary mechanism is the key enabler for scaling the fleet view to practical sizes. Without it, either the fleet view is too expensive to run (>1 full-model query per session row) or too opaque (no row-level status, defeating the purpose of a visual fleet view).

**Effort:** 3 — Moderate. The supervisor daemon itself is substantial engineering (process lifecycle, disk persistence, worktree management, TUI), but the cheap-model summary mechanism is relatively straightforward once the daemon infrastructure exists: route status-description generation requests to a configurable cheap model endpoint at bounded intervals. Lyra already has provider abstraction and multi-model support in `packages/lyra-*`, so adding a Haiku-class route for summaries is wiring work, not research.

**Tier:** Breakthrough for Lyra — The supervisor daemon is Lyra's Phase 3 cornerstone and the defining architectural advantage over single-session competitors. The cheap-model summary mechanism is the practical enabler that makes the fleet view useful at scale, directly influencing Lyra's value proposition as a multi-agent orchestration platform.
