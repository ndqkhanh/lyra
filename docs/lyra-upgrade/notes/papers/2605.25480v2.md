## 1. Mechanism (step-by-step)

LLM-Wiki operationalizes the **Retrieval-as-Reasoning** paradigm through three principles: **compilability**, **composability**, and **evolvability**.

### 1.1 Index-Time: Wiki Compilation (Compilability)

Raw source documents are compiled into a structured, interlinked Wiki rather than flat embedded chunks. The process follows Algorithm 1:

```
Algorithm 1: Index-time Wiki compilation
Require: Source batch X, current Wiki W, directory indices I,
         source archives A, active Error Book constraints C
Ensure: Updated Wiki W and Error Book B
1: for each source passage x ∈ X do
2:   S ← SELECT_PAGES(x, I)           {select relevant existing pages}
3:   U ← COMPILE_WIKI_PAGES(x, S, C)   {generate pages, links, index updates}
4:   E_s ← STRUCTURAL_VALIDATE(U, W)    {detect dangling links, malformed refs, etc.}
5:   E_c ← CONTENT_VALIDATE(U, W, A)    {source-grounded LLM verification + cross-page consistency}
6:   E ← E_s ∪ E_c
7:   if E ≠ ∅ then
8:     B ← UPDATE_ERROR_BOOK(B, E)      {accumulate errors}
9:     C ← ACTIVE_CONSTRAINTS(B)        {inject learned constraints}
10:    U ← CODE_AUTO_FIX(U, E_s)        {deterministic structural repair}
11:  end if
12:  W ← APPLY_UPDATES(W, U)
13: end for
14: if PERIODIC_FIX_DUE(B) then
15:  W ← LLM_PERIODIC_FIX(W, B)        {LLM-based content repair}
16:  B ← VERIFY_AND_CLOSE(B, W)         {close resolved errors}
17: end if
18: return W, B
```

**Wiki structure:** Each page has YAML frontmatter (type, created, updated, aliases, tags), a blockquote summary, structured key facts, bidirectional `[[wikilinks]]` to related pages, and source references. Directory `_index.md` files act as browsable tables of contents grouped semantically.

### 1.2 Query-Time: Compositional Traversal (Composability)

The agent is equipped with two tools exposed through standard tool-calling interfaces:

- **wiki_search(query):** Searches Wiki index prioritizing structured signals (page names, aliases, tags, descriptions) before falling back to page content. Returns candidate pages and metadata.
- **wiki_read(paths):** Batch-reads directory indices (`_index.md`) or full pages. Content includes inter-page wikilinks as traversal affordances.

**Traversal strategies** (adaptively selected per query):

| Strategy | When Applied | Example |
|----------|-------------|---------|
| **Direct access** | Known entities | One search + one read → answer |
| **Link-following traversal** | Multi-hop bridge queries (A→B→answer) | Read page A → follow link to B → read B |
| **Browse-first traversal** | Open-ended / exploratory queries | Read `_index.md` → select pages → batch-read |

**Termination criteria:** Agent assesses evidence sufficiency after each `wiki_read`. Stops when (a) all reasoning chains traced, (b) tool-call budget T_max = 15 reached, or (c) patience threshold P = 3 consecutive empty searches exceeded. At least one `wiki_read` required before answering.

### 1.3 Error Book: Self-Evolution (Evolvability)

A persistent YAML file (`error_book.yaml`) drives closed-loop self-correction through a 5-stage lifecycle:

1. **Discover:** Deterministic validators detect structural errors (dangling links, incomplete pages, malformed references, unseen overwrites, index inconsistencies). Source-grounded LLM verification and cross-page consistency checks detect content-level errors (unsupported facts, cross-page contradictions).

2. **Attribute:** Each error traced to root cause. E.g., "assuming a linked page exists without checking the index."

3. **Constrain:** Root cause formalized as natural-language constraint rule. E.g., "NEVER create a link to a page not present in `_index.md`" or "Do not add entity attributes unless supported by the cited source digest."

4. **Inject:** All open constraint rules appended to the compilation prompt for subsequent batches.

5. **Verify & Close:** System re-validates previously erroneous pages. If error no longer appears after constraint injection, entry marked as closed.

**Two-layer repair:**
- **Layer 1 (Code Auto-fix):** Runs after every batch; deterministic fixes for structural errors (dangling links, formatting, index inconsistencies).
- **Layer 2 (LLM Periodic Fix):** Triggers every N articles; handles semantic/content errors (missing pages, incomplete digests, unsupported facts, contradictions). At finalization, a 3-round code-fix ↔ LLM-fix loop catches all remaining errors.

**Error taxonomy (7 categories):**

| Error Type | Detection Method | Distribution Range |
|-----------|-----------------|-------------------|
| Dangling Links | Filesystem cross-validation | 29.1–63.8% |
| Malformed Refs | Regex validation | 18.9–28.5% |
| Unsupported Facts | Source-grounded LLM check | 5.8–12.7% |
| Index Inconsistency | Bidirectional diff | 2.2–10.9% |
| Incomplete Pages | Template completeness | 2.1–9.1% |
| Unseen Overwrite | Set comparison | 2.4–3.6% |
| Cross-Page Contradictions | Sampling-based consistency | 1.9–7.3% |

## 3. Trade-offs

| Win | Lose |
|-----|------|
| +8.1 F1 over best baseline on MuSiQue (compositional) | Compilation cost: each passage requires SELECT_PAGES + COMPILE_WIKI_PAGES (one-time, amortized over queries) |
| +8.9 AC points on high multi-doc AuthTrace queries | Single-doc questions slightly worse (-2.3 AC vs HippoRAG 2) — Wiki structure can omit fine-grained local details when summarizing |
| 0.983 F1 on 4-hop questions (Dense RAG: 0.924) | Wiki grows unwieldy at tens of thousands of pages; directory indices need hierarchical sharding |
| Query latency 14.9-27.1s (2.5x faster than LightRAG) | Web-scale / frequently-changing corpora unsupported — requires stale-fact handling, global directory maintenance |
| Persistent Error Book drives self-improvement across batches | Two LLM calls per passage (select pages + compile) at index time; cost scales linearly with corpus |
| Works across answer LLMs (GLM-5.1 and GPT-4o) | Not tested on open-domain full-Wikipedia retrieval (only dataset-provided context setting) |
| Human-auditable Wiki pages (YAML + Markdown, fully readable) | Not multimodal — text-only compilation currently |

## 4. Design Rationale

The central thesis is that retrieval's bottleneck is **knowledge organization**, not retrieval algorithm quality. The key insight: pre-compiling documents into explicitly linked Wiki pages transforms retrieval from a one-shot similarity-lookup into a compositional reasoning process over a navigable structure.

**Why Wiki pages rather than embeddings/vectors/triples/summaries?**
1. **Explicit bidirectional links** make intermediate entities in reasoning chains immediately discoverable — the agent follows structural pointers instead of relying on probabilistic embedding similarity.
2. **Human-auditable format** enables both machine traversal and human inspection/debugging of compilation errors.
3. **Front-loaded organization:** Compilation cost is paid once at index time and amortized over all queries; at query time, pre-compiled links eliminate expensive runtime LLM calls for entity disambiguation and relation extraction.

**Why the Error Book?** LLM-generated compilation inevitably introduces errors (dangling links dominate at 29-64%). Without persistent correction, quality silently degrades. The Error Book converts one-off post-processing into cumulative learning: each batch contributes reusable constraints that prevent recurrence of known error patterns.

**Why two-layer repair?** Structural errors (links, formatting, indices) are frequent, deterministic, and automatable via code. Content errors (unsupported facts, contradictions) require reasoning and benefit from LLM-based repair. Separating them allows Layer 1 to keep the Wiki structurally traversable at near-zero incremental cost, while Layer 2 runs periodically to improve factual grounding.

## 5. Limitations & Failure Modes

**Explicit limitations (per authors):**
1. **Compilation cost:** SELECT_PAGES + COMPILE_WIKI_PAGES per source passage make initial construction more expensive than chunk-and-embed approaches (amortized over queries).
2. **Scalability ceiling:** As Wiki grows to tens of thousands of pages, directory indices become unwieldy and page selection may degrade. Web-scale dynamic corpora require hierarchical indexing, sharding, stale-fact handling, and global directory maintenance — all future work.
3. **Single-doc disadvantage:** Wiki-structured summarization can omit fine-grained local details needed for single-document factual lookup, where HippoRAG 2 outperforms by 2.3 AC points.

**Implicit failure modes (from ablation/analysis):**
4. **Non-traversable structure defeats the approach:** Removing progressive traversal (single search + single read, no link-following) causes 11.7-13.8 F1-point drop — the compiled structure is only useful when actively traversed.
5. **Error accumulation without Error Book:** Recurring errors silently degrade downstream retrieval quality by 3.4-4.0 F1 points.
6. **Not open-domain evaluated:** All experiments use dataset-provided context (closed-corpus setting), not full Wikipedia. Open-domain retrieval quality depends on whether the corpus is fully compiled, which is substantially harder.
7. **Static compilation model:** No mechanism for incremental updates to individual pages when source documents change; recompilation from scratch needed for document updates.
8. **Text-only:** No multimodal (image, table, diagram) Wiki pages supported.

## 6. Transfer to Lyra

### The ONE Transferable Idea

**"Compile-once, traverse-many" Knowledge Compiler:** Build a subsystem that compiles agent tool outputs, conversation artifacts, and retrieved documents into structured, bidirectionally-linked "Wiki-style" memory pages with YAML frontmatter metadata, aliases, explicit cross-links, and source provenance. At query/planning time, the agent traverses these pages via search→read→link-follow operations rather than issuing one-shot embedding lookups against a flat vector store. This transforms Lyra's retrieval from "retrieval-as-lookup" (flat chunk similarity) to "retrieval-as-reasoning" (structured traversal over compiled knowledge).

Concretely for Lyra:
- **Index time:** When Lyra receives tool outputs, memory writes, or conversation summaries, a Compiler step structures them into Markdown pages with explicit `[[links]]` to related pages (prior conversations, related tools, similar errors).
- **Query time:** The Lyra agent uses `memory_search()` and `memory_read()` tools to traverse this compiled structure, following links between related memories, rather than depending entirely on embedding similarity.
- **Error Book analogue:** Track when memory links dangle (referenced entities no longer exist), when facts contradict across pages, and when indices are stale — accumulate constraints that improve future compilation.
