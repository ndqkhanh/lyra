# τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains

**Authors:** Shunyu Yao, Noah Shinn, Pedram Razavi, Karthik Narasimhan (Sierra / Princeton)
**Venue:** arXiv:2406.12045v1, June 17, 2024 (Preprint, Under Review)
**Code:** https://github.com/sierra-research/tau-bench

## 1. Mechanism (step-by-step)

### 1.1 Problem Formulation
Each task is a POMDP (S, A, O, T, R, U):
- **State space** S = S_db ⊗ S_user (database state × user state)
- **Action space** A = A_db ∪ A_user (API tool calls ∪ natural language messages to user)
- **Observation space** O = O_db ∪ O_user (API responses ∪ user messages)
- **Transition** T_db: (s_db, a_db) → (s'_db, o_db) — deterministic Python function
- **Transition** T_user: (s_user, a_user) → (s'_user, o_user) — stochastic LM sample
- **Reward** R: S → {0, 1}

### 1.2 Components
1. **Databases (JSON):** 500 users, 50 products, 1000 orders (retail); 500 users, 300 flights, 2000 reservations (airline)
2. **API Tools (Python):** 15 tools (retail: 7 write + 8 read; airline: 6 write + 7 read) — deterministic, implemented as Python functions
3. **Domain Policy (Markdown):** System prompt with rules, procedures, constraints. Some rules API-enforced (e.g., payment not found → error), others require agent compliance (e.g., baggage allowance calculation)
4. **User Simulator (LM):** Uses gpt-4-0613 with temperature=1.0. Receives hidden instruction specifying identity, intent, preferences. Cannot see agent-tool interactions. Outputs "###STOP###" to end episode.
5. **Task Instances (JSON):** Instruction for user simulation + annotated ground truth DB write actions + expected output substrings

### 1.3 Evaluation Protocol
```
r = r_action × r_output
```
- **r_action** ∈ {0, 1}: final database state matches unique ground truth outcome
- **r_output** ∈ {0, 1}: agent responses contain all required information substrings

### 1.4 pass^k Metric (novel contribution)
Probability that ALL k i.i.d. trials succeed:

```
pass^k = E_task [ (c choose k) / (n choose k) ]
```

Where n = total trials, c = successful trials. Unbiased estimator using combinatorics. This measures **consistency/reliability** (not best-of-k discovery like pass@k).

### 1.5 Construction Pipeline
- **Stage I:** Manual co-design of minimal realistic schemas, APIs, policies
- **Stage II:** LM-assisted data generation — gpt-4 generates Python sampling code, manually polished
- **Stage III:** Manual task annotation with iterative validation — run >40 trials per task with gpt-4-turbo FC agent, examine zero/low-success tasks, fix ambiguities

### 1.6 Agent Loop
```
1. System prompt = domain policy + tool definitions
2. At each turn, model autonomously chooses: user message OR tool call
3. Max 30 actions per task
4. Agent temperature = 0.0
5. User simulator temperature = 1.0
6. Episode ends when user emits ###STOP###
```

| claude-3-opus | 44.2% | 34.7% | 39.5% |
| claude-3-sonnet | 26.3% | 27.6% | 27.0% |
| mistral-large | 30.7% | 22.4% | 26.6% |
| gemini-1.5-pro | 21.7% | 14.0% | 17.9% |

**Key:** Even SOTA (gpt-4o) succeeds on <50% of tasks. No model solves τ-bench.

### 2.2 pass^k Consistency (gpt-4o FC, τ-retail)
| k | pass^k |
|---|--------|
| 1 | ~61% |
| 2 | ~50% |
| 4 | ~35% |
| 8 | <25% |

pass^8 < 25% means agent solves the same task 8/8 times only 25% of the time.

### 2.3 Method Comparison (τ-retail, gpt-4o)
| Method | pass^1 |
|--------|--------|
| Function Calling (FC) | 61.2% |
| ReAct (text-formatted) | ~48% |
| Act-only (no reasoning trace) | ~42% |

FC consistently outperforms text-formatted methods. Adding "think" function to FC did not help.

### 2.4 Failure Breakdown (36 failed gpt-4o FC trajectories in τ-retail)
| Failure Type | % |
|-------------|-----|
| Wrong argument (bad IDs, hallucination) | 33.3% |
| Wrong information (missing/miscalculated info) | 22.2% |
| Wrong decision (violated domain rules) | 25.0% |
| Partial resolution (compound requests) | 19.4% |

### 2.5 Cost
- Agent cost: $0.38/task (95.9% input prompt, 4.1% completion)
- User simulation: $0.23/task
- Total: ~$200 for one trial across all τ-retail tasks

|-------|------------|----------------|---|

shows when complex rules matter (airline), removing policy hurts capable models more.

## 3. Trade-offs

| Win | Lose |
|-----|------|
| Faithful, fast rule-based evaluation (DB state comparison) replaces subjective human judgment | Requires labor-intensive manual task annotation to guarantee unique DB outcomes |
| pass^k metric measures consistency/reliability, not just best-of-k — critical for production deployment | pass^k requires many trials per task (cost multiplies with k) |
| LM-simulated users produce diverse, natural conversations with stochastic variation | User simulator LM (gpt-4-0613) has limited reasoning/capacity — may not catch all edge cases |
| Modular framework allows domain extension | Only 2 domains tested; uncertain if methodology scales to medical/legal/tax |
| Deterministic API tools prevent evaluation noise from tool execution errors | Domain policies are simplified vs real-world — may not capture full complexity |
| Open-source codebase encourages community contribution | Task curation used gpt-4-turbo for tuning → implicit model bias in task design |

## 4. Design Rationale

The authors observed that existing agent benchmarks (WebArena, SWE-bench, BFCL) lack two critical real-world dimensions: **(1) multi-turn human interaction** where information must be gathered incrementally, and **(2) domain-specific rule following** where agents must consult policy documents. Task-oriented dialogue benchmarks (MultiWOZ) are static and don't test database-backed tool use. Tool-use benchmarks (BFCL, ToolBench) are single-turn with all information upfront.

τ-bench unifies both by:
- Using LM-simulated users instead of scripted dialogues (captures stochastic real-world variation)
- Embedding complex domain policies as system prompts (tests rule-following)
- Comparing final DB state to ground truth (objective, fast, no human judge needed)
- Defining pass^k to measure reliability (not just average success)

The key insight: if an agent cannot consistently handle the same task re-stated slightly differently, it is not production-ready — regardless of average success rate.

## 5. Limitations & Failure Modes

1. **User simulation fidelity:** gpt-4-0613 as user simulator may fail at reasoning, calculation, long-context tracking, or following instruction prompts precisely. Users may authorize suboptimal choices without double-checking agent recommendations.

2. **Task annotation bias:** Task instructions were iteratively refined by observing gpt-4-turbo FC agent trajectories. This could make tasks artificially solvable by that specific model while remaining hard for others — a form of annotator-model coupling.

3. **Domain scope:** Only 2 domains (retail, airline) with simplified policies. Results may not transfer to higher-stakes domains (medical, legal, financial) where rule complexity is orders of magnitude larger.

4. **User instruction gaps:** Instructions don't contain all domain knowledge. Real users don't know complex policies either, but the simulator's ignorance may cause underspecified task outcomes.

5. **Reward sufficiency:** r=1 is necessary but not sufficient for success — agents could achieve correct DB state while violating policies (e.g., no user confirmation). No LM-judge supplement for rule compliance.

6. **Cost scaling:** Running pass^8 on all tasks is expensive (~$200/trial × 8 × 2 domains ≈ $3200+ at gpt-4o pricing). This limits adoption for rapid iteration.

7. **Temperature sensitivity:** Agent temperature fixed at 0.0; no exploration of how different temperatures affect pass^k curves.

## 6. Transfer to Lyra

### The One Transferable Idea

**The pass^k reliability metric with LM-simulated user interaction as a consistency evaluation layer for Lyra.** Instead of only measuring average success (pass^1), Lyra should be evaluated on its ability to handle the **same** task correctly across multiple independent runs with stochastic user simulation. This directly addresses Lyra's need for production-grade reliability measurement and surfaces fragility that average metrics hide.

### Workstream Route: §4.5 (Reliability & Robustness)

- **Impact:** 5 — This directly defines how Lyra measures reliability, the core concern of the entire upgrade
- **Effort:** 4 — Requires building a domain-specific user simulator, task annotations with unique outcomes, and running multi-trial evaluations
- **Tier:** **breakthrough** — A reliability-first evaluation framework that surfaces consistency failures is prerequisite to production deployment; without it, Lyra cannot credibly claim robustness

### Concrete Application
- Define a mini τ-bench for Lyra's target domain(s) with policy documents, API tools, and LM-simulated user scenarios
- Run pass^4 or pass^8 on every release candidate as a reliability gate
- Track pass^k curves over time as a key metric alongside standard benchmarks
