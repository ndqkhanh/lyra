# Evolve as a Team: Collaborative Self-Evolution for LLM-based Multi-Agent Systems

**Authors:** Zhezheng Hao (Zhejiang Univ), Tianfu Wang (HKUST), Huanshuo Dong, Ziyan Liu, Hong Wang, Xiankun Lin, Qiang Lin (Tencent), Can Wang, Hande Dong, Jiawei Chen (Zhejiang Univ + Tencent)

**Venue:** arXiv preprint, May 28, 2026 (arXiv:2605.29790v1). Code: https://github.com/zz-haooo/Meta-Team

## 1. Mechanism (Step-by-Step)

**Core Insight.** The paper identifies an architectural mismatch in MAS evolution: MAS *execute* through distributed contexts (each agent holds only its local trajectory), but existing evolution methods *flatten* the full multi-agent trajectory into a single analyzer, reintroducing the context bottleneck that MAS were designed to solve. The proposed fix: **a MAS should evolve the same way it executes — collaboratively, with distributed context.**

**Three-Scheme Analysis (Global vs Local vs Collaborative).**

The paper formalizes three ways to organize MAS experience for attribution/evolution:

| Scheme | Context Organization | Per-Analyzer Context | Cross-Agent Awareness |
|--------|---------------------|---------------------|----------------------|
| Global | Flatten full τ into one LLM call | Very long (full team trajectory) | Full |
| Local | One analyzer per agent, sees only own τᵢ | Short (single-agent sub-trace) | None |
| Collaborative | One analyzer per agent sees own τᵢ, plus cross-agent communication | Short + targeted messages | Recovered via post-task exchange |

The global scheme suffers on trajectories >128K tokens (Agent Accuracy drops from 64.1% to 35.0% on long traces), while the local scheme lacks cross-agent context. The collaborative scheme achieves 77.5% Agent Accuracy and 43.1% Step Accuracy — the best in both length regimes.

**Meta-Team's Multi-Scale Evolution (Algorithm 1).**

Given an initial MAS M₀ = (A, O) with candidate agent pool A★, team constitution C, and for each task xₖ:

1. **Execute** the task: recruit A ⊆ A★, run the team, collect experience eₖ = (xₖ, τₖ, rₖ) where rₖ comes from the evaluator V.

2. **Agent-Level Evolution (L1)** — For each agent aᵢ ∈ A (in parallel):
   - Agent reviews its own local trace τᵢ
   - Solicits cross-agent evidence: queries how its outputs affected downstream agents
   - Updates its behavioral patches Δᵢ, skill library Kᵢ, and produces a summary uᵢ
   - Operator: (Δᵢ, Kᵢ, uᵢ) ← Ω_L1(sᵢ, τᵢ, rₖ)

3. **Interaction-Level Evolution (L2)** — For each interacting pair (aᵢ, aⱼ):
   - Revisit collaboration history (message gaps, handoff quality, dependency patterns)
   - Update teammate profiles Φᵢ, Φⱼ (how each agent understands the other's strengths/limitations)
   - Update pairwise collaboration notes Rᵢ, Rⱼ
   - Operator: (Φᵢ, Rᵢ, Φⱼ, Rⱼ) ← Ω_L2(sᵢ, sⱼ, τₖ, rₖ)

4. **Team-Level Evolution (L3)** — Collective discussion among all agents:
   - Aggregates summaries {uᵢ} from L1 and selected evidence from L2
   - Revises team constitution S = (A★, C): may add/remove roles, reorganize structure, update shared rules
   - Only concise summaries go to the team level — NOT the full flattened trajectory
   - Operator: S ← Ω_L3(S, {uᵢ}, τₖ, rₖ)

5. **Commit gate**: validate updates (role consistency, tool availability, format validity, budget constraints). If retry requested and budget remains, re-execute xₖ with updated M.

6. **Agent scaffold structure**: sᵢ = (πᵢ, Δᵢ, Kᵢ, Φᵢ, Rᵢ)
   - πᵢ: base role prompt
   - Δᵢ: behavioral patches (what to observe, verify, report, avoid)
   - Kᵢ: skill library (loaded by progressive disclosure)
   - Φᵢ: teammate profiles
   - Rᵢ: pairwise correlation notes

**Orchestration Protocol.** Open-roster design: candidate pool A★, dynamic recruitment via STARTAGENT. Primitives: LISTPOOL, STARTAGENT, STOPAGENT, FINALIZE, TERMINATE. Append-only message bus with per-agent mailboxes.

**Collaborative Attribution on TraceElephant.**

In the collaborative scheme, each analyzer posts a short summary of its findings, reads other analyzers' summaries, then re-audits its sub-trace and submits (i_erred, my_step, c, r) where c is self-confidence and r=1 if it disagrees with the global verdict with counter-evidence. Final vote: weight w = c(1 + αr) with α=1.

## 3. Trade-offs

| Win | Cost/Loss |
|-----|-----------|
| **+6.6 avg points** over hand-crafted MAS across 9 benchmark columns | Extra evolution cost: each post-task reflection consumes LLM calls for L1+L2+L3 (3 scales of analysis per task) |
| **+13.1 points** on long-horizon tasks (SWE-Pro Ansible) where centralized analysis fails | Post-task communication rounds add latency overhead not present in single-pass execution |
| **No context saturation** on >128K trajectories, unlike global scheme which collapses (35.0% → Agent Acc) | Collaborative scheme still drops from 77.5% to 45.0% Agent Accuracy on >128K traces — degradation exists but is milder |
| **Cross-language transfer:** evolved on Python, works on C/C++/Java without re-evolution | Evolution is benchmark-specific (separate evolution set per benchmark); no cross-benchmark knowledge transfer demonstrated |
| **Cost-efficient:** under 1/3 budget, Meta-Team still achieves best performance-cost Pareto frontier | Without budget controls, evolution can be expensive — paper reports $30–$150 per-case evolution budgets in Table 6 |
| **Model-agnostic:** works with any LLM backbone, scaffold-only updates | No parameter fine-tuning — recurring team behaviors cannot be internalized into the base model, limiting compounding gains over many iterations |
| **Interpretable evolution:** plain-text patches and profiles readable by humans | Evolution artifacts are scaffold-specific; not portable across different MAS frameworks |
| **Bottom-up emergence:** team can discover missing roles (2 extra workers added automatically on 256K context) | Open-roster dynamic recruitment adds execution complexity and potential for runaway team size |

## 4. Design Rationale

**Why collaborative over centralized analysis?** The authors argue from first principles: MAS solve the single-agent context bottleneck by distributing execution across agents. Centralizing analysis for evolution re-creates the exact bottleneck MAS were designed to escape. This is validated empirically: global analysis degrades sharply on >128K trajectories even when the full trace fits within the model's context window (1M tokens). The failure is not overflow but *reasoning burden* — the model cannot reliably locate the decisive failure step in an interleaved multi-agent trace.

**Why three scales (L1+L2+L3)?** The scales mirror the compositional structure of MAS: agent scaffold, inter-agent protocol, and shared team scaffold. A single failure may involve all three (e.g., an agent's bug causes a bad handoff which reveals a missing role). Treating them independently misses cross-scale causality; treating them with a single monolithic update loses granularity. The ablation confirms complementarity: L1 is most impactful (-7.9 points when removed on ResRub), but L2 and L3 each contribute unique gains.

**Why teammate profiles instead of binary communication graphs?** Prior methods (AgentNet, GPTSwarm) evolve binary edges in a communication DAG. The authors argue that richer teammate profiles — capturing *how* to query and rely on teammates, not just *whether* to communicate — enable more calibrated collaboration. This is a design choice favoring qualitative understanding over structural optimization.

**Why open-roster rather than fixed topology?** Fixed topologies (like OWL's Planner-Coordinator-Worker) cannot adapt to different task scales. The open-roster design allows Meta-Team to grow (2 extra workers on 256K context) or shrink based on task demands, discovered through team-level evolution.

## 5. Limitations and Failure Modes

1. **Scaffold-only evolution.** Meta-Team does not touch execution infrastructure — tool APIs, environment harnesses, verifiers, or memory backends require separate engineering. A team may learn it needs a tool but cannot create one.

2. **No parameter fine-tuning.** All evolution is through explicit scaffold text updates. Recurring patterns that could be internalized into model weights (via fine-tuning or RL) remain as prompt patches, which consume context budget and may be inconsistently followed.

3. **Benchmark-specific evolution.** Each benchmark requires its own evolution set and produces its own artifacts. No cross-task knowledge transfer is demonstrated. The evolved team for SWE-Pro Ansible does not help on BeyondSWE.

4. **Collaborative attribution degrades on very long traces (>128K).** Agent Accuracy drops from 77.5% to 45.0%, and Step Accuracy drops to 19.6%. The method is more robust than global analysis but still struggles with very long interleaved trajectories.

5. **No open-source LLM validation.** All experiments use Claude Sonnet 4.6. Behavior with weaker open-source models (which may have worse long-context reasoning) is unknown.

6. **Evolution quality depends on backbone LLM quality.** If the backbone model cannot reliably reflect on its own behavior, collaborative attribution becomes noise amplification rather than signal aggregation. The paper does not test with weaker models.

7. **Runaway team growth risk.** Team-level evolution can add roles; without explicit guardrails, the team could grow unboundedly. The paper mentions budget constraints as a guardrail but does not characterize growth limits.

8. **Communication overhead in evolution.** Post-task communication (L2, L3) adds LLM calls proportional to agent count. For large teams, this quadratic communication cost could dominate the evolution budget.

## 6. Transfer to Lyra

**The ONE Idea:** Distributed, agent-local context preservation with structured post-task cross-agent communication for failure attribution and system self-improvement — "evolve as a team, not as a monolith."

**Application to Lyra:** Lyra's current architecture runs multiple subsystems (router, memory, context-manager, safety-guard, tools-executor, verifier). When a user task fails, attributing the failure to a specific subsystem is currently done through centralized log inspection. Instead, each Lyra subsystem could carry its own local execution trace into a post-task collaborative reflection phase, where subsystems exchange processed findings (not raw logs) to identify cross-subsystem failure chains. This would enable:

1. **Subsystem-level self-evolution:** Each subsystem (router, memory, etc.) autonomously updates its behavioral patches based on local evidence and cross-subsystem feedback.
2. **Interface-level calibration:** Subsystems update their "teammate profiles" — e.g., the router learns the memory subsystem's actual retrieval latency/reliability rather than assuming design-time specs.
3. **Architecture-level adaptation:** Collective discussion could surface needs like "we need a dedicated citation tracker" or "the verifier and safety guard should swap execution order."

**Workstream route:** §4.2 (Memory + Self-Evolution) — this directly feeds the self-improvement loop where Lyra learns from its own execution experience. Also touches §4.1 (Context Management) through the distributed context preservation mechanism, and §4.7 (Verification) through collaborative failure attribution.
