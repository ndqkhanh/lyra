## 1. Mechanism (Step-by-Step)

BLADE evaluates LM agents on open-ended data-driven scientific analysis through a three-tiered decision representation and automatic matching framework.

### 1.1 Three-Tier Decision Representation

**Conceptual Variables (CVs):**
- Each CV `c ∈ C` is a triplet `(c_desc, c_type, C_cols)` where:
  - `c_desc`: natural language description (e.g., "player physicality")
  - `c_type ∈ {IV, DV, Control}`: variable role in the statistical model
  - `C_cols ⊆ S`: set of column vectors in the final transformed data that operationalize this CV

**Data Transformations (as Bipartite Data Flow Graph):**
- Represented as `G = (T ∪ P, E)` where:
  - `T = {t₁, t₂, ...}`: transform nodes, each defined by a fixed verb from vocabulary `V = {derive, filter, slice, groupby, deduplicate, impute, rollup}`
  - `P = {p₁, p₂, ...}`: column pointer nodes holding column vector values `v_p`
  - `E ⊆ (T × P) ∪ (P × T)`: edges connecting transforms to their input/output columns
- Each transform `t` has input columns `I(t) = {p ∈ P | (p, t) ∈ E}` and output columns `O(t) = {p ∈ P | (t, p) ∈ E}`, with `|I(t)| > 0` and `|O(t)| ≥ 1`
- A set of all alternative graphs `G = {G₁, G₂, ..., Gₙ}` captures multiple justifiable approaches
- Properties: topological sort of any graph yields equivalent results; column-level granularity enables partial credit

**Statistical Models:**
- Each model `m ∈ M` is a tuple `(m_desc, M_cols)` where:
  - `m_desc`: natural language specification (e.g., "logistic regression with log link")
  - `M_cols ⊆ C_cols`: column vectors used, constrained to a single consistent data flow graph (`∃Sᵢ ∈ {S₁, ..., Sₙ} | M_cols ⊆ Sᵢ`)
- Associated CVs derived as: `C_m = {cᵢ | C_cols,ᵢ ∩ M_cols ≠ ∅}`

### 1.2 Two Evaluation Tasks

**Task 1 — Discern Justifiable Decisions (188 MCQs):**
- MCQ1: Given RQ + dataset, identify most/least justifiable conceptual variable
- MCQ2: Given RQ + dataset + CV, identify most/least justifiable transformation to operationalize it
- Negative samples from expert-labeled unjustifiable decisions and mismatched variable transformations

**Task 2 — Generate End-to-End Analysis:**
- Agents submit 3 artifacts: (1) list of conceptual variables with descriptions/types/columns, (2) executable Python `transform(df: pd.DataFrame) -> pd.DataFrame` function, (3) statistical model function
- ReAct agent variant: Up to 10 interaction steps with Python 3.10 sandbox (pandas, sklearn, scipy, statsmodels, numpy, matplotlib, seaborn)

### 1.3 Automatic Matching Engine

**Step 1 — LM-based Conversion (GPT-4o, temperature=0):**
- Transform code → individual transform units (verb + input/output columns), validated at 97% correctness
- Model code → natural language specification + column list, validated at 97% correctness

**Step 2 — Value Matching (Exact):**
- If `v_p = v_p'` (all cell values equal between two column vectors), all transforms in the transitive closure of that column's ancestors are matched: `Match(t) = 1 ∀t ∈ I(p)⁺`
- Captures functionally equivalent transformations with different surface syntax

**Step 3 — Fuzzy Graph Isomorphism Matching:**
- Node label mapping `L: T → V × Pⁿ` captures transform verb + parameter columns
- If subgraph `H(t)` (transitive closure of t and its parents) is isomorphic to `H(t')` including node labels, all contained transforms are matched
- Handles numerical parameter differences (e.g., filter `rpg > 0.5` vs `rpg > 0.45`)

**Step 4 — Semantic Matching for CVs and Models:**
- GPT-4o determines semantic equivalence between concept descriptions (93% validated correctness for CVs, 92% for models)
- Uses Liang et al. (2023) prompting approach with JSON-structured inputs

### 1.4 Evaluation Metrics

- **Average Precision**: `p_avg = (1/n) Σᵢ |Rᵢ ∩ G| / |Rᵢ|`
- **Coverage@k**: `coverage@k = |∪ᵢ₌₁ᵏ Rᵢ ∩ G| / |G|` for k=10
- **F1-score**: `F1 = 2 × (p_avg × coverage@10) / (p_avg + coverage@10)`, bootstrapped 1000 iterations for 95% CIs
- Decision-type weighted F1 for aggregate reporting

## 3. Trade-offs (Wins vs Loses)

| Win | Cost |
|-----|------|
| Automatic evaluation of open-ended analyses eliminates need for human judges post-construction | LM-based evaluation modules (GPT-4o) can hallucinate matches/mismatches (mitigated: 92-97% validated correctness on 615-sample audit) |
| Multi-granularity matching (value exact + graph fuzzy + semantic) awards meaningful partial credit for partially correct pipelines | Significantly complex infrastructure: data flow graph construction, bipartite matching, transitive closure traversal, graph isomorphism checking |
| Decision-based evaluation captures intermediate reasoning quality — not just final-answer correctness | Only covers 3 specific decision types; does not evaluate exploratory data analysis, result interpretation, or hypothesis generation |
| Expert-validated ground truth with multiple justifiable alternatives (536 decisions, 12 datasets, 11 annotators) captures the "forking paths" of real science | Extremely expensive to construct (multi-round annotation, expert co-authors); not easily extensible to new domains |
| ReAct agent interaction consistently improves coverage (diversity) across all decision types | Even the best agent F1-score is only ~45%, leaving enormous headroom; statistical model precision is universally below 35% |
| BLADE correlates with but extends beyond code generation benchmarks (HumanEval) | Coverage/diversity does NOT improve with better code generation — current LM training paradigms may be structurally misaligned |
| Fixed transform verb vocabulary (7 verbs) ensures discrete, matchable decisions | May miss novel transformation strategies not expressible in the predefined verb set |
| Single-table assumption simplifies task formulation | Real scientific analyses frequently require multi-table joins, time series, hierarchical data |

## 4. Design Rationale

The authors chose a **decision-based, multi-alternative evaluation framework** over final-answer benchmarks because scientific data analysis is inherently a "garden of forking paths" — multiple defensible approaches exist involving different variable operationalizations, transformations, and statistical models. A single correct answer would misrepresent the nature of science.

The **bipartite data flow graph** representation was chosen because: (a) any topological sort of a graph yields the same computational result, enabling order-invariant matching; (b) column-level granularity enables partial credit for correct intermediate steps even when later steps fail; (c) graph isomorphism matching handles semantically equivalent transforms with different surface syntax or numerical parameters.

**LM-based semantic matching** (GPT-4o) was chosen over heuristic/rule-based matching because conceptual variables and model descriptions are expressed in natural language requiring semantic understanding that rule-based systems cannot reliably capture. The 92-97% validated correctness was deemed an acceptable trade-off for full automation.

The **ReAct agent** baseline was chosen over more complex architectures to establish a clean, reproducible lower bound, isolating the effect of interactive data exploration from architectural complexity.

## 5. Limitations and Failure Modes

1. **No result interpretation evaluation**: BLADE does not assess whether agents correctly interpret statistical outputs (p-values, coefficients, effect sizes), which is essential for drawing valid scientific conclusions.
2. **Single-table constraint**: All 12 datasets are single tables; real scientific workflows require multi-source joins, time series alignment, and hierarchical data handling.
3. **No exploratory analysis evaluation**: The iterative hypothesis-refinement and data-exploration phase is excluded from the benchmark scope.
4. **LM-based evaluation hallucination**: Despite 92-97% validated correctness on a 615-sample audit, the GPT-4o evaluation modules can still produce incorrect matches or mismatches, introducing systematic measurement error.
5. **Limited domain coverage**: 12 datasets across behavioral science, biology, economics, and education — may not generalize to physical sciences, clinical research, or engineering.
6. **Agent-specific failure modes observed**: (a) hallucinated columns not in the dataset, (b) empty or trivial transform code (especially GPT-3.5, Gemini 1.5 Pro), (c) failure to create composite/derived variables, (d) irrational interaction terms without main effects in regression models, (e) redundant or collinear variable inclusion.
7. **Coverage metric ceiling**: coverage@10 is bounded by the number of expert-annotated alternatives in the ground truth, potentially penalizing genuinely novel but valid approaches not anticipated by annotators.
8. **Temperature 0.8 for generation**: While promoting diversity, this may inflate variance in the F1 estimates despite bootstrapping.

## 6. Transfer to Lyra

**The ONE transferable idea**: BLADE's **column-level data-flow-graph representation with fuzzy graph isomorphism matching** provides a principled mechanism for evaluating multi-step agent pipelines where multiple execution paths can produce equivalent results. For Lyra, this approach can be adapted to verify that generated code/data-transformation pipelines produce semantically correct outputs even when the surface implementation differs from reference solutions — enabling partial-credit scoring for complex, open-ended agent tasks.

**Workstream route**: §4.5 (Verification and Correctness) — BLADE's evaluation framework is fundamentally a verification mechanism for open-ended agent outputs, aligning with Lyra's need for robust, automatic correctness assessment of multi-step agent-generated artifacts.

**Impact**: 3/5 — Provides a validated, publication-quality evaluation methodology with concrete metrics, but requires substantial adaptation from data-science domain to Lyra's general agent-task domain.

**Effort**: 4/5 — Building column-level data flow graphs with fuzzy isomorphism matching for arbitrary Lyra task types would require significant engineering, including a task-specific transform verb taxonomy and graph construction pipeline.

**Tier**: **investigate** — The approach is promising but domain-specific. A prototype targeting Lyra's code-generation verification tasks (e.g., checking that generated SQL/Python transformations produce equivalent DataFrames) would determine transferability before committing to full implementation.
