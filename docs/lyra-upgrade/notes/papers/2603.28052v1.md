# Meta-Harness: End-to-End Optimization of Model Harnesses

**Authors:** Yoonho Lee, Roshen Nair, Qizheng Zhang, Kangwook Lee (Stanford), Omar Khattab (MIT), Chelsea Finn (Stanford)
**arXiv:** 2603.28052v1 [cs.AI], March 30, 2026

## 1. Mechanism (step-by-step)

Meta-Harness is an **outer-loop system that searches over executable harness code** for LLM applications. It treats the harness (the code that determines what to store, retrieve, and present to the model) as the optimization target, using an agentic proposer with full filesystem access to all prior candidates' source code, evaluation scores, and execution traces.

### Core Algorithm (Algorithm 1)

```
Input: tasks X, LLM M, proposer P, iterations N
1. Initialize population H (seeded from baseline harnesses: zero-shot, few-shot, ACE, etc.)
2. Initialize filesystem D ← ∅ (stores code, scores, traces per candidate)
3. For each H ∈ H: Evaluate H on X, store (H, E_H) → D
4. For t = 1..N:
   a. Proposer P queries filesystem D via grep, cat, etc.
      - Reads median 82 files/iteration (41% source code, 40% execution traces, 6% scores)
      - References 20+ prior candidates per step
   b. Proposer proposes k new harnesses {H_1..H_k}
   c. For each H: validate interface, evaluate, store → D
5. Return Pareto frontier from D
```

### Key Design Principles

1. **Full-history filesystem access instead of compressed feedback.** Unlike prior text optimizers (OPRO, TextGrad, GEPA, TTT-Discover), Meta-Harness does not compress feedback into scalar scores or summaries. Every prior candidate gets a directory with source code, scores, and full execution traces. The proposer reads selectively using terminal tools rather than consuming a single monolithic prompt.

2. **Agentic proposer, not raw LLM.** The proposer is a coding agent (Claude Code with Opus-4.6) that can invoke developer tools, navigate the filesystem, read code, grep logs, and edit files. It decides what to inspect and which edits to make — the outer loop imposes no parent-selection rule, no fixed mutation operators, no template filling.

3. **Code-space search with natural regularization.** Harnesses are single-file Python programs modifying task-specific prompting, retrieval, memory, and orchestration logic. Representing harnesses as programs biases the proposer toward coherent algorithms rather than brittle hard-coded solutions.

4. **Domain-specific skill** guides the proposer: defines role, directory layout, CLI commands, output format, and forbidden actions — but leaves diagnosis procedure free.

### Practical Implementation
- Each harness is a single-file Python program
- Evaluation produces up to ~10M tokens of diagnostic information per candidate (3 orders of magnitude beyond prior text optimizers' ~1K–30K token budgets)
- Typical run: ~60 harnesses evaluated over 20 iterations
- Proposer: Claude Code with Opus-4.6
- Lightweight validation test before full evaluation catches malformed candidates

### Concrete Example: TerminalBench-2 Search Trajectory

Iterations 1-2: Proposer bundled structural fixes with prompt edits → both regressed
Iteration 3: Proposer identified confound — shared prompt intervention was the common factor, not the structural fixes. Tested structural fixes alone → smaller regression, confirming diagnosis.
Iterations 4-6: Continued probing completion logic, all regressed.
Iteration 7: Proposer pivoted to purely additive modification (environment bootstrapping) — "avoid touching previously fragile completion machinery." This became the best candidate.
Iterations 8-10: Composition of winning idea with earlier fixes, cross-run transfer.

This demonstrates **causal reasoning over prior failures** enabled by full-history access.

## 3. Trade-offs

| Win | Loss |
|-----|------|
| 10x faster convergence (4 evals vs 40) | ~500x more diagnostic tokens per evaluation (10M vs 20K) |
| +7.7 acc with 4x fewer context tokens on text classification | Requires strong coding agent proposer (became practical only ~2026) |
| +4.7 pts avg across 5 unseen models in math | Search cost scales with evaluation cost; each candidate needs full eval |
| Beats hand-engineered harnesses on competitive TerminalBench-2 | TerminalBench-2 uses same split for search/eval (discovery problem; risk of benchmark overfitting) |
| Harnesses are readable Python (100-1000 lines), inspectable for overfitting | Only tested with one proposer (Claude Code Opus-4.6); effect of proposer choice is unknown |
| Transfers to OOD datasets and unseen models | Proposer reads median 82 files/iteration — significant overhead for simple tasks |
| Pareto frontier enables accuracy-context trade-off selection | No co-evolution of harness + model weights (future work) |
| Minimal outer-loop structure; improves automatically as coding agents get stronger | Relies on agent forming correct causal hypotheses from traces; misdiagnosis compounds |

## 4. Design Rationale

The central thesis: **compressed feedback destroys the diagnostic information needed for harness engineering.** Harnesses act over long horizons — a single choice about what to store, retrieve, or present can affect behavior many reasoning steps later. Scalar scores and summaries remove the signal needed to trace downstream failures to upstream design decisions.

Filesystem access lets the proposer **decide what to inspect** rather than having information preselected by a fixed outer-loop structure. This matters because the relevant diagnostic information varies by failure mode: sometimes it is in code, sometimes in execution traces, sometimes in cross-candidate comparison.

The choice of a coding agent (not raw LLM) is deliberate: the proposer must retrieve information, navigate artifacts, and edit code as part of the search itself. Coding agents are trained on read-write-execute workflows that naturally align with this pattern. The outer loop is deliberately minimal (no fixed mutation operators, no parent-selection rules, no archive structures) so the proposer's capability ceiling rises automatically with coding agent progress — following Sutton's "Bitter Lesson" principle that general-purpose search with scale beats hand-crafted structure.

## 5. Limitations & Failure Modes

1. **Single proposer dependency:** All experiments use Claude Code with Opus-4.6. Unknown how results vary with weaker proposers (GPT-OSS, Gemini) or future agents. A weaker proposer might fail to form causal hypotheses from traces and produce random-walk search behavior.

2. **TerminalBench-2 discovery problem:** Same 89-task set used for both search and evaluation. While standard practice for this benchmark, and the authors checked for task-specific string leakage via regex audits, benchmark overfitting remains a risk. Cross-benchmark transfer not demonstrated for coding domain.

3. **Diagnostic volume scaling:** Each evaluation produces up to ~10M tokens of diagnostic data. For longer-horizon tasks (multi-day agents), the trace volume could become intractable even for filesystem-based access.

4. **Causal misdiagnosis risk:** The proposer can form incorrect causal hypotheses from traces. The TerminalBench trajectory shows correct diagnosis after 2 regressions, but more complex failure modes could lead to extended dead ends. No mechanism to detect or recover from systematic proposer errors.

5. **Compute cost:** Each iteration requires full evaluation of k candidates. With expensive benchmarks (e.g., SWE-bench at ~$100/task), the search cost could be prohibitive. The authors note evaluation is the main bottleneck.

6. **No co-evolution with model weights:** Harness and model are optimized independently. If the harness exploits model-specific weaknesses, it may not transfer (though math results show cross-model transfer does occur).

7. **Skill engineering overhead:** The domain-specific skill (proposer instructions) is the "strongest lever" on search quality and requires manual iteration. Search quality is sensitive to skill quality — poorly written skills yield poor search.

8. **Validation limited to 3 domains:** Text classification, math reasoning, agentic coding. Behavior in other domains (multimodal, long-document QA, real-time systems) unknown.

## 6. Transfer to Lyra

### The One Transferable Idea

**Replace Lyra's hand-tuned prompt construction, memory management, and retrieval logic with an agentic outer-loop search that uses filesystem-accessible execution traces to optimize harness code automatically.** The key insight: give a coding agent (Claude Code / Opus) full access to Lyra's prior execution traces, scores, and internal harness source code, then let it propose targeted harness edits based on causal diagnosis of failures rather than scalar reward gradients. This is directly applicable because Lyra already has a modular harness (the `src/` directory), produces execution traces, and uses a coding agent as its base model.

### Workstream Route: §4.1 Harness Engineering (primary) and §4.2 Memory & Context Management (secondary)

Meta-Harness directly addresses Lyra's need to optimize:
- Prompt construction strategies (§4.1)
- Retrieval policies and memory update rules (§4.2)
- Context budget allocation across the agent loop (§4.2)
- Tool-use orchestration logic (§4.1)

The discovered patterns (draft-verification loops, label-primed query anchoring, domain-routed retrieval, environment bootstrapping) are directly transferable as seed harnesses for Lyra's analogous subsystems.

### Assessment

| Dimension | Score | Rationale |

| Effort | 4 | Requires building evaluation infrastructure for Lyra tasks, writing domain-specific skills, integrating filesystem-based trace logging, and running ~60-iteration search loops |

### Concrete Next Steps for Lyra
1. Define Lyra's harness interface: a single-file Python class with standard `build_prompt()`, `update_memory()`, `should_retrieve()` methods
2. Build evaluation infrastructure: release 50-100 Lyra task instances as a search set with scoring
3. Write a Lyra-specific Meta-Harness skill for the proposer
4. Seed with Lyra's current hand-engineered harness as baseline
5. Run ~20 iterations, select Pareto-optimal harness, evaluate on held-out tasks
