## 1. Mechanism (step-by-step)

### Problem Formulation
Given a labeled tabular dataset D = (X, y) with X in R^{m x n}, the goal is to find a transformation function T: X -> X_tilde where X_tilde = X union T(X) that maximizes validation performance of a downstream model f.

### Multi-Agent Architecture (Agent Pool)
MALMAS decomposes feature generation into 6 specialized agents spanning three orthogonal dimensions from feature engineering practice (transformation complexity, data scope, data-type dependency), inspired by the "golden features" categorization (Zhang et al., 2024):

- **A1 — Unary-Feature Agent:** Applies unary transformations f_unary(X) to individual features (e.g., log, sqrt, binning)
- **A2 — Cross-Compositional Agent:** Combines multiple inputs f_compositional(X) to capture higher-order interactions (e.g., feature ratios, products)
- **A3 — Temporal-Feature Agent:** Extracts temporal patterns f_temporal(X) for time-series columns
- **A4 — Aggregation-Construct Agent:** Generates group-level summary features f_aggregation(X) (e.g., group-by mean, count, std)
- **A5 — Local-Transform Agent:** Applies region-specific transformations f_local-transform(X) to capture locally informative patterns
- **A6 — Local-Pattern Agent:** Discovers latent patterns via clustering or local interaction modeling f_local-pattern(X)

### Iterative Generation Algorithm (Algorithm 1)

For each round r = 1,...,R (R=4 in experiments):

1. **Routing:** A Router Agent selects an active subset A^(r) from the full agent pool A based on task metadata M and GlobalMem^(r-1).

2. **Parallel Generation:** Each active agent A_i in A^(r):
   - Constructs a role-specific prompt from metadata M, effective features from FeedMem^(r-1), and distilled guidance from ConMem^(r-1) and GlobalMem^(r-1)
   - Uses LLM π_θ to propose transformation f_i^(r)
   - Instantiates and evaluates resulting features under metric E
   - Stores feedback in FeedMem_i^(r)

3. **Memory Update:**
   - **Procedural Memory:** ProcMem_i^(r) = {(base_cols, transform_type, feature_name, description, round)} — records what was tried, suppresses duplicates
   - **Feedback Memory:** FeedMem_i^(r) = {(feature_name, metric, value, is_effective, round)} — utility attribution linking each feature to validation gain
   - **Conceptual Memory:** ConMem_i^(r) = LLM(ProcMem_i^(r), FeedMem_i^(r)) — distills reusable heuristics

4. **Global Consolidation:** A Summary Agent aggregates local memories across all active agents:
   Mem^(r) = Union of (ConMem_i^(r) union FeedMem_i^(r)) across A^(r)
   GlobalMem^(r) = Summary(Mem^(r))

5. **Feature Selection:** TopN-Features selects best-performing features from all agents' outputs; selected features are merged into the dataset for the next round:
   X^(r+1) = X^(r) union S^(r), where S^(r) = TopN(T^(r), F^(r))

### Key Design Elements
- The Router activates ~4 agents per round on average (adaptive subset, not all-or-nothing)
- Each agent maintains its own local memory; the Summary Agent creates shared global memory
- Conceptual memory compresses verbose traces into compact rules, keeping prompts concise
- The system uses DeepSeek-V3 as the default LLM backbone

## 4. Design Rationale

**Why multi-agent?** Single-agent LLM approaches (CAAFE, OCTree) use rigid, static generation strategies that homogenize feature exploration. Decomposing feature engineering into orthogonal dimensions (unary, compositional, temporal, aggregation, local) forces complementary search, reducing functional redundancy and expanding the overall feature space.

**Why memory?** Without feedback-driven signals, feature generation becomes disconnected from downstream performance — an inefficient, trial-and-error process. Three memory types each solve a distinct problem: procedural memory prevents redundant exploration (what was tried), feedback memory enables credit assignment (what worked), and conceptual memory provides compact reusable heuristics (why it worked). The global memory propagates insights across agents.

**Why router?** Running all 6 agents every round wastes tokens on inapplicable strategies. The router adaptively selects ~4 agents per round based on task metadata and accumulated memory, achieving comparable performance to full activation while reducing token consumption (~148k vs ~173k tokens). Dynamic scheduling improves efficiency — more agents early for exploration, fewer later for refinement.

## 5. Limitations & Failure Modes

1. **Label dependency:** MALMAS requires labeled data for validation feedback. Effectiveness degrades when labels are scarce or evaluation budgets are limited. No support for unsupervised or self-supervised feature generation.

2. **Tabular-only:** Designed exclusively for tabular data. Applicability to text, image, graph, or multimodal feature engineering is unexplored.

3. **Computational bottleneck at scale:** As the candidate feature pool grows, repeated downstream training + validation (XGBoost per round per candidate) becomes expensive. Performance is sensitive to available evaluation budget.

4. **Non-monotonic agent addition:** Adding agents does not guarantee monotonic improvement — A2->A3 shows a mean rank regression (3.69->3.88), suggesting certain agent combinations can introduce noise that displaces robust features under fixed top-N selection.

5. **LLM backbone sensitivity:** GPT-4.1-mini (smaller model) produces mean rank 1.37 vs DeepSeekV3's 1.12, and the gap between LLM-based methods narrows — indicating that weaker reasoning models constrain semantic transformation quality.

6. **Interpretability not guaranteed:** While MALMAS provides transformation descriptions and memory traces, the LLM-driven generation process does not guarantee full interpretability of every derived feature.

7. **Bias amplification risk:** Downstream evaluation may inadvertently favor transformations that correlate with sensitive attributes. Schema constraints and fairness audits are recommended but not built into the framework.

8. **Diminishing returns:** Performance plateaus at R=3-4 rounds. No adaptive stopping criterion — fixed R=4 may be suboptimal for simpler datasets.

9. **Leakage risk:** May propose invalid or data-leaking features if the schema is ambiguous or the data pipeline is misconfigured. Execution-time validation recommended.

## 6. Transfer to Lyra

### The ONE Transferable Idea
**Multi-level agent memory with explicit credit assignment for iterative refinement.** MALMAS shows that separating memory into three types (procedural traces, feedback utility, conceptual heuristics) and consolidating them into a shared global memory through a Summary Agent enables cumulative improvement across rounds. Lyra's agent loops could adopt this tripartite memory architecture: procedural memory to avoid duplicating failed tool calls, feedback memory to attribute task success to specific actions, and conceptual memory to distill reusable patterns — all consolidated by a Summary Agent into a shared context for subsequent interactions.

### §4 Workstream Route
- **Primary:** §4.2 (Memory & Context Management) — The structured memory hierarchy directly informs Lyra's context architecture
- **Secondary:** §4.1 (Agent Architecture) — The Router + Specialized Agent Pool + Summary Agent pattern maps to Lyra's multi-agent orchestration

### Impact / Effort / Tier
- **Impact:** 4 — Significant because Lyra currently lacks cross-turn memory with explicit credit assignment; this would enable progressive improvement rather than isolated per-turn interaction
- **Effort:** 4 — Requires designing three memory stores, a Summary Agent, and integration with existing agent loops; non-trivial but the paper provides clear schemas
- **Tier:** Breakthrough — Addresses a core architectural gap (feedback loops) that current Lyra design docs acknowledge as unsolved
