## 1. Mechanism

OPEN JARVIS introduces two core innovations: the **spec abstraction** and **LLM-guided spec search**.

### 1.1 Five-Primitive Spec Architecture

A personal AI system is decomposed into five typed, independently swappable primitives composed into a declarative `Spec`:

```
Spec S := {
  Intelligence: (model, params, quant)      // LM architecture + weights
  Engine:       (backend, batch, kv_cache)   // Inference runtime
  Agents:       (loop, prompts, tool_strategy) // Reasoning loop
  Tools & Memory: (set, descriptions, memory)  // Data integration + storage
  Learning:     (optimizer, reward, gate)    // Optimizer that updates the spec
}
```

Each primitive is an **independent degree of freedom**. Prior systems hardcode 2-3 of these while exposing only 1-2 for tuning. The spec makes all five editable fields of a single optimizable object. On disk, the spec serializes to TOML. Primitives communicate through a thread-safe publish-subscribe EventBus.

### 1.2 LLM-Guided Spec Search (Algorithm 1)

A local-cloud collaboration: frontier cloud models propose edits at search time; the resulting spec runs entirely on-device at inference time.

**Greedy gated search loop:**

```
Require: Spec S0, teacher T, gate G, regression tolerance ε, budget B
1: S ← S0
2: while not converged and cost < B do
3:   C ← T.diagnose(traces(S))                    // Cluster failure modes
4:   e ← T.propose(S, C)                           // Propose edits across any primitive(s)
5:   S' ← apply(S, e)
6:   if GateOK(S', S, C, ε) then
7:     S ← S'                                       // Greedy accept
8:   end if
9: end while
10: return S
```

**Gate condition:** For an edit targeting failure cluster c:

```
G_c(S') > G_c(S)   AND   G_c'(S') ≥ G_c'(S) − ε  ∀c' ≠ c
```

Default ε = 1%. This single rule applies across all four editable primitives.

**Four phases per search step:**
1. **Diagnose:** Teacher LM ingests traces, groups by failure mode into clusters annotated with student vs. teacher success rates and natural-language skill-gap characterization (e.g., "student fails on multi-hop questions requiring calendar lookups because it does not invoke the calendar tool").
2. **Plan:** Teacher proposes edits targeting specific primitives — Intelligence (model switch, quantization, LoRA/GRPO training trigger), Engine (backend switch, batch size, KV-cache), Agents (system prompt, few-shot exemplars, agent type, turn limits), Tools & Memory (tool add/remove, description rewrite, memory backend change).
3. **Execute:** Evaluate each edited spec on held-out gate built from benchmark splits, agentic datasets (GeneralThoughtArchive, ToolScale), and user-approved scrubbed traces.
4. **Commit:** Accept only gated improvements; log rejected edits.

**Composite reward for Intelligence training edits (Equation 1):**

```
R(q, y) = α·R_acc(q, y) − β·Ê(q, y) − γ·L̂(q, y) − δ·Ĉ(q, y)
```

Default weights: (α, β, γ, δ) = (0.5, 0.1, 0.1, 0.3). All efficiency quantities normalized to dimensionless z-scores per benchmark.

**What runs where:** At inference time, model inference and agent execution run on-device. Teacher calls provide diagnoses, proposals, and labels only during the bounded search phase. Cloud-as-tool is disabled in headline local configurations. Intelligence training (LoRA/GRPO) also runs locally.

### 1.3 Baselines for Comparison

- **Evolutionary spec search (Algorithm 2):** Population-based reflective mutation with Pareto-frontier maintenance and merge (extends GEPA to four-primitive space). Same edit catalog, trace corpus, gate, budget.
- **Single-component optimizer (Algorithm 3):** Restricted to one primitive type (prompt-only or weight-only). DSPy, prompt-only GEPA, SFT, LoRA.
- **Template-random proposer:** Samples edit templates from catalog uniformly, uses same gate. No trace diagnosis. Isolates whether gains come merely from the catalog + gate.

### 1.4 Evaluation Architecture

Each spec is evaluated via an instrumented wrapper recording five per-query quantities: accuracy, energy (joules, via vendor APIs), latency (wall-clock seconds), power (watts), and dollar cost ($). Energy for cloud baselines estimated from datacenter-level figures. All measurements at batch size 1 (interactive personal-AI workload).

## 3. Trade-offs

| Win | Lose |
|-----|------|
| **~800× lower marginal API cost** ($0.001 vs $0.009/query) | **3.2 pp accuracy deficit** (best local 80.3% vs. cloud 83.5%) |
| **~4× lower end-to-end latency** for agentic workloads | **13.8 pp gap** on τ²-Bench Telecom; **15.4 pp gap** on DeepResearchBench |
| **Privacy by architecture**: no data leaves device during inference | **Cloud teacher required at search time** ($15.6/benchmark) — amortizes but not zero |
| **Offline capability** — no network dependency for inference | **Single-machine eval only** — multi-tenant/distributed untested |
| **1–20× lower energy per query** | **Hardware upfront cost** ($599–$8,900) replaces recurring API spend |
| **LLM-guided search closes 13–32 pp** of local-cloud gap | **Composite reward trades ~2.4 pp accuracy** for energy/latency/cost Pareto |
| **7–11× lower optimization cost** than single-primitive baselines | **Search convergence**: k=5 stagnation may hit local optima (1.2 pp gap to Best-of-5) |
| **No single-primitive dependency** — edits span all 4 editable primitives | **GPT-5-mini judge bias** may inflate GPT-family scores |
| Local models match/exceed cloud on **4 of 8 benchmarks** | **GAIA deep reasoning** remains hard for ≤9B models regardless of configuration |
| **TOML serialization** enables versioning, sharing, reproducibility | **Terms of service risk**: cloud teacher APIs may restrict training competing models |

## 4. Design Rationale

**Why decompose into five typed primitives?** Existing personal AI stacks (OpenClaw, Hermes Agent, LangChain, CrewAI) hardcode prompts, tool descriptions, memory configuration, and runtime settings for their intended cloud model. When a local model is substituted, all these co-adapted components break simultaneously. Exposing each as an independently editable typed slot in a unified spec makes the breakage visible and fixable. This is analogous to how imperative deep learning frameworks (PyTorch) unified model construction by making layers composable — the spec unifies personal AI stack construction by making primitives composable.

**Why LLM-guided spec search over single-primitive optimization?** Prompt-only optimizers (DSPy, GEPA) close only ~5 pp of the local-cloud gap because they cannot change the model, runtime, or tool configuration. Weight-only optimizers (LoRA, SFT, GRPO) cannot fix misaligned prompts, tool descriptions, or engine settings. The useful intervention depends on the failure mode (retrieval→Tool edits, reasoning→Intelligence edits, control-flow→Agent edits, efficiency→Engine edits), and many failures require coordinated changes across primitives. LLM-guided spec search exploits this coupling: a single proposal can simultaneously rewrite a tool description AND adjust model weights against the resulting prompt.

**Why cloud-at-search-time, local-at-inference-time?** Frontier cloud models excel at reading traces and reasoning about coordinated edits but cost $0.009/query and require data transmission. Local models have low latency, zero marginal API cost, and privacy, but cannot self-improve across primitives. The division of labor captures the best of both: capability flows from cloud to local through the optimized spec and stays there, making zero cloud calls at inference time.

**Why a greedy gated acceptance with ε=1% regression tolerance?** The gate prevents optimization from degrading already-working capabilities while allowing the system to accept edits that improve a targeted failure cluster. This is more sample-efficient than population-based approaches (evolutionary) because rejected edits don't trigger expensive training runs, and accepted edits compound across sessions. The per-cluster gate (rather than a global accuracy threshold) enables fine-grained targeted improvements.

## 5. Limitations & Failure Modes

1. **Benchmark ceiling effects:** PinchBench saturates at 100% for both cloud and multiple local models. The tie reflects ceiling rather than true parity. Not weighted heavily in headline claims.

2. **Cloud baseline anomalies:** Some cloud models exhibit unexpectedly low scores on specific benchmarks (attributed to incomplete tool integration in the evaluation harness, not model failure). Anchored by Claude Opus 4.6 and GPT 5.4.

3. **Statistical precision:** Five runs per configuration provide limited precision for sub-5 pp accuracy differences. The 3.2 pp average cloud-local gap should be interpreted with this in mind.

4. **LLM judge bias:** GPT-5-mini as judge may systematically favor GPT-family outputs. No cross-judge validation with Claude or human raters has been conducted. However, Claude Opus 4.6 is the strongest teacher on LiveCodeBench despite the GPT-family judge — the inverse of the direction judge bias would predict.

5. **Single-machine evaluation:** All hardware results collected on single-machine deployments. Distributed or multi-tenant configurations not evaluated.

6. **Search convergence:** k=5 stagnation stopping condition may produce local optima. Best-of-5 restarts improve by only 1.2 pp on average, suggesting the greedy search space is well-behaved, but no formal convergence guarantee exists.

7. **Reward weight sensitivity:** Composite reward weights (0.5, 0.1, 0.1, 0.3) are defaults, not fully swept. Accuracy-only (α=1) configuration reaches 2.4 pp higher accuracy, which the composite reward deliberately trades for better efficiency Pareto.

8. **Teacher API ToS:** Frontier cloud models used as teachers (GPT 5.4, Claude Opus 4.6, Gemini 3.1 Pro) may have terms of service restricting the use of outputs to train competing models. The paper notes that most edits update Agent/Tool/Engine fields rather than training a competing foundation model, and Intelligence edits train only small adapters (LoRA) on open-weight models.

9. **Local-teacher fallback not quantified:** Users can substitute a larger local model as the teacher for strict local-only operation, but the resulting accuracy and convergence tradeoff is not evaluated.

10. **Dual-use risk:** General-purpose agent framework could automate harmful tasks (spam, social engineering, scraping). Security layer provides prompt injection detection, SSRF protection, sandboxed code execution, and PII scanning, but these are mitigations, not guarantees.

## 6. Transfer to Lyra

### The One Transferable Idea

**The spec abstraction as a typed configuration object over agent primitives, with failure-cluster-driven cross-primitive optimization.** Lyra should adopt OPEN JARVIS's insight that agent prompts, tool descriptions, memory configuration, model selection, and inference runtime are coupled degrees of freedom that must be jointly optimizable. The key mechanism: a typed Spec object where each slot (Model, Runtime, Agent Loop, Tools, Memory, Optimizer) is an independently swappable field, enabling a teacher model (or Lyra's orchestration layer) to propose coordinated edits across slots based on diagnosed failure clusters, with a held-out gate accepting only non-regressing improvements.

### Workstream Route

**§4.2 — Agent Architecture (primary)** and **§4.5 — Tool & Memory System (secondary)**.

Rationale: The spec directly addresses Lyra's agent architecture by providing a typed decomposition of the agent stack. The failure-cluster-driven optimization loop maps onto Lyra's verification and self-improvement workstreams. The Tools & Memory primitive maps to Lyra's tool orchestration and retrieval layers.
