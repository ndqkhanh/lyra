**arXiv:** 2605.15184v1 (14 May 2026)
**Venue:** Preprint (no conference venue stated)

## 1. Mechanism (step-by-step)

### Core Research Question

Does the choice of retrieval strategy (lexical grep vs. semantic vector search) interact systematically with agent architecture and tool-calling paradigm, or are these dimensions independent? The paper runs two factorial experiments to answer this.

### Experimental Setup

**Dataset:** 116-question representative subset of LongMemEval-S, spanning 6 task categories:
- **KU** (knowledge-update): Tracking state changes over time
- **MS** (multi-session): Aggregating info across sessions
- **SS-A** (single-session-assistant): Recalling model-generated content
- **SS-P** (single-session-preference): User personal preferences
- **SS-U** (single-session-user): User-stated facts
- **TR** (temporal-reasoning): Computing durations, ordering events, resolving dates

Each question has ≥1 oracle sessions containing necessary evidence, plus variable distractor sessions. Per-question haystacks range from 39–66 sessions at "full" configuration.

**Corpus Preprocessing:** Chronos pipeline extracts structured temporal events (dates, intervals, time spans) from raw transcripts and serializes them alongside dialogue turns into per-question JSON files. This mirrors production long-memory agent configurations.

### Retrieval Implementations

**Grep (Lexical):**
- Loads per-question conversation turns + temporal events into memory
- Executes regex matching over raw text fields
- Scores results by match count
- No embedding model, vector index, or external service required
- All matching performed in-process over local files

**Vector (Semantic):**
- Embeds each conversation turn and temporal event at ingestion time
- Stores in per-question ANN index with versioned schema
- At query time: embed natural language query → ANN search → reranking step → return top-k results (k chosen by agent)

### Agent Harnesses

**Custom (Chronos):**
- LangChain-based agent with 4 search tools (grep/vector over turns and events)
- Dynamic prompting: system instructions, search hints, tool-use guidance conditioned on detected question category
- Initial broad context block (top-15 vector results) before tool-calling loop begins
- Loop continues until model produces final answer

**Provider-Native CLIs:**
- Claude Code (Anthropic), Codex CLI (OpenAI), Gemini CLI (Google)
- Each receives question + dynamically generated search strategy
- Invoke bash-callable wrapper scripts for grep and vector search via absolute paths
- Sandboxed execution in standard mode

### Tool-Calling Architectures

**Standard (Inline):**
- Search results returned directly as tool response messages in conversation context
- Model receives full result set within context window
- Simpler but creates context pressure with large result sets

**Programmatic (File-Based):**
- Search results written to disk
- Agent receives only a file path or summary pointer
- Must execute explicit action (grep/cat/read_file) to access results
- Decouples result size from context window pressure
- Enables agent-driven post-retrieval filtering (progressive disclosure)

### Models Evaluated

Claude Opus 4.6, Claude Haiku 4.5, GPT-5.4, Gemini 3.1 Pro, Gemini 3.1 Flash-Lite

### Evaluation Protocol

GPT-4o as grader; binary judgment per question under category-conditioned instructions (off-by-one tolerance for temporal counts, rubric scoring for preferences, abstention handling). Accuracy = fraction of questions with affirmative grader judgment.

### Experiment 1 Design

Full factorial: Retrieval mode (grep-only vs. vector-only) × Harness (Chronos/Claude Code/Codex/Gemini CLI) × Tool calling method (inline vs. programmatic) × Model (5 LLMs). All at full haystack.

### Experiment 2 Design

Paired grep-only and vector-only accuracy across increasing session limits (s5, s10, s20, s30, full). Oracle sessions always retained; remaining slots filled with distractors sampled from other sessions in the same per-question bundle. Same distractor sets for grep and vector within each configuration.

**Key findings from Table 1:**
- Inline grep exceeds inline vector for **every single harness-model pair** (10/10)
- Largest margin: Chronos + Gemini 3.1 Flash-Lite (86.2% vs. 62.9% = Δ23.3pp)
- Narrowest margin: Claude Code + Claude Opus 4.6 (76.7% vs. 75.0% = Δ1.7pp)
- Same model (Claude Opus 4.6): Chronos 93.1% vs. Claude Code 76.7% — a Δ16.4pp gap from harness alone
- Programmatic delivery reorders grep-vs-vector: vector wins on 5/10 pairs under programmatic mode
- Codex/GPT-5.4 programmatic grep collapse: 93.1% → 55.2% (Δ37.9pp drop just from switching delivery mode)

## 3. Trade-offs

| Dimension | Lexical (Grep) Wins | Dense (Vector) Wins |
|---|---|---|
| **Accuracy (inline)** | Higher on every harness-model pair (Table 1) | Only wins under programmatic delivery on 5/10 pairs |
| **Context scaling** | Stable or rising with more sessions (e.g., Claude Code Opus: 91.4→94.0%) | Often peaks early then degrades (Chronos Opus: 94.8%→84.5% mid-grid dip) |
| **Weaker models** | Smaller gap: Haiku grep 55.2% vs. vector 44.0% (+11.2pp) on Claude Code | Hurts weaker models disproportionately |
| **Setup cost** | Zero: no embedding model, no vector index, no external service | Requires embedding pipeline, ANN index, reranker |
| **Latency/cost** | Negligible (in-process regex) | Embedding + ANN + rerank compute cost |
| **Paraphrase recovery** | Brittle to vocabulary mismatch — if agent never guesses the right substring, nothing retrieved | Can surface semantically related passages even with different wording |
| **Precision at scale** | Ruthlessly precise when pattern matches exist; discriminative substring → exact hit | Admits topical "false friends" — distractor sessions that share topic overlap |
| **Small corpus (s5)** | Often behind vector at low session counts | Stronger at low noise: Chronos Opus vector 94.0% vs. grep 89.3% at s5 |
| **Harness sensitivity** | Large: same model varies 16.4pp across harnesses | Also large but different pattern: some harnesses favor vector throughout |
| **Programmatic delivery** | Codex/GPT-5.4 collapses from 93.1% to 55.2% | More resilient to programmatic delivery on some pairs |

## 4. Design Rationale

The paper's core insight is that **retrieval strategy, agent harness, and tool-calling method form a single jointly-determined system** — not independent design choices. The authors choose a factorial design (not ranking-only comparison) because:

1. **Analogy to compiler optimization:** Just as compiler flags interact with hardware, retrieval gains interact with the agent shell that translates retrieved hits into reasoning tokens. A ranking metric (nDCG, MRR) in a static pipeline cannot capture this.

2. **LongMemEval as task:** Selected because answers often license on verbatim spans (dates, counts, preferences) that are stable under tokenization. This is a deliberate stress test — if lexical tools cannot win here, they probably cannot win anywhere. The authors are explicit that this task distribution favors lexical methods.

3. **File-based delivery as a stress test:** Programmatic routing tests whether the agent can reliably execute multi-step workflows (search → write → read → integrate → answer). It separates "retrieval quality" from "tool-use competence," exposing failure modes invisible in inline-only evaluations.

4. **Scaling study as interaction test:** Rather than claiming "grep beats vector at scale," the scaling experiment reveals the *crossover* behavior: vector often leads at low session counts, but the crossing point depends on harness + backbone, not corpus size alone.

## 5. Limitations & Failure Modes

1. **Task specificity:** Conclusions are tied to long-memory conversational QA with literal evidence. In domains where answers require synthesis over paraphrased abstracts (scientific literature), visual-heavy documents, or code semantics, dense retrieval and hybrid routing may dominate. The authors explicitly disclaim "grep beats vector in general."

2. **Single corpus:** Only LongMemEval-S. No evaluation on BEIR, narrative QA, or multi-hop reasoning benchmarks. Generalizability to non-chat corpora is unknown.

3. **Incomplete scaling rows:** Codex vector intermediate configurations are pending; no Codex grep scaling row exists. Cannot state a vendor-complete picture of CLI grep vs. vector under matched noise caps.

4. **No hybrid retrieval evaluation:** Despite discussing RRF and hybrid approaches in the literature review, experiments only compare grep-only vs. vector-only. The most practically interesting configuration — agents choosing between both tools dynamically — is not tested.

5. **Stochastic distractor sampling:** Session-limit curves are not smooth capacity laws. Mid-grid peaks may reflect favorable distractor samples rather than inherent scaling properties. The paired comparison within each configuration is valid, but extrapolation to monotone scaling is not warranted.

6. **No trace-level causal attribution:** Cannot attribute accuracy differences to specific mechanism (query formulation quality, retrieved set composition, agent's reading behavior, or stop-condition decisions). The paper can only report end-to-end scores, not why they differ.

7. **Grader reliability:** Single GPT-4o grader, no inter-annotator agreement or human validation of binary judgments reported. Category-conditioned instructions mitigate but do not eliminate grader bias risk.

8. **Commercial model versions:** Model names (GPT-5.4, Gemini 3.1 Pro/Flash-Lite) are version-locked. Results may not transfer to future model releases or fine-tuned variants.

## 6. Transfer to Lyra

### The One Idea

**Agent harness architecture is NOT passive infrastructure for retrieval — it is a first-class design variable that can invert the lexical-vs-semantic accuracy ordering.** The same underlying model operating over byte-identical text corpora can vary by 16+ percentage points depending solely on harness, system prompt, tool descriptions, and output delivery path. For Lyra, this means: when designing the tool-calling loop, treat retrieval strategy selection, harness scaffolding, and result delivery format as a single joint design problem. Specifically, Lyra should implement **both grep and vector tools** (not default to vector-only) and let the agent route between them based on query type, while carefully engineering the tool-output delivery path (inline vs. file-based) based on the agent's demonstrated ability to close multi-step read-integrate loops.

### Route to Workstream

**§4.2 (Context Engineering & Tool Surface)** — This finding directly impacts how Lyra constructs tool definitions, formats tool outputs, and manages context pressure. It also has implications for §4.3 (Memory & Retrieval) regarding when to prefer lexical over dense retrieval for long-horizon conversation memory.

### Impact Assessment

| Dimension | Score | Rationale |
|---|---|---|
| **Impact** | 4/5 | Fundamentally challenges the "default to vector" assumption in most RAG systems; demonstrates harness architecture as a first-class variable with effects as large as swapping retrieval methods |
| **Effort** | 2/5 | Adding grep as a tool and tuning tool-output delivery is low-engineering-effort; the main cost is evaluation rigor across harness configurations |
| **Tier** | **Breakthrough** | The finding that harness can invert retrieval ordering (16pp swings) is not incremental — it changes how agent builders should think about retrieval architecture |
