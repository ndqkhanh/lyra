## 1. Mechanism (Step-by-Step)

### Problem Formulation
Binary routing between a **strong model** M_s (e.g., GPT-4, high quality, high cost) and a **weak model** M_w (e.g., Mixtral-8x7B, lower quality, lower cost). Given a query q, the router R^α selects which model to invoke.

### Win Prediction Model
A model P_θ(wins|q) estimates the probability that the strong model will outperform the weak model on query q. Trained by maximizing likelihood of human preference data:

```
max_θ Σ_{(q, l_{s,w}) ∈ D_pref} log P_θ(l_{s,w} | q)
```

where l_{s,w} ∈ {win_s, tie, win_w} from pairwise human judgments.

### Routing Decision with Cost Threshold α
```
R^α(q) = M_weak   if P(wins|q) < α
         M_strong if P(wins|q) ≥ α
```
α ∈ [0,1] controls the quality-cost trade-off: higher α favors cheap weak models, lower α favors expensive strong models.

### Data Source
Primary data: **Chatbot Arena** — 80k human-judged battles, 65k usable pairwise comparisons across 64 models, 100+ languages (81% English). Models clustered into 10 tiers via dynamic programming on leaderboard scores. Strong models = top 2 tiers; weak models = tier 3.

**Key challenge:** Label sparsity (<0.1% comparison labels between any two model pairs). Addressed by model tiering.

### Data Augmentation (Two Methods)
1. **Golden-labeled datasets (D_gold):** MMLU validation split (~1,500 MCQs). Compare model responses to known correct answer to derive comparison labels l_{s,w}.
2. **LLM-judge-labeled datasets (D_judge):** GPT-4-as-a-judge on open-ended queries. Used Nectar dataset queries with existing GPT-4 responses, generated Mixtral-8x7B responses, and had GPT-4 judge the pairs. ~120K samples at ~$700 total cost.

### Four Router Architectures

#### A. Similarity-Weighted (SW) Ranking (Bradley-Terry)
- **No training required** — inference-time only.
- Embed queries with `text-embedding-3-small`.
- Cosine similarity S(q, q') between test query q and each training query q', scaled by max similarity in dataset:

```
S(q, q') = (ϵ·ϵ') / (||ϵ||·||ϵ'|| · max_{1≤s≤|D_pref|} (ϵ'·ϵ_s)/(||ϵ'||·||ϵ_s||))
```

- Weight scalar: ω' = γ^{1+S(q,q')} with γ = 10 (exponential scaling).
- Learn BT coefficients ξ_s, ξ_w by minimizing weighted BCE loss:
```
argmin_{ξ_s, ξ_w} Σ ω' · ℓ(l_{s,w}, 1/(1 + e^{ξ_s - ξ_w}))
```
- Win probability: P_θ(wins|q) = 1/(1 + e^{ξ_s - ξ_w})

#### B. Matrix Factorization (Recommender-System Inspired)
- Hidden scoring function δ: M × Q → R using bilinear form:

```
δ(M, q) = w_2^T (v_m ⊙ (W_1^T v_q + b))
```

where v_m ∈ R^{d_m} (model embedding), v_q ∈ R^{d_q} (query embedding), W_1 ∈ R^{d_q × d_m} and b ∈ R^{d_m} (projection layer), w_2 ∈ R^{d_m} (linear regression), ⊙ = Hadamard product.
- Win probability: P_θ(wins|q) = σ(δ(M, q) - δ(M', q))
- Training: 8GB GPU, ~10 epochs, batch size 64, Adam (lr=3×10⁻⁴, wd=1×10⁻⁵).

#### C. BERT Classifier
- BERT_BASE architecture, full-parameter fine-tuning.
- Win probability: P_θ(wins|q) = σ(W h_{CLS} + b), where h_{CLS} is the classification token embedding.
- Training: 2×L4 24GB GPUs, ~2000 steps, batch size 16, max seq len 512, lr=1×10⁻⁵, wd=0.01.

#### D. Causal LLM Classifier
- Llama 3 8B, instruction-following paradigm.
- Comparison labels appended as vocabulary tokens; win probability = softmax over label classes L.
- Training: 8×A100 80GB GPUs, ~2000 steps, batch size 8, max seq len 2048, lr=1×10⁻⁶.

### Evaluation Metrics

**Performance Gap Recovered (PGR):**
```
PGR(M_R^α) = (r(M_R^α) - r(M_w)) / (r(M_s) - r(M_w))
```

**Average Performance Gap Recovered (APGR):**
```
APGR ≈ (1/10) Σ_{i=1}^{10} PGR(M_R^{α_i})
```
Discretized over 10 cost levels c_i ∈ [0%, 100%].

**Call-Performance Threshold CPT(x%):** Minimum % of calls to strong model needed to achieve PGR of x%.

### Cost Model
GPT-4: $10/M input tokens, $30/M output tokens → estimated $24.7/M tokens avg. Mixtral-8x7B: $0.24/M tokens. Cost ratio ≈ 100:1.

## 3. Trade-offs (Wins vs Loses)

| Wins | Loses |
|------|-------|
| **2-3.66× cost savings** while maintaining 87-95% of strong model quality | **Only binary routing** — no N-way extension demonstrated |
| **Zero-retraining generalization** to unseen model pairs (Claude, Llama) | **Poor OOD performance without augmentation** — routers perform at random level on MMLU/GSM8K when trained only on Arena chat data |
| **Data augmentation is sample-efficient** — <2% additional data (1,500 golden labels) yields +20% APGR improvement | **Augmentation is expensive** — LLM-judge dataset costs ~$700 to generate 120K labels |
| **Multiple router architectures** span cost-capability spectrum (CPU to 8×A100) | **SW ranking is slow** (2.9 req/s) vs GPU routers (42-155 req/s) |
| **Open source framework** for training, serving, evaluation | **Performance variance unexplained** — different router architectures on same data perform differently with no clear explanation |
| **Benchmark-dataset similarity score** provides quantitative metric for predicting router performance | **Real-world distributions differ from benchmarks** — similarity score only helpful if you know the target query distribution |
| Router overhead <0.4% of LLM generation cost | **Label sparsity** in Chatbot Arena data requires model tiering heuristic |

## 4. Design Rationale

**Why preference data over synthetic labels?** Human judgments from Chatbot Arena capture real user preferences across 100+ languages and diverse domains, avoiding biases from reward models (Zooter's QwenRM) or automatic metrics (Hybrid-LLM's BARTScore). The Bradley-Terry formulation directly models pairwise comparison outcomes rather than absolute quality scores.

**Why matrix factorization?** Inherits from recommender systems — the query-model interaction matrix has low-rank structure because queries that are similar (e.g., math problems) exhibit similar win/loss patterns across strong vs weak models. This is computationally cheaper than fine-tuning BERT or Llama while achieving comparable or better performance.

**Why data augmentation?** Chatbot Arena data distribution (conversational, multi-turn chat) differs fundamentally from benchmark distributions (MCQ knowledge tests, math word problems). Augmentation bridges this gap by injecting in-domain preference signals. Golden labels work for structured tasks (MMLU MCQs); LLM-as-judge works for open-ended tasks (MT Bench, GSM8K).

**Why multiple architectures?** Different deployment constraints (GPU availability, latency requirements, throughput needs) require different router implementations. SW ranking needs no training; matrix factorization trains on a single 8GB GPU; causal LLM requires 8×A100. Users select based on cost/latency budget.

**Why binary routing first?** The strong/weak binary problem captures the most common practical scenario (migrating from expensive proprietary to cheaper open-source models) and provides foundation for future N-way extension.

## 5. Limitations & Failure Modes

1. **Binary routing only.** No N-way extension demonstrated. Real-world deployments may need to route among 3+ model tiers simultaneously.
2. **Distribution shift vulnerability.** Routers trained purely on Arena conversational data fail on structured benchmarks (MMLU, GSM8K), performing at random level. Requires per-domain augmentation, which may not scale to arbitrary deployment distributions.
3. **Unexplained performance variance.** Different router architectures trained on identical data show significant performance gaps on the same benchmark (e.g., CPT(50%) ranges 13.40%-31.50% on MT Bench with D_arena + D_judge). No clear explanation or selection criterion provided.
4. **Augmentation cost.** LLM-judge labeling costs ~$700 for 120K samples and requires access to GPT-4 as judge. Golden-label augmentation requires pre-existing labeled datasets, which many real-world domains lack.
5. **Chatbot Arena data dependency.** Training signal quality depends entirely on human preference data from a single platform. Label sparsity (<0.1% between model pairs) requires heuristic model tiering, which may group models with different capability profiles.
6. **Cost model simplification.** Assumes single-turn, short prompts. Real-world multi-turn conversations with long contexts would change the cost calculus. Strong model pricing changes frequently (the paper uses deprecated gpt-4-1106-preview pricing).
7. **No latency analysis.** The paper measures throughput (req/s) but not per-request latency, which matters for interactive applications.
8. **Decontamination approach is simple.** Uses embedding similarity threshold (>0.95) to detect contamination — may miss paraphrased or semantically equivalent examples.

## 6. Transfer to Lyra

### The One Transferable Idea
**Preference-data-driven cost-quality routing for Lyra's agent model selection.** Lyra can train a lightweight router (matrix factorization or BERT-based) that dynamically selects between expensive frontier models (Claude Opus, GPT-4) and cheaper models (Claude Haiku, local Llama) based on query complexity. The router learns from Lyra's own eval harness results — essentially treating Lyra's benchmark runs as preference data between model pairs. This enables automatic cost optimization without manual per-task model selection rules.

### Workstream Route
**§4.3 — Cost-Optimized Inference** (primary). The routing mechanism directly addresses the cost-quality Pareto frontier that Lyra faces when invoking LLMs for agent tasks. Also feeds **§4.1 — Agent Architecture** (secondary), as the router can be integrated as a middleware layer in Lyra's agent loop, preceding the LLM call step.

### Impact: 4
High — directly reduces Lyra's per-query inference cost by 2-3× with minimal quality degradation. The framework is open source and the matrix factorization approach trains on a single 8GB GPU.

### Effort: 3
Moderate — requires (1) collecting preference data from Lyra's existing eval runs, (2) implementing the matrix factorization or SW ranking router, (3) integrating into Lyra's model invocation pipeline, and (4) calibrating the α threshold for Lyra's specific quality targets. The open-source framework reduces implementation burden.

### Tier: **breakthrough**
This is a proven technique (ICLR 2025 publication) with open-source code, strong empirical results, and direct applicability to Lyra's cost structure. It can be implemented incrementally (start with SW ranking, upgrade to matrix factorization) and evaluated against Lyra's own benchmarks before production deployment.
