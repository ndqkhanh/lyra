## 1. Mechanism (Step-by-Step)

Graphusion is a zero-shot knowledge graph construction (KGC) pipeline that builds a globally-connected KG from free text using LLMs with retrieval augmentation. It operates in three sequential steps, where each subsequent step depends on and processes the output of the previous.

### Problem Formalism

A Knowledge Graph is defined as:
```
KG = {(h_i, r_i, t_i) | h_i, t_i ∈ E, r_i ∈ R, i = 1, 2, ..., n}
```
where E = set of entities, R = 7 predefined relation types, n = total number of triplets.

The task: given free text corpus T (optionally with an expert-annotated KG G_E), produce a comprehensive KG where |KG| >> |G_E|.

### Step 1: Seed Entity Generation

**Input:** Free-text corpus T (e.g., 4,605 ACL paper abstracts from 2017-2023).

**Algorithm:**
1. Apply BERTopic (Grootendorst 2022) to T for topic modeling.
2. For each discovered topic, identify the most representative entities via class-based TF-IDF scoring.
3. Collect these representative entities into a seed entity set Q = {q_1, q_2, ..., q_k}.

**Rationale:** LLMs in zero-shot settings tend to produce irrelevant entities or entities with poor granularity (too broad, e.g., "models", or too specific, e.g., "annotated data"). Topic modeling provides a domain-grounded seed list that constrains LLM extraction to relevant, appropriately-grained entities.

**Output:** Seed entity list Q.

### Step 2: Candidate Triplet Extraction

**Input:** Seed entity list Q, free-text corpus T.

**For each query entity q ∈ Q:**

1. **Retrieval:** Fetch documents from T containing q via information retrieval (implemented with Embedchain).
2. **Chain-of-Thought Prompt (4-stage):**
   - *Stage A:* Extract in-domain entities from the retrieved context (must be fine-grained enough for a lecture slide or Wikipedia page).
   - *Stage B:* Determine relations between q and extracted entities in triplet format: `(head_entity, relation, tail_entity)`.
   - *Stage C:* Respect relation directionality. Among 7 relation types, only `Compare` and `Conjunction` are direction-insensitive. The 7 relation types are:
     - `Prerequisite_of` — One entity is a required precursor for another
     - `Used_for` — One entity is utilized to accomplish/facilitate another
     - `Compare` — Comparison between entities
     - `Conjunction` — Entities connected as a group
     - `Hyponym_of` — Hierarchical (subtype) relation
     - `Evaluate_for` — One entity assessed in context of another
     - `Part_of` — Constituent/component relation
   - *Stage D:* Discover novel triplets even when q is not the head/tail — expanding coverage beyond the seed entity.

3. **LLM Backend:** The prompt is sent to an LLM (GPT-4o, GPT-4, GPT-3.5, or LLaMA3-70B) with temperature=0.

**Output:** Zero-shot KG denoted as ZS-KG (or LLM-KG) — a collection of candidate triplets from all q ∈ Q, containing potential conflicts and duplications.

### Step 3: Knowledge Graph Fusion (Core Innovation)

This is the key differentiator from prior work. It reconciles local extractions into a globally consistent KG.

**For each query entity q ∈ Q:**

1. **Sub-graph Retrieval:**
   ```
   LLM-KG_q = {(h, r, t) ∈ ZS-KG | h = q or t = q}
   ```
   This extracts the sub-graph centered on q from the LLM-generated KG.
   Optionally, if expert-annotated KG G_E exists, also retrieve E-G_q.

2. **Dynamic Background Retrieval:** Re-query the free-text corpus T for passages containing q to provide context for conflict resolution.

3. **Fusion Prompt (4 rules):**
   - **Rule 1 — Union:** Combine all entities and edges from LLM-KG_q and E-G_q.
   - **Rule 2 — Entity Merging:** Merge semantically similar entities. Example: `NMT` → `neural machine translation`. The more specific/meaningful entity name is kept. This is critical because different documents use different names for the same concept.
   - **Rule 3 — Conflict Resolution:** For each entity pair with multiple/conflicting relations, retain exactly one relation. Use the dynamically retrieved `###Background` text to select the correct relation. Example conflict: `(ROUGE, Evaluate_for, question answering model)` vs `(ROUGE, Used_for, question answering model)`. The LLM resolves by consulting the background evidence.
   - **Rule 4 — Novel Triplet Discovery:** For every possible entity pair not already covered, examine cross-subgraph pairs (entity from Graph 1 matched with entity from Graph 2). Consult `###Background` to infer new triplets. Example: connecting `hierarchical attention network` to `reading comprehension` via `Used_for` even though they never co-occur in the same document.
4. **LLM Backend:** Same as Step 2, using temperature=0.

**Output:** Final fused KG with merged entities, resolved conflicts, and novel cross-document triplets.

### TutorQA QA Pipeline

For downstream QA, Graphusion adds a 2-stage graph interaction:
1. **Command Query Stage:** LLM independently generates graph query commands from the user question.
2. **Answer Generation Stage:** Retrieved graph paths are provided as contextual prompts to the LLM for answer generation.

### Evaluation Design

**Human Evaluation:** 100 randomly sampled triplets per model, rated 1-3 by two NLP domain experts:
- Entity Quality: relevance + appropriate granularity
- Relation Quality: logical accuracy
- Inter-Annotator Agreement (Kappa score)

**TutorQA Metrics per Task:**
- T1 (Relation Judgment): Accuracy (binary True/False)
- T2 (Prerequisite Prediction): Similarity Score (cosine similarity between predicted and gold entities via BERT embeddings)
  ```
  Score = Σ_{m∈C_pred} Σ_{n∈C_gold} sim(m,n) / (|C_pred| × |C_gold|)
  ```
- T3 (Path Searching): Similarity Score
- T4 (Sub-graph Completion): Accuracy (binary relation classification)
- T5 (Similar Entities): Hit Rate (%)
- T6 (Idea Hamster): Expert evaluation on 4 criteria (Entity Relevancy, Entity Coverage, Project Convincity, Scientific Factuality), each rated 1-5.

Chain-of-Thought prompting for link prediction *does not improve* results and more frequently produces negative (NO) predictions, suppressing system performance. This is acknowledged as a drawback.

## 3. Trade-offs (Wins vs Loses)

| Dimension | Win | Lose |
|---|---|---|
| **KG completeness** | Global fusion discovers cross-document relations that local methods miss | Fusion step adds an extra LLM call per entity, increasing latency ~2x vs single-pass extraction |
| **Entity quality** | Seed entity generation via BERTopic ensures domain-relevant granularity | Quality is bounded by BERTopic's topic modeling quality; poor topics → poor entities |
| **Relation accuracy** | Conflict resolution via background retrieval fixes contradictory triplets | Relies on LLM judgment for conflict resolution; no formal verification of resolved relations |
| **Zero-shot capability** | No training data required; works across domains (NLP, Japanese medical) | Domain adaptation requires only prompt changes, but relation type definitions must be manually specified |
| **Cost efficiency** | Cheaper than GraphRAG (avoids hierarchical clustering + community detection overhead) | Still expensive compared to pure local extraction (~$500 for this project on 4.6K abstracts) |
| **Novelty** | Infers triplets not present in any single document | Novel triplet inference can hallucinate incorrect relations (acknowledged failure mode) |
| **Scalability** | Processes 4.6K paper abstracts successfully | Quadratically scales with number of seed entities (each gets LLM call); not tested on full papers |
| **Evaluation rigor** | Human experts + IAA metrics | Only 100 triplets evaluated; inter-annotator agreement reported but exact Kappa not given for T1-T5 |
| **Baseline comparison** | Beats zero-shot, RAG, and GraphRAG baselines | GraphRAG baseline modified to fit evaluation, may not represent optimal GraphRAG performance |

## 4. Design Rationale

The core design decision is the **extract-then-fuse** paradigm instead of single-pass extraction or hierarchical clustering.

**Why not single-pass zero-shot LLM?** Single-pass extraction from individual sentences/documents produces disconnected sub-graphs with duplicate entities, conflicting relations, and missing cross-document connections. Scientific KGs require a global perspective because concepts like "hierarchical attention network" and "reading comprehension" may never co-occur in one document but are related.

**Why not GraphRAG?** GraphRAG uses hierarchical clustering + community detection to index graphs, which is computationally expensive and focuses on query-focused summarization rather than KG construction quality. It does not explicitly handle entity merging or conflict resolution, and often defaults to predicting a single relation type when uncertain (e.g., 40/100 Part_of predictions).

**Why seed entities?** Without seed entities, LLMs generate entities at inconsistent granularity (too broad: "models", "benchmark"; too specific: "annotated data"). BERTopic provides a principled, automated way to discover domain-relevant entities at appropriate granularity without manual curation.

**Why LLM-based fusion instead of rule-based?** Entity merging ("NMT" vs "neural machine translation") and conflict resolution require semantic understanding and domain knowledge. Rule-based approaches (string matching, TF-IDF) fail for abbreviations, synonyms, and context-dependent conflicts. LLMs bring the necessary semantic reasoning.

**Why background retrieval in fusion?** Conflicts cannot be resolved from the KG alone — the resolution evidence exists in the original text. Dynamic retrieval provides the grounding text that the LLM uses to adjudicate between conflicting relations.

## 5. Limitations & Failure Modes

1. **Hallucination in novel triplet inference:** The fusion step can propose incorrect triplets. The paper shows this explicitly: e.g., "word embedding" being categorized as "Part_of computer science" (too broad). No verification mechanism exists to validate inferred triplets.

2. **CoT harms link prediction:** Chain-of-Thought prompting produces more false negatives (NO predictions), suppressing overall performance. The paper cannot explain why CoT fails for this specific task.

3. **GraphRAG comparison is weakened:** The GraphRAG baseline was modified (custom prompt tuning, NLP-specific relation definitions) to fit the evaluation framework. Results may not represent optimal GraphRAG performance, limiting the strength of comparative claims.

4. **Domain specificity:** The 7 relation types were designed for NLP-domain educational KGs. Extension to other domains (medical, legal) requires redefining relation types — this is manual, domain-expert work.

5. **No quantitative cross-domain evaluation:** Japanese medical extension is purely qualitative. No multilingual or cross-domain benchmark numbers exist beyond NLP.

6. **Entity granularity is brittle:** BERTopic's seed entities determine the quality of everything downstream. Poor topic modeling → bad entities → incorrect relations → flawed fusion. There is no fallback or correction mechanism.

7. **Scale limitations:** Evaluated on 4,605 paper abstracts only. Full-paper processing (especially for domains with lengthy publications) is untested. Computational cost scales linearly with seed entity count.

8. **Human evaluation sample size:** Only 100 random triplets evaluated per model. Statistical significance of differences between models (e.g., GPT-4 vs GPT-4o) is uncertain.

9. **No learning from corrections:** The pipeline is purely zero-shot with no feedback loop. Errors made in one run persist in subsequent runs. Fine-tuning was attempted and failed.

10. **Fine-tuning attempts failed:** Both on TutorialBank and NLP-Papers, fine-tuning LLaMA2-70B degraded or did not improve performance. The cause (data quality vs task suitability) is undetermined.

11. **Single-pass fusion:** The fusion step processes each entity's sub-graph once. Conflicts spanning three or more sub-graphs may not be resolved correctly because fusion is pairwise (LLM-KG_q + E-G_q).

12. **RAG data quality sensitivity:** Using LectureBankCD documents as RAG context *decreased* link prediction performance due to noise and excessive length. This implies the framework is sensitive to retrieval quality.

## 6. Transfer to Lyra

### The ONE Transferable Idea

**The "Extract-Locally, Fuse-Globally" RAG pattern:** A two-phase architecture where (1) an LLM extracts structured knowledge (entities + relations) from individual retrieval contexts, then (2) a second LLM pass fuses all local extractions into a globally consistent representation through entity merging, conflict resolution using re-retrieved background evidence, and cross-document inference. This pattern directly addresses the core problem in agent memory systems: local observations are disconnected and conflicting, but global reasoning requires consistency.

### Workstream Route: §4.2 — Memory

The fusion module's design (entity deduplication, conflict resolution with retrieval grounding, novel connection inference) maps directly to Lyra's memory subsystem challenges:
- **Session memory consolidation:** Multiple tool-call observations about the same entity need merging across conversation turns.
- **Cross-document knowledge synthesis:** When Lyra reads multiple files/docs about the same concept, the fusion pattern resolves conflicting information.
- **Long-term memory indexing:** Seed entities from topic modeling provide a principled approach to what Lyra should "remember" vs. discard.

This is not §4.3 (Context/Retrieval) because the core contribution is knowledge *representation and consolidation*, not retrieval mechanics. It is not §4.5 (Router) because it addresses how knowledge is structured, not how queries are dispatched.

### Impact / Effort / Tier Assessment

| Metric | Rating | Rationale |
|---|---|---|
| **Impact** | 4/5 | Memory consolidation is a critical gap in Lyra; fusion pattern could significantly improve cross-turn entity coherence |
| **Effort** | 4/5 | Requires implementing BERTopic seed detection, designing fusion prompts, building a graph store with merge/conflict/resolution operations, and integrating with existing retrieval |
| **Tier** | **Breakthrough** | This is a novel architectural pattern not present in Lyra today; implementing it would meaningfully advance the memory subsystem; the extract-then-fuse paradigm is a fundamentally different approach than Lyra's current stateless retrieval model |
