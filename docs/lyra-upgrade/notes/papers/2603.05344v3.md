# Building Effective AI Coding Agents for the Terminal: Scaffolding, Harness, Context Engineering, and Lessons Learned

**Authors:** Nghi D. Q. Bui (OpenDev)
**Venue:** arXiv:2603.05344v3 [cs.AI], 13 Mar 2026 — Technical Report
**Codebase:** Rust, https://github.com/opendev-to/opendev

## 1. Mechanism (step-by-step, with equations/algorithms)

OpenDev is a compound AI system [Zaharia et al. 2024] — not a monolithic LLM call, but a structured ensemble of agents and workflows, each independently bound to a user-configured LLM. The system operates across four layers: Entry/UI, Agent Core, Tool/Context, and Persistence.

### 1.1 Compound Architecture with Per-Workflow LLM Binding

Five distinct model roles route to specialized LLMs with fallback chains:
- **Action model**: Primary tool-based reasoning (default for all workloads)
- **Thinking model**: Extended reasoning WITHOUT tool access (optional, configurable depth: OFF/LOW/MEDIUM/HIGH). Fallback: action model.
- **Critique model**: Self-evaluation inspired by Reflexion [Shinn et al. 2023]. Fallback: thinking model → action model.
- **Vision model**: VLM for screenshots/images. Fallback: action model if vision-capable.
- **Compact model**: Smaller/faster model for summarization during compaction. Fallback: action model.

Provider abstraction lazily initializes HTTP clients per model role; capabilities cached locally with stale-while-revalidate (24h TTL).

### 1.2 Extended ReAct Execution Loop (Algorithm 1)

Each user query executes through six phases per iteration:

**Phase 0 — Staged Context Management:**
```
p = token_count(S) / max_context
if p > 0.99 → compact(S)        # Full LLM summarization
elif p > 0.85 → prune_old_tool_outputs(S)  # Fast pruning pass
elif p > 0.80 → mask_old_observations(S)   # Replace with refs (~15 tokens each)
elif p > 0.70 → log_warning(p)
```
Token count calibrated from API-reported `prompt_tokens` (not local estimates) — providers inject invisible preambles that make local counting systematically wrong.

**Phase 1 — Thinking (if enabled):**
- Separate thinking LLM call WITH NO TOOL SCHEMAS
- At HIGH depth, self-critique automatically included: critique model evaluates the trace → thinking model refines with critique as input
- Trace injected as system reminder into action context

**Phase 2 — Action:**
- Assembled prompt: system prompt (from PromptComposer) + selected memory bullets from ACE playbook + all tool schemas + conversation history + thinking trace
- LLM call returns text, tool calls, or both

**Phase 3 — Decision/Dispatch/Doom-Loop Detection:**
- **Fingerprint-based doom-loop detection**: Each tool call fingerprinted as `md5(tool_name, args)`, tracked in a 20-item sliding window. If any fingerprint appears ≥3 times → inject SYSTEM WARNING. If recurs after warning → escalate to approval-based pause. Two-tier escalation is critical: LLMs can ignore injected text but cannot bypass a genuine execution halt.
- No doom loop → parallel execution (thread pool, max 5 concurrent for reads), serial execution for writes
- Error recovery: classify into 6 categories → inject targeted template (permission, file-not-found, edit-mismatch, syntax, rate-limit, timeout). Max 3 nudge attempts per error sequence.
- Todo-based completion validation prevents premature exit with incomplete work.

**Termination paths:** explicit completion tool, text-only response with no errors, exhausted nudge budget (3 consecutive failures), or iteration safety limit.

### 1.3 Subagent-Based Planning (Dual-Agent Architecture)

Planning is NOT a mode switch — it is subagent delegation:
1. Main agent receives user prompt, checks for `/plan` command or planning intent heuristics
2. Main agent spawns `spawn_subagent(type="Planner")` — a Planner subagent with read-only tools only (write tools ABSENT from schema, not just blocked at runtime)
3. Planner explores codebase (read-only), produces structured plan file (7 sections: goal, context, files to modify, new files, implementation steps, verification criteria, risks)
4. Returns plan_file_path to main agent → `present_plan(plan_file_path)` for user review
5. User: revise (re-spawn Planner with feedback) or approve (proceed to Normal Mode execution)

Design evolution: replaced a brittle 4-tool state machine (enter/exit plan mode) that would get stuck. Schema-level enforcement (write tools absent from subagent schema) eliminates bypass attempts.

### 1.4 Context Engineering Pipeline

**Dynamic System Prompt Construction (Priority-Ordered Conditional Composition):**
Pipeline: Filter → Sort (ascending priority) → Load → Join
- 21 modular markdown sections per agent, each with condition predicate and priority
- Sections gated on runtime context (e.g., `main-git-workflow.md` only if `in_git_repo`)
- Provider-specific sections gated on `model_provider` field (exactly one of OpenAI/Anthropic/Fireworks included)
- `${VAR}` placeholders resolved by centralized PromptVariables registry
- Two-tier fallback: missing section → skip; wholesale failure → monolithic core template

**Provider-Level Prompt Caching:**
`compose_two_part()` splits into stable (cacheable, ~80-90% of prompt) and dynamic parts. Anthropic adapter sets `cache_control: {"type": "ephemeral"}` on stable block. ~88% reduction in input token cost for cached portion.

**Dual-Memory Architecture for Thinking:**
- **Episodic memory**: LLM-generated summary of full history (strategic context: decisions, goals, key findings). Regenerated from FULL history every 5 messages (not incrementally summarized — prevents summary drift).
- **Working memory**: Last 6 exchanges verbatim (operational detail: file contents, error messages, line numbers)
- Combined injection: episodic summary + working memory + user query → bounded thinking context regardless of session length

**Adaptive Context Compaction (ACC) — Five Stages:**
1. Warning (70%): monitor, no reduction
2. Observation Masking (80%): older tool results → compact reference pointers (~15 tokens each, from thousands)
3. Fast Pruning (85%): walk backward, replace past-recent-window results with `[pruned]` markers — deletion-class operation, no LLM cost
4. Aggressive Masking (90%): shrink preservation window to most recent outputs only
5. Full Compaction (99%): serialize entire history to scratch file, LLM summarizer compresses middle while preserving recent messages verbatim. Artifact Index (registry of all touched files) injected into summary. History archive path provided for recovery.

**Quantitative effect:** ACC reduces peak context consumption of observations by ~54%, often eliminating emergency compaction over 30-turn sessions.

### 1.5 Automated Memory Pipeline (ACE — Agentic Context Engineering)

Four-stage pipeline processing tool outcomes into a persistent playbook:
1. **BulletSelector**: Scores playbook bullets by effectiveness (0.5 weight), recency decay (0.3), cosine similarity to current query over cached embeddings (0.2). Top-ranked bullets injected into system prompt.
2. **Reflector** (every 5 messages): Analyzes accumulated experience → reasoning trace, error identification, root-cause analysis, correct approach. Produces effectiveness tags (helpful/harmful/neutral).
3. **Curator**: Reads reflection → plans concrete mutations (add, update, tag, remove) → emits DeltaBatch.
4. **Mutation application**: Applied to Playbook's bullet table, persisted to session-scoped JSON.

### 1.6 System Reminders — Event-Driven Behavioral Steering

24 named reminders in 6 categories (phase control, task lifecycle, todo enforcement, error recovery, behavioral correction, JSON retry). Injected as `role: user` messages (NOT `role: system`) at maximum recency. Guardrail counters cap per-type frequency (e.g., MAX_TODO_NUDGES=2, MAX_NUDGE_ATTEMPTS=3). One-shot flags prevent redundant injection.

### 1.7 Tool System

35 built-in tools across 12 handler categories. Key innovations:
- **9-pass fuzzy matching for edits**: Chain-of-responsibility pattern from exact match through whitespace-normalized, indentation-flexible, escape-normalized, context-aware anchor matching. Short-circuits on first match.
- **Lazy MCP discovery**: External tool schemas loaded only via `search_tools(keyword_query)`. Baseline overhead reduced from 40% to <5% of context.
- **Two-phase skill loading**: Metadata index at startup (names + descriptions), full content on `invoke_skill`.
- **Six-stage shell execution**: Safety gates → command preparation → server detection (16 regex patterns auto-promote to background) → execution fork (PTY for bg, piped for fg) → output management (30k char limit, head-tail truncation) → timeout/interrupt handling.
- **LSP integration**: 30+ languages via lazy language server processes, two-level cache (Level 1: raw LSP responses, Level 2: processed symbol trees), keyed by MD5 file content hash.

### 1.8 Five-Layer Defense-in-Depth Safety

Layer 1: Prompt-level guardrails (security policy, git conventions, action safety)
Layer 2: Schema-level tool gating (plan-mode whitelist, per-subagent allowed_tools)
Layer 3: Runtime approval system (Manual/Semi-Auto/Auto levels, pattern/command/prefix/danger rules, persistent permissions)
Layer 4: Tool-level validation (DANGEROUS_PATTERNS blocklist, stale-read detection, output truncation)
Layer 5: Lifecycle hooks (external scripts at PRE_TOOL_USE can block with exit code 2)

## 3. Trade-offs (wins vs loses table)

| Win | Cost/Loss |
|-----|-----------|
| Per-workflow LLM binding enables cost-optimal model selection per cognitive task | 5x model configuration complexity; users must understand which model suits each workload |
| Schema-level tool gating (absent tools → no bypass attempts) is more robust than runtime permission checks | Reduces flexibility — subagent cannot "request" a tool it genuinely needs; requires re-construction |
| Eager agent construction (prompt + schemas built in `__init__`) eliminates first-call latency and race conditions | Higher memory footprint at startup; all subagents pre-allocate their contexts |
| Tool result summarization extends session life 2x (15-20 → 30-40 turns) | Information loss risk — agent may miss details in summarized outputs; recoverable via re-read |
| Lazy MCP discovery reduces context overhead from 40% to <5% | Discovery overhead per new tool use (must search then invoke); friction for MCP-heavy workflows |
| Separate thinking phase (no tools in schema) produces better reasoning traces | Adds latency (separate LLM call); at HIGH depth, includes critique = 2 extra calls |
| System reminders as role:user messages improve compliance over role:system | User-role injection pollutes conversation semantics; nudges capped to prevent noise loops |
| Fingerprint-based doom-loop detection catches stuck loops in 3 repetitions | MD5 hashing misses semantically-equivalent-but-syntactically-different calls; false negatives possible |
| Periodic episodic memory regeneration from full history prevents summary drift | Higher cost than incremental summarization (full-history LLM call every 5 messages) |
| Shadow git snapshots provide per-step undo without touching user's git | Additional storage overhead; cleanup via `git gc --prune=7.days` |
| Single MainAgent class with parameterized behavior eliminates diamond inheritance | Debugging complexity — all behavioral variation encoded in configuration, not type system |

## 4. Design Rationale (why this approach)

The paper's central thesis is that **terminal-native coding agents face three structural challenges that require engineering, not just better models**: (1) finite context windows over sessions exceeding token budgets, (2) destructive operation prevention when the agent executes arbitrary shell commands, and (3) capability extension without overwhelming the prompt budget.

**Why compound architecture over monolithic?** Different execution phases have fundamentally different requirements: reasoning needs deliberation without tool pressure, visual tasks need VLMs, and bulk summarization benefits from cheaper/faster models. Using one model wastes cost on simple tasks or sacrifices quality on hard ones. Task-specific routing with fallback chains balances cost, latency, and capability.

**Why subagent-based planning over state-machine mode switching?** The initial 4-tool state machine (enter_plan_mode, exit_plan_mode, create_plan, edit_plan) was brittle — agents would fail to exit plan mode, getting stuck read-only. Subagent delegation eliminates state entirely: the Planner subagent has write tools ABSENT from schema (not blocked), and the main agent never leaves Normal Mode. This is the "missing road, not guardrail" principle.

**Why eagerly build agents?** Lazy prompt building introduced first-call latency visible to users and race conditions with MCP server discovery. Eager building guarantees every agent is complete at construction time.

**Why 9-pass fuzzy matching for edits?** Analysis of failure logs revealed LLM formatting drift falls into distinct categories (whitespace, indentation, escapes, partial-context anchoring). A chain-of-responsibility with progressive relaxation converts near-misses into successful edits while exact matches short-circuit with zero overhead.

**Why role:user for reminders?** After 40+ turns, another system message blends into background noise the model has already partially forgotten. A user message appears at maximum recency — the model treats it as "something that just happened requiring a response." Empirically, user-role reminders produced noticeably higher compliance rates.

## 5. Limitations & Failure Modes

**No quantitative benchmarking:** The paper's most significant limitation — it explicitly acknowledges lacking systematic evaluation on SWE-bench, Terminal-Bench, or LongCLI-Bench. Architectural claims are supported by internal measurements only. This limits comparison with published systems.

**Globally fixed parameters:** The 70% compaction threshold, 3 nudge attempts, 6 thinking depth levels are hardcoded — no adaptive per-task tuning. A simple debugging task wastes budget on thinking; complex refactoring may benefit from deeper deliberation.

**Summary drift in ACE pipeline:** While episodic memory regeneration corrects summary drift, the ACE playbook (flat natural-language bullets) lacks hierarchical organization. Cross-project knowledge transfer is not implemented.

**MD5 fingerprint false negatives:** Doom-loop detection via `md5(tool_name, args)` misses semantically identical but syntactically different calls (e.g., same file path with different quoting).

**Limited multi-agent coordination:** Subagents communicate only through completion markers — no peer-to-peer communication, shared blackboard architectures, or negotiation protocols for conflicting tool outcomes.

**Potential context starvation under deep nesting:** If subagents spawn subagents, each layer adds its own context overhead — no documented guard against recursive context consumption.

**Approval fatigue risk:** Despite persistent permissions, the three-level autonomy model (Manual/Semi-Auto/Auto) still requires user vigilance. Semi-Auto auto-approves a curated allowlist which may not cover all safe patterns in diverse workflows.

**MCP discovery overhead for tool-heavy workflows:** Lazy discovery is efficient when few external tools are used, but for workflows using many MCP tools, the search-then-invoke pattern accumulates overhead.

**No hard guarantees on safety:** The 5-layer defense-in-depth architecture is best-effort — there is no formal verification of safety properties. Layer 3 (runtime approval) can be configured to Auto, effectively disabling human review.

## 6. Transfer to Lyra (the one idea + §4.x workstream + Impact/Effort/Tier)

### The One Transferable Idea: **Event-Driven System Reminders as role:user Messages at Maximum Recency**

OpenDev's most actionable insight for Lyra is the **system reminders** mechanism (Section 2.3.4). The core finding: in long-running sessions (30+ tool calls), initial system-prompt instructions suffer from attention decay — the model reliably violates them because the instructions sit at the distant beginning of a context now dominated by tool outputs. The solution: **short, targeted reminders injected as role:user messages at the point of decision**, capped by per-type guardrail counters (max 2-3 fires) to prevent noise loops. Key implementation details:
- Inject as `role: user`, not `role: system` — the model assigns higher salience to recent user messages
- 8 event detectors monitor conversation state at iteration boundaries (tool failure without retry, exploration spirals, premature completion, etc.)
- 24 reminder templates stored as plain text files (auditable, extensible without code changes)
- One-shot flags for signals that should fire exactly once; attempt budgets for repeatable nudges
- The system works without them, but works "measurably better" with them

This is directly applicable to Lyra's long-running research and coding sessions, where context windows routinely exceed 30 turns and instruction fade-out is a predictable failure mode.

### Workstream Route: **§4.1 (Harness/Agent Loop Engineering)**

System reminders are a harness-level mechanism — they sit at the boundary between tool execution and the next LLM call, injecting targeted guidance based on conversation state. This feeds directly into Lyra's ReAct loop infrastructure.

### Impact/Effort/Tier Assessment

- **Impact:** 4 — High. Directly addresses a reproducible, high-frequency failure mode (attention decay leading to premature completion, exploration spirals, abandoned error recovery). Low implementation risk because reminders reinforce existing instructions rather than introducing new ones.
- **Effort:** 2 — Low. The mechanism is lightweight: (a) define event detectors (state inspection at iteration boundaries), (b) create ~10-15 reminder templates as markdown files, (c) add guardrail counters to IterationContext, (d) inject as role:user before next LLM call. No new external dependencies.
- **Tier:** **Investigate** — Strong candidate for implementation. The pattern is simple, well-documented with failure modes and guardrails, and has immediate applicability. However, the paper lacks quantitative ablation of reminder effectiveness (no A/B with/without metrics), so Lyra should measure compliance rates before/after to confirm benefit.
