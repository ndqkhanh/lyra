## 1. Mechanism (step-by-step)

Paper Circle is a full-stack multi-agent research platform with two complementary pipelines: **Discovery** (finding papers) and **Analysis** (understanding papers). Both are built on HuggingFace's `smolagents` library using CodeAgent (CoA) orchestrators and ToolCallingAgent (ToCA) specialists.

### 1.1 Discovery Pipeline

**Architecture:** A `Tracker` coordinates 6 agents, maintaining shared `PipelineState` that is persisted to a backing store and displayed to the user. Each agent step regenerates synchronized artifacts (JSON, CSV, BibTeX, Markdown, HTML).

**Agent Roles (in execution order):**

1. **Intent Classification Agent:** Parses natural-language query into structured constraints — search mode (offline/online/both), conference filters, year range, max results, ranking preferences. Uses a web agent for ambiguous queries or recent knowledge.

2. **Paper Search Agent:** Executes retrieval based on intent classification:
   - **Offline:** Loads local JSON corpus → BM25 indexing via `rank_bm25` (Okapi BM25) → optional semantic similarity (sentence-transformers `all-MiniLM-L6-v2`) → optional cross-encoder rerank (Qwen3-Reranker-0.6B)
   - **Online:** Parallel queries to arXiv, Semantic Scholar, OpenAlex, DBLP APIs via ThreadPoolExecutor
   - **Deduplication:** Two-stage — DOI-based then title-based (normalized, lowercased, punctuation-stripped)
   - **Query Expansion:** Natural-language query → structured spec with core keywords, required constraints, related terms, negative keywords, plausible paper titles

3. **Sorting Agent:** Reorders papers using multi-criteria scoring:

   **Individual Score Dimensions:**
   - **Similarity:** TF-IDF cosine similarity between query and paper (title+abstract concatenation)
     ```
     similarity(q, p) = (v_q · v_p) / (||v_q|| · ||v_p||)      (Equation 1)
     ```
   - **Recency:** Normalized publication year
     ```
     recency(p) = (year(p) − year_min) / (year_max − year_min)  (Equation 2)
     ```
   - **Novelty:** TF-IDF distance from corpus centroid document vector (surfaces papers with unusual terminology)
   - **BM25:** Okapi BM25 normalized to [0,1]
   - **Citation Count:** From Semantic Scholar/OpenAlex (disabled by default to avoid recency bias)

   **Combined Score (weighted sum):**
   ```
   combined(p) = w_s·similarity + w_r·recency + w_n·novelty + w_b·bm25    (Equation 3)
   ```
   Mode-specific weights:
   - **Stable:** w_s=0.5, w_r=0.2, w_n=0.1, w_b=0.2
   - **Discovery:** w_s=0.3, w_r=0.1, w_n=0.4, w_b=0.2
   - **Balanced:** w_s=0.3, w_r=0.2, w_n=0.2, w_b=0.3

   **Cross-Encoder Reranking (optional):** Two-stage — BM25 retrieves top-200 candidates, then Qwen3-Reranker cross-encoder scores query-document pairs via cross-attention.

   **Maximal Marginal Relevance (MMR):**
   ```
   MMR = arg max_{p∈R\S} [λ·sim(p,q) − (1−λ)·max_{s∈S} sim(p,s)]    (Equation 4)
   ```
   λ values: Stable=0.8, Discovery=0.5, Balanced=0.65

4. **Analysis Agent:** Computes aggregate statistics — source distribution, year trends, top authors/venues, keyword frequency, citation summaries.

5. **Export Agent:** Produces synchronized multi-format outputs (JSON, CSV, BibTeX, Markdown, HTML dashboard).

6. **Web Search Agent:** Auxiliary external web search when online lookups needed.

**State Management:** `PipelineState` tracks papers, links, statistics, summaries. Each step increments a counter, logs action metadata (agent name, action, results preview, parameters, timestamps), and regenerates all synchronized artifacts. Outputs include: `papers.json`, `links.json`, `stats.json`, `summary.json`, `retrieval_metrics.json`, plus human-readable exports and live HTML dashboard with 10-second auto-refresh.

### 1.2 Analysis Pipeline (Paper Mind Graph)

**Architecture:** A CodeAgent orchestrator manages 7 specialized ToCA/CoA roles operating on individual papers via a 4-stage pipeline.

**Stage 1 — PDF Ingestion:**
- **Parser:** PyMuPDF extracts metadata (title, authors, abstract, arXiv ID, venue, page count), hierarchical sections (via numbering patterns), figures/tables (captions, page locations, nearby context), equations (numbered with surrounding context)
- **SemanticChunker:** Structure-aware chunking with configurable 1500-char limit. Unlike token-based chunking, preserves document structure — paragraphs grouped within sections, figures/tables/equations as distinct chunks with captions and context.

**Stage 2 — Graph Construction (GraphBuilder):**
Four specialized CoA-based extractors operate in 5 sequential phases:
1. **Concept Extractor:** Classifies concepts by type (definition, technique, theory, phenomenon) and importance (core, supporting, background). Outputs structured JSON.
2. **Method Extractor:** Targets sections with keywords ("method", "approach", "architecture", "algorithm"). Extracts name, description, category (proposed, baseline, component), key steps.
3. **Experiment Extractor:** Recovers experimental setups, datasets, evaluation metrics, key results. Identifies dataset nodes.
4. **Linkage Agent:** Connects figures/tables to concepts/methods based on captions, nearby text, and concept list. Determines relationship type (illustrates, summarizes, compares, demonstrates).
5. **Inter-concept Relations:** Discovers relationships between extracted concepts.

**Knowledge Graph Schema:**
- **Node types:** papers, sections, concepts, methods, experiments, datasets, figures, tables, equations
- **Edge types:** hierarchy, definition, proposal, usage, evaluation, illustration, dependency
- **Provenance metadata on every node/edge:** source chunk IDs, page numbers, verification status, confidence scores, timestamps

**Stage 3 — Graph-Aware Q&A:**
- `EmbeddingStore`: Indexes text chunks and node descriptions (sentence-transformers with bag-of-words fallback)
- `GraphRetriever`: Retrieves top-k similar chunks + nodes, expands context via 1-hop graph neighbors, returns chunks + nodes + connecting edges
- `PaperQA agent`: Constructs prompt with text chunks (section-sourced), concept descriptions, graph relationships. Returns answer + supporting sections + figures/tables + confidence estimate
- `locate()` function: Finds specific items by searching across nodes, figures, tables, text chunks → returns page numbers and context

**Stage 4 — Coverage Verification:**
`CoverageChecker` produces report with:
- Figure coverage (% linked to concepts/methods)
- Table coverage (% linked to results/experiments)
- Section coverage (% with extracted concepts)
- Equation coverage (% linked to defining concepts)
- Overall coverage score (0–100%)
- Lists of unlinked items with suggestions, critical issues flagged

**Human Verification Workflow:** `VerificationManager` supports verify_node, edit_node, add_edge, remove_edge, flag_for_review — all logged with timestamps. Nodes carry `verification_status` field (auto-generated, human-verified, human-edited, flagged).

### 1.3 Review Pipeline

7 specialized agents coordinated by Multi-Agent Orchestrator with ThreadPoolExecutor for parallel execution:
1. **Deep Analyzer:** Mathematical foundations, methodology components, primary experimental findings
2. **Critic:** Senior reviewer emulation (NeurIPS/ICML style) — strengths/weaknesses, author-facing questions, scores for novelty/clarity/significance
3. **Literature Expert:** Semantic Scholar + arXiv interfaces, maps paper position in research landscape, verifies citation accuracy
4. **Contribution Analyzer:** Separates explicit author claims from verified contributions, flags overclaiming or missing baselines
5. **Reproducibility Checker:** Source code availability, hyperparameter specifications, dataset accessibility, compute requirement disclosures
6. **Summarizer:** Multi-fidelity summaries (executive → deep technical précis)
7. **Knowledge Graph Agent:** Constructs concept graph for the reviewed paper

### 1.4 Implementation Stack

- **Frontend:** React, TypeScript, Vite, TailwindCSS — discovery, reading circles, discussion
- **Backend:** FastAPI (Python), scikit-learn, NumPy, pandas
- **Database:** Supabase (PostgreSQL + Auth)
- **Deployment:** Dockerfile, Railway/Render/Vercel configurations
- **Core files:** `backend/agents/discovery/pca.py` (multi-agent pipeline), `backend/core/paperfinder.py` (deterministic pipeline)
- **Compute:** 4×40GB NVIDIA GPUs, Ollama platform with fastllm library

- **Best model (gpt-oss:120b):** Rating MAE = 1.68, Presentation MAE = 0.60, Contribution MAE = 0.62

- **Chat-style models (gpt-oss):** More consistent, better instruction-following for end-to-end reviewing

- **NASA-TLX workload:** 1.2/7 overall (5 of 6 subscales at minimum 1/7)

## 3. Trade-offs

| Dimension | Win | Cost/Loss |
|---|---|---|
| **BM25 + Reranker vs BM25 only** | Best MRR (0.8692) and R@5 (0.9400) | 28× slower (935s vs 33s) |
| **Multi-agent vs BM25 baseline** | +2pp hit rate (80% vs 78%), better ranking (MRR 0.627 vs 0.541) | +21-22s latency per query |
| **Full pipeline vs Minimal** | Higher MRR (0.8629 vs 0.8420) | Slightly slower (33.75s vs 33.34s); marginal gain |
| **Intent Classification removal** | Faster pipeline (31.47s) | MRR drops from 0.8629 to 0.8554 (0.75pp) |
| **Discovery mode vs Stable mode** | Surfaces hidden gems (λ=0.5 diversity) | Reduced relevance precision (w_n=0.4 vs 0.1) |
| **Semantic-only vs BM25** | Can capture conceptual similarity | R@1 drops from 0.80 to 0.62 (18pp loss) |
| **Hybrid (BM25+semantic) vs BM25** | No additional benefit | No improvement; extra compute |
| **Multi-source vs single-source** | Covers 91% of corpus (vs 20-63% single-source) | Slower, requires deduplication (43.5% duplicates) |
| **Large models for review** | Better review quality (gpt-oss:120b) | Correlation with humans still r < 0.25; expensive |
| **5 export formats** | Downstream compatibility | Per-session overhead |
| **Deterministic pipeline** | Reproducibility, auditable step logs | Less flexible than pure LLM search |
| **Online + Offline vs Offline only** | Broader coverage | Hit rate drops to 0.62 (Online/Offline Mix) due to API inconsistency |

## 4. Design Rationale

**Why smolagents (HuggingFace) as the orchestration foundation:** Lightweight, open-source, supports both CodeAgent (CoA) for planning/orchestration and ToolCallingAgent (ToCA) for specialized tool-bound tasks. The framework provides (i) tool invocation, (ii) multi-step planning via orchestrator, and (iii) delegation to specialized agents out of the box. Paper Circle extends this with structured outputs, offline search, and evaluation metrics while preserving the clean tool interface (explicit parameters → formatted string responses).

**Why coder LLMs over chat LLMs for discovery:** Code-generation-trained models produce more structured, machine-parseable outputs and follow multi-step tool-use sequences more reliably. The paper shows qwen3-coder variants dominating retrieval benchmarks. However, **chat-style LLMs (gpt-oss) outperform coders for review tasks** — suggesting task-dependent model selection.

**Why deterministic scoring + synchronized outputs:** Unlike purely LLM-based search that may produce different results on each run, the BM25+TF-IDF+MMR pipeline produces reproducible rankings. Every agent step regenerates all export artifacts, enabling step-level audit trails.

**Why multi-source aggregation:** Single sources miss 70-80% of papers. The paper demonstrates that arXiv alone misses 70.9% and Semantic Scholar alone misses 80.4% of their corpus. Aggregating 4+ APIs with deduplication achieves 91% coverage.

**Why separate Discovery and Analysis pipelines:** Discovery handles breadth (finding papers), Analysis handles depth (understanding papers). This separation allows independent optimization, modular evaluation, and users who only need one capability.

**Why typed Knowledge Graph over flat extraction:** Typed nodes with provenance enable graph-aware QA (1-hop neighbor expansion), coverage verification (ensuring nothing is silently dropped), and downstream structured export. Full traceability from any graph element back to source PDF location is the key architectural commitment.

**Why human-in-the-loop verification, not full automation:** The system is positioned as a "collaborative workbench" that augments rather than replaces researchers. The VerificationManager and reading circle features reflect this philosophy.

## 5. Limitations and Failure Modes

1. **Review agent does not correlate with human judgment:** Across all models tested, correlation with human reviewer scores is |r| < 0.25, with several metrics showing negative correlations. The system cannot reliably distinguish strong from weak submissions. The authors explicitly warn: "the system should not be used as a trusted mechanism for comparing or ranking papers."

2. **Code-specialized models fail at review workflows:** qwen3-coder-30b struggles to sustain coherent review workflows, producing larger errors on overall rating (MAE 2.79-2.99) and contribution (MAE 1.39-1.47). Chat-style models (gpt-oss) perform better, suggesting a fundamental mismatch between code-generation training and review tasks.

3. **Online/Offline Mix degrades performance:** The mix configuration drops to 62-64% hit rate (vs 96-98% for offline-only or filtered), likely due to API inconsistency and result aggregation challenges.

4. **Semantic-only retrieval severely underperforms BM25:** R@1 drops from 0.80 to 0.62 (18pp). Lexical matching remains crucial for precise paper retrieval — a finding that contradicts the trend toward dense embeddings for everything.

5. **Reranker is prohibitively slow:** BM25 + Reranker achieves best MRR but at 28× the latency (935s vs 33s), making it impractical for interactive use.

6. **Domain coverage untested beyond CS/ML:** The corpus spans ICLR, NeurIPS, ICML, CVPR, etc. (Table 2: 291 papers across 10+ CS venues). No validation in other scientific domains despite claims of domain-agnostic design.

7. **Small-scale user study:** Only 81 sessions with preliminary NASA-TLX and usability results. Not a rigorous HCI evaluation.

8. **Hybrid retrieval provides no benefit:** BM25 + semantic combined performs identically to BM25 alone, suggesting the semantic signal adds noise rather than complementary information in academic retrieval.

9. **Requires GPU infrastructure:** All experiments conducted on 4×40GB GPUs with Ollama. Local-only deployment requires significant hardware.

10. **Dependency on external APIs for online search:** arXiv, Semantic Scholar, OpenAlex, DBLP APIs must be available and responsive. Rate limiting or API changes could degrade online retrieval.

11. **Review evaluation is small and narrow:** 50 ICLR 2024 papers only. No testing on papers from other venues, years, or disciplines.

## 6. Transfer to Lyra

### The ONE Transferable Idea

**Typed Knowledge Graph Construction Pipeline with Provenance-Backed Extraction Agents:** A multi-agent system where specialized extractors (Concept, Method, Experiment, Linkage) build a typed graph from research papers with full traceability metadata (source chunk IDs, page numbers, confidence scores, verification status) on every node and edge. The graph then powers graph-aware QA (1-hop neighbor expansion) and a Coverage Verifier that prevents silent information loss by reporting what was missed.

### Why This Matters for Lyra

Lyra's research corpus ingestion currently lacks structured knowledge extraction from papers. This pipeline provides:
- **Structured paper understanding** (not just chunked text) enabling graph-aware retrieval
- **Provenance tracking** so every extracted claim can be traced to its source location
- **Coverage verification** as a built-in quality gate ensuring Lyra doesn't miss figures, tables, or equations
- **Multi-agent extraction** where specialized agents handle different entity types, mirroring Lyra's existing agent architecture
- **Human verification hooks** aligning with Lyra's supervised research philosophy
