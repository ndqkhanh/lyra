## 1. Mechanism (step-by-step)

LAMO (Lightweight Agent Multi-role Orchestration) is a framework for training a **single 3B-parameter MLLM** to flexibly assume multiple skill-specific roles in GUI automation, enabling MAS (Multi-Agent System) adaptation without training separate expert models.

### 1.1 Role-Oriented Data Synthesis

The core insight: lightweight MLLMs degrade on long-horizon tasks where they must simultaneously handle screen analysis, policy decisions, and tool invocation — but perform reliably when these components are handled independently. LAMO decomposes GUI automation into **five core capabilities** and synthesizes skill-specific training data for each using teacher models:

| Capability | Role | Teacher Model | Output |
|---|---|---|---|
| **ATA** (Action-Tool Alignment) | Policy Executor | Qwen2.5-VL-72B (MT1) | Maps high-level instructions to low-level executable tools |
| **LCC** (Logic-Consistent CoT) | Reasoner | Gemini-2.5-Pro (MT2) | Step-wise logically rigorous chain-of-thought |
| **SU** (Screen Understanding) | Observer | Gemini-2.5-Pro (MT2) | Multi-grained semantic screen descriptions |
| **GP** (Goal Planning) | Planner | Gemini-2.5-Pro (MT2) | Sub-goal decomposition with actionable tips |
| **SG** (Screen Grounding) | Grounder | Qwen2.5-VL-72B (MT1) | Fine-grained spatial/UI layout perception |

**ILG (Intricate-Layout Grounding) augmentation:** Rule-based procedure that overlays target elements onto background screens with multiple distractor elements at random scaling to create cluttered grounding samples. This improves grounding robustness without expensive human annotation.

### 1.2 Two-Stage Training Recipe

**Stage 1 — SFT with Perplexity-Weighted Cross-Entropy (PWCE):**
- 1 epoch, lr=4e-6, warmup ratio 0.03, global batch size 256, LoRA (rank 128, alpha 256)
- Key innovation: PWCE loss reweights tokens by their perplexity during training
- Formula: `LPWCE = LCE + λ * LPW`
- Perplexity weight for token i: `wi = (1 + α * PPLi / (PPL̄ + ε)) / (1/|M| * Σ_j∈M (1 + α * PPLj / (PPL̄ + ε)))`
- High-perplexity tokens (typically coordinate numbers) receive larger loss weights, steering optimization toward spatially critical outputs
- Hyperparameters: ε=1e-12, β=1.5, α=0.5, λ=0.09

**Stage 2 — Multi-Task RL with GRPO:**
- 1 epoch, lr=1e-6, rollout batch size 32, 8 rollouts per sample
- Vision backbone frozen; merge layer + LLM trained
- Task pool: ATA, SU, GP, SG, LCC (formatted as step-wise agentic task)
- Reward functions are task-specific and rule-based:
  - **SU/GP:** Normalized TF-IDF similarity between prediction and label → `ragent ∈ [0,1]`
  - **SG:** Geometric distance from predicted coordinates to ground truth
  - **ATA/Agentic:** Binary scores for tool class correctness + tool value correctness
  - All tasks get length penalty: `rpenalty = -φ * length(ypred) / Lmax` (φ=0.3, Lmax=120)
- GRPO (Group Relative Policy Optimization) used for multi-task cooperative exploration

### 1.3 Multi-Role Orchestration (Three Inference Modes)

**Mode 1 — End-to-End Reasoning (Monolithic):**
```
St = MΘ(G, Ie2e, o≤t, a<t)
```
Output format: `<think>CoT</think> <answer>action decision</answer> <tool_call>atomic action at</tool_call>`

**Mode 2 — Multi-Agent System (MAS) via Parameter Sharing (Algorithm 1):**
A single shared backbone instantiates four distinct roles:
1. **Observer** `MΘ^Observer(Ĩobs, ot)` → `Cs2w`: Rich semantic screen description
2. **Planner** `MΘ^Planner(Ĩplan, G, o≤t)` → `(Cplan, Ctips)`: Goal decomposition into subtasks
3. **Allocator** `MΘ^Allocator(Ĩact, ot, a<t, Cs2w, Cplan, Ctips)` → `Caction`: Single executable action
4. **Executor** `MΘ^Executor(Ĩexec, ot, Caction)` → `at`: Tool selection and execution in environment

This reduces per-agent context length, mitigates "lost-in-the-middle" and Thought-Action hallucinations.

**Mode 3 — Policy Executor:**
```
Caction* = MΔ^Planner(IΔ*, G, o≤t, a<t)   # External large MLLM planner
at = MΘ^Executor(Ĩexec, ot, Caction*)       # LAMO-3B executes
```
Pairs LAMO-3B as a plug-and-play executor with any advanced external planner (Gemini-2.5-Pro, GPT-5).

### 1.4 Compute
8× NVIDIA H20 96GB GPUs. AdamW optimizer.

## 3. Trade-offs

| Win | Cost / Loss |
|---|---|
| 3B model achieves SOTA or competitive performance against 7B–72B GUI agents across 5 benchmarks | Requires external large-MLLM planner for complex long-horizon tasks (>10 steps); solo E2E is only 50.0% on MiniWob++ |
| MAS mode yields +21.8% over monolithic E2E on MiniWob++ via role decomposition | MAS orchestration adds 4× inference passes per step (Observer → Planner → Allocator → Executor), increasing latency and token cost |
| Policy Executor mode achieves 77.2–77.6% SOTA by pairing with external planners | Performance ceiling is bounded by external planner quality; dependency on proprietary models (Gemini/GPT) |
| Parameter sharing enables one model to serve all roles (no separate expert training) | Single-backbone bottleneck: all roles share same 3B capacity limits; cannot specialize as deeply as dedicated experts |
| PWCE loss improves coordinate prediction accuracy (+3.6% on MW) | Adds training complexity (hyperparameters α, β, ε, λ) and requires per-token perplexity computation |
| ILG data massively boosts complex-layout grounding (+34.7% on SP-pro) | Rule-based augmentation may not cover all real-world layout pathologies |
| 10× fewer params than Qwen2.5-VL-32B with only 5.1 points gap on OSWorld | Still 5.1 points behind on desktop tasks; mobile-optimized, desktop lags |

## 4. Design Rationale

**Why multi-role orchestration instead of training separate experts?** Training multiple skill-specific MLLMs (e.g., one for planning, one for grounding, one for execution) is prohibitively expensive — Agent-S2 deploys 3+ large models (UI-TARS-72B, Tesseract OCR, UNO). LAMO's parameter sharing amortizes training cost across roles while enabling knowledge transfer between tasks via shared representations learned during multi-task RL.

**Why PWCE instead of standard cross-entropy?** Standard CE treats all tokens equally, but coordinate tokens exhibit systematically higher perplexity during SFT — the model is uncertain about spatial outputs. PWCE dynamically upweights high-perplexity tokens (discovered empirically: coordinates are 2–5× higher perplexity than text tokens), steering optimization toward spatially critical predictions without manual token-type detection.

**Why two-stage (SFT → RL) instead of RL-only?** Pure RL from the base model would require discovering both domain knowledge AND optimal policies simultaneously — an intractable exploration problem for a 3B model. SFT first distills teacher knowledge (domain concepts, tool formats, screen semantics), then RL refines the policy to maximize task completion. Ablation confirms SFT+RL gives 10.4% + 14.8% additive gains.

**Why ILG augmentation?** Real GUI environments have cluttered layouts, overlapping elements, and distractor UI components that confuse MLLM spatial perception. Rule-based ILG synthesis creates arbitrarily many challenging grounding examples from existing metadata, entirely avoiding human annotation cost while providing controlled difficulty scaling.

**Why policy executor mode as the primary deployment paradigm?** The authors argue that lightweight models will never match large models in planning depth due to scaling laws. Instead of fighting this, LAMO embraces a symbiotic architecture where the small model handles reliable low-level execution (where precision matters more than reasoning depth) and the large model handles high-level planning. This creates a "rising tide" effect — LAMO-3B automatically benefits as planner models improve.

## 5. Limitations & Failure Modes

1. **Long-horizon degradation (>10 steps):** The 3B parameter budget fundamentally limits reasoning depth. Tasks requiring extended multi-step planning still need an external planner — LAMO-3B alone cannot handle these.
2. **Desktop environment weakness:** Performance degrades on OSWorld (38.5% vs. mobile 60.3–77.6%). Spreadsheet scenarios and software-specific prior-dependent applications remain challenging due to higher visual complexity and domain-specific UI patterns.
3. **External planner dependency:** Policy Executor mode's ceiling is gated by the external planner's capability. If the planner produces ambiguous or incorrect high-level instructions, LAMO-3B has limited capacity to detect or correct these upstream errors.
4. **Single-backbone constraint:** All four MAS roles share one 3B backbone. This prevents role-specific architecture optimizations and means capacity is split across capabilities rather than dedicated.
5. **Rule-based rewards:** GRPO relies on string-matching and TF-IDF similarity rewards, which are coarse proxies for task success. Complex semantic correctness (e.g., "was the right button clicked for the right reason?") is not captured.
6. **Backbone specificity:** Only validated on Qwen2.5-VL-3B. Transferability to other lightweight architectures (e.g., Kimi-VL, InternVL-small) is unverified.
7. **No safety/robustness evaluation:** The paper does not evaluate adversarial GUI states, injection attacks via UI text, or safe operation boundaries.

## 6. Transfer to Lyra

**The One Idea:** Train a single lightweight agent model to flexibly assume multiple specialized roles (Observer, Planner, Allocator, Executor) through role-oriented data synthesis and multi-task RL, enabling MAS-style orchestration via parameter sharing rather than deploying separate expert models. This "one-model-many-roles" pattern is directly applicable to Lyra's agent architecture — instead of building separate agents for research, verification, execution, and planning, Lyra could train (or prompt-engineer) a single model that dynamically adopts the appropriate role based on task context.

**Workstream Route:** §4.2 — Agent Architecture & Multi-Agent Systems  
**Impact:** 4 (transformative pattern: parameter-shared multi-role agents could reduce Lyra's agent fleet complexity by 3–5×)  
**Effort:** 4 (requires role-specific data synthesis pipeline, multi-task RL training infrastructure, and role-orchestration runtime)  
**Tier:** **investigate** — The multi-role parameter-sharing pattern is novel and well-validated but the paper targets GUI automation (visual grounding, click actions). Adapting to Lyra's text/code-dominant agent workflows requires significant translation. The concept is high-value but the domain gap is real.
