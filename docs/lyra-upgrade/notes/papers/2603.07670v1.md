## 1. Mechanism (step-by-step)

The paper is a survey that formalizes LLM agent memory as a **write-manage-read loop** within a POMDP framework, then taxonomizes and compares five mechanism families.

### 1.1 Core Formalization (POMDP)

At each discrete step t, the agent:

```
a_t = π_θ( x_t, R(M_t, x_t), g_t )        (1)  — policy reads memory then acts
M_{t+1} = U( M_t, x_t, a_t, o_t, r_t )   (2)  — memory is updated after action
```

Where `π_θ` is the policy (prompted or fine-tuned LLM), `R` reads from memory, `U` writes to/manages memory, `g_t` encodes active goals, `o_t` is environment feedback, and `r_t` is reward. Memory `M_t` serves as the belief state — an internal summary of history standing in for the unobservable true state. The loop is recursive: the agent's decisions determine what gets written, and what is written shapes future decisions.

### 1.2 Three-Dimensional Taxonomy

- **Temporal scope:** Working (context window), Episodic (concrete experiences), Semantic (abstracted knowledge), Procedural (reusable skills/plans). The hard question: *when does an episodic record graduate to semantic status?*
- **Representational substrate:** Context-resident text, vector-indexed stores (FAISS/ANN), structured stores (SQL/KG), executable repositories (code libraries, plan templates), and hybrid stores (e.g., MemGPT's 3-tier architecture).
- **Control policy:** Heuristic (fixed top-k, time-based eviction), Prompted self-control (LLM calls memory tools), Learned control (RL-optimized memory actions via GRPO).

### 1.3 Five Mechanism Families

**Family 1 — Context-resident compression (Section 4.1):**  
Keep memory in the prompt via sliding windows, rolling summaries, hierarchical summaries, or task-conditioned compression. Self-Controlled Memory [Liang et al., 2023] lets the agent choose which segments keep full detail. Core pathology is *summarization drift*: after ~3 compression cycles, rare-but-critical facts vanish. Extending context windows to 200k tokens delays but does not eliminate the problem; attention cost is quadratic.

**Family 2 — Retrieval-augmented stores (Section 4.2):**  
Populate an external store with interaction records, then retrieve via dense passage retrieval (DPR + FAISS), BM25 sparse retrieval, metadata filters, or multi-query fan-out with result fusion. Key design choices:
- Indexing granularity: fine-grained (individual turns) vs coarse-grained (full sessions) → pragmatic sweet spot is multi-granularity.
- Query formulation: raw user input is often a poor retrieval query → LLM-reformulated queries, subgoal-augmented retrieval signals.
- Self-RAG gate [Asai et al., 2024]: decides whether retrieval is warranted at all, cutting unnecessary latency.
- RET-LLM [Sun et al., 2024]: write structured triplets at storage time, query via natural language.

**Family 3 — Reflective self-improving memory (Section 4.3):**  
After task completion, the agent writes natural-language post-mortems (Reflexion), clusters related observations, and synthesizes higher-order reflections (Generative Agents). Retrieval scoring: weighted mix of recency (exponential decay), relevance (embedding similarity), and importance (self-assessed integer). Central risks: *self-reinforcing error* (false beliefs never challenged), *over-generalization* (lesson from one context applied blindly elsewhere). Mitigation: reflection grounding — require citations to specific episodic evidence.

**Family 4 — Hierarchical virtual context (Section 4.4):**  
OS-inspired paging between tiers. MemGPT's three tiers: main context (RAM = system prompt + recent msgs + relevant records), recall storage (disk = searchable DB of all past messages), archival storage (cold = vector-indexed documents). Agent calls memory management functions to move data; an interrupt mechanism passes control on each user message or timer event. Achilles' heel: *orchestration failures are silent* — paging out the wrong record produces a slightly worse response, no error signal.

**Family 5 — Policy-learned memory management (Section 4.5):**  
Agentic Memory (AgeMem) [Yu et al., 2026] treats five memory operations (store, retrieve, update, summarize, discard) as callable tools, then optimizes the entire pipeline with RL. Three-stage training: (1) supervised warm-up on memory demonstrations, (2) task-level RL with outcome rewards, (3) step-level GRPO for denser credit assignment. Learned policies discover non-obvious strategies like proactive summarization before context fills.

**Family 6 — Parametric memory (Section 4.6):**  
Embed memory inside model weights via fine-tuning / adapters. MemLLM [Modarressi et al., 2024] couples parametric and non-parametric knowledge. Hard to audit, hard to delete from, expensive to update — most deployed agents favor non-parametric stores.

### 1.4 Three Architecture Patterns (Section 7.6)

- **Pattern A:** Monolithic context — all memory in the prompt.
- **Pattern B:** Context + retrieval store — working memory in context, long-term records in external vector/structured store.
- **Pattern C:** Tiered memory with learned control — multiple tiers managed by RL-controller. The paper recommends starting with Pattern B and graduating to C only when empirical data shows learned control meaningfully improves the workload.

### 1.5 Engineering Realities

- **Write path:** Filtering, canonicalization, deduplication, priority scoring, metadata tagging. Optimal filtering thresholds are domain-specific.
- **Read path:** Two-stage retrieval (BM25 → cross-encoder reranker), retrieval gating, token budgeting, cache layers for high-frequency records.
- **Staleness handling:** Temporal versioning, source attribution, contradiction detection, periodic consolidation sweeps.
- **Privacy:** Encryption, per-user access scoping, automated PII redaction, configurable retention, auditable deletion across all tiers.
- **Observability:** Log every memory operation with timestamps, triggering context, and involved records. "Memory diffs" between turns provide high diagnostic value.

## 2. Results (benchmark numbers with units)

The paper is a survey, so results are drawn from synthesized findings across cited systems and benchmarks:

### System-Level Results

| System | Key Metric | Value |
|--------|-----------|-------|
| Reflexion | HumanEval pass@1 | 91% (vs. 80% GPT-4 baseline) |
| ReAct | ALFWorld absolute gain | +34% absolute |
| Voyager (with skill library) | Unique items | 3.3× more than prior Minecraft agents |
| Voyager (with skill library) | Tech-tree milestone speed | 15.3× faster than prior agents |
| RETRO (7.5B params) | Benchmarks matched vs. Jurassic-1 (175B) | Matched or exceeded on 10/16 benchmarks |
| Generative Agents (no reflection) | Behavior degradation | Degeneration to repetitive, context-free responses within 48 simulated hours |
| MemoryArena (swap memory for long-context) | Task completion drop | From >80% to ~45% on interdependent multi-session tasks |

### Benchmark Findings

- **LoCoMo** [Maharana et al., 2024]: 35 sessions, 300+ turns, 9k–16k tokens per conversation. RAG-augmented LLMs lag far behind humans, especially on temporal and causal dynamics.
- **MemBench** [Tan et al., 2025]: Distinguishes factual vs. reflective memory, participation vs. observation modes. Metrics span effectiveness, efficiency, and capacity.
- **MemoryAgentBench** [Hu et al., 2025]: Probes four cognitive competencies — accurate retrieval, test-time learning, long-range understanding, selective forgetting. **No current system masters all four.** Most fail conspicuously on selective forgetting.
- **MemoryArena** [He et al., 2026]: Multi-session interdependent tasks in four domains (web navigation, preference-constrained planning, progressive information search, sequential formal reasoning). **Models scoring near-perfectly on LoCoMo plummet to 40–60% in MemoryArena** — exposing the gap between passive recall and active decision-relevant memory use.
- **Cross-benchmark lesson:** The gap between "has memory" and "does not have memory" is often larger than the gap between different LLM backbones.
- **Cost observation:** None of the current benchmarks systematically report efficiency metrics (token consumption, latency overhead) alongside effectiveness numbers.

## 3. Trade-offs (wins vs. loses)

| Aspect | Win | Loss / Cost |
|--------|-----|-------------|
| Context-resident memory | Zero infrastructure, perfect in-window recall, fully transparent | Summarization drift after ~3 compression cycles; quadratic attention cost with longer windows; "lost in the middle" effect — information in center of long contexts recalled less reliably |
| Retrieval-augmented stores | Scales to millions of records, no retraining needed, supports structured queries with DB backends | 200–500ms latency added; retrieval quality bottleneck — surfaces plausible but stale/off-topic records; loses structured causal/temporal relationships |
| Reflective memory | Verbal post-mortems give 11pp gain on HumanEval with no gradient updates | Self-reinforcing error — false belief "approach A always fails" persists forever; over-generalization across contexts; severity scales with agent lifetime |
| Hierarchical memory (MemGPT) | OS-inspired paging gives illusion of unlimited context; interrupt mechanism enables background memory ops | Orchestration failures are *silent* — evicted critical records produce no error, just slightly worse responses; "memory blindness" when cold storage is invisible |
| Learned control (AgeMem) | Discovers non-obvious strategies (proactive summarization); consistently outperforms all baselines on 5 benchmarks | RL training over long horizons is expensive; poor transfer across task distributions; hard to explain/interpret memory actions |
| Parametric memory (fine-tuning) | Seamless integration — model "just knows"; no retrieval latency | Hard to audit, hard to delete from (machine unlearning immature), expensive to update (each fact needs fine-tuning) |
| Long context alone | Simpler architecture | 200k-token models consistently underperform purpose-built memory on selective retrieval; storage not the bottleneck — retrieval quality is; cost scales quadratically |
| Storage maximalism | Never misses a fact | Degraded retrieval precision; governance and privacy headaches; PII redaction becomes harder |

## 4. Design Rationale (why this approach)

The paper's architecture recommendations emerge from empirical and theoretical arguments:

1. **POMDP formalization over ad-hoc design:** Casting memory as a belief state in a POMDP clarifies that agent memory is *not merely a database lookup* — it is about maintaining a sufficient statistic of interaction history for good action selection under computational and storage budgets. This unifies disparate designs under one framework.

2. **Pattern B as pragmatic default:** Context + retrieval store is recommended as the starting point because it balances engineering burden against capability. Pattern A (monolithic context) cannot handle cross-session persistence. Pattern C (learned control) adds training cost and interpretability risk that should be justified by empirical gain.

3. **Memory deserves first-class engineering investment:** The paper argues that model selection gets months of benchmarking while memory architecture "often gets an afternoon." Ablation results consistently show that the memory-vs-no-memory gap exceeds the gap between different LLM backbones — flipping priorities to treat memory as first-class may be the "single highest-leverage intervention available to agent builders."

4. **Write-path filtering is application-specific, not one-size-fits-all:** The optimal false-negative rate for a medical triage agent (near-zero) differs from a casual chat assistant (tolerable). Write-path design should be informed by a risk analysis mapping memory failure modes to downstream consequences.

5. **Observability as the missing production bridge:** Memory operation logging, replay tools, and "memory diff" diagnostics are rarely discussed in research but are the primary reason demo-stage systems fail in production. Techniques borrowed from database engineering (query performance monitoring, index optimization) would significantly improve reliability.

## 5. Limitations & Failure Modes

1. **Summarization drift:** After 3+ compression cycles, rare-but-critical facts vanish silently. The agent "remembers" a sanitized, generic version of history that fails on edge cases.

2. **Self-reinforcing error in reflective memory:** If the agent incorrectly concludes "approach A always fails," it avoids that path forever, never collecting disconfirming evidence. Severity scales with agent lifetime — catastrophic in long-running production agents.

3. **Silent orchestration failures in hierarchical memory:** Evicting the wrong record from context produces no error, just a slightly worse response. Requires detailed logging for diagnosis — investment few systems make.

4. **No system masters selective forgetting:** MemoryAgentBench shows most systems fail conspicuously on forgetting. Current approaches are crude: hard time-based expiration, storage-limit eviction, or nothing. Inability to discard outdated information gradually poisons retrieval precision.

5. **Cross-session coherence is underexplored:** Maintaining consistent knowledge and behavior across sessions separated by hours/days is a distinct unsolved challenge. MemoryArena's multi-session tasks reveal performance drops from near-perfect to 40–60%.

6. **No community-standard evaluation harness:** Each benchmark uses its own datasets, metrics, and protocols, making cross-paper comparison unreliable.

7. **Cost-efficiency blind spot:** No current benchmark systematically reports token consumption and latency overhead alongside accuracy — reported gains may not be "free."

8. **Retrieval quality, not storage capacity, is the bottleneck:** Agents routinely surface plausible but stale or off-topic records. Causal retrieval (retrieving by what *caused* something, not what is *similar*) remains largely unexplored.

9. **Privacy governance immaturity:** Machine unlearning for parametric memory is not production-ready. Deletion compliance across all tiers (including vector indices and backups) is rarely implemented.

10. **No strong cross-domain memory transfer:** Identifying which memories generalize across domains vs. which are context-specific remains an open problem.

11. **Multi-agent memory governance is uncharted:** Access control over shared stores, consensus protocols for concurrent writes, and principled boundaries between shared/private memory are unexplored.

## 6. Transfer to Lyra

### The One Idea

**Adopt a Pattern-B memory architecture (Context + Retrieval Store) with multi-signal retrieval scoring and operation-level observability logging, graduated to Pattern C (learned control via RL) only when empirical benchmarks prove the cost is justified.**

Specifically for Lyra:

1. **Implement the write-manage-read loop** (Equations 1-2): Every session interaction gets stored in an external retrieval store with metadata tagging (timestamp, session ID, task label, importance score). The read path uses multi-signal retrieval: recency (exponential decay), relevance (embedding similarity), and importance (self-assessed integer).

2. **Add memory operation observability:** Log every write, read, update, and delete with timestamps and triggering context. Implement "memory diffs" between conversation turns for debugging — this is the single most underinvested practical necessity identified in the paper.

3. **Use two-stage retrieval:** Fast BM25/metadata filter → cross-encoder reranker. Add a retrieval-or-not gate to skip retrieval for straightforward tasks (saves latency and tokens).

4. **Implement write-path quality:** Filter low-signal records (small talk, redundant confirmations), canonicalize entities, deduplicate overlapping entries, score by priority and novelty.

5. **Adopt dual-buffer consolidation:** Newly formed memories sit in a "hot buffer" during a probation period and are promoted to long-term storage only after passing quality checks (re-verification, deduplication, importance scoring). This parallels hippocampal-to-neocortical transfer and prevents noise accumulation.

### Workstream Route

**§4.2 — Memory & Context Engine**

The paper directly maps to Lyra's memory subsystem architecture. The write-manage-read loop formalization, three-axis taxonomy, five mechanism families, and practical engineering patterns (write-path filtering, read-path optimization, staleness handling, observability) provide a complete design blueprint.

### Impact / Effort / Tier

- **Impact:** 5 — Memory is identified as the single highest-leverage intervention; the memory-vs-no-memory gap exceeds the LLM-backbone gap.
- **Effort:** 3 — Pattern B is well-documented with off-the-shelf components (vector DB + BM25 + cross-encoder). Pattern C requires RL infrastructure.
- **Tier:** **breakthrough** — This survey provides the foundational reference architecture for Lyra's memory subsystem. The POMDP formalization, multi-signal retrieval, and observability logging requirements are directly actionable and differentiate Lyra from long-context-only agents.
