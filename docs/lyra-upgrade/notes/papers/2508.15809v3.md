## 1. Mechanism (step-by-step)

CoQ is a multi-agent framework with 4 specialized agents orchestrated in a pipeline for SQL-aided table understanding. The core problem: given a 2-tuple X = (Q, T) where Q is a natural language question and T = {S, D} is a table (schema S, data D), identify the relevant data subset Dr ⊆ D and derive answer A.

### Agent 1: Semantic Splitter (Schema Abstraction + Parallel Decomposition)

**Natural-Language-Style Table Schema:**
Replaces raw table input with a 3-component natural-language representation:
- **Table Name:** Concise keywords summarizing table content/purpose
- **Table Headers:** List of (column name, column value type) pairs — provides structural abstraction without layout noise
- **Value Examples:** Random sampled rows in PIPE format (pipe-delimited, "|" separators) — proven to improve LLM table task performance

Key insight: SQL generation depends primarily on high-level schema information, not detailed cell contents. Expressing schema in natural language aligns with LLMs' pretraining strengths as language models.

**Parallel Decomposition:**
Splits complex questions into semantically independent sub-questions. Unlike sequential decomposition (where error in sub-question i cascades to i+1), CoQ identifies questions targeting disjoint table regions with no interdependencies. Each sub-question is self-contained (no pronouns referencing entities from other sub-questions).

### Agent 2: SQL Query Generator (Clause-by-Clause Strategy)

Five SQL clause types are defined:
1. **SELECT-FROM clause:** Foundation — selects task-relevant columns
2. **WHERE clause:** Row filtering based on question-relevant conditions
3. **WITH AS clause:** CTE for intermediate transformations (new columns, splitting/concatenating existing ones)
4. **Aggregate function clause:** COUNT, SUM, AVG, MAX, MIN operations
5. **ORDER BY clause:** Sorting for ranking/positional reasoning

The generation process:
1. Start with basic SELECT-FROM selecting relevant columns
2. Sample representative rows for the Planner to observe data patterns
3. Each subsequent clause is appended one at a time under Dynamic Planner guidance
4. After each clause addition, the query is executed for validation
5. If execution fails, error is traced to the most recently added clause for targeted correction
6. If correction fails, the agent **reverts to the last validated query** (rollback mechanism)
7. Forms a chain of progressively refined queries where each step builds on a validated state

### Agent 3: Dynamic Planner (Hybrid Reasoning Division + Early Stopping)

**Hybrid Reasoning Division Strategy:**
- **Mechanical reasoning** (filtering, aggregation, arithmetic) → delegated to SQL
- **Logical reasoning** (comparison, inference, interpretation) → delegated to LLM
- Crucially: SQL execution results are treated as **intermediate data**, NOT final answers
- LLM receives SQL outputs and applies inference to produce the answer

**Sufficiency-based Early Stopping (Algorithm 1):**
```
Algorithm 1: SUFFICIENCY-BASED EARLY STOPPING
Input:  (Q, T) — question Q, table T = (S, D)
Output: D̂ — extracted data subset sufficient to answer Q

1. chain ← [Generator(Q, T)]
2. repeat:
3.   sql ← chain[-1]
4.   D' ← ExecuteSQL(T, sql)
5.   plan ← Planner(Q, S, sql, D')
6.   if plan ≠ STOP then:
7.     next_sql ← Generator(Q, T, chain, plan)
8.     chain.append(next_sql)
9. until plan = STOP
10. D̂ ← D'
11. return D̂
```

The Planner decides: "Is the current SQL result sufficient to answer the question?" If yes, stop. If no, select the next clause type to append. This prevents over-generation of complex SQL and ensures reasoning depth adapts to question complexity.

### Agent 4: Answer Generator
- Produces sub-answers from each sub-question's SQL results
- Combines all sub-answers into a single, cohesive natural language final answer
- Integrates localized reasoning results fluently without listing/numering

## 3. Trade-offs

| Win | Lose |
|-----|------|
| +13.66% accuracy on WikiTQ over SOTA with GPT-3.5 | More LLM calls than simplest baselines (mean 7.63 vs. 1-3 for single-prompt methods) |
| Invalid SQL rate slashed from 9.48% to 3.34% (GPT-3.5) | Requires SQL execution environment (SQLite) — cannot work with non-relational structured data |
| Robust to structurally complex tables (IM-TQA: 74.96% vs. 68.90%) | Natural-language schema may lose fine-grained value-level information on large tables |
| CoQ + GPT-3.5 beats vanilla GPT-4.1 on WikiTQ (74.77% vs. 70.97%) | Prompt engineering overhead: 11 distinct prompt templates for different agents and clause types |
| Graceful degradation via rollback-to-last-valid-query | Extra latency from iterative clause validation and SQL execution at each step |
| Modest token cost increase for large accuracy gain (cost ~$0.00668 vs. $0.00632 for H-STAR on hard subset) | Only tested on English + Chinese; multilingual generalization unvalidated |
| Works across open-source (LLaMA 2, 3.1, DeepSeek-V3) and closed-source (GPT-3.5, 4.1) backbones | 29% of errors on hard cases are annotation noise, not fixable by system improvements |
| -18.81% accuracy drop when removing hybrid reasoning → validates architecture | Clause-by-clause approach requires careful ordering and cannot handle arbitrary SQL patterns |

## 4. Design Rationale

The paper's core question: "Is a natural-language-style schema sufficient for SQL generation?" The answer is yes, because SQL generation depends primarily on high-level schema semantics (column names, types), not detailed cell values. Expressing schema in natural language aligns with LLM pretraining while bypassing their known weakness with structured/tabular formats.

**Why clause-by-clause instead of single-shot SQL generation:** Single-shot generation of complex, multi-clause SQL is brittle — small errors cascade. By incrementally constructing queries and validating each addition, errors are localized to the most recent clause. The rollback mechanism ensures the system always has at least one executable query. This is effectively a form of validated iterative refinement.

**Why hybrid reasoning instead of SQL-only reasoning:** Pure SQL approaches force all logic (including comparison, inference, contextual interpretation) into SQL, producing long, fragile queries coupled to specific data formats. By separating mechanical operations (SQL: filtering, aggregation, arithmetic) from logical operations (LLM: comparison, inference), each system operates in its zone of competence. The key innovation is treating SQL outputs as intermediate data, not final answers — this relaxes the precision requirement on SQL and enables the LLM to handle edge cases (e.g., string format variations, ambiguous values).

**Why parallel decomposition instead of sequential:** Sequential decomposition creates cascading error dependency. Many complex table questions involve semantically independent sub-regions that can be processed in parallel, reducing failure correlation.

## 5. Limitations & Failure Modes

1. **Language generalisation unknown:** Only tested on English (WikiTQ, TabFact, FeTaQA, Open-WikiTable) and Chinese (IM-TQA). Performance on other languages entirely unexplored.
2. **SQL-only execution backend:** Requires a SQLite database — cannot generalize to non-tabular structured data (graphs, trees, JSON). The paper acknowledges this as a direction for future work (Appendix I.3).
3. **Natural-language schema information loss:** Random-sampled value examples may miss critical edge cases or structural irregularities (e.g., "total" aggregate rows). The paper notes that "noisy sampled values may occasionally mislead the model" in bridge-type questions (Appendix J.4).
4. **Annotation-dependent evaluation:** 29% of errors on the challenging subset stem from incorrect gold annotations (ambiguous questions, semantically equivalent answers in different formats). This inflates the apparent error rate.
5. **No multi-turn/dialogue support:** The framework operates on single-turn QA. Real-world table understanding often involves follow-up questions, refinement, and clarification.
6. **Computational overhead for simple cases:** For straightforward lookup questions, the multi-agent pipeline adds unnecessary LLM calls and latency compared to single-shot approaches.
7. **Prompt fragility:** 11 distinct prompt templates with detailed constraints — small prompt changes could significantly alter behavior; no systematic prompt robustness analysis was conducted.
8. **Query safety:** No discussion of SQL injection risks or sandboxing guarantees. The SQL executor runs arbitrary LLM-generated SQL.
9. **String matching noise tolerance is partial:** The fuzzy matching heuristic (LIKE, IN) handles minor variations but cannot cover all structural noise patterns in real-world tables.

## 6. Transfer to Lyra

**The ONE transferable idea:** **Hybrid Reasoning Division with Sufficiency-based Early Stopping.** CoQ's core insight — separating mechanical/structural operations from logical/semantic inference, with a principled stopping criterion — is directly applicable to Lyra's agent architecture. Rather than having the LLM attempt to handle everything (code execution, parsing, AND reasoning), Lyra should (1) delegate deterministic, structural operations to tool-backed subsystems (SQL/code executor equivalent), (2) reserve the LLM for logical inference and synthesis over intermediate results, and (3) use a sufficiency check as the termination condition for iterative refinement loops, preventing over-generation.

**Workstream route:** §4.2 (Agent Reasoning & Planning Architecture). This directly informs Lyra's planner design — the Dynamic Planner's decision loop (check sufficiency → choose next action → execute → validate → repeat) is a template for Lyra's own planning-execution-verification cycle. The rollback mechanism (revert to last valid state on failure) also maps to Lyra's error recovery patterns.

**Impact:** 4 — fundamental architectural pattern applicable across Lyra's core reasoning loop.
**Effort:** 3 — requires thoughtful decomposition of operations into "mechanical vs. logical" categories and implementation of a sufficiency-check gating mechanism, but the pattern is clean and well-defined.
**Tier:** Breakthrough. This is not an incremental prompt engineering trick but a principled architecture for hybrid symbolic-neural reasoning that directly addresses Lyra's core challenge of reliable multi-step planning.
