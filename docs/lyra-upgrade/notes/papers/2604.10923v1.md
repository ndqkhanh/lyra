## 1. Mechanism (step-by-step, equations, algorithms)

Mem2Evolve introduces a **co-evolutionary paradigm** that couples dynamic capability expansion with experience distillation via a Dual-Memory architecture:

**Dual-Memory Mechanism:**
- **Asset Memory** M_A = B_agt ∪ B_tool: stores reusable execution-ready capabilities
  - Agent Bank B_agt: each agent defined as m_agt = ⟨ρ, ε, σ, T_avail⟩ (role, expertise, suggestions, available tools)
  - Tool Bank B_tool: each tool defined as m_tool = ⟨n, d_func, c_impl, ω_doc⟩ (name, functional description, implementation code, I/O documentation), MCP-compliant
- **Experience Memory** M_E = E_agt ∪ E_tool: each item e = ⟨h_title, d_desc, U_case, κ_content⟩
  - Agent Experience: strategic insights from trajectory reflections
  - Tool Experience: implementation guidelines from creation/debugging processes

**Forward Inference (3 phases):**
1. **Task Planning:** LLM π_θ decomposes query q_t into sub-tasks S = {s_1, ..., s_k}
2. **Asset Recruitment** via Recruitment Function Γ(s_i):
   - If sim(s_i, M_A) ≥ δ: reuse existing assets (top-1 for agents, top-k for tools)
   - Otherwise: Create new assets conditioned on experience and web search
     - Tool Creation: m_new_tool ~ π_θ(s_i | Retrieve(s_i, E_tool), Web(s_i))
     - Agent Creation: synthesize new expert agents from task requirements
3. **Execution:** ReAct-based, aggregating results {r_1, ..., r_k} → final answer a_t

**Backward Evolution (3 phases):**
1. **Trajectory Evaluation:** LLM-as-Judge produces r_t ∈ {0,1} (success/failure) and c_t (critique)
2. **Asset Memory Evolution:** Self-Correction Loop
   - Validate: LLM synthesizes test cases from critique, executes new assets against them
   - If r_t=1 AND Valid(m_new, c_t) → keep; otherwise Improve(m_new, c_t) iteratively
   - On validation pass: M_A ← M_A ∪ {m_final}
3. **Experience Memory Evolution:**
   - Success (r_t=1): abstract high-level guidelines, strategic advice, coordination patterns
   - Failure (r_t=0): encode anti-patterns, failure-fix pairs
   - M_E ← M_E ∪ {e_new}

**Experience-Guided Tool Creation (3-stage strategy):**
1. Tool Spec Generation: formal spec with name, I/O, core logic steps
2. Tool Documentation + Experience Collection: web search (GitHub, Stack Overflow) + Experience Memory retrieval
3. Tool Implementation: MCP-compliant code generation

## 2. Results (real benchmark numbers with units)

All experiments use GPT-5-chat as LLM backbone. Total: 6 task categories, 8 benchmarks.

**Main Results (Pass@1 %):**
| Benchmark | Best Baseline | Mem2Evolve | Δ |
|---|---|---|---|
| GAIA (L1/L2/L3/Total) | 81.13/75.58/46.15/72.73 (Alita) | 88.68/82.56/57.69/76.31 | +3.58 total |
| ALFWorld | 93.40 (AFLOW) | 94.31 | +0.91 |
| HotpotQA | 60.80 (AFLOW) | 60.80 | tie |
| 2WikiMultihopQA | 80.00 (SwarmAgentic) | 82.00 | +2.00 |
| AIME24 | 70.00 (Alita) | 76.70 | +6.70 |
| AIME25 | 66.67 (Alita) | 73.33 | +6.66 |
| TravelPlanner | 59.14 (SwarmAgentic) | 59.25 | +0.11 |
| WebShop | 37.90 (AFLOW) | 39.20 | +1.30 |
| **Average** | 63.78 (Alita) | **70.24** | **+6.46** |

Vs. naive LLMs: +18.53%. Vs. experience-only: +11.80%. Vs. OpenAI DeepResearch on GAIA: 76.31 vs 67.36 (+8.95).

**Ablation Study:**
- w/o Tool Creation: -10.28% (largest drop)
- w/o Expert Agent Creation: -1.72%
- w/o Tool Memory: -3.13%
- w/o Agent Memory: -4.73%

**Experience-Guided Creation Analysis:**
- First-Pass Validity increase: GAIA +18.3% (32.7→51.0), AIME24 +18.9%, AIME25 +20.6%
- Average Improve Iterations reduction: GAIA -0.51 (1.45→0.94), AIME24 -0.52, AIME25 -0.56

**Single-Task Self-Evolution:** Memory initialization from same task consistently improves performance, with most gains from small memory fraction (diminishing returns beyond ~25% initial memory).

**Cross-Task Self-Evolution:** Heterogeneous memory from GAIA transfers to 7 other benchmarks; performance matches or exceeds 25% single-task initialization.

## 3. Trade-offs (wins vs loses)

**Wins:**
- Dynamic capability expansion: creates new tools/agents on demand, not bounded by static library
- Experience stabilizes asset creation: 56% higher first-pass validity, 68% fewer fix iterations
- Cross-task memory reuse without negative transfer
- MCP-compliant tool generation ensures model-agnostic interoperability
- Self-correction loop with unit test validation prevents low-quality assets from entering Asset Memory

**Loses:**
- Requires sandboxed code execution (SandboxFusion) → limits open-world deployment
- LLM-as-Judge for trajectory evaluation is noisy (no ground truth assumed)
- Forward inference + backward evolution ~2x more LLM calls than static baselines
- Expert agent creation contributes only +1.72% gain (tools dominate)
- WebShop gain is modest (+1.30%), suggesting web navigation remains hard even with co-evolution
- Memory scalability not tested beyond ~200 tasks; retrieval quality may degrade with very large Asset/Experience Memory

## 4. Design Rationale (why this approach)

The authors ground their design in **Piaget's equilibrium theory**: intelligence evolves through interplay of assimilation (integrating new experiences, the "forward" pass) and accommodation (adapting internal structures, the "backward" pass). This maps to:
- **Experience-centric agents** = assimilation only (learn from past but cannot expand capability space)
- **Capability-centric agents** = accommodation only (create new capabilities without experiential guidance)
- **Mem2Evolve** = both loops in equilibrium

The "Reuse first, Create on demand" strategy is rational: most sub-tasks should reuse existing assets (efficiency), only triggering expensive creation when a capability gap exists. The confidence threshold δ controls this trade-off.

Experience-guided creation addresses the core failure of prior capability-centric approaches: generating tools from scratch leads to non-replicable success and repeated errors. By conditioning tool creation on both web documentation and past experience (success + failure), Mem2Evolve constrains the generation toward feasible, proven patterns.

The Self-Correction Loop with unit tests addresses the LLM reliability problem: correct task answer ≠ robust tool. Validation gate prevents bad assets from polluting Asset Memory.

## 5. Limitations & Failure Modes

1. **Sandbox dependency:** All generated code executes in SandboxFusion; cannot interact with local filesystems or unrestricted network → limits deployment to open-world settings
2. **LLM-as-Judge noise:** No ground-truth labels available during backward evolution (simulates real world). Judge errors propagate into both asset retention and experience distillation
3. **Retrieval quality sensitivity:** The δ threshold and embedding similarity determine whether creation or reuse triggers. Poor similarity matching → unnecessary creation (expensive) or incorrect reuse (wrong tool for task)
4. **Cold start:** Starts with only web search tool. Early evolution cycles may be highly unstable before sufficient experience accumulates
5. **Experience staleness:** No mechanism described for pruning outdated experience; as environment changes, old experience may become harmful
6. **Single-model backbone:** All experiments use GPT-5-chat; no evidence of cross-model generalization. The framework's behavior with weaker models (which hallucinate more) is unknown
7. **Test generation circularity:** LLM both creates tools AND generates validation tests → potential for self-consistent but wrong tool-test pairs
8. **No cost analysis:** No comparison of token cost or latency vs. baselines (critical for practical deployment)

## 6. Transfer to Lyra (one idea + route + Impact/Effort/Tier)

**Idea:** Implement a **Dual-Memory Co-Evolution Loop** in Lyra's agent runtime, where:
- Lyra's Plugin Registry becomes the Asset Memory (tools + specialized sub-agents)
- Session trajectories with reflection become Experience Memory
- When Lyra encounters a task beyond current capability, use experience-guided tool/agent creation
- A self-correction loop validates new assets before registry inclusion

**Route:** §4.2 (Agent Architecture) - extend the existing agent runtime with Asset Memory semantics and a Backward Evolution pass that analyzes task trajectories post-completion

**Impact:** High - would enable Lyra to autonomously expand its capability set over repeated use, reduce human intervention for adding new integrations

**Effort:** High - requires sandboxed code execution, LLM-as-Judge infrastructure, embedding-based retrieval over assets/experiences, and careful orchestration of forward/backward phases

**Tier:** Tier 3 (6+ months) - foundational infrastructure change; depends on plugin system maturity, sandbox safety, and trajectory storage systems
