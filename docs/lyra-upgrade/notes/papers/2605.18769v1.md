## 1. Mechanism (step-by-step)

ClusterRAG is a three-stage pipeline that enhances personalized RAG by borrowing documents from behaviorally similar users.

### Stage 1: User Representation and Retrieval

**Step 1.1 — User Embedding Construction.** Each user `u` has a profile `U_p = {d_1, ..., d_n}` (e.g., historical papers, tweets). Each profile document `d_i` is encoded via ColBERTv2's dense embedding. The user representation `z_u` is the mean of document embeddings:

```
z_u = (1/n_u) * sum_{i=1}^{n_u} f(d_i)      (Equation 1)
```

where `f(·)` is the ColBERTv2 embedding function.

**Step 1.2 — Density-Based User Clustering.** Instead of O(N^2) pairwise similarity, users are grouped via **HDBSCAN** (hierarchical density-based clustering). HDBSCAN automatically determines the number of clusters — critical because the number of user cohorts is unknown a priori. Outliers are assigned to a dedicated noise cluster.

**Step 1.3 — Intra-Cluster Similarity Ranking.** For each cluster `C`, an intra-cluster similarity matrix `R^C` is constructed:

```
R^C_{u,v} = ColBERTv2(z_u, z_v)              (Equation 2)
```

where `u, v ∈ C` and `v ≠ u`. Diagonal self-similarity entries are discarded. For each user, the **top-k** most similar users within the cluster are retained.

### Stage 2: Profile Retrieval

**Step 2.1 — Retrieval Mode Selection.** Three modes:
1. **User-only:** Only the target user's own profile documents.
2. **Collaborative:** Documents from the top-k similar users' profiles (useful for sparse/cold-start users).
3. **Hybrid:** Combines both — this is the primary mode that yields the best results.

**Step 2.2 — Document Clustering.** All candidate profile documents are encoded and partitioned via HDBSCAN into topical clusters `C = {C_1, ..., C_K}` with centroids `M = {μ_1, ..., μ_K}`.

**Step 2.3 — Two-Stage Cluster-Level Retrieval.** The query embedding `e_q` is compared against all centroids to select the top-`B` clusters. Then within each selected cluster, documents are reranked by similarity to `e_q`, and the top-`m` documents are selected. This reduces complexity from **O(N) to O(K + B·N/K)** where `B ≤ K ≤ N`.

**Default hyperparameters:** `k = 1` similar user, `m = 2` profile documents, `γ = 0.55`, beam size 4.

### Stage 3: Personalized Generation

**In-Prompt Augmentation (IPA):** Retrieved profile documents are inserted directly into the LLM prompt. The allocated profile length is computed via a budget formula:

```
|U_p| = G_t(L_max - min(|q|, ⌊γ·L_max⌋))   (Equation 3)
```

where `γ ∈ [0, 1]` balances query space vs. profile space, `L_max = 512` tokens, and `G_t` is a task-specific prompt generator. This formulation works for both training-free (zero-shot) and fine-tuned LLMs.

**Cold-start handling:** When no historical documents exist, the user embedding is derived from the current query alone, defaulting to user-only or hybrid retrieval.

**Key quantitative findings:**
- Hybrid mode (ClusterRAG-H) wins on **every single metric across all 6 tasks**
- ClusterRAG uses only **2 profile documents** vs. baselines requiring 4+ documents (better for low-resource settings)
- Retriever ranking: **ColBERTv2 > BGE > Contriever > BM25 > Recency > Random** (Table 3)
- LLM versatility: Zero-shot FlanT5-XXL and Qwen2-7B-Instruct both benefit (Table 4), pFlan LaMP-1 Acc 0.648, pQwen2 LaMP-5 R-1 0.488
- Ablation: removing user clustering drops MAE from 0.270 to 0.320; removing intra-cluster similarity drops R-1 from 0.521 to 0.501
- Optimal k (similar users) = 3, optimal m (profile docs) = 6-7 (Tables 8-9)
- HDBSCAN Silhouette scores: 0.535-0.601 vs. k-means: 0.274-0.389 (Table 10)
- Training: Quadro RTX 8000 48GB, 10-24 hrs per experiment, FlanT5-base (250M params)

## 3. Trade-offs

| Win | Cost / Trade-off |
|-----|------------------|
| Consistent SOTA across all LaMP tasks (hybrid mode) | Requires offline clustering preprocessing (HDBSCAN) |
| Works with sparse profiles (cold-start resilient) | HDBSCAN hyperparameter sensitivity (min_cluster_size, min_samples) |
| Retriever-agnostic — works with ColBERT, BGE, Contriever, BM25 | ColBERTv2 adds ~0.1M params for late-interaction projection layer |
| Works with both fine-tuned (FlanT5-base, FlanT5-XXL) and zero-shot (Qwen2-7B-Instruct) LLMs | Performance ceiling bound by underlying LLM quality |
| Only 2 profile documents needed (vs. 4+ for baselines) | Two-stage retrieval adds latency vs. single-pass retrieval |
| Graceful degradation to user-only mode when collaborative signals unavailable | Cluster centroid storage overhead grows with cluster count K |
| HDBSCAN auto-discovers cluster count (no need to specify k) | Embedding precomputation needed; not fully online |

## 4. Design Rationale

1. **HDBSCAN over k-means:** Density-based clustering auto-discovers the number of user cohorts (unknown a priori) and handles variable-density groups. Ablation shows HDBSCAN Silhouette scores 0.535-0.601 vs k-means 0.274-0.389, validating this choice.

2. **ColBERTv2 for both user similarity and document ranking:** Late-interaction (token-level) matching gives richer similarity signals than single-vector cosine similarity. The v2 variant adds residual compression and denoised supervision for generalization. It serves dual purpose: intra-cluster user ranking + document retrieval/reranking.

3. **Two-stage retrieval (cluster-then-document):** Reduces complexity from O(N) to O(K + B·N/K). This is critical for scaling to millions of users/documents. Topical clustering ensures coherence of retrieved documents.

4. **IPA over model-modification approaches:** In-Prompt Augmentation works with any generative model (training-free or fine-tuned), unlike prefix-tuning or LoRA which require per-user adapters. This is essential for model-agnostic deployment.

5. **Averaging document embeddings** for user representation: Simple, efficient, and avoids the need for learned user embeddings that require per-user training.

## 5. Limitations and Failure Modes

1. **English-only, text-only:** No evaluation on multilingual or multimodal datasets. LaMP-1 and LaMP-5 provide only paper abstracts (not full text), limiting contextual depth.

2. **Prompt engineering not optimized:** The IPA strategy is basic; more advanced structured prompt formulations could further improve results but were not the study's focus.

3. **LLM-dependency ceiling:** End performance inherits all limitations of the underlying LLM (hallucinations, biases, context window constraints).

4. **Static embeddings:** User embeddings are precomputed offline — evolving user profiles require periodic batch re-clustering or incremental update strategies (discussed but not implemented).

5. **Cold-start quality:** When user history is absent, the embedding is derived from a single query — inherently weaker than profile-based embeddings.

6. **Collaborative bias amplification:** Similar users may reinforce existing biases (acknowledged in ethical considerations). No fairness metrics reported.

7. **Single experimental run:** Results are from one run (stated explicitly), so variance across random seeds is not characterized.

8. **LaMP-6 excluded:** Email subject generation task not evaluated because data is not publicly available.

## 6. Transfer to Lyra

**The one transferable idea:** Cluster-based collaborative filtering for personalized context retrieval — group Lyra users/agents by behavioral similarity via HDBSCAN, then retrieve interaction histories from top-k similar users to enrich prompt context when a target user's own history is sparse (cold-start or low-activity users).

**Workstream route:** §4.2 — Memory (user/agent profiling and context retrieval)

**Impact:** 4/5 — Directly addresses the cold-start and sparse-profile problem that plagues personalized agents. Lyra serves many users with varying activity levels; collaborative retrieval from similar users is a lightweight alternative to per-user fine-tuning.

**Effort:** 3/5 — Requires:
- User embedding pipeline (aggregate interaction documents → ColBERTv2 or equivalent → mean pooling)
- HDBSCAN clustering infrastructure (offline batch)
- Modification to Lyra's retriever to support collaborative + hybrid retrieval modes
- Prompt template modification for IPA with budget allocation

**Tier:** **breakthrough** — This is a novel capability (cluster-based CF for agent personalization) with strong empirical evidence across diverse tasks, and the retriever-agnostic design means it can integrate with Lyra's existing retrieval stack without disruptive changes.
