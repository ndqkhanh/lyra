## 1. Mechanism (Step-by-Step)

### 1.1 Problem Formulation: Action-World Interaction Loop

The paper formulates multimodal agent memory as a formal interaction loop. At step `t`:

- The world has a **latent state** `z_t` (not directly observable).
- The agent receives a partial **observation** `o_t = Ω(z_t)` (language, visual inputs, logs).
- The agent selects an **action** `a_t = π(o_t, m_t)` based on the observation and its current memory state `m_t`.
- The environment executes the action and returns **feedback** `f_t`: `(z_{t+1}, f_t) = ℰ(z_t, a_t)`.

The full trajectory `τ = (x; η_1, ..., η_T)` records `η_t = (o_t, a_t, f_t)`. Trajectories are segmented into sessions: `τ = τ^(1) ◦ τ^(2) ◦ ... ◦ τ^(S)`. The world state persists across sessions, while the agent only observes local context per session — creating the core memory problem.

### 1.2 Four-Stage Memory Lifecycle (Diagnostic Framework)

The framework decomposes memory evaluation into four observable stages with stage-specific annotations:

**Stage 1 — Observe to Write**:
- Given previous memory `m_{s-1}` and session trajectory `τ^(s)`, the system produces a memory delta `Δ_s = Write(m_{s-1}, τ^(s))`.
- Goal: selective retention — identify which evidence will be useful for future sessions, not a full transcript dump.
- Evaluated via: Memory Recall (coverage against gold memory points), Memory Correctness, Hallucination, Irrelevance.

**Stage 2 — Update and Consolidate**:
- `m_s = Maintain(m_{s-1}, Δ_s)`. Must support revision, consolidation, removal as user preferences, task states, and environmental evidence evolve.
- Evaluated via: Update Handling (correctly replacing stale facts), Interference Rejection (not storing noise/jokes/corrections).
- Update scoring: `Update = (1.0·N_updated + 0.5·N_both + 0.0·N_outdated) / N_total`

**Stage 3 — Retrieve for Decision**:
- For query `q`, retrieval returns `R_{s,q} = Retrieve(m_s, q)`.
- Goal extends beyond semantic similarity to **decision relevance** — retrieved context must contain evidence needed for the current answer or action.
- Evaluated via: Retrieval Coverage (RC, LLM-judge), Recall@K (K ∈ {1,5,10}), NDCG@K (graded relevance with rank discount: `DCG_K = ρ_1 + Σ_{k=2}^K ρ_k / log_2(k+1)`).

**Stage 4 — Use and Act**:
- `ŷ_{s,q} = Answer(q, R_{s,q})`. Failures arise when the system ignores relevant evidence, relies on outdated memory, or fails to translate past experience into appropriate action.
- Evaluated via: QA-Correct, QA-Hallucination, QA-Omission, F1 (token-overlap with stemming, `F1 = 2PR/(P+R)`), BLEU-1.

### 1.3 Benchmark Construction Pipeline

1. **Session Segmentation**: Lifelong Evolution sessions generated from hidden world states; Agentic Execution sessions split at subgoal boundaries, key feedback points, state changes.
2. **Gold Memory Point Extraction**: Facts to retain, state updates to revise, evidence required by future questions.
3. **Merge, Revise, Deduplicate**: Cross-session memory points unified, redundancies removed, temporal consistency enforced.
4. **QA Checkpoint Construction**: Midway and final QA pairs from refined gold memory points, covering 11 question types across 4 axes (Basic, Robustness, Reasoning, Multimodal).

### 1.4 Annotation Schema

- **Gold Memory Points**: Information that should be retained after a session (ground-truth memory content).
- **State Updates**: Where previously stored information becomes outdated and must be revised.
- **Distractors (Interference)**: Plausible but irrelevant/superseded information to test discrimination.
- **Evidence Points**: Subset of gold memory points necessary to answer each question correctly.
- **Per-question type labels**: 11 mutually exclusive types: Fact Recall, Dynamic Update, Memory Boundary, Memory Conflict, Temporal Reasoning, Knowledge Reasoning, Test-Time Learning, Visual Fact Recall, Visual Search, Visual Update, Cross-modal Reasoning.

### 1.5 Evaluated Systems

Three memory paradigms evaluated:
- **Long-Context Agents** (GPT-5.4-mini, DeepSeek V4, Gemini 3 Flash, Claude Haiku 4.5, Qwen3.5 Plus): Full history concatenated as in-context memory — no explicit abstraction, updating, or retrieval.
- **Manually Designed Memory** (MemGPT, Mem0, A-Mem, UniversalRAG, SimpleMem, Omni-SimpleMem, M2A, ViLoMem, MIRIX, AUGUSTUS): Explicit write-update-retrieve pipelines with observable memory states. All use GPT-5.4-nano as backbone.
- **Harness-Based Memory** (OpenClaw + GPT-5.4/DeepSeek-V4, Codex + GPT-5.4): Agents autonomously manage memory through the harness.

### 2.5 Per-Capability Breakdown

- **Lifelong Evolution vs Agentic Execution**: Most systems drop 5-15 percentage points on Agentic Execution.

- **Memory Boundary** (abstaining when answer not in memory): GPT-5.4-mini collapses on this axis despite strength on reasoning.

## 3. Trade-offs (Wins vs Loses)

| Dimension | Win | Loss |
|---|---|---|
| **Memory Storage vs QA Quality** | RAG systems (Qwen3-VL RAG: 86.22% Recall, 98.15% Correctness) build near-perfect memory stores | Same system achieves only 51.86% QA-C — stored evidence not reliably retrieved or used. MemGPT: 57.81% QA-C best overall but still 42.19% failure. |
| **Harness Flexibility vs Reliability** | Harness agents (OpenClaw, Codex) adapt memory strategy to task, outperform most fixed pipelines on agentic tasks | More computationally expensive (100k-120k tokens/session), framework-dependent, same backbone performs differently across harnesses (48-53% QA-C spread). |
| **Text-Only vs Multimodal Memory** | Text-based systems (A-Mem, MemGPT) produce more stable final answers with lower hallucination rates (1.18-2.57%) | Multimodal systems (ViLoMem: 10.65% hallucination) struggle to encode visual evidence — gains from visual access are offset by unreliable visual memory. |
| **Retrieval Coverage vs Precision** | Larger retrieval budgets (K=10) improve recall of relevant evidence | Introduces outdated/conflicting/irrelevant items that hurt answer quality — NDCG degrades, visual redundancy compounds. |
| **Write-Heavy vs Read-Heavy Design** | Write-heavy (A-Mem, MIRIX: front-load ingestion, serve queries fast) | Slow total task time (282-317s); read-heavy (SimpleMem: 786s) re-scans dialogue at query time. M2A (10.0s) balances both. |
| **Append-Only vs Mutable Memory** | Append-only is simpler and preserves all historical information | 53-59% update handling ceiling across all systems — stale facts coexist with new, causing Memory Conflict failures. |
| **Manual Design vs Learned Memory** | Manual pipelines provide structure, transparency, auditability (observable memory state) | Fixed assumptions break in agentic environments; cannot reorganize when task domain shifts (17% performance gap Lifelong Evolution → Agentic Execution). |

## 4. Design Rationale

**Why this approach over alternatives**:

1. **Action-World Loop over static recall benchmarks**: Prior benchmarks (LoCoMo, LongMemEval, MemoryAgentBench) measure recall over static dialogue and collapse memory into single end-of-task accuracy. WorldMemArena treats memory as a process shaped by action and world state evolution, capturing how memory supports dynamic task execution rather than passive retrieval.

2. **Four-stage lifecycle over single-score evaluation**: Without stage decomposition, it is impossible to localize whether a failure originates in writing (missed what mattered), maintenance (kept stale facts), retrieval (did not surface evidence), or use (ignored retrieved evidence). The lifecycle framework enables attribution.

3. **Both Lifelong Evolution AND Agentic Execution**: Exclusively dialog-based benchmarks miss memory from real agent actions/observations/feedback. Exclusively agentic benchmarks miss controlled state evolution. WorldMemArena covers both to test persistent state tracking AND action-grounded experience reuse.

4. **Shared evidence annotations over opaque scores**: Gold memory points, update flags, distractors, and evidence chains create a shared reference base for comparing fundamentally different systems (long-context, RAG, harness) that would otherwise be incommensurable.

5. **Unified adapter interface**: Seven-method `MemoryAdapter` (reset, ingest_turn, end_session, snapshot_memories, export_memory_delta, retrieve, get_capabilities) unifies Python, Qdrant, Neo4j, and external systems under one evaluation protocol.

## 5. Limitations & Failure Modes

### Benchmark Limitations
- **LLM-as-Judge reliability**: All memory quality judgments (Correctness, Hallucination, QA) rely on GPT-5.4-mini as evaluator. Judge bias toward certain answer styles may systematically advantage systems sharing the same model family.
- **Text-centric visual encoding**: Systems compress visual observations to text (captions, OCR, summaries). The benchmark does not test end-to-end visual memory preservation — visual memory is only testable if it was textualized.
- **Simulated environments**: Agentic Execution uses reconstructed trajectories from existing benchmarks (EmbodiedBench, VisualAgentBench, Agent-Arena), not live agent deployment. The closed-world nature may not capture open-ended agent failures.
- **Backbone confounding**: All manually designed memory systems use GPT-5.4-nano. Results may change with different backbones. Long-context baselines use different models, making direct comparison imperfect.

### System Failure Modes Identified
- **Append-dominant maintenance**: All systems default to adding new information rather than revising or deleting obsolete entries. Memory grows unboundedly.
- **Snowball collapse**: Early omissions reduce evidence available for later retrieval. Incorrect answers contaminate subsequent memory updates, creating compounding degradation over long trajectories.
- **Experiential evidence fragility**: Tool feedback, failed actions, visual details, and causal lessons are systematically lost. Textual facts survive; action-grounded knowledge does not.
- **Domain brittleness**: Systems tuned for conversational/document memory perform poorly on agentic trajectories where evidence is distributed across actions, tool outcomes, and environment state transitions.
- **Visual evidence underutilization**: Even multimodal systems default to text-based retrieval, making visual evidence only usable if correctly textualized during writing.
- **Storage-QA decoupling**: High memory coverage does not translate to correct answers — the retrieval-to-use bridge is the primary bottleneck.

## 6. Transfer to Lyra

### The ONE Transferable Idea

**Adopt the four-stage memory lifecycle (Write → Maintain → Retrieve → Use) as Lyra's internal memory evaluation framework.** Rather than measuring memory as a single quality score, decompose Lyra's memory pipeline into observable stages with stage-specific metrics (coverage, correctness, update handling, interference rejection, retrieval coverage, use fidelity). This enables targeted debugging: when memory fails, the framework localizes whether the failure is in (1) writing the right things, (2) maintaining consistency as world state evolves, (3) surfacing relevant evidence at decision time, or (4) correctly using retrieved evidence.

### Assessment

- **Impact**: 4 — Memory is core to Lyra's long-horizon agent architecture. A lifecycle diagnostic framework provides the missing evaluation vocabulary to determine whether Lyra's memory actually works.
- **Effort**: 3 — Requires adding stage-level instrumentation (not a full rewrite). The annotation schema (gold memory points, updates, distractors) can be adapted from the paper's definitions. LLM-as-Judge metrics can reuse Lyra's existing evaluation infrastructure.
- **Tier**: **Investigate** — This is an evaluation methodology paper, not a deployable system. The core value is the diagnostic framework, which Lyra should adopt internally before building any complex memory pipeline. A small-scale internal benchmark following the four-stage lifecycle would validate whether Lyra's emerging memory architecture actually produces usable memory.
