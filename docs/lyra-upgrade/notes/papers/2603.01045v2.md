## 1. Mechanism (step-by-step)

### 1.1 Core Problem Definition

The paper asks whether LLM-based agents can **compute with distributed information** (not merely exchange it). Each agent holds only a local shard of the global input and must coordinate to produce a globally correct answer — a scenario called **information silos**.

### 1.2 Task Space (Communication Complexity Grounding)

Tasks are categorized into 3 levels based on optimal communication complexity (Yao 1979):

| Level | Name | Optimal CC | Topology | Examples |
|-------|------|------------|----------|----------|
| I | Aggregation | O(N) | Star/tree | Global Max, Word Freq, Distributed Vote, Checksum, Top-K |
| II | Mesh Network | O(N) | Linear chain | Prefix Sum, Moving Avg, Trapping Rain, Pipeline Hash |
| III | Global Shuffle | O(N log N) to O(N²) | Full mesh | Distributed Sort, Graph Components, K-Means, PageRank, Matrix Multiply |

Each task τ_k is defined as a triple:

```
τ_k = (f_k, X_k, y*_k)
```

where `f_k` is the computational function, `X_k` is the global input data, and `y*_k` is the ground-truth answer.

### 1.3 Task Construction Pipeline

Tasks are NOT raw LeetCode problems. For each task category, a custom Python generator:
1. Samples `N × k` integers uniformly at random
2. Partitions into `N` equal shards `X₁, ..., X_N`
3. Computes exact ground-truth answer `y* = f(X)`
4. Records fixed random seed for reproducibility

This ensures infinite fresh instances with exact ground truth.

### 1.4 Communication Protocols (3 variants)

**P2P (Peer-to-Peer):** Directed messaging via SQLite-backed mailboxes. Agents call `send_message(target_id, content)`, `receive_messages()`. Agents must decide both WHAT and WHOM to communicate.

**BP (Broadcast):** Each message reaches all agents simultaneously. Central aggregator collects messages each round and distributes compiled history. Agents call `broadcast_message(content)`.

**SFS (Shared File System):** Indirect coordination through shared key-value store. Agents call `read_file(path)`, `write_file(path, content)`. Blackboard architecture — agents never communicate directly.

### 1.5 Evaluation Metrics

**Success Rate (S):** Proportion of agents converging to correct answer.

```
S = (1/N) Σᵢ₌₁ᴺ 1[ŷᵢ = y*]
```

A task instance is "successful" when S = 1 (unanimous convergence).

**Partial Correctness Score (PCS):** Continuous measure — for Level-I: fraction within tolerance; Level-II: fraction of correctly computed elements per segment; Level-III: longest correctly ordered subsequence ratio.

**Token Consumption (C):** Average tokens consumed per agent per round.

**Communication Density (D):** Actual number of directed edges / N(N-1) — captures "how much" communication relative to maximum possible.

**Relative Coordination Cost (RCC):**

```
RCC = 1 - SR(N=k) / SR(N=1)
```

Measures the fraction of single-agent performance lost to coordination overhead.

### 1.6 Execution Pipeline

**Phase 1 — Data Partition:** `PARTITION(X, N) → {X₁, ..., X_N}`, equal-sized shards, no agent privileged.

**Phase 2 — Agent Initialization:** Each agent receives `INIT(i) ← (desc(f, X_i), P)` — task description, local data, protocol constraint. Structural guidance without role prescription.

**Phase 3 — Collaborative Execution:** Iterative rounds (max R_max = 100). All N agents activated in parallel per round. Messages/files from round r visible at start of round r+1. Termination when all agents submit or round limit reached.

**Phase 4 — Metric Computation:** Compute S, PCS, C, D from submitted answers and communication logs.

### 1.7 Key Design Choice: Role-Agnostic Prompts

Prompts provide task-structural information (dependency patterns, coordination approaches) but:
- NEVER assign semantic roles (no "Manager", "Worker", "Coordinator")
- NEVER prescribe execution sequences
- All agents receive structurally identical prompts (modulo ID and data shard)
- Phrase "No single agent has sufficient information" included to prevent premature submission

This isolates coordination capability from role-playing bias.

### 1.8 Experiment Design

Full factorial: `N ∈ {2, 5, 10, 20, 50, 100} × P ∈ {P2P, BP, SFS} × M ∈ {DeepSeek-V3.1, GPT-OSS-120B, Qwen3-Next-80B-A3B}`

Controls: N=1 single-agent baseline (receives complete input, no communication). All models at default temperature, 128K context windows, deployed on GH200 cluster (~500+ GPU-hours per experiment). 1,620 experiments total.

## 3. Trade-offs

| Decision | Wins | Loses |
|----------|------|-------|
| **P2P protocol** | Best at Level-II (mesh/chain tasks); enables task-appropriate routing discovery; highest density → most information exchanged | Higher token consumption (363 tokens/round); density creates redundancy; agents broadcast to unnecessary peers |
| **BP protocol** | Best overall SR (40.4%); lowest token consumption (297/round); simple one-to-all semantics | Creates aggregation bottlenecks at scale; single point of overload on implicit aggregator; hurts Level-III vs P2P |
| **SFS protocol** | Supports asynchronous coordination; good for tasks with temporal decoupling; lowest communication density | Consistently worst SR (31.5%); file-based coordination too slow for rapid synchronization; agents never form direct awareness |
| **Larger agent count** | Parallelizes local computation; Level-I tasks maintain >40% SR even at N=100 | RCC compounds exponentially; Level-III reaches 0% SR at N≥50; density DECREASES at scale when denser coordination is most needed |
| **Role-agnostic design** | Isolates coordination capability from role-playing bias; generates unlimited instances without reengineering prompts | Agents lack structural coordination scaffolds; may explain some failure modes (no designated aggregator to formalize consensus) |
| **Spontaneous leader emergence** | Helps Level-I tasks (slight); agents naturally discover coordination patterns | Catastrophically hurts Level-III (0% SR vs 33.3%); aggregator overwhelmed by global data; centralization creates bottlenecks |
| **Planning round scaffold** | +5-8pp gains on Level-II/III; most effective intervention | Cannot prevent collapse at N≥50; Communication-Reasoning Gap persists regardless |
| **N=1 oracle baseline** | Establishes clear upper bound; isolates coordination overhead via RCC | Single-agent performance itself degrades with input size (confounds attribution for Level-I at high N) |

## 4. Design Rationale

**Why communication-complexity grounding?** The authors argue that existing benchmarks either prescribe fixed communication structures or focus on social simulation. By grounding difficulty in principled communication complexity theory (Yao 1979), observed performance gaps can be attributed to coordination demands rather than ad hoc task choice. This enables the RCC metric — the fraction of single-agent performance lost to coordination — as a clean measure of multi-agent overhead.

**Why role-agnostic?** Role-assignment (e.g., "doctor", "engineer") introduces inductive bias that confounds evaluation of coordination ability. A "doctor" agent may underperform on artistic tasks regardless of coordination quality. By stripping roles, SILO-BENCH isolates whether agents can discover coordination strategies from task structure alone.

**Why real generators instead of static test sets?** Static test suites create overfitting risks. Programmatic generators produce unlimited fresh instances with exact ground truth, enabling reproducible evaluation at any scale without data leakage.

**Why structural guidance without prescription?** Prompts describe dependency patterns (e.g., "cumulative sums from preceding agents") and suggest coordination approaches as options (e.g., "consider establishing a coordinator") but never mandate execution sequences. This tests genuine autonomous coordination discovery — a capability the results show is largely absent.

**Why N=1 baseline?** Single-agent oracle represents the theoretical upper bound. The RCC isolates pure coordination cost from intrinsic task difficulty, enabling the paper's central finding: multi-agent performance collapse is driven by coordination failure, not task hardness.

## 5. Limitations & Failure Modes

### Explicit Limitations (per authors)

1. **Only 3 communication protocols evaluated** — no hierarchical (tree-based), consensus-based (Paxos/Raft), or hybrid protocols tested
2. **Single run per configuration** — due to computational constraints (~500+ GPU-hours per experiment), each (N, P, M) configuration tested once with fixed random seeds; no statistical confidence intervals
3. **Homogeneous agent teams only** — all agents use same model; no heterogeneous model mixing evaluated
4. **Text-only communication** — no tool-use, code execution, or structured data exchange channels beyond natural language
5. **Default temperature** — all models at default sampling parameters; effect of temperature on coordination unexplored
6. **Model scope** — only 3 models tested; GPT-4, Claude, Gemini, Llama families absent
7. **Algorithmic task scope** — 30 tasks inspired by LeetCode; real-world coordination (software engineering, scientific research) may differ
8. **Single-turn verification** — N=1 oracle receives full input in one turn; doesn't account for iterative refinement capability

### Failure Modes Discovered

1. **Premature Submission (37.2%):** Agents commit answers before receiving sufficient information. Even with explicit "No single agent has sufficient information" prompt, agents rush to submit based on partial data.

2. **Consensus Failure (29.9%):** Agents exchange information extensively but produce divergent answers (e.g., 12 distinct answers for XOR checksum, answers ranging 42-238). Communication channels work; agreement mechanisms do not.

3. **Computation Error (28.6%):** Agents receive complete global data but make arithmetic/logic errors during final integration (e.g., submitted 619 instead of 620).

4. **Leader Bottleneck:** Spontaneous leader emergence on Level-III tasks causes the aggregator to become overwhelmed by global data volume, producing 0% success rate.

5. **Scale Collapse:** Performance degrades multiplicatively with scale and complexity — all models reach effectively zero success at N ≥ 50 on Level-III tasks, regardless of protocol or scaffold.

## 6. Transfer to Lyra

### The One Idea

**The Communication-Reasoning Gap:** Agents spontaneously form task-appropriate topologies and exchange information actively, yet systematically fail at the reasoning-integration stage where partial information must be synthesized into correct answers. The PCS-to-SR gap (26pp on Level-I) proves agents hold sufficient information but cannot transform it. This is NOT a context-window problem (context utilization <10% for most runs) — it is a distributed reasoning deficit.

### Application to Lyra Multi-Agent Orchestration

For Lyra's multi-agent workflows (Team mode, Swarm mode, Parallel agents), this paper provides three concrete design mandates:

1. **Never rely on emergent coordination for correctness-critical tasks.** The spontaneous leader emergence data (0% SR on Level-III vs 33.3% without) shows that self-organized centralization produces bottlenecks. Lyra must implement explicit, verifiable consensus protocols for any multi-agent computation where correctness depends on information synthesis.

2. **Implement information sufficiency detection before answer commitment.** Premature submission is the #1 failure mode (37.2%). Lyra agents should track which peers' data they have received and estimate completeness before calling `submit_result()`. A simple heuristic — "have I received messages from >X% of peers?" — could eliminate this failure class.

3. **Measure and track RCC (Relative Coordination Cost) as a Lyra health metric.** RCC = 1 - SR(multi-agent)/SR(single-agent). Run periodic calibration benchmarks comparing single-agent vs multi-agent performance on the same task. Spiking RCC signals coordination degradation and should trigger protocol reselection or scale reduction.

### Concrete Implementation Sketch

```python
# Information sufficiency tracking per agent
class SufficiencyTracker:
    def __init__(self, total_agents: int):
        self.total = total_agents
        self.received_from: set[int] = set()
        self.sufficiency_threshold: float = 0.8  # configurable

    def record_exchange(self, from_agent: int):
        self.received_from.add(from_agent)

    def is_sufficient(self) -> bool:
        return len(self.received_from) / self.total >= self.sufficiency_threshold

    def warn_if_premature(self) -> str | None:
        if not self.is_sufficient():
            return (
                f"WARNING: You have only received data from "
                f"{len(self.received_from)}/{self.total} agents "
                f"({len(self.received_from)/self.total:.0%}). "
                f"Do NOT submit answer until you have data from "
                f"at least {int(self.sufficiency_threshold * self.total)} agents."
            )
        return None

# RCC monitoring integration
def compute_rcc(single_agent_sr: float, multi_agent_sr: float) -> float:
    """Relative Coordination Cost — fraction of single-agent performance lost."""
    return 1.0 - (multi_agent_sr / single_agent_sr) if single_agent_sr > 0 else 1.0
```

### Non-Transferable Aspects

- The specific LeetCode-inspired task generators (Lyra agents solve real-world tasks, not algorithmic puzzles)
- The exact 3-protocol P2P/BP/SFS model (Lyra has its own communication substrate via MCP and worktrees)
- The homogeneous single-model assumption (Lyra supports multi-provider routing)
