## 1. Mechanism (step-by-step)

AUTO REPRODUCE is a three-stage multi-agent pipeline for end-to-end reproduction of AI research experiments. Two specialized agents collaborate: a **Research Agent** (text-centric tasks: summarization, citation analysis) and a **Code Agent** (code-centric tasks: implementation, debugging).

### Stage 1: Literature Review
1. **PDF Extraction:** MinerU converts source PDF to Markdown, preserving math formulas and tables (unlike naive parsing).
2. **Hierarchical Summarization:** Research Agent performs three-level summarization:
   - Holistic paper-level overview
   - Method-specific summary (math formulations, architecture details)
   - Experiment-specific summary (hyperparameters, training configs, evaluation)
3. **Optional Visual Diagram Enrichment:** Agent can ingest architecture diagrams for augmented understanding.

### Stage 2: Paper Lineage (CORE ALGORITHM — Algorithm 1)
```
Input: Paper P, research agent RA, code agent CA, k (default=3), instructions I
Output: K_lineage = {⟨S₁, Code₁⟩, ⟨S₂, Code₂⟩, ...}

1. RA(P, k) → {P₁, ..., Pₖ}    ▷ Select top-k relevant cited papers
2. For each Pᵢ:
   a. Download paper via ArXiv/Semantic Scholar API → Textᵢ
   b. RA(Textᵢ) → (Sᵢ, Uᵢ)     ▷ Extract summary + repo URL
   c. If Uᵢ is valid:
      - Download repo via GitHub API → Repoᵢ
      - CA(Sᵢ, Repoᵢ, I) → Codeᵢ  ▷ Filter relevant source files
      - Kᵢ = ⟨Sᵢ, Codeᵢ⟩         ▷ Summary-code pair
   d. Else: Kᵢ = Sᵢ (summary only, still useful as conceptual knowledge)
   e. Add Kᵢ to K_lineage
3. Return K_lineage
```
- Citation relevance is determined by analyzing in-text citation context within the source paper's full text.
- Comparison baselines in the experimental section are prioritized as the most critical references.
- Top-k relevant papers are validated against expert-curated gold-standard references (Top-1 Recall@3 = ~0.43 for Claude-3.5-Sonnet).

### Stage 3: Code Development (three sub-stages)
**3a. Data Acquisition:**
- Dataset categorization: standard benchmarks (use torchvision/established libraries) vs. custom datasets (provide preprocessing pipelines).
- Proactive inference mechanism: Code Agent generates analysis code on sampled mini-batches to extract tensor shapes and data types, preventing runtime shape mismatch errors.

**3b. Method Replication:**
- Dual-agent iterative loop:
  - Code Agent synthesizes implementation from paper summary + data attributes + lineage knowledge
  - Research Agent validates against method summary, provides corrective feedback, dynamically updates summary
- Lineage `<summary, code>` tuples serve as domain-aligned reference exemplars.
- **EDIT command:** Granular line-range replacement (`EDIT\n N M\n<new code>\n`) instead of full-file regeneration. Reduces token overhead. Error analysis + code editing decoupled into two inference steps.

**3c. Experiment Execution:**
- Mini-batch sampling for accelerated debugging (avoids full-dataset runs).
- Early-exit mechanisms (e.g., `break` after N steps) for dry-run validation of epoch configs.
- Final refactoring pass removes debug scaffolding, early-exits, and cleans generated code.
- Docker container provides Python runtime (PyTorch, NumPy); missing deps installed via `bash` commands.

**Debugging Protocol:**
- Max 20 debug tries per sub-phase (bugs typically resolved in 5-8 iterations).
- Sampling-based unit testing: run on mini-batches, not full datasets.

## 3. Trade-offs

| Win | Lose / Cost |
|---|---|
| 92-95% execution rate vs. 2-18% for baselines | Requires reference code repos for lineage; papers without repos get summary-only (weaker signal) |
| Perf Gap drops from ~99 (ChatDev) to <25 (Gemini-2.5-Pro) | Cost per reproduction: $1.87 (o3-mini), plus compute for GPU runs |
| Paper lineage provides implicit domain knowledge (tacit conventions, implementation practices) | Paper lineage selection recall is moderate (~43% Top-1 Recall@3 with Claude-3.5-Sonnet); misses 57% of expert-identified most-relevant references |
| EDIT command (line-range replacement) cuts token overhead vs. full-file regeneration | Granular editing can introduce line-offset bugs when context shifts |
| Mixed-level evaluation correlates better with humans (r=0.81) than paper-level (r=0.48) | Mixed-level requires both paper extraction AND reference code, increasing evaluation cost |
| MinerU PDF parsing significantly improves extraction fidelity (+11.55 Mixed-Level over naive parsing) | Visual diagram augmentation provides only marginal gain (~0.17 Mixed-Level) |
| Debugging+refinement critical: removing both drops Perf Gap from 31.62 → 88.78 | Max 20 debug attempts; bugs beyond this threshold remain unfixed |
| Works across 13 diverse AI sub-domains (CV, NLP, time series, PDEs, etc.) | Single-experiment only; cannot handle repo-level multi-experiment reproduction |
| Decouples error analysis from code editing — higher success rate | Two-step process increases total inference calls |

## 4. Design Rationale

- **Paper lineage over pure RAG:** Authors observed that domain-specific tacit knowledge (common module architectures, data processing pipelines) is rarely stated explicitly in papers but emerges from cited literature. Mining the citation graph + associated repos captures this implicit knowledge better than retrieving general web knowledge.
- **Sampling-based unit testing over full execution:** Full dataset execution is too slow for iterative debugging. Mini-batch sampling provides rapid feedback (shape validation, data flow) while keeping iteration cycles short.
- **Dual-agent (research + code) over single agent:** Research tasks (summarization, citation analysis) and code tasks (implementation, debugging) require different expertise and tool access. Decoupling prevents context pollution and enables specialized prompt engineering per role.
- **EDIT command over full-file regeneration:** Token efficiency. Most bugs localize to a few lines; regenerating entire files wastes context budget and risks introducing new errors elsewhere.
- **Mixed-level evaluation over paper-only or code-only:** Paper-level inflates scores (rewards broad similarity); code-level deflates them (penalizes syntactic variation). Mixed-level grounds abstract requirements in concrete implementation patterns, yielding scores that correlate best with human judgment (r=0.81-0.83).

## 5. Limitations & Failure Modes

1. **Single-experiment scope:** Framework reproduces individual experiments, not full repositories with multiple interacting experiments and baselines.
2. **Data preprocessing gap:** Requires human-provided preprocessing pipelines for custom datasets. Cannot autonomously infer data cleaning/preprocessing steps from papers alone.
3. **Moderate lineage recall:** Top-1 Recall@3 ~0.43 means the most relevant reference paper is missed 57% of the time. Missed lineage degrades method replication quality.
4. **Debug ceiling:** Max 20 debug iterations; complex data flow errors (incorrect tensor shapes in deep architectures) are the #1 source of remaining failures. Pretrained model architectures are particularly error-prone (hidden dims, norm layer configs).
5. **No license-violation guard:** System clones repos automatically; no built-in license compliance checking beyond the manual audit in the appendix.
6. **LLM judge bias:** Evaluation uses o1 as judge; overrates consistency for text-based comparisons. Mixed-level mitigates but does not eliminate this.
7. **Training config omissions:** Source papers frequently omit learning rate decay strategies and schedulers — no mechanism to infer these from code lineage alone.
8. **Cost scaling:** $1.87/experiment with o3-mini is affordable, but evaluating with o1 judge ($20/benchmark run) accumulates. Not tested at scale (hundreds of papers).
9. **Concurrency/parallelism:** No multi-experiment parallel reproduction mentioned; sequential pipeline only.

## 6. Transfer to Lyra

**The ONE Transferable Idea: Paper Lineage Algorithm for Implicit Knowledge Mining**

When Lyra's deep-research agents attempt to understand or replicate complex research, they face the same problem AUTO REPRODUCE addresses: critical implementation details are *not in the paper* — they are spread across the cited literature and associated code repositories. The paper lineage algorithm provides a systematic method to trace citation graphs, download cited papers, identify their repos, extract `<summary, code>` pairs, and use these as domain-aligned reference exemplars.

Lyra can adapt this by:
1. For any paper being deep-researched, automatically construct its paper lineage (top-k cited papers + their repos)
2. Build `<summary, code>` tuples as structured knowledge for downstream reasoning
3. Use lineage-derived exemplars to improve code generation and understanding tasks

**Workstream Route:** §4.15 Deep Research (primary) + §4.6 Tools (code execution/debugging) + §4.14 Autonomy (multi-agent collaboration pattern)

| Dimension | Rating |
|---|---|
| **Impact** | **4** — Directly upgrades Lyra's ability to understand and reproduce research; the paper lineage concept is novel and transferable. The gap between paper text and implicit implementation knowledge is a universal problem in AI research. |
| **Effort** | **4** — Requires ArXiv API + GitHub API integration, citation graph traversal, repo filtering logic, and `<summary, code>` pair construction. The core algorithm (Algorithm 1) is well-specified but implementation touches multiple subsystems. |
| **Tier** | **breakthrough** — Paper lineage is a fundamentally new capability that Lyra currently lacks. It would allow Lyra to autonomously build deep understanding of research papers by tracing their intellectual lineage, not just reading the paper in isolation. |

**Evidence strength:** The ablation shows removing paper lineage drops Mixed-Level score from 69.97 → 63.15 and increases Perf Gap from 31.62 → 39.59 (Claude-3.5-Sonnet). This is a moderate but real effect validated across 13 diverse papers.
