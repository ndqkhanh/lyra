Open-source: https://github.com/FSoft-AI4Code/CodeWiki

## 1. Mechanism (step-by-step)

CodeWiki is a semi-agentic framework that generates repository-level documentation through three phases inspired by dynamic programming principles.

### Phase 1: Repository Analysis & Hierarchical Module Decomposition

**Dependency Graph Construction.** Tree-Sitter parsers extract ASTs across 7 languages (Python, Java, JavaScript, TypeScript, C, C++, C#). The parser identifies functions, methods, classes, structs, modules, and their interdependencies: function calls, class inheritance, attribute access, and module imports. These are normalized to a unified `depends_on` relation, producing a directed graph G = (V, E) where edge (u, v) ∈ E means component u depends on v.

**Entry Point Identification.** Topological sorting identifies zero-in-degree components -- independent entry points (main functions, API endpoints, CLI entry points, public interfaces) where users interact with the system. These become high-level components.

**Hierarchical Decomposition.** High-level components are recursively partitioned into manageable modules based on component interdependencies and semantic coherence. For scalability, only component IDs serve as input (not full source), producing a feature-oriented module tree.

### Phase 2: Recursive Documentation Generation (core innovation)

**Agent Architecture.** Each leaf module is assigned a specialized agent equipped with:
1. Complete source code access for the module
2. Full module tree for cross-module understanding
3. Documentation workspace tools (view, create, edit operations)
4. Dependency graph traversal for contextual exploration

**Agent Workflow.** The agent (1) analyzes components to understand functionality and interfaces, (2) explores context by traversing dependencies within and across modules, and (3) generates comprehensive markdown documentation including descriptions, usage examples, API specifications, and architectural insights.

**Dynamic Delegation (key innovation).** When module complexity exceeds single-pass capacity, agents delegate sub-modules to specialized sub-agents. Delegation criteria:
- Code complexity metrics (cyclomatic complexity, nesting depth)
- Semantic diversity (functionally distinct subcomponents)
- Context window utilization (leaf module threshold: 32,768 tokens)

Algorithm 1 (Recursive Module Documentation):
```
Initialize documentation workspace
for each leaf module m in T:
    agent ← CreateAgent(m, G, T)
    while m not fully processed:
        agent.GenerateDoc(m.name)
        if delegation requested:
            sub ← agent.GetDelegationSpecs()
            UpdateModuleTree(T, m, sub)
            foreach new leaf m' in sub:
                Recursively process m'
        ReviseDoc(m.name)
ProcessParentModules(T)
return Repository documentation
```

Maximum delegation depth: 3 levels. Processing is strictly bottom-up.

**Cross-Module Reference Management.** A global registry tracks documented components and their locations. When agents encounter external components during traversal, the resolution system creates cross-references rather than duplicating content, maintaining conciseness while preserving completeness.

### Phase 3: Hierarchical Assembly & Documentation Synthesis

After leaf documentation is complete, parent modules undergo LLM synthesis. The LLM receives: child module documentation, module tree structure, dependency information, and synthesis instructions. Synthesis involves multiple stages:
1. Analyzing child documentation for themes and patterns
2. Generating architectural overviews explaining module collaboration
3. Creating feature summaries distilling capabilities
4. Developing usage guides for public interfaces
5. Producing architectural diagrams (visual artifacts: architecture diagrams, data-flow representations, sequence diagrams)

### Evaluation: CodeWikiBench

**Rubric Generation.** Official documentation from target repositories is hierarchically parsed into structured JSON. A Rubric Generator Agent produces hierarchical rubrics mirroring repository functionality. Multiple independent generations using different model families (Claude Sonnet 4, Gemini 2.5 Pro, Kimi K2 Instruct) are synthesized to reduce single-model biases.

**Judge Protocol.** Three Judge Agents (Gemini 2.5 Flash, GPT OSS 120B, Kimi K2 Instruct) evaluate leaf-level requirements with binary decisions (0 = not satisfied, 1 = satisfied) and concise reasoning. Judges evaluate only leaf-level criteria, not abstract concepts.

**Score Aggregation.** For leaf nodes with m assessments s1..sm: S(ℓ) = mean(s_i), with reliability σ_ℓ = stddev(s_i). For internal nodes with children c1..ck having scores S(ci) and weights w(ci): S(n) = Σ(w(ci)·S(ci)) / Σw(ci), with σ_n = sqrt(Σ(w(ci)²·σ_ci²)) / Σw(ci). This weighted aggregation propagates both scores and uncertainty from leaves to root.

**Temporal Separation.** Repository snapshots from Aug-Sep 2025, postdating model knowledge cutoffs (Claude Sonnet 4: March 2025), preventing data leakage.

## 2. Results

### Overall Quality Scores (with standard deviations)
| System | Avg Score |
|--------|-----------|
| CodeWiki | **68.79% ± 3.84** |
| DeepWiki (closed-source) | 64.06% ± 3.60 |
| deepwiki-open | 50.05% ± 4.02 |
| OpenDeepWiki | 47.13% ± 4.25 |

CodeWiki outperforms DeepWiki by +4.73 percentage points, OpenDeepWiki by +21.66pp, deepwiki-open by +18.74pp.

### By Language Category
| Category | CodeWiki | DeepWiki | Δ |
|----------|----------|----------|-----|
| Scripting (Py, JS, TS) | **79.14%** | 68.67% | **+10.47pp** |
| Managed (C#, Java) | **68.84%** | 64.80% | +4.04pp |

### Per-Repository Highlights
- **puppeteer (TypeScript):** CodeWiki 83.00% vs DeepWiki 64.46% — **+18.54pp** (best individual gain)
- **OpenHands (Python):** CodeWiki 82.45% vs DeepWiki 73.04% — +9.41pp
- **ml-agents (C#):** CodeWiki 79.78% vs DeepWiki 74.80% — +4.98pp
- **wazuh (C, 1.45M LOC):** CodeWiki 42.30% — worst overall, C challenges both systems

### Coverage Metrics
CodeWiki satisfies more leaf requirements than DeepWiki in 5/7 repositories. Example: OpenHands 59/67 requirements satisfied vs DeepWiki 54/67.

### Human Evaluation Pilot (3 participants, 3 repos, 9 assessments)
CodeWiki preferred in **7/9 (77.8%)** assessments. Alignment with automated scores: OpenHands (+9.41% automated) → unanimous 3/3 CodeWiki preference; puppeteer (+18.54%) → 2/3 preference; svelte (+3.45%) → 2/3 preference.

### Rubric Reliability
Semantic consistency: 73.65%, Structural consistency: 70.84% (averaged across all benchmark repos).

### Scalability
Processed repos from 86K LOC (ml-agents) to 1.45M LOC (wazuh). Performance variation correlates primarily with language characteristics, not repository size.

### Model Configuration
- Generation: Claude Sonnet 4 (temp 0.0, max_tokens 16384, context 200K)
- Rubric generation: Claude Sonnet 4 + Gemini 2.5 Pro + Kimi K2 Instruct
- Judging: Gemini 2.5 Flash + GPT OSS 120B + Kimi K2 Instruct

## 3. Trade-offs

| Win | Loss |
|-----|------|
| +4.73pp over closed-source DeepWiki on average quality | Underperforms DeepWiki on C/C++ (-3.15pp, systems languages) |
| +10.47pp on scripting languages (Python, JS, TS) | Significant LLM API costs — multiple models for rubric generation + judging + documentation |
| +18.54pp best individual repo gain (puppeteer/TS) | Rubric reliability only ~72% (73.65% semantic, 70.84% structural) — not gold-standard |
| Scales to 1.45M LOC via hierarchical decomposition | Max delegation depth limited to 3 levels — may be insufficient for extremely deep hierarchies |
| Open-source (MIT-style, on GitHub) | Requires Tree-Sitter parser setup for all 7 target languages |
| Generates visual artifacts (architecture diagrams, data-flow) alongside text | Pilot human eval too small (3 participants, 3 repos) for statistical significance |
| Multilingual support (7 languages) | Leaf module threshold (32K tokens) may not match all model context windows |
| Temporal separation from training data prevents leakage | Multi-model consensus judging increases cost proportionally with judge count |

## 4. Design Rationale

**Why hierarchical decomposition over whole-repo prompting?** Context windows cannot fit large repositories (wazuh at 1.45M LOC). Breaking into modules with bounded input size ensures scalable processing while preserving architectural coherence. The dynamic programming inspiration comes from the bottom-up synthesis: solve sub-problems (leaf modules) first, then combine solutions upward.

**Why recursive agents instead of single-pass generation?** Repository documentation requires both local detail (function specs) and global coherence (architectural patterns). A single agent cannot maintain both simultaneously at scale. Recursive delegation mirrors how humans document large systems: delegate sections, then synthesize.

**Why multi-model consensus judging?** Single-model LLM-as-a-judge suffers from biases. Using 3 diverse models (Gemini, GPT, Kimi) with binary leaf-level assessment and averaging reduces individual model biases. Standard deviation propagation quantifies reliability.

**Why AST-based dependency analysis?** Pure LLM-based dependency inference hallucinates cross-file relations. Tree-Sitter provides deterministic, language-agnostic dependency extraction that scales reliably across 7 languages.

**Why temporal separation?** Using repo snapshots from Aug-Sep 2025 when all models have knowledge cutoffs before March 2025 eliminates contamination — the models cannot have memorized these codebases.

## 5. Limitations & Failure Modes

1. **Systems programming language degradation:** C/C++ scores (53.24%) trail DeepWiki (56.39%). Pointer operations, manual memory management, template metaprogramming, and preprocessor macros resist static analysis. These constructs *are* the architecture in systems code, making the current analysis phase insufficient.

2. **Automatic rubric quality not verified:** Generated rubrics show only 73.65% semantic and 70.84% structural reliability across model families. Some rubrics may be difficult to interpret or miss key architectural aspects. No systematic human verification of rubric quality was performed.

3. **LLM-as-judge biases:** Despite multi-model consensus, evaluation methodology inherits LLM biases. The pilot human study (3 participants, 3 repos, 9 comparisons) is too small for statistical significance. Broader human evaluation with rubric-based assessment is needed.

4. **Model specificity:** Only Claude Sonnet 4 was tested for documentation generation. Performance with other models (GPT-4, Gemini, open-source) is unknown. Temperature fixed at 0.0 — creative documentation styles not explored.

5. **Delegation depth cap:** Maximum 3 levels of delegation — extremely deep module hierarchies hit this cap. Leaf module threshold of 32K tokens may be suboptimal for different models.

6. **Language-specific parser limitations:** Tree-Sitter grammars vary in quality across languages. C++ template metaprogramming and C preprocessor macros are particularly challenging to parse accurately.

7. **Static analysis blind spots:** Dynamic features (runtime imports, reflection, dependency injection) are invisible to AST-based static analysis, leading to incomplete dependency graphs.

## 6. Transfer to Lyra

**The ONE transferable idea:** The three-phase hierarchical-decomposition-with-recursive-agentic-synthesis pattern. When Lyra needs to operate on large-scale codebases (analyzing, refactoring, documenting), it can: (1) use Tree-Sitter AST parsing to build a dependency graph and decompose the repo into a feature-oriented module tree, (2) recursively process leaf modules with specialized agents that can dynamically delegate when context limits are exceeded, and (3) hierarchically synthesize parent-level understanding from child outputs with cross-reference tracking via a global registry. This pattern directly addresses the context-window bottleneck that limits large-repo operations.

**§4 Workstream Route:** §4.2 — Context & Memory. This paper's core contribution is bounded-context processing of arbitrarily large codebases through hierarchical decomposition and recursive synthesis. The dynamic delegation mechanism (complexity-triggered sub-agent spawning) maps directly to Lyra's context management strategy for large-scale repository operations.

**Impact:** 4 — The hierarchical decomposition pattern is proven across 7 languages, scales to 1.45M LOC, and directly addresses a hard constraint (context window limits). However, it requires significant integration work (Tree-Sitter parser setup, agent orchestration, cross-reference registry).

**Effort:** 4 — Requires: (a) Tree-Sitter parser integration for Lyra's target languages, (b) implementing the dependency graph construction and topological decomposition logic, (c) building the recursive agent delegation controller, (d) implementing the cross-module reference registry, (e) creating the hierarchical synthesis prompts. Multi-language support adds complexity.

**Tier:** **investigate** — The pattern is proven (paper results are strong) but requires adaptation to Lyra's specific architecture and agent framework. Worth prototyping on a 2-language subset (Python + TypeScript) before committing to full 7-language support. The C/C++ weakness is acceptable since Lyra's primary target languages are Python and TypeScript.
