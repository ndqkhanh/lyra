## 1. Mechanism (step-by-step)

VIRS CI (Virtual Scientists) is an LLM-based multi-agent system that simulates collaborative scientific idea generation. It has two architectural layers:

### Layer 1: Scientific Research Ecosystem (digital twin of research communities)

- **Past Paper Database (Bpast)**: FAISS-indexed papers published before a chosen time boundary (ybound), each with title, citation count, and abstract embeddings. Provides retrieval corpus for idea grounding and novelty checking.
- **Contemporary Paper Database (Bcon)**: FAISS-indexed papers published after ybound, used ONLY for evaluation (never exposed to agents during generation). Enables computing three novelty metrics.
- **Author Knowledge Bank**: AgentScope KnowledgeBank module embedding real scientist profiles (name masked, affiliations, citation count, research interests, collaboration history) for RAG retrieval during discussions. Built from AMiner CS dataset (1.7M authors, 2.1M papers) and OAG 3.1 (35.8M authors, 130.7M papers). Embedding model: `mxbai-embed-large`.
- **Adjacency Matrix A**: Collaboration counts between scientists. All values incremented by +1 to implement an explore-exploit mechanism — scientists with zero prior collaborations still have non-zero probability of selection, enabling "fresh team" formation.

### Layer 2: Five-Step Multi-Agent Pipeline

**Step 1 — Collaborator Selection**: Random scientist s0 is chosen as team leader. Leader sends invitations to potential collaborators sampled from probability distribution P_{i,j} = A_{i,j} / sum_j(A_{i,j}). Invitee evaluates invitation via chain-of-thought, considering leader's profile and current team composition. Accepts/rejects accordingly. Process repeats until team size n is reached.

**Step 2 — Topic Discussion** (K turns): Team engages in inter- and intra-team discussion with round-table sequential topology. Each agent at turn k receives prompt:
```
Q_{k,i} = <Q_team, Q_topic, union_{t=1}^{k-1}(D_t), union_{j=0}^{i-1}(R_{k,j})>
```
where `D_t` = team leader's summary of turn t, `R_{k,j}` = agent j's response at turn k.

**Invitation Mechanism** (intra-team): Agents can use RAG to consult scientists outside the team by mentioning their names. A new temporary agent is initialized with the mentioned scientist's profile and included in discussion, but NOT added to the fixed-size team. This simulates real-world informal consultations.

After K turns, team leader generates final topic via consensus. Scientists uninterested in the topic may leave. If no consensus, discussion terminates and restarts.

**Step 3 — Idea Generation** (K turns): Agents propose ideas with three required components: (1) idea description, (2) experimental plan, (3) self-assessment (novelty, feasibility, clarity scores). Ideas are seeded by retrieving relevant papers from Bpast using the topic R_topic. Prompt:
```
Q_{k,i} = <Q_idea, R_topic, Bpast(R_{k,i-1}), union_{t=1}^{k-1}(D_t), union_{j=0}^{i-1}(R_{k,j})>
```
Agents can refine existing ideas or propose new ones. After K turns, top-3 highest-confidence ideas form the idea list I.

**Step 4 — Novelty Assessment**: Blind review — agents receive idea list I with retrieved similar papers from Bpast, NO dialogue memory (simulating anonymous review). Prompt:
```
Q_{k,i} = <Q_check, union_{j=1}^{3}(I_j, Bpast(I_j))>
```
Each agent votes for the most novel idea via chain-of-thought. Highest-voted idea becomes the final idea R_idea.

**Step 5 — Abstract Generation** (K turns): Team leader provides initial draft. Subsequent agents: (1) evaluate prior abstract (novelty/clarity/feasibility scores), (2) propose modifications, (3) produce revised abstract. No dialogue history — iterative refinement only, using:
```
Q_{k,i} = <Q_abstract, Q_judgment, R_{k,i-1}>
```

**Optional Self-Review** (Appendix B.1): After final abstract, team leader checks its novelty against Bpast. If similarity too high: revise (max 2 attempts, then discard and regenerate idea). This module was excluded from main comparisons due to uncertain inference costs.

### Key Design Patterns
- RAG (AgentScope KnowledgeBank) used throughout all five steps for background knowledge access
- Chain-of-thought reasoning for all agent decisions (invitation acceptance, topic consensus, idea refinement, voting)
- Explore-exploit balance via adjacency matrix increment (uniform +1 in default; normal distribution variant tested)
- Round-table sequential discussion topology (preferred over random; sequential gave higher ON across most settings)
- Fixed K turns for fairness in comparisons; adaptive turn pattern (leader-decided) tested in ablation and found to both reduce cost AND improve novelty

## 3. Trade-offs (wins vs loses)

| Axis | Win | Lose |
|------|-----|------|
| **Team size** | Larger teams (≤8) increase diversity and ON via broader perspectives; multi-agent consistently outperforms single-agent (+44.1% CI) | Too-large teams (100) create coordination overhead, diluted contributions, and groupthink — ON collapses |
| **Discussion turns** | More turns (≤5) deepen insights and refine ideas; peak ON at K=5 | Excessive turns (>5) cause agent fatigue, reduced engagement, and creativity decline |
| **Team freshness** | 50% new members balances novel perspectives with institutional knowledge; peak HD and ON | 0% freshness (all returnees) = stale ideas; 100% freshness = loss of domain depth |
| **Team diversity** | Diverse backgrounds improve alignment with emerging trends (lower CD), especially for larger teams | Over-diversity hurts cohesion; reverse U-shaped — 50-75% optimal for size=8 |
| **Invitation mechanism** | External expert consultation via RAG adds fresh perspectives without bloating team | Adds inference overhead per consultation; requires name-mention triggers |
| **Novelty assessment** | Blind review step catches idea-redundancy before abstract writing; +0.25 ON improvement (size=8) | Adds K additional inference turns; requires well-constructed Bpast for meaningful comparison |
| **Self-review** | Catches low-novelty abstracts post-generation; +0.24 ON improvement (size=8) | Introduces uncertain inference cost; can loop up to 2 revisions before discarding idea |
| **Adaptive turns** | 28.5% lower cost + higher ON vs fixed turns (e.g., 3.49 vs 3.26 for size=4) | Requires capable team leader to decide when to stop; may under-discuss if leader is hasty |
| **Paper database (Bpast)** | Grounding prevents shallow/fanciful ideas; ON jumps from ~2.6 to ~4.2 (CS dataset) when DB used in both idea gen + novelty assessment | Quality dependent on paper corpus coverage; embedding-based retrieval may miss semantically distant but relevant papers |
| **LLM capability** | GPT-4o yields highest scores across all metrics; LLaMA3.1-70b > 8b but diminishing returns | Cost scales with model size; 70b only marginally better than 8b on novelty, suggesting ceiling effect |

## 4. Design Rationale

The authors chose a multi-agent system over single-agent because real-world science is inherently collaborative — existing single-agent approaches (AI Scientist, HypoGen) miss the diverse-perspective synergy that drives breakthrough research. The five-step pipeline maps directly to how human research teams operate: assemble team, pick topic, brainstorm ideas, evaluate novelty, write abstract.

Key architectural decisions and their motivations:
- **Explore-exploit in collaborator selection** (adjacency matrix +1): Prevents agents from always picking prior co-authors. Mirrors Science-of-Science findings that fresh collaborations produce more original/impactful research (Zeng et al., 2021, *Nature Human Behaviour*).
- **Inter- and intra-team discussion**: Goes beyond prior group chat patterns. The Invitation Mechanism allows agents to consult real scientists outside the fixed team, simulating informal academic consultations without bloating the formal team roster.
- **RAG-based author knowledge bank**: Avoids overloading the system prompt with all team member profiles while still giving each agent on-demand access to any scientist's full background. AgentScope's KnowledgeBank provides this infra.
- **Blind review in novelty assessment**: Removing dialogue history during the voting step simulates anonymous peer review, reducing social conformity bias ("I agree with the previous speaker") that would otherwise favor earlier ideas.
- **Abstract as evaluation target** (not full paper): Computational constraints made full-paper generation infeasible at scale. Abstracts are argued to effectively represent core novelty.
- **No pretraining on collaboration data**: Unlike ResearchTown which uses synthetic profiles, VIRS CI uses real (anonymized) scientist data from AMiner/OAG to ground collaboration dynamics in empirical reality.
- **Fixed-K turns as experimental control**: While adaptive turns perform better (Section D.3.2), fixed K ensures fair cost-controlled comparisons across methods.

## 5. Limitations and Failure Modes

1. **Simplified team dynamics**: Real-world scientists work on multiple projects simultaneously and teams overlap/cross-pollinate. VIRS CI models only single-project, single-team formation — missing multi-team concurrency, competition between teams, and researchers moving between projects.

2. **LLM bias toward established domains**: The underlying LLM training data favors well-cited, mainstream research areas. VIRS CI may systematically under-generate ideas in emerging, niche, or underrepresented fields — reinforcing existing disparities in scientific knowledge production.

3. **Hallucinated claims in generated abstracts**: Example abstracts show fabricated quantitative results (e.g., "n=500", "42% reduction", "median increase: 12 months") — these are plausible-sounding but entirely unsupported. Risk is acute for medicine/policy domains where such claims could propagate through the literature ecosystem.

4. **Misuse potential**: System can automate fraudulent paper generation or facilitate plagiarism at scale. No built-in watermarking or detection safeguards beyond self-review.

5. **Data privacy concerns**: Even with name masking, aggregation of real scientist profiles into retrievable knowledge banks creates re-identification risks if the system were deployed at community scale.

6. **Novelty metric limitations**: The ON metric (embedding-distance-based) captures semantic dissimilarity but cannot distinguish "genuinely novel" from "nonsensical but distant." Pearson r=0.52 with humans suggests moderate but imperfect alignment. Abstracts that are grammatically divergent but substantively identical to prior work could score high.

7. **Team size scaling failure**: At size=100, performance degrades sharply — system was not designed for large-team coordination. In practice, LLM context window limits and coordination costs make very large teams intractable.

8. **Data leakage**: While argued to affect all methods equally, using papers from 2010-2023 as Bcon with LLMs trained through Dec 2023 means models have seen the "contemporary" papers during pretraining. The temporal isolation experiment (OAG 3.2, 2024-2025) shows minimal ON degradation (3.40→3.35), supporting the claim of robustness but not eliminating the concern.

9. **Compute cost scaling**: Each run is ~10 min on A100 for 4-member teams with LLaMA3.1-8b. Scaling to GPT-4o with API costs, large teams, or many runs quickly becomes expensive. This limits large-N experiments and statistical power for fine-grained factor analysis.

10. **Eastern institutional concentration**: All authors are from Chinese institutions. While datasets are international (OAG, AMiner), the human evaluation used 10 CS PhD students whose cultural/academic background may bias novelty judgments toward specific research traditions.

## 6. Transfer to Lyra

### The ONE transferable idea

**The Invitation Mechanism + Inter/Intra-Team Discussion pattern**: VIRS CI allows agents within a team to dynamically consult external experts (outside the formal team roster) via RAG-based ad-hoc agent initialization, enriching discussion without permanently expanding the team. This is a lightweight, composition-friendly alternative to static multi-agent architectures.

### Application in Lyra

Lyra's §4 architecture (multi-agent orchestration) should adopt this pattern: when a Lyra subagent encounters a boundary question (e.g., a coding agent needs deployment expertise, a security reviewer needs domain-specific threat knowledge), it can invoke an on-demand "consultant agent" initialized from Lyra's knowledge bank with the appropriate expertise profile. The consultant joins the conversation for one or more turns but does NOT persist in the team roster, avoiding coordination overhead while still injecting specialized knowledge.

### Workstream Route

**§4.2 — Multi-Agent Orchestration Layer** (enhances Lyra's agent-to-agent communication topology beyond static team assignment)
