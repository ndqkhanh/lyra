## 1. Mechanism (step-by-step, equations, algorithms)

### Core Idea
A three-agent system (Selector, Reader, Writer) that iteratively reads sections of reference papers in an optimized order, maintaining a size-constrained working memory, then generates a Related Work Section (RWS). Two graph-aware selector strategies (citation graph, co-occurrence graph) constrain reading order to better capture inter-paper relationships.

### Three-Agent Architecture

**Selector** — Decides what to read next:
```
(R_t, s_t) = Selector((s_0,1, ..., s_N,1), M_{t-1}, H_{t-1})
```
Input: abstracts of all papers, current working memory M_{t-1}, reading history H_{t-1}. Output: (paper ID, section name) to read next, or `<End>` to terminate.

**Reader** — Digests content and updates memory:
```
M_t = Reader((R_t, s_t), M_{t-1})
```
Enforced size constraint: 4096 tokens. Must reorganize memory at each step, discarding irrelevant information.

**Writer** — Generates final RWS:
```
RWS = Writer(M_T, H_T)
```
Prompted with explicit instructions: avoid isolated descriptions, explain relationships, group similar studies, provide example of well-crafted RWS for in-context learning.

### Five Selector Strategies (performance order: SR < RR < Vanilla < Graph-Co < Graph-Ci)

**1. Sequential Reading (SR):** Reads papers by ID, sections in order.
```
H_T = {(R_0, s_0,1), ..., (R_N, s_N,L_N)}
```

**2. Random Reading (RR):** Shuffles sequential order to mitigate position bias.

**3. Vanilla LLM-Based:** Dynamic LLM decision at each step:
```
(R_t, s_t) = LLM((s_0,1, ..., s_N,1), M_{t-1}, H_{t-1})
```

**4. Graph-Co (Co-occurrence Graph):**
- Graph: G_co = (V_co, E_co) where nodes = papers, edges = papers co-cited in same sentence of a prior paper's RWS
- Selector positioned at paper R_{t-1}, operates within one-hop subgraph
- Chooses to continue reading current paper OR jump to adjacent paper in graph

**5. Graph-Ci (Citation Graph):**
- Graph: G_ci = (V_ci, E_ci) where edges = citation relationships
- Same traversal mechanism as Graph-Co but constrained by citation structure
- One-hop subgraph defined similarly:
  ```
  V_{t-1} = {R_{t-1}} ∪ {R_i | (R_i, R_{t-1}) ∈ G or (R_{t-1}, R_i) ∈ G}
  ```

### Working Memory Design
- JSON format storing: paper ID, sections read, extracted key information (issue, methods, relations)
- Constrained to 4096 tokens — reader must compress/prioritize at each step
- Reading history H tracks (paper_id, section_name) tuples to prevent cyclic reading

OARelatedWork (Docekal et al., 2024) — open-domain, average 70K tokens input per test instance. Experiments on 10% subset.

## 3. Trade-offs (wins vs loses)

### Wins
- **Consistent improvement across all base models**: Works with weak (Llama3-8B), medium (Claude-3-Haiku), and strong (GPT-4o) models
- **Dramatic reading reduction**: Graph-Ci reads only 25.81% of content while achieving best results — 3.9x reading efficiency
- **Robust to input configuration**: Works with abstracts only, intro+conclusion, RWS only, or full text
- **Explicit relationship modeling**: Graph constraints force the model to traverse related papers together, producing denser co-occurrence graphs
- **Human-validated**: Win rates 56-68% over strongest baselines in human pairwise evaluation
- **High memory fidelity**: 96% retention, 95% accuracy in working memory — minimal hallucination
- **Robust to prompt variation**: Performance stable across rewritten prompts (GPT-4o Graph-Ci: 3.87 vs 3.86)

### Loses
- **Large gap to human quality**: Best model generates avg 3.24 edges vs human 9.48 — models over-elaborate on some references and under-connect others
- **Section-level graph doesn't help**: Using section-level similarity graph performs worse than article-level graphs (Table 4)
- **Weaker models less sensitive to selectors**: Llama3-8B shows minimal performance differences between selector strategies — the framework's benefits are gated by base model capability
- **Requires pre-specified reference set**: Users must manually provide the set of references in advance — no automatic retrieval
- **Static graphs**: Co-occurrence and citation graphs are pre-computed; no dynamic graph construction during reading
- **Full-text performance declines for weaker models**: Llama3-8B and Claude-3-Haiku perform worse with additional sections (more content → more confusion). Only GPT-4o benefits.

## 4. Design Rationale (why this approach)

1. **Multi-agent decomposition matches the task structure**: RWG requires three distinct cognitive operations — deciding what to read (planning), comprehending content (understanding), and synthesizing output (generation). Assigning each to a separate agent with its own prompt and memory scope mirrors how humans approach literature review.

2. **Graph constraints encode domain knowledge**: Citation and co-occurrence graphs capture real academic relationship structures. Constraining the reading order to graph-adjacent papers forces the model to process related work together, naturally producing more interconnected output.

3. **Size-constrained working memory as an attention bottleneck**: The 4096-token memory limit forces the reader to actively curate and compress — a form of learned attention that prevents context dilution. This is the key reason the framework outperforms "dump everything into context" approaches.

4. **Separating reading order from content digestion**: The Selector-Reader split allows optimizing traversal strategy independently of comprehension quality. The selector can be replaced (5 strategies tried) without changing the reader.

5. **RWS as the most information-dense section**: The finding that 73.5% of reading targets the RWS of references validates the design — RWS sections are the highest-signal content for writing new RWS. This aligns with academic writing practice.

6. **Why Graph-Ci > Graph-Co**: Co-occurrence graphs are highly connected (many papers co-occur together), imposing weak constraints. Citation graphs are sparser and more directional, providing stronger structural guidance.

## 5. Limitations & Failure Modes

1. **Human quality gap (3.2 vs 9.5 avg edges)**: The model still cannot match human-level synthesis. References that should be summarized in one sentence are often over-elaborated, reducing coherence. This is identified as the primary limitation.

2. **Requires manual reference curation**: Users must provide the reference set upfront. No automatic retrieval or relevance filtering — limits practical deployability. Authors acknowledge this as a key future direction.

3. **Graph construction is external**: Citation and co-occurrence graphs must be pre-computed from external sources. In domains without rich citation data, the graph-aware selector degrades to vanilla.

4. **Section-level relationships don't help**: Using BERT-embedding similarity between sections (threshold 0.5) to guide reading performs worse than article-level graphs (Table 4). The paper-level structure matters more.

5. **Weaker models can't leverage full text**: Llama3-8B and Claude-3-Haiku degrade in performance when given more content sections, even with the framework. The selector's effectiveness is gated by the base model's long-context capability.

6. **Single-turn evaluation only**: The RWS is generated in one pass. No iterative revision or human-in-the-loop refinement explored.

7. **No ablation on memory size**: 4096 tokens is fixed. The sensitivity to this parameter is not explored — larger models might benefit from larger memory.

8. **10% dataset subset**: All experiments use only 10% of OARelatedWork due to dataset size. Full-dataset results may differ.

9. **Closed-source model reproducibility**: Claude-3-Haiku and GPT-4o results depend on specific API versions (claude-3-haiku-20240307, gpt-4o-2024-08-06) that may become unavailable.

## 6. Transfer to Lyra

**One Idea:** Implement a **graph-constrained iterative reading loop** for Lyra's research and document-analysis capabilities, where a Selector agent decides which section of which source to read next based on a citation/relationship graph, a Reader agent digests it into a size-constrained working memory, and Lyra's existing generation pipeline produces the final synthesis.

**Route:** §4.1 (Overall Framework) + §4.2 (Graph-Aware Selector) — Build a relationship graph from Lyra's document corpus (citation links, co-occurrence from existing summaries, or semantic similarity), implement Selector and Reader agents as specialized system prompts within Lyra's tool-calling loop, constrain working memory to a fixed token budget with explicit reorganization instructions.

**Impact:** MEDIUM — Enhances Lyra's ability to synthesize across large document collections without context window limits. Most relevant for research/synthesis tasks involving 10+ sources.

**Effort:** LOW-MEDIUM — Requires: (1) relationship graph construction from document metadata or embeddings (existing Lyra infrastructure), (2) two new system prompts (Selector, Reader) — prompt engineering only, (3) working memory management logic (~100 lines). No training required. The main work is prompt design and graph construction.

**Tier:** Tier 2 (medium-impact, low-effort, prompt-engineering-heavy)
