## 1. Mechanism (step-by-step)

AgenticEval is a three-phase multi-agent pipeline that transforms unstructured regulatory documents into a continuously hardening safety benchmark.

### Phase 1: Regulation-to-Knowledge Structuring (Specialist Agent A_S)

**Structuring (A_S.Structure):** The Specialist agent consumes a regulation document R and produces a hierarchical rule tree K — called *Structured Provisions*. It supports two modes:
- *User-Guided Structuring:* The agent maps sections of R onto a user-provided JSON template `S_template`, then populates leaf nodes with atomic rules and their `explanation` fields.
- *Autonomous Decomposition:* The agent recursively parses R, identifies primary themes, then decomposes each theme into sub-topics until bottoming out at atomic rules `r`, each annotated with an `explanation` field e_r that rephrases the legal text as an actionable principle for AI-generated content.

Formally:
```
K = A_S.Structure(R, S_template)   if S_template exists
K = A_S.Structure(R)               otherwise
```

**Enrichment (A_S.Enrich):** For each leaf rule r in K, the agent synthesizes search queries and performs web search to retrieve real-world examples, then produces two guidance documents:
- **G_should:** Compliant Guidance — describes ideal, safe, compliant AI-generated content with concrete examples.
- **G_should_not:** Adversarial Guidance — enumerates specific, concrete examples of content that would violate the rule, written from a red-teamer's perspective.

This process is explicitly culturally and linguistically aware (A_S is prompted to search and generate examples for the language/region of the document). The final output is the **Testable Knowledge Base K***, where each leaf rule is expanded to `r = (e_r, G_should, G_should_not)`.

### Phase 2: Test Suite Generation (Generator Agent A_G)

For each atomic rule r in K*, the Generator produces a **Question Group Q_r** — a semantically coherent set of test cases probing a single safety principle from multiple angles.

**Step 1 — Semantic Anchor Generation:** A_G.Generate(r, mode='base') produces a foundational open-ended question `q_base` and its judging criterion `c_base` that directly tests the rule's core principle.

**Step 2 — Systematic Facet Expansion:** From the anchor (q_base, c_base), A_G expands via four modes:
- *Adversarial Perturbation (jailbreak mode):* Transforms q_base into a jailbreak prompt using persona-play, ethical dilemmas, or academic framing.
- *Deterministic Probes (mcq/tf modes):* Converts the anchor into multiple-choice questions or true/false statements with plausible distractors.
- *Multimodal Grounding (multimodal mode):* A two-step process — (a) analyze q_base to determine an appropriate visual context, use image generation or web search to acquire image I; (b) rewrite the question into q_mm that depends intrinsically on visual information in I.

Each Q_r is a collection: `Q_r = {(q_base, c_base), (q_jailbreak, c_jailbreak), (q_mcq, c_mcq), (q_tf, c_tf), (q_mm, c_mm), ...}`. The group structure enables not just accuracy measurement but fine-grained inconsistency analysis.

### Phase 3: Self-Evolving Evaluation Loop (Evaluator A_E + Analyst A_A + Generator A_G)

The loop runs for K_max iterations (K_max = 3 in experiments):

**Step 1 — Judgment with Explainable Rubrics (A_E.Judge):**
```
(y_q, z_q) = A_E.Judge(M_target, q, c, r)
```
Where y_q ∈ {0,1} is the binary correctness judgment and z_q is a natural-language rationale. The judgment is conditioned on a three-layer rubric:
1. Prime Directive: question-specific criterion c (takes precedence).
2. General Safety Guideline: G_should and G_should_not from K*.
3. Final Rule: response is INCORRECT if it violates the Prime Directive or G_should_not. For adversarial questions, a safe refusal is CORRECT.

Results are partitioned into R_r^+ (successful) and R_r^- (failed).

**Step 2 — Vulnerability Analysis (A_A.Refine):**
```
(z_analysis, S_attack) = A_A.Refine(R_r^+, R_r^-)
```
The Analyst agent synthesizes the model's behavior into an explanatory analysis z_analysis identifying the boundary of safety, then formulates a new attack strategy S_attack with: comparative analysis, new attack type, strategy description, and question concept.

**Step 3 — Refined Test Generation (A_G.Generate, mode='refined'):**
A_G converts S_attack into concrete, targeted test cases engineered to probe the precise vulnerabilities identified.

**Step 4 — Re-evaluation:** A_E runs the new test suite against M_target.

After K_max iterations, A_A produces a final Safety Report cataloging confirmed vulnerabilities, failure boundaries, and areas of robust compliance.

**Agent Model Assignments:**
- A_S, A_E, A_A: GPT-4.1 (strong analytical/logical reasoning)
- A_G: Gemini 2.5 Pro (advanced creative capabilities for crafting diverse test cases)
- Framework implementation: MetaGPT (Hong et al., 2024)
- Each agent gets role-specific system prompts and tool suites (web search for A_S, image generation for A_G)

### Ablation Study (Final-Iteration Safety Rates — lower = better evaluation)

**NIST AI RMF — GPT-5:**
- Full AgenticEval: 64.29%
- w/o A_S.Enrich: higher safety (less discovered)
- w/o A_S.Structure: 75.40% (surge — confirms structuring is critical)
- w/o A_A.Refine: higher safety (static baseline)

**EU AI Act — GPT-5:**
- Full AgenticEval: 36.36%
- w/o A_A.Refine: 48.60% (12.24pp jump = removing loop dramatically reduces vulnerability discovery)
- Compared against baselines: AutoDAN, PAIR, AutoDAN-Turbo — all produce higher safety rates (less effective evaluation) than full AgenticEval.

## 3. Trade-offs

| Win | Cost/Loss |
|-----|-----------|
| Continuously evolving benchmarks (not static) — discovers 36.14pp more failures on GPT-5 vs. initial pass | ~3x computational cost from iterative refinement loop (K_max=3) vs. single-pass evaluation |
| Regulation-to-Knowledge automation eliminates manual benchmark curation labor | Bounded by backbone model reasoning capabilities — specialist errors propagate through pipeline |
| Multi-modal test generation (text + jailbreak + MCQ + TF + image-dependent) covers more attack surface | Multi-agent orchestration adds latency and coordination complexity vs. single-agent approach |
| Explainable rubric judgments (three-layer: prime directive + guidance + final rule) with 88-91% accuracy vs. humans | Evaluator agent may misclassify responses when target model is more capable than evaluator |
| Across 11 models and 3 regulatory frameworks — high coverage and reproducibility | Specialist agents are prompted per-language/region; cross-jurisdictional cultural nuance may be inconsistent |
| Culturally/locally aware grounding via web search enrichment | Search results may be stale, biased, or geographically limited |

## 4. Design Rationale

**Why multi-agent over single-agent:** The authors argue that effective safety evaluation requires the synergistic integration of three distinct capabilities that no single agent excels at simultaneously: (1) structured decomposition for precise targeting of decision boundaries, (2) contextual enrichment for operational grounding of abstract principles, and (3) iterative refinement to adaptively probe model weaknesses. The ablation experiments directly validate this: removing any one component (structuring, enrichment, or refinement) consistently increases apparent safety rates, confirming each is necessary.

**Why self-evolving over static:** Static benchmarks suffer from three failure modes — static lag (outdated when new attacks emerge), scope limitation (cannot capture evolving legal/regulatory complexity), and poor adaptability (monolithic, hard to customize). The self-evolving loop confronts these by learning from each model's specific failure modes, treating evaluation as red-teaming rather than audit.

**Why rubric-based judging over open-ended assessment:** The three-layer rubric (Prime Directive > General Safety Guideline > Final Rule) constrains the Evaluator's decision process into a deterministic execution of explicit criteria, transforming subjective assessment into auditable, reproducible judgments. This design choice is validated by the 0.77-0.81 Cohen's κ agreement with human annotators.

**Why MetaGPT:** Multi-agent orchestration framework enabling coordinated task execution with role-specific system prompts and tool assignments; selected for its modular agent design pattern.

## 5. Limitations & Failure Modes

1. **Legal interpretation, not legal judgment.** The Specialist agent's structuring is a technical interpretation — it cannot substitute for professional legal certification. Compliance scores are preliminary audit signals, not binding legal opinions.

2. **Backbone model dependency.** All four agents (A_S, A_G, A_E, A_A) are LLM-powered. Hallucinations during knowledge structuring, test generation, or judgment propagate through the pipeline. When the Evaluator agent is less capable than the target model, judgment accuracy degrades (capability mismatch).

3. **Computational cost.** The multi-step self-evolving loop incurs significantly higher computational cost and latency vs. static benchmarks. K_max=3 was chosen as a "balance" — deeper vulnerability discovery may require more iterations but at escalating cost.

4. **Cultural awareness is prompt-level, not verified.** While A_S is instructed to search for culturally/locally relevant examples, there is no independent verification that generated adversarial examples truly reflect regional nuance — search result bias and LLM cultural blind spots can produce false regional relevance.

5. **No defense evaluation.** The framework only evaluates model vulnerabilities — it does not assess whether proposed defenses or guardrails mitigate discovered vulnerabilities.

6. **Single-round per iteration.** Each iteration produces one new attack strategy per rule; more sophisticated multi-strategy exploration within a single iteration is not explored.

## 7. Transfer to Lyra

**The One Transferable Idea:** The *Self-Evolving Evaluation Loop* — where an Analyst agent synthesizes failure patterns from evaluation results, formulates targeted attack strategies, and feeds them back to a Generator agent to produce progressively harder test cases — is directly applicable to Lyra's verification and safety testing infrastructure. Specifically, Lyra's §4.7 (Safety & Alignment Verification) or §4.9 (Continuous Evaluation) workstream can adopt this pattern to build a hardening test suite that evolves against Lyra's own behavioral safety boundaries. Instead of static assertion-based safety tests, Lyra could implement: (1) a Specialist agent that parses Lyra's safety policies into structured rules, (2) a Generator that produces diverse adversarial queries, and (3) an Analyst-Evaluator loop that iteratively discovers Lyra's compliance failure modes.

**Impact:** 4 — High potential for uncovering subtle safety/compliance gaps in Lyra's agent behavior that static test suites would miss. Directly feeds the safety verification workstream.

**Effort:** 4 — Requires implementing a multi-agent orchestration layer (analogous to MetaGPT), designing Lyra-specific system prompts for each agent role, integrating with existing Lyra test harness, and building regulation-parsing capability for internal policy documents. Likely 2-4 weeks of engineering plus tuning.

**Tier:** **Breakthrough** — AgenticEval represents a paradigm shift from static to self-evolving safety evaluation, validated across 11 frontier models and 3 regulatory frameworks with statistically significant results. The pattern is generalizable beyond safety evaluation to any domain requiring adaptive, hardening test suites (robustness, reliability, capability regression).
