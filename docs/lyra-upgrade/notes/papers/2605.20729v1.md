## 1. Mechanism (step-by-step)

MTR-SUITE is a unified framework with three integrated components for conversational retrieval benchmarking:

### 1.1 MTR-EVAL: Diagnostic Auditing

**Problem:** Existing benchmarks suffer from two error types:
- **Annotation Noise:** `G_i \ Ĝ_i ≠ ∅` — irrelevant documents in ground truth cause model *overestimation*
- **Annotation Sparsity:** `Ĝ_i \ G_i ≠ ∅` — valid supporting documents omitted from ground truth cause valid retrievals penalized as false negatives

**Four-dimension audit via heterogeneous LLM-as-a-Judge:**
1. **Query-Evidence Alignment:** LLM evaluates whether each gold document `d ∈ G_i` actually contains the answer to `q_i`. Low score = annotation noise.
2. **Evidence Completeness (Discriminability Testing):** Present LLM with gold document + hard negatives. If LLM consistently selects a non-gold document as more relevant, it signals annotation sparsity. This is a proxy task since enumerating all relevant docs is intractable.
3. **Answer-Evidence Faithfulness:** Verify answer `a_i` is fully grounded in `G_i` (hallucination detection).
4. **Answer Quality:** Evaluate linguistic quality (coherence, helpfulness) independent of evidence.

**Bias mitigation:**
- Multi-LLM ensemble reduces self-preference bias
- Pointwise scoring eliminates position bias
- Document positions randomized in Discriminability Testing
- Human correlation: Pearson 0.82 (Query-Evidence), 0.89 (Answer Faithfulness), 0.74 (Answer Quality)

**Validation:** 300 manually reviewed cases — 98% of LLM-flagged missing documents confirmed valid by human review (Fleiss' Kappa = 0.92).

### 1.2 MTR-PIPELINE: Multi-Agent Synthesis

**Stage 1 — Knowledge Base Curation:**
1. Remove non-textual elements
2. Recursive chunking (Langchain delimiters: `\n\n`, `\n`, space, period, comma, etc.)
3. MinHash-LSH deduplication of near-duplicate chunks
4. Hybrid quality filter: NVIDIA quality classifier + FineWeb-EDU scorer
5. Retain only chunks with high information density scored as "High Quality"

**Stage 2 — Greedy Traversal Clustering (core algorithmic novelty):**
```
Algorithm: Greedy Traversal Clustering
Input: Document embeddings D = {e1, e2, ..., eN}, cluster size k
1. Compute pairwise cosine similarities → weighted undirected graph
2. Select random starting node n_current
3. visited ← {n_current}
4. While |visited| < N:
   a. n_next ← argmin(cosine_distance(n_current, n)) for n ∉ visited
   b. Add edge (n_current, n_next) to path
   c. visited ← visited ∪ {n_next}
   d. n_current ← n_next
5. Segment the TSP circuit every k nodes → clusters of size k
6. Remove duplicates from adjacent documents using 5-gram similarity
Output: k clusters, each with exactly k semantically related documents
```

**Advantages over conventional clustering (K-means, DBSCAN):**
1. Fixed cluster size `k` maximizes context window utilization
2. Each document visited exactly once → zero redundancy and elimination of evaluation bias
3. Smooth semantic gradient mimics human browsing trajectory (hyperlinks)
4. No threshold parameter tuning needed

**Stage 3 — Multi-Agent Dialogue Generation (three agents):**
1. **Questioner (User Simulator):** Formulates queries based on document cluster + conversation history. Decides hard topic switching vs. soft drill-down. Prompt constrains each question to be answerable by exactly one specific document.
2. **Responder (RAG Simulator):** Generates answers strictly grounded in the designated gold document, mimicking ideal RAG behavior. Uses chain-of-thought reasoning.
3. **Polisher (Refiner):** Post-processes dialogue to inject conversational phenomena — coreference ("What about him?"), ellipsis ("And how about Paris?"), and casual phrasing. Ablation shows Polisher drops human detection of machine-generation from 79% to 62%.

**Cost model ($0.005/dialogue):**
```
Cost = 1 × 3000 × ($0.24/1M) + 7 × 3000 × ($0.19/1M) + (8 × 80) × ($0.38/1M)
     ≈ $0.005
```
Uses DeepSeek-V3.2 via OpenRouter with prefix-caching. 1/300-1/400 of human annotation cost ($1.50-$2.00/dialogue).

### 1.3 MTR-BENCH: The Benchmark

**Statistics:**
| Metric | Value |
|--------|-------|
| Conversations | 1,000 (test), 3,987 (dev) |
| Turns | 8,000 (test), 31,896 (dev) |
| Turns/Conversation | 8 |
| Topics/Conversation | 5.6 (avg) |
| Tokens/Question | 15.33 |
| Tokens/Answer | 86.90 |
| Knowledge Cutoff | 2025.01 (Wikipedia dump) |
| Corpus Size | ~1M documents |
| Domain Coverage | 19 categories (People & Society 18.6%, Arts 12.1%, Science 10.4%, etc.) |

**Three engineered difficulty factors:**
1. **Hard Topic Switching:** Simulates users introducing entirely new queries without clearing history, causing severe contextual interference
2. **Production-Grade Responses:** Mirrors real-world RLHF-trained LLMs — verbose responses (~87 tokens avg) and ambiguous-decision style instead of clarifying questions
3. **Industrial-Scale Knowledge:** Recent 2025.01 Wikipedia dump (targets long-tail/unseen knowledge) + optimized 1024-char document granularity

## 3. Trade-offs

| Dimension | Win | Lose |
|-----------|-----|------|
| **Cost** | $0.005/dialogue vs $1.50-2.00 (300-400x cheaper) | Requires LLM API access; self-hosting inference costs not quantified |
| **Annotation Quality** | MTR-EVAL scores exceed human baselines on Query-Evidence (4.8 vs 3.9); 98% precision on sparsity detection | LLM-as-judge introduces model-specific biases (partially mitigated by ensemble) |
| **Discriminative Power** | 43.54-point gap between MTR-BENCH and prior benchmarks; extended R@k reveals model-dependent scaling | Retrieval-only evaluation — no end-to-end RAG quality measurement |
| **Realism** | Hard topic switching, verbose responses, ambiguous-decision style match production patterns | Benchmarks focus on Wikipedia/general-domain; domain-specific quality depends on source corpus availability |
| **Scalability** | Fully automated pipeline enables on-demand benchmark refresh | Quality filter ablation shows difficulty is engineered, not emergent — may overfit to selected hardness factors |
| **Generality** | Validated on both Wikipedia and financial domain | Financial corpus is proprietary — full reproducibility limited |
| **Bias** | Pointwise scoring + position randomization reduces position/self-preference bias | Multi-LLM ensemble still shares architectural biases (all Transformer-based) |

## 4. Design Rationale

**Why not manual annotation?** Human annotators operate with a "local view" — they formulate queries based only on the document they are reading, without global corpus visibility. This leads to annotation sparsity (valid retrievals penalized as false negatives). Manual annotation also costs $1.50-2.00/dialogue and cannot scale to rapidly-evolving enterprise knowledge bases.

**Why not rule-based automation (e.g., CORAL)?** Static heuristics (e.g., converting Wikipedia section headers into questions) inherit the same local-view limitation. Without global validation, generated queries may be ambiguous or better answered by unannotated documents. MTR-EVAL showed CORAL scores lower than human-annotated datasets on Answer Faithfulness (3.1) and Evidence Completeness (3.1).

**Why greedy traversal clustering instead of K-means/DBSCAN?**
- K-means/DBSCAN produce clusters of uncontrollable sizes exceeding context windows
- Threshold-based neighbor selection causes document overlap across clusters, introducing evaluation bias from repeated exposure
- Greedy TSP-like traversal produces a smooth semantic path that naturally mimics human browsing, with guaranteed fixed cluster size and zero redundancy

**Why retrieval-only evaluation?** Standard end-to-end metrics (Exact Match, BLEU) require rigid formatting or short ground-truth answers, which contradict the verbose, explanatory nature of real-world RAG responses. Retrieval quality dictates the factual upper bound of any RAG system, so diagnosing the retriever precisely is prioritized over a potentially noisy E2E evaluation.

## 5. Limitations & Failure Modes

1. **Retrieval-only scope:** MTR-BENCH focuses exclusively on the retrieval component. End-to-end RAG quality (generation faithfulness, citation accuracy) is not evaluated. The authors argue this is deliberate to avoid forcing artificial short-answer formats, but it leaves a gap in holistic RAG assessment.

2. **LLM-as-judge circularity risk:** MTR-EVAL uses LLMs to audit benchmarks, introducing potential for model-specific biases. Multi-LLM ensemble and pointwise scoring mitigate this, but the shared Transformer architecture across all judge models (Gemma, Qwen, Llama, Mistral, Command-a, GLM) may encode common blind spots.

3. **General-domain focus:** MTR-BENCH is built from Wikipedia 2025.01. While the pipeline is validated on a proprietary financial corpus, the financial results use a private knowledge base — full reproducibility is not possible.

4. **No statistical significance testing** for pairwise model comparisons on MTR-BENCH. The performance differences between some retrievers (e.g., stella vs bge) may not be statistically meaningful.

5. **Quality filter trade-off:** The quality filter deliberately removes simpler passages to increase benchmark difficulty. This may create an artificially hard benchmark that does not represent typical production retrieval workloads where both easy and hard queries coexist.

6. **Cost analysis assumes specific API:** The $0.005/dialogue estimate uses DeepSeek-V3.2 pricing via OpenRouter with prefix caching. Costs may vary significantly with different model providers, deployment modes, or at much larger scales.

7. **English-only:** No multilingual evaluation or synthesis demonstrated. The recursive chunking separators are English-focused.

8. **Topic distribution skew:** Humanities and Arts constitute ~30% of MTR-BENCH, while other categories represent ~5% each. This may advantage retrievers with stronger humanities performance.

## 6. Transfer to Lyra

### The One Idea

**Automated conversational retrieval benchmark synthesis via greedy traversal clustering + multi-agent dialogue generation (MTR-PIPELINE).** Lyra can adopt this pipeline to generate high-fidelity, continuously-refreshed evaluation datasets at negligible cost. Instead of relying on static, human-annotated benchmarks that suffer from annotation sparsity and cost $1.50-2.00 per dialogue, Lyra can build domain-specific evaluation suites on-demand — synchronized with its knowledge base updates — using the three-agent architecture (Questioner, Responder, Polisher) and the greedy traversal clustering algorithm. The MTR-EVAL auditing methodology further provides a systematic quality gate for Lyra's own generated benchmarks.

### Workstream Route
**§4.5 — Evaluation & Benchmarking (RAG subsystem)**

This directly feeds the evaluation harness for Lyra's retrieval and conversational search capabilities. The greedy traversal clustering is an elegant replacement for naive threshold-based clustering when building evaluation datasets. The multi-agent generation pattern (separating question generation, answer grounding, and linguistic polishing into distinct roles) is reusable for Lyra's own data synthesis pipelines.

### Impact/Effort/Tier
- **Impact:** 4 — Directly improves Lyra's ability to evaluate retrieval quality at scale; enables continuous benchmarking
- **Effort:** 3 — Requires implementing greedy traversal clustering (~200 lines), adapting three prompts for Lyra's domain, and integrating with existing embedding infrastructure. The paper provides complete prompts in Appendix Tables 12-18
- **Tier:** `breakthrough` — The 43.54-point performance gap demonstrates this approach reveals retrieval weaknesses invisible to existing benchmarks, and the 1/400x cost reduction enables evaluation at a scale previously impossible for enterprise RAG systems
