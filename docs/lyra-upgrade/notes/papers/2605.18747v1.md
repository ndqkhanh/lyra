## 1. Mechanism (Step-by-Step)

This is a **taxonomy/survey paper** organizing 300+ papers across three connected layers of "code as agent harness":

### Layer 1: Harness Interface — Code for Reasoning, Acting, Environment Modeling (§2)

**Code for Reasoning (§2.1):**
- **Program-Delegated Reasoning**: Model generates programs; external interpreters execute and verify. PoT, PAL, Chain of Code. Separates problem decomposition from computation.
- **Formal Verification/Symbolic Interfaces**: Hybrid neural-symbolic methods (CodeSteer, VisualCoder). Proof assistants (Lean, Coq, Isabelle) as verifiable reasoning backends.
- **Iterative Code-Grounded Reasoning**: Generate→Execute→Verify→Refine loops. CodePRM learns process rewards over execution trajectories. RLEF optimizes via multi-step execution feedback. EG-CFG injects execution signals during generation.

**Code for Acting (§2.2):**
- **Grounded Skill Selection**: SayCan maps language plans to feasible skills via affordance; KnowNo adds conformal prediction for uncertainty calibration.
- **Programmatic Policy Generation**: Code-as-Policies (CaP) generates Python programs as robot control policies. Code-BT compiles to behavior trees.
- **Lifelong Code-Based Agents**: Voyager (Minecraft skill library), LYRA (human corrections→reusable skills), ViReSkill (vision-grounded replanning).

**Code for Environment (§2.3):**
- **Structured World Representations**: ViStruct, FactoredScenes, Code2World — encode environments as executable programs.
- **Execution-Trace World Modeling**: CWM learns world models from program traces. WorldCoder writes updatable Python world models.
- **Code-Grounded Evaluation**: SWE-bench (unit tests as ground truth), AgentBench, LiveCodeBench — execution-based evaluation.
- **Verifiable Environment Construction**: SWE-smith, EnvScaler — programmatic synthesis of evaluation environments.

### Layer 2: Harness Mechanisms — Planning, Memory, Tool Use, Control, Optimization (§3)

**Planning (§3.1):**
- Linear decomposition (Self-Planning, WebAgent, PLAN.md files)
- Structure-grounded (CodePlan with plan graphs, VerilogCoder with task-circuit graphs)
- Search-based (Tree-of-Code, ReThinkMCTS, SWE-Search)
- Orchestration-based (MapCoder stages, Blueprint2Code pipelines, Intelligent Harness Runtime)

**Memory & Context Engineering (§3.2):**
- Working memory: SWE-agent state tracking, CodeMem budgeted slot management
- Semantic memory: AutoCodeRover repo structure retrieval, RepoCoder iterative evidence collection
- Experiential memory: MemGovern (governed experience replay), ExpeL (reflection traces)
- Long-term memory: MemCoder (commit-structured), TALM (tree-structured generation)
- Multi-agent memory: ChatDev phase-level context, G-Memory hierarchical sharing
- Context compaction: LongCodeZip (coarse-to-fine compression), SWE-Pruner (task-aware pruning)

**Tool Use (§3.3):**
- Function-oriented: ToolCoder (API search integration), RAG-for-Code
- Environment-interaction: SWE-agent (shell/editor interface), OpenHands workspace
- Verification-driven: AgentCoder (programmer-tester-executor loop), VeriGuard (proof-gated generation)
- Workflow-orchestration: MapCoder, OpenHands SDK with lifecycle hooks

**PEV Control Loop (§3.4):**
The Plan→Execute→Verify loop is the central harness control mechanism:
1. **Plan**: Externalize intended change + validation criteria as contract
2. **Execute**: Apply within sandboxed + permissioned environment (read-only / sandbox-edit / full-access tiers)
3. **Verify**: Deterministic sensors (linters, compilers, tests, analyzers) + human-review gates
4. **Repair/Escalate**: Sensor evidence routes to model diagnosis, missing context retrieval, localized patching, or HITL escalation

**Agentic Harness Engineering (AHE) (§3.5):**
- Deep telemetry: structured traces (prompts, token cost, tool latency, edited files, diffs, test results, stack traces, permission requests, human interventions)
- Evolution Agent: observes trajectories → diagnoses failures → proposes harness revisions (prompts, tool schemas, retrieval policy, permission rules, workflow topology) → evaluates on held-out tasks → promotes verified improvements
- Governed harness mutation: changes evaluated in sandboxes, compared against regression suites, HITL approval for risky modifications

### Layer 3: Scaling the Harness — Multi-Agent Orchestration (§4)

**Role Specialization (§4.1):**
- Manager, Planner, Coder, Reviewer, Tester, Executor roles
- Synthesis agents, Understanding agents, Verification agents, Execution agents, Planning agents
- EvoMAC introduces Gradient Agent (reads execution logs to attribute failures) and Updating Agent (revises workflow DAG)

**Interaction Modes (§4.1.2):**
- Collaborative synthesis (PairCoder Navigator-Driver)
- Critique and repair (virtually all systems)
- Adversarial validation (AutoSafeCoder fuzzing, MAGE waveform mismatch)
- Reasoning debate (CANDOR 3-panelist majority vote)

**Workflow Topologies (§4.1.3):**
- Chain (waterfall), Cyclic (agile/iterative), Hierarchical (manager→workers), Star (hub→parallel)
- Adaptive: Dynamic agent pool scaling (SoA), Feedback-driven DAG restructuring (EvoMAC), Runtime self-reorganization (SEW)

**Shared Harness Representations (§4.3):**
- Implicit/file-only → Repository-based → Execution-based → Blackboard/Shared-state
- **Key finding**: Majority of systems are in the implicit/file-only category; the central gap is lack of formal shared code-centric harness substrate
- None of the surveyed systems fully unify repository-based and execution-based representations

**Convergence Patterns (§4.3.2):**
- Test-gated (most principled, e.g., AgentCoder), Security-gated (AutoSafeCoder), Performance-gated (MACRO), Score-based (MAGE, CodeCoR), Consensus-voting (CANDOR), Implicit (most common — fixed iterations with no objective criterion)

### Open Problems (§5.2):
1. Harness-level evaluation beyond final task success (trajectory efficiency, verification strength, recovery ability, state consistency, safety compliance, replayability)
2. Semantic verification beyond executable feedback (verification stack with explicit scope)
3. Self-evolving harnesses without regression (change contracts, held-out suites, safety invariants)
4. Transactional shared program state (reads/writes/assumptions/versions/conflict policies)
5. Human-in-the-loop safety as harness state (multi-tier permissions, auditable approvals)
6. Multimodal code-harness systems (visual grounding, multimodal context compression)
7. Toward a science of harness engineering

## 2. Results

As a survey paper, this work does not present original experimental results. It synthesizes evidence from 300+ cited papers. Key benchmark figures cited from the literature:

Key qualitative findings:
- Execution-based convergence (test-gated) is the most principled pattern; implicit convergence (fixed iterations) remains most common — a significant gap
- LLM-simulated execution can match real execution for common bugs but fails on corner cases (crashes, resource exhaustion, boundary conditions)
- Topology complexity inversely correlates with harness-state formality: systems with explicit shared substrates use simpler topologies
- Production harnesses (Claude Code, Codex, Copilot) are becoming dominant training data sources for next-gen code models

## 3. Trade-offs

| Win | Cost/Loss |
|-----|-----------|
| Code as harness provides **executable verification** (tests, compilers) — objective signals that cannot hallucinate | **Oracle adequacy crisis**: weak test suites can create false sense of correctness; green tests ≠ full specification |
| Explicit shared harness substrate enables **simpler, more transparent coordination** topologies | Building/maintaining formal shared state requires **significant infrastructure** (blackboard systems, transactional semantics) |
| Deterministic verification sensors (linters, type checkers, fuzzers) provide **reliable control signals** for the PEV loop | **Verification stack complexity** grows with each added sensor; must declare what each verifies and what it misses |
| Multi-agent role specialization improves **division of labor and inspectability** | **Context management becomes the tax** of implicit shared state; each agent sees only a filtered view |
| Agentic Harness Engineering enables **data-driven harness improvement** without model retraining | **Regression risk**: harness mutations can weaken safety, increase cost, or hide failures on rare tasks |
| Code-mediated coordination (files, diffs, tests, logs) is richer than pure message-passing | **Coordination bottlenecks persist**: each channel trades off fidelity, latency, and scope; conflicts across channels remain unresolved |
| LLM-simulated execution achieves 98%+ precision for common bugs, reducing compute cost | **Silent failures on corner cases**: simulated reasoning misses runtime crashes, resource exhaustion, boundary conditions |

## 4. Design Rationale

**Why "code as harness" rather than "code as output":** The authors argue that code's three properties — executability (machine-verifiable outcomes), inspectability (structured traces for diagnosis), and statefulness (persistent, modifiable task progress) — make it the ideal operational substrate for grounding agent behavior, not merely a product to generate. Natural language is ambiguous, non-executable, and ephemeral; code is the opposite.

**Why a 3-layer taxonomy:** The survey organizes around how code enters the agent loop (interface), how it sustains reliability over time (mechanisms), and how it scales across agents (orchestration). This follows the natural lifecycle of agentic systems from single-shot to persistent to collaborative.

**Why PEV as the central control loop:** Separating planning (intent externalization), execution (bounded state transition), and verification (deterministic sensor readout) makes the harness governable — each phase has distinct permissions, sandboxing, and audit requirements. This contrasts with monolithic approaches where model reasoning and tool execution are interleaved without explicit control boundaries.

**Why AHE (Agentic Harness Engineering):** Observed failures in code agents often arise from missing repository context, brittle tool interfaces, weak validators, or mismatched permission boundaries — not from model generation quality. Therefore, the harness itself must be an object of optimization, measured through deep telemetry and evolved under governed mutation.

## 5. Limitations & Failure Modes

1. **Oracle adequacy is the single biggest threat to validity**: The paper identifies that execution feedback creates a "false sense of correctness" when verifiers are incomplete. Unit tests, static analyzers, and GUI checkers all miss failures. The survey does not solve this — it frames it as the key open problem.

2. **Implicit/hidden state dominates deployed systems**: The majority of surveyed multi-agent systems lack formal shared harness substrates. Agents reconstruct state from conversational history at each invocation, making them vulnerable to belief-state divergence that the system cannot detect or correct.

3. **No unified structure+behavior representation**: No surveyed system combines repository-based representation (static code structure, dependencies) with execution-based representation (dynamic runtime behavior, traces) into a single queryable substrate. This prevents answering questions like "which components are slow" or "does this refactoring break external APIs."

4. **Implicit convergence is the norm**: Most systems terminate after fixed iterations with no objective quality criterion — a direct consequence of lacking formal shared substrates.

5. **Failure attribution is immature**: Best step-level attribution accuracy in production agent loops is only 14–53%, meaning most harness debugging remains guesswork.

6. **Survey scope limitation**: The paper explicitly excludes model-internal capabilities (reasoning architecture, training methods) and focuses only on system-provided harness infrastructure + agent-initiated code artifacts. A complete picture requires integrating all three.

7. **Rapidly moving target**: The survey captures a 2026 snapshot; production harnesses (Claude Code, Codex, Copilot) evolve weekly, and their internal architectures are partially proprietary.

## 6. Transfer to Lyra

**The ONE transferable idea:** The **PEV (Plan→Execute→Verify) control loop** with explicit, deterministic verification sensors, permission tiers, and sandbox boundaries. This is the survey's core architectural pattern and directly addresses Lyra's current weakness: verification that relies on the model's own self-assessment rather than deterministic code execution signals.

**Applied to Lyra:** Lyra should structure every agent action as a PEV transition:
- **Plan**: Externalize intended changes into a structured contract (modified files, expected invariants, validation commands, rollback points). Use PLAN.md-style persistent artifacts.
- **Execute**: Apply changes within a sandboxed workspace with permission tiers (read-only for browsing, sandbox-edit for code changes, full-access gated by HITL for deployments/network).
- **Verify**: Run deterministic sensors (linters, type checkers, unit tests, static analyzers, fuzzers) and gate state acceptance on their output. Only escalate to human/agentic critique when sensor evidence is ambiguous.

**Workstream route:** §4.4 (Agent Verifier) — This directly upgrades Lyra's verification subsystem from model-self-assessment to deterministic execution-grounded verification. Secondary impact on §4.5 (Harness Engineering) for the deep-telemetry/Evolution Agent pattern.

**Feasibility rationale:** Lyra already has execution substrates (Python REPL, shell commands) and tool interfaces. The missing piece is structuring them into a formal PEV loop with explicit verification gates, permission tiers, and artifact-level contracts. This is an architectural refactor rather than new model training.
