# FrugalGPT: How to Use Large Language Models While Reducing Cost and Improving Performance

**Authors:** Lingjiao Chen, Matei Zaharia, James Zou (Stanford University)  
**Venue:** arXiv:2305.05176v1, May 2023; also presented at ICML 2023 as "Less is More: Using Multiple LLMs for Applications with Lower Costs"  
**Citations:** 150+ (Semantic Scholar)

## 1. Mechanism (Step-by-Step)

FrugalGPT is a **cost-aware LLM orchestration framework** with three strategy families. The core contribution is the **LLM Cascade**, which routes each query to the cheapest model capable of answering it reliably.

### 1.1 Problem Formulation

Given a query distribution Q, a marketplace of K LLM APIs with per-token pricing, and a budget b:

**Objective:** Maximize task accuracy subject to E[cost] <= b

The search space is vast: which prompt to use, which LLM(s) to invoke, how to aggregate responses.

### 1.2 Strategy 1: Prompt Adaptation

**Prompt Selection:** Given a query q, embed it with a sentence transformer (all-MiniLM-L6-v2), compute cosine similarity against a pool of in-context examples, and retain only the top-k (e.g., k=5 instead of k=20). This reduces prompt token count by ~70%.

**Query Concatenation:** Batch multiple queries into one prompt (e.g., 3 queries share system instructions + few-shot examples), reducing per-query overhead by ~50%.

### 1.3 Strategy 2: LLM Approximation

**Completion Cache:** Two modes:
- *Simple cache:* exact-match cache with TTL. ~8% hit rate, ~99% cost savings per hit.
- *Semantic cache:* embedding-based similarity lookup. ~21% hit rate, ~95% cost/latency reduction per hit.

**Model Fine-Tuning:** Collect responses from an expensive LLM (GPT-4) on a small training set, then fine-tune a smaller model (GPT-J, Haiku) to replicate those outputs. Converts a 281-token zero-shot prompt for Opus (3.2 cents) to a few-shot prompt for Haiku (0.05 cents) — a ~98.5% cost reduction.

### 1.4 Strategy 3: LLM Cascade (Core Mechanism)

**Step 1 — Build an ordered LLM list L = [M_1, M_2, ..., M_m]:** Sort LLMs by cost (cheapest first). The paper uses m=3.

**Step 2 — Train a scoring function g(q, a) -> [0, 1]:** A DistilBERT model is fine-tuned for regression to predict the reliability of an LLM answer `a` for query `q`. Input: concatenation of query text and generated answer. Output: reliability score between 0 and 1.

**Step 3 — Learn per-LLM thresholds tau_i:** On a validation set, grid-search over threshold values for each LLM in the cascade to maximize accuracy conditioned on the cost budget. The optimization prunes candidate lists where consecutive LLMs produce nearly identical answers (low disagreement).

**Step 4 — At inference time, for each query q:**
```
for i = 1 to m:
    a_i = M_i(prompt(q))
    score = g(q, a_i)
    total_cost += cost(M_i, prompt(q), a_i)
    if score > tau_i:
        return a_i  // accept answer, stop cascade
    // else: escalate to next (more expensive) LLM
return a_m  // fallback: return last LLM's answer
```

**Step 5 — Budget-aware optimization:** The cascade is tuned so that the expected cost across all queries stays within budget b, while maximizing accuracy. The paper approximates the objective via interpolation over sampled queries.

### 1.5 Key Enabler: LLM Complementarity

The Maximum Performance Improvement (MPI) matrix measures pairwise complementarity: what fraction of queries that LLM_X gets wrong does LLM_Y get right? On HEADLINES, ~6% of GPT-4 errors are correctly answered by GPT-J or J1-L. On COQA, ~13% of GPT-4 errors are correctly answered by GPT-3. This complementarity is what makes cascading strictly better than using any single model.

### 1.6 Cost Model

Cost = (prompt_tokens * prompt_rate) + (generation_tokens * generation_rate) + fixed_per_query_fee

The paper surveys 12 LLM APIs from 5 providers (OpenAI, AI21, Cohere, ForeFrontAI, Textsynth), finding pricing differentials of up to 150x (GPT-4: $30/10M prompt tokens vs GPT-J: $0.20/10M prompt tokens).

## 3. Trade-Offs

| Win | Cost / Lose |
|-----|-------------|
| 59-98% cost reduction vs. best individual LLM | Requires labeled training data from same distribution as target queries |
| +1.5-4% accuracy improvement possible at equal cost | Training the scoring function and tuning thresholds is a one-time upfront cost (amortized over query volume) |
| Adaptively selects cheapest-sufficient model per query | Cascade adds latency: sequential LLM calls instead of one parallel call (not addressed in paper) |
| Works with any LLM marketplace / provider mix | Scoring function (DistilBERT) quality limits cascade accuracy — a weak scorer causes unnecessary escalation or premature acceptance |
| Semantic cache provides 21% hit rate at 95% savings | Cache can serve stale/wrong answers if not invalidated; semantic threshold requires backtesting |
| Prompt selection reduces tokens by 70% | Removing examples can degrade few-shot reasoning on complex queries |
| Model fine-tuning yields 94% cost reduction | Fine-tuned model may not generalize beyond the expensive LLM's training distribution |
| Complementarity enables beating any single model | In ~6-13% of cases (MPI ceiling), still misses answers that all models get wrong |

## 4. Design Rationale

**Why cascade over single-model routing?** The authors observed that LLM errors are not nested — cheaper models are not strict subsets of expensive ones. The MPI analysis proved complementarity: GPT-J sometimes succeeds where GPT-4 fails (~6% of queries). A cascade exploits this by giving cheap models "first crack" at every query, only escalating when the scorer flags low reliability.

**Why DistilBERT as scorer?** The scoring function must be cheap enough to not eat into cost savings. A 66M-parameter DistilBERT costs negligible compute compared to any LLM API call, making it essentially "free" to run before each escalation decision.

**Why m=3 cascade length?** The paper fixes cascade depth at 3 for experiments, striking a balance between cost granularity and latency. More tiers would allow finer cost control but increase worst-case latency.

**Why three separate strategies?** Prompt adaptation and LLM approximation are composable with the cascade — the paper notes that joint prompt+LLM selection yields further gains. Each strategy addresses a different cost driver: token count (prompt adaptation), redundant computation (cache), and model selection (cascade).

## 5. Limitations and Failure Modes

1. **Requires labeled training data:** The cascade scoring function and thresholds need a validation set drawn from the same distribution as production queries. Domain shift degrades routing accuracy.

2. **One-time training cost:** Learning the cascade strategy itself consumes resources — justified only when downstream query volume exceeds the training set size.

3. **Latency unaddressed:** Sequential LLM calls in a cascade increase worst-case response time. The paper does not measure or optimize for latency.

4. **All-models-wrong failure:** When every LLM in the cascade produces an incorrect answer, FrugalGPT still queries all m models (maximum cost for zero gain) — the scorer cannot reject answers it cannot detect as wrong.

5. **Uncertainty when all models agree:** When all LLMs give the same answer but FrugalGPT's scorer remains uncertain, it may query all tiers unnecessarily — an open problem acknowledged by authors.

6. **Fairness, privacy, environmental impact not addressed:** Noted as future work.

7. **Prompt adaptation can hurt complex reasoning:** Fewer in-context examples may degrade multi-step reasoning tasks where diverse exemplars matter.

8. **Cache age/staleness:** Cached answers become outdated; semantic similarity threshold tuning requires careful backtesting on ~5K requests.

9. **Evaluation limited to classification/short-answer tasks:** No evaluation on long-form generation, creative writing, or open-ended dialogue.

10. **No attention-acceleration coverage:** The paper explicitly excludes orthogonal approaches like FlashAttention, KV-cache optimization, etc.

## 6. Transfer to Lyra

**The ONE transferable idea:** A **learned LLM cascade with a lightweight DistilBERT-class scorer** that routes each user query through a tiered model chain (cheap -> expensive), accepting early answers when the scorer is confident and escalating only when necessary. This directly applies to Lyra's router subsystem (§4.5), where different query types (factual lookup, code generation, reasoning) warrant different model tiers and cost allocations.

**Workstream:** §4.5 — Router & Model Selection (query-adaptive model routing with cost-awareness)

**How Lyra can adopt it:**
- Replace Lyra's static model-routing rules with a learned scoring function that assesses answer reliability per query
- Build a 2-3 tier cascade: local/edge model -> mid-tier API (Haiku) -> frontier API (Sonnet/Opus)
- Train the scorer on Lyra's own query-answer pairs using a small classifier (DistilBERT or modern equivalent like DeBERTa-v3-small)
- Implement MPI-style complementarity analysis across Lyra's candidate models to inform cascade ordering

**Impact:** 5 (directly reduces per-query cost by 50-90% while maintaining accuracy, core to Lyra's cost sustainability)  
**Effort:** 2 (cascade logic is <200 lines; scorer training needs labeled validation set; deployment is stateless routing)  
**Tier:** breakthrough (transforms Lyra's cost structure permanently; cascading is additive to existing routing, not a rewrite)
