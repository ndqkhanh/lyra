# MUSE-Autoskill: Self-Evolving Agents via Skill Creation, Memory, Management, and Evaluation

**Authors:** Huawei Lin (ByteDance / RIT), Peng Li, Jie Song, Fuxin Jiang, Tieying Zhang (ByteDance Inc.)
**Venue:** arXiv preprint, May 2026
**arXiv ID:** 2605.27366v1
**Correspondence:** tieying.zhang@bytedance.com
**Backbone model:** GPT-5.5 (04/24/2026)
**Benchmark:** SkillsBench (51 tasks, 4 super-domains: Science & Engineering, Data Analysis, Document Processing, Ops & Planning)

## 1. Mechanism (step-by-step)

MUSE-Autoskill is a **training-free, skill-centric agent framework** organized around a complete five-stage skill lifecycle. All non-built-in functionality is implemented as skills, and the agent dynamically creates, reuses, evaluates, and refines them within a ReAct loop.

### Architecture (Figure 3)

The system has two tiers:
- **Master Agent**: A ReAct loop (Plan → Action → Observation) over a pretrained LLM
- **Skill Subsystem**: Creation, Storage (Skill Bank), Evaluation, Feedback/Refinement, Memory

### Five Lifecycle Stages

1. **Skill Creation** — The agent invokes `skill_create` (one of two built-in skills; the other is `web_search`) when no existing skill fits the task. It specifies intent (purpose, inputs, expected outputs), and the system generates a structured skill package: `SKILL.md` (YAML frontmatter with name/description + Markdown body with workflow steps), optional `scripts/`, `tests/`, `resources/` directories. The skill format mirrors Anthropic's Agent Skills standard for interoperability. On the 35/51 tasks where Phase 1 succeeded, creation costs ~383K tokens and ~164 s per skill (median).

2. **Skill Evaluation** — After creation, the system runs the bundled pytest test suite inside a sandbox. **Tests must pass before the skill is registered** into the Skill Bank. Failed tests trigger automatic refinement (update_skill), forming the create → evaluate → register loop. 9% of MUSE-generated skills include `tests/` (vs. 0% for human-authored SkillsBench skills).

3. **Skill Memory** — Three memory tiers: (a) **Short-term**: current task context, adaptively compressed; (b) **Long-term**: persistent cross-session notes (e.g., "prefer batched I/O"); (c) **Skill-level memory** (the novel contribution): a `.memory.md` file per skill that accumulates notes, lessons, failure modes, and usage observations across tasks. When a skill is loaded later, this experience is surfaced alongside `SKILL.md`.

4. **Skill Management** — At task start, a YAML catalog of all skills (name + description only, following Anthropic's progressive-disclosure pattern) is injected into the system prompt. The agent selects relevant skills via `read_skill`. Maintenance includes: **refinement** (patch on test/execution failure), **merging** (deduplicate overlapping skills), **pruning** (remove consistently failing or unused skills). A bank with 100 skills adds ~5-10K tokens of catalog, not ~500K of full bodies.

5. **Skill Refinement** — When unit tests or runtime execution fail, the agent invokes `update_skill` to patch the package, then re-runs tests. This closes the self-evolution loop.

### Context Management (Figure 4)

Context is modeled as a **DAG of conversation nodes**, one per ReAct turn (plan, action, observation triple). Each node has two pointer sets: mutable `parent_id` (active chain sent to LLM) and immutable `history_prev`/`history_next` (full original history). Compression is two-level:

- **Level 1** (per-node): If a single node exceeds 15K tokens (`NODE_COMPRESS_TOKEN_THRESHOLD`), its content is summarized in-place. KEEP_FIRST and KEEP_LAST (both 5 turns) are pinned verbatim.
- **Level 2** (chain compression): If the total exceeds 180K tokens (`COMPRESS_TOKEN_THRESHOLD`), a contiguous span of middle turns is collapsed into one synthetic summary node, which replaces them in the active chain.

Original nodes are preserved via immutable history pointers, enabling full replay and cross-session resume via `ctx_state.json` snapshots.

### Skill Execution

Skills run inside an **isolated sandbox** (create_sandbox, sandbox_run, sandbox_upload/download, close_sandbox) with its own filesystem. Execution reuses the agent's general-purpose tools (file reading, terminal commands, sandbox calls) rather than a separate execution engine.

### Skill Package Schema (Appendix B)

- Directory root: kebab-case skill name
- `SKILL.md`: YAML frontmatter (name, description) + Markdown body (trigger conditions, core principles, recommended tools, step-by-step workflow)
- Optional: `scripts/`, `tests/` (pytest-compatible), `resources/`, `references/`
- `.memory.md`: per-skill memory, excluded from package during transfer

## 2. Results (real benchmark numbers)

### Skill Usage (52→68%)
- All three GPT-5.5-backed agents benefit from human-authored skills: Codex 52.11% → 67.28% (+15.17 pp), Hermes 47.89% → 61.21% (+13.33 pp), MUSE-Autoskill 53.19% → 68.40% (+15.21 pp).
- MUSE-Autoskill leads in 3 of 4 super-domains with human skills. Trails Codex in Sci & Eng (72.86% vs. 78.57%) due to 3 boundary tasks where verifier penalizes methodology choices.

### Self-Generated Skills (53→60% overall, ~88% on covered tasks)
- MUSE-Autoskill self-created skills: 60.35% across all 51 tasks (+7.16 pp over no-skill baseline).
- On the **35 tasks where generation succeeded** (68.6% coverage), Phase 2 accuracy reaches **87.94%**, exceeding the human-skill ceiling of 68.40%.
- 16 tasks fail Phase 1 (coverage bottleneck), contributing 0% to the macro-average.

### Cross-Agent Transfer
- Hermes improves from 47.89% to 58.40% (+10.51 pp) when using MUSE-generated skills without modification.
- Closes **79% of the gap** between Hermes-no-skills and Hermes-human-skills.
- Hermes (58.40%) and MUSE-Autoskill (60.35%) end within ~2 pp on the same generated skills.

### Cost Efficiency (Table 6, Figure 5)
- Generated skills are **Pareto-optimal**: higher reward AND lower latency AND fewer tokens vs. both no-skills and human-skills conditions.
- MUSE-Autoskill with generated skills: 493K tokens, 411 s latency, 15 turns (vs. 578K/684s/20t without skills, vs. 615K/656s/19t with human skills).
- Hermes with generated skills: 97K tokens, 257 s, 13 turns (vs. 181K/370s/14t without, vs. 186K/369s/14t with human).
- **-20% tokens and -37% latency** for MUSE-Autoskill; **-48% tokens and -30% latency** for Hermes.
- 383K token generation cost amortizes after ~3 reuses for MUSE-Autoskill; latency saving exceeds creation cost on first reuse.
- ~58% of input tokens are prompt-cache hits; output tokens are <3% of total.

### Skill Anatomy (Figure 6)
- MUSE skills median SKILL.md: 326 lines (15.8 KB) vs. human skills: 146 lines (6.6 KB) — ~2.2x longer.
- 91% of MUSE skills are "SKILL.md only" (no subdirectories); 9% include tests/.
- Human skills: 69% SKILL.md only, 22% include scripts/, 0% include tests/.

### Per-Domain with Std Dev (Table 10)
- Sci & Eng: largest benefit from skills (lifts +17 to +24 pp), σ shrinks for all agents.
- Document Processing: highest baselines (71-82%), small headroom (+2 to +11 pp).
- Ops & Planning: lowest baselines (36-40%), skills recover +14 to +17 pp.

## 3. Trade-offs

| Dimension | Win | Cost/Loss |
|-----------|-----|-----------|
| **Accuracy** | +15.21 pp with human skills; +7.16 pp self-generated; 87.94% on covered tasks | 16/51 tasks (31.4%) produce no skill at all (coverage bottleneck) |
| **Latency** | -37% for MUSE, -30% for Hermes with generated skills | One-time creation cost: ~383K tokens, ~164 s per skill |
| **Token usage** | -20% for MUSE, -48% for Hermes with generated skills | ~2.2x longer SKILL.md than human-authored (326 vs 146 lines median); catalog adds 5-10K tokens/100 skills |
| **Skill depth** | More procedural detail replaces noisy reasoning | Deeper ReAct loops than peers (18-19 turns median vs. Codex 11-12, Hermes 13-14) |
| **Transferability** | Cross-agent transfer: Hermes closes 79% of gap, within ~2 pp of MUSE | Only validated MUSE→Hermes direction; per-skill memory excluded from transfer |
| **Reliability** | Unit-test-gated registration; refinement on failure | Skills distilled from single trajectory — may encode trajectory-specific quirks (e.g., hvac-control regression 80%→20%) |
| **Context management** | Two-level adaptive compression preserves replayability; original nodes kept via immutable history pointers | Compression costs one LLM call per 10-20 turns on long tasks |
| **Coverage** | 68.6% of tasks generate usable skills | Most failures cluster in specialized production tooling + numerical non-textual reasoning |

## 4. Design Rationale (why this approach)

1. **Training-free by design**: All skill operations (creation, evaluation, refinement, compression) use the same pretrained LLM via inference-time calls. This avoids coupling skills to a trained policy or requiring fine-tuning when switching backbones. Contrast with RL-based methods (Skill1, SkillOS, SkillMaster) where skills are tied to a policy.

2. **Full lifecycle coverage**: Prior methods each address 1-3 stages of the skill lifecycle (creation + refinement for Voyager/AutoSkill; creation only for Anthropic Skills). MUSE argues that all five stages (creation, memory, management, evaluation, refinement) must coexist for skills to be reliable, long-lived assets rather than disposable artifacts.

3. **Skill-level memory as a distinct scope**: Rather than pooling all experience into one flat memory (as Reflexion, ExpeL do), MUSE gives each skill its own `.memory.md` file. This lets accumulated experience surface at invocation time without cluttering the context — lessons about PDF parsing are only loaded when the PDF skill is used.

4. **Unit-test-driven evaluation for reliability**: Anthropic Skills leaves evaluation to human authors. MUSE makes unit tests a system requirement: skills must pass their bundled tests to be registered, and test failure triggers automatic refinement. This is the only training-free system with this property.

5. **Externalized skill format**: Using Anthropic's open Agent Skills format means skills are directories of Markdown + scripts, not internal model states. This enables cross-agent transfer (validated empirically), version control, and human inspection.

6. **Two-level compression over truncation**: Truncation (dropping middle turns) loses ~30-40% of early-context facts that are revisited. Summarization preserves these at ~1/10 token cost.

## 5. Limitations & Failure Modes

1. **Coverage bottleneck (primary)**: Skill generation depends on Phase 1 success. 16/51 tasks (31.4%) produce no successful trajectory → no skill. Failures concentrate in specialized production tooling (network routing diagnosis, intrusion detection, LLM internals) and numerically-heavy non-textual reasoning (PDEs, MILP, 3D parsing). The paper leaves "partial skill extraction from failed trajectories" to future work.

2. **Single-trajectory distillation**: Each skill is distilled from one successful run, not from multiple diverse solutions. This can encode trajectory-specific quirks: the hvac-control regression (80%→20%) occurs because the source trajectory used a calibration routine specific to one simulator's noise profile.

3. **Within-task evaluation**: Skills are evaluated on the same tasks from which they were distilled. Although the verifier is deterministic and no ground-truth is leaked into skills, this overstates the within-task gain by coupling skill content to source trajectories.

4. **Cross-agent transfer limited**: Only validated for MUSE→Hermes direction. Broader generalization across more agents unconfirmed.

5. **51/94 task subset**: Excluded tasks have more complex Docker environments and may be harder. Reported numbers may overestimate system-wide performance.

6. **Confidence intervals**: Only 5 runs per task; CIs are wide, especially for binary-reward tasks.

7. **Backbone single model**: Only tested on GPT-5.5. No results with other model families (Claude, Gemini, Llama).

8. **No independent benchmark**: Only evaluated on SkillsBench. Generalization to other benchmarks (GAIA, SWE-bench) not assessed.

9. **Per-skill memory not transferred**: The `.memory.md` is excluded from skill packages during transfer (by design), so accumulated experience does not carry over.

## 6. Transfer to Lyra

### The ONE transferable idea

**Skill-level memory with unit-test-gated lifecycle**: Lyra should adopt a per-tool/per-skill `.memory.md` file that accumulates usage patterns, failure modes, and parameter quirks across sessions. This experience would be surfaced as context the next time that tool/skill is invoked, enabling Lyra to learn from past mistakes without manual curation.

More broadly, the five-stage lifecycle (create → evaluate-gate → register → accumulate memory → refine on failure) can be applied to Lyra's tool definitions: when Lyra dynamically generates a new tool (e.g., a custom parser or API wrapper), the system should (a) auto-generate a test suite for it, (b) only register it for reuse if tests pass, (c) attach a `.memory.md` that grows with each use, and (d) trigger automatic repair when execution fails.

### Workstream routing: **§4.2 (Tool & Skill Architecture)**

This directly feeds Lyra's tool/skill subsystem with lifecycle-management patterns. The skill catalog mechanism (progressive disclosure — name+description eagerly, full body on demand) is also directly applicable to Lyra's tool-registration and context-budget management.

### Assessment

| Metric | Value |
|--------|-------|
| **Impact** | 4 — Test-gated skill registration + per-skill memory would significantly improve reliability of dynamically generated Lyra tools |
| **Effort** | 3 — Requires implementing `.memory.md` append-only files, a test-generation step during tool creation, and a registration gate; moderate engineering |
| **Tier** | **Breakthrough** — No existing Lyra subsystem does lifecycle-managed, test-gated, memory-accumulating tool evolution; this fills a clear gap |

### Concrete Lyra implementation sketch
1. When Lyra's `tool_create` is invoked, also generate a `tests/` directory with at least one parameterized test case.
2. Run tests in a sandbox before registering the tool.
3. Attach a `.memory.md` file per tool for accumulating usage notes.
4. On tool execution failure, invoke `tool_update` with error trace, re-run tests, re-register.
5. Implement progressive disclosure for the tool catalog (name+description in system prompt; full spec loaded on demand).
