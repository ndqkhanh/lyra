## 1. Mechanism (step-by-step)

SkillOS is an experience-driven RL training recipe for learning skill curation in self-evolving LLM agents. The architecture is a **modular two-agent system**:

### Architecture
- **Frozen Agent Executor (𝜋L):** Solves tasks by retrieving relevant skills from a shared SkillRepo via BM25 (top-k=5). Never updated during training.
- **Trainable Skill Curator (𝜋S):** Observes the executor's trajectory after each task and issues structured curation operations (insert, update, delete) to modify the SkillRepo. Trained via GRPO.

### Skill Representation
Each skill is a single Markdown file with:
- **YAML frontmatter:** `name` and `description` fields
- **Markdown body:** Sections like `# Workflow`, `# When NOT to Use`, `# Prerequisite Constraints`, plus emergent sections (failure handling, conditional branches, optimization tips)

### Training Pipeline (Algorithm 1)

```
For each training step:
  1. Sample a task group G = (x₁, ..., x_|G|) from grouped training data
  2. Initialize empty SkillRepo S ← ∅
  3. For each task xᵢ in G (i = 1...|G|):
     a. Retrieve relevant skills S̃ ← BM25(xᵢ, S)
     b. Run frozen executor: ξᵢ ← RunTask(S̃, 𝜋L, xᵢ)
     c. Sample curation rollout: cᵢ ~ 𝜋S(· | ξᵢ, S̃)
     d. Apply operations: S ← ApplyOps(S, cᵢ)
  4. Compute composite reward: r = r_task + λ_f·r_fc + λ_u·r_cnt + λ_c·r_comp
  5. Update 𝜋S via GRPO
```

### Composite Reward (Equation 1)
```
r = r_task       # Average success on tasks 2..|G| (task 1 uses empty repo)
  + λ_f·r_fc     # Fraction of valid function calls
  + λ_u·r_cnt    # Content quality (LLM-as-judge: abstraction, reusability, actionability, faithfulness)
  + λ_c·r_comp   # Compression reward: 1 - |S|/|𝜒| (discourages verbatim copying)
```

### GRPO Optimization (Equation 2)
```
L = 𝔼_n[min(ρ_n·A_n, clip(ρ_n, 1-ε, 1+ε)·A_n)]
```
Where A_n = r_n - (1/N)Σr_n' is the group-relative advantage, and ρ_n is the importance ratio. KL term is **discarded** to encourage exploration.

### Task Grouping (§3.2.1)
Two-stage pipeline for reasoning tasks:
1. **Attribute Annotation:** Gemini-2.5-Pro annotates each task with 5 dimensions: Topics (T), Skills (S), Concepts (C), Heuristic Strategies (R), Common Pitfalls (P)
2. **Group Construction:** Dependency gating via soft-Jaccard similarity (cosine threshold τ=0.60 on all-MiniLM-L6-v2 embeddings) with constraints on shared foundation, shared reasoning, non-duplication, progression, and curriculum direction

For agentic tasks (ALFWorld, WebShop), default task-type annotations serve as the grouping signal directly.

### Curation Operations
- `insert_skill(name, content)` — create new skill
- `update_skill(skill_name, [new_name], [new_content])` — revise existing skill
- `delete_skill(skill_name)` — remove obsolete/harmful skill

### Training Details
- Base model: Qwen3-8B (both curator and executor during training)
- Hardware: 16× H100 GPUs
- Framework: verl (Sheng et al., 2024)
- LR: 1×10⁻⁶, batch size: 32, GRPO group size: 8
- Training time: ~3 days (ALFWorld), ~2.5 days (reasoning), ~5 days (WebShop)
- Max prompt length: 16,384 tokens; max response: 4,096 tokens

## 3. Trade-offs

| Win | Cost / Loss |
|---|---|
| +9.8% relative SR improvement across benchmarks | 3-5 days training on 16 H100 GPUs |
| Cross-executor generalization (8B→32B→Gemini) | Frozen executor limits mutual adaptation |
| Cross-task generalization (trained on ALFWorld, helps WebShop) | Off-diagonal transfer occasionally negative |
| Learned 8B curator outperforms Gemini-2.5-Pro zero-shot curator | Complex two-stage grouping pipeline required (LLM annotation + dependency gating) |
| -6.0% fewer interaction steps (cost savings) | BM25 retrieval is simple; dense retrieval might improve further |
| Self-organizing skill repo (meta-strategies emerge) | Single-file Markdown skills lack hierarchical composition |
| No executor retraining needed (modular deployment) | LLM-as-judge for content quality introduces noise and latency |
| GRPO without KL term enables exploration | Risk of policy collapse without KL regularization |
| Composite rewards attribute delayed feedback | Reward engineering adds hyperparameters (λ_f, λ_u, λ_c) |

## 4. Design Rationale

**Why decouple curator from executor?** Separating the skill curator (𝜋S) from the executor (𝜋L) isolates the contribution of skill curation to downstream performance. It also enables modular deployment — a single trained curator can serve multiple executors without retraining. The frozen executor also prevents confounding between curation quality and executor adaptation.

**Why grouped task streams?** Random task ordering provides only local, short-horizon feedback (was the last insert useful now?). Grouped task streams, where earlier tasks create skills evaluated by later related tasks, transform curation into a **long-horizon** learning problem. This design provides denser signals for complex operations (update, delete) that prior work struggled to learn.

**Why composite rewards?** The delayed nature of curation feedback (a skill created now may help 20 tasks later) makes end-to-end task reward alone too sparse. Adding intermediate signals — valid function calls, content quality judged by LLM, and repository conciseness — provides credit attribution that bridges the gap between curation actions and eventual task outcomes.

**Why Markdown skills?** Following Anthropic's SKILL.md paradigm (2025), Markdown provides a human-readable, editable, and composable format. It is natively supported by LLM tool use and aligns with the broader community standard for agent skills.

**Why GRPO over PPO?** GRPO's group-relative advantage normalization provides training stability and sample efficiency. Discarding the KL term encourages policy exploration, which is beneficial when the base model (Qwen3-8B) has no prior curation experience.

## 5. Limitations & Failure Modes

1. **Simple Retrieval (BM25):** Keyword-based retrieval may miss semantically relevant skills that use different terminology. Dense or hybrid retrieval could improve recall but was deferred to isolate the curation study.

2. **Flat Skill Representation:** Single-file Markdown skills cannot represent hierarchical compositions or executable scripts. Multi-file, hierarchical, and partially executable skills are needed for complex workflows.

3. **Frozen Executor Constraint:** The curator cannot shape executor behavior beyond what it writes into SkillRepo. Miscalibration between curated skills and executor idiosyncrasies cannot be resolved by the curator alone. Joint optimization could yield better alignment but at substantially higher cost.

4. **No Multi-Agent Support:** SkillRepo is a single agent's private artifact. No mechanisms exist for shared memory, conflict resolution between agents, or cross-agent credit attribution.

5. **Training Cost:** 3-5 days on 16 H100 GPUs is substantial. Smaller-scale or online adaptation methods are not explored.

6. **LLM-as-Judge Noise:** Content quality rewards depend on an external LLM judge whose assessments may be inconsistent or poorly calibrated, injecting noise into the RL signal.

7. **Negative Cross-Task Transfer:** Training on one domain occasionally hurts performance on another (Figure 3: -1.2 to -2.8 relative improvement in some off-diagonal cells), indicating that domain-agnostic skill curation is not guaranteed.

8. **Static Group Construction:** The grouping pipeline is one-shot and offline. In truly open-ended streaming settings, task dependencies are not known in advance.

## 6. Transfer to Lyra

**The ONE transferable idea:** Train a small RL-based *Skill Curator* model (separate from the main agent) that learns to insert, update, and delete skills in a Markdown-based skill repository. The curator is trained via GRPO on grouped task streams, where earlier tasks create skills that are evaluated by later related tasks, using a composite reward that combines downstream task success with intermediate signals (content quality, conciseness, function-call validity). This enables Lyra to **self-evolve** its skill collection from accumulated user interactions without manual curation.

**Workstream route:** §4.4 — Skills (primary). Also touches §4.2 — Memory (skill repo as procedural memory), §4.16 — Reliability (curator as quality-gate for skills), and §4.27 — RL-Optimizer (GRPO training infrastructure).

**Impact:** 5 (directly addresses the core Lyra skill management bottleneck; skill curation is the #1 cited challenge in the agent skills literature)
**Effort:** 4 (requires GRPO training infrastructure similar to verl, grouped task stream construction pipeline, LLM-as-judge for content quality, and 16+ GPU training run)
**Tier:** breakthrough (learned skill curation consistently outperforms frontier model zero-shot curation and generalizes across executors/tasks — a qualitative capability leap over current static skill management)
