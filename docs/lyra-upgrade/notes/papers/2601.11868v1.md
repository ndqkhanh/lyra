## 1. Mechanism (step-by-step)

Terminal-Bench 2.0 is a **hard benchmark for CLI-based AI coding agents**, constructed through a rigorous multi-stage pipeline designed to test realistic engineering tasks in isolated terminal environments. The core mechanisms are:

### A. Task Construction Pipeline (7-stage verification)

Each of the 89 tasks is built as a self-contained unit with four components:

1. **Instruction** — textual description of the task the agent must complete within a time limit inside a Docker container.
2. **Docker image** — containerized environment with all relevant packages, dependencies, and pre-populated files pinned via Dockerfile.
3. **Verification tests** — property-based tests that check the *final container state* (file contents, process outputs, artifact existence), NOT the agent's commands or console output. This outcome-driven approach means agents can solve tasks with any strategy.
4. **Reference solution** — manually written oracle solution that passes all verification tests.

**Seven-stage quality control:**

- **Stage 1**: Automated GitHub workflow runs the oracle solution to confirm solvability.
- **Stage 2**: Contributor self-checklist (10 items): specificity, anti-cheating, pinned dependencies, edge case coverage, etc.
- **Stage 3**: LLM-backed automated check tool scans for typos, hardcoded solutions, missing file references.
- **Stage 4**: Deterministic CI checks: canary string presence, Dockerfile sanity, test file references, privilege checks.
- **Stage 5**: Experienced human reviewers manually inspect each task.
- **Stage 6**: Multiple models run via Terminus 2; contributors analyze failures to distinguish capability gaps from task flaws.
- **Stage 7**: Two additional auditors perform final manual review for dataset inclusion.

Additionally, an **adversarial exploit agent** (Appendix B.4) probes tasks for design flaws that could allow cheating (e.g., reading solution files directly, exploiting environment setup scripts). Tasks flagged are re-designed.

### B. Evaluation Protocol

- **Agents evaluated**: Claude Code, Codex CLI, Gemini CLI, OpenHands, Mini-SWE-Agent, Terminus 2 (6 agents total).
- **Models evaluated**: 16 models spanning GPT-5.2 down to GPT-OSS-20B.
- **Total trials**: 32,155 trials, with >= 5 runs per model-agent-task combination.
- **Execution**: Real terminal shells inside Docker containers, internet access allowed, agent behavior unconstrained.
- **Metric**: Resolution Rate = fraction of tasks where all verification tests pass. Reported with 95% confidence intervals (binomial proportion).

### C. Error Analysis Framework

Two levels of error analysis:

- **Trajectory-level** (Figure 8): Uses an LLM judge (GPT-5 high-reasoning) to classify failures into three high-level classes — **Execution** (commands fail), **Coherence** (agent loses track of goal/context), **Verification** (agent fails to confirm work is complete). Human agreement rate: 90%.
- **Command-level** (Figure 9): Across 3,800 uniformly sampled command failures, categorized by error type. Dominant failure: "executables not installed / not in PATH" (24.1%), followed by "failures when running executables" (9.6%).

### D. Task Difficulty Calibration

- **Expert time estimates**: 48.6% < 1 hour, 47.3% = 1 hour to 1 day, 4.1% = 1 day to 1 week.
- **Junior engineer time estimates**: 8.1% < 1 hour, 71.6% = 1 hour to 1 day, 16.2% = 1 day to 1 week, 4.1% >> 1 week.
- **Human-empirical difficulty correlation**: r = 0.436, p << 0.001. Human "hard" labels are reliable (93.3% are also empirically hard), but "medium" labels are noisy (54.5% are actually hard for models).

### Key Comparative Findings

- **Ceiling**: No model+agent combination exceeds **62.9%**, leaving ~37% of tasks unsolved by frontier systems.
- **Best open-weight model**: Kimi K2 Thinking + Terminus 2 at **35.7% ± 2.8%** (nearly half of closed-source best).
- **Model scaling gap**: Codex CLI resolution rate increases by **52%** when using GPT-5.2 instead of GPT-5-Nano (62.9% vs. 11.5%).
- **Agent scaffolding gap**: Gemini 2.5 Pro sees a **17 percentage point** increase when paired with Terminus 2 (32.6%) instead of OpenHands (15.7%).
- **Historical progress**: "In eight months between the release of Gemini 2.5 Pro and GPT 5.2, state-of-the-art performance nearly doubled."
- **Command error rate**: Ranges from **9.2%** (Grok 4) to **26.7%** (GPT-OSS-120B).
- **Token inefficiency**: Claude Opus 4.5 + Claude Code consumes 256.9M input tokens (highest) for only 52.1% resolution rate, vs. GPT-5.2 + Codex CLI achieving 62.9% with 137.5M input tokens. **"Higher token count does not necessarily correlate with better performance."**
- **Claude Code as agent**: Claude Code + Claude Opus 4.5 achieves 52.1% (using 256.9M input / 0.8M output tokens) — a bizarrely lopsided input/output ratio suggesting the tool-use conversation format inflates context.
- **Claude Haiku 4.5 + OpenHands**: 13.3% resolution rate using **663.1M input tokens** (the highest token count in the entire table), an egregious case of context amplification with weak output.
- **GPT-OSS-20B (smallest open model tested)**: 3.1%–3.4% resolution rate, confirming strong model scale dependency.

## 3. Trade-offs (wins vs. costs)

| Win | Cost |
|-----|------|
| **Extremely rigorous task validation** — 7-stage pipeline with 3 human auditor passes plus adversarial exploit agent. Each task receives ~3 reviewer-hours of scrutiny. | **High construction cost per task** — 229 submissions filtered to 89 tasks, requiring paid crowd-sourcing, expert review, and CI infrastructure. Not easily scalable. |
| **Outcome-driven evaluation** — verification tests check final container state, not agent trajectory, allowing creative solutions and avoiding brittle trajectory-matching. | **Cannot diagnose intermediate failures** — tests only detect final-state correctness; a correct answer reached by lucky probing is indistinguishable from deliberate reasoning. |
| **Realistic Docker environments with internet** — agents face real unix tooling, package managers, and web resources, matching real engineering workflows. | **Non-determinism** — internet access + variable machine resources + container runtime drift mean results are not perfectly reproducible across runs. |
| **Broad model-agent coverage** — 16 models x 6 agents = 32,155 trials provide the most comprehensive CLI agent benchmark to date. | **Excludes non-CLI paradigms** — GUI-based agents, browser-only agents, and IDE-embedded coding assistants are not evaluated. |
| **Public dataset + evaluation harness** — enables community benchmarking and progress tracking. | **Training contamination risk** — despite canary strings, the public nature of the dataset leaves open the possibility of memorization (private test set deferred to future work). |
| **Multi-axis error analysis** — trajectory-level (LLM judge) + command-level (structured parsing) = actionable failure taxonomy. | **LLM judge subjectivity** — despite 90% human agreement, the trajectory-level error classifier (GPT-5) introduces its own biases into failure categorization. |

## 4. Design Rationale (why this approach)

**Why CLI-focused benchmark?** Previous coding benchmarks (HumanEval, SWE-bench, BigCodeBench) focus on generating code snippets or patches. Real engineers spend significant time navigating terminal environments: installing packages, debugging runtime errors, manipulating files, chaining commands. No existing benchmark systemically evaluates this skill set at scale.

**Why outcome-driven rather than trajectory-driven?** By checking only final container state (files, processes, outputs), the benchmark avoids penalizing unorthodox but valid solution paths. This mirrors how real engineering tasks are evaluated: "did it work?" not "did you do it the way I would have?"

**Why Docker containers?** Docker provides reproducible, isolated execution environments that can be destroyed after each trial. This enables safe execution of arbitrary agent commands (including destructive ones) and precise post-hoc state inspection. Pinned package versions via Dockerfiles reduce — though do not eliminate — reproducibility drift.

**Why internet access?** Real engineering work uses Stack Overflow, documentation, and package registries. Disabling internet would make tasks artificially harder and less representative of actual workflows. The risk of agents discovering the benchmark dataset is acknowledged but deemed acceptable given the low base rate observed.

**Why 7-stage validation?** Terminal environments are inherently brittle (a single typo in a path or missing dependency can make a task unsolvable). The multi-stage pipeline — combining automated checks, human review, model probing, and adversarial testing — is designed to eliminate spurious failures and ensure tasks genuinely measure agent capability, not task ambiguity.

## 5. Limitations & Failure Modes

1. **Internet access — adversarial risk**: Agents could theoretically locate the public dataset and read oracle solutions. The authors note this has not been observed in "tens of thousands of agent trajectories" but acknowledge the risk. Mitigations: canary strings in repo files for contamination detection; private test set deferred to future work.

2. **Training data contamination**: Despite BigBench canary strings in all repo files, models trained on GitHub may have memorized reference solutions. No model provider disclosed training data details, so contamination cannot be ruled out. A private test set is identified as necessary future work.

3. **Reproducibility drift**: Pinned Docker packages reduce but do not eliminate drift. Internet-dependent tasks (downloading external resources, querying live APIs) are inherently non-deterministic. "Variability in machine resources and container runtime enforcement can lead to differences."

4. **Residual task flaws**: Despite 3 human auditor passes, "there remains the possibility that some tasks could fall short of our verification criteria." The authors accept this tradeoff for task diversity and realism.

5. **LLM-judge bias in error analysis**: Trajectory-level failure classification uses GPT-5 as a judge. While 90% agreement with human annotators is reported, the judge model's own biases (over-indexing on certain error patterns, under-detecting subtle coherence failures) may distort the error taxonomy.

6. **Narrow task scope**: All 89 tasks are CLI-only, self-contained within single Docker containers. This excludes: multi-machine coordination, long-running services, GUI interactions, collaborative workflows, and security-sensitive operations (privilege escalation, network attacks).

7. **Resolution rate as sole metric**: The benchmark uses a binary pass/fail metric (all verification tests pass = success). This collapses partial progress (solving 80% of sub-goals) into failure, potentially underselling models that make meaningful partial progress.

8. **Task construction cost**: The 7-stage pipeline requires ~3 reviewer-hours per task plus automated CI. Scaling beyond 89 tasks would be expensive, limiting benchmark freshness as models improve.

## 6. Transfer to Lyra

### The One Idea: **Property-Based Outcome Verification for Agent Evaluation**

Terminal-Bench's core architectural insight — **verify the final state, not the trajectory** — is directly transferable to Lyra's evaluation infrastructure. Instead of checking whether a Lyra agent used the "correct" sequence of tool calls, Lyra should define verification predicates that check properties of the final output state (file correctness, data integrity, task completion markers). This enables:

- **Creative solution paths**: Lyra agents can develop novel strategies without being penalized for non-canonical approaches.
- **Automatic evaluation at scale**: Property-based tests are deterministic and fast, enabling regression testing across model upgrades.
- **Adversarial robustness testing**: Like Terminal-Bench's exploit agent, Lyra can run adversarial probes to verify that verification predicates cannot be gamed.

### §4 Workstream Route: §4.5 — Evaluation Framework & Reliability

Terminal-Bench's methodology directly informs the evaluation architecture described in §4.5 (reliability testing, regression benchmarking, and performance measurement). The outcome-driven verification pattern should be incorporated into Lyra's eval harness design, specifically:

- Define task-specific `verify(state: ContainerState) -> bool` predicates
- Run across model upgrades as regression tests
- Include adversarial probes to validate predicate robustness
- Use confidence intervals (binomial proportion) for result reporting

### Impact/Effort/Tier

| Dimension | Rating | Rationale |
|-----------|--------|-----------|
| **Impact** | 4/5 | Restructures evaluation from heuristic to rigorous; enables continuous benchmarking as Lyra evolves |
| **Effort** | 3/5 | Requires designing verification predicates per task type + Docker containerization + CI integration; non-trivial but bounded |
| **Tier** | **breakthrough** | Changes the evaluation paradigm from trajectory-matching to outcome-verification, which is a fundamental upgrade over current LLM-as-judge approaches |

### Additional Transferable Patterns

1. **Command-level error taxonomy**: Classify agent failures as Execution/Coherence/Verification failures — Lyra can log these categories for debugging.
2. **Multi-agent scaffold comparison**: The 6-agent comparison shows scaffolding matters as much as the model; Lyra should benchmark with multiple agent harness architectures.
3. **Task difficulty calibration**: Correlate human difficulty estimates with empirical agent performance (r = 0.436 methodology) to prioritize which Lyra capabilities to improve.
