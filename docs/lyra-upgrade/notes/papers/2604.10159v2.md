# ODUTQA-MDC: A Task for Open-Domain Underspecified Tabular QA with Multi-turn Dialogue-based Clarification

**Authors:** Zhensheng Wang, Zhanteng Lin, Wenmian Yang (corresponding), Kun Zhou, Yiquan Zhang, Weijia Jia — Beijing Normal University

**Venue:** arXiv:2604.10159v2 [cs.CL], 18 Apr 2026

---

## 1. Mechanism (Step-by-Step)

ODUTQA-MDC defines a two-stage task and provides the **MAIC-TQA** multi-agent framework to solve it.

### Task Definition
Given a user query against a multi-table PostgreSQL database:
1. **Underspecification Detection:** Identify which SQL clause is affected: SELECT (intent unclear), FROM (missing/erroneous scope), WHERE (missing/erroneous condition), or Mixed.
2. **Clarification-based Dynamic QA:** Interact with a user simulator to resolve ambiguities, then perform Table Retrieval and SQL Generation to produce the final answer.

### Dataset Construction Pipeline
1. Start with 90 seed templates from RETQA (real estate domain: Property, Land Auction, Enterprise Finance).
2. Normalize tables into 209 tables (102 Property + 103 Land Auction + 4 Finance by-year).
3. Map each template variable to its SQL clause counterpart: FROM (table captions), SELECT (column headers/intent), WHERE (conditions).
4. Inject underspecification via two strategies:
   - **Template Restructuring:** Replace explicit column references with vague expressions (e.g., "green coverage ratio" → "how is the environment?") — produces SELECT underspecification; omit variables to create Missing-type FROM underspecification.
   - **Value Modification:** Alter entity values post-generation — produces WHERE underspecification (abbreviations for full names), Error-type FROM (typos), Unmatch-type FROM (logical conflicts, e.g., nonexistent city-district pair).
5. Three clarification dictionaries store ground-truth values: SELECT-Clarification (column name), FROM-Clarification (correct scope values), WHERE-Clarification (full entity names).
6. Stratified sampling across 76 template groups yields 25,105 QA pairs (5,095 well-specified + 7,892 single-underspecified + 12,118 mixed-underspecified), split 6:2:2 train/val/test.
7. LLM-based paraphrasing (Qwen2.5-72B) with forbidden-keyword constraints to ensure natural language without accidentally resolving ambiguities.

### Label Annotation Scheme
- **Intent Underspecification:** Binary label (True/False) from SLU classifier output.
- **Scope Underspecification:** Triple `[slot_content, slot_type, error_type]` where error_type ∈ {Missing, Error, Unmatch}.
- **Condition Underspecification:** Triple `[slot_content, slot_type, "not exist"]`.

### Conversational Clarification Interface
- Python-callable simulator gating clarification on detection accuracy: corrective information is provided **only** when the predicted label matches ground truth.
- Two modes: **Fixed** (standardized templates for reproducibility) and **Dynamic** (LLM-paraphrased with keyword enforcement — Qwen2.5-72B rewrites while mandating inclusion of ground-truth keywords).
- Post-generation verification: validates keyword presence in paraphrased output, falls back to template on failure (max 5 retries).
- Design: **Deterministic Decision Layer** (what to clarify from gold labels) + **Probabilistic Generation Layer** (how to phrase it via LLM).

### MAIC-TQA Multi-Agent Framework (4 agents)

**Agent 1 — SLU Module (Section 4.2):**
- BERT-based classifier for intent detection + BIO slot filling.
- If intent underspecification detected → template-based follow-up ("Please clarify your request") → user response concatenated → BERT reprocessed (single iteration).
- Clarified intent mapped to one of 3 domains: Property Sales, Land Auctions, Enterprise Finance.

**Agent 2 — Scope Validator Agent (Section 4.3):**
- Input: original query, domain label, extracted slots, required slot types.
- **Step 1:** Check for missing slots → classify as `[_, slot_type, "Missing"]`.
- **Step 2:** If all required slots present, call `slotSearchTool` (Algorithm 1) which substring-matches each slot against table captions in the domain database.
- Classification priority: Missing > Unmatch (individual slots exist but combination does not) > Error (slot content not found in any table) > Correct (all individual + combined queries return >0).

**Agent 3 — Table Retrieval Agent (Section 4.4):**
- Generates a table caption summary from full dialogue history (original query + clarifications).
- Two-stage retrieval: (1) exact match of summary against database table captions; (2) fallback to BM25 similarity search. If agent cannot produce a summary, full dialogue history is used directly for BM25.

**Agent 4 — SQL Generation and Validation Agent (Section 4.5):**
- Input: complete dialogue history, predicted domain, extracted slots, table captions.
- Selects prompt template with 5 gold SQL examples for in-context learning.
- Generates SQL, executes via `sqlQueryTool` (Algorithm 2 — PostgreSQL executor with cross-database fallback).
- If result empty/incomplete: calls SQL validation function, generates condition underspecification label `[slot_content, slot_type, "not exist"]`, requests user clarification, single round of SQL regeneration.
- If regeneration fails → empty output recorded.

### Key Algorithms

**Algorithm 1 — slotSearchTool:** For each slot in input list, counts how many table captions in the domain contain that slot as a substring. Returns `Dict[str, int]`.

**Algorithm 2 — sqlQueryTool:** Executes SQL on named database via PostgresQueryExecutor. If domain unknown, iterates all databases. Returns list result, error message, or "Failed to execute" string.

- **EA improvement over clarification-free baseline: +17.82 to +33.69 percentage points** across all models and modes (best: Qwen3 32B, Fix mode).

- Mixed underspecification detection remains extremely challenging (max 68.50% Acc) due to error accumulation.
- Dynamic mode generally comparable to or slightly better than Fixed mode, confirming robustness of the clarification interface design.

## 3. Trade-offs

| Dimension | Win | Cost |
|-----------|-----|------|
| **EA (execution accuracy)** | +17.82 to +33.69pp over clarification-free baseline across all models | Requires 4-agent pipeline + dialogue state management |
| **Table Retrieval** | +17.45 to +36.32pp F1 over SLUTQA | Additional inference calls for BM25 fallback and summary generation |
| **Scalability of evaluation** | Automated user simulator enables evaluation of 25K QA pairs without human interaction | Simulator trades behavioral realism for reproducibility — no chitchat, goal deviation, or linguistic noise |
| **Modular architecture** | Ablation studies isolate contribution of each clarification type; agents independently improvable | 4-agent coordination adds latency; error propagation across agents (failed detection → no clarification → cascading failure) |
| **Dynamic clarification** | Linguistic diversity from LLM paraphrasing without factual degradation (keyword enforcement) | Additional LLM call per clarification turn; variance in LLM robustness to diverse phrasing |
| **Single-domain construction** | Controlled, systematic underspecification injection with ground-truth verification | Generalizability to healthcare, e-commerce, etc. unvalidated; real estate-specific entity types and query patterns |
| **Template-based generation** | 25K high-quality QA pairs with verified ground truth, bypassing expensive human annotation | Formal template structure may differ from authentic user query patterns despite LLM paraphrasing |
| **SQL clause alignment** | Fine-grained, interpretable underspecification types enable targeted system interventions | Excludes GROUP BY, HAVING, ORDER BY, nested queries — limits compositional reasoning stress |
| **Fine-tuned BERT for SLU** | 99.78% intent accuracy, anchors the pipeline reliably | Requires training data with manual annotations; ICL alternatives achieve ~90% F1 without fine-tuning |

## 4. Design Rationale

**Why template-based construction with controlled perturbation?** The authors argue that manual annotation or crowdsourcing is "prohibitively expensive" and suffers from inconsistent quality. Template filling with controlled underspecification injection ensures every generated QA pair has verified ground truth for both the target SQL and the underspecification labels. This is standard practice in the field (cf. MULTITQ, RETQA, SpatialRGPT-Bench). The deliberate decoupling of semantic patterns (templates encode SQL intent and underspecification type) from surface forms (LLM paraphrases with forbidden-keyword constraints) addresses the criticism that template-generated data lacks linguistic diversity.

**Why a simulated rather than human-in-the-loop clarification interface?** Three reasons: (1) **Reproducibility** — human responses would make the "test set" non-stationary, preventing fair model comparison; (2) **Scalability** — evaluating 25K QA pairs across 5 models with human interaction would be infeasible; (3) **Scientific control** — isolating model capability in resolving logical ambiguities from robustness to open-domain distractions. The hybrid deterministic-probabilistic design (logic-gated content, LLM-phrased form) is the key architectural compromise.

**Why align underspecification to SQL clauses?** Mapping ambiguity types to SELECT (intent), FROM (scope), and WHERE (condition) clauses creates an interpretable taxonomy that enables: (a) targeted agent specialization, (b) fine-grained evaluation of which ambiguity type each model struggles with, and (c) direct integration with text-to-SQL pipelines. This is a deliberate scoping choice — they explicitly exclude open-ended linguistic ambiguity to isolate the "logical clarification mapping" capability.

## 5. Limitations and Failure Modes

1. **Single-domain construction:** The entire dataset is from real estate (property sales, land auctions, enterprise finance). The authors acknowledge this and claim schema-agnostic design, but no cross-domain validation is performed. Entity types, query patterns, and underspecification distributions may not transfer.

2. **Simulated user lacks human stochasticity:** No chitchat, topic drift, goal deviation, or emotional nuance. The authors frame this as a deliberate benchmark design choice, but it means strong performance on ODUTQA-MDC does not guarantee robustness in production human-in-the-loop settings.

3. **Simplified SQL scope:** Intentionally excludes GROUP BY, HAVING, ORDER BY, nested subqueries, and complex aggregations. The authors state this is "a deliberate design choice to isolate... logical clarification mapping," but it means the benchmark does not stress compositional reasoning or advanced SQL operations.

4. **Single clarification iteration:** Intent clarification is limited to one round; SQL regeneration after WHERE clarification is limited to one attempt. Real interactions often require multiple back-and-forth rounds.

5. **Error accumulation in Mixed underspecification:** Detection accuracy drops to 68.50% (best) because failing to detect any one type causes overall failure. The current framework has no partial-credit or progressive-resolution mechanism for mixed cases.

6. **BM25 retrieval dependency:** Table retrieval fallback relies on BM25 lexical matching, which may struggle with semantic mismatches between dialogue summaries and formal table captions.

7. **GPT/Claude API models not evaluated:** All experiments use Chinese LLMs (Qwen3, Kimi-K2, GLM-4, Doubao). Performance on Western API models (GPT-4, Claude, Gemini) is unknown.

8. **BERT fine-tuning requirement:** The SLU Module's strong performance depends on fine-tuning with manual annotations, reducing plug-and-play usability.

## 6. Transfer to Lyra

### The One Idea
**SQL-clause-aligned ambiguity taxonomy with gated, accuracy-conditional clarification delivery.** The paper demonstrates that classifying user query ambiguities by which part of a structured query they affect (SELECT=intent, FROM=scope, WHERE=condition) and withholding corrective information until the system correctly identifies the ambiguity type creates a safe, measurable clarification loop that prevents hallucinated corrections and enables targeted agent specialization.

### Workstream Route
**§4.5 — Agentic Engineering / Action Space Design.** This pattern directly applies to Lyra's tool-calling and structured data interaction agents: when an agent interacts with databases, APIs, or structured knowledge stores, ambiguous user inputs can be classified by which part of the structured query they break, and clarification can be gated on detection confidence to prevent cascading errors.

### Impact / Effort / Tier
- **Impact:** 3 (valuable for agent-structured-data interaction quality, but not a core LLM capability improvement)
- **Effort:** 3 (requires building a clarification taxonomy, a detection classifier/agent, and a gated clarification interface — moderate multi-agent engineering)
- **Tier:** **investigate** — the core pattern is compelling and transferable, but the paper is single-domain (real estate), uses only Chinese LLMs, and its simulated-clarification evaluation paradigm needs validation against real human interactions before Lyra adopts it as a standard pattern.
