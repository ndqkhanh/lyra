## 1. Mechanism (step-by-step)

### Problem Formulation
Given a task query `q`, the system learns a **Designer policy** `π_D` that generates a task-specific multi-agent system `d`, and an **Executor policy** `π_E` that runs the instantiated system to produce execution trajectory `e`. The coupled RL objective is:

```
d ~ π_D(·|q),   e ~ π_E(·|q, d),   R = R(q, d, e)
```

where `R` is a binary outcome reward (correctness + format bonus with λ=0.4).

### Step 1: SFT Cold Start
- Distill from DeepSeek-V3.2 prompted with diverse workflow templates (single-agent, ensemble-voting, solver-critic reflection, solver-tester, etc.)
- Retain trajectories where final answer is correct → 3K Designer examples + 8K Executor examples
- Motivates: even DeepSeek benefits from MAS workflow prompting (AIME 2024: 63.3% direct → 66.7% with MAS workflow)

### Step 2: Online MAS Construction
- Designer generates **lightweight Python scripts** specifying:
  - Agent roles (e.g., AlgebraicSolver, GeometricSolver, MathJudge)
  - Interaction protocols (e.g., ensemble+judge, reflection, single-agent)
  - Tool interfaces and execution control flow
  - Role-specific system prompts (77.5% byte-unique per query after RL)
- Uses predefined coordination structures, agent templates, and tool interfaces as building blocks
- Vocabulary of 54 distinct role names across all workflows

### Step 3: Executor-Designer Hierarchical Rollout (Credit Assignment)
**Bi-level Tree Structure** — for each query `q`:
- **Level 1 (Designer):** Generate M=4 independent MAS designs `{d_1, ..., d_M}`
- **Level 2 (Executor):** For each design `d_i`, run N=4 independent executions `{e_{i,1}, ..., e_{i,N}}`
- Produces an M×N evaluation matrix per query

**Decomposed Advantage Estimation:**
- **Designer advantage:** Average over N executions to smooth execution stochasticity, then normalize across M designs:
  ```
  R̄_i^D = (1/N) Σ_j R(e_{i,j}, d_i)
  Â_i^D = (R̄_i^D - μ_q^D) / (σ_q^D + ε)
  ```
- **Executor advantage:** All executor trajectories across all designs for the same question form one GRPO group, normalized at question level:
  ```
  G_q^E = {τ | τ ∈ T_{i,j}, i∈[M], j∈[N]}
  Â^E(τ) = (R(e_{i,j}, d_i) - μ_q^E) / (σ_q^E + ε)
  ```

### Step 4: Stagewise Co-evolution (Training Schedule)
Addresses the non-stationarity problem where each role is the other's environment. Alternates active role every K=30 steps:

```
(α_D^(t), α_E^(t)) = (0,1) for Executor stages, (1,0) for Designer stages
⌊t/K⌋ mod 2 determines which role is active
```

Only trajectories from the active role contribute to the gradient. Shared parameters are updated continuously. This isolates each phase to one reward distribution, reducing gradient interference.

### Step 5: GRPO Policy Optimization
Both roles optimized with Group Relative Policy Optimization:
```
L_r(ϑ_r) = -(1/|G^r|) Σ_i min(ρ_i^r · Â_i^r, clip(ρ_i^r, 1-ε, 1+ε) · Â_i^r)
```
where `ρ_i^r = π_{ϑ_r}(o_i|c_i) / π_{ϑ_r,old}(o_i|c_i)` and `r ∈ {D, E}`.

### Training Configuration
- Shared-policy setting: same LLM backbone for both Designer and Executor
- Training data: mixture of Polaris-Dataset-53K (math) + APPS/CodeContests (code), RL batch size 8
- Learning rate: 5×10⁻⁶
- Max prompt/response length: 8192 tokens (no-thinking mode)

## 3. Trade-offs

| Win | Lose |
|-----|------|
| +11.2-12.8% avg over single-agent baseline across 6 benchmarks | Requires SFT cold start from a strong proprietary teacher (DeepSeek-V3.2) |
| Breaks frozen-executor ceiling that limits prior Auto-MAS approaches | M×N=16 rollouts per query (4 designs × 4 executions) — compute-intensive |
| Stagewise training prevents collapse seen in coupled training (coupled variant degrades to token repetition) | Stagewise doubles training wall-clock (alternating phases, only one role updated at a time) |
| Shared policy outperforms separate policies (40.0% vs 33.3% on AIME24) | Only validated at 4B/8B scale; may not transfer to larger models |
| Structural adaptation: designer learns task-dependent routing (reflection for hard math, single for easier tasks) | Binary outcome rewards only — no fine-grained learning signal for intermediate steps |
| Cross-task generalization: math+code mixture training helps both domains | CodeContests remains stubbornly low (14-17%) — minimal improvement over SA |
| Hierarchical rollout gives cleaner credit assignment than flat rollout | Empirically tuned stage length K=30; 1-step alternation causes training collapse at step ~150 |

## 4. Design Rationale

**Why end-to-end RL?** Prior automatic MAS approaches either do training-free search (AFlow, ADAS) or optimize only the meta-designer while freezing executor agents (MAS-GPT, FlowReasoner, MaAS). The frozen executor imposes a hard performance ceiling — no matter how good the designer gets, it cannot induce specialized execution behaviors. End-to-end co-training allows both sides to mutually improve.

**Why hierarchical rollout?** Standard single-level rollout conflates designer quality and executor stochasticity into one entangled reward signal. The bi-level tree (M×N matrix) decomposes credit: averaging over N executions isolates design quality; question-level normalization across all trajectories gives stable executor signals.

**Why stagewise co-evolution?** The designer and executor form a coupled system where each is the other's environment — a classic MARL non-stationarity problem. Simultaneous updates produce noisy/conflicting gradients that cause training collapse (observed: token repetition). Alternating phases with K>1 steps allows each role to accumulate consistent gradient signal before switching context. K=1 collapses; K=10-30 is stable; K=30 gives best final reward.

**Why shared policy?** Designer and Executor learning are not independent subtasks — sharing representations allows training signal from one role to serve as inductive bias for the other, improving generalization and reducing overfitting to role-specific trajectories.

**Why script-based MAS generation?** Python scripts (rather than JSON configs or natural language) give the designer precise control over agent topology, tool interfaces, and control flow — enabling rich, executable MAS designs.

## 5. Limitations & Failure Modes

1. **Scale ceiling:** Only validated on Qwen3 4B and 8B. No experiments on 32B, 70B, or 405B models due to compute constraints. Scaling behavior unknown.
2. **Domain narrowness:** Only math and code benchmarks. No testing on general agent tasks (web navigation, tool use, multi-step planning, embodied agents).
3. **SFT dependency:** Requires cold-start distillation from a strong teacher (DeepSeek-V3.2). Performance without cold start is not reported — reinforcement learning from scratch may be infeasible.
4. **Binary rewards only:** Outcome-based rewards (0/1) provide no signal for intermediate reasoning quality, partial progress, or near-misses. May limit sample efficiency.
5. **Training instability with wrong K:** 1-step alternation causes training collapse at ~150 steps with token repetition. The optimal K=30 is empirically found, not theoretically grounded.
6. **CodeContests weak performance:** 14.2-17.0% across all variants — minimal improvement over single-agent baseline on this benchmark. Suggests the framework struggles with algorithmic competition problems requiring deep problem-specific insight.
7. **No multi-turn interaction:** Execution agents run within the generated workflow but the designer does not adapt mid-execution based on executor observations.
8. **Compute requirements:** 8×H200 GPUs, M×N=16 rollouts per query, SFT cold start phase — not accessible to resource-constrained researchers.
9. **Workflow template dependency:** Designer constrained to pre-defined coordination structures (single, ensemble, reflection, solver-tester). Cannot invent entirely novel interaction patterns.

## 6. Transfer to Lyra

### The One Transferable Idea

**Stagewise Designer-Executor Co-evolution with Hierarchical Credit Assignment.** Lyra's meta-router (the "Designer" that selects agent topologies and routes tasks) and its execution agents (the "Executors" that carry out tool-augmented work) should be co-trained using alternating optimization phases. Without this, Lyra faces the same "frozen-executor ceiling" that plagues all current automatic MAS approaches — the router gets better at designing workflows, but execution agents never learn specialized behaviors for those workflows, and vice versa.

The hierarchical rollout structure (M candidate designs × N executions each) provides clean credit assignment: design quality is isolated by averaging over execution variance, while executor quality is measured at the question level across all designs. The stagewise alternation (K-step phases) prevents the gradient interference that causes coupled training to collapse.

### Workstream Route

**§4.2 — Router/Orchestrator.** This directly feeds the workstream on Lyra's workflow compiler and task router. The key architectural insight is that Lyra's routing decisions and execution capabilities must co-evolve; optimizing either in isolation hits a ceiling.

### Impact / Effort / Tier

| Dimension | Rating | Justification |
|-----------|--------|---------------|
| **Impact** | 4/5 | Directly addresses Lyra's core architectural challenge; the frozen-executor ceiling is a first-order limitation in current multi-agent systems |
| **Effort** | 5/5 | Requires (a) SFT cold-start pipeline for Lyra's router + executors, (b) hierarchical rollout infrastructure (M×N tree), (c) GRPO training loop with stagewise scheduling, (d) 8+ GPU training setup, (e) reward design for Lyra's task domains |
| **Tier** | **breakthrough** | This is a novel paradigm-level contribution (first end-to-end trainable Auto-MAS). Adapting it for Lyra would produce publishable research while solving a fundamental architectural bottleneck. High-effort but high-reward. |

**Key implementation considerations for Lyra:**
- Lyra's "workflows" are more constrained than the paper's Python scripts (Lyra has fixed orchestration primitives) — the designer action space would be smaller but cleaner
- Lyra's execution agents already have tool-use capabilities, which the paper's executors lack — this is an advantage
- The hierarchical rollout (M×N) maps naturally to Lyra's multi-turn interaction model
- The stagewise alternation period K would need tuning for Lyra's specific task distribution
- Cold-start distillation could use Lyra's existing agent traces as seed data
