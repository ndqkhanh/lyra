## 1. Mechanism

### Memory Architecture (4 stores, following MemGPT taxonomy)

| Store | Content | Example Query |
|-------|---------|---------------|
| STM (Short-Term Memory) | Current conversation, last N turns | "What did I just mention?" |
| Summary | Compressed user facts, preferences, biographical details | "What is my phone number?" |
| LTM (Long-Term Memory) | Summaries of past conversations | "What did we talk about last week?" |
| Episodic | Raw transcripts | Exact wording, precise timestamps |

### Routing Problem Formalization

Let S = {STM, Sum, LTM, Epi}. Given query q, routing policy π selects stores Ĝ = π(q) ⊆ S. Ground-truth stores G are the stores containing information needed to answer q.

**Three evaluation metrics:**

- **Coverage:** `(1/N) Σ 1[G_i ⊆ Ĝ_i]` — did we include all needed stores? Coverage failure = answer not retrievable from context.
- **Exact Match (EM):** `(1/N) Σ 1[G_i = Ĝ_i]` — did we select precisely the needed stores, no more?
- **Waste:** `(1/N) Σ |Ĝ_i \ G_i|` — count of unnecessary stores retrieved. Proxy for token cost and contextual noise.

### Cost-Sensitive Decision Framework (Equation 4)

```
π*(q) = argmax_{G⊆S} E[Acc(q, G) - λ Σ_{s∈G} c_s]
```

Where Acc(q, G) is expected probability of correct answer when stores G are retrieved, c_s is retrieval cost of store s, and λ controls the accuracy–cost tradeoff. Uniform retrieval = special case λ=0 (all stores regardless of cost).

### Algorithm 1: Hybrid Store Routing

```
1: Input: Query q
2: Extract semantic signals from q
3: if quantity signal ("list all", "every")        → {LTM, Epi}
4: else if temporal signal ("before", "changed")   → {LTM, Epi}
5: else if multi-hop signal ("compare", "relate")  → {Sum, LTM}
6: else if current session ("just said", "today")  → {STM}
7: else if fact lookup ("what is my", "who is my") → {Sum}
8: else                                            → {Sum, LTM}  // safe fallback
```

When no rule fires, embedding similarity (query-store) is used as tiebreaker. Fallback Sum+LTM yields highest coverage (89%) among all 2-store combinations.

### Routing Policies Compared

1. **Uniform Baseline:** Retrieve from all 4 stores (guaranteed coverage, highest cost)
2. **Rule-based (linguistic only):** Pronouns, tense patterns only
3. **Hybrid (linguistic + semantic + embedding similarity):** Algorithm 1 + embedding tiebreaker
4. **Oracle Upper Bound:** Uses ground-truth store labels (not deployable, quantifies headroom)
5. **Fixed Subset Policies:** e.g., STM+Sum+LTM (deployable, strong baseline)

### Ground-Truth Store Labels by Query Type

| Query Type | Required Stores |
|------------|----------------|
| single_hop | Sum |
| single_session | STM |
| recent_session | LTM |
| multi_hop | Sum + LTM |
| memory_capacity | LTM + Epi |
| temporal | LTM + Epi |
| knowledge_update | Sum + LTM |

## 2. Results

### Synthetic Routing Evaluation (1,000 queries, 7 types, 70/30 train/test split)

| Policy | Coverage | Exact Match | Waste |
|--------|----------|-------------|-------|
| Uniform | 100% | 8% | 2.9 |
| Rule-based (linguistic only) | 57% | 35% | 0.5 |
| **Hybrid (ours)** | **94%** | **58%** | **1.2** |
| Oracle | 100% | 100% | 0.0 |

### LLM Evaluation (150 questions, GPT-3.5-turbo and GPT-4o-mini, temperature=0)

**GPT-4o-mini:**
| Policy | Overall Acc | Short (200t/store) | Long (1000t/store) | Context Tokens |
|--------|-------------|---------------------|---------------------|----------------|
| Oracle | **86.7%** | 94% | 72% | **299** |
| STM+Sum+LTM | 84.7% | 92% | 70% | 591 |
| Uniform | 81.3% | 92% | 60% | 787 |
| Hybrid | 70.7% | 80% | 52% | 379 |

**GPT-3.5-turbo:**
| Policy | Overall Acc | Short | Long | Tokens |
|--------|-------------|-------|------|--------|
| Oracle | 85.3% | 93% | 70% | 299 |
| STM+Sum+LTM | 85.3% | 92% | 72% | 591 |
| Uniform | 83.3% | 91% | 68% | 787 |
| Hybrid | 69.3% | 79% | 50% | 379 |

**Key numbers:**
- Oracle achieves **62% token reduction** (299 vs 787) while improving accuracy **+5.4pp** (86.7% vs 81.3%) over uniform
- Long-context gap: oracle **72%** vs uniform **60%** — a **+12pp** advantage when noise is amplified
- Strong fixed policy (STM+Sum+LTM) is within **2pp** of oracle accuracy (**84.7%** vs 86.7%)
- Hybrid heuristic gap to oracle: **16pp** (70.7% vs 86.7%)
- Coverage-accuracy gap explained: **12% routing errors** + **18% extraction errors**
- Accuracy differences >4% are statistically significant at p < 0.05 (bootstrap, 1,000 iterations)

| Features | Coverage | Δ |
|----------|----------|---|
| Linguistic only (pronouns, tense) | 57% | baseline |
| + Semantic (quantity, temporal, multi-hop) | 90% | **+33pp** |

## 3. Trade-offs

| Win | Lose |
|-----|------|
| **+5.4pp accuracy** over uniform retrieval (86.7% vs 81.3%) | Heuristic router leaves **16pp gap** to oracle — rule-based patterns insufficient |
| **62% fewer context tokens** (299 vs 787) — direct API cost savings | Synthetic labels from query taxonomies, not human annotation — may miss edge cases |
| **Long-context penalty amplified:** +12pp oracle advantage when stores contribute 1,000 tokens each | Only tested on 2 model families (GPT-3.5-turbo, GPT-4o-mini); generalization to other architectures unknown |
| **Fixed subset (STM+Sum+LTM) is deployable immediately** at 84.7% accuracy with moderate cost (591 tokens) | No within-store top-k retrieval tested — full-store concatenation used, not realistic for production |
| **Semantic signals dominate:** +33pp coverage gain over linguistic-only routing | Episodic retrieval needed in only a small subset of cases; can be actively harmful when over-retrieved |
| **<6ms routing overhead** (negligible vs 500-2000ms LLM inference) | 58% exact match for hybrid = 42% of queries retrieve unnecessary stores, adding noise |
| Store-access cost reduced **29%** with hybrid routing | Coverage (94%) ≠ QA accuracy (70%) — correct store selection does not guarantee correct answer extraction |

## 4. Design Rationale

**Why route before retrieval?** Most memory-augmented agents retrieve from all stores uniformly, relying on the LLM to filter noise during generation. This is wasteful (unnecessary token cost) and harmful (irrelevant context degrades accuracy, especially in long-context settings). The paper posits store selection as a **decoupled first-class design decision** — choose which stores to query before touching any retrieval pipeline.

**Why two-stage evaluation?** Synthetic routing labels validate store-selection behavior in isolation. LLM QA evaluation measures downstream accuracy effects. Together they separate "does the router pick the right stores?" from "does picking the right stores actually improve answers?"

**Why coverage-first?** Missing a required store makes a question unanswerable under the full-store-concatenation protocol. The hybrid heuristic optimizes for coverage first (conservative fallback when signals are ambiguous), then precision when signals are clear.

**Why Sum+LTM as fallback?** Tested all six 2-store combinations; Sum+LTM yields highest coverage (89%), making it the safest default when routing signals are ambiguous.

**Why cost-sensitive formulation?** The decision-theoretic framework (Eq. 4) provides a principled interpretation: routing is not just about accuracy but about the accuracy-per-token frontier. This explains why selective retrieval often beats uniform retrieval even though uniform provides strictly more information.

## 5. Limitations & Failure Modes

1. **Synthetic labels, not human-annotated:** Ground-truth store labels derived from query taxonomies (LoCoMo, LongMemEval) rather than human judgment. Real-world store necessity depends on how information is written, summarized, and updated — not captured by taxonomy-derived labels.
2. **Only 2 model families tested (GPT-3.5-turbo, GPT-4o-mini):** Models with different context-handling strategies (e.g., Claude with longer context windows, Gemini with different attention patterns) may respond differently to routing policies.
3. **No within-store top-k retrieval:** Full store concatenation isolates store-selection effects but is unrealistic for production. The interaction between routing decisions and within-store ranking/filtering remains unexplored.
4. **16pp heuristic-to-oracle gap:** Rule-based heuristics leave substantial headroom. Learned end-to-end routing policies that jointly optimize store selection and evidence retrieval are needed.
5. **Coverage-accuracy gap (24pp):** Even when the hybrid selects correct stores (94% coverage), QA accuracy is only 70%. Two distinct failure modes: routing errors (12% of QA errors) and extraction errors (18% of QA errors where model fails despite correct store selection, often due to over-retrieval noise).
6. **Conflicting information across stores:** When LTM contains outdated facts that conflict with Summary store, uniform retrieval forces the model to arbitrate — and it sometimes picks the wrong source. Example: "Who is my current manager?" where LTM mentions a previous manager in a detailed passage.
7. **Small evaluation scale:** 150 QA questions, 4 stores, 7 query types. Scaling to more stores, more query types, and larger datasets is needed.

## 6. Transfer to Lyra

### The One Idea

**Store routing as a first-class memory access primitive.** Instead of Lyra's current implicit/uniform memory retrieval pattern, implement a lightweight query-to-store classifier that maps each incoming user query to a subset of relevant memory stores before retrieval. This decouples *where* to look from *what* to find, reducing token waste and improving signal-to-noise ratio in the context window.

### Concrete Implementation Path

1. **Phase 1 (immediate):** Adopt the fixed STM+CurrentSession+Summary+LTM-Lite subset as Lyra's default retrieval policy — this alone captures 84.7% of oracle performance at moderate token cost without requiring any ML pipeline.
2. **Phase 2 (short-term):** Implement the hybrid rule-based router (Algorithm 1) adapted to Lyra's specific store taxonomy (working memory, session memory, project memory, episodic log). Use embedding similarity as tiebreaker.
3. **Phase 3 (long-term):** Train a learned router (small classifier or fine-tuned lightweight model) that optimizes directly for downstream task completion accuracy rather than proxy metrics like coverage.

### Workstream Route

**§4.2 — Memory & Context Architecture.** This paper directly validates a core design hypothesis for Lyra's memory subsystem: that partitioning memory into semantically distinct stores and routing queries selectively is architecturally superior to uniform retrieval. It provides both the formal framework (cost-sensitive subset selection) and the empirical evidence (62% token reduction, +5.4pp accuracy) to justify this design investment.
