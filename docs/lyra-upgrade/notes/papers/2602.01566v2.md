## 1. Mechanism (step-by-step, with equations/algorithms)

FS-Researcher is a **dual-agent, file-system-based framework** that decouples deep research into two sequential stages, each executed by a separate agent that operates on a shared persistent file-system workspace.

### 1.1 Architecture: ReAct loop

Each agent executes a standard ReAct loop:

```
T_i, A_i = M_θ(T_{j<i}, A_{j<i}, O_{j<i}, P)    (Equation 1 — model generates thought + action)
O_i = Execute(A_i)                                 (Equation 2 — environment executes action)
```

Where M_θ is the backbone LLM, P is the prompt (system + user query), and T_i/A_i/O_i are thought, action, observation at step i.

### 1.2 Tools (2 categories)

**File System Tools**: `ls` (list directory), `grep` (regex search), `read_file` (paginated), `insert`/`delete`/`replace` (line-level edits).
**Web Browsing Tools**: `search_web` (Google SERP API), `read_webpage` (Jina AI API, paginated).

### 1.3 Workspace design (persistent across sessions)

The workspace contains two file types:
- **Deliverables**: Index file (`index.md`), knowledge base directory (`knowledge_base/`), raw sources directory (`sources/`), and final report (`report.md`).
- **Control Files**: `Todos` (tasks with [PENDING]/[IN-PROGRESS]/[COMPLETE] states), `Checklist` (static acceptance criteria), `Logs` (execution trajectory records).

A **session** is defined as a complete agent run from input prompt to final response. The workspace persists across sessions, enabling multi-session iterative refinement.

### 1.4 Stage 1: Context Builder (Librarian Agent)

Given a research topic, the Context Builder:
1. **Inspects workspace** at session start, formulates a plan, and creates/updates `index.md` with a "Table of Contents" that deconstructs the research topic hierarchically.
2. **Browses the internet**: Uses `search_web` → `read_webpage` in a "search-then-read" pattern (empirically confirmed via heatmap analysis).
3. **Distills notes** into `knowledge_base/` with tree-like directory structure, where folder/file names reflect semantic relationships between deconstructed topics.
4. **Archives raw webpages** into `sources/` with citation pointers (every statement in notes has a relative-path citation to a source file).
5. **Self-checks** at session end against the checklist, marking incomplete items as [IN-PROGRESS] and recording findings in the log file.
6. **Iterates** through multiple sessions (3/5/10 rounds) until budget limit or all checklist items pass. The `index.md` and `knowledge_base/` are dynamically updated — this is NOT a linear fill-in-blanks workflow.

### 1.5 Stage 2: Report Writer (Author Agent)

Once Context Builder marks the KB as complete:
1. **Web tools are removed** — Report Writer treats the KB as sole fact source.
2. **Creates outline** (`report_outline.md`) in first session, with each section carrying [PENDING]/[IN-PROGRESS]/[COMPLETE] status.
3. **Writes section-by-section** — exactly one section per session, followed by section-level self-check against section checklist.
4. **Overall review** after all sections complete, using a report-level checklist. Failed sections are re-marked [IN-PROGRESS].
5. **No budget limit** in this stage — runs until all checks pass.

### 1.6 Multi-session workflow loop

```
Session N start:
  1. ls workspace → inspect current state
  2. Read log file → understand prior decisions
  3. Formulate plan based on current todos
  4. Execute: search → read → write notes/files → update todos
  5. Self-check vs checklist → mark issues
  6. Write log entry → session ends
Session N+1 picks up from saved state.
```

### Key algorithms/patterns

- **Index-driven exploration**: `index.md` serves as both plan and navigation map. The target hierarchy defined there drives which folders/notes the Context Builder fills.
- **Citation grounding**: Every note statement carries `[source path]` pointer for full traceability.
- **Checklist-gated iteration**: Both stages gate progress on checklist verification, creating a self-correcting loop.
- **Separation of concerns**: Context Builder = evidence collection + organization; Report Writer = synthesis + composition. Never interleaved.

## 4. Design Rationale (why this approach)

The core rationale is that **the context window is the binding constraint** on deep research. Prior approaches (summarization of tool observations, sub-agent delegation) only delay the context limit — they remain bounded by it. The authors cite three converging observations:

1. **File systems are the native substrate for complex human knowledge work** (e.g., researchers organizing papers in folders). Mirroring this pattern gives agents a well-established interface for long-horizon tasks.

2. **Separation of concerns is critical**: In deep research, evidence collection and report writing compete for the same token budget in single-agent designs. By separating them into distinct agents with a shared persistent workspace, each stage gets full context for its specialized task. The ablation removing Dual-Agent causes the largest quality drop (-10.35 RACE), confirming this hypothesis.

3. **Iterative refinement requires persistent state**: Without a file system, internal states (thoughts, tool observations) are ephemeral — discarded when the agent loop ends. A persistent workspace enables multi-session refinement where each session builds on previous findings, analogous to how human researchers work over multiple sittings.

The design of **section-wise writing** (rather than one-shot report generation) is motivated by the observation that one-shot generation tends to produce "a mere list of facts, lacking explanation and in-depth analysis." Section-level self-checks provide frequent re-grounding opportunities.

## 5. Limitations & Failure Modes

1. **Backbone model dependence**: The framework requires strong reasoning and function-calling abilities. Smaller/weaker models exhibit shorter trajectories and more premature stopping. The file I/O operations (insert/delete/replace/grep) are especially demanding. GPT-5-mini needs 10 rounds to match what GPT-5 achieves in 3.

2. **Readability-comprehensiveness trade-off**: As the KB grows and reports become denser, readability degrades. A post-hoc rephrasing pass can recover it (51.66→51.92), but this is benchmark-specific rather than a general solution.

3. **Citation accuracy variance**: GPT-5 tends to "stack several citations at the end of a paragraph," causing misalignment between cited sources and fact statements — scoring 60.04% vs Claude's 76.17%.

4. **False sense of completeness**: The self-check mechanism can mark tasks complete based on criteria satisfaction even when the KB has genuine gaps, if the checklist doesn't capture those gaps.

5. **Hallucination propagation**: Despite citation grounding, the system may propagate inaccurate, biased, or outdated web-sourced information into the final report.

6. **File operation vulnerabilities**: Incorrect edits, inconsistent state updates, or erroneous tool use can corrupt the workspace, especially with weaker models.

7. **No quantitative ablation on checklist/control files alone**: The Persistent Workspace ablation removes todos, logs, AND structured KB together — the individual contribution of control files vs KB structure is not isolated.

8. **Prompt injection risk**: Persisting raw web content and intermediate notes increases attack surface for malicious pages.

## 6. Transfer to Lyra (the one idea + §4.x workstream + Impact/Effort/Tier)

### Transferable Idea

**Persistent file-system workspace as external memory for multi-session agent orchestration.** FS-Researcher demonstrates that using a file system (structured markdown directories with control files: todos, checklists, logs) as durable external memory enables iterative agent refinement beyond the context window. For Lyra, this translates to: Lyra's research agents can persist intermediate findings, search plans, and evidence trees in a `.lyra/workspace/` directory with hierarchical organization and self-check gating, enabling multi-session research that survives context window exhaustion and allows human-in-the-loop review between sessions.

### Workstream Route

**§4.2 Memory architecture (persistent cross-session state)** — This paper provides concrete implementation evidence for the persistent-workspace pattern: control files (todos, checklists, logs), deliverable directories, and checklist-gated iteration. It directly supports the memory subsystem's "external durable store" design.

### Impact/Effort/Tier

- **Impact**: 4 (proven SOTA on mainstream benchmarks; framework-level gain of +2.80 RACE over official harness; clean ablation results)
- **Effort**: 2 (file-system operations are simple — mkdir, read/write markdown, todo status updates; no novel algorithms; Lyra already has file I/O capabilities)
- **Tier**: **breakthrough** (external memory via file system is a validated, generalizable pattern that fundamentally extends agent capabilities beyond the context window, demonstrated at SOTA level on competitive benchmarks)
