# Self-Evolving Multi-Agent Systems via Decentralized Memory

**Authors**: Guangya Hao (University of Cambridge), Yunbo Long (University of Cambridge), Zhuokai Zhao (University of Chicago)
**Venue**: Preprint — arXiv:2605.22721v1 [cs.MA], May 21, 2026. Not yet peer-reviewed.

## 1. Mechanism (step-by-step)

DecentMem is a decentralized memory framework where each agent maintains a **private dual-pool memory** and an online router balances exploitation vs. exploration using stage-wise feedback from an LLM-as-a-judge.

### 1.1 Dual-Memory Pool Architecture

For each agent `a_m`, memory is partitioned into two disjoint pools:

```
M_m = M_m,E-pool ∪ M_m,X-pool
```

- **Exploitation Pool (E-pool)**: Stores consolidated past collaboration trajectories. Each memory piece `z = (ξ, r*)` where `ξ` is the context prototype and `r* = (r_trajectory, r_comment)` encodes both the action sequence and the agent's self-commentary (rationale). Records not just *what* was solved but *how* and *by whom*.
- **Exploration Pool (X-pool)**: A temporary buffer of LLM-generated candidate solutions for unseen contexts. Reset after each task when its contents are consolidated into the E-pool.

### 1.2 Online Router (Pool Selection)

At each stage `t`, when agent `a_m` encounters sub-task `x^(t)`, the router selects a pool with probability proportional to weights:

```
α_m,E-pool = w_m,E-pool / (w_m,E-pool + w_m,X-pool)
α_m,X-pool = 1 - α_m,E-pool
```

Where `w_m,X-pool = 1.0` (fixed) and `w_m,E-pool` is dynamically updated.

### 1.3 Memory Retrieval / Generation

**If E-pool selected**: Retrieve Top-K memory pieces by embedding similarity:
```
ρ_m^(t) = Top-K( M_m | sim(e(x^(t)), e(ξ_z)) )
```
Subject to a similarity threshold `τ`. If no sufficiently similar memory found → **fallback to X-pool**. This threshold prevents mismatched reuse when the current task deviates from past experience.

**If X-pool selected (or E-pool fallback)**: Generate a novel exploratory memory piece `z_new` for the current context using the LLM.

### 1.4 Action Generation

Selected memory (either retrieved `ρ_m^(t)` or generated `z_new`) is fed to the LLM:
```
v_m^(t) = Π_act( x^(t), ϕ_m^(t), ρ_m^(t) / z_new )
```
Where `ϕ_m^(t)` is context from predecessor/neighbor agents. When E-pool memory contains a compatible collaboration trajectory, the historical allocation can be reused as a coordination prior.

### 1.5 Dual-Memory Update (LLM-as-a-Judge)

After execution, an external LLM judge evaluates the trajectory **stage by stage** on four dimensions: correctness, allocation quality, intermediate coherence, and final integration. Let `q_prev` and `q_curr` be consecutive stage scores, and `Δt = I[q_curr > q_prev]`.

**If E-pool was used at stage t:**
```
w_m,E-pool ← w_m,E-pool + 0.5    if Δt = 1 (improvement)
w_m,E-pool ← max(1.0, 0.5 × w_m,E-pool)  otherwise (decay)
```

**If X-pool was used at stage t:**
```
w_m,E-pool ← max(1.0, 0.5 × w_m,E-pool)  if Δt = 1 (exploration succeeded, suppress E-pool over-dominance)
w_m,E-pool ← w_m,E-pool + 0.5            otherwise (exploration failed, boost E-pool)
```

**After task completion:**
```
M_m,E-pool ← M_m,E-pool ∪ M_m,X-pool    (consolidate)
M_m,X-pool ← ∅                            (reset)
```

### 1.6 Theoretical Framework

The search process is modeled as a **graph-structured random walk with heuristic teleportation**. For each agent, the solution subspace is `G_m = (V_m, E_m)`. The state distribution evolves as:

```
p_{m,ℓ+1} = M_{m,ℓ} p_{m,ℓ} = [α_{m,ℓ} T_m + (1 - α_{m,ℓ}) h_m 1^T] p_{m,ℓ}
```

Where:
- `T_m`: Column-stochastic transition matrix from similarity-based local walk (E-pool)
- `h_m`: LLM prior teleportation vector with full support over `V_m` (X-pool)
- `α_{m,ℓ}`: Routing probability

### 1.7 Theoretical Guarantees

**Theorem 1 (Global Reachability)**: With `w_X-pool > 0` and `(h_m)_i > 0 ∀i`, the transition matrix `M_{m,ℓ}` is strictly positive → Markov chain is irreducible and aperiodic → agent cannot be permanently trapped in a local optimum.

**Theorem 2 (Logarithmic Regret)**: Under strict concavity of the reward function and existence of a unique optimal `α* ∈ (0.5, 1)`, the online routing achieves `E[R(T)] = O(log T)`, matching the `Ω(log T)` stochastic bandit lower bound. Fixed routing policies (including α = 0.5) incur `Θ(T)` linear regret.

**Key insight**: Pure E-pool (α = 1) may get trapped in local optima. Pure X-pool (α = 0) discards structured reuse. Only the adaptive mixture guarantees both global reachability and meaningful self-evolution.

## 3. Trade-offs

| Win | Loss / Cost |
|-----|-------------|
| **+8.6% avg accuracy** over strongest centralized memory | Per-agent dual-pool memory management adds implementation complexity |
| **Up to 49% token reduction** vs. centralized baselines | Requires LLM-as-a-judge for stage-wise evaluation (additional inference cost not fully accounted) |
| **Agent diversity preserved** — gains grow with coordination stochasticity | Similarity threshold τ introduces a hyperparameter; no systematic sensitivity analysis provided |
| **O(log T) regret guarantee** matching theoretical lower bound | Assumes strict concavity of reward function (Assumption 1) — may not hold for all task distributions |
| **~2.5× faster convergence** via self-evolution | Decentralized design means no cross-agent knowledge sharing; potentially slower for tasks where shared insight is beneficial |
| **Plug-in compatibility** with AutoGen, DyLAN, AgentNet | Evaluated only on 3-agent systems; scaling behavior to larger swarms (10+, 100+) unknown |
| **Both accuracy AND efficiency improve** simultaneously (Pareto-dominant) | X-pool reset after each task discards unused exploratory candidates — wasteful if task distribution is stationary |
| **Dual-pool design prevents local optima traps** | Requires consolidation step (Eq. 8) after every task, adding per-task overhead |

## 4. Design Rationale

**Why decentralized over centralized**: Centralized memory homogenizes agent behavior because all agents retrieve from the same pool — the role-complementary specialization that makes multi-agent systems valuable is gradually lost. This is not a minor inefficiency; it is a structural flaw. The authors argue centralization is "the wrong default" inherited from single-agent memory architectures.

**Why dual-pool over single-pool**: Pure exploitation traps agents in local optima (the E-pool's local walk cannot escape closed communicating classes). Pure exploration is memoryless (discards structured reuse). The mathematical proof (Remark 1) shows both boundary cases fail — only the adaptive mixture guarantees global reachability.

**Why online routing over fixed schedule**: Fixed routing policies incur Θ(T) linear regret. The online router converges to the optimal exploitation-exploration balance α* at an O(log T) rate, which is order-optimal. An LLM-as-a-judge provides stage-wise feedback rather than relying on final-answer-only signals, enabling fine-grained credit assignment.

**Why agent-private memory**: Preserves diversity because consolidated experience never leaves the agent that earned it. This is especially important as coordination becomes more stochastic — the empirical margin grows from +2.7% (pre-designed workflows) to +23.1% (opportunistic coordination).

## 5. Limitations and Failure Modes

1. **Domain coverage gap**: Evaluated on math, code, QA, and embodied tasks. Not tested on legal reasoning, medical diagnosis, or other high-stakes domains where incorrect memory retrieval could cause harm. Authors explicitly acknowledge this.

2. **LLM-as-a-judge reliability**: The stage-wise evaluation depends on an external LLM judge. If the judge is biased, poorly calibrated, or itself fails on certain task types, the online reweighting degrades. No analysis of judge quality or judge-model sensitivity.

3. **Small-scale validation**: All experiments use 3-agent systems. Scaling properties (10+, 100+ agents) are untested. In large swarms, per-agent dual-pool memory may still create N × memory overhead, and the consolidation-reset cycle may become a bottleneck.

4. **Threshold sensitivity**: The similarity threshold τ for E-pool fallback is mentioned but never systematically ablated. If set too high, agents rarely reuse experience; too low, mismatched memory degrades performance.

5. **Privacy claim unsubstantiated**: The paper claims privacy benefits from decentralization but provides no formal privacy analysis (e.g., differential privacy guarantees, information leakage bounds).

6. **X-pool reset waste**: After each task, the X-pool is consolidated into the E-pool and reset (Eq. 8). In stationary task distributions, unused exploratory candidates are discarded, which is wasteful.

7. **Not peer-reviewed**: This is a preprint (May 2026). No conference or journal acceptance yet.

8. **Assumption 1 (strict concavity of r(α))**: Required for the O(log T) regret proof but not empirically verified. If the reward function is non-concave or multi-modal, the regret bound may not hold.

## 6. Transfer to Lyra

### The One Transferable Idea

**Replace Lyra's centralized/shared agent memory with a per-agent dual-pool (E-pool + X-pool) architecture with online LLM-judge reweighting.** Each Lyra agent maintains its own exploitation pool (consolidated past interaction trajectories) and exploration pool (LLM-generated candidates for novel contexts). An online router balances the two based on stage-wise performance feedback, preserving agent diversity while enabling structured experience reuse. The key insight for Lyra: decentralized memory prevents the "diversity collapse" that occurs when all agents share the same memory, and the dual-pool design mathematically guarantees the system cannot be permanently trapped in local optima.

### §4 Workstream Route

**§4.2 — Memory Architecture**: This directly impacts the design of Lyra's agent memory subsystem. The dual-pool pattern with online exploitation-exploration routing is a concrete, theoretically-grounded architecture that replaces the current centralized memory design.

### Impact / Effort / Tier

| Dimension | Rating | Justification |
|-----------|--------|---------------|
| **Impact** | 4/5 | Directly applicable to Lyra's core memory architecture; theoretical guarantees (O(log T) regret, global reachability) provide strong foundation; demonstrated gains across diverse MAS frameworks and model sizes |
| **Effort** | 4/5 | Requires significant refactoring: (a) implementing dual-pool data structures per agent, (b) embedding-based similarity retrieval, (c) LLM-as-a-judge stage-wise evaluation pipeline, (d) online weight update logic, (e) consolidation-reset cycle, (f) integration with existing Lyra agent lifecycle |
| **Tier** | **Breakthrough** | Addresses a structural limitation (centralized memory → diversity collapse) with a theoretically-grounded solution that simultaneously improves accuracy and reduces cost. The monotonic gain pattern with coordination stochasticity is especially relevant for Lyra's multi-agent architecture. |

### Implementation Sketch for Lyra

```
AgentMemory {
  ePool: MemoryPiece[]    // consolidated trajectories
  xPool: MemoryPiece[]    // LLM-generated candidates
  wE: float               // E-pool weight (adaptive)
  wX: float = 1.0         // X-pool weight (fixed)
  
  select(): MemoryPiece {  // Online router
    α = wE / (wE + wX)
    if random() < α:
      result = similaritySearch(ePool, currentContext, τ)
      return result ?? generateFromXPool()
    else:
      return generateFromXPool()
  }
  
  update(poolUsed, scoreImproved) {  // LLM-judge feedback
    if poolUsed == E_POOL:
      wE = scoreImproved ? wE + 0.5 : max(1.0, 0.5 * wE)
    else:  // X_POOL
      wE = scoreImproved ? max(1.0, 0.5 * wE) : wE + 0.5
  }
  
  consolidateTask() {  // After task completion
    ePool.extend(xPool)
    xPool.clear()
  }
}
```

### Key Risks for Lyra Adoption

- LLM-as-a-judge adds per-stage inference cost; needs to be benchmarked against Lyra's token budget
- 3-agent validation in paper vs. Lyra's potentially larger agent configurations
- Similarity threshold τ needs tuning for Lyra's domain
- X-pool LLM generation quality depends on the underlying model's creative capability
