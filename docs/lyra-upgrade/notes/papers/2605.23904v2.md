## 1. Mechanism (Step-by-Step)

SkillOpt is the first systematic controllable text-space optimizer for agent skills. It treats a natural-language skill document (typically `best_skill.md`, 300-2000 tokens) as the external trainable state of a **frozen** target agent model. A separate, stronger **optimizer model** (teacher) converts scored rollout trajectories into bounded add/delete/replace edits, and edits are accepted only when they strictly improve a held-out validation score.

### Problem Setup (Section 3.1)

- A skill `s` is a natural-language policy inserted into the agent context before execution.
- The target model `M` is frozen (no weight updates). Only the skill document changes.
- Data is split: `D_train` (rollout evidence), `D_sel` (validation gate), `D_test` (final reporting only).
- The optimizer state contains: current skill, best validation-gated skill, cached skill hashes (for deduplication), an epoch-local rejected-step buffer, and optional slow/meta-update state.
- Output: `best_skill.md` — only the best accepted skill is exported.

### Forward Pass: Rollout Evidence (Section 3.2)

At each optimization step:
1. The frozen target model `M` runs a rollout batch from `D_train` with the current skill.
2. Harness records: task metadata, messages, tool calls, observations, command outputs, final answers, verifier feedback, and benchmark-specific context.
3. Default batch size `B = 40`. Accumulation is supported: multiple rollout batches reflected on separately, merged into one update.

### Backward Pass: Minibatch Reflection (Section 3.3)

The optimizer model converts trajectories into skill edits:
1. **Separate** failures from successes.
2. **Partition** each group into reflection minibatches (default `Bm = 8`) — crucial because single-trajectory analysis produces anecdotal fixes, while minibatches expose reusable procedural errors (wrong source, wrong format, missing verification).
3. **Failure minibatches** propose missing or corrective rules.
4. **Success minibatches** preserve behaviors that already work.
5. Each reflection returns **structured add/delete/replace edits** (or rewrite suggestions in rewrite mode).
6. **Hierarchical merge**: consolidate failure-driven and success-driven edits separately, then combine with priority on failure corrections. Deduplicates, resolves contradictions, filters example-specific suggestions.

### Bounded Text Updates (Section 3.4)

The critical innovation — a **textual learning rate**:
- Edit budget `Lt` = maximum number of skill edits applied at step `t`.
- After aggregation, the optimizer ranks the merged edit pool by expected utility and **clips to top `Lt` edits**.
- Default: `Lt = 4` with cosine schedule (starts larger, decays to minimum of 2).
- This prevents unbounded rewrites that erase useful rules, introduce incompatibilities, or overfit to local failures.
- Edit operations: `append`, `insert_after`, `replace`, `delete` — all structured, parseable JSON operations.
- Each edit records a `support_count` and `source_type` (failure/success) for ranking.

### Validation Gate & Rejected-Edit Buffer (Section 3.5)

- Every candidate skill `s̃` is evaluated on `D_sel` with the same frozen `M` and harness.
- **Strict gate**: accepted only when `score_cand > score_cur` (ties rejected — no silent drift).
- If accepted and also exceeds `score_best`: becomes `best_skill.md`.
- If rejected: edits and failure patterns stored in epoch-local buffer `B`.
- The buffer is shown to the optimizer in later reflection calls → **negative feedback** without inference-time cost.
- Every step records `edit_apply_report.json` — per-edit accept/skip status, full audit trail.

### Epoch-Wise Slow/Meta Update (Section 3.6)

- At epoch boundaries, samples **same training items** under previous epoch's skill and current skill.
- Groups into: improvements, regressions, persistent failures, stable successes.
- Optimizer writes **longitudinal guidance** into a protected section (`<!-- SLOW_UPDATE_START -->` … `<!-- SLOW_UPDATE_END -->`) that step-level edits cannot touch.
- **Meta skill** is optimizer-side only: summarizes edit pattern effectiveness, guides future optimizer prompts. Never shipped with target model.

### Algorithm 1 Pseudocode (Appendix C.1)

```
1. scur ← s0, sbest ← s0
2. For each epoch e = 1..E:
3.   For each optimization step:
4.     Collect rollout batches: M(x, scur) for tasks x ∈ D_train
5.     Split evidence into failure/success minibatches (size Bm)
6.     Optimizer O → failure patches, success patches
7.     Hierarchical merge → ranked edits → clip to Lt
8.     Apply edits → candidate skill s̃
9.     If Hash(s̃) not cached: Evaluate(M, s̃, D_sel)
10.    If score_cand > score_cur: accept; update sbest if better
11.    Else: store rejected edits in buffer B
12.  End for
13.  Slow update: compare epoch-end skills on same tasks → protected guidance
14.  Meta update: optimizer memory for future edit generation
15. End for
16. Return sbest, score_test
```

### Harness-Agnostic Deployment (Section 3.7)

A lightweight adapter interface constructs batches, injects skills, runs native harness, and returns scored trajectories. Same optimizer works across direct chat, Codex CLI, and Claude Code CLI.

## 3. Trade-offs

| Win | Lose |
|-----|------|
| +23.5 avg over no skill (GPT-5.5 direct chat) | Training cost: 20-214M tokens per skill (one-time) |
| 52/52 cells best or tied-best against all baselines | Requires scored trajectories + held-out selection split |
| Zero inference-time overhead at deployment (compact .md) | Only one skill per domain; not a multi-domain library |
| Compact artifacts (379-1,995 tokens; 1-4 edits reach deployment) | Cannot handle open-ended tasks without verifier |
| Transfer positive across models, harnesses, benchmarks | Optimizer model cost during training (stronger optimizer = better results) |
| Fully inspectable/auditable text output | Optimized skills may encode domain-specific heuristics |
| Works on small models (GPT-5.4-nano +26.7; Qwen3.5-4B +19.2) | External state, not weight-space adaptation — ceiling limited by base model |
| Harness-agnostic (same optimizer for direct chat, Codex, Claude Code) | Larger rollouts/batches increase training cost linearly |
| Cosine LR schedule works robustly across settings | Gains saturate on high-ceiling benchmarks (SearchQA: 77.7→87.3, only +9.6) |

## 4. Design Rationale

**Why train the skill document instead of model weights?** Closed frontier models (GPT-5.5, GPT-5.4) and many open models are inaccessible for weight-space training. Skills are a natural adaptation layer — they package procedures, heuristics, tool policies, and failure modes as external text. If the adaptation target is the agent's procedure, the skill document should be the trainable object.

**Why deep-learning-disciplined optimization?** Prior approaches (one-shot generation, self-revision, evolutionary loops) lack controls for evidence quality, step size, validation, and update direction. SkillOpt maps optimizer design to ML training analogs: rollout/minibatch sizes control evidence noise; edit budget is the learning rate; held-out gate is validation; slow/meta update is momentum. This discipline prevents the "semantic drift" that unbounded self-editing causes.

**Why bounded add/delete/replace instead of full rewrite?** Unbounded rewrites can erase useful rules, introduce incompatible instructions, or overfit to local failures. Atomic edit operations preserve skill continuity while allowing the skill to acquire new procedures. The hierarchy of merge operations (per-minibatch failure/success → merged failure → merged success → final failure-prioritized merge) ensures recurring patterns dominate single-instance fixes.

**Why separate optimizer and target model?** A stronger optimizer model (e.g., GPT-5.5 training skills for GPT-5.4-nano) costs only training-time API calls and adds nothing at deployment. Table 5 confirms: strong optimizer (GPT-5.5) beats target-matched optimizer by 2.9-7.1 points.

**Why protected slow-update section?** Fast step-level edits learn from current batch; slow epoch-level updates learn from cross-epoch comparison. Without the protected region, step edits would overwrite durable procedural lessons — especially damaging on procedural benchmarks (22.5-point drop on SpreadsheetBench when removed).

## 5. Limitations & Failure Modes

1. **Verifier dependency**: The optimization loop requires scored trajectories with automatic verifiers, exact-match metrics, or executable checks. For open-ended domains where success is subjective, multi-dimensional, or costly to judge, the validation gate needs stronger human or model-based evaluation.

2. **Training cost amortization**: Training requires rollout computation and optimizer model calls (20-214M tokens per skill). Cost is amortized when reused, but may be unappealing for one-off tasks.

3. **Single-skill ceiling**: SkillOpt optimizes one portable skill per domain, not a library. Highly heterogeneous domains requiring many disjoint procedures may exceed what one compact document can encode.

4. **Domain overfitting risk**: Optimized skills can encode domain-specific heuristics from the training distribution. Careful held-out evaluation remains necessary before cross-domain transfer.

5. **SearchQA saturation**: On high-ceiling benchmarks where frontier models already perform well (SearchQA 77.7 baseline), gains are limited (+9.6). The method benefits most when procedural gaps exist between model capability and task demands.

6. **No weight-space adaptation**: The frozen-model approach means skill quality is bounded by what textual instructions can express — if the target model fundamentally lacks a capability, no skill document can add it.

7. **Not tested on open-ended dialogue/creative tasks**: Benchmarks all have verifiable ground truth; effectiveness on subjective or creative agent tasks is unknown.

## 6. Transfer to Lyra

### The One Idea

**Treat Lyra's system prompt and skill documents as explicitly trainable artifacts using a validation-gated optimizer loop.** Instead of hand-crafting Lyra's base prompt or one-shot generating skill documents, implement an offline training loop where: (a) a separate optimizer model analyzes Lyra's execution trajectories, (b) proposes bounded add/delete/replace edits under a textual learning-rate budget, and (c) a held-out validation gate accepts edits only when they strictly improve task-completion metrics. The resulting compact prompt/skill artifact is auditable, portable, and adds zero inference-time overhead.

### Workstream Route

**§4.5 — Prompt & Skill Management** (with cross-cutting impact on §4.2 Context Assembly and §4.10 Agent Harness). The bounded-edit-with-validation-gate pattern applies directly to Lyra's system prompt engineering, tool-calling policies, output-format constraints, and error-recovery procedures. The cross-harness transfer property (Codex skill works in Claude Code at +59.7 points) validates that optimized procedural artifacts survive environment changes — relevant for Lyra's multi-backend ambitions.
