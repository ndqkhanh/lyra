# NEXUSSUM: Hierarchical LLM Agents for Long-Form Narrative Summarization
**Authors:** Hyuntak Kim*, Byung-Hak Kim*† (CJ Corporation, AI R&D Division)
**Venue:** arXiv:2505.24575v1 [cs.CL], 30 May 2025
**License:** Not specified

## 1. Mechanism (step-by-step)

NEXUSSUM is a training-free, hierarchical multi-agent LLM framework for summarizing long-form narratives (books, movie scripts, TV scripts). It processes text through three sequential stages using a chunk-and-concat pattern:

### Stage 1: Dialogue-to-Description Transformation (Preprocessor Agent P)
- **Input:** Raw narrative text N (mixed dialogue + description)
- **Chunking:** Segment N into k scene-based chunks: N = n1 ⊕ n2 ⊕ ... ⊕ nk (chunk size = 8 scenes)
- **Transformation:** For each chunk ni, an LLM (prompted with conversion guidelines) rewrites character dialogues into third-person reported speech while preserving scene headings, stage directions, and narrative context.
- **Output:** Preprocessed narrative N' = P(n1) ⊕ P(n2) ⊕ ... ⊕ P(nk) in unified prose format

### Stage 2: Hierarchical Narrative Summarization (Summarizer Agent S)
- **Input:** Preprocessed narrative N'
- **Chunking:** Further split N' into j scene-based chunks: N' = n'1 ⊕ n'2 ⊕ ... ⊕ n'j (j = k)
- **Per-chunk Summarization:** Each chunk is independently summarized by S, capturing key events, character interactions, and significant plot points.
- **Concatenation:** Initial summary S0 = S(n'1) ⊕ S(n'2) ⊕ ... ⊕ S(n'j)

### Stage 3: Iterative Compression (Compressor Agent C)
- **Sentence-Based Chunking:** S0 is split into l0 chunks by sentence-level grouping with a maximum token size δ per chunk: S0 = s0,1 ⊕ s0,2 ⊕ ... ⊕ s0,l0
- **Hierarchical Iterative Compression:** For i = 1 to n iterations:
  Si = Ci(si-1,1) ⊕ Ci(si-1,2) ⊕ ... ⊕ Ci(si-1,li-1)
- **Stopping Criterion:**
  - If Si exceeds target word count θ → continue compressing
  - If Si falls below θ → use previous iteration's output
  - Maximum 10 iterations enforced
- **Hyperparameters:** δ (chunk size in words), θ (lower bound word count target)

### Key Equation — Length Adherence Rate:
LAR = 1 - |Lgen - Ltarget| × Ltarget^(-1)

### Implementation Details:
- Base model: Mistral-Large-Instruct-2407 (123B)
- Inference: vLLM, temperature=0.3, top-p=1.0, seed=42
- Hardware: 4× A100 GPUs
- Optional: Claude 3 Haiku experiments at temperature=0
- Alternatives: CoT reasoning in P, Few-Shot learning in S and C for domain adaptation

### Time Complexity:
- Zero-Shot LLM: O(n²) + O(nr) — quadratic in input length due to self-attention
- NEXUSSUM: O(n) — linear, because each stage operates on constant-size chunks with constant compression ratios
  T_NEXUSSUM = O(n[c1(1+a1) + a1c2(1+a2) + a1a2c3(1+a3)]) → O(n)

## 3. Trade-offs (wins vs loses)

| Wins | Loses |
|------|-------|
| +30.0% BERTScore improvement on BookSum over fine-tuned CachED | Readability rated 2.17/5 by human experts vs 4.17/5 for Zero-Shot |
| No fine-tuning required — purely prompt-based multi-agent | High per-sample cost: 3+ LLM agent passes (P + S + multiple C iterations), requiring 4× A100 GPUs |
| Precise length control: LAR ~0.9-1.0 vs ~0.25-0.6 for Zero-Shot prompts | Requires per-dataset hyperparameter tuning (δ and θ) |
| O(n) inference time complexity vs O(n²) for full-context models | Maximum 10 compression iterations — may not converge for all target lengths |
| Scales to arbitrary input length via chunking (tested up to 158K tokens) | Chunk-based processing can break cross-chunk dependencies if events span chunk boundaries |
| Adaptable via prompt engineering (CoT/Few-Shot) without retraining | Prompt engineering itself requires task-specific tuning (SummScreenFD needed CoT+FewShot for +5.0 BERTScore) |
| Near-perfect factual accuracy (96.83 NarrativeFactScore with refinement) | BERTScore/ROUGE scores do not align with human preference — Zero-Shot preferred despite lower automated scores |

## 4. Design Rationale (why this approach)

1. **Dialogue-to-Description transformation over raw script input:** Narrative texts inherently mix dialogue with description. Multi-speaker dialogue fragments coherence — converting to prose before summarization reduces ambiguity and unified the input format for the summarizer. This is a domain-specific insight (RQ2) not addressed by generic long-context methods.

2. **Hierarchical multi-agent over single-pass LLM:** Even 200K-token context windows exhibit "lost in the middle" degradation on narratives of 40K-160K tokens. Chunking into scene-based units (~8 scenes each) preserves local narrative structure, while hierarchical merging maintains global coherence.

3. **Iterative compression over one-shot length control:** Prompt-based length instructions ("write 600 words") are unreliable (Zero-Shot produced 219 words for a 600-word target). Iterative compression with a hard lower bound θ provides deterministic length control.

4. **Scene-based chunking for narratives (not arbitrary token splits):** Scenes are natural semantic boundaries in scripts. Chunking at scene boundaries preserves narrative units intact, unlike arbitrary 512/1024 token windows that can split mid-dialogue.

5. **Training-free by design:** The paper explicitly avoids fine-tuning to remain adaptable across novels, movie scripts, and TV shows without per-domain model training.

## 5. Limitations & Failure Modes

1. **Readability gap:** The most significant failure mode — human experts rated NEXUSSUM summaries 2.17/5 on readability vs 4.17/5 for Zero-Shot. Summaries are dense, factual, but "scattered" and hard to follow for non-expert readers. NEXUSSUMR (with a rewrite agent) partially closes this gap to 3.67 but still lags behind Zero-Shot.

2. **Automated metrics don't capture human preference:** BERTScore and ROUGE improvements do not correlate with readability or user satisfaction. The paper explicitly acknowledges this evaluation paradigm limitation.

3. **Computational cost:** Three sequential LLM agent stages with potentially 10 compression iterations per sample. Not suitable for real-time or interactive summarization.

4. **Per-dataset hyperparameter sensitivity:** Chunk size δ and lower bound θ must be tuned per dataset. BookSum needs δ=300, MovieSum/MENSA δ=300, SummScreenFD needs maximum chunk size. Wrong δ causes significant performance drop (BookSum drops from 67.16 to 50.51 when using 100K chunk size).

5. **Cross-chunk dependency loss:** Although scene-based chunking is better than arbitrary token splits, events spanning chunk boundaries may lose coherence. No explicit cross-chunk attention or memory mechanism.

6. **Hallucination without refinement:** Base NEXUSSUM scores 90.16 NarrativeFactScore — meaning ~10% of atomic facts may be hallucinated. Requires explicit post-hoc refinement to reach 96.83.

7. **Provider dependency:** Primary experiments use Mistral-Large (123B) via API. Results may not transfer to smaller/weaker LLMs used as agents.

## 6. Transfer to Lyra

**The One Idea:** The Dialogue-to-Description Transformation preprocessor — a domain-specific preprocessing stage that converts unstructured multi-turn dialogue into unified narrative prose before downstream processing. For Lyra, this maps to converting user-agent conversation logs into structured narrative context before feeding into the memory system, retrieval pipeline, or context window assembly.

**Workstream Route:** §4.1 (Context & Memory) — This directly feeds the context ingestion and memory encoding pipeline. Lyra's conversation history (multi-turn dialogues with tool calls, interleaved system/user/assistant messages) suffers from the same fragmentation problem that NEXUSSUM addresses for movie scripts. A preprocessor agent that transforms conversation logs into coherent narrative summaries would improve context utilization efficiency and reduce "lost in the middle" degradation.

**Impact:** 4 — High potential to improve Lyra's context utilization and memory encoding quality, especially for long-running sessions with extensive conversation history.

**Effort:** 3 — Requires prompt engineering for the preprocessor agent and integration into Lyra's context pipeline. No model training needed. The main cost is inference overhead for the transformation pass.

**Tier:** Investigate — Worth prototyping because: (a) the core technique is simple (prompt-based LLM transformation), (b) the problem it solves (mixed-format text fragmentation) directly applies to Lyra's conversation logs, and (c) it requires no fine-tuning. However, the human evaluation shows readability trade-offs that need careful design for Lyra's use case, and the per-sample inference cost must be measured.
