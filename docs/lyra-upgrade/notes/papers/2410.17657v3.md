## 1. Mechanism (step-by-step)

ReflecTool is a two-stage framework for tool-augmented clinical agents. The agent action space combines tool actions AT (15 domain-specific clinical tools) and inner actions AI = {Plan, Think, Finish}. At step i, action ai ∈ A = AT ∪ AI, observation oi = ai(param_ai), and next action ai+1 ~ πθ(a | ci, X) where ci is trajectory history.

### Stage 1: Optimization Stage (Algorithm 1)

1. Agent generates initial trajectory C1 = LLM(X) on a small pre-defined training subset.
2. **Reflection on C1:** LLM(X, C1, y) → S (suggestion comparing C1 with ground-truth answer y).
3. **Regenerate refined trajectory:** LLM(X, C1, S) → C2.
4. If y_C2 = y (successful), save C2 into long-term memory M: M ← M ∪ {X, C2}.
5. **Tool-wise experience extraction:** Compare C1 and C2 for each action that appears in both trajectories: LLM(X, C1, C2, y) → EX. Merge each action-specific suggestion into tool-wise experience: LLM(E(a), EX(a)) → E(a). E accumulates as E = {E1, E2, ...} ∪ {E_Plan, E_Think, E_Finish}.
6. Steps 1-5 repeat over optimization samples. Each successful task produces one memory item + one set of tool-wise suggestions.

### Stage 2: Inference Stage

1. **Memory retrieval:** Given query q, retrieve top-k similar cases from long-term memory using BM25: M(q) = TopK_max(sim(q, qi | qi ∈ M)).
2. **Memory-augmented action:** ai+1 ~ πθ(a | ci, X, M(q)).
3. **Tool-wise verification:** At each step, the verifier improves action quality using tool-wise experience E. Two methods:

**Iterative Refinement (Eq. 7-8):**
- Initial action a⁰i generated from Eq. 6.
- For j = 1, 2, ..., n refinement steps: aʲi = LLM(ci, a^{0:j-1}_i, X, M(q), E(a^{0:j-1}_i))
- Early stop if aʲi = a^{j-1}_i (verifier outputs identical action).
- Final action: aʲi if converged, else aⁿi.

**Candidate Selection (Eq. 9):**
- Sample n candidate actions a^{0:n}_i from output space.
- Select best: ai+1 = arg max_{a ∈ a^{0:n}_i} pθ(a | ci, X, M(q), E(a^{0:n}_i))

### Clinical Toolbox (15 tools)
- Knowledge: Google Search, MedRAG (PubMed + StatPearls + Textbooks via BM25), DrugBank, UMLS
- MultiModal: HuatuoGPT-Vision (medical MLLM), MedCaptioner, MiniCPM (general MLLM)
- Numerical: Calculator (Python eval), DBManual (SQL schema description), SQLCoder (NL→SQL, max 3 retry on error)
- Data: Spacy (SciSpaCy NER), LongDocRAG (Llama-Index chunking + retrieval)

## 3. Trade-offs

| Win | Loss |
|-----|------|
| +10 points over pure LLMs, +3 points over strongest agent baseline (Reflexion) across both 7B and 72B scales | Requires optimization stage on labeled subset (cold-start: no training data = no memory) |
| Candidate Selection steadily improves with larger n (≥ +4pts at n=32), Iterative Refinement best at low n=2 | Iterative Refinement degrades beyond n=2 (over-refinement) |
| Candidate Selection + strong model, Iterative Refinement + weak model — adaptive strategy confirmed | Two-stage architecture adds complexity; optimization stage latency grows linearly with sample count |
| Tool selection error reduced 12-72× vs ReAct, 8-21× vs Reflexion at step-level | 15-tool action space is domain-specific; generalizing to arbitrary toolsets not tested |
| Long-term memory benefits ALL agent methods (ReAct, Reflexion, CRITIC also improve) | BM25 retrieval from memory; semantic mismatch possible (no embedding-based retrieval explored) |
| Candidate Selection naturally parallelizable (lower runtime: 28.56s vs 47.90s for Iterative Refinement on 72B) | Relies on Qwen2's strong instruction-following; Llama3 series showed formatting errors requiring prompt adjustment |
| No fine-tuning required — works with any instruction-following LLM | Trajectories that lead to correct results may contain incorrect intermediate steps (reliability issue acknowledged by authors) |
| Optimization stage builds increasingly effective memory (monotonic improvement) | CAB benchmark may not fully encompass real clinical complexity; ongoing updates needed |

## 4. Design Rationale

**Why two-stage (optimization + inference) instead of online-only reflection?** Online-only methods like Reflexion reflect and retry within a single episode. But they have no persistent memory across episodes — each new task starts from scratch. The optimization stage builds cross-episode knowledge: successful trajectories as exemplars (long-term memory) and action-specific guidance (tool-wise experience). This turns episodic reflection into cumulative learning. The ablation proves this: removing long-term memory costs 4-7 points.

**Why tool-wise experience instead of just saving trajectories?** Saving full trajectories helps with similar tasks (retrieval) but doesn't help the model learn *how to use tools better* on novel tasks. Tool-wise experience EX isolates per-action patterns — e.g., "after getting MedRAG results, cross-reference with another source" or "ensure SQLCoder query matches the database schema from DBManual." These action-level heuristics transfer across task types.

**Why two verification methods (Iterative Refinement vs Candidate Selection)?** Inspired by Snell et al. (2024) on scaling test-time compute: refinement (sequential improvement) vs selection (parallel sampling then picking best). The finding that each excels at different model strengths mirrors the test-time compute literature — weaker models benefit from step-by-step guidance (refinement), stronger models benefit from generating good options and picking the best (selection). This adaptive strategy maximizes model potential regardless of backbone capability.

**Why BM25 for memory retrieval instead of embeddings?** BM25 is simple, deterministic, zero-config, and works well for keyword-matching clinical queries. The paper does not compare against embedding-based retrieval — this is a deliberate simplicity choice, not a performance claim.

**Why 15 heterogeneous tools instead of a unified interface?** Clinical data comes in diverse formats (free text, images, SQL databases, knowledge graphs, uploaded files). A unified tool would need to handle all modalities — complex and brittle. Heterogeneous tools let each tool specialize, with the agent learning to route between them. The tool selection error analysis (§5.5) shows ReflecTool dramatically reduces misuse of modality-specific tools (SQLCoder, DBManual, LongDocRAG).

## 5. Limitations & Failure Modes

1. **Optimization stage requires labeled data:** The entire memory-building process depends on having ground-truth answers y to verify trajectory success. For truly novel tasks with no labeled examples, the optimization stage cannot run — the method degrades to a zero-shot agent. This is the single biggest deployment constraint.

2. **Trajectory reliability unverified:** The authors acknowledge that "some trajectories lead to correct results does not guarantee that the underlying processes are entirely correct." A trajectory might arrive at the right answer via flawed reasoning. These "lucky" trajectories get saved into long-term memory and can mislead future retrievals. No mechanism exists to validate trajectory quality beyond final-answer correctness.

3. **Iterative Refinement degrades with more steps:** Performance peaks at n=2 and declines beyond — the verifier can "over-correct" and drift from the correct action. This limits how much test-time compute can be usefully spent on refinement.

4. **Domain-specific toolset assumption:** The 15-tool clinical toolbox is hand-crafted for CAB's five dimensions. No experiments on arbitrary or dynamically-changing toolsets. Tool-wise experience extraction assumes a fixed, known action space A = AT ∪ AI.

5. **Qwen2 dependency:** Best results achieved with Qwen2 series (strong instruction-following). Llama3 series required "carefully adjusting prompts" due to formatting errors — the method is sensitive to backbone instruction-following quality.

6. **BM25 retrieval limitation:** Retrieval uses lexical matching (BM25). Semantically similar but lexically different queries may miss relevant memories. Clinical terminology variation (synonyms, abbreviations) could cause retrieval failures.

7. **CAB benchmark coverage:** 18 tasks across 5 dimensions is comprehensive for current clinical agent benchmarks but may not capture the full complexity of real-world clinical workflows (multi-turn patient interactions, evolving treatment plans, integration with live hospital systems).

8. **No multi-turn dialogue evaluation:** All 18 CAB tasks are single-turn (question → answer). Real clinical agents need multi-turn interaction. The framework's memory and reflection mechanisms are not tested in conversational settings.

## 6. Transfer to Lyra

**The One Idea:** Tool-wise experience accumulation — maintaining a per-tool experience bank E = {E_Calculator, E_MedRAG, E_CodeInterpreter, ...} that captures action-specific usage patterns learned from comparing successful vs failed trajectories. During inference, before each tool invocation, a lightweight verifier consults the corresponding tool-wise experience to improve parameters or select among candidates. This is a practical, modular, data-driven alternative to hand-crafted tool descriptions or static few-shot examples.

**Why it matters for Lyra:** Lyra's tool-using agents (§4.7, maturity `draft`) currently rely on static tool descriptions and fixed few-shot examples. As Lyra's tool ecosystem grows (code execution, web search, file operations, database queries), each tool develops its own usage patterns, common failure modes, and parameter quirks. Tool-wise experience would let Lyra's agents accumulate and share per-tool knowledge across sessions — e.g., "when using the CodeInterpreter tool for data analysis, always load pandas first and check column dtypes before operations." This is far more granular and transferable than episode-level trajectory memory.

**Workstream route:** §4.7 (Tool-Using Agent Architecture), with integration points at §4.4 (Context/Memory — long-term memory store) and §4.19 (Quality Gate — verifier for action quality).

**Impact:** 4 — High. Addresses a core limitation in Lyra's tool-using capability: the gap between static tool descriptions and learned tool expertise. Tool-wise experience naturally accumulates as Lyra agents execute more tasks, creating a virtuous cycle. The Candidate Selection variant maps well to Lyra's planned multi-model architecture (generate candidates with cheap model, select with quality gate).

**Effort:** 3 — Moderate. Core components are algorithmically simple: (a) trajectory comparison via LLM call, (b) per-tool experience merging (append + dedup), (c) BM25 or embedding-based retrieval from memory, (d) verifier prompt that injects tool-wise experience before action. No training, no architecture changes. Main work: defining the experience schema, building the memory store, integrating verifier into Lyra's agent loop, and curating an initial optimization set. The clinical toolbox would be replaced by Lyra's existing tool definitions.

**Tier:** Breakthrough — Addresses the tool-utilization gap (§4.7 maturity `draft`) with a practical, training-free method backed by strong empirical evidence (+3 points over Reflexion, 12-72x tool error reduction). The two verification methods provide an adaptive strategy for Lyra's heterogeneous model routing. Candidate Selection is naturally parallel and maps to Lyra's planned multi-provider architecture.
