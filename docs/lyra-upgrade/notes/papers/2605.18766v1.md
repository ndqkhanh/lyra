## 1. Mechanism (Step-by-Step)

### Core Problem
Traditional table retrieval for text-to-SQL uses **fixed-k top-k retrieval**: compute query-table similarity scores, take the top k. But the number of required tables per query varies from 1 to 366 (Spider 2.0), making any fixed k suboptimal — small k misses evidence, large k injects noise.

### ATR Architecture

**Model:** ModernBERT-large (bidirectional encoder-only transformer, 8,192 token context window).

**Input Sequence Structure:**
```
[T_th; q; T_1; t_1; ...; T_n; t_n]
```
Where `T_th` is a learnable threshold token, `q` is the query text, `T_i` is a table token, and `t_i` is the table's textual representation (database name, table name, column names).

**Training — Three Complementary Objectives:**

1. **Adaptive Thresholding Loss (L_AT):**
   - `L1`: For each *relevant* table r, maximize `exp(logit_r) / (sum over relevant tables + T_th of exp(logits))` — pushes relevant table logits above the threshold.
   - `L2`: Maximize `exp(logit_Tth) / (sum over irrelevant tables + T_th of exp(logits))` — pushes irrelevant table logits below the threshold.
   - `L_AT = α·L1 + β·L2` with α=0.8, β=0.03

2. **Relevance Calibration Loss (L_RC):**
   - Binary cross-entropy on each table's logit against ground-truth relevance.
   - `L_RC = -(1/|T+ ∪ T-|) [Σ_relevant log(σ(logit_r)) + Σ_irrelevant log(1-σ(logit_r))]`
   - Maximizes the logit margin between relevant and irrelevant tables.

3. **Semantic Grouping Loss (L_SG):**
   - Contrastive loss on table embeddings `e_i`:
   - If tables share a join key (same label g): minimize `||e_i - e_j||²`
   - If not joinable: maximize margin `max(0, m - ||e_i - e_j||)²`
   - Encourages joinable tables to cluster in embedding space.

**Final Objective:**
`L_ATR = L_AT + λ·L_RC + γ·L_SG`
with λ=0.13, γ=0.04.

**Inference — Sliding Window Reranking:**

Algorithm with window size W and retention size R:
1. Sort tables by bi-encoder similarity (initial ranking), process from *lowest-ranked* to highest.
2. Take the W lowest-ranked tables, compute ATR logits for all table tokens and threshold token T_th.
3. Retain top-R tables by logit for the next window.
4. Merge retained R with next (W-R) tables. Repeat.
5. Track the rank of T_th: once T_th's rank falls below R within its window, its position is finalized.
6. Final retrieval = all tables whose logits outrank the finalized threshold logit.

**Key Hyperparameters:**
- Spider/BIRD: W=20, R=15
- Spider 2.0: W=10, R=5
- Two-stage pipeline: bi-encoder retrieves top 50 candidates → ATR reranks and thresholds

## 3. Trade-offs

| Win | Lose |
|-----|------|
| Eliminates fixed-k trade-off: retrieves exactly needed tables per query | Requires training a separate reranker model (ModernBERT-large) |
| 20%+ precision gain on Spider over best baseline | Needs joinability labels for semantic grouping loss |
| 430-522 fewer tokens per query = lower generator cost | Sliding window runs 7-23x more inference passes than single-pass |
| 80.5% GPU memory reduction on large schemas | Only evaluated on tabular data (no text, images, mixed modalities) |
| Outperforms LLM-based adaptive retrieval (Adaptive-RAG, FLARE) in both accuracy and speed | Two-stage pipeline (bi-encoder + ATR) adds complexity vs single-stage |
| Works out-of-domain (trained on Spider+BIRD, tested on Spider 2.0) | Cannot process tables with >512 token schemas |
| Near-oracle performance (0.3% gap on Spider w/ Gemini-2.5) | Sliding window adds latency for small corpora (0.12s → 0.17s on Spider with W=10/R=6) |

## 4. Design Rationale

The authors argue that **fixed-k retrieval is fundamentally broken** for table retrieval because:
1. The number of required tables varies from 1 to 366 across queries (even within the same database).
2. A single k creates an unavoidable precision-recall tension (Fig 5).
3. Previous work (JAR, Murre, etc.) improved table representations but never addressed the fixed-k assumption itself.

**Why adaptive thresholding rather than iterative LLM calls:** Adaptive document methods (FLARE, Adaptive-RAG) use LLM confidence or classifier-based iteration, but these are (a) expensive (LLM calls per iteration), (b) slow (9-14s end-to-end), and (c) not designed for structured tabular data. ATR avoids generator interaction entirely — the threshold token is a learned, query-specific decision boundary embedded in the encoder.

**Why sliding window rather than full reranking:** Directly encoding all 50 candidate tables in one pass would hit the 8,192 token limit and incur quadratic attention cost. The sliding window bounds memory while guaranteeing that the threshold token rank is correctly determined by exhaustively comparing against all tables in overlapping windows.

**Why train on both high-rank and low-rank candidate segments:** By pairing each query with both the top-50 and bottom-50 bi-encoder candidates, ATR learns to operate when the candidate set contains no relevant tables (reducing false positives at inference).

## 5. Limitations and Failure Modes

1. **Tabular-only scope:** ATR targets structured tables exclusively. Extending to mixed data modalities (text chunks + tables + code) is an open problem.

2. **Joinability dependency:** Semantic grouping loss requires database schema joinability information. In databases without explicit foreign keys, this must be inferred or omitted, degrading the grouping benefit.

3. **Schema length ceiling:** Tables with schemas exceeding 512 tokens are excluded. Queries requiring excluded tables are removed from evaluation — real-world applicability on wide tables is untested.

4. **Sliding window latency overhead:** Even with memory savings, ATR runs 7-23 forward passes vs 1 for single-pass. On small corpora (Spider with 737 tables, average schema ~50 tokens), the overhead is marginal (0.12s → 0.17s). On large schemas, the window/retention trade-off (Table 3) must be tuned per dataset.

5. **Training domain gap:** ATR is trained only on Spider + BIRD (max 1-5 tables per query). On Spider 2.0 (up to 366 tables), recall drops to 72.4% (from 99.5% on Spider). The adaptive threshold generalizes partially but not perfectly to enterprise-scale queries.

6. **Bi-encoder bottleneck:** ATR reranks the top-50 bi-encoder candidates. If the initial bi-encoder misses relevant tables entirely (recall@50 < 100%), ATR cannot recover them.

7. **No multi-turn or interactive setting:** The method assumes a single-shot retrieval scenario. It is untested for conversational or iterative query refinement.

## 6. Transfer to Lyra

### The One Transferable Idea

**Adaptive thresholding for retrieval — replacing fixed-budget retrieval with query-dependent cutoff.** Instead of "retrieve top-k chunks" or "retrieve top-k tools," Lyra could learn a query-complexity-dependent decision boundary that selects *exactly* the evidence needed per turn. A trainable threshold token embedded in the context assembler could determine: "does this query need 3 documents, or 30?" — adapting retrieval budget dynamically.

### Workstream Route

**§4.1 — Context Assembly (Dynamic Context Budgeting).** The adaptive thresholding mechanism maps directly to Lyra's context assembly subproblem. Currently, Lyra likely uses either fixed-budget retrieval (k chunks, k messages) or simple similarity-cutoff. ATR's threshold token approach provides a principled, learnable alternative that optimizes for both precision and recall jointly, reducing noise without missing critical evidence.

### Impact / Effort / Tier

| Dimension | Rating | Rationale |
|-----------|--------|-----------|
| Impact | 4/5 | Eliminates a fundamental precision-recall trade-off in any retrieval pipeline; directly improves downstream task accuracy and reduces token costs |
| Effort | 4/5 | Requires (1) training a small encoder with threshold token on Lyra's retrieval data, (2) constructing joinability-analogous labels (e.g., co-citation, tool co-usage), (3) integrating into Lyra's context assembly loop |
| Tier | **Breakthrough** | The adaptive retrieval paradigm is novel in the agent context (vs top-k everywhere) and could reshape how Lyra budgets context across turns |
