## 1. Mechanism (step-by-step)

Amber is an iterative multi-agent RAG framework with three core components operating in a unified loop.

### 1.1 Overall Architecture

Given a query `q` and empty initial memory `M₀ = ∅`:

**Loop (iteration t):**

1. **Adaptive Information Collector (AIC)** acts as the scheduler. It retrieves top-`k` text chunks `Cₜ = {c₁ᵗ, c₂ᵗ, ..., cₖᵗ}` from external corpus `D` using the current query `qₜ`.

2. **Multi-granular Content Filter (MCF)** applies two-level hierarchical filtering to each chunk `cᵢ`:

   **Level 1 — Chunk-Level Filter (f_c):**
   ```
   f_c(prompt_chunk, q, c_i) ∈ {True, False}
   ```
   Uses an NLI-based fine-tuned LLM to evaluate whether chunk `c_i` is relevant to query `q`. If `False`, the entire chunk is discarded. Training data is constructed semi-automatically by prompting GPT-4 to generate NLI judgments (useful/useless) for each query-reference pair.

   **Level 2 — Sentence-Level Filter (f_sentence):**
   ```
   p_i = f_sentence(prompt_sentence, q, c_i)
   ```
   For chunks passing Level 1, extracts only relevant sentences. Training uses STRINC metric (single-hop QA) and CXMI metric (multi-hop QA) to label sentence relevance. The fine-tuned model `M_slf` is trained with input (query + passages P) -> output (filtered context `t_output`).

   **Output:** Filtered document set `Pₜ = {p₁, p₂, ..., pₘ}`.

3. **Agent-based Memory Updater (AMU)** — The core multi-agent memory mechanism. Three agents collaborate in sequence:

   - **Reviewer:** Examines proposed memory update `m_{t+1}` against current memory `m_t`, retrieved passages `p_t`, and user query `q`. Identifies strengths and weaknesses.
   - **Challenger:** Builds on Reviewer's assessment, identifies potential flaws, overlooked constraints, conflicts with existing knowledge, or unmet requirements. Raises probing questions.
   - **Refiner:** Synthesizes feedback from Reviewer + Challenger into concrete modifications to `m_{t+1}`, producing a revised memory. Focuses on accuracy, clarity, and query adherence.

   This triad ensures memory updates undergo rigorous evaluation, critical examination, and precise refinement:
   ```
   m_{t+1} = AMU(q, C_t, m_t)
   ```

4. **AIC evaluation:** The collector evaluates whether `m_{t+1}` contains sufficient information to answer `q` fully:
   - If **sufficient** → terminate loop, generate answer `a` via zero-shot ICL using `m_T` as context.
   - If **insufficient** → generate refined query `q_{t+1} = AIC(q, q_t, m_{t+1})` targeting missing information, proceed to next iteration.

### 1.2 Training Details

- MCF models fine-tuned using LLaMA-Factory on LLaMA3-8B and Qwen2-7B
- 2 epochs, batch size 4 per device
- Chunk-level: NLI task (useful/useless classification)
- Sentence-level: Context extraction (input: query + passages, output: filtered sentences)
- GPUs: NVIDIA 4090 (24GB), inference via VLLM 0.6.3.post1

### 1.3 Stopping Criterion

- AIC decides stop/no-stop per iteration
- Max iterations: recommended 3 (tested at 1, 3, 5; performance peaks at 3)
- Query log tracking to avoid duplicate retrieval

## 2. Results (real benchmark numbers)

All experiments use Llama3-8b as default model, BM25 retriever for single/multi-hop, GTR-XXL for long-form ASQA.

|---------|------|--------|-----|-------------|------------|-----------|-----------|
| SQuAD | single-hop | acc | 12.6 | 30.4 | 33.6 (ReAct) | 33.0 (Ada-RAG) | **34.6** |
| NaturalQuestions | single-hop | acc | 24.0 | 33.2 | 37.9 (Self-RAG) | 44.6 (Ada-RAG) | **44.2** |

**Best performer:** Amber with Qwen2-7b achieves 56.0% acc on 2WikiMQA, 52.6% on HotpotQA, 49.7% str-em on ASQA.

### 2.2 Classifier Performance (Figure 2)

- Both Qwen2-7b and Llama3-8b fine-tuned filters achieve **>90% accuracy** in classifying useful retrieved passages
- Successfully exclude **>40%** of negative/irrelevant retrieved knowledge

## 3. Trade-offs

| Win | Loss |
|-----|------|
| +10-30% accuracy over Vanilla RAG on multi-hop QA | Multiple LLM calls per query (Reviewer + Challenger + Refiner + AIC evaluation) |
| Outperforms all adaptive RAG baselines (Adaptive-RAG, FLARE, ReAct, Self-RAG) | Requires fine-tuning of separate MCF models (2 models: chunk-level + sentence-level) |
| >90% classifier accuracy with >40% negative passage elimination | Substantial training data construction overhead (GPT-4 labeling + NLI dataset creation) |
| Memory integration across retrieval steps prevents isolated retrieval problem | Answering each question takes more time than vanilla/single-shot approaches |
| Generalizable across 3 LLM families (Qwen2-7b, Llama3-8b, GPT-3.5) | Performance gap between models: Qwen2-7b significantly outperforms Llama3-8b on multi-hop (56.0 vs 43.8 acc on 2WikiMQA) |
| Simple training strategy compared to Self-RAG's multi-label classification | Only tested on QA tasks — unknown generalization to other RAG domains |

## 4. Design Rationale

The authors identify three failure modes in prior RAG systems:
1. **Isolated retrieval:** each retrieval step operates independently without summarizing memory across steps
2. **No validity checking:** LLMs do not actively evaluate whether retrieved information is actually useful before reasoning
3. **Noise from redundant content:** effective parts within retrieved segments are few; excessive redundancy obscures important details

Their approach choices:
- **Multi-agent memory (AMU)** over simple concatenation: three-role debate (Reviewer/Challenger/Refiner) ensures memory is critiqued from multiple angles before acceptance, inspired by multi-agent collaboration literature
- **Greedy collection-then-filter** over confidence-based retrieval (like FLARE): first gather extensively, then assess incorporation — avoids LLM overconfidence biasing retrieval decisions
- **Two-level filtering (MCF)** over single-level: chunk-level irrelevance and sentence-level irrelevance are distinct problems requiring separate handling; NLI framing for chunk relevance is more systematic than heuristic-based filtering

---

## 5. Limitations & Failure Modes

1. **Computational cost:** Multiple fine-tuning steps required (chunk classifier + sentence extractor), demanding substantial data collection, compute, and time
2. **Latency:** Multiple LLM accesses per query (3-agent AMU + AIC evaluation per iteration, max 3 iterations) — each question takes significantly longer than vanilla RAG
3. **Model sensitivity:** Performance varies substantially by base LLM — Qwen2-7b achieves 56.0 vs Llama3-8b's 43.8 on 2WikiMQA (same framework, 28% difference)
4. **Domain scope:** Only tested on QA (single-hop, multi-hop, long-form) — no results for dialogue, summarization, or code generation RAG tasks
5. **Fixed retriever:** Only BM25 and GTR-XXL tested — no dense retriever experiments for multi-hop, no evaluation with modern embedding models
6. **No failure analysis:** Paper lacks qualitative error analysis showing when/why the system still produces wrong answers despite the memory mechanism
7. **No real-time guarantees:** Iterative multi-agent loop with LLM calls is incompatible with sub-second latency requirements

## 6. Transfer to Lyra

**The one idea:** The three-agent memory updater (Reviewer/Challenger/Refiner) pattern — where retrieved information is not directly appended but instead debated and refined through multi-role critique before acceptance into working memory — is directly transferable to Lyra's context assembly pipeline. Rather than concatenating retrieved chunks into context, Lyra could use a lightweight multi-agent critique loop to filter, integrate, and condense retrieved knowledge into a single coherent memory note before passing it to the reasoning engine.

**Workstream:** §4.2 (Memory & Context Assembly) — this directly feeds the memory subsystem's need for smarter context condensation.

**Assessment:**
- **Impact:** 4 — multi-agent critique of retrieved context could significantly improve Lyra's answer quality on multi-hop queries, reducing hallucination from irrelevant retrieval
- **Effort:** 4 — requires implementing the three-agent dialogue pattern, prompt engineering for Reviewer/Challenger/Refiner roles, and integration with existing retrieval pipeline; 2-3 weeks of focused development
- **Tier:** **investigate** — promising but computationally expensive per query; should prototype and benchmark against simpler filtering approaches before full commitment
