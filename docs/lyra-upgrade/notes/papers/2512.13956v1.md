## 1. Mechanism (step-by-step)

The AOI (AI-Oriented Operations) framework orchestrates three specialized agents with an LLM-based Context Compressor and a three-layer memory architecture to automate IT operations.

### 1.1 Observer Agent (Central Coordinator)

**Task Decomposition (Algorithm 1):** When a complex task τ arrives, the Observer evaluates its complexity C(τ). If C(τ) > θ_complex, τ is hierarchically decomposed into atomic subtasks {τ₁, τ₂, ..., τₘ}. Each subtask is typed as `probe` (information gathering) or `execute` (system modification), assigned resource estimates R(τᵢ), and prioritized P(τᵢ) via dependency analysis. Simple tasks are enqueued directly.

**Dynamic Scheduling (Equation 2):**

```
Schedule(t) = argmax_{a ∈ {probe, execute}} E[Reward(a, X(t), C(t))]
```

- Probe reward = expected information gain (reduction in system state uncertainty)
- Execute reward = estimated progress toward target state X*
- Optimal exploration-exploitation ratio: λ = 0.35

**Global Objective (Equation 1):**

```
J(A) = α·T_completion + β·C_resource + γ·R_risk
```

Where T_completion = MTTR, C_resource = compute/network overhead, R_risk = operational risk score of SLA violations or system instability. α, β, γ are weighting coefficients.

### 1.2 Probe Agent (Read-Only Safety Enforcer)

**Safety-by-Design:** Operates under strict least-privilege:
- **Whitelist:** {SELECT, SHOW, DESCRIBE, GET, LIST, READ}
- **Blacklist:** {DELETE, UPDATE, INSERT, DROP, ALTER, TRUNCATE}
- File ops: read-only mode only
- Network ops: query-type requests only

**Safe Information Probing (Algorithm 2):** Generate probe script → Validate safety → If safe, execute each command sequentially in read-only mode → Log errors, continue with remaining commands → If unsafe, reject and request revision → Store raw output in memory layer 1.

### 1.3 Executor Agent (Conservative System Modification)

**Checkpoint-Rollback Pattern (Algorithm 3):** Create full-system checkpoint → Generate execution plan with pre-execution validation and dependency checks → For each action: optionally query Probe for current state, update parameters, execute, validate result → On critical failure: instant rollback to checkpoint → Store results in memory layer 1.

### 1.4 LLM-Based Context Compressor (Algorithm 4)

**Sliding Window Compression (Equation 3):**

```
Window_i = [start_i, start_i + window_size]
start_i = i × (window_size × overlap_ratio)
```

With `overlap_ratio = 0.5` to prevent boundary information loss. Optimal window = 768 tokens.

**Compression Pipeline:**
1. Split raw context into sliding windows {W₁, W₂, ..., Wₖ}
2. For each window: LLM extracts CriticalInfo (fault signatures, error codes, performance anomalies)
3. LLM summarizes (Wᵢ, I_critical) → summary Sᵢ
4. Merge overlapping summaries: C_merged ← MergeOverlaps(C_compressed)
5. If compression ratio > target: secondary compression pass

### 1.5 Three-Layer Memory Architecture

| Layer | Content | Retention | Fed By | Queried By |
|-------|---------|-----------|--------|------------|
| L1: Raw Context Storage | Unprocessed probe/executor outputs | 24 hours | Probe, Executor | Context Compressor |
| L2: Task Queue Management | Structured execution instructions | Lifecycle-managed | Observer | Executor |
| L3: Compressed Context Cache | LLM-processed strategic intelligence | 7 days | Context Compressor | Observer |

**Complexity:** Time O(n·w), Space O(k·w) where n=context length, w=window size, k=overlapping windows.

### Implementation Stack
- Agents: Python 3.9, FastAPI, containerized microservices
- LLM Backend: Fine-tuned GPT-4 API (2.3s avg latency per compression)
- Memory: Redis Cluster (distributed, auto-failover, persistent)
- Safety Verification: TLA+ formal specifications + runtime safety rules
- Infrastructure: 8× AWS EC2 c5.4xlarge (16 vCPU, 32GB RAM), 10 Gbps, Kubernetes 1.24

## 3. Trade-offs (wins vs loses)

| Win | Lose |
|-----|------|
| 34.4% MTTR reduction over best baseline | External GPT-4 API dependency (2.3s latency per compression, cost, network dependency) |
| 72.4% context compression with 92.8% info retention | Compression degrades performance for unprecedented failure modes (training corpus bias) |
| 96.7% system safety score via read-only Probe + checkpointing | Conservative execution adds latency from checkpointing overhead on every plan |
| Agent specialization (Observer/Probe/Executor) enables near-linear scalability (0.93 SI) | Inter-agent communication overhead increases with task count; 50 tasks shows 31.2 min MTTR vs 21.6 at single task |
| Dynamic scheduling (λ=0.35) outperforms static strategies | Tuning λ requires domain-specific calibration per environment |
| 3-layer memory with 7-day compressed cache enables cross-incident learning | Longer memory retention (120h) adds resource consumption with minimal TSR gain (+3.5% at 72h vs +minimal at 120h) |
| Read-only Probe eliminates destructive information gathering | Whitelist/blacklist approach brittle to novel command types; requires manual maintenance |

## 4. Design Rationale (why this approach)

1. **Agent Specialization over Monolithic LLM:** The authors argue that a single LLM agent suffers from "lost in the middle" context degradation and cannot simultaneously handle safe exploration AND system modification. Three specialized agents with clear role boundaries (Observer coordinates, Probe reads safely, Executor writes with checkpoints) provide inherent safety guarantees impossible in monolithic designs. Ablation confirms: single-agent TSR is 9.6% lower.

2. **LLM-based over Statistical Compression:** Traditional keyword/statistical compression loses semantic relationships (e.g., causal chains between error patterns). The LLM's semantic understanding preserves operational narratives — error patterns linked to resource thresholds linked to root causes — that statistical methods flatten. Ablation shows Context Compressor is the single most important component (5.7% TSR drop without it).

3. **Sliding Window over Chunked Compression:** 50% overlap prevents information loss at window boundaries where critical causal chains might be severed. Window_i and Window_{i+1} share 384 tokens (at 768 token window), ensuring fault signatures crossing boundaries are preserved in both summaries.

4. **Exploration-Exploitation Balance (λ=0.35):** Pure exploitation (λ→0) wastes time on wrong fixes without diagnosis; pure exploration (λ→1) never executes. The 0.35 ratio means ~35% of scheduling decisions favor probing over execution, empirically optimal for the tested fault types.

5. **Three-Layer Memory over Single Store:** Raw layer (24h) provides high-fidelity traceability for current incidents. Task Queue provides structured execution state. Compressed layer (7d) enables cross-incident pattern learning without raw data bloat. Separation prevents the Observer from drowning in 24h of raw logs during strategic decisions.

6. **TLA+ Formal Verification:** Runtime safety rules alone are insufficient for distributed systems. TLA+ model checking verifies deadlock-freedom and safety invariants at design time, complementing runtime whitelist enforcement.

## 5. Limitations & Failure Modes

### Explicit Limitations (from paper)

1. **LLM Service Dependency:** GPT-4 API introduces 2.3s latency per compression operation, and external service dependency unacceptable for latency-critical environments.
2. **Training Data Coverage:** Performance tightly coupled to quality and coverage of training scenarios; novel/unseen hybrid fault types degrade accuracy.
3. **Computational Overhead:** Context compression and multi-agent coordination incur additional overhead vs simpler approaches.
4. **Unprecedented Failures:** Limited capability handling completely novel failure modes not present in training corpus.

### Observed Failure Modes (from paper case studies)

5. **Rapid Propagation (<2s):** AOI cannot react to failures propagating faster than its Agent+LLM loop latency.
6. **Unseen Hybrid Faults:** Combinations of fault types absent from training corpus cause misclassification.
7. **GPT Latency Under Load:** Extreme operational load causes compression latency to pile up, creating temporary decision delays — a cascading bottleneck.

### Critical Integrity Concern

8. **Synthetic Cross-Dataset Claims:** Table IV self-discloses that cross-dataset numbers are "synthetic for manuscript demonstration." The HDFS, BGL, and OpenStack results cannot be trusted as they were apparently never actually measured. This is a severe credibility issue that undermines the paper's real-world applicability claims.

### Unaddressed Limitations

9. No open-source LLM alternative evaluated (proprietary GPT-4 lock-in).
10. No cost analysis provided for GPT-4 API usage at scale.
11. No adversarial evaluation of the safety verifier (deliberately malicious plans).
12. Only 50 fault types covered; real production environments have orders of magnitude more.
13. Single cloud provider (AWS); no multi-cloud or on-prem evaluation.
14. No human-in-the-loop evaluation; assumes full autonomy without measuring human override rate.

## 6. Transfer to Lyra

### The ONE Transferable Idea

**Three-Layer Memory Architecture with LLM-Based Sliding-Window Context Compression.** Lyra's agents generate enormous context volumes across long multi-turn sessions — debugging traces, tool outputs, reasoning chains, memory writes. AOI's pattern of separating memory into Raw (short-term, 24h retention for traceability), Structured Task Queue (current execution state), and Compressed Semantic Cache (7-day retention of LLM-extracted strategic intelligence) maps directly to Lyra's context management bottleneck. The 50%-overlap sliding window compression that preserves 92.8% of critical information while achieving 72.4% compression ratio provides a concrete algorithm for Lyra's context window management when agents approach the 200K token limit.

### Workstream Route: §4.2 (Memory & Context Architecture)

This feeds directly into Lyra's L2/L3 memory layer design — specifically the compressed semantic cache layer that enables cross-session pattern reuse without raw data bloat.
