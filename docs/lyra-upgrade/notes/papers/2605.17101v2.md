# SEMA-RAG: A Self-Evolving Multi-Agent Retrieval-Augmented Generation Framework for Medical Reasoning

**Authors:** Yongfeng Huang (CUHK), Ruiying Chen (Wuhan UT), James Cheng (CUHK)
**Venue:** arXiv preprint, May 2025
**arXiv ID:** 2605.17101v2

---

## 1. Mechanism

SEMA-RAG decomposes medical RAG into a three-agent pipeline that mirrors clinical workflow — interpretation → exploration → adjudication — replacing the single-round, monolithic retrieval paradigm with task-decoupled, sufficiency-driven iterative retrieval.

### Step-by-Step Algorithm

**Phase 1: I-Agent — Clinical Schema Interpreter**

Given an unstructured medical question `Q`, I-Agent produces a structured Clinical Schema tuple:

```
Q′ = ⟨oint, oent, ocons, qinit⟩ = Agent_I(Pmt_I, Q)
```

Where:
- `oint` — clinical intent (diagnosis, treatment, dosage, etc.)
- `oent` — core medical entities (diseases, drugs, findings)
- `ocons` — clinical constraints (time course, demographics, comorbidities, severity, contraindications)
- `qinit` — a concise, neutral, search-oriented initial query

The schema is linearized for dense retrieval via a parameter-free concatenation:

```
q̂_init = Linearize(Q′) = Concat(qinit, ⊕, oint, ⊕, oent, ⊕, ocons)
```

This makes clinically important but implicit constraints visible to the retriever, reducing semantic drift. `Q′` is retained as the clinical anchor for downstream coordination.

**Phase 2: E-Agent — Self-Evolving Explorer**

E-Agent implements a sufficiency-gated iterative retrieval loop:

**Initialization:**
- `Q_1 = {q̂_init}` (initial query set)
- `C_0 = ∅` (empty evidence set)
- Parameters: `T_max = 2`, `k = 16`, `m = 3`

**Retrieval step (round t):**
```
TopK(q) = Top-k_{D∈C} ⟨Eqry(q), Edoc(D)⟩
```

Where `Eqry` and `Edoc` are frozen MedCPT dual-encoder embeddings, and similarity is cosine/inner product over FAISS-indexed Textbooks + StatPearls corpus.

**Evidence accumulation:**
```
D_t = ∪_{q∈Q_t} TopK(q)
C_t = C_{t-1} ∪ {D_i ∈ D_t : ID(D_i) ∉ IDs(C_{t-1})}
```

Documents are deduplicated by deterministic ID.

**Sufficiency assessment:**
```
[s_t, g_t, Q_{t+1}] = Agent_E(Pmt_E, [Q′, Q_t, C_t])
```

Where:
- `s_t ∈ {0, 1}` — evidence sufficiency flag
- `g_t` — concrete gap description (if insufficient)
- `Q_{t+1} = {q¹_{t+1}, ..., q^m_{t+1}}` — up to m=3 targeted follow-up queries

**Termination conditions:**
1. `s_t = 1` (evidence sufficient)
2. `t = T_max` (max rounds reached)
3. Stagnation: `Q_{t+1} = ∅`

Upon termination, the closed evidence set and trajectory are recorded:
```
C* = C_T, τ = {[Q_1, C_1], ..., [Q_T, C_T]}
```

**Phase 3: A-Agent — Evidence Arbiter**

Two sub-phases:

**3a. Evidence Adjudication:**
```
R = Agent_A(Pmt_adj, [Q, C*, S*])
```

Where `S* = {(ID(D_i), D_i) | D_i ∈ C*}` preserves source traceability. The report `R` organizes:
- Supporting evidence claims with source IDs
- Conflicting or limiting evidence
- An integrated synthesis statement

**3b. Evidence-Grounded Answering:**
```
ỹ = Agent_A(Pmt_ans, [Q, R])
```

Final answer is selected from candidate set `Y` grounded solely in the traceable evidence report.

### Control Flow (Pseudocode)

```
function SEMA_RAG(Q):
    // Phase 1: Interpret
    Q′ = I_Agent.interpret(Q)
    q̂_init = linearize(Q′)
    
    // Phase 2: Explore
    Q_1 = {q̂_init}, C_0 = ∅, t = 1
    while t ≤ T_max:
        D_t = ∪_{q∈Q_t} retrieve_topk(q, k=16)
        C_t = deduplicate(C_{t-1} ∪ D_t)
        s_t, g_t, Q_{t+1} = E_Agent.assess(Q′, Q_t, C_t)
        if s_t == 1 or Q_{t+1} == ∅: break
        t += 1
    
    // Phase 3: Adjudicate
    R = A_Agent.adjudicate(Q, C_t, source_ids)
    ỹ = A_Agent.answer(Q, R)
    return ỹ
```

### Key Design Decisions

| Decision | Value |
|----------|-------|
| Max retrieval rounds (T_max) | 2 |
| Documents per query (k) | 16 |
| Max follow-up queries (m) | 3 |
| Retriever | MedCPT (dense dual-encoder, FAISS) |
| Corpus | Textbooks + StatPearls |
| I/E-Agent temperature | 1.0 (exploration) |
| A-Agent temperature | 0.0 (deterministic answer) |

## 3. Trade-offs

| Win | Lose |
|-----|------|
| +6.46 avg accuracy over strongest single-round baseline, consistently across 5 backbones | 2-3× more LLM API calls per question (I-Agent + E-Agent × T rounds + A-Agent × 2 phases) |
| Largest gains on hard benchmarks (MedQA-US: +12.81, PubMedQA*: +8.60) where premature commitment is most costly | Sufficiency assessment itself is an LLM meta-cognition task — can misjudge, causing early termination |
| Task decoupling makes each agent simpler and easier to prompt-engineer than one monolithic reasoning chain | T_max=2 caps exploration depth; some questions need deeper evidence chains |
| Self-evolving loop works across retriever backends (domain MedCPT → general qwen3-embedding) | Temperature=1.0 for I/E agents introduces non-determinism; some variation across runs |
| Benefits persist on small models (gemma3:4b) — not dependent on frontier-scale LLMs | Domain-specific components (medical corpus, MedCPT encoder) create an adaptation tax for other domains |
| Generalizes beyond discrete QA to open-ended generation and multi-turn dialogue with minimal A-Agent adaptation | Evidence report generation adds latency before final answer (sequential dependency) |

**Cost model:** Each question consumes ~(1 + T) retrieval rounds × k passages + (1 + T + 2) LLM calls. With T_max=2 and typical T=1.5, this is roughly 3-4 LLM calls per question vs 1-2 for single-round RAG.

## 4. Design Rationale

The authors diagnose the core problem in medical RAG as "cognitive overload" — forcing a single reasoning chain to simultaneously interpret clinical questions, explore evidence spaces, and adjudicate conflicting evidence. This overload causes two structural failures: (a) poor question-to-query translation lacking clinical semantics, and (b) no iterative sufficiency feedback, preventing reliable evidence chains.

**Why decouple into three agents?** Clinical reasoning is naturally phased — clinicians first frame the question, then gather evidence iteratively (assessing sufficiency at each step), then integrate findings. SEMA-RAG mirrors this phased workflow. The decoupling allows each agent to be optimized via role-specific prompts (Figures 4-8 in the paper) without the interference that occurs when one model must context-switch between tasks.

**Why self-evolving (intra-test-time) rather than static multi-round?** Fixed multi-round pipelines issue a predetermined number of queries regardless of evidence quality. The sufficiency gate (`s_t`) makes the loop adaptive — it stops early when evidence is adequate and only issues follow-up queries targeting concrete gaps (`g_t`). This prevents both premature commitment (the problem with single-round) and wasteful over-retrieval (the risk with naive multi-round).

**Why A-Agent as a separate adjudicator?** Separating evidence synthesis from answer selection prevents the model from anchoring on a candidate answer before fully integrating evidence. The two-phase adjudication (report first, then answer) creates a traceable audit trail that would be impossible in end-to-end generation.

## 5. Limitations & Failure Modes

1. **Class-level vs option-level sufficiency (critical):** E-Agent's sufficiency check stops when the correct *class* is identified (e.g., "Gram-negative"), but this may be insufficient to discriminate among options within that class (e.g., rod vs. coccobacillus). The failure case in Table 7 (MedQA-US Q0060) shows the system correctly ruling out Gram-positive distractors but then committing to the wrong Gram-negative option because no option-separating evidence was retrieved.

2. **T_max=2 caps exploration depth:** Complex multi-hop clinical cases requiring 3+ evidence-linking steps cannot complete their chains. The fixed budget trades coverage for cost.

3. **Sufficiency assessment as meta-cognition bottleneck:** The LLM must accurately judge whether evidence is sufficient — a meta-cognitive task that itself can fail. If E-Agent incorrectly declares sufficiency=1, the pipeline commits with incomplete evidence with no recovery path.

4. **Temperature-based non-determinism:** I-Agent and E-Agent use temperature=1.0, meaning different runs on the same question may produce different schemas and query trajectories.

5. **Domain adaptation tax:** The MedCPT retriever and medical corpus are domain-specific. Transferring to non-medical domains requires retriever replacement and corpus curation.

6. **Sequential agent dependency:** A-Agent's evidence report must complete before answer selection begins; there is no parallelization within a single question.

## 6. Transfer to Lyra

### The One Idea: Sufficiency-Gated Iterative Retrieval

The E-Agent's **sufficiency-driven self-evolving retrieval loop** is directly transferable to Lyra's research architecture. The core pattern — (1) retrieve evidence, (2) assess whether it sufficiently covers all query dimensions, (3) if not, identify the single most important missing gap, (4) generate targeted follow-up queries against that gap, (5) loop until sufficient — replaces Lyra's current single-shot RAG with an adaptive, convergent evidence-gathering process.

### Workstream Route: **§4.2 (Context/Retrieval Engine)** — primary fit

The pattern also strengthens **§4.6 (Reliability/Grounding)** because the sufficiency gate acts as a verifiability checkpoint before any output is produced, and A-Agent's traceable evidence report creates a natural audit trail.

### Scoring

| Dimension | Value | Rationale |
|-----------|-------|-----------|
| **Impact** | 4 | Adaptive evidence-gathering addresses Lyra's core research quality challenge; applicable across all RAG-dependent features |
| **Effort** | 3 | Requires prompt-engineering the sufficiency assessor, adding a retry loop around existing retrieval, and implementing gap-targeted query generation. No new infrastructure beyond what `lyra-deep-research-workflow.js` already contemplates. |
| **Tier** | **breakthrough** | The pattern is directly portable beyond medicine — sufficiency-gated loops apply to any domain where retrieval completeness matters. The 3-agent decomposition (interpreter → explorer → arbiter) maps naturally to Lyra's research query → evidence gathering → synthesis pipeline. |

### Concrete Implementation Sketch for Lyra

```
// LyraSufficiencyLoop (inspired by E-Agent)
async function gatherSufficientEvidence(query, maxRounds=3) {
    let evidence = [];
    let queries = [query];
    for (let t = 0; t < maxRounds; t++) {
        const roundResults = await parallelRetrieve(queries, k=16);
        evidence = deduplicate([...evidence, ...roundResults]);
        const {sufficient, gap} = await assessSufficiency(query, evidence);
        if (sufficient) break;
        queries = await generateGapQueries(query, gap, m=3);
    }
    return evidence;
}
```
