## 1. Mechanism (step-by-step)

MetaClaw is a **continual meta-learning framework** that jointly maintains a meta-model M = (θ, S) where θ is the base LLM policy parameters and S = {s₁, s₂, ..., s_K} is a library of reusable skill instructions. It evolves M through two complementary loops operating at different timescales:

### Loop 1: Skill-Driven Fast Adaptation (seconds, gradient-free, zero downtime)

1. **Execute task:** For incoming task τ, retrieve relevant skills via embedding-based cosine similarity: `S_τ ← Retrieve(S_g, τ)`, then collect trajectory `ξ_i ← Execute(π_θ(· | τ, S_τ))`.

2. **Detect failure:** If trajectory ξ_i reveals a failure mode, add (τ_i, ξ_i) to the support set `D^sup_g`. Successful trajectories go to the RL buffer B.

3. **Skill evolution** (when `|D^sup_g| ≥ threshold`):
   - An LLM-based skill evolver E analyzes the failure trajectories and synthesizes new behavioral instructions:
     ```
     S_{g+1} = S_g ∪ E(S_g, D^sup_g)
     ```
   - The skill generation counter g increments.
   - New skills take effect immediately via prompt injection with **zero service downtime** — no weight modification needed.

4. **Support-query separation:** When g advances, all samples with version ≤ g are flushed from the RL buffer B. This prevents stale reward contamination (trajectories collected under old skill context carrying rewards that don't reflect current agent behavior).

### Loop 2: Opportunistic Policy Optimization (minutes to hours, gradient-based)

1. **Accumulate query data:** After skill adaptation, the agent continues serving tasks. Post-adaptation trajectories (query set `D^qry_{g+1}`) accumulate in the RL buffer B.

2. **Idle detection via OMLS:** The Opportunistic Meta-Learning Scheduler monitors three signals:
   - **Sleep window:** Configurable hours (e.g., 23:00–07:00)
   - **System inactivity:** OS keyboard/mouse idle timer (e.g., macOS `ioreg HIDIdleTime`; default threshold 30 min)
   - **Calendar-aware:** Google Calendar API queries — if user is in a meeting, training window opens

3. **Trigger RL training** (when OMLS detects idle + |B| ≥ batch size):
   - Policy update via GRPO with a Process Reward Model (PRM):
     ```
     θ_{t+1} = θ_t + α∇_θ E_{(τ,ξ,g')∼B} [R(π_θ(· | τ, S_{g'}))]
     ```
   - Uses **cloud LoRA fine-tuning** (no local GPU required; proxy-based architecture).
   - Trainer supports pause/resume across fragmented idle windows via mid-batch checkpointing.

4. **Hot-swap weights:** After training completes, the updated θ replaces the active model weights.

### Key Data Structure: Skill Generation Versioning

Every trajectory is stamped with its skill generation g at collection time. The strict separation of support data (pre-adaptation, consumed by skill evolver) from query data (post-adaptation, used for RL) is the core mechanism that prevents the meta-learning objective from collapsing. Without versioning, RL would optimize θ against rewards conditioned on a skill context that no longer exists.

### Virtuous Cycle

Better θ → more informative failure trajectories → richer skill synthesis → higher-reward trajectories → better θ. This creates a meta-learning effect: the system learns to become better at adapting.

## 2. Results (real benchmark numbers)

### MetaClaw-Bench (934 questions, 44 simulated workdays)

**Part I (30 workdays, 346 questions):**

| Model | Condition | Accuracy | File-Check Completion |
|-------|-----------|----------|----------------------|
| GPT-5.2 | Baseline | 41.1% | 14.7% |
| GPT-5.2 | +Skills | 44.0% (+7.1% rel) | 17.1% |
| Kimi-K2.5 | Baseline | 21.4% | 2.0% |
| Kimi-K2.5 | +Skills | 28.3% (+32.2% rel) | 2.0% |
| Kimi-K2.5 | Full | **40.6%** | **16.5%** (8.25×) |

**Part II (14 workdays, 588 questions):**

| Model | Condition | Accuracy | File-Check Completion |
|-------|-----------|----------|----------------------|
| GPT-5.2 | Baseline | 44.9% | 58.4% |
| GPT-5.2 | +Skills | 49.1% (+9.4% rel) | 67.5% |
| Kimi-K2.5 | Baseline | 21.1% | 18.2% |
| Kimi-K2.5 | +Skills | 26.9% (+27.5% rel) | 33.8% |
| Kimi-K2.5 | Full | **39.6%** | **51.9%** (+185% rel) |

### AutoResearchClaw (23-stage autonomous research pipeline, skills-only):

| Metric | Baseline | +Skills | Change |
|--------|----------|---------|--------|
| Stage retry rate | 10.5% | 7.9% | ↓24.8% |
| Refine cycle count | 2.0 | 1.2 | ↓40.0% |
| Pipeline stage completion | 18/19 | 19/19 | ↑5.3% |
| Composite robustness score | 0.714 | 0.845 | ↑18.3% |

### Key trends:
- Kimi-K2.5 Full (40.6%) nearly closes the gap with GPT-5.2 Baseline (41.1%)
- RL training inflection point at day 8 on Part II; file-check passes escalate from ~9% (days 1-4) to 100% (days 12, 14)
- Per-day accuracy peaks at ~0.8 for Full around days 19-20 in mid-range difficulty
- Skills-only lifts multi-choice but not file-check; Full reverses this pattern

## 3. Trade-offs

| Win | Cost / Loss |
|-----|-------------|
| Skills take effect instantly with zero service downtime | Skill library grows monotonically (no pruning/forgetting mechanism) |
| RL policy optimization yields 8.25× completion gains for weak models | RL training requires idle windows; may take days to accumulate sufficient query data |
| No local GPU needed (cloud LoRA + proxy architecture) | Requires configured cloud LoRA training endpoint per backbone model |
| Stronger models (GPT-5.2) still benefit (+7-9% relative) | Gains diminish for already-capable models — diminishing returns on strong baselines |
| Cross-domain generalization (CLI skills transfer to research pipeline) | Skills are authored as natural-language heuristics — no formal verification of correctness |
| Calendar-aware scheduling anticipates idle periods proactively | OMLS depends on user configuration (sleep hours, calendar access); may not suit all deployment environments |
| Support-query separation prevents stale reward contamination | Versioning flushes all pre-adaptation samples — potentially discards useful data from near-threshold trajectories |
| Gradient-free skill adaptation avoids unstable RL early in deployment | Skill evolver is itself an LLM call — introduces token cost and latency per adaptation step |

## 4. Design Rationale

The core insight is that **behavioral heuristics and policy-level capabilities operate at fundamentally different timescales** and are naturally complementary. A single failure can teach "always backup before modifying" (seconds, prompt-level), but reliably executing complex multi-step file operations requires gradient-based policy refinement over many trajectories (hours). Prior work treated these as separate problems: memory/skill systems accumulated static artifacts without weight coordination, while RL systems optimized against fixed reward signals without updating behavioral context.

The dual meta-parameter formulation M = (θ, S) with explicit support-query separation is the architectural innovation. It encodes the meta-learning insight that **what fails before adaptation should not train what succeeds after adaptation**. The proxy-based cloud LoRA architecture was chosen to make the system deployable without local GPU infrastructure, lowering the barrier for personal agent platforms like OpenClaw that serve 20+ messaging channels.

## 5. Limitations & Failure Modes

1. **Benchmark is authored, not organic:** MetaClaw-Bench is a simulated environment with authored tasks, not real user sessions. The 934 questions over 44 days may not reflect actual production task distributions, drift patterns, or failure modes.

2. **OMLS deployment constraints:** Idle-window detection requires user configuration (sleep schedule, calendar API access, OS idle timer polling). Users without consistent schedules, those who decline calendar access, or shared machines may not provide reliable idle windows.

3. **Only two backbone models evaluated:** Results are shown for GPT-5.2 and Kimi-K2.5 only. Generalization to other model families (Claude, Gemini, open-weight models) is unverified.

4. **Monotonic skill growth:** The skill library S grows without bound (no pruning, deduplication, or forgetting). Skill collision/contradiction is not addressed.

5. **Cloud dependency:** Full pipeline requires a cloud LoRA training endpoint. Users without API access to trainable model endpoints (e.g., many proprietary API-only models) cannot use the RL component.

6. **Late-day convergence:** All conditions converge to similarly low performance on the hardest tasks (days 25-30), indicating accumulated skills and policy updates hit a ceiling that only stronger base model weights can break.

7. **RL causes multi-choice regression:** MetaClaw (Full) slightly decreases multi-choice accuracy as the policy shifts toward file-execution behavior — a narrow-specialization risk.

## 6. Transfer to Lyra

### The ONE transferable idea

**Dual-timescale continual meta-learning with explicit support-query separation.** Lyra should maintain a co-evolving pair (base policy weights, reusable skill/instruction library) where fast prompt-level adaptation handles immediate failure recovery and slow RL-based optimization refines the underlying policy during idle periods. The versioning mechanism that stamps every trajectory with its skill generation and flushes stale samples is the critical engineering detail that prevents the learning loop from collapsing — without it, RL gradients optimize against a behavioral context that no longer exists.

### Workstream route: **§4.2 — Memory & Learning**

This feeds directly into Lyra's Memory and Learning subsystem by providing a principled architecture for continuous agent improvement that distinguishes between two forms of knowledge (fast behavioral heuristics vs. slow policy refinement) and coordinates them through a versioned data pipeline.
