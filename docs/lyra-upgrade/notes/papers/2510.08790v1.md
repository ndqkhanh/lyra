## 1. Mechanism (Step-by-Step)

COMPASS (Context-Organized Multi-Agent Planning and Strategy System) is a **hierarchical three-agent architecture** that separates tactical execution, strategic oversight, and context management into dedicated components. The core insight is that long-horizon agent failures stem from **context mismanagement**—as execution traces grow linearly O(t), critical evidence gets buried (context overflow) or lost (truncation), causing premature conclusions or blind persistence.

### Architecture: Three Specialized Agents

**Agent 1 — Main Agent (Tactical Executor):**
- Operates a standard ReAct-style think-act-observe loop
- At step t, receives a **dynamically refreshed compact context** `x_t` from the Context Manager (NOT the full history)
- Produces reasoning traces `r_t` and tool actions `a_t`, appending to trajectory `T_t`
- Does NOT monitor global progress itself — focuses solely on faithful tool execution

**Agent 2 — Meta-Thinker (Strategic Overseer):**
- Runs **asynchronously** alongside the Main Agent — does NOT block execution
- Monitors the trace queue `T_t` for anomalies: looping behavior, tool misuse, reasoning drift, completion signals
- Remains silent until triggered; upon detection issues one of five strategic decisions:
  - **PERSIST** — continue current plan (local error, refine search)
  - **PIVOT** — redirect strategy (global dead-end, switch data source)
  - **VERIFY** — pause for additional checks
  - **TERMINATE** — stop and return answer
- Operates on single-turn slices, not full traces → lightweight, low-latency

**Agent 3 — Context Manager (Context Controller):**
- After each Meta-Thinker intervention, **synthesizes a refreshed context** `x_{t+1}` from three sources:
  1. Persistent structured **notes** `n_t` (accumulated across all turns)
  2. Current reasoning **trajectory** `T_t` from Main Agent
  3. Meta-Thinker's **strategic signal** `decision_t`
- Output is a structured brief with 6 sections: Task restatement, Most-Recent Evidence, Critical Constraints & Corrections, Open Items, Next Actions, Tool Hints
- Appends key observations to the rolling note store: evidence, constraints, open items
- Typical output: ≤200-300 tokens

### Dual-Loop Algorithm (Algorithm 1)

```
Outer Loop (Strategic):
  For t = 0 to Tmax:
    1. x_t = ContextManager.SynthesizeContext(n_t, q)
    2. T_t = ExecuteTurn(MainAgent, MetaThinker, x_t, I_max)
       // Inner ReAct loop with async Meta-Thinker monitoring (Algorithm 2)
    3. decision = MetaThinker.GetDecision(T_t, x_t)
    4. If decision = STOP or t = Tmax-1: return ExtractAnswer(T_t, n_t)
    5. n_{t+1} = UpdateNotes(n_t, T_t, decision)  // append structured brief

Inner Loop (Tactical, Algorithm 2):
  For i = 0 to I_max:
    If MetaThinker.IsTriggered() or MainAgent.HasFinalAnswer(): break
    step = MainAgent.Execute(x, T, O)  // one tool call
    T.append(step)  // MetaThinker observes asynchronously
```

### Key Design Decisions:
- **Asynchronous monitoring**: Meta-Thinker does not block the Main Agent's execution — preserves fluidity of single-agent systems while adding oversight
- **Rolling note store**: Not a full history; only extracted evidence, constraints, and open items survive across turns → bounded memory
- **Explicit role/context separation**: Each agent has an isolated context window, preventing cross-contamination

### Extensions:

**Context-12B — Trained Context Manager:**
- SFT on Gemma-3-12B using 10,347 query-context pairs extracted from COMPASS rollouts across GAIA, SimpleQA, HotPotQA, GPQA, MMLU, MMLU-Pro
- Data filtering: retain 3-25 tool calls, upsample recovery sequences (2.3x), stratify by context complexity
- DPO fine-tuning with 8,200 preference pairs (4 candidates per trajectory, ranked by `score = 1{success} - 0.001 * tokens`)
- Training: 3,000 SFT steps on 4×A100 (80GB), then 6,000 DPO steps on 8×A100 (80GB)

**COMPASS-TTS — Test-Time Scaling:**
- Three sampling strategies:
  - **Full-PS**: n parallel full-pipeline runs → synthesizer aggregates
  - **MT-PS**: Only Meta-Thinker parallelized → merged into single plan
  - **CM-PS**: Only Context Manager parallelized → single context injected
- Sweet spot: n = 2-4 parallel samples

## 3. Trade-offs

| Win | Loss / Cost |
|-----|-------------|
| +20% relative accuracy over SAS baselines (GAIA: 16.8→35.4%) | ~2.2x token cost (185K vs ~85K for SAS baseline on BrowseComp) |
| Balanced strategic reasoning (PAR: 0.85, PVR: 0.48, CA: 0.88) vs SAS blind persistence (PAR: 0.92, PVR: 0.12) | Three-agent orchestration complexity (orchestration framework + prompt maintenance) |
| Asynchronous monitoring preserves SAS fluidity (no blocking) | Meta-Thinker operates on single-turn snapshots — may miss long-range patterns |
| Context-12B: 30% token reduction with DPO, comparable to Flash-level context management | Additional training pipeline needed (480 GPU-hrs, 10K+ examples) |
| COMPASS-TTS matches/exceeds established DeepResearch agents (BrowseComp: 72.1 vs 69.1) | Test-time scaling: Full-PS at n=8 uses ~8x tokens; sweet spot at n=2-4 |
| Model-agnostic architecture — works on Pro and Flash | Proprietary Gemini models used; open-source models "significantly underperform" per authors |
| Single-agent augmentation path (add thinking+context tools) gives incremental gains (29.8% GAIA) — COMPASS gives jump to 35.4% | Ablation shows removing Context Manager with Flash backend causes 212K token blowup from repeated context revisitation |

## 4. Design Rationale

**Why hierarchical 3-agent rather than monolithic SAS or full MAS?**
- Monolithic SAS suffers from context window overload — as |C_t| grows O(t), critical early evidence and constraints get "lost in the middle," causing premature conclusions and superficial reflection. SAS cannot self-correct reliably (Huang et al., 2024a).
- Full MAS achieves SOTA but relies on manually designed coordination pipelines and human-in-the-loop signals — brittle, unscalable, and domain-specific.
- COMPASS preserves the end-to-end autonomy of SAS while externalizing strategic reasoning and context curation into dedicated agents with **isolated context windows**. The Meta-Thinker's context is specifically curated to enable anomaly detection without being polluted by execution traces.

**Why asynchronous Meta-Thinker?**
- Synchronous oversight would block the Main Agent at every step, destroying the fluidity that makes SAS efficient.
- Prompt-caching (Gim et al., 2024) reduces Meta-Thinker latency further since it operates on single-turn slices.

**Why train Context-12B?**
- Context Manager is the most structured/deterministic component — "operates more like a summarizer than an open-ended reasoner" (§D.6) — making it the safest to distill into a smaller model.
- Larger models for context management are token-expensive and overkill for structured summarization.

## 5. Limitations and Failure Modes

1. **Benchmark scope is narrow**: Evaluation limited to QA-style agentic tasks (GAIA, BrowseComp, HLE) using search, browsing, and code execution tools. No testing in open-ended domains, multi-step task completion, or real-world deployment.

2. **Proprietary model dependency**: All primary results use Gemini 2.5 Pro/Flash. Authors explicitly note that "common open-source models currently underperform significantly" on these tasks, limiting reproducibility and generalizability.

3. **Context Manager over-compression risk**: Flash-based Context Manager showed token efficiency gains but also evidence of "excessive plan revision, triggering strategic interventions that extend execution" — compression can become a source of instability.

4. **Meta-Thinker blind spots**: Operates on single-turn snapshots; may miss long-range strategic patterns spanning many turns that are not captured in a single turn's trace.

5. **No dynamic role negotiation**: The three-agent topology is static. Agents cannot re-allocate responsibilities based on task difficulty or detected capability gaps.

6. **Human-in-the-loop not fully replaced**: While COMPASS automates strategic signals, the writing still references HITL as a baseline — suggesting COMPASS may still fail in ways human oversight would catch.

7. **COMPASS-TTS cost-accuracy plateau**: Full-PS gains plateau after n=4, suggesting diminishing returns from additional sampling — practical ceiling exists.

8. **No multi-turn RL training**: Post-training pipeline only targets Context Manager (distillation), not the Meta-Thinker or Main Agent — strategic reasoning relies entirely on in-context learning.

## 6. Transfer to Lyra

**The One Transferable Idea:** Explicit **context window management via a dedicated "Context Manager" that synthesizes structured briefs** (evidence, constraints, open items, next actions) from full execution histories, enabling bounded context size across long-horizon agent runs while preserving strategic continuity. This directly addresses Lyra's planned multi-turn orchestration where context accumulation across subtask handoffs will degrade reasoning quality. The 6-section brief template (Task, Evidence, Constraints, Open Items, Next Actions, Tool Hints) provides a concrete, proven output schema.

**Workstream Route:** **§4.2 — Agent Harness (Context & State Management subsystem)**
COMPASS is fundamentally about structured context curation in multi-agent settings. Lyra's agent harness needs a context compression layer between orchestration steps; COMPASS's Context Manager + rolling note store pattern is a direct architectural transfer with the added benefit that a smaller model (e.g., Gemma-3-12B equivalent) can be fine-tuned for this specific function via SFT+DPO distillation from a frontier teacher.

**Impact:** 4/5 — Context degradation is the leading cause of long-horizon agent failure; solving it enables reliable multi-turn operation.
**Effort:** 4/5 — Requires (a) designing prompt templates for Lyra-specific context briefs, (b) collecting training data by running Lyra rollouts with a frontier model as teacher, (c) SFT+DPO fine-tuning of a small context-management model (~480 GPU-hours), and (d) integration into Lyra's orchestration loop.
**Tier:** **Breakthrough** — This is not parity work; the structured context management pattern with an SFT'd compact model is directly architecture-shaping for Lyra's core reliability.
