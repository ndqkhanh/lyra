# FAMA: Failure-Aware Meta-Agentic Framework for Open-Source LLMs in Interactive Tool Use Environments

**Authors:** Amir Saeidi*, Venkatesh Mishra*, Souradeep Mukhopadhyay, Gaowen Liu, Ali Payani, Jayanth Srinivasa, Chitta Baral (*equal contribution)
**Affiliations:** Arizona State University, Cisco Research
**Venue:** arXiv:2604.25135v1 [cs.CL], 28 Apr 2026

## 1. Mechanism (step-by-step, equations, algorithms)

FAMA is a two-stage, training-free framework for improving open-source LLM agents in multi-turn conversational tool-use tasks.

**Pre-defined Agent Pool A:**
- Domain Constraints Extractor Agent (DCE) — extracts domain policies
- Tool Suggestion Agent (TSA) — suggests appropriate tools for tasks
- Tool Output Reformulator Agent (TOR) — reformats complex tool outputs
- Planner Agent — decomposes tasks into steps
- Decision Verifier Agent — verifies correctness of actions
- User Context Manager (Memory module) — maintains conversation history

**Pre-defined Error Categories E:**
1. **Domain Policy Violation (DCV):** agent performs actions forbidden by domain rules or skips required steps
2. **Wrong Retrieval from Complex Tool Outputs (WRCO):** fails to correctly extract information from structured tool responses
3. **Contextual Misinterpretation and Hallucination (CM):** misunderstands user intent despite correct word-level comprehension
4. **Incomplete Fulfillment or Early Stopping (IFU):** prematurely terminates or fails to complete all user requirements

**Algorithm 1: FAMA Framework**
```
1. Run baseline agent on all tasks T. Collect failure trajectories F.
2. For each failure (τ, ξ):
   a. For each error category e ∈ E:
      Run independent error analysis agent → o_{τ,e} (categorical decision + rationale)
   b. Concatenate all O_τ = {o_{τ,e}}
   c. Orchestrator Agent analyzes O_τ and full trajectory ξ → identifies primary failure error(s) Ê_τ
   d. Mitigation Agent conditions on Ê_τ and agent definitions A → selects optimal subset A*_τ ⊆ A
3. Re-execute tasks with only A*_τ agents providing context to tool-use agent
```

**Stage 1: Failure Analysis**
- |E| independent error analysis agents, each focused on a single error category
- Each produces: {violation: Yes/No, rationale: "..."}
- Orchestrator Agent takes all outputs + full trajectory → root cause analysis
  Example: {"root_cause_analysis": "The primary root cause of the task failure is the Domain Constraint Violation (DCV)."}

**Stage 2: Dynamic Agent Selection**
- Mitigation Agent takes: selected error categories + functional definitions of all agents in A
- Returns: minimal subset A* ⊆ A that addresses identified failures
- Example: {"agent_list": ["Domain Extractor Agent"]} — single agent, not full ensemble

**Stage 3: Context Injection**
- Selected agents inject targeted context into the tool-use agent's prior context before each decision step
- This is NOT multi-agent collaboration — agents operate independently and their outputs are concatenated as additional context

**Key Design Properties:**
- **Training-free:** No model fine-tuning required
- **Minimal agent selection:** Avoids context window bloat from full agent ensembles
- **Model-specific error profiles:** Different models get different agent subsets based on their actual failure patterns
- **Extensible:** New specialized agents can be added to A without changing orchestration logic

## 2. Results (real benchmark numbers with units)

Evaluate across 4 open-source models (Qwen3-4B-Inst, Qwen3-14B, Qwen3-32B, Qwen2.5-72B-Inst) on 3 benchmarks: τ-bench, τ-trait, ACEBench.

**τ-bench Results (Pass^1, averaged improvement over baselines):**

*Airline Domain (average Pass^1 across 4 models):*
- FAMA: 32.60% avg vs. ReAct: 26.30%, FC: 18.60%, IRMA: 29.30%
- FAMA improvement over best baseline: +4.63% (ReAct), +11.57% (FC), +5.27% (IRMA)

*Retail Domain (average Pass^1 across 4 models):*
- FAMA: 39.29% avg vs. ReAct: 30.97%, FC: 28.04%, IRMA: 30.76%
- FAMA improvement over best baseline: +5.30% (ReAct), +8.96% (FC), +6.15% (IRMA)

**Best individual model gains (Pass^1):**
- Qwen3-14B Airline: ReAct 18.40% → FAMA 36.80% (+18.40%, 2x improvement)
- Qwen3-4B Retail: ReAct 17.22% → FAMA 34.60% (+17.38%)
- Qwen2.5-72B Retail: ReAct 43.47% → FAMA 44.17% (+0.70%, returns diminish at scale)
- Qwen3-32B Retail: ReAct 38.00% → FAMA 40.50% (+2.50%)

**ACEBench Results (End-to-End Accuracy):**
- Qwen3-4B: Base 10.0% → FAMA-Base 16.7%, ReAct 10.0% → FAMA-ReAct 20.0%
- Qwen2.5-72B: Base 23.3% → FAMA-Base 50.0% (+26.7%, largest gain)
- Qwen3-32B: ReAct 13.3% → FAMA-ReAct 30.0% (+16.7%)

**τ-trait Results (Pass^1, Telecom + Telehealth):**
- Consistent FAMA advantage over IRMA across all models
- Best gain: Qwen3-14B Telecom ReAct 15.55% → FAMA 43.00% (+27.45%)
- Some cases FC outperforms FAMA at Pass^1 (e.g., Qwen3-4B Telehealth FC 34% vs FAMA 32%), but FC inconsistent across domains

**Failure Analysis (error distribution across all models):**
- Domain Constraint Violations: 15-55% of failures per model
- Contextual Misinterpretation: 35-61% of failures per model
- Most recommended agents: Memory module (highest count), DCE (second highest)

**Efficiency (Qwen3-32B):**
- Token overhead: ReAct 0%, IRMA 50-58%, FAMA ~30%
- Average latency: ReAct-non-thinking 60s/49s, FAMA 91s/57s, IRMA 150s/112s (Airline/Retail)

## 3. Trade-offs (wins vs loses)

**Wins:**
- Training-free: works with any off-the-shelf LLM without fine-tuning
- Model-specific adaptation: different models get different agent subsets based on their actual failure modes
- Consistent across benchmarks: improvements across τ-bench, τ-trait, ACEBench (3 different domains, 6+ sub-domains)
- Context efficiency: FAMA uses ~30% token overhead vs. 50-58% for full multi-agent (IRMA)
- Minimal agent sets: often just 1-2 agents needed (DCE + Memory for τ-bench, Planner + Verifier for ACEBench)
- Extensible: new error categories and specialized agents can be added without changing orchestration
- Strong on small models: largest relative gains on Qwen3-4B and Qwen3-14B

**Loses:**
- Predefined agent pool bounds effectiveness: cannot address failure modes with no corresponding agent in A
- No automatic agent synthesis: new failure patterns require manual agent design
- Stage 1 requires running baseline agent first → 2x execution cost for task set
- Error analysis depends on frontier model quality (GPT-4o/GPT-4.1-mini used as judgment agents)
- Diminishing returns on stronger models: Qwen2.5-72B gains only 0.70-4.5% on τ-bench
- Not tested on proprietary/frontier models (Claude, GPT-5) — unclear if failure patterns differ significantly
- Memory module is domain-dependent: optimal k (recent queries retained) varies (k=2 for Airline, k=6 for Retail)
- Error categories may not generalize to non-conversational tool-use scenarios (e.g., code generation, embodied agents)

## 4. Design Rationale (why this approach)

**Why failure-aware, not capability-aware:** The authors argue that prior work focused on adding capabilities (more agents, better prompts, more context) but ignored that different models fail differently. FAMA inverts this: first understand how a specific model fails, then add precisely what it needs.

**Why minimal agent subsets:** Using ALL agents (IRMA approach) degrades performance for some model-domain pairs (e.g., Qwen3-32B Airline: ReAct 30.40% vs IRMA 24.40%). Excess context from irrelevant agents competes with critical information (domain policies, tool outputs) in limited context windows. FAMA's minimal selection avoids this.

**Why training-free for open-source models:** Fine-tuning open-source models on tool-use tasks requires expensive trajectory collection and training infrastructure. FAMA's inference-time orchestration is immediately deployable. Moreover, the error profiles are model-specific, so a one-size-fits-all fine-tuned model may not address each model's idiosyncratic failures.

**Why independent error analysis agents:** Each agent specializes in a single error category with detailed failure cause lists (Appx E: 5 DCV causes, 6 WRCO causes, 4 IFU causes, 4 CM causes). This decomposition makes the analysis task tractable for LLMs and produces interpretable rationales.

**Why two judgment models produce same decisions:** Using GPT-4o vs GPT-4.1-mini yields consistent error identification (both flag DCV and CM as primary) and agent recommendations. This robustness reduces dependency on any single proprietary model for the analysis stage.

## 5. Limitations & Failure Modes

1. **Agent pool coverage bound:** FAMA effectiveness is fundamentally bounded by the coverage of A. If no agent in A addresses a failure mode, performance cannot improve. The framework does not auto-discover or synthesize new agents
2. **Benchmark scope:** τ-bench/τ-trait/ACEBench are structured conversational domains. FAMA has not been tested on open-ended environments (WebArena, SWE-bench, embodied agents) where failure taxonomies may differ
3. **Two-pass overhead:** Stage 1 runs baseline agent on ALL tasks before Stage 2 can proceed. For large task sets, this doubles execution time. In production, failure analysis would need periodic re-running
4. **Frontier model dependency for reasoning:** GPT-4o/GPT-4.1-mini serve as judgment agents. Their cost and availability gate the entire framework for organizations without API access
5. **Memory module tuning:** Optimal memory size k is domain-specific, requiring per-domain tuning. The paper found k=2 for Airline, k=6 for Retail — no principled method for selecting k a priori
6. **Context window overflows:** Thinking variants of Qwen3 models suffer frequent token limit violations (up to 23 task failures per run). FAMA's overhead, while lower than IRMA, still pushes small-context models toward their limits
7. **Error detection false positives:** The orchestrator agent can misidentify the root cause. A trajectory may fail for multiple reasons; attributing to a single error category may miss compound failures
8. **No longitudinal analysis:** Error profiles are computed once from baseline runs. As the agent improves (with FAMA), its failure profile may shift, requiring re-analysis — but this is not studied

## 6. Transfer to Lyra (one idea + route + Impact/Effort/Tier)

**Idea:** Implement a **Failure-Aware Context Injection** mechanism in Lyra's agent runtime. After each Lyra task failure, run lightweight error classification (DCV, WRCO, CM, IFU — adapted to Lyra's domain) to identify root cause. Maintain a small pool of specialized "helper prompts" (planner prompt, domain policy extractor, tool output simplifier, verifier prompt). On subsequent task attempts, inject only the prompts corresponding to the detected failure mode as additional system context — avoiding full multi-agent overhead.

**Route:** §4.2 (Agent Architecture) — add a failure analysis module to the existing agent loop that classifies failures post-task and caches recommended context injections for similar future tasks

**Impact:** Medium — addresses Lyra's likely failure modes (domain policy violations in tool use, contextual misinterpretation in complex user requests) with minimal training cost; immediately deployable

**Effort:** Low-Medium — requires: (1) defining Lyra-specific error taxonomy, (2) creating 3-5 specialized helper prompts, (3) implementing failure classifier using existing LLM backend, (4) building recommendation cache; no model training

**Tier:** Tier 1 (1-2 months) — training-free, builds on existing agent infrastructure, immediate ROI via improved task completion rates on Lyra's tool-use workflows
