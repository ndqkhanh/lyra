# GENESISFUNC: Multi-Agent Data Generation for Accurate and Generalizable Function-Calling

**Authors:** Hao-Xiang Xu, Chong Deng, Jiaqing Liu, Wen Wang, Qian Chen, Lujia Bao, Xiangang Li, Zhen-Hua Ling (Tongyi Fun Team, Alibaba Group)
**Venue:** arXiv preprint (arXiv:2605.28835v1 [cs.CL], 10 Apr 2026)
**Repository:** https://github.com/famoustourist/GenesisFunc

## 1. Mechanism (step-by-step)

GENESISFUNC is a three-stage pipeline for synthesizing function-calling training data for LLMs.

### Stage 1: Tool Pool Construction
- Source all tools from the **BFCL evaluation set** (Yan et al., 2024), a widely used public benchmark with manually designed, real-world tools.
- **Semantic clustering** via GPT-4o: each tool pair scored for functional similarity, score r in [0,1]; r > 0.75 groups tools as functionally related.
- **Human verification**: light pass to ensure correctness and usability.
- Result: a curated **Tool Pool of 1,000 tools** spanning multiple domains (Weather, Math, Finance, Entertainment, etc.).

### Stage 2: Multi-Agent Dialogue Generation
Four LLM-based agents (Gemini-2.5 Pro backbone; model-agnostic design) coordinate:

1. **Sample Agent**: Selects a tool subset Ts = Ttarget U Tdistractors from the pool. Target tools are grouped by semantic similarity (r > 0.75). Distractors sampled by relevance: high (r > 0.6), medium (0.3 < r <= 0.6), low (r <= 0.3). This forces the downstream model to discriminate between related and unrelated tools.

2. **Memory Agent**: Records dialogue instances D = {d1, ..., dk} with semantic type labels tau(di) in C. Summarizes past (di, tau(di)) pairs and guides the generator to produce dialogues with **unseen tau**, preventing context repetition and increasing semantic diversity.

3. **Function Agent**: Selects one or more tools {t1, ..., tk} from Ts to address a query q. Applies a **dynamic slot-selection strategy**: randomly chooses a subset P' of optional parameters to instantiate. This yields varied parameter-filling patterns (heterogeneous slot utilization) and improves generalization.

4. **Judge Agent**: Evaluates **N=4 candidate dialogues** per round, scoring on problem significance and tool appropriateness. The best candidate d* is selected. Positional bias controlled via random shuffling and A/B swap tests.

**Dialogue Generation System** (User Agent U + Assistant Agent A):
- Action space: A_asst = {call, ask, answer}
- Three dialogue types produced:
  - **Single-turn**: single-task and multi-task variants
  - **Multi-turn**: single-task and multi-task variants (alternating ask/clarify, call, summarize)
  - **Special cases**: relevance-checking (no applicable tool) and error-detection (invalid parameters)
- Algorithm 1 (pseudocode in paper) defines the full iterative generation loop: U issues query -> A plans action -> FunctionAgent selects tools/fills params -> A summarizes -> JudgeAgent picks best -> MemoryAgent updates forbidden types -> state advances.

### Stage 3: Multi-Stage Evaluation
1. **Rule Checker**: Static compliance checks across 4 aspects — tool definition completeness, call format & parameter compliance, dialogue structure soundness, tool-assistant consistency. Returns pass/fail with correction hints.
2. **Model Checker** (GPT-4o): Post-hoc semantic evaluation — faithfulness, task satisfaction, compliance. Assigns confidence score; samples with score < theta=0.75 rejected. (Distinct from Judge Agent, which operates during generation.)
3. **Human Validation**: ~5% of samples (error rate <5% after automated screening) reviewed by human experts. ~80% of remaining errors are parameter-extraction errors. Total cost: **~15 human-hours**.

### Dataset Composition
- 2,000 single-turn dialogues + 2,000 multi-turn dialogues + 500 special-case dialogues
- Avg 3.11 tools used per dialogue, 4.46 turns per multi-turn scenario, 3.27 tasks per multi-task case
- Training format: Alpaca format (instruction = system prompt + tool pool + user query; output = tool call)

### Training Recipe
- **SFT**: LoRA fine-tuning on Qwen3-8B (LoRA rank=16, alpha=32, lr=1e-4, cosine schedule, warmup ratio=0.1, batch size=48, 3 epochs). Completed on **1x A800 GPU in ~30 minutes**.
- **RL (optional)**: GRPO (Grouped Relative Policy Optimization), a PPO variant that normalizes advantages within response groups per query. No KL penalty against reference model. Reward = R_structural + R_correct:
  - R_structural: binary per-call schema check (Eq 6-7)
  - R_correct: 0-3 per-call (3=exact match, 2=tool+partial params, 1=tool only, 0=mismatch; Eq 8-9)
- RL configured on **4x A800 GPUs, ~4 hours**.

## 3. Trade-offs

| Win | Cost / Lose |
|-----|-------------|
| +2.5% over prior SOTA ToolACE-8B (BFCL Non-Live) | Pipeline uses proprietary models (Gemini-2.5 Pro, GPT-4o) for generation and evaluation — API costs not quantified |
| +15.3% over ToolACE-8B on API-Bank (out-of-domain) | Multi-agent framework adds orchestration complexity vs single-agent pipelines |
| Covers all 5 dialogue types (unique: Multi-Multi, Special-Case) | ~15 human-hours still required for final validation (not fully automated) |
| Model-agnostic: works across Qwen, LLaMA backbones with consistent gains | Open-source model substitution (Qwen3-32B) drops quality ~0.5-0.9% on BFCL |
| Preserves general abilities (MMLU, GSM8K, etc.) after FC fine-tuning | Still trails GPT-4 in reasoning/comprehension (~77 vs ~88 on ACEBench) |
| Training cheap: SFT 30 min on 1xA800, RL 4h on 4xA800 | Data generation API costs not reported; likely significant (Gemini-2.5 Pro for all agents) |
| Scales to new tools without regressing old benchmarks | Diminishing returns beyond 5 dialogues/tool; full 4.5K dialogue dataset not enormous |
| Dynamic slot selection outperforms fixed strategies | Single-agent alternatives not ablated (only multi-agent components removed) |
| Strong RL multi-turn gains (+5 points on multi-turn ACEBench) | RL(all) underperforms SFT — careful data partitioning required |

## 4. Design Rationale

**Why multi-agent over monolithic generation**: Each agent specializes — Memory for diversity, Judge for quality, Sample for relevance — avoiding the failure mode where a single LLM generates repetitive, low-quality dialogue. The Memory Agent explicitly prevents reproducing seen semantic contexts; the Judge Agent selects the best of N=4 candidates (a generation + filtering pattern).

**Why BFCL tools instead of synthetic APIs**: Synthetic/manually designed APIs are unreliable and hard to scale. BFCL tools are real, verified, and cover diverse real-world domains. Using them makes the training data distribution closer to real deployment.

**Why dynamic slot selection**: Fixed strategies (always-fill or never-fill optional params) create distributional bias. Random subset selection exposes the model to sparse, partial, and complete parameter patterns, improving generalization to arbitrary user queries.

**Why SFT + staged RL**: Full RL from scratch on all data hurts performance (RL(all) = 73.00 vs SFT = 73.60 on ACEBench Normal). SFT provides a strong base; RL applied only to multi-turn data improves complex interactions (+5 points) without destabilizing single-turn or special-case handling.

**Why N=4 for Judge Agent**: Empirically balances selection quality and generation cost. More candidates increase quality but linearly increase API cost.

## 5. Limitations & Failure Modes

1. **API-model gap**: GENESISFUNC-8B still trails GPT-4 in broader reasoning and comprehension. Function-calling specialization alone cannot close the general intelligence gap.

2. **Complex chained tool sequences not covered**: The training data does not fully encompass tightly coupled multi-tool sequences requiring sequential dependencies (e.g., search -> filter -> compute -> plot). This limits applicability to true agentic workflows.

3. **Tool pool scope constrained**: Only 1,000 tools from BFCL. Coverage of niche/domain-specific tools (e.g., healthcare APIs, enterprise systems) is unverified.

4. **Evaluation breadth**: Only 3 benchmarks (BFCL, API-Bank, ACEBench). No real-world deployment study, no latency analysis, no robustness to adversarial queries.

5. **Data contamination concern**: Training uses BFCL tool schemas; while queries are novel, tool definitions overlap with evaluation. The "in-domain" label may overstate some gains.

6. **Proprietary model dependency**: Pipeline uses Gemini-2.5 Pro and GPT-4o. Full reproduction requires paid API access. Open-source substitution causes moderate degradation (~0.5-0.9%).

7. **Limited automation**: ~15 human-hours of validation required per dataset generation cycle. Not fully self-supervised.

8. **No non-English evaluation**: Despite ACEBench being bilingual, results are only reported on the Chinese+English aggregate — no per-language breakdown.

9. **Parameter extraction bias**: ~80% of post-automated-screening errors are parameter extraction errors (not tool selection or intent). Suggests pipeline underperforms on argument-value grounding relative to tool identification.

## 6. Transfer to Lyra

**The one idea**: The **Memory-Agent-driven diversity control loop** combined with a **Judge-Agent quality selector** (N=4 candidate generation + best-selection) as a reusable pattern for synthesizing diverse, high-quality function-calling training data from an existing tool registry.

**Application**: Lyra's §4.3 (Tool-Use / Function-Calling Subsystem) can adopt this pattern. Lyra already has a tool registry (the plugin system + built-in tools). Instead of hand-crafting training examples, Lyra could implement a multi-agent pipeline that: (1) samples tool subsets from its registry; (2) generates user-assistant dialogues with a Memory Agent preventing repetition; (3) uses a Judge Agent to filter quality; (4) runs rule-based + model-based evaluation. This would produce a Lyra-specific function-calling dataset that covers Lyra's unique tool surface (code execution, file ops, web search, memory, etc.) with the diversity and scene coverage GENESISFUNC demonstrates.

**Workstream route**: §4.3 (Tool Guild / Function Calling)

**Impact**: 4 (directly improves tool-calling accuracy; the Memory-Judge pattern is the core differentiator from simpler synthetic data approaches)
**Effort**: 4 (requires building multi-agent orchestration; existing Lyra agent infrastructure can be reused; Gemini/GPT-4o dependency may need open-source substitution)
**Tier**: breakthrough (proven pattern with strong empirical gains, transferable to Lyra's unique tool surface)
