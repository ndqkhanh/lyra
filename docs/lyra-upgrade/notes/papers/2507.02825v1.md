## 1. Mechanism

The paper introduces the **Agentic Benchmark Checklist (ABC)**, a systematic framework for assessing and improving the evaluation rigor of agentic benchmarks. The mechanism operates in two conceptual layers and three assessment pillars:

### 1.1 Operational/Conceptual Decomposition

The authors decompose agentic evaluation into a pipeline:

```
Target Capability → [Task Validity gate] → Task Success → [Outcome Validity gate] → Positive Evaluation Result
```

- **Task Validity:** The task is solvable if and only if the agent possesses the target capability. Violations produce false positives (shortcuts) or false negatives (impossible tasks).
- **Outcome Validity:** A positive evaluation result occurs if and only if the task was actually successful. Violations produce mis-scores (both over- and underestimation).

### 1.2 Task Validity Checks (10 items, grouped into 3 sub-areas)

**Tool (T.1-T.3):** Specify tool versions, ensure API availability, handle API failures gracefully.
**Environment (T.4-T.6):** Clear residual state between runs, isolate agents from ground truth, freeze environment at release time.
**Implementation (T.7-T.10):** Verify ground truth correctness, verify each task is solvable, provide an Oracle solver, eliminate exploitable implementation vulnerabilities.

### 1.3 Outcome Validity Checks (organized by evaluation method type)

The checklist tailors checks to the specific evaluation method:

| Evaluation Method | Checks | Key Failure Modes |
|---|---|---|
| Whole String Matching | O.a.1-2 | Misses semantically equivalent answers; penalizes redundant words |
| Substring Matching | O.b.1-3 | Negation modifiers ignored; answer-listing passes; shallow ground truth enables guessing |
| LLM-as-a-Judge | O.c.1-2 | Accuracy/consistency unvalidated; susceptible to reward hacking |
| Unit Testing | O.d.1-2 | Test cases unverified; no coverage/complexity metrics |
| Fuzz Testing | O.e.1-3 | Edge cases missed; limited data types/layouts; inputs don't affect outputs |
| E2E Testing | O.f.1-2 | Branches uncovered; flaky/non-deterministic results |
| State Matching | O.g.1-3 | Incomplete state space; irrelevant states included; trivial state modifications pass |
| Answer Matching | O.h.1-2 | Implicit format assumptions; success by guessing |
| Quality Measures | O.i.1 | Metrics exploitable without task completion |

### 1.4 Benchmark Reporting Checks (13 items)

Three sub-groups: **Transparency & Validity (R.1-R.6)**, **Flaw Mitigation (R.7-R.9)**, and **Result Interpretation (R.10-R.13)**. Items include open-sourcing, contamination prevention, confidence intervals, non-AI baselines, and trivial-agent baselines.

### 1.5 Application Method

Each checklist item is scored 1 (satisfied) or 0 (not satisfied). Partial scores are averaged within each pillar. The checklist is applied through: (a) document review of benchmark design, (b) adversarial experiments to validate suspected flaws, (c) quantitative measurement of estimation error magnitude.

## 2. Results

### 2.1 Quantitative Flaw Measurements Across Benchmarks

| Benchmark | Issue | Quantitative Impact |
|---|---|---|
| τ-bench (Airline) | Trivial agent passes unsolvable tasks | **38% false success rate** on impossible tasks (outperforms GPT-4o agent) |
| τ-bench | Agent can list all possible answers | **40% overestimation** (substring matching matches verbatim DB text) |
| SWE-Lancer | Agents can overwrite test files w/ trivial assertions | **100% score achievable** without solving any task |
| KernelBench | Fuzzing omits shape/memory layout variation | **31% absolute overestimation** of kernel correctness |
| SWE-bench-Verified | Unit tests fail to capture edge cases | **24% of top-50 leaderboard entries are incorrect**; 5.2-7.7% pass without correct patches |
| WebArena | Substring matching + unvalidated LLM judge | **1.4-5.2% overestimation** |
| OSWorld (Chrome) | Stale HTML selectors from website changes | **28% absolute underestimation** (13/46 tasks broken) |
| CVE-Bench (pre-ABC) | Naive SLEEP-clause-in-log check for time-based SQLi | **32.5% overestimation** |
| CVE-Bench (pre-ABC) | Ungated outbound server access from Docker network | **10% overestimation** |

### 2.2 ABC Assessment Scores (10 benchmarks scored)

- **Task validity:** 7/10 benchmarks violated — especially those providing tools to agents. KernelBench and OSWorld scored most poorly.
- **Outcome validity:** 7/10 benchmarks violated. SWE-bench and SWE-Lancer scored most poorly.
- **Benchmark reporting:** 0/10 benchmarks satisfied all criteria; 80% fail to acknowledge known weaknesses.

### 2.3 ABC Case Study: CVE-Bench Improvement

Applying ABC to CVE-Bench (a complex cybersecurity benchmark with one-day/zero-day scenarios):
- Fixed time-based SQL injection eval (naive SLEEP check → actual execution verification): reduced overestimation by **32.5% absolute**
- Fixed ungated outbound server (Docker network bypass → properly firewalled): reduced overestimation by **10% absolute**
- **Total: 33% absolute reduction in performance overestimation**, confirmed by cybersecurity experts

### 2.4 Relative Error Upper Bound

The paper demonstrates that relative estimation errors can reach **up to 100%** (i.e., doubling or completely zeroing the perceived capability) when outcome validity or task validity is violated.

## 3. Trade-offs

| Win | Cost / Loss |
|---|---|
| Systematic, actionable taxonomy for eval rigor (first of its kind for agentic benchmarks) | Manual assessment required — ABC cannot be fully automated; requires expert judgment |
| Identifies concrete, quantitative flaws across 10 major benchmarks | Checklist is non-exhaustive; future agent capabilities may reveal new failure modes |
| Reduces CVE-Bench overestimation by 33% absolute | Applying all checks is resource-intensive (re-implementing evals, running pilot experiments, expert review) |
| Decomposition by eval-method-type makes checks directly actionable for benchmark developers | Some checks involve inherent trade-offs (e.g., cheap substring matching vs. expensive expert annotation) |
| Transparency about flaws builds community trust and enables better leaderboard interpretation | Surfaces embarrassing flaws that benchmark creators may resist acknowledging |
| Provides quantitative evidence of eval flaws (not just theory) | Snapshot analysis — findings are stale as benchmarks update |
| LLM-as-a-Judge check (O.c.1) forces validation of judge accuracy | Validating judge accuracy requires human annotation budget, counteracting scalability benefits of LLM judging |

## 4. Design Rationale

The paper argues that existing benchmark assessment frameworks (BetterBench, etc.) target multiple-choice and text-generation benchmarks, which have simpler evaluation semantics (categorical labels, BLEU/ROUGE). Agentic benchmarks introduce two qualitatively harder challenges: (1) complex task setup with dynamic environments, tools, and multistep interactions, and (2) unstructured task outcomes (code, file edits, environment states) requiring domain-specific grading. Rather than propose a single metric, ABC decomposes rigor into orthogonal validity dimensions (task validity + outcome validity) and then sub-decomposes by evaluation method type (unit test, fuzz test, substring match, etc.). This makes the checklist actionable: a benchmark developer using unit tests gets a different set of checks than one using LLM-as-a-Judge. The rationale for the two-threat taxonomy comes from first-principles: the conceptual chain `capability → task success → eval result` has exactly two equivalence points that can break. The empirical grounding (17 benchmarks from top AI providers, Jan'24-Mar'25) ensures relevance to current practice rather than hypothetical concerns.

## 5. Limitations & Failure Modes

1. **Temporal scope:** Only covers benchmarks from top AI providers released between January 2024 and March 2025. Benchmarks before or after this window are not analyzed.
2. **Non-exhaustive checklist:** The taxonomy is based on current understanding of agent capabilities. Future agents with qualitatively different capabilities (e.g., long-horizon autonomous planning) may introduce new eval failure modes not captured by ABC.
3. **Snapshot staleness:** All findings reflect benchmark state at time of writing. Benchmarks may have been patched since; conclusions may not apply to updated versions.
4. **Manual application required:** ABC is not automated; applying it requires deep understanding of each benchmark's codebase and evaluation logic, plus adversarial creativity to discover shortcuts.
5. **Provider bias in benchmark selection:** The corpus is limited to benchmarks used by top-8 AI providers; community benchmarks without corporate adoption may be missed.
6. **No causal framework:** ABC identifies flaws but does not provide a statistical framework for how flaws propagate into aggregate leaderboard rankings (only per-benchmark error bounds).
7. **Limited coverage of AI-safety-specific benchmarks:** Only Cybench and MLCommons safety benchmark covered; safety-specific eval properties (jailbreak detection, refusal scoring) may need additional checks.
8. **English-language only:** The benchmarks analyzed are English-only; non-English or multilingual agentic benchmarks may have distinct validity challenges.

## 6. Transfer to Lyra

### The ONE Transferable Idea

**Adopt the ABC two-threat decomposition (Task Validity + Outcome Validity) as Lyra's internal eval-harness quality standard.** Every Lyra eval — whether for model routing (§5), tool-use accuracy (§6), plugin correctness (§7), or autonomy scoring (§14) — should explicitly document: (1) what shortcuts/impossible-task risks exist in task design, and (2) what grading flaws exist in outcome assessment. Apply the specific sub-checklist items from ABC based on evaluation method type (substring matching for text evals, unit-test coverage metrics for code evals, state-matching completeness for environment evals). Use the reporting checklist (R.1-R.13) as the template for Lyra's eval scorecards. Run a trivial-agent baseline on every Lyra eval to surface outcome-validity failures before publishing leaderboard numbers.

### Workstream Route

**§16-reliability** (eval rigor and result trustworthiness) — primary. The ABC framework directly improves Lyra's ability to produce trustworthy eval numbers for all other subsystems. Also feeds **§26-harness-engineering** (building Lyra's own eval infrastructure) and **§14-autonomy** (ensuring autonomous-loop success metrics are not gamed).
