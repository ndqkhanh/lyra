## 1. Mechanism (step-by-step)

ERL is a parameter-free, two-component self-improvement loop for LLM agents. It neither fine-tunes nor re-executes tasks; it distills single-attempt trajectories into reusable heuristics and retrieves them at test time.

### Phase 1: Heuristic Generation (Experience Accumulation)

1. **Execute agent on a task.** The agent uses a standard ReAct scaffold (Reasoning + Action + Observation loop). The environment returns binary success/failure feedback.
2. **Reflect via post-mortem analysis.** After each task, an LLM (GPT-5.2) runs a structured reflection over the triple: `(task_description, trajectory, outcome)`.
   - For **failure**: pinpoint the exact breakpoint (tool misuse, logic error) and derive a corrective rule.
   - For **success**: identify the "winning move" and derive a best-practice rule.
3. **Emit a structured heuristic.** Each heuristic contains:
   - `Analysis`: root cause of success/failure in this specific trace
   - `Learned Guideline`: a trigger-action rule in imperative form, e.g. *"When sending emails to calendar attendees, first resolve names to email addresses via the Contacts tool before calling the email API."*
4. **Store in a persistent pool.** Heuristics are accumulated across 8 training universes (112 execution + 132 search tasks). No retries; single-attempt only.

### Phase 2: Retrieval-Augmented Execution (Test Time)

1. **Decompose the new task.** An LLM (GPT-5.2) analyzes the task, breaking it into sub-tasks and action steps.
2. **Score each heuristic.** The LLM scores every heuristic in the pool (0-100) on three criteria:
   - **Similarity** of task descriptions
   - **Diversity** of experiences (cover a range of potential lessons)
   - **Informativeness** of the guideline content (detailed, actionable advice)
3. **Retrieve top-k.** The top-k heuristics (default k=20) are selected. Selection is task-specific; heuristics are NOT blindly concatenated.
4. **Inject into system prompt.** Retrieved heuristics are prepended to the agent's system prompt before the ReAct loop begins. No per-turn retrieval overhead.

### Key Design Properties

- **No re-execution required.** Unlike ExpeL and AutoGuide, ERL needs only a single trajectory per task. No Reflexion retries, no contrastive trajectory pairs.
- **Per-task enrichment.** Each new task adds one heuristic to the pool — the pool grows linearly with deployment.
- **Selective retrieval beats full inclusion.** Injecting all heuristics without retrieval drops performance (53.8% vs 56.1%); random selection peaks at 40-60 heuristics then degrades.

### Iterative Variant (Algorithm 1 in paper)

An iterative version processes tasks in batches, retrieving from the pool as it builds. However, this yields *worse* test generalization (-5.4%) because early heuristics encode naive mistakes that disappear as the agent improves — paradoxically reducing the breadth of captured failure modes.

## 2. Results (benchmark numbers with units)

### Gaia2 Benchmark (Search + Execution splits)

| Method | Execution (%) | Search (%) | Overall (%) |
|---|---|---|---|
| ReAct Baseline | 43.1 | 53.6 | 48.3 |
| Few-shot Trajectories | 41.7 | 51.2 | 46.4 |
| ExpeL | 45.8 | 56.0 | 50.9 |
| AutoGuide | 39.6 | 61.9 | 50.8 |
| **ERL (Ours)** | **51.4** | **60.7** | **56.1** |

- **+7.8 pp** over baseline (48.3 → 56.1)
- **+5.2 pp** over strongest prior method (ExpeL at 50.9)
- Gains consistent across splits: +8.3 pp (Execution), +7.1 pp (Search)

### Reliability: pass@3 and pass^3

| Metric | Baseline | ERL | Delta |
|---|---|---|---|
| pass@3 (Execution) | 60.4% | 62.5% | +2.1 pp |
| **pass^3 (Execution)** | **22.9%** | **31.2%** | **+8.3 pp** |
| pass@3 (Search) | 82.1% | 82.1% | 0 |
| **pass^3 (Search)** | **28.6%** | **39.3%** | **+10.6 pp** |

Key insight: Gains come primarily from improving **reliability** (pass^3), not from solving novel tasks (pass@3). ERL makes the agent more consistent, not more capable at the frontier.

### Ablation: Retrieval Method

| Configuration | Overall (%) |
|---|---|
| ERL (LLM retrieval, k=20) | **56.1** |
| No retrieval (all heuristics) | 53.8 |
| Embedding retrieval (Qwen3-0.6B, k=20) | 53.3 |
| Random selection (best, ~50 heuristics) | 53.8 |
| Only failure heuristics | **58.9** |
| Only success heuristics | 49.9 |

- LLM retrieval >> embedding retrieval by +2.8 pp
- Failure-derived heuristics surpass success-derived overall (58.9% vs 49.9%)
- BUT: task-dependent — failure heuristics excel on Search (+14.3 pp over baseline); success heuristics excel on Execution (+9.0 pp)

### Token-Matched Comparison (Heuristics vs. Raw Trajectories)

At matched token budgets (~20 scenarios): heuristics yield +5.5 pp gain (Execution) and +23.8 pp gain (Search) over raw trajectory few-shot. Raw trajectories degrade with context length beyond ~30k tokens; heuristics remain stable.

### τ²-bench (Dual-Control, Airline/Retail/Telecom)

| Domain | Baseline | ERL |
|---|---|---|
| Airline | 36.7% | 38.3% |
| Retail | 43.3% | 47.5% |
| Telecom | 30.0% | **28.3%** |
| Overall | 36.7% | 38.0% |

Modest gains on single-control domains; Telecom degrades due to combinatorial task composition and dual-control user variability.

### Cost Analysis (Gaia2 full eval run)

| Configuration | Token Input (M) | Token Output (M) | Cost ($) | Avg Turns |
|---|---|---|---|---|
| Baseline | 103.8 (82% cached) | 4.3 | 15.27 | 16.6 |
| ERL (total) | 200.5 (85% cached) | 4.3 | **21.40** | 17.6 |

- Heuristic generation: $2.42; Retrieval: $1.38; Rollout: $17.60
- **+40% total cost** increase. Rollout alone: +15% (prompt caching absorbs much of the input token increase).
- Input tokens nearly double (+85%) due to ~20k heuristic tokens appended per turn.

### Without Reward Signal

When the agent must self-assess success/failure (70% accuracy), ERL drops to 51.2% (-4.8 pp), still above baseline (48.3%).

## 3. Trade-offs

| Win | Lose |
|---|---|
| +7.8 pp success rate on Gaia2; +5.2 pp over best prior method | +40% total API cost; +85% input tokens per rollout |
| Large reliability gains (pass^3: +8.3 pp Exec, +10.6 pp Search) | Negligible pass@3 gains — no new capability, just consistency |
| Heuristics 23.8 pp better than raw trajectories on Search at matched tokens | Requires binary outcome signal; self-assessed drops 4.8 pp |
| Single-attempt learning (no Reflexion retries, no contrastive pairs) | Iterative accumulation hurts generalization (-5.4 pp) |
| LLM retrieval 2.8 pp > embedding retrieval | Every retrieval call costs tokens ($1.38 per eval run) |
| Failure heuristics give +14.3 pp on Search | But underperform on Execution; need both sources in deployment |
| Works without fine-tuning; compatible with closed-source models | Assumes shared tool/app environment (12 apps, 101 tools) across universes |
| Heuristics are human-readable and auditable | No heuristic contradiction resolution or deduplication mechanism |
| Scales linearly: one heuristic per task | k>20 retrieval degrades; pool management becomes harder with scale |

## 4. Design Rationale

**Why heuristics, not trajectories?** The authors argue (and show empirically) that raw trajectories lack the abstraction necessary for transfer. A trajectory says "what happened"; a heuristic says "what to do differently next time." Heuristics capture trigger-action rules that are more context-efficient (5.5-23.8 pp better at matched token budgets) and generalize across structurally similar but superficially different tasks.

**Why single-attempt instead of Reflexion retries?** Predecessors (ExpeL, AutoGuide) require contrastive pairs (success + failure trajectories for the same task). This assumption fails in production where tasks cannot be retried. ERL extracts lessons from one shot, matching real deployment constraints.

**Why LLM-based retrieval over embeddings?** Embedding similarity matches on surface features (shared tools, keywords) but misses deeper structural patterns (error types, solution strategies). LLM retrieval considers the *content* of heuristics (error patterns, lessons learned), not just task similarity. This produces +2.8 pp over embedding retrieval.

**Why inject once per task (not per turn)?** AutoGuide retrieves at every ReAct turn, incurring per-step overhead. ERL injects heuristics into the system prompt once, leveraging prompt caching. This trades per-turn adaptivity for lower cost and faster execution.

## 5. Limitations & Failure Modes

1. **Requires binary outcome signal.** Performance degrades when reward is self-assessed (-4.8 pp). Real-world tasks often lack clean success/failure labels.
2. **No heuristic contradiction resolution.** As the pool grows, contradictory heuristics can accumulate (e.g., "always do X first" vs. "always do Y first"). The paper acknowledges this but provides no solution.
3. **Fails on combinatorial/dual-control domains.** Telecom (τ²-bench) degrades (-1.7 pp) because tasks are composed combinatorially and user interaction is unpredictable — heuristics match poorly to specific sub-task compositions.
4. **Iterative learning hurts generalization.** Paradoxically, learning from progressively improving trajectories (-5.4 pp vs. batch) produces narrower heuristics that miss naive failure modes.
5. **Fixed tool environment.** All experiments assume 12 apps + 101 tools that stay constant across universes. Applicability to environments with tool evolution is untested.
6. **Retrieval bottleneck at scale.** LLM-based retrieval scales as O(pool_size), requiring the full pool in context. k>20 is impractical; the paper suggests a two-stage embedding+LLM reranking pipeline (not implemented).
7. **Only tested on GPT-5-mini/5.2.** No results for open-source models or other providers.
8. **No latency measurement.** Acknowledged as missing; retrieval adds one LLM call per task.

## 6. Transfer to Lyra

### The One Transferable Idea

**Post-task heuristic generation with structured trigger-action rules and selective retrieval.** After every Lyra task execution, a dedicated reflection step (a) pinpoints the root cause of success/failure, (b) emits a structured heuristic with `[Trigger, Action, Rationale]` fields, and (c) stores it in a persistent pool. At task start, an LLM scorer retrieves the top-k (k=10-20) heuristics by task similarity + diversity + informativeness and injects them into the system prompt. This costs no fine-tuning, works with any LLM backbone, and the paper shows it yields +7.8 pp reliably.

### Workstream Routing

**§4.2 — Memory (Heuristic & Lesson Store).** The heuristic pool is a specialized episodic-to-semantic memory bridge. It maps directly to Lyra's planned memory subsystem, adding a concrete implementation pattern: format memories as trigger-action rules, retrieve by LLM-scored relevance (not just embedding similarity), and inject into system prompts pre-execution.

### Scoring

- **Impact:** 4 — Proven +7.8 pp gain on a real agent benchmark (Gaia2); reliability component (pass^3) is precisely what Lyra needs for production robustness
- **Effort:** 3 — No model training required; needs: (a) heuristic generation prompt, (b) retrieval prompt, (c) pool storage (simple JSON/SQLite), (d) injection into system prompt. Core integration estimated at 1-2 weeks.
- **Tier:** **Breakthrough** — parameter-free, architecture-agnostic, directly addresses Lyra's reliability gap, and the mechanism is simple enough to implement immediately.
