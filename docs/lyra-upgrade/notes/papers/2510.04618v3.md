## 1. Mechanism

### 1.1 Task Definition

Each SWE-bench task instance is a tuple of `(issue, codebase_snapshot, gold_patch, tests)`:

- **Problem Statement**: The GitHub issue text (title + body + discussion context) describing a real bug or feature request.
- **Codebase Snapshot**: The repository at the commit *immediately before* the fix was applied.
- **Gold Patch**: The actual merged PR diff that resolved the issue.
- **Test Suite**: Partitioned into `FAIL_TO_PASS` (tests that were failing before the fix and pass after) and `PASS_TO_PASS` (tests that were passing before and must remain passing after).

### 1.2 Dataset Construction Pipeline

```
Step 1: Repo Selection
  → Filter 12 popular Python repos (django, scikit-learn, sympy, pytest, matplotlib, sphinx, flask, seaborn, requests, pylint, xarray, astropy)
  → Criteria: >50 stars, active maintenance, well-tested

Step 2: PR-Issue Linking
  → Scrape merged PRs that reference a GitHub issue (via "Closes #N" or "Fixes #N")
  → Extract issue text, PR diff, and pre-PR commit hash

Step 3: Test Extraction
  → Checkout pre-PR commit
  → Run the PR's modified test files → identify FAILING tests
  → Checkout post-PR commit (with fix)
  → Run same tests → identify PASSING tests
  → Keep only instances where: at least 1 test transitions from fail→pass AND at least 1 test stays pass→pass

Step 4: Instance Filtering
  → Remove instances with: broken environments, flaky tests, or ambiguous issue-fix mappings
  → Result: 2,294 instances from 12 repos
```

### 1.3 Evaluation Harness Architecture

```
For each task instance:
  1. Launch Docker container with repo-specific environment
  2. Apply codebase snapshot at pre-fix commit
  3. Provide model with problem statement + codebase access
  4. Model generates a patch (unified diff or file edits)
  5. Apply model's patch to the codebase
  6. Run FAIL_TO_PASS tests → must all pass
  7. Run PASS_TO_PASS tests → must all still pass
  8. Binary verdict: RESOLVED (all tests pass) or NOT RESOLVED
```

**Key constraint**: The model's patch is evaluated against the *exact* test suite from the original PR. The model never sees the test code — only the issue text and repository files.

### 1.4 SWE-agent Architecture (highest-performing open method)

SWE-agent introduces the **Agent-Computer Interface (ACI)** design pattern:

```
Agent Loop:
  State = {codebase viewport, command history, linter output}
  
  Actions available:
    - bash(command) → execute shell command, return stdout/stderr
    - open(file, line) → view a file window around the specified line
    - edit(file, old_str, new_str) → replace text in file
    - search(query) → grep/search across codebase
    - submit(patch) → finalize and submit the unified diff
  
  Each turn:
    1. LM observes current state + action history
    2. LM selects an action from the action space
    3. Action is executed in the Docker sandbox
    4. Linter runs on edited files → feedback appended to state
    5. Loop until LM calls submit() or max turns reached
  
  Key ACI principles:
    - Fixed, minimal action space (5 actions)
    - Each action has a strict JSON schema
    - Linter provides immediate feedback after each edit
    - No "magic" hidden state — everything visible in history
```

### 1.5 SWE-bench Lite

A curated 300-instance subset for faster evaluation iteration:
- Selected from the same 12 repos
- Prioritizes instances with unambiguous issue-fix mappings
- Designed to correlate well with full SWE-bench results
- Reduces evaluation time from ~10 hours to ~1 hour

### 2.4 Key Numeric Findings

- **Unassisted LMs fail almost completely**: GPT-4 resolves 0/2294 issues without tool use.
- **Agent scaffold provides ~12x improvement**: SWE-agent raises GPT-4 from 0.33% to 12.47%.
- **Claude models consistently outperform GPT-4 family** on this benchmark when given the same scaffold.
- **Simple ACI beats complex prompting**: SWE-agent's 5-action design outperformed more complex agent frameworks at the time of publication.
- **Evaluation cost is significant**: Full SWE-bench evaluation requires ~10 compute-hours for one model run (Docker test execution dominates).

## 3. Trade-offs

| Win | Loss |
|-----|------|
| Realistic benchmark: measures practical SWE ability on real codebases | Only Python — no TypeScript, Go, Rust, Java |
| Reproducible: Docker-based isolated evaluation, same tests every run | Slow evaluation (~10 hours per model for full benchmark, ~1 hour for Lite) |
| Binary, objective metric (resolved/not) | Binary metric misses partial-credit — a 90%-correct patch scores 0 |
| Prevents regressions via PASS_TO_PASS tests | Some issues have ambiguous specifications; multiple valid patches exist but only one is "correct" |
| SWE-bench Lite enables fast model iteration | Lite subset may introduce selection bias toward "easier" instances |
| Agent scaffold (ACI) dramatically improves performance | Agent loop adds significant inference cost (10-30 LM calls per instance vs. 1) |
| Open-source harness; anyone can reproduce results | Docker environment fragility; some instances fail due to env issues, not model errors |

## 4. Design Rationale

1. **Why real GitHub issues?** Synthetic benchmarks (HumanEval, MBPP) test isolated function-writing; actual software engineering requires navigating large codebases, understanding context, and modifying existing code without regressions. SWE-bench measures the full stack.

2. **Why the FAIL_TO_PASS + PASS_TO_PASS split?** A patch that fixes a bug but breaks unrelated functionality is a net-negative change. Requiring both suites to pass enforces non-regression — a core requirement of real PR review.

3. **Why the ACI design?** The authors argue that most LLM agent designs over-complicate the action space (dozens of tools, complex prompts). SWE-agent shows that 5 well-designed actions (bash, open, edit, search, submit) + linter feedback enable better performance than more complex systems. The key insight: **constrain the action space to reduce the LM's decision complexity**.

4. **Why Docker sandboxing?** Prevents model patches from causing side effects (deleting files, breaking the OS). Enables clean teardown between instances and ensures reproducibility.

5. **Why SWE-bench Lite?** Full evaluation is too slow for iterative model development. A high-signal 300-instance subset enables fast experimentation while maintaining rank correlation with full-bench results.

---

## 5. Limitations & Failure Modes

1. **Language monoculture**: All 12 repos are Python. Results may not generalize to other languages or ecosystems (npm, cargo, maven).

2. **Ambiguous issue specifications**: Some real GitHub issues are poorly written, contradictory, or underspecified. A model might produce a valid fix that differs from the gold patch and still be marked "not resolved."

3. **Incomplete test coverage**: The gold patch may fix edge cases not covered by the extracted test suite. A model patch that passes all tests could still have bugs.

4. **Environment fragility**: Docker container setup is complex (different Python versions, system dependencies per repo). ~5-10% of instances may fail due to environment issues rather than model errors.

5. **Single correct answer assumption**: Multiple valid implementations can fix the same bug. The benchmark rewards exact test-passing, not code quality or idiomatic correctness.

6. **No human baseline**: Human software engineer performance on SWE-bench is not measured, making it hard to calibrate model scores against "good enough" thresholds.

7. **Exact-match testing**: Tests check for exact outputs. Patches that produce semantically correct but syntactically different outputs fail.

8. **SWE-bench Lite curation bias**: The 300-instance subset was manually curated to have unambiguous issue-fix mappings, potentially making it easier than the full benchmark distribution.

## 6. Transfer to Lyra

### The One Idea: Agent-Computer Interface (ACI) Design for Tool-Optimized Action Spaces

The SWE-agent ACI demonstrates that **a small, strictly-typed set of tools with immediate feedback (linter) outperforms larger, more complex tool suites**. Lyra should adopt this design principle: define a canonical set of 5-8 core tools with rigid, validated input/output schemas rather than open-ended natural-language tool descriptions.

### Mapping to Lyra Architecture

- **Workstream**: §4.2 — Agent Architecture (Tool/Action Design)
- **Sub-area**: Tool Schema Design and Action Space Minimization

### Application Strategy

Instead of Lyra's current approach of exposing numerous loosely-defined capabilities to the LM, adopt ACI principles:
1. Audit current Lyra tools → cull to 5-8 essential actions
2. Add strict JSON schema validation per tool
3. Implement immediate feedback channels (linter, type-checker, test runner) after each action
4. Maintain full action history in the agent's context window for self-correction

### Scoring

| Dimension | Score | Rationale |
|-----------|-------|-----------|
| Impact | 4 | ACI redesign would fundamentally improve Lyra's action reliability and reduce error rates — directly addresses the core agent loop |
| Effort | 3 | Tool audit + schema design + feedback integration is moderate effort (~1-2 weeks of focused work); no new infrastructure needed |
| Tier | **breakthrough** | This is not parity work — it's an architectural insight that can give Lyra a step-function improvement in agent performance, backed by strong evidence (12x improvement over naive LM on SWE-bench) |
