## 1. Mechanism (step-by-step)

MATA is a 3-stage multi-agent TableQA pipeline that orchestrates complementary reasoning paths (CoT, PoT, text2SQL) through a system of 6 LLM agents and 3 lightweight tools, using the same backbone LLM for all agents but with role-specific prompts.

### Stage 1: Agent Selection with Scheduler (Sch)

**Architecture:** MobileBERT (Sun et al., 2020) text encoder + 2-layer MLP = 24.65M parameters total.

**Inputs:**
- Text embedding of concatenated question + table schema (from MobileBERT)
- 6 numeric features (row count, column count, table size, unique words in question, numeric token count in question, question-schema word overlap)
- 4 boolean features (integer-type exists, float-type exists, string-type exists, NaN exists)

**Output:** 2-dimensional vector of logits [prob_pot, prob_sql], trained with Binary Cross Entropy for 45 epochs on 173,664 samples from 57,888 (T,Q) pairs.

**Decision rule (Algorithm 1):**
```
sol_cot, A_cot ← CoTA(T, Q)                    # CoT always runs first
prob_pot, prob_sql ← Sch(T, Q)
if prob_pot >= prob_sql:
    C_pot, A_pot ← Code&Debug(PoTA, T, Q, N=3)  # Execute PoT first
    if A_cot != Last(A_pot):                      # If CoT and PoT disagree
        C_sql, A_sql ← Code&Debug(t2SA, T, Q, N=3)  # Also run SQL
    else:
        C_sql, A_sql ← ∅                          # Skip SQL (agreement = early exit)
else:
    C_sql, A_sql ← Code&Debug(t2SA, T, Q, N=3)   # Execute SQL first
    if A_cot != Last(A_sql):                      # If CoT and SQL disagree
        C_pot, A_pot ← Code&Debug(PoTA, T, Q, N=3)  # Also run PoT
    else:
        C_pot, A_pot ← ∅                          # Skip PoT
```

User can disable Sch to always run all 3 paths (higher cost, sometimes higher accuracy on complex tasks).

### Stage 2: Code Generation & Debugging (Algorithm 2)

CoT Agent runs **once only** — empirical studies show CoT outputs rarely change with self-refinement (Tables 20-21), so no Debug Agent is used.

For PoT and text2SQL, iterative debugging loop (up to N=3 rounds):

```
function Code&Debug(Agent, T, Q, N):
    C, A ← ∅
    Debug = (Agent == PoTA) ? PDA : SDA
    code_0, A_0 ← Agent(T, Q)                    # Initial generation
    Append (code_0, A_0) to C, A
    for i = 0 to N-1:
        code_{i+1}, A_{i+1} ← Debug(T, Q, code_i, A_i)
        Append (code_{i+1}, A_{i+1}) to C, A
        if Stop_condition:                         # Early termination
            break
    return C, A
```

**PoT stop condition:** Average of 4 code-similarity metrics > 0.9 (Levenshtein, difflib SequenceMatcher ratio, AST edit distance, opcode similarity).

**text2SQL stop condition:** Generated query unchanged from previous iteration, OR previously failing query now executes successfully.

Empirical justification: Tables 16-19 show most models converge within 1-2 iterations. N=3 is default.

### Stage 3: Final Answer Decision (Algorithm 3)

```
C, P, TS ← CC(T, Q, sol_cot, A_cot, C_pot, A_pot, C_sql, A_sql)
if max(C, P, TS) > θ:                             # θ = 0.1
    A_final ← argmax_{A in {A_cot, A_pot, A_sql}} {C, P, TS}
else:
    A_final ← JA(T, Q, sol_cot, A_cot, C_pot, A_pot, C_sql, A_sql)
if len(A_final) > 100:
    A_final ← FM(A_final)
return A_final
```

### Tool Models (under 500M params, ~0.6% of total latency):
| Tool | Implementation | Parameters | Function |
|------|---------------|-----------|----------|
| Scheduler (Sch) | MobileBERT + 2-layer MLP | 24.65M | Routes PoT vs text2SQL first |
| Confidence Checker (CC) | Fine-tuned DeBERTaV3-large | 435M | Scores 3 candidate answers |
| Format Matcher (FM) | Qwen2.5-Instruct (zero-shot) | 500M | Condenses verbose answers |

### Agent Models (same backbone LLM, different prompts):
| Agent | Abbreviation | Function |
|-------|-------------|----------|
| CoT Agent | CoTA | Text-based chain-of-thought reasoning |
| PoT Agent | PoTA | Python/pandas code generation |
| text2SQL Agent | t2SA | SQL query generation |
| Python Debug Agent | PDA | Refines/debugs PoT code |
| SQL Debug Agent | SDA | Refines/debugs SQL queries |
| Judge Agent | JA | Tool-calling LLM that aggregates all reasoning paths |

### CC Training Details:
- Two-stage soft labeling: (1) EM=true -> score 1.0, (2) EM=false -> score = F1 score
- Input structured with XML-style special tokens (table metadata, reasoning types, execution steps, `<NOTHING>` for skipped paths)
- Segmented training with sliding window for large tables
- Trained on 2x 80GB A100 GPUs, batch_size=18, lr=1e-6, cosine schedule, 10 epochs
- CC outputs confidence for CC-selected answer achieves ROC-AUC 0.869-0.886 (Table 9)

## 3. Trade-offs

| Dimension | Wins | Losses |
|-----------|------|--------|
| **Model compatibility** | Works across 10 models (3B to 32B, open-source + closed-source) | Lightweight tools (Sch, CC) trained on specific model distributions; may not transfer perfectly |
| **Accuracy vs speed** | 40.1% EM gain on hard tasks | 4x slower than SynTQA (27.55s vs 6.86s); each reasoning path still needs full LLM inference |
| **Reasoning diversity** | 3 complementary paths (CoT, PoT, text2SQL) catch different error modes | Sch can reduce answer diversity; on TableBench, omitting Sch sometimes yields marginally better results |
| **Inference optimization** | CC eliminates 95.8% of JA calls (easy) and 60.6% (hard); Sch eliminates 7-15% of code agent calls | Optimization is heuristic; CC threshold θ=0.1 empirically tuned, no calibration guarantees |
| **Complexity vs simplicity** | Modular agents allow flexible reasoning | 6 agents + 3 tools = 9 components to maintain; training pipeline requires curating 173K annotated samples |
| **Generalization** | Out-of-distribution benchmarks used (different from training data) | Only entity-type TableQA evaluated; excludes descriptive analysis, chart generation, multi-table QA |
| **Small model performance** | Makes 3B models competitive (EM 0.736 on Penguins with llama3.2-3B) | Small models still lag large ones significantly on complex tasks (EM 0.354 vs 0.620 on TableBench) |

## 4. Design Rationale

**Why multiple reasoning paths:** Appendix A demonstrates that no single reasoning strategy (CoT, PoT, text2SQL) dominates across model sizes, architectures, or question types. For example, in 7B models alone, text2SQL is best for Mistral, PoT for Qwen2.5-Coder, and CoT for Qwen2.5. This empirical finding is the core justification for multi-path diversity — previous work wrongly assumed task-type determinism.

**Why lightweight tools over LLM-only:** The authors explicitly argue that LLM-based verification (JA) is both expensive and less reliable than a dedicated classifier (CC). The ablation study shows CC removal causes the largest accuracy drop — the CC does not just save cost, it *improves* accuracy by avoiding over-prompting degradation (a known phenomenon from Chen et al., 2024a; Huang et al., 2025).

**Why CoT runs once:** Tables 20-21 show CoT outputs stabilize at N=1 for >95% of examples across all 10 models. Text-based reasoning simply does not benefit from iterative refinement the way code-based reasoning does.

**Why model-agnostic:** The paper positions itself against prior work that only works with GPT-series models. The practical motivation is privacy-sensitive or cost-constrained deployments where open-source models are mandatory. This is validated by showing strong performance with models as small as 3B parameters.

**Why CC > JA for candidate selection:** CC achieves ROC-AUC 0.869-0.886 while being 500M params vs full LLM inference. The high-confidence partition has EM 0.545-0.700 vs low-confidence EM 0.092-0.267, demonstrating effective separation.

## 5. Limitations & Failure Modes

1. **Does not address fundamental LLM inference cost:** Text is explicit — "Each reasoning path still requires full LLM inference, which can be computationally expensive, especially for large-scale models." MATA reduces *unnecessary* calls but the calls it does make are still expensive.

2. **Sch can harm performance in edge cases:** On TableBench, omitting Sch sometimes yields marginally better results because more reasoning diversity helps on complex questions. The Sch's routing decisions are based on table/query features, not on actual reasoning quality.

3. **CC training distribution dependence:** CC is trained on outputs from 3 specific models (phi4-14B, Qwen2.5-Coder-14B, CodeLLaMA-13B). When deployed with a completely different backbone family, CC's confidence scores may be miscalibrated (though the paper provides general calibration metrics in Table 9).

4. **Only entity-type TableQA evaluated:** Excludes descriptive analysis, anomaly detection, causal analysis, chart generation tasks from TableBench (193/886 examples excluded). No evaluation on multi-table QA.

5. **FM threshold is heuristic:** The 100-character length threshold for invoking Format Matcher is arbitrary and may incorrectly truncate valid long answers or fail to format answers just under the threshold.

6. **Mistral-7B debugging weakness:** Table 16-19 shows Mistral-7B requires significantly more debugging iterations than other models, attributed to "limited self-refinement capability." MATA's debugging strategy is less effective for models with poor code-correction ability.

7. **No latency comparison against API-based models:** Latency only reported for local models; closed-source API models' overhead is provider-dependent and not directly comparable.

8. **Training data cost:** Building the 173,664-sample training dataset for Sch and CC requires running 3 complementary reasoning paths across 57,888 T,Q pairs with 3 different LLMs — a substantial upfront computational investment.

9. **Not real-time compatible:** Average 27.55s per query on local A100 is too slow for interactive applications, even with efficiency optimizations.

## 6. Transfer to Lyra

### The One Transferable Idea

**Lightweight confidence-gated multi-path orchestration with early exit.** MATA uses small models (24-500M params) as gating classifiers that decide when expensive LLM verification is needed. The confidence checker (DeBERTaV3 435M) scores multiple reasoning outputs and only invokes the expensive Judge Agent when no candidate exceeds a threshold. This pattern — a cheap classifier controlling access to expensive LLM reasoning — reduces unnecessary LLM calls by 60-96% while *improving* accuracy by avoiding over-prompting degradation.

### Route to Lyra Workstream: **§4.1 (Agent Orchestration & Routing)**

MATA is fundamentally an agent routing architecture: a cheap scheduler decides which agents to invoke, and a cheap confidence checker decides whether to engage an expensive judge/verifier agent. This maps directly to Lyra's need for intelligent tool/agent dispatch.

**Specific application:** Lyra could use fine-tuned lightweight classifiers (e.g., DeBERTa-style or distilled student models) as confidence gates that decide:
- Whether to call an expensive Opus-level reasoning step after a cheaper Haiku/Sonnet pass
- Which specialized sub-agent to invoke next based on task features
- When parallel reasoning branches can be pruned early (agreement-based early exit)

### Impact/Effort Assessment
- **Impact:** 4 — This pattern demonstrably improves both efficiency and accuracy (not just one or the other) across diverse models
- **Effort:** 3 — Requires training lightweight classifiers for Lyra-specific agent outputs, curating training data from agent execution traces, and integrating gating logic into the orchestration pipeline
- **Tier:** **breakthrough** — The "classifier-as-gate" pattern has not been widely adopted in general-purpose agent frameworks; MATA provides rigorous empirical evidence across 10 models
