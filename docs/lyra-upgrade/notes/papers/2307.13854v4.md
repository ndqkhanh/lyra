## 1. Mechanism (step-by-step)

WebArena defines a formal environment **E = ⟨S, A, O, T⟩** with state space S, action space A, observation space O, and deterministic transition function T: S × A → S. An agent, given a natural language intent i, issues an action a_t ∈ A based on i, current observation o_t, action history a_1^{t−1}, and observation history o_1^{t−1}. A reward function **r(a_1^T, s_1^T)** measures functional correctness by inspecting whether the final and intermediate states satisfy the intent's requirements.

### Environment Architecture (4 websites + tools + knowledge)

1. **E-commerce** (OneStopShop): Adobe Magento 2, ~90k products across 300+ categories with prices, descriptions, images, reviews. Data from Webshop dump (Yao et al., 2022a).
2. **Social forum** (Reddit clone): Postmill (open-source Reddit alternative). 95 subreddits, 127,390 posts, 661,781 users. Top-50 subreddits + manual selection for northeast US cities + ML/DL topics.
3. **Collaborative development** (GitLab): Based on real gitlab-org/gitlab. 300 repositories (80% from top-90th-percentile by stars, 20% from bottom-10th), 1000+ accounts with ≥1 commit.
4. **Content Management System** (CMS): Adobe Magento Admin Portal. Sample data from official guide.
5. **Utility tools**: OpenStreetMap (northeast US only, due to storage constraints), calculator, scratchpad.
6. **Knowledge resources**: English Wikipedia (Kiwix offline server, knowledge cutoff May 2023), GitLab user manual, Adobe Commerce Merchant documentation (scraped).

All delivered as **self-contained Docker images** (one per website, no external volume mounts). Reset via container restart (seconds to ~1 minute).

### Observation Space (Multi-modal, Multi-tab)

Three rendering modes:
- **Raw DOM HTML**: Full HTML DOM tree (verbose but complete)
- **Screenshot**: RGB pixel array (for vision-based agents)
- **Accessibility tree**: Subset of DOM with only display-relevant elements. Each element annotated with role (e.g., "link", "button"), text content, properties (e.g., focusable), and a **unique element ID** (generated during tree traversal). This is the default mode. All modes support viewport-limited content for context-length management.

**Multi-tab support**: First web benchmark to support multiple browser tabs (opened tabs list + focused tab content), enabling cross-tab comparisons and tool usage.

### Action Space (3 categories)

| Category | Actions | Element Selection |
|----------|---------|-------------------|
| Element Operations | click(elem), hover(elem), type(elem, text, press_enter), press(key_comb), scroll(dir) | By pixel coordinates (x,y) OR unique element ID |
| Tab Management | tab_focus(index), new_tab, tab_close | — |
| URL Navigation | goto(URL), go_back, go_forward | — |
| Completion | stop [answer], where answer can be text or "N/A" | — |

Element IDs transform element selection into an **n-way classification problem**, eliminating coordinate disambiguation.

### Benchmark Suite

**241 templates → 812 instantiated intents** (avg 3.3 instantiations per template). Three task categories:

1. **Information-seeking** (~22.2%): Expects textual answer. Evaluated via:
   - `exact_match(â, a*)`: Identical string match (for standardized-format answers)
   - `must_include(â, a*)`: Expected content present anywhere in answer
   - `fuzzy_match(â, a*)`: GPT-4-0613 as semantic equivalence judge (prompt: "Help a teacher to grade the answer..."). Evaluated at 100% accuracy on date/time format variants.

2. **Site navigation**: Requires reaching pages meeting specific conditions. Evaluated via `r_prog(s)` — programmatic inspection of intermediate states:
   - **Locator**: DB query, website API call, or JavaScript `document.querySelector` to retrieve target content
   - **Keyword matching**: exact_match or must_include on located content

3. **Content & configuration operation**: Requires creating, revising, or configuring content. Same `r_prog(s)` evaluation with database/API/JS locators + keyword verification.

**Unachievable tasks**: Labeled "N/A". Agent must output "N/A" rather than hallucinate. Tests model's ability to recognize impossible requests.

**Human performance**: 78.24% overall (74.68% info-seeking, 81.32% others). 50% of failures from intent misinterpretation, incomplete answers, or partial execution.

### Baseline Agent Implementation

- **Models**: GPT-3.5-TURBO-16K-0613, GPT-4-0613, TEXT-BISON-001
- **Temperature**: 1.0, top-p: 0.9, max steps: 30
- **Early termination**: Same action repeated >3 times on same observation, or 3 consecutive invalid actions
- **Prompting**: 2-shot ICL with accessibility tree observations + element IDs
- **Two strategies**: (a) Direct action prediction, (b) Chain-of-Thought reasoning-before-action ("Let's think step-by-step... In summary, the next action I will perform is ```action```")
- **UA hint instruction**: "If you believe the task is impossible to complete, provide the answer as 'N/A'"

## 3. Trade-offs (wins vs loses)

| Wins | Loses |
|------|-------|
| **Full reproducibility**: Docker-based self-contained environment; no reliance on live websites that change | **Operational overhead**: Docker setup, container management, reset latency (seconds to 1 minute per reset) |
| **Functional correctness evaluation**: Checks actual system state (databases, page content) rather than surface-form action matching | **Per-task evaluator cost**: Each task requires custom `r_prog` implementation (DB queries, JS selectors, API calls) |
| **Multi-tab support**: First web benchmark enabling cross-tab workflows; emulates real browsing | **Limited scope**: 4 domains, northeast US map only; ~90k products vs millions on real Amazon |
| **Multi-modal observations**: DOM, screenshot, and accessibility tree modes enable diverse agent architectures | **Accessibility tree limitations**: Loses visual layout cues (spatial positioning, font sizes, colors); no support for vision-only reasoning in default mode |
| **User role simulation**: Pre-configured user profiles with distinct permissions and histories; automatic login via cookies | **Static roles**: Users have fixed histories; no dynamic account creation or permission changes |
| **Template-based benchmarking**: 241 templates → 812 instances; tests cross-template generalization | **Template leakage risk**: Tasks from same template may share surface patterns despite different execution traces |
| **Unachievable task design**: Tests model honesty (refusing hallucination) | **UA hint calibration**: Hint helps unachievable detection (77.78% GPT-4) but cripples achievable-task performance (54.9% false-positive "impossible") |
| **Knowledge base integration**: Wikipedia + user manuals as independent searchable websites | **Knowledge cutoff**: Wikipedia frozen at May 2023; no incremental updates |

## 4. Design Rationale

**Why self-hosted Docker over live websites?** Live websites introduce CAPTCHAs, unpredictable content modifications, configuration changes, and A/B tests — all of which prevent fair, reproducible benchmarking across time. Docker images provide deterministic initial states and full control over the environment. This is the same rationale as using a physics simulator instead of real robot hardware for early-stage RL research.

**Why accessibility tree as default observation?** The accessibility tree retains structured information (element roles, text, properties) while being significantly more compact than raw DOM (1,000s vs 10,000s of tokens). Adding unique element IDs transforms element selection from a coordinate-prediction problem into an n-way classification problem, which is easier for LLMs. This is the same design choice as in MiniWoB++ but applied to realistic websites rather than toy interfaces.

**Why functional correctness over action-sequence matching?** Complex web tasks have many valid execution paths (e.g., finding a product via search, category navigation, or direct URL). Sequence matching penalizes valid alternative trajectories. By evaluating the final system state (database contents, page content, URLs), the metric measures whether the agent *achieved the goal* regardless of *how* it got there. This aligns with the outcome-based evaluation philosophy in code generation (Chen et al., 2021) and open-domain QA.

**Why template-based intent generation?** Single-instance benchmarks test memorization. Templates with multiple instantiations (avg 3.3) test whether the agent can generalize the *procedure* rather than memorize specific answers. Two instantiations of a template require similar high-level reasoning but different concrete steps, creating a natural test of compositional generalization.

## 5. Limitations & Failure Modes

### Environment Limitations
- **Domain coverage**: Only 4 domains (shopping, forums, Git, CMS); no email, calendar, finance, healthcare, or social media beyond Reddit-style forums
- **Geographic scope**: Northeast US only for map component; no international data
- **Scale mismatch**: ~90k e-commerce products vs millions on real platforms; 300 GitLab repos vs tens of millions
- **No visual layout**: Accessibility tree strips CSS layout, colors, font hierarchy — agents cannot use visual salience cues
- **No dynamic content**: No ads, no recommendation algorithm updates, no user-generated content drift

### Agent Failure Modes (from trajectory analysis)
- **Premature "N/A"**: GPT-4 falsely labels 54.9% of feasible tasks as impossible (with UA hint). Model gives up too early when it encounters unfamiliar UI patterns
- **Observation anchoring**: Agent latches onto the first relevant-seeming information without verification. Example: uses homepage "best-selling" display instead of generating the actual historical sales report
- **Granularity blindness**: Agent overlooks subtle observation changes (e.g., text already in an input field, already-on-correct-page indicators), repeating actions until step limit
- **Action repetition loops**: Same action repeated identically >3 times triggers early termination; this happens frequently when model fails to parse observation changes
- **Domain knowledge gaps**: Non-programmers struggle with Git concepts (merge requests, forks); non-merchants struggle with CMS product configuration. Human performance drops significantly for domain-specific tasks

### Evaluation Limitations
- **Per-task evaluation engineering**: Each content/config task requires custom JS/Database locators — not scalable to arbitrary tasks
- **GPT-4 as fuzzy-match judge**: While 100% accurate on date/time formats, semantic equivalence judgment quality on complex open-ended answers is not fully validated
- **No partial credit**: Stop-action evaluation is binary (correct/incorrect); doesn't capture near-misses or partially correct trajectories

## 6. Transfer to Lyra

### The One Idea: Functional Correctness Evaluation via Programmatic State Inspection

**Core concept**: Instead of evaluating agent performance by comparing its action sequence to a gold-standard trajectory (surface-form matching), evaluate by programmatically inspecting the **final system state** — database contents, page DOM state, file system artifacts — to determine whether the agent achieved the goal. WebArena implements this through `r_prog(s)` with locators (DB queries, API calls, `document.querySelector` JS selectors) that retrieve goal-relevant state, followed by keyword matching on the retrieved content.

**Why this matters for Lyra**: Lyra's evaluation currently relies on trajectory comparison or LLM-as-judge, both of which have well-known problems (brittleness to valid alternative paths, hallucination risk in LLM judges). Programmatic state inspection is objective, reproducible, and path-agnostic — it measures *outcome* not *process*.

### Workstream Route: §4.5 — Evaluation & Testing

This feeds the evaluation infrastructure workstream. Lyra should build a `StateInspector` abstraction that, for each benchmark task, defines:
1. **Locators**: How to retrieve goal-relevant state (DB query, filesystem check, API call, element selector)
2. **Predicates**: What must be true about the located state (exact match, must include, fuzzy match for semantic equivalence)
3. **Unachievable detection**: Define tasks where the correct answer is "can't be done" to test agent honesty

### Scoring

| Dimension | Value | Rationale |
|-----------|-------|-----------|
| **Impact** | 4/5 | Changes fundamental evaluation paradigm; makes Lyra evaluations objective and path-agnostic |
| **Effort** | 3/5 | Requires per-task evaluator engineering (DB queries, JS selectors, API calls) but the pattern is clear and reusable |
| **Tier** | **breakthrough** | Fundamentally different evaluation methodology that measures functional correctness rather than trajectory similarity |

### Concrete Lyra Implementation Sketch

```python
class StateInspector:
    """Programmatic state inspection for functional correctness evaluation."""
    
    def __init__(self, locators: dict[str, Callable], predicates: dict[str, Callable]):
        self.locators = locators    # e.g., {"url": locate_current_url, "body": locate_element_text}
        self.predicates = predicates  # e.g., {"url_contains": lambda x, y: y in x}
    
    def evaluate(self, state: dict, intent: dict) -> bool:
        located = {k: loc(state) for k, loc in self.locators.items()}
        return all(pred(located[k], intent[k]) for k, pred in self.predicates.items())
```

This complements the existing LLM-as-judge pipeline by providing ground-truth functional evaluation for tasks where the outcome is objectively verifiable.
