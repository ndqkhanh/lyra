## 1. Mechanism (step-by-step)

The paper proposes a unified framework for analyzing and building trustworthy agentic AI through two orthogonal organizing principles: a **five-stage agent lifecycle** and a **defense-in-depth assurance stack**.

### Agent Workflow (Perceive -> Plan -> Act -> Reflect -> Learn)

1. **Perceive**: The agent ingests observations _o\_t_ from the environment, infers state _s\_t_, validates inputs (jailbreak detection, OOD detection, input provenance/sanitization), and quantifies uncertainty. Risks include data poisoning, adversarial perturbations, indirect prompt injection, and instruction-data boundary confusion.

2. **Plan**: The agent decomposes goals into multi-step plans using the world model, subject to constraints _K_ and budgets _B_. Safety is formalized via **Constrained MDPs (CMDPs)**: max_π J(π) s.t. J_ci(π) ≤ d_i. Lagrangian or primal-dual updates enforce constraints. Risk-sensitive objectives (CVaR) emphasize tail-risk reduction. Constitutional constraints encode norms as reusable critique-and-revision procedures.

3. **Act**: The agent executes actions _a\_t_ via tools/APIs/actuators. Pre-execution checks enforce permissions, budgets, and policy compliance; post-execution validation and rollback hooks catch violations. Runtime shields, guardrails, least-privilege tool access, sandboxing, and HITL approval gates intervene when plans would produce harmful actions.

4. **Reflect**: The agent self-evaluates outcomes, detects errors and goal/value conflicts via anomaly detection (OOD/drift), and schedules human confirmation when confidence drops. Simulation-based testing, red teaming, trace auditing, and formal verification of components catch silent failures.

5. **Learn**: The agent updates policy, value function, memory, and retrieval indexes offline/online using safe update rules. Regression gating, canary rollouts, conservative safe policy improvement, and incident-driven datasets prevent safety regressions. Non-parametric updates (prompt templates, tool schemas, memory policies) are version-controlled.

### Assurance Stack (Four Tiers)

1. **Upfront (pre-deployment)**: hazard analysis, red teaming, domain randomization, simulation certification.
2. **Training-time**: constrained RL (CPO), safe exploration, preference optimization (RLHF/RLAIF/DPO).
3. **Runtime**: shielding, least-privilege tools, anomaly detection, rollback, shadow/canary deployment.
4. **Post hoc**: telemetry, reproducible traces, failure analysis, continuous improvement.

### Privacy Formalization

- **(ε, δ)-Differential Privacy** for indistinguishability guarantees: Pr[M(D) ∈ S] ≤ e^ε Pr[M(D') ∈ S] + δ.
- **Contextual Integrity (CI)**: information flows conform to appropriate norms (who shares what with whom, under which transmission principles).
- Distinction between **static privacy** (training-time memorization) and **dynamic privacy** (runtime information flows across the agent loop).

### Evaluation Hub Architecture

Unified metric dictionary with **outcome metrics** (SR, CER, SafetyScore) and **process metrics** (CVR, DCR/Trace-Coverage, CompVR). Three-tier release gating: Tier 0 (offline regression, CVR=0), Tier 1 (simulation/sandbox stress, CER<0.1%), Tier 2 (canary/shadow with auto-rollback).

## 2. Results

This is a **survey paper** -- it synthesizes literature rather than running original experiments. Key empirical findings consolidated from surveyed work:

| Finding | Source | Value/Benchmark |
|---------|--------|-----------------|

- **SafeMind**: Graded safety assessment (SafetyScore), event-level harm tracking for embodied agents
- **AgentDojo**: Dynamic prompt injection attack/defense measurement (ASR/RR, tool-policy violations)
- **AgentHarm**: Harmful capability testing with task-level agent affordances
- **MLA-Trust**: Multimodal GUI agent privacy leakage and attribute inference benchmarks

- **ToolEmu-style sandbox**: LM-emulated sandbox evaluation for risky tool-use trajectories without real side effects

## 3. Trade-offs

| Win | Loss |
|-----|------|
| Defense-in-depth across all 5 lifecycle stages prevents single-point failures; no single stage can be fully secured by mitigating another | Increased system complexity, latency, and engineering overhead (sandboxing, authenticated protocols, policy engines) |
| Process metrics (CVR, DCR, CompVR) catch intermediate violations that outcome-only evaluation misses | Higher instrumentation cost; trace schemas and judge calibration add maintenance burden |
| Runtime shielding + least-privilege tools block catastrophic actions even when planning fails | Reduced autonomy and responsiveness; false positives block benign edge cases |
| Differential privacy provides formal ε-δ guarantees for data protection | Privacy-utility trade-off: DP reduces personalization fidelity and requires careful budget accounting under repeated queries |
| Staged rollout (shadow -> canary -> full) with automated rollback catches regressions before wide impact | Slower iteration; stronger gating delays beneficial capability updates |
| Memory governance (sensitivity tagging, expiration policies) limits long-horizon leakage | Less context/memory for personalization; potential loss of task-relevant history |
| Centralized multi-agent oversight prevents emergent cascades and collusion | Coordination overhead; potential single point of failure |
| Stronger privacy/security controls (DLP, TEEs, zero-trust intake) reduce exfiltration risk | Performance overhead, developer complexity, possible blockage of legitimate data flows |
| Credential vaulting + ephemeral tokens bound blast radius of injected instructions | Engineering overhead; more frequent re-authentication events |

## 4. Design Rationale

The authors argue that **trustworthiness must be assessed at the system level**, not the model level, because agent autonomy qualitatively expands the risk surface. Their core design decisions:

1. **Two dimensions not six**: They focus exclusively on Safety & Robustness + Privacy & System Security (treating value alignment, transparency, fairness, accountability as supporting context) because these two are "most critical for high-risk deployments." This avoids an impossibly broad survey while maintaining depth.

2. **Workflow lens (Perceive->Plan->Act->Reflect->Learn)**: Rather than organizing by method class (RL vs. prompting vs. formal methods), the lifecycle lens pinpoints _where_ failures occur and _where_ mitigations intervene. This enables a consistent risk->method mapping regardless of implementation approach.

3. **Process + outcome evaluation**: The authors argue that "an agent can produce a correct final answer while violating constraints at intermediate steps." Thus release gates require both episode-level outcomes AND step-level process signals.

4. **Defense-in-depth is mandatory**: The paper explicitly states mitigations across stages are "complementary, not substitutable" -- a poisoning attack at perceive cannot be fully neutralized by act-time guardrails.

5. **Real-world case studies anchor the theory**: The OpenClaw/Moltbook security incidents (Jan 2026) serve as a concrete demonstration of the "lethal trifecta" (access private data + process untrusted content + communicate externally).

## 5. Limitations & Failure Modes

1. **Illustrative, not exhaustive**: The authors explicitly state that risks and methods are "illustrative examples reflecting the current state of knowledge, rather than a provably exhaustive enumeration." New failure modes expected as architectures evolve.

2. **No original experiments**: As a pure survey with a case study, there are no original benchmark results, ablation studies, or empirical validation of any recommended mitigation. All performance claims are citations.

3. **Evaluation intractability**: The paper acknowledges that exhaustive long-horizon evaluation is combinatorially impossible (action sequences grow exponentially with trajectory length). Practical alternatives (dangerous-chain stress testing, time-to-violation) have limited coverage.

4. **Sim-to-real gap**: Simulation is essential for rare events but mismatch between simulated and real environments remains a "core limitation." Domain randomization helps but does not close the gap.

5. **Judge fragility**: LLM-as-a-judge can be "misled by plausible rationales even when actions are unsafe." Adversarial evaluation gaming (agents learn to optimize for judge scores) is noted as an unresolved problem.

6. **Static benchmarks saturate quickly**: Agents or training pipelines "may implicitly overfit to known test distributions," reducing benchmark validity over time.

7. **Multi-agent attribution unsolved**: "Assigning responsibility requires protocol-aware traces, message authentication, and evaluation designs that separate individual from collective failure modes" -- these are noted as open problems.

8. **Scalable oversight bottleneck**: As trajectory length grows, human oversight becomes "increasingly costly and error-prone." AI-assisted oversight "introduces recursive trust concerns that remain unresolved."

9. **Credential recovery gaps**: Once a secret leaks into agent memory/logs, it "can persist and be replayed by future plans -- turning a single exposure into sustained compromise."

## 6. Transfer to Lyra

**The ONE transferable idea**: The **three-tier release gating with process metrics** (Tier 0: offline regression with CVR=0 -> Tier 1: sandbox stress with CER<0.1% -> Tier 2: canary with auto-rollback). This directly maps to Lyra's need for a systematic evaluation and deployment pipeline that catches regressions across model updates, prompt changes, tool-policy changes, and memory-policy changes.

**Why this idea**: Lyra is designed as a multi-stage agent with planning, tool use, memory, and scratchpad. The paper's risk->stage mapping (Table 4) and release-gating tiers (Table 7) provide an immediately actionable template for Lyra's evaluation infrastructure. The key insight is that Lyra should not be evaluated on final task success alone -- it needs step-level CVR (constraint violation rate) tracking and trace completeness (DCR) to catch intermediate tool misuse, policy violations, and evidence-free reasoning.

**Workstream route**: **Section 4.5 (Verification & Safety)** -- this paper provides the evaluation architecture and gating framework for the verification subsystem.

**Impact**: 4/5 -- directly applicable to Lyra's multi-stage agent architecture; the process-metric framework is immediately implementable.
**Effort**: 4/5 -- requires building trace schemas, regression packs, sandbox infrastructure, and CI-integrated metric dashboards across all Lyra stages. Non-trivial engineering.
**Tier**: **breakthrough** -- this structured release-gating evaluation framework, combined with the stage-aligned threat model, gives Lyra a principled path to production deployment that most agent projects lack.
