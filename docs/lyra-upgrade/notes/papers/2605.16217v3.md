## 1. Mechanism

### 1.1 Two-Agent Architecture

Argus consists of two cooperating agents sharing a Directed Acyclic Graph (DAG) of evidence:

- **Searcher:** A stateless ReAct agent that takes a single query, executes a rollout of thoughts→tool-calls→observations (SEARCH/VISIT/ANSWER), and returns the trajectory trace H. No inter-Searcher communication, no access to the graph.
- **Navigator:** Maintains the shared evidence graph G, orchestrates verification, and produces the final answer.

### 1.2 Evidence Graph Structure

The graph is formally defined as:

```
G = (E, C, A)
A ⊆ (E ∪ C) × C × {+1, −1}
```

- E = evidence nodes (raw findings, each tagged with source URL)
- C = claim nodes (tentative claims from Searcher rollouts, including final answers)
- A = directed arcs connecting evidence/claims to claims, labeled +1 (support) or -1 (contradict)

### 1.3 Three-Stage Pipeline

**Stage I — Searching for Evidence.** The Navigator rewrites the input question q into one or more angle-diverse queries. In solo mode: one rewrite; in parallel mode: K rewrites. Each query is dispatched to a Searcher for an independent ReAct rollout.

**Stage II — Verifying and Assembling the Graph.** The Navigator parses each returned trajectory H into evidence and claim nodes, attaches them to G via support/contradict arcs. Evidence nodes are deduplicated at the source-URL level. The Navigator then:
1. Labels every claim node as `supported`, `contradicted`, or `unverified` using a learned policy (not a fixed counting rule)
2. Inspects G holistically (not per-claim) and emits a batch of verification queries V = {v₁, ..., vₘ} targeting:
   - Unverified claims → seek corroborating sources
   - Contradicted claims → seek authoritative conflict resolution
   - Unaddressed sub-questions → direct sub-queries
3. Dispatches one Searcher per verification query, all running concurrently
4. Repeats until it emits an end-of-loop token or compute budget B is exhausted

**Stage III — Synthesizing the Final Answer.** The Navigator clears its working context from the loop and reasons over (q, G) alone via synthesis policy π_syn:

```
y* = π_syn(q, G)
```

Every factual claim in y* traces back to specific evidence nodes and source URLs, making (y*, G) fully auditable.

### 1.4 Training with GRPO + Contrastive Reward

Both agents share a Qwen3.5-35B-A3B MoE backbone (35B total, 3B active, 256 experts top-8). The Searcher is SFT-only (~10K WebSailor-v2 trajectories). The Navigator is warm-started with SFT then RL-trained end-to-end with GRPO.

**Contrastive Reward:**
```
Rᵢ = clip(R_w/ᵥ + λ(R_w/ᵥ − R_w/o ᵥ), 0, 1),  λ = 0.5
```

- R_w/ᵥ = LLM-as-judge score on synthesis using post-verification graph G_post
- R_w/o ᵥ = score using pre-verification graph G_pre (shadow pass, no gradient)
- The bonus λ(R_w/ᵥ − R_w/o ᵥ) isolates verification's causal contribution

**GRPO Objective:**
```
L_GRPO(θ) = E_Hᵢ [min(ρᵢ A(Hᵢ), clip(ρᵢ, 1−ϵ, 1+ϵ) A(Hᵢ))] − β D_KL(π_θ || π_θref)
```

Where A(Hᵢ) = Rᵢ − mean(R_j) is group-relative advantage. N=8 rollouts per prompt, ϵ=0.2, β=0.001.

### 1.5 Key Invariant

Training uses only single Searcher trajectories per question. At inference, parallelism K is a configuration knob — the Navigator's policy operates on (q, G) alone and generalizes zero-shot to K>1 without retraining.

### 2.5 Training Dynamics

- Avg. reward on held-out BrowseComp rose from 0.54 to 0.80 across 100 GRPO steps
- Verified reward R_w/ᵥ consistently above unverified R_w/o ᵥ (gap ~0.05-0.10)
- Verification trigger rate rose from 0.52 to 0.75 and plateaued as synthesis nodes grew
- Training: 64×H200 GPUs, ~1.5 days wall-clock, 5,298 decontaminated training questions

## 3. Trade-offs

| Win | Cost |
|-----|------|
| Compositional evidence assembly eliminates duplicate rollouts | High inference budget: 0.4M–25.6M tokens/question |
| Context-efficient: 1200:1 compression decouples Navigator from Searcher count | Wall-clock bottleneck: slowest parallel Searcher dominates latency |
| Zero-shot transfer of Navigator across Searcher backbones | Requires pretrained strong Searcher; cannot fix fundamentally broken search |
| Fully auditable/source-traced answers | Training cost: 64×H200 GPUs for 1.5 days |
| Log-linear scaling with no observed ceiling at K=64 | Only tested with one Navigator backbone (Qwen-35B-A3B) |
| +12.6 on GAIA, +6.2 on Seal-0 over strongest proprietary | Inherits Searcher recall ceiling from absent/paywalled sources |
| Solo mode already beats best proprietary on 3 of 8 benchmarks | Not designed for low-latency use cases |

## 4. Design Rationale

**Why evidence graph over trajectory aggregation:** Parallel rollout aggregation (majority vote, best-of-N, LLM aggregation) saturates because K actors retrieve overlapping evidence. The central insight is that deep research answers are *compositional* — they require complementary pieces of evidence, not multiple guesses at the full answer. A DAG makes missing pieces and contradictions structurally computable, transforming the problem from trajectory selection to evidence composition.

**Why contrastive RL reward:** A binary correctness reward would credit rollouts where the verification stage added nothing. The contrastive term λ(R_w/ᵥ − R_w/o ᵥ) directly rewards verification queries that causally improve the answer, isolating the signal the Navigator needs to learn effective dispatch.

**Why batched graph-level verification:** Per-claim verification misses interdependencies between claims. Holistic graph inspection lets the Navigator identify patterns across claims (e.g., a single missing constraint undermines multiple claims simultaneously) and produce a coordinated batch of targeted queries.

**Why single-Searcher training with zero-shot parallelism:** Training with K>1 Searchers in the loop would require RL credit assignment across agents, a known-hard problem. Training on single trajectories keeps the policy simple while the abstraction (q, G) ensures inference-time parallelism works without retraining.

## 5. Limitations and Failure Modes

1. **Inference compute cost:** Per-question token consumption ranges from 0.4M (K=1) to 25.6M (K=64), making it unsuitable for low-budget or real-time use cases.
2. **Wall-clock latency:** The slowest Searcher in a parallel batch dominates end-to-end time. Navigator synthesis is a single forward pass, but Searcher variance adds tail latency.
3. **Searcher recall ceiling:** Argus cannot answer questions whose underlying web sources are absent, paywalled, or inaccessible. Performance scales roughly linearly with Searcher backbone quality (Table 2).
4. **Single Navigator backbone:** All experiments use Qwen3.5-35B-A3B as Navigator. No evidence the approach works with smaller/weaker navigator models.
5. **Standard agentic risks:** Misinformation propagation, copyright concerns around web content reuse. Source tracing mitigates but does not eliminate these risks.
6. **Format rigidity:** RL training enforces a strict state machine over DAG output format; rollouts violating format are rejected. Brittleness to format drift is unexplored.
7. **Only English and Chinese evaluated:** BrowseComp-ZH tests Chinese, but no other languages tested.

## 6. Transfer to Lyra

### The One Transferable Idea

**Structured Evidence DAG as a compact context compression and multi-source verification substrate.** Instead of aggregating raw agent trajectories (which saturates context and duplicates evidence), maintain a shared DAG where evidence and claims are nodes, support/contradiction are edges. This lets the orchestrator (Navigator analog) reason over a structured representation that stays compact even as parallel agent count scales. The 1200:1 compression ratio proves this decouples reasoning context from search budget.

### Workstream Route

**§4.2 (Memory Subsystem) and §4.7 (Multi-Agent Orchestration).** The evidence DAG pattern addresses two Lyra concerns simultaneously: (a) compact representation of accumulated evidence across conversational turns (memory), and (b) structured coordination between parallel research sub-agents (orchestration). It also touches §4.3 (Context Management) via the context-compression property.

### Impact/Effort/Tier

- **Impact:** 4 — Could meaningfully improve Lyra's ability to synthesize across multiple sources without context blowup, and enables auditable source-traced answers.
- **Effort:** 4 — Requires implementing a DAG construction pipeline, verify-and-dispatch loop, and potentially GRPO-style training; significant engineering beyond simple integration.
- **Tier:** **Breakthrough** — The compositional evidence assembly paradigm represents a qualitative shift from trajectory aggregation and applies directly to Lyra's core architecture. The cross-backbone transfer result suggests the Navigator abstraction is robust enough to adopt independently of Searcher implementation.
