## 1. Mechanism (step-by-step)

Evo-Attacker formulates tool attacks against LLM-based Multi-Agent Systems (LLM-MAS) as a memory-augmented reinforcement learning process with three synergistic stages:

### Stage 1: Attack Memory Generation
- Bootstrap a dynamic attack memory **M_A** (initially empty) through exploration.
- Each successful attack episode (verified system failure) is archived as a structured entry:
  ```
  m^(e) = ⟨X_ctx, T_trace⟩
  ```
  where `X_ctx = (G, T, a*)` encodes the communication graph, task, and target agent; `T_trace = {(τ_t, φ_t, r'_t)}^K_{t=1}` records the full sequence of tool calls, modifications, and perturbed returns.
- Memory accumulates as: `M_A = {m^(e) | e = 1, ..., N_M}`

### Stage 2: Memory-Augmented Attack (Deliberative Reasoning)
The attacker policy π_θ executes a three-phase loop at each turn t:

**Retrieve**:
- Generate retrieval query `q_t ~ π_θ(·|X_ctx, x_t)` where `x_t = ⟨C_t(a*), H_{t-1}⟩` combines current tool calls with interaction history.
- Query M_A via semantic similarity to retrieve top-k memories `M_t^(k) ⊂ M_A`.

**Reflect**:
- Perform feasibility analysis on retrieved experiences:
  ```
  c_t, d_t ~ π_θ(·|M_t^(k), X_ctx, x_t)
  ```
- Decision `d_t ∈ {ATTACK, CONTINUE, NOOP}`:
  - ATTACK: sufficient guidance, suitable vulnerability.
  - CONTINUE: insufficient information, refine query with `c_t` and loop.
  - NOOP: unsuitable interaction, preserve budget.

**Modify**:
- On ATTACK: target tool-call index `i_t` and synthesize modification instruction:
  ```
  (i_t, φ_{t,i_t}) ~ π_θ(·|c_t, x_t)
  ```
- Apply the modifier to produce adversarial return `r'_{t,i_t}` delivered to the target agent.
- Budget B constrains total modifications per episode.

### Stage 3: Optimization via Attack-Flow GRPO
- Define trajectory `ζ = [(s_1, y_1), ..., (s_L, y_L)]` interleaving attacker outputs and frozen environment responses.
- Composite reward:
  ```
  R(ζ) = I(J(o_sys) = 1) + λ · R_struct(ζ)
  ```
  where `I(·)` indicates system failure and `R_struct` penalizes format violations.
- Group-relative advantage over G=8 parallel rollouts:
  ```
  A_i = (R(ζ_i) - mean({R_1...R_G})) / std({R_1...R_G})
  ```
- Policy gradient with masked tokens and KL regularization:
  ```
  L(θ) = (1/G) Σ_i (1/L_i) Σ_{t∈I_atk} [min(ρ_t·A_i, clip(ρ_t, 1±ε)·A_i) - β·KL(π_θ||π_ref)_t]
  ```
  where `I_atk` iterates exclusively over attacker-generated tokens (victim agent and tool return tokens are masked).

### Threat Model
- Gray-box: attacker compromises tool channels of a single target agent a*.
- Capabilities: intercept tool invocations, replace returns r with r'.
- Blind to: inter-agent messages, agent internal states.
- Constraint: ≤B tool return modifications per episode.

## 2. Results (real benchmark numbers)

### Main Attack Effectiveness (Table 1 — Flat architecture, representative)
| Domain | Benchmark | w/o Attack | Evo-Attacker | Degradation (↓) |
|--------|-----------|-----------|-------------|-----------------|
| Code   | MAB.code (TS) | 66.2 | 39.2 | ↓27.0 |
| Code   | HumanEval (Pass@1) | 67.5 | 38.6 | ↓28.9 |
| Research | MAB.research (TS) | 80.0 | 54.6 | ↓25.4 |
| Research | DRB (RACE) | 34.8 | 22.1 | ↓12.7 |
| Web    | WebArena (SR) | 33.3 | 14.5 | ↓18.8 |
| Web    | WebShop (Score) | 61.6 | 35.3 | ↓26.3 |

Evo-Attacker achieves the **largest performance degradation** across all benchmarks and architectures, consistently surpassing all baselines (Forced Output, InjecAgent, Web Fraud, Prompt Infection). Worst baseline typically achieves only ↓2-8 in code domains where Web Fraud is inapplicable.

### Ablation Study (Table 2 — averaged across subtasks)
| Configuration | Code ↓ | Research ↓ | Web ↓ |
|--------------|--------|------------|-------|
| Full Evo-Attacker | ↓26.5 | ↓18.6 | ↓22.3 |
| w/o Retrieval (RT) | ↓14.9 | ↓8.4 | ↓13.9 |
| w/o Reflection (RF) | ↓17.5 | ↓11.5 | ↓15.4 |
| w/o Attack-Flow GRPO (RL) | ↓12.2 | ↓7.7 | ↓11.4 |

RL removal causes the most severe degradation, confirming Attack-Flow GRPO is essential for long-horizon planning.

### Cross-Model Robustness (Table 3)
- GPT-4o-mini (zero-shot, no training): Code ↓24.7, Research ↓14.4, Web ↓23.5
- Ministral-3-8B (RL-optimized): Code ↓26.3, Research ↓16.8, Web ↓21.9
- RL-optimized open-source models match or surpass closed-source zero-shot performance.

### Stealthiness
- 85-95% bypass rate against detectors: GPT-4o-mini, GPT-4o, Qwen3-72B, Gemini-2.5-flash, Deepseek-V3.

### Sensitivity Analysis
- Attack budget 1→5: monotonic improvement, stronger in complex tasks (MAB.research: ~25→35 score decline).
- Reflection depth 1→5: diminishing returns after depth 3.
- Retrieved memories 0→20: steady gains, diminishing after ~10.

## 3. Trade-offs

| Win | Lose |
|-----|------|
| Generalizes across Flat/Chain/Hierarchical architectures without per-architecture tuning | Higher computational cost and token consumption (deliberative reasoning + GRPO) |
| RL enables small open-source models (8B) to match/surpass closed-source (GPT-4o-mini) | Training requires G=8 parallel rollouts per step; 500+50 bootstrap samples needed |
| Memory enables continual self-evolution against non-stationary environments | Memory quality depends on bootstrap sample diversity |
| Three-phase reasoning (Retrieve-Reflect-Modify) avoids wasteful budget expenditure | CONTINUE loop adds variable latency; N_max cap may truncate useful reasoning |
| Model-agnostic: effective against GPT, Gemini, Llama, Ministral victim backbones | Stealthiness depends on domain richness (lower in syntax-rigid code tasks) |
| Terminal reward broadcasting solves credit assignment without dense intermediate rewards | Single terminal reward may be noisy for very long horizons |

## 4. Design Rationale

The core insight is that **static attack templates fail in non-stationary multi-agent environments** because tool schemas, agent policies, and communication topologies evolve. Evo-Attacker addresses this via three design choices:

1. **Memory over templates**: Archives proven attack patterns per context rather than hard-coding heuristics. This enables generalization across domains (code, research, web) that baselines like Web Fraud (web only) cannot achieve.

2. **Deliberative reasoning over single-step injection**: The Retrieve-Reflect-Modify loop allows the attacker to assess context before acting, avoiding detection and budget waste. This is critical in hierarchical architectures where naive injections are filtered at parent nodes.

3. **Attack-Flow GRPO over standard RL**: Broadcasting terminal rewards to all reasoning tokens solves the credit assignment problem unique to long-horizon tool attacks, where early retrieval/reflection decisions may only pay off many turns later. Masking non-attacker tokens ensures the policy learns from its own interventions, not environmental noise.

Why Qwen3-8B for attacker and Qwen3-14B for victim: balances computational tractability with sufficient reasoning capacity for both sides.

## 5. Limitations & Failure Modes

1. **Computational overhead**: Deliberative reasoning and GRPO optimization incur significantly higher token consumption and compute cost compared to template-based attacks. Noted as "a necessary trade-off."

2. **Narrow detector scope**: Stealthiness evaluated only against LLM-based semantic detectors. Does not address non-semantic defenses such as cryptographic signature verification of tool returns, strict whitelist filtering of tool arguments, or deterministic schema validation.

3. **Controlled environments only**: All experiments run in simulated settings with no real-world services. Transfer to production deployments (where tool APIs have rate limits, authentication, schema enforcement) is unvalidated.

4. **Budget constraint assumption**: B=3 may be unrealistic when defenders employ anomaly detection over longer horizons.

5. **Bootstrap dependency**: Initial attack memory requires 500+50 labeled samples; zero-shot cold-start performance before exploration is weak.

6. **Single-agent targeting**: Only compromises one target agent; systems with redundant verification agents might detect discrepancies.

## 6. Transfer to Lyra

**The one transferable idea**: Memory-augmented deliberative RL for adversarial self-testing of tool-execution pipelines.

**Adaptation**: Flip Evo-Attacker's attack pipeline into Lyra's internal red-teaming subsystem. Instead of attacking tool returns, Lyra would (1) maintain an "adversarial memory" of past brittleness patterns across its tool ecosystem, (2) use Retrieve-Reflect-Modify reasoning to probe its own tool responses for edge-case failures, and (3) apply Attack-Flow GRPO-style terminal reward broadcasting to train a self-defense policy that hardens tool call schemas against injection. This directly fuels Lyra's **reliability verification loop** — the memory of discovered vulnerabilities becomes a continuously evolving test suite.

**Workstream**: §4.5 (Safety & Reliability), specifically the adversarial robustness / red-teaming sub-stream.
