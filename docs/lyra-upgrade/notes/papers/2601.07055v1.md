## 1. Mechanism

Dr.Zero is a data-free self-evolution framework for search-augmented LLMs organized as an alternating proposer-solver training loop. Both the proposer and solver are initialized from the same base LLM and share access to an external search engine (E5-base retriever over English Wikipedia). No human demonstrations, labeled questions, or annotated answers are used at any point.

### 1.1 Architecture & Self-Evolution Feedback Loop

The framework alternates two training phases:

```
Step 1: Proposer Update (HRPO)
  proposer → generates question+answer pairs → solver evaluates → difficulty reward → HRPO updates proposer

Step 2: Solver Update (GRPO)
  proposer → generates training QA pairs → solver solves them → outcome reward → GRPO updates solver
```

As the solver improves, it raises the bar for question difficulty, which in turn pushes the proposer to generate harder queries — creating an automated curriculum.

### 1.2 Proposer Training: Hop-Grouped Relative Policy Optimization (HRPO)

**Problem it solves:** Standard GRPO requires nested sampling (m questions, n predictions each = (m+1)*n rollouts per prompt). For multi-turn search agents with tool calls, this is prohibitively expensive.

**HRPO algorithm (Equation 2-3):**

1. Proposer generates exactly ONE question per prompt (no nesting).
2. Generated QA pairs are clustered by **hop count** h ∈ H (number of reasoning steps).
3. Within each hop-group, solver rewards r are standardized to compute advantages:

```
A_i,h = (r_i - E_j∈Ih[r_j]) / √(Var_j∈Ih[r_j] + δ)
```

4. The proposer policy gradient is:

```
J(θ) = E_{(x,y)~π_θ, n}[ A_i,h * log π_θ(y|x) ] - βD_KL
```

No ratio clipping (strictly on-policy). Group size in HRPO = 1, reward size = 5, KL coefficient = 0.

**Proposer reward function (Equation 4):**

```
r(y, {ŷ_i}^n_i=1) = I(0 < k < n) * (n-k)/(n-1) + r_f

where k = Σ I(y = ŷ_i)  (number of correct solver predictions out of n)
```

The reward is:
- **0** if the solver gets all n answers correct (too easy) or all incorrect (too hard/unsolvable).
- **Maximized** (=1 + r_f) when exactly 1 out of n is correct — the "sweet spot" of difficult-but-solvable.
- **Decays linearly** as k increases.
- A format reward r_f (max 0.5) enforces structural compliance: `<think>` blocks, valid tool calls, `<question>` tags, `<answer>` tags.

### 1.3 Solver Training: Standard GRPO

The solver is trained via GRPO (group size = 5) on QA pairs generated by the current proposer. The reward is purely outcome-based (correctness of final answer against synthesized ground truth). Policy gradient uses the standard clipped surrogate with ε = 0.2 and KL penalty β = 0 or 0.001.

### 1.4 Training Schedule

- Each iteration: 50 steps proposer (HRPO), then 50 steps solver (GRPO).
- Default question hop-distribution: 4:3:2:1 ratio for 1-hop:2-hop:3-hop:4-hop.
- Total: 3 iterations = 150 steps per model, significantly fewer than R1/Search-R1.
- Base models: Qwen2.5-3B-Instruct and Qwen2.5-7B-Instruct.
- Precision: BF16-mixed, AdamW with β=(0.9, 0.999), learning rate 5e-7 to 1e-6, batch size 256, max sequence 3072-4096 tokens, max 5 turns per rollout.

### 1.5 Search Engine

E5-base model for embedding queries and documents (English Wikipedia dump). Top-3 documents retrieved via approximate nearest neighbor (ANN) search. Same engine for all baselines.

## 3. Trade-offs

### Wins

| Aspect | Gain |
|---|---|
| Zero training data | Matches/surpasses supervised baselines without any human questions, demonstrations, or labels |
| Compute efficiency | HRPO reduces proposer training rollouts by 4x (from ~20 to ~5 per prompt) |
| Generalization (1-hop) | 3B model beats Search-R1 by 22.9% on NQ; strongly generalizes on knowledge-intensive retrieval |
| Automated curriculum | Proposer-solver feedback loop generates increasingly difficult questions without manual difficulty tuning |
| Decoupling proposer/solver | Eliminates memorization issues seen in unified models (e.g., SQLM) |

### Loses

| Aspect | Cost |
|---|---|
| Multi-hop trade-off | HRPO achieves lower scores than GRPO on multi-hop tasks (Bamboogle: 0.200 vs. 0.272) — hop-grouping loses per-question signal |
| Performance plateau | Gains saturate after 2-3 iterations; cannot scale indefinitely with more self-play rounds |
| 7B instability | Larger model exhibits more training instability (inconsistent token IDs across multi-turn steps) |
| Base model ceiling | Self-evolution cannot exceed the fundamental capability limits of the base model |
| Retrieval dependency | Relies on a high-quality search index (E5 + Wikipedia); performance degrades sharply without the initial document anchor |
| Length constraints | Models truncate at max sequence length (3072-4096 tokens), causing incomplete trajectories on complex multi-hop tasks |

## 4. Design Rationale

**Why proposer-solver decoupling:** Prior work (SQLM) used a single unified model as both proposer and solver, which led to memorization and poor generalization. Decoupling prevents the model from simply regurgitating training patterns and forces true multi-hop reasoning.

**Why HRPO over GRPO for the proposer:** Standard GRPO requires nested sampling (multiple questions per prompt, multiple answers per question), which scales as O(mn) rollouts. For multi-turn search agents where each rollout involves multiple tool calls, this is computationally prohibitive. HRPO avoids nesting by generating one question per prompt and using hop-grouped baselines for low-variance advantage estimation.

**Why hop-based grouping:** Questions with the same number of hops share structural similarity (same number of search calls, similar reasoning depth). Grouping by hop creates a natural, interpretable clustering that aligns the difficulty distribution and stabilizes the advantage baseline compared to a global baseline (REINFORCE++) which fails from high variance.

**Why the linear difficulty reward:** The reward `(n-k)/(n-1)` for 0<k<n creates a gradient that peaks at exactly one correct solution. This is more effective than a parabolic reward peaking at 50% accuracy because it provides a continuous signal that distinguishes between "barely too easy" (k=2) and "very easy" (k=n-1), encouraging the proposer to push toward the frontier.

**Why 4:3:2:1 hop ratio:** Empirical finding — smaller models benefit from strengthening fundamental search on simpler questions, while larger models also benefit from multi-hop curriculum. The ratio balances both.

## 5. Limitations & Failure Modes

1. **Multi-hop ceiling:** HRPO's group-level baseline discards per-question granularity, causing weaker signals on complex multi-hop questions. GRPO still wins on Bamboogle and MuSiQue.

2. **Iteration saturation:** After 2-3 iterations (100-150 steps per model), performance plateaus or even regresses (7B iter 3 drops from 0.372 to 0.360). Self-evolution is not open-ended.

3. **Training instability at scale:** The 7B model exhibits more frequent failures from inconsistent tokenization/IDs across multi-turn reasoning steps. These failures are non-trivial to diagnose.

4. **Truncation failures:** At max sequence length (3072-4096 tokens), the solver occasionally fails to complete multi-hop trajectories, particularly for 4-hop questions.

5. **Format deviation:** During long-context generation (high-hop questions), models occasionally violate formatting constraints (missing closing tags, malformed tool calls).

6. **Single-source evaluation:** All evaluation uses exact match with a single retrieval corpus (English Wikipedia via E5). Generalization to other corpora, languages, or retrieval backends is not tested.

7. **Base model lock-in:** Self-evolution cannot transcend the intrinsic capability ceiling of the base model. A Qwen2.5-3B will never reach 7B performance through self-play alone.

8. **Seed document dependency:** The proposer requires an initial seed document to anchor question generation. Without it (Table 7), performance drops 19.4%. The framework cannot generate questions ex nihilo.

9. **No factuality verification:** The proposer can generate factually incorrect answers (hallucinated ground truth), which then trains the solver on incorrect signals.

## 6. Transfer to Lyra

### The ONE Idea

**Self-evolving search-agent training via alternating proposer-solver RL with hop-grouped advantage estimation (HRPO), using zero external training data.**

The proposer generates diverse multi-hop questions anchored on seed documents; the solver's success/failure at answering them produces a difficulty signal; HRPO clusters questions by complexity (hop-count) to compute low-variance advantages without nested sampling; and the symbiotic loop creates an automated curriculum. Lyra's multi-turn agent architecture can directly adopt this paradigm to bootstrap training data, reduce human annotation cost to near-zero, and continuously improve agent reasoning capabilities through self-play.

### Workstream Route: §4.1 (Agentive Reasoning Engine) and §4.2 (Training/Optimization Pipeline)

This feeds two workstreams:
- **§4.1:** The proposer-solver architecture with external tool (search) access is directly applicable to Lyra's multi-turn reasoning engine.
- **§4.2:** HRPO provides a concrete, efficient RL training algorithm for Lyra's agent optimization pipeline that avoids the cost of human demonstrations.
