## 1. Mechanism (step-by-step)

### 1.1 Problem Formulation

CODESKILL learns a **skill-management policy** M_θ for a frozen downstream coding agent π. Given:
- Trajectory evidence τ = (o_1, a_1, ..., o_T, a_T, y) from coding tasks
- Current skill bank B = {s_i}^N_{i=1}
- Retrieved skill-bank context C ⊆ B

M_θ outputs an operation u = (a, z) where a ∈ A (operation type) and z is the content. The objective:

```
max_θ E_{τ, x'} [ R_task( π(x' | B') ) ]
where u = M_θ(τ, C), B' = Update(B, u)
```

### 1.2 Multi-Granularity Skill Bank

Two skill types organized into a single bank B:

| Type | Scope | Example Trigger |
|---|---|---|
| **Task-level** | High-level strategies for a task family | "Inspecting repository, localizing issue, validating fix" |
| **Event-driven** | Local guidance for recurring execution events | "Command failures, error messages, test-output patterns" |

Each skill is a markdown instruction file with: title, trigger condition, actionable instructions.

### 1.3 Three Skill-Management Components

**Extraction.** Input: trajectory evidence (single or small set of related trajectories). Output: new task-level skill, new event-driven skill, or `skip`. Task-level extraction abstracts high-level procedures; event-driven extraction captures local execution patterns.

**Evolution.** Input: existing skill + new/failed trajectory evidence. Output: revised candidate skill or `skip`. Updates applicability conditions or procedural guidance when new evidence reveals missing cases, better procedures, or failure modes.

**Maintenance.** Input: candidate skill + retrieved similar skills from bank. Output: `add` (inserts new non-overlapping knowledge), `merge` (combines overlapping but complementary skills), or `drop` (rejects redundant, weakly grounded, overly specific, or non-transferable skills).

### 1.4 Skill Usage at Inference

Dense semantic similarity retrieval (sentence embeddings): task-level skills matched to task goal; event-driven skills matched to agent's current reasoning + observation via trigger conditions. Skills injected as prior knowledge into the frozen coding policy prompt.

### 1.5 Training Pipeline

**Phase 1 — Supervised Warmup.** Teacher model (GPT-5.4-mini) generates structured operation targets u* = (a*, z*) from trajectory evidence + skill-bank context. ~12,856 SFT examples across extraction, evolution, and maintenance actions. Fine-tune Qwen3.5-4B-Instruct with LoRA (qwen3_nothink template, 14k max seq len, bf16, 2 epochs, lr=1e-4, cosine scheduler, ~20h on 4×H100).

**Phase 2 — RL with GRPO.** Group Relative Policy Optimization:

```
L_GRPO = -(1/G) Σ_j [ min(ρ_j Â_j, ρ̄_j Â_j) - βD_j ]

where ρ_j = M_θ(u_j|q) / M_θold(u_j|q)
      ρ̄_j = clip(ρ_j, 1-ε, 1+ε)
      Â_j = (R_j - μ_R) / (σ_R + ε_A)
      D_j = KL penalty to reference model
```

**Hybrid Reward.** The reward for each operation u:

```
R(u; q) = λ·R_Q(u; q) + R_A(u; τ^u_π) · R_E(u; x_u, π)
```

- **R_Q ∈ [0,1]:** Rubric-based LLM-as-judge quality reward. Evaluates grounding, reusability, specificity, format, and actionability with action-specific criteria.
- **R_E:** Execution reward = V(τ^u_π) - b_π(x_u). Measures verifier improvement over no-skill baseline. Baseline b_π(x_u) = (1/n) Σ V(τ^0_{π,i}), pre-cached with n=4 rollouts.
- **R_A ∈ [0,1]:** Alignment factor. Judges whether the rollout actually matches the skill trigger condition and follows its workflow. Addresses credit assignment — the agent might succeed for reasons unrelated to the skill.
- **λ = 0.25:** Dense quality supervision weight.

**Phase 3 — Three-Stage Curriculum Training.** Follows the skill bank lifecycle:
1. Stage 1: Extraction only (trajectory evidence → new skills)
2. Stage 2: Extraction + Evolution (existing skills revised with new evidence)
3. Stage 3: Full pipeline (extraction + evolution + maintenance)

This curriculum enables data reuse: extracted skills become evolution candidates, both feed maintenance. ~660 unique instances across all phases. Total RL training: ~210h on 4×H100, lr=2e-6, group size=6, 500 steps.

**Reverse Retrieval for Evaluation Instances.** When computing execution reward for a generated skill s_u, select evaluation task x_u ~ TopK(s_u, D_task) by using the skill content to retrieve the most relevant task goals or baseline trajectories (reverse direction from inference-time retrieval).

### 1.6 Algorithm (GRPO Training Loop)

```
1. For all tasks x ∈ D: pre-cache no-skill baseline b_π(x) via n=4 rollouts
2. For each prompt q:
   a. Sample G=6 operations {u_j} from old policy M_θold
   b. For each u_j: compute R_Q (quality); if skill produced, reverse-retrieve x_j,
      run skill-conditioned rollout τ_j ~ π(·|x_j, s_j), compute R_E + R_A
   c. Compute group-normalized advantage Â_j
   d. Update M_θ with GRPO objective
```

## 2. Results (benchmark numbers)

### 2.1 Main Results (Frozen coding policy: Qwen3.5-35B-A3B)

| Method | EnvBench-Py Succ↑ | EnvBench-Java Succ↑ | SWE-Bench V. Succ↑ | Terminal-Bench 2 Succ↑ | Avg Succ↑ | Avg Steps↓ |
|---|---|---|---|---|---|---|
| No-skill baseline | 6.98 | 27.10 | 57.33 | 25.88 | 29.57 | 44.12 |
| Subtask Memory (GPT-5.4-mini) | 9.30 | 32.71 | 61.33 | 30.59 | 33.48 | 39.76 |
| Prompt Skill Mgmt (GPT-5.4-mini) | 11.63 | 36.45 | 64.67 | 28.24 | 35.25 | 36.99 |
| SFT-CODESKILL (Qwen3.5-4B) | 13.95 | 35.51 | 64.00 | 24.71 | 34.54 | 38.04 |

**Key deltas:**
- CODESKILL vs no-skill: **+9.69** average pass rate (**+32.8% relative**)
- CODESKILL vs strongest baseline (Prompt Skill Mgmt GPT-5.4-mini): **+4.01** average pass rate (**+11.4% relative**)
- CODESKILL vs SFT-only: **+4.72** average pass rate (**+13.7% relative**)
- Reasoning steps reduced: 44.12 → 35.15 (**-20.3%**)

### 2.2 Generalization to Different Coding Policy (GPT-5.4-mini as π)

| Method | Avg Succ↑ |
|---|---|
| No-skill baseline | 21.80 |
| Prompt Skill Mgmt (GPT-5.4-mini) | 27.86 |
| **CODESKILL (Qwen3.5-4B)** | **30.73** |

CODESKILL improves over no-skill by **+8.93** (+41.0% relative) and over strongest baseline by **+2.87** (+10.3% relative), even though it was trained with Qwen3.5-35B-A3B feedback. Demonstrates policy-transfer generalization.

### 2.3 Out-of-Distribution Generalization (Terminal-Bench 2)

Terminal-Bench 2 was never used in training. CODESKILL improves from 25.88 (no-skill) to 34.12 (+8.24 pass rate). SFT-CODESKILL actually *degrades* on Terminal-Bench 2 (24.71 vs 25.88), showing RL is essential for OOD transfer.

### 2.4 Ablation: Lifecycle Components

| Variant | Avg Succ↑ | Skill Bank Size |
|---|---|---|
| No-skill baseline | 29.57 | 0 |
| Event-driven only | 34.51 | 916 |
| Task-level only | 32.35 | 336 |
| Extraction only | 38.63 | 1252 |
| Extraction + Evolution | **40.75** | 1252 |
| Full lifecycle (CODESKILL) | 39.26 | **676** |

Full lifecycle shrinks bank by **46.0%** (1252→676) with only ~2% pass rate cost.

### 2.5 Training Rewards

- 20-step trend reward: 0.004 (steps 1-20) → 0.158 (steps 180-200), showing gradual improvement
- Quality reward stabilizes after ~100 steps

### 2.6 Skill Bank Dynamics

- Add decisions dominate early (small bank, uncovered knowledge)
- Merge/drop decisions increase as bank grows
- With sufficient evolution steps, bank size stabilizes (nearly flat) — maintenance controls unbounded growth

## 3. Trade-offs (wins vs loses)

| Win | Lose / Cost |
|---|---|
| +32.8% pass rate over no-skill; +11.4% over strongest baseline | ~230 total GPU-hours training (20h SFT + 210h RL) on 4×H100 |
| Skill bank maintained at stable size (676 vs 1252 without maintenance) | Full lifecycle maintenance costs ~2% pass rate vs extraction+evolution only |
| RL policy transfers to unseen coding policy (GPT-5.4-mini) | Requires pre-caching no-skill baselines for all training instances (n=4 rollouts each) |
| Event-driven + task-level skills are complementary | Two skill granularities add bank management complexity |
| Hybrid reward better than quality-only or execution-only | LLM-as-judge for R_Q and R_A introduces judge model cost (GPT-5.4-mini API calls) |
| RL enables OOD generalization (Terminal-Bench 2); SFT-only degrades | SFT without RL may overfit to training task distributions |
| Small model (4B) with RL outperforms large model (GPT-5.4-mini) with prompt-based management | Small model (Qwen3.5-4B) with prompt-based management is worse than no-skill baseline |
| Procedural skills reduce reasoning steps by 20.3% | Fixed natural-language instruction format limits expressiveness (no executable scripts/APIs) |
| Single-operation action space simplifies training and reward assignment | Cannot express multi-skill coordinated updates, skill splitting, or batch operations |

## 4. Design Rationale (why this approach)

1. **Why learnable policy over fixed prompts:** Fixed prompts and heuristics predefine what to extract and how to update memory, but cannot adapt these decisions to the specific downstream agent. What constitutes a "good" skill depends on whether the frozen coding agent π can actually use it — a property only observable through execution feedback.

2. **Why RL over pure SFT:** SFT alone produces skills that look plausible but fail to transfer to unseen task types (Terminal-Bench 2). RL with downstream execution feedback forces the policy to internalize what actually helps the agent, not just what looks like a good skill.

3. **Why hybrid reward (not execution-only):** Execution reward is sparse, noisy, and has a credit-assignment problem in long-horizon coding rollouts. The alignment factor R_A gates execution reward by checking whether the agent actually followed the skill. The quality reward R_Q provides dense, stable supervision to prevent reward collapse.

4. **Why three-stage curriculum:** The skill bank lifecycle is sequential — extracted skills become evolution candidates, both become maintenance candidates. Introducing operations progressively allows data reuse and avoids the cold-start problem where stage-3 training has no skills to maintain.

5. **Why multi-granularity bank:** Task-level skills capture strategic knowledge transferable across related tasks; event-driven skills capture local, recurring patterns (error messages, command failures) that recur across *any* task. They are complementary.

6. **Why LoRA on small backbone (4B):** The skill-management policy is a meta-policy, not the task-solver. A small model with RL optimization suffices to learn the management decisions; larger models for the frozen π handle the actual coding.

## 5. Limitations and Failure Modes

1. **Natural-language instruction skills only.** Cannot express executable scripts, APIs, tool definitions, or structured resources. Limits applicability in settings where agents can extend their own toolsets.

2. **Single-operation action space.** Cannot jointly revise multiple skills, split overly broad skills, or coordinate multi-skill updates in one step. Each decision is atomic and isolated.

3. **Training cost.** ~230 GPU-hours on 4×H100 plus GPT-5.4-mini API costs for teacher data generation (12,856 SFT examples) and judge calls during RL (500 steps × group size 6 × 3 rubrics per operation).

4. **Reliance on strong teacher model.** GPT-5.4-mini generates SFT targets and serves as LLM-as-judge. Degradation likely with weaker teachers; quality of warmup data upper-bounds RL potential.

5. **Fixed retrieval mechanism.** Dense semantic similarity only. No learned retrieval, no adaptive retrieval conditioned on task state. Skills may be retrieved that are similar in embedding space but irrelevant in the current execution context.

6. **SFT-only degrades on OOD tasks.** Without RL, the policy overfits to training task distributions. SFT-CODESKILL does not improve over no-skill on Terminal-Bench 2.

7. **No continuous online learning.** Skill bank updated in discrete batch episodes, not continuously during agent operation. The bank cannot adapt mid-rollout.

8. **Evaluated on single frozen coding agent type per experiment.** Generalization tested across Qwen→GPT but not across fundamentally different agent architectures (e.g., tree-search vs ReAct).

## 6. Transfer to Lyra

### The One Transferable Idea

**Replace Lyra's fixed-prompt skill/memory extraction with a learnable skill-management policy optimized by RL against the frozen Lyra agent using hybrid rubric+execution rewards.** Instead of hand-crafted heuristics for what to extract and retain from conversation/memory traces, train a small policy model to decide what constitutes a reusable skill, when to evolve it, and when to drop it — using Lyra's own downstream task performance as the optimization signal.

### Workstream Route

**§4.2 — Memory & Context Architecture.** This directly feeds Lyra's memory subsystem. CODESKILL's architecture maps onto Lyra's need for:
- Multi-granularity skill/memory extraction from conversation trajectories
- Skill bank maintenance (add/merge/drop) to prevent unbounded memory growth
- Event-driven local guidance skills that trigger on recurring failure patterns
- Task-level strategic skills that transfer across related user intents

| Dimension | Score | Rationale |
