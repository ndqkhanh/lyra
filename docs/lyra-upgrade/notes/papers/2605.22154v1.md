## 1. Mechanism (step-by-step)

IdleSpec is an inference-time framework that exploits tool-call idle time in LLM agents for speculative planning. It comprises three phases per agent step: Drafting (during idle), Aggregation (at observation arrival), and Posterior Update (after aggregation).

### Phase 1: Idle-Time Drafting (Section 4.1)

While a tool call executes, the agent iteratively generates plan candidates under *two complementary strategies*:

**Progressive Drafting:** Assumes the forthcoming observation will succeed and contribute to task progress. The agent proactively drafts the next action to advance along the current trajectory.

**Recovery Drafting:** Assumes the forthcoming observation shows no progress (empty, off-target, or erroneous). The agent drafts an alternative plan that pursues the same sub-goal from a different angle, avoiding previously-tried approaches.

**Iterative procedure:** Drafting runs concurrently with tool execution. At each iteration:
1. A strategy is sampled (see Phase 3)
2. A draft is generated and added to a buffer
3. Previous drafts are fed back as context (`plan_history`) to promote diversity
4. If the observation arrives mid-generation, the in-flight draft is discarded

**Candidate cap:** The buffer is capped at K=5 candidates to prevent context overflow.

At the end of idle time, the final candidate set is:
```
D_final = D_prog ∪ D_rec
```

### Phase 2: Draft Aggregation at Test Time (Section 4.2)

When the observation arrives, the agent conditions its next reasoning step on the full candidate set D_final. **Crucially, plans are treated as reference points, not mandatory constraints** — the agent is free to synthesize a different plan if none fit. This is essential because drafts were generated under observation uncertainty; enforcing them degrades performance (Table 6b).

### Phase 3: Strategy Sampling with Posterior Updates (Section 4.3)

**Forecast:** After each observation, the agent produces a binary forecast signal `ℓ ∈ {PROG, REC}`, indicating which drafting strategy is more promising for the *next* idle period.

**Probabilistic model:** A Beta-Bernoulli conjugate pair:
- `p = Pr(ℓ = PROG)` — probability the forecast favors progressive
- Prior: `p ~ Beta(α, β)`, initialized to `α = β = 1` (uniform)
- Update rule (Eq. 4):
  - If `ℓ = PROG`: `(α, β) ← (α + 1, β)`
  - If `ℓ = REC`: `(α, β) ← (α, β + 1)`

**Adaptive strategy sampling (Thompson sampling):** At each drafting iteration during the *next* idle period, draw `p̂ ~ Beta(α, β)` and select:
- `s = PROG` if `p̂ > 0.5`
- `s = REC` otherwise

This allocates more computation to the strategy the forecast favors while retaining stochastic exploration for robustness.

### Algorithm Pseudocode (Algorithm 1)

```
Initialize Beta posterior (α, β) ← (1, 1)
Initialize empty draft buffer D ← ∅
s ← s₀
while task not finished do
    Send (s, D) to Main API → obtain next action
    Clear D ← ∅
    Execute the returned action
    while action execution in progress do  // Drafting phase
        Sample p̂ ~ Beta(α, β)
        Select strategy s* ← PROG if p̂ > 0.5 else REC
        if s* = PROG then Generate progressive draft
        else Generate recovery draft
        if |D| < K then Append draft to D
    end while
    Receive observation o
    Ignore in-flight idle draft responses, finalize D
    Send (T, s, o) to Forecast API → obtain ℓ ∈ {PROG, REC}
    Update posterior (α, β) with ℓ using Eq. (4)
    s ← s ∥ (action, o)  // append step to trajectory
end while
```

### Key Design Constants
- **Candidate cap K = 5** across all experiments
- **Agent frameworks tested:** OAgents (GAIA/FRAMES), OpenHands (MLE-Bench), SmolAgents (generalization)
- **Models tested:** Gemini-2.5-Flash, Qwen3.5-4B, Gemma4-E4B
- **Decoding:** temperature 0.6, top-p 1.0 (Gemma4-E4B: temperature 1.0, top-p 0.95, top-k 64)

## 3. Trade-offs

| Wins | Losses |
|---|---|
| +5.1% average accuracy on Gemini-2.5-Flash across GAIA+FRAMES | Additional token cost during idle windows: +5,284 tokens per GAIA L2 task (Table 3) |
| +9.1% Any Medal rate on MLE-Bench | No improvement when tool calls are ultra-short (< 1 reasoning step) |
| Near-zero end-to-end latency overhead (374s vs 376s on GAIA L3) | Higher per-task compute on metered APIs — speculative drafting consumes GPU cycles that would otherwise be idle |
| Compatible with test-time scaling methods (+3-4% additive gains) | In-flight drafts discarded if observation arrives mid-generation → wasted computation |
| Generalizes across agent frameworks (OAgents → SmolAgents) and model sizes (4B → Flash) | Capped at K=5 candidates; very long idle windows cannot generate more drafts |
| Consistent gains across difficulty levels (hardest levels benefit most) | Recovery-only drafting can harm performance by over-switching; requires balanced sampling |
| Self-adjusting via posterior feedback — no manual tuning per task | Thompson sampling adds one more hyperparameter (the Beta prior) that could theoretically need tuning per domain |

## 4. Design Rationale

**Why Planning over Summarization/Reflection?** The authors empirically compare three idle-time strategies (Figure 2c). Summarization and reflection degrade performance because they commit to incomplete interpretations before observations arrive (e.g., reflection misjudging a valid action as erroneous). Planning admits a *conditional* formulation ("if A holds, do X; else Y"), making it resilient to observation uncertainty.

**Why Dual Drafting (Progressive + Recovery)?** Single-mode speculation (only progressive or only recovery) underperforms (Table 6a). Progressive-only misses failure cases; recovery-only keeps switching plans without forward progress. The dual approach covers both exploitation and exploration, pre-expanding the search space for the agent.

**Why Thompson Sampling?** A simple Beta-Bernoulli model provides natural exploration-exploitation balance with uncertainty quantification. The posterior adapts to the trajectory's needs without manual tuning. Random selection and deterministic forecast-direct selection both underperform (Table 6c).

**Why Reference-Point Aggregation?** Best-of-N selection and mandatory enforcement both hurt accuracy (Table 6b) because drafts are generated under observation uncertainty. Treating plans as suggestions rather than commands lets the agent integrate the new observation freely.

**Why Iterative + Immediate Termination?** Idle-time budgets vary significantly across tool calls (Figure 2b). An iterative design that terminates on observation arrival achieves higher utilization (34.6% vs 13.2% for Sleep-time Compute) while avoiding wasted computation.

## 5. Limitations and Failure Modes

1. **Idle-time dependency:** No gains when tool calls finish faster than one reasoning step (ultra-short ratio > 0.75). The agent falls back to vanilla behavior.
2. **Token cost overhead:** Speculative drafting consumes additional LLM tokens during idle windows (~5,284 tokens for GAIA L2 with Qwen3.5-4B), which translates to higher API cost on metered services even though latency is unchanged.
3. **Rebuttal to "latency is free":** The paper explicitly acknowledges that "hardware is not free during idle periods" and additional compute translates to "higher aggregate energy consumption and carbon footprint per task" (Appendix A.6).
4. **K=5 candidate cap:** Very long idle windows may leave compute budget unused. The paper does not investigate adaptive K.
5. **ReAct-only validation:** Only tested in sequential ReAct-style agent loops. Extension to asynchronous/parallel tool calls and multi-agent paradigms is mentioned as future work but not validated.
6. **In-flight draft waste:** If an observation arrives mid-generation, the in-flight draft is discarded. This wastes compute especially when drafts are long.
7. **Prompt sensitivity not fully characterized:** Only the Sleep-time Compute baseline's prompts were sensitivity-tested; IdleSpec's four prompts are assumed to transfer across tasks without tuning.
8. **Single-modal decision signal:** The forecast only uses a binary PROG/REC signal; richer feedback (scalar confidence, specific failure modes) is not explored.
9. **No small-model decoupling:** All drafting uses the same primary model. Future work proposes using a smaller specialized model during idle time to reduce cost — not yet implemented.

## 6. Transfer to Lyra

### The One Transferable Idea

**Adaptive idle-window speculative reasoning with dual optimistic/pessimistic branching and self-adjusting strategy selection via posterior feedback.**

Lyra agents spend substantial time waiting for tool calls (web search, code execution, file I/O, sub-agent invocations). Instead of treating this as dead time, Lyra could run lightweight planning during idle periods: generate both a "forward progress" plan and a "recovery" plan, then self-assess which strategy was more useful at each step to bias future drafting. This requires no model training — only prompt engineering and a Beta counter in the execution loop.

### Workstream Route: §4.3 — Agent Control Loop / Inference-Time Reasoning

Lyra's agent execution loop (the reason-act-observe cycle) is the direct integration point. IdleSpec is a drop-in modification to the loop that adds drafting threads triggered by tool-call dispatch and terminated by tool-call completion.
