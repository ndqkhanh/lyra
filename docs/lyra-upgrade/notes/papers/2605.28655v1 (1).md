## 1. Mechanism (step-by-step)

AUTO S CIENTISTS is a decentralized multi-agent system where *n* long-running LLM agents self-organize into teams, propose experiments, execute them, and reorganize when progress stalls — all without a central orchestrator.

### 1.1 Problem Formulation
Given a task description, dataset *D = (D_train, D_val)*, evaluation metric *ℓ*, and optional starting program *p_0*, the goal is to find *p\* = arg max ℓ_eval(p; D)* over programs explored by agents.

### 1.2 Shared State *S* (four layers)
- **Champion *p\***: current best model with full hyperparameters and reproduction instructions
- **Experiment log *L***: every completed experiment with outcome, metric delta, training diagnostics
- **Shared forum *F***: structured posts for proposals, debates, results, mechanistic analyses
- **Team-local state**: per-team experiment queues *Q_k*, dead-end registries *D_k*, hypothesis documents (cross-team readable)

### 1.3 Two-Phase Cycle

**Phase 1 — Discussion & Self-Organization (Algorithm 2)**
1. Agents read task spec, current *p\**, and prior posts on *F*
2. Each agent posts: (i) candidate research directions, (ii) ranked hypotheses with reasoning, (iii) self-termination vote: `[DISCUSS-MORE]` or `[DISCUSS-DONE]`
3. Later agents critique earlier posts, identify gaps in search-space decomposition
4. Discussion terminates when majority votes `[DISCUSS-DONE]`
5. Alphabetically-last analyst consolidates proposals into roster *R = {(T_k, axis_k, members_k)}^K_{k=1}* and writes to *S*

**Phase 2 — Parallel Execution**
Agents operate in a heartbeat loop (Algorithm 1):
- Read roster *R* and forum *F*
- If `[DISCUSSION-TRIGGER]` exists or *R* is empty → run Algorithm 2 (discussion)
- If not assigned to team → exit (no-team exit)
- If experiment agent with unposted result → post `[RESULT]` and exit (resume)
- Otherwise → run role-specific cycle

### 1.4 Analyst Agent Cycle (Algorithm 4)
1. **Stagnation detection**: If no improvement in recent experiments or proposals concentrated on narrow changes → post `[DISCUSSION-TRIGGER]`
2. **Coverage audit**: Scan *p\** for all numeric parameters; match against *L* to identify never-varied parameters
3. **Empirical axis priors**: Compute mean effect size per (axis, direction) pair:
   ```
   μ_{a,d} = (1/|E_{a,d}|) * Σ_{e∈E_{a,d}} |Δ_e|
   ```
   Cold directions (|E_{a,d}| < 3) get exploration bonus; directions with μ_{a,d} < σ are deprioritized
4. **Proposal generation**: Draft 2 proposals subject to:
   - *Ambition quota*: ≥1 must be "bold" (parameter-count change ≥10%, confirmed bug fix, untested axis flagged twice, or hypothesis-tension probe)
   - *Diversity rules*: (i) two proposals target different directions, (ii) no 3+ consecutive same-axis pushes, (iii) no proposal in dead-end range *D_k* unless explicitly justified
   - *Post-KEEP step*: If champion updated, ≥1 proposal must target the property responsible for the improvement via a different mechanism
5. Append proposals to *Q_k*

### 1.5 Experiment Agent Cycle (Algorithm 3)
1. Claim queued experiment *q* from *Q_k* (optimistic locking on version token; no double-claim)
2. Apply code diff to *p\**, train candidate *p′*, compute Δ = ℓ(p′) − ℓ(p\*)
3. **Noise-aware promotion gate** (Equation 1):
   ```
   promote(p′) = true                    if Δ > M·σ   (M = 2)
                 confirm(p′, seed₂)      if 0 < Δ ≤ M·σ
                 false                   if Δ ≤ 0
   ```
   where confirm() reruns with a new seed; promotes only if *both* runs strictly improve.
4. **Noise-floor calibration** (Equation 2): Once ≥3 duplicate-seed pairs accumulate, σ is the pooled within-pair standard deviation:
   ```
   σ = sqrt( (1/(2n)) * Σ_{i=1}^{n} (ℓ_{1,i} - ℓ_{2,i})² )
   ```
   σ is locked after 5 pairs to prevent retroactive reclassification.
5. Record outcome to *L*, release claim, post `[RESULT]` to *F*

### 1.6 Stagnation & Reorganization
When a team's recent experiments consistently fail (no improvement in ~10 experiments), analysts post `[DISCUSSION-TRIGGER]`. Agents enter discussion, can create/merge/split/retire/rebalance teams. Dead-end registries *D_k* prevent redundant exploration.

### 1.7 Implementation
- All agents use Claude Code with Claude Sonnet 4.6 backend
- Deterministic monitor process invokes agents in a heartbeat loop
- File discovery via list-decide-read protocol (lightweight metadata first, then selective fetch)
- 3 analyst agents + 6 experiment agents (default), H100 GPUs

### GPT nanochat Training Optimization
- **From baseline (val_bpb = 0.998):** AUTO S CIENTISTS reaches val_bpb ≈ 0.978 in **34 experiments** vs. Autoresearch's 65 experiments → **1.9× speedup**

## 3. Trade-offs

| Wins | Loses |
|------|-------|
| +8.33 pp on BioML-Bench over best single-agent | Higher LLM token usage (within same order of magnitude as Autoresearch) |
| 1.9× faster convergence on GPT training | More complex orchestration (heartbeat loop, optimistic locking, forum protocol) |
| Continues discovering improvements after single-agent plateaus (7 vs 0 KEEPs) | Team-size is fixed before run; oversubscription (n=14) degrades performance |
| Avoids repeated dead-ends via shared registry *D_k* | BioML-Bench restricted to 1 H100; parallel GPU scaling not evaluated |
| Pre-execution critique filters weak ideas before compute spent | No multi-objective optimization (MSE degraded +0.006 on ProteinGym) |
| Emergent cross-team knowledge transfer (analyst not always needed) | Only evaluated with Claude Sonnet 4.6 backend; LLM-agnostic claim not tested across models |
| Noise-aware gate prevents champion pollution from stochastic metrics | No statistical significance tests on ablation (n=1 per condition) |
| Produces model cards + research insights as byproducts | Requires task with evaluable metric ℓ; not applicable to open-ended discovery without defined loss |

## 4. Design Rationale

**Why self-organization over central planner:** Scientific hypotheses shift as evidence accumulates; a fixed decomposition at the start cannot anticipate which directions will become productive. Self-organization allows teams to emerge, merge, and retire based on accumulated experimental evidence rather than pre-programmed decomposition.

**Why pre-execution critique:** In long-running experiments, compute is the scarce resource (each experiment costs GPU time). Filtering proposals through peer critique before execution reduces wasteful trials — agents diversify away from redundant proposals, identify saturated directions, and transfer hypotheses across teams.

**Why shared state over message-passing:** A persistent shared state (*S*) decouples agent timing: agents read/write asynchronously without waiting for responses. This enables parallel execution while maintaining a single source of truth for the champion, dead ends, and experiment history.

**Why analyst/experiment role split:** Separating proposal generation (analyst) from execution (experiment) creates specialization — analysts maintain search knowledge and prioritize directions; experiment agents focus on correct implementation and noise-gated evaluation. However, ablation shows the analyst role is at-or-below replacement on simpler search surfaces.

**Why noise-aware gating:** Stochastic evaluation metrics cause "champion pollution" — a noisy improvement becomes the new baseline, corrupting all downstream comparisons. The two-tier gate (M=2σ direct accept, 2σ band with seed confirmation) prevents this without wasting experiments on calibration (σ is calibrated lazily from duplicate-seed pairs that arise naturally).

## 5. Limitations & Failure Modes

1. **Not LLM-call efficient:** Uses more tokens than single-agent Autoresearch (Table S8); the gain is in experiment selection quality, not token efficiency.
2. **Single-GPU BioML-Bench constraint:** Evaluation used 1 H100 per task, so GPU-bound experiments ran sequentially — the system's parallel execution capacity was not exercised on the largest benchmark.
3. **Fixed team size:** n=14 degraded every task vs. n=9; optimal crew size is task-dependent. No dynamic scaling mechanism exists.
4. **Single-objective optimization:** On ProteinGym, Spearman ρ improved but MSE degraded. The system cannot optimize multi-objective trade-offs (e.g., ranking quality + calibration).
5. **No statistical rigor on ablations:** n=1 run per ablation condition; multi-replicate studies needed to confirm component contributions.
6. **LLM-backend monoculture:** Only tested with Claude Sonnet 4.6; claim of LLM-agnosticism untested. Different model behaviors could affect critique quality and proposal diversity.
7. **Requires evaluable metric:** The system assumes a well-defined ℓ_eval; not applicable to open-ended scientific tasks without quantifiable feedback.
8. **Cold-start sensitivity:** Run-to-run variance of 0.0018 in val_bpb across 3 runs; different proposal orderings lead to different intermediate paths, though final regions are robust.
9. **Stagnation threshold is heuristic:** "No improvement in ~10 experiments" is a fixed rule; no adaptive stagnation detection.
10. **Alphabetical tiebreaker fragility:** The consolidator role assigned to "alphabetically-last analyst" is a brittle coordination primitive that could fail if agent naming conventions change.

## 6. Transfer to Lyra

### The ONE Transferable Idea
**Decentralized self-organizing agent teams with stagnation-triggered reorganization and a shared dead-end registry.** Lyra's multi-agent architecture can adopt this pattern: instead of a central router/planner assigning tasks, let specialized agents self-organize into teams around research directions, critique each other's proposals before execution, share results (especially failures) through a common state, and reorganize when progress stalls. The dead-end registry is the critical novel component — tracking *what didn't work and why* prevents redundant exploration, which is directly applicable to Lyra's iterative code generation and debugging loops.

### Workstream Route: §4.2 — Multi-Agent Architecture & Orchestration
This feeds Lyra's agent team coordination layer. Currently Lyra has a router pattern; the AutoScientists approach replaces centralized routing with emergent team formation through shared state, which could improve Lyra's ability to explore diverse solution strategies in parallel for complex coding tasks.
