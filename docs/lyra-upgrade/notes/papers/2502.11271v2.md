# OctoTools: A Multi-Agent Framework with Extensible Tools for Complex Reasoning
**Authors:** Pan Lu\*, Bowen Chen\*, Sheng Liu\*, Rahul Thapa, Joseph Boen, James Zou (\* equal contribution, Stanford University)
**Venue:** arXiv preprint 2502.11271v2 (last revised 13 Apr 2026)
**Links:** https://octotools.github.io/ | Code, Demo, Tool Cards, Visualization, Video all publicly available

## 1. Mechanism (step-by-step)

OctoTools is a **training-free, two-agent framework** (planner + executor) that solves complex reasoning queries by decomposing them into multi-step tool-use trajectories. The key architectural innovation is the separation of strategic planning from command execution, combined with **standardized tool cards** that make the system extensible without retraining.

### 1.1 Tool Cards (Encapsulation Layer)
Each external capability is wrapped in a **tool card** — a structured metadata object containing:
- `tool_description`: natural-language description of what the tool does
- `inputs` / `outputs`: typed schema (e.g., `image`, `prompt` → `str`)
- `demos`: example invocations (`tool.execute(image="img.png", prompt="Describe...")`)
- `user_metadata`: developer-provided constraints, limitations, and best-practice usage notes

Tool cards are **modular relative to the framework** — adding a new tool requires only lightweight NL metadata and a few demo commands. The framework never needs modification.

### 1.2 Planner Agent (Strategic Layer)
The planner operates at two levels:

**High-level plan (initialization):**
Given a query `q` and toolbox `D = {d_1, ..., d_n}`, the planner inspects all tool cards and generates a global plan that:
1. Summarizes the query objective
2. Identifies required skills (e.g., "visual understanding", "numerical calculation")
3. Selects relevant tools
4. Notes additional considerations (verification needs, tool limitations)

**Low-level plan (iterative action prediction):**
At each step `t`, the planner's **action predictor** produces an action `a_t` containing:
- A sub-goal (e.g., "detect baseballs in the image")
- The selected tool `d_t`
- Relevant context from the trajectory so far

A **context verifier** then checks completeness, detects ambiguities, and decides whether to `CONTINUE` (next iteration) or `STOP` (solution found).

### 1.3 Executor Agent (Execution Layer)
Two sub-components:

**Command Generator:** Takes the planner's text-based action `a_t` and translates it into an **executable Python command** `o_t` that calls tool `d_t` with proper arguments. This is powered by a language model.

**Command Executor:** Runs `o_t` in a Python environment, obtains result `r_t` (tool output, logs, or errors). Updates the trajectory: `s_t := (a_t, o_t, r_t)`.

The trajectory `(s_0, s_1, ..., s_T)` preserves full history of actions, code, and results.

### 1.4 Solution Summarizer
When the verifier concludes the problem is solved, a separate LLM call compiles the final answer from the trajectory, integrating intermediate tool outputs into a user-friendly summary.

### 1.5 Task-specific Toolset Optimization (Algorithm 1)
Not all tools help all tasks — enabling all tools can introduce noise. A greedy 3-stage algorithm on validation data:

- **Stage 1 (Baseline):** Measure accuracy with base toolset `D_base` (the `Generalist_Solution_Generator`)
- **Stage 2 (Individual evaluation):** For each candidate tool `d_i`, add it to `D_base` and measure ∆ accuracy. If `∆d_i > 0`, mark `d_i` as beneficial.
- **Stage 3 (Selection):** `D* = D_base ∪ {d_i | ∆d_i > 0}`

Complexity: `O(n)` instead of `O(2^n)` exhaustive search. The optimization is performed once per task domain (not per query).

### 1.6 Control Flow
```
User Query q
  → Planner: high-level plan, initial context s_0
  → FOR t = 1 to T (max steps, default 10):
      → Planner: action a_t (sub-goal, tool, context)
      → Executor: command o_t → execute → result r_t
      → Context update: s_t = (a_t, o_t, r_t)
      → Verifier: CONTINUE or STOP
  → Solution Summarizer: final answer from trajectory
```

| Gain over GPT-4o CoT | **+7.7%** (50.8% → 58.5%) |

### 2.4 Ablations

- **Step budget:** Accuracy improves from ~55% (1 step) to ~59% (10 steps). Average actual steps used: 2.56 with GPT-4o (verifier stops early).
- **Toolset strategy:** Base-only (53.9%), Full-toolset (57.4%), Optimized-toolset (58.9%)
- **Weaker backbone (GPT-4o-mini):** OctoTools still provides +7.1% over GPT-4o-mini zero-shot across 16 tasks
- **Compact open-source backbones:** Qwen2.5-3B gains +13.6%, Qwen2.5-7B gains +6.3% (4 representative tasks)
- **Cross-backbone consistency:** Claude 3.5 Haiku (+5.8%), Gemini 2.5 Pro (+7.4%), Grok-2 Vision (+6.9%), Qwen2.5-VL-72B (+8.4%)

### 2.5 Robustness to Tool Failures
With Qwen2.5-7B, injected random tool errors:
- p=0.0: 41.4% avg on 10 tasks
- p=0.4: 39.8% (only −1.6% drop)
- p=0.6: 35.3% (−6.1% drop)

### 2.6 Cost/Latency (per query, GPT-4o)
- Cost: ~$0.05/query
- Avg steps: 2.56 (not the full 10-step budget)
- Avg time: 58.8s
- Avg tokens: 38.0K

## 3. Trade-offs

| Win | Loss |
|-----|------|
| Training-free: no fine-tuning needed for new tools or domains | Performance ceiling tied to base LLM capability |
| Extensible: new tools added via lightweight tool cards (NL metadata + demos) | Tool quality directly impacts downstream accuracy (65% of failures from weak tools) |
| Planner-executor separation reduces command errors (only 1.5% invalid commands) | Two-agent structure means multiple LLM calls per step, increasing latency |
| Multi-step decomposition enables gains on hard reasoning tasks | Cost scales with step budget (38K tokens/query avg, $0.05/query GPT-4o) |
| Toolset optimization reduces noise from irrelevant tools | Greedy search is not globally optimal; requires validation data per task |
| Robust to tool noise (graceful degradation up to p=0.4) | Fragile when base LLM hallucinates tool metadata |
| Works across diverse backbones (5 LLMs tested, consistent 5.8–8.4% gains) | Open-source backbones (Qwen2.5-3B) still start from low absolute accuracy (23.5%) |
| Transparent trajectories improve interpretability and trust | Long trajectories increase memory footprint; some queries exceed 90s |
| Modular design enables independent tool upgrades (e.g., DINO → DINO-X) | Static per-task toolset; no dynamic query-level adaptation |

## 4. Design Rationale

The authors chose a **structured planner-executor split over peer-to-peer multi-agent chat** (like AutoGen/MetaGPT) for three reasons:

1. **Reliability:** When a single LLM handles both strategy ("which tool?") and execution ("write the code to call it"), the dual responsibility leads to errors, especially for complex or environment-specific code. Separating these roles reduces invalid command generation to 1.5%.

2. **Observability:** The fixed, hierarchical interaction produces a structured, auditable trajectory. Each step records what was planned, what code was generated, and what result was returned. This enables the context verifier to check consistency — a feature absent in conversational multi-agent systems.

3. **Extensibility without retraining:** The tool card abstraction means new tools require only NL metadata and demo commands — no model fine-tuning, no framework changes. This contrasts with Toolformer-style approaches that need supervised data for each new tool, and with Chameleon-style approaches that hard-code tool integration.

The **greedy toolset optimization** was chosen over global search because the authors observed that "enabling all tools may introduce noise or slow performance" — the greedy approach reduces complexity from `O(2^n)` to `O(n)` while still yielding 1.5% improvement over full-toolset.

## 5. Limitations and Failure Modes

1. **Base LLM dependency (65.0% of failures):** Weak or incapable tools are the #1 failure cause. Since OctoTools is training-free, it cannot compensate for tools that fundamentally cannot solve the task.

2. **Imperfect planning (77.5% combined):** 45.0% of failures from imperfect low-level plans (wrong sub-goal decomposition), 32.5% from imperfect high-level plans (wrong tool selection strategy). Stem from LLM reasoning limits, not the framework.

3. **Tool quality dependence:** External tools (Google Search, PubMed API, EasyOCR) may produce inaccurate or incomplete results. OctoTools has no mechanism to detect or compensate for silently wrong tool outputs.

4. **Static toolset optimization:** Greedy search over validation data is not globally optimal. Does not adapt per-query — the same toolset is used for all queries in a task domain.

5. **Computational cost:** Multi-step planning adds latency (avg 58.8s/query with GPT-4o) and token consumption (38K tokens/query). Some queries exceed 90 seconds.

6. **Security concerns:** Python_Code_Generator executes LLM-generated code. While sandboxing is mentioned as possible, no implementation is provided. External tool calls may expose user data to third-party services.

7. **Reproducibility drift:** Tools relying on third-party APIs (Google Search, PubMed) may change interfaces or become deprecated. Exact reproduction requires containerized environments.

## 6. Transfer to Lyra

**The one transferable idea:** **Standardized Tool Cards as a training-free extensibility mechanism for LLM agent toolkits.**

Lyra should adopt the tool-card pattern (structured metadata with `tool_description`, typed `inputs`/`outputs`, `demos`, and developer-provided `user_metadata` with limitations/best-practices) as the canonical way to register new capabilities in the Lyra agent system. This enables:
- Plug-and-play tool addition without modifying the agent loop
- Developer-authored guardrails embedded in tool metadata (e.g., "this tool may fail in low-light images — verify with alternative tools")
- Automated toolset optimization (greedy validation-based selection) for different task domains
- Clean separation between tool capabilities and agent orchestration logic

**Workstream route:** §4.3 (Tool & Plugin Architecture) — this feeds directly into the plugin/tool registration system design.
