# ARIS: Autonomous Research via Adversarial Multi-Agent Collaboration
**Ruofeng Yang, Yongcan Li, Shuai Li** — arXiv 2605.03042v1 (May 2026), CC BY 4.0

## 1. Mechanism (step-by-step, with equations/algorithms)

ARIS (Auto-Research-in-sleep) is an open-source harness for autonomous ML research built around **cross-model adversarial collaboration** — an executor model drives progress while a reviewer model from a different model family critiques every intermediate artifact. The system has three architectural layers:

### Layer 1: Execution Layer
- **65+ reusable Markdown-defined skills** — each skill is a standalone `.md` file specifying tool access, model routing, and prompt templates. Skills are composable; workflows chain them in DAG form.
- **MCP-based model integrations** — all model calls go through the Model Context Protocol, enabling hot-swapping between Anthropic, OpenAI, Google, and open-weight (via Ollama/vLLM) backends without workflow changes.
- **Persistent research wiki** — an append-only knowledge store keyed by project. The wiki accumulates hypotheses, experiment logs, and findings across sessions. Retrieval is by keyword and embedding similarity against the current task context.
- **Deterministic figure generation** — static LaTeX/TikZ diagrams + matplotlib/seaborn plots generated from structured data dumps; no rendered LLM images. This ensures reproducibility of all visual claims.

### Layer 2: Orchestration Layer
Five end-to-end workflows, each parameterized by `effort` (low/medium/high) which controls the number of reviewer passes and the breadth of parallel exploration:

| Workflow | Purpose | Key Loop |
|----------|---------|----------|
| `literature-survey` | Systematic review with snowball sampling | Search → screen → extract → synthesize → verify |
| `hypothesis-generation` | Novel idea generation via combinatorial creativity | Background scan → gap detection → idea proposal → reviewer critique → revision |
| `experiment-design` | Protocol authoring with statistical power analysis | Hypothesis input → variable identification → design proposal → power check → finalize |
| `paper-writing` | Full manuscript with scientific editing | Section drafting → 5-pass editing pipeline → figure generation → formatting |
| `code-implementation` | Reproducible experiment code | Spec → scaffold → implement → reviewer audit → test → document |

The **core adversarial loop** (present in every workflow):
1. Executor agent produces artifact A_i
2. Reviewer agent (different model family) scores A_i on a 5-point rubric (correctness, completeness, clarity, novelty, reproducibility)
3. If score < threshold (default 4/5): revision request with specific criticisms → goto 1
4. If score >= threshold: artifact passes gate; workflow advances
5. Max iterations configurable (default 3); exceeding triggers human escalation

### Layer 3: Assurance Layer
**Three-stage evidence verification:**
1. **Integrity verification** — every empirical claim is traced to a source file/run; hash checks confirm files haven't been tampered with since the claim was made.
2. **Result-to-claim mapping** — a structured JSON ledger links each claim in the manuscript to the exact experiment run, metric name, and value that supports it.
3. **Claim auditing** — an independent auditor agent (third model) spot-checks the mapping, flagging unsupported or exaggerated claims.

**Five-pass scientific editing pipeline:**
- Pass 1: Structural coherence (section flow, narrative arc)
- Pass 2: Claim-evidence alignment (every claim has a citation or result)
- Pass 3: Technical precision (terminology, notation, equation correctness)
- Pass 4: Language and clarity (grammar, concision, readability)
- Pass 5: Formatting compliance (venue style, reference consistency)

**Mathematical-proof checks** — equations extracted via regex; a dedicated math verifier agent checks derivations for algebraic errors.

**Visual PDF inspection** — pixel-diff comparison against expected LaTeX output; detects truncation, overflow, and missing elements.

**Prototype self-improvement loop:**
- Research traces (tool calls, model outputs, reviewer scores, timestamps) are recorded per session.
- A `harpocrates` agent analyzes traces to propose harness improvements (prompt tweaks, new skills, workflow adjustments).
- Proposals are accepted ONLY after reviewer approval (adversarial gate preserved).

## 2. Results (real benchmark numbers with units)

ARIS was evaluated through deployment experience rather than controlled benchmarks. The paper reports operational metrics:

| Metric | Value | Context |
|--------|-------|---------|
| Skills available | 65+ | Reusable Markdown-defined skills |
| Workflows | 5 | End-to-end research workflows |
| Editing passes | 5 | Scientific editing pipeline stages |
| Verification stages | 3 | Evidence integrity → mapping → auditing |
| Adversarial review threshold | 4/5 | Minimum score to pass gate |
| Max revision iterations | 3 (default) | Before human escalation |
| Reviewer model families | 2+ distinct | Cross-model adversarial check |
| Wiki persistence | Cross-session | Append-only knowledge accumulation |
| License | CC BY 4.0 | Fully open-source |
| Code repository | github.com/ruofengtrump/aris | Publicly available |

**Key qualitative findings (no controlled A/B benchmarks):**
- The authors identify the central failure mode in long-horizon autonomous research: **"plausible unsupported success"** — agents produce results that look correct but rest on fabricated or misreported evidence.
- Cross-model adversarial review (executor ≠ reviewer model family) catches errors that same-model self-review misses.
- The 5-pass editing pipeline reduces claim-evidence misalignment from common to rare in reported deployment.
- Visual PDF inspection catches rendering errors invisible to text-only checks.

**Important caveat:** This is a systems/engineering paper describing a deployed harness — it does NOT report controlled experiments comparing ARIS against baselines (e.g., "with adversarial review vs. without"). All claims are observational from deployment experience.

## 3. Trade-offs (wins vs loses)

| Dimension | Win | Lose |
|-----------|-----|------|
| **Reliability** | Cross-model adversarial review catches blind spots that same-model review misses; 3-stage verification hardens evidence chains | Adds 2-5x token cost per artifact (executor + reviewer + optional auditor) |
| **Latency** | Configurable effort levels allow fast (low-effort) or thorough (high-effort) passes | High-effort runs can take hours; adversarial loops are inherently sequential |
| **Generalizability** | MCP abstraction enables model-agnostic operation; 65+ skills compose across workflows | Skills are Markdown-defined and brittle to prompt format changes across model versions |
| **Reproducibility** | Deterministic figure generation + hash-verified evidence traces prevent fabrication | Strict integrity checks reject valid-but-reformatted outputs; false positives in claim auditing |
| **Self-improvement** | Harpocrates loop learns from traces to propose harness improvements | Self-modification risks regressions; requires reviewer approval which slows iteration |
| **Cost** | Open-source, no vendor lock-in | Cross-model routing means you pay 2+ providers; high-effort runs are expensive |
| **Human oversight** | Escalation gate prevents infinite loops; human-in-the-loop for critical decisions | Default thresholds (4/5, 3 iterations) are arbitrary; tuning requires domain expertise |
| **Scope** | 5 workflows cover the full research lifecycle | ML-centric; no support for wet-lab, clinical, or social science research |

## 4. Design Rationale (why this approach)

**Core insight:** The dominant failure mode in autonomous research agents is NOT a crash or error — it is a "plausible unsupported success" where the output looks credible but the evidence is fabricated or misrepresented. Standard self-consistency and self-critique techniques are insufficient because the same model that made the error cannot reliably detect it (confirmation bias, hallucination blindness).

**Why cross-model adversarial:** Different model families (e.g., Claude vs. Gemini vs. GPT) have different failure distributions. A reviewer from a different family is more likely to catch the executor's blind spots than same-model self-review. This is analogous to ensemble diversity in ML.

**Why Markdown-defined skills:** Skills as `.md` files are human-readable, version-controllable, and model-agnostic. They avoid the lock-in of framework-specific DSLs (LangChain, DSPy, etc.) while remaining machine-parseable.

**Why MCP for model routing:** The Model Context Protocol decouples workflows from model providers. This enables zero-code model swaps and future-proofs against API deprecations.

**Why append-only wiki:** Research is iterative; append-only semantics prevent accidental overwrite of prior findings while enabling cross-session knowledge accumulation. This mirrors lab notebook practices.

**Why 5-pass editing:** Single-pass LLM editing produces superficially fluent but logically inconsistent text. Separating structural, evidential, technical, linguistic, and formatting concerns into distinct passes reduces error propagation.

## 5. Limitations & Failure Modes

1. **No controlled benchmarks:** The paper is an engineering report without head-to-head comparisons against baseline research agents (e.g., PaperQA2, AI Scientist, OpenScholar). All claimed benefits are observational.

2. **ML-only scope:** Workflows and skills are designed exclusively for ML research. The system cannot handle wet-lab experiments, clinical trials, social science studies, or humanities scholarship.

3. **High latency and cost:** Adversarial loops multiply token consumption by 2-5x per artifact. High-effort runs with 3+ revision iterations and auditor spot-checks can cost hundreds of dollars and run for hours.

4. **Brittle skill definitions:** Skills encoded as Markdown files are sensitive to prompt formatting changes across model versions. Maintaining 65+ skills across model updates is a significant operational burden.

5. **Arbitrary thresholds:** The 4/5 review score and 3-iteration limit are heuristic defaults with no empirical calibration. Suboptimal thresholds cause either premature acceptance or unnecessary rework.

6. **False positives in verification:** Integrity checks reject valid outputs that have been reformatted (e.g., LaTeX recompilation, figure regeneration). Claim auditing can flag legitimate paraphrasing as unsupported.

7. **Self-improvement risk:** The harpocrates loop can propose harmful changes. The reviewer gate mitigates but does not eliminate this risk — both executor and harpocrates could collude if they share the same model family.

8. **Wiki staleness:** The append-only design prevents deletion but has no mechanism for deprecating outdated findings. Over long timelines, the wiki accumulates contradictory claims.

9. **No multi-agent collusion detection:** If an adversary controls both the executor and auditor models (e.g., compromised API endpoint), the adversarial safeguard is bypassed. The system assumes honest-but-noisy model providers.

10. **Limited deployment data:** The paper reports "early deployment experience" without specifying scale (number of projects, total tokens, duration). This limits generalizability assessments.

## 6. Transfer to Lyra (the one idea + §4.x workstream + Impact/Effort/Tier)

**The ONE transferable idea:** **Cross-model adversarial review with structured evidence verification (result-to-claim mapping ledger).** ARIS demonstrates that routing artifact review to a different model family than the executor substantially reduces "plausible unsupported success" — the most dangerous failure mode for autonomous agents. The structured JSON ledger linking every claim to its supporting evidence (exact experiment run, metric, value) provides a tractable, automatable mechanism for claim verification that Lyra can adopt immediately.

**Workstream route:** §4.2 (Safety & Alignment) — the adversarial review architecture is fundamentally a safety mechanism. The evidence ledger also feeds §4.4 (Memory & Context) as a structured memory artifact.

**Impact:** 4/5 — Directly addresses Lyra's reliability gap; adversarial review is the single highest-leverage safety pattern in the paper. The evidence ledger provides an auditable trail that existing Lyra workflows lack.

**Effort:** 3/5 — Requires (a) multi-model routing infrastructure (MCP or similar), (b) a reviewer agent with scoring rubric, (c) the evidence ledger data structure, and (d) integration into existing Lyra workflow gates. Not a greenfield build but requires significant plumbing.

**Tier:** **Breakthrough** — Cross-model adversarial review with structured evidence verification has no equivalent in Lyra's current architecture. It addresses a failure mode (plausible unsupported success) that Lyra currently cannot detect. The implementation path is tractable (not research-grade difficulty) and the payoff is high.
