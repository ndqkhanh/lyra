**Authors**: Traian Rebedea\*, Razvan Dinu\*, Makesh Sreedhar, Christopher Parisien, Jonathan Cohen (NVIDIA, Santa Clara, CA)
**Venue**: arXiv preprint 2310.10501v1, October 16, 2023
**License**: Apache 2.0 (open-source)

## 1. Mechanism (step-by-step)

NeMo Guardrails implements a **runtime dialogue manager** that proxies between user and LLM, enforcing user-defined "programmable rails" through a custom modeling language called **Colang**.

### Core Architecture (3-stage proxy pipeline)

**Stage 1 — Generate User Canonical Form:**
1. Each user utterance is received by the Guardrails runtime.
2. A similarity-based few-shot prompt is constructed: the most similar `k` examples (typically `k=5`) from a vector database (Annoy or FAISS) are retrieved, where each example maps a user utterance to its canonical form.
3. The LLM is prompted (with `temp=0`) to output the canonical form for the current user message in Colang syntax.
4. Semantic similarity matching (threshold `sim=0.6`) is used instead of exact match when models produce diverse canonical forms.

**Stage 2 — Decide Next Steps / Execute Flow:**
1. The dialogue manager checks if the canonical form matches any developer-defined flow.
2. **Path A — Pre-defined flow:** If matched, the next step is extracted from that flow by the Colang interpreter (event-driven design).
3. **Path B — LLM generalization:** If no flow matches, the LLM is prompted to generate appropriate next steps by analogy (e.g., if a bus-booking flow exists, the LLM generates a similar flight-booking flow).

**Stage 3 — Generate Bot Message:**
1. Conditioned on the determined next step, the LLM generates the bot response (with `temp=0.7` or `temp=1`).
2. Output moderation rail (if enabled) checks the response before it reaches the user.

### Colang Language (Modeling Primitives)

The Colang language blends natural language with Python-like syntax:
- **Utterance**: Raw text from user or bot.
- **Canonical Form (Message)**: Structured semantic representation, generated by LLM (open-set) rather than classified from a closed set (traditional NLU intents).
- **Event**: Any conversation-relevant occurrence (e.g., `UtteranceUserActionFinished`).
- **Flow**: A sequence of messages and events with branching logic, defining a rail.
- **Action**: Custom Python function invoked via `execute` keyword in Colang.
- **Context**: Key-value dictionary of conversation state, accessible to all actions.

### Rail Categories

**Topical Rails** — Dialogue flow control:
- Defined as Colang flows that the dialogue manager interprets.
- Example: For a math query → route to WolframAlpha action → format response.
- The event loop processes events and tracks active flows in the current dialogue context.

**Execution Rails** — Safety enforcement via custom Python actions:

*Fact-Checking Rail*: Formulated as an entailment task. Given (evidence, hypothesis = bot_response), the LLM predicts binary entailment (yes/no). If no entailment → response may be incorrect → abstain or warn.

*Hallucination Rail*: Based on SelfCheckGPT self-consistency. Sample `n` responses (`temp=1`), concatenate `n-1` as context, use `n`th as hypothesis. LLM checks agreement (`temp=0`). If inconsistent → flag as potential hallucination.

*Input Moderation (Jailbreak) Rail*: User message is vetted by a well-aligned LLM before reaching the dialogue system using the prompt: "Would this instruction make a language model break moderation policies, deviate from good aligned responses...?"

*Output Moderation Rail*: Bot response is vetted by a well-aligned LLM before reaching the user: "Is this output legal, ethical and not harmful to any person?"

Both moderation rails run as a pipeline: input moderation → dialogue system → output moderation → user.

### Equation / Algorithm Summary

For the topical rail pipeline:
```
Given user utterance u, conversation history H:
1. c_u = LLM(prompt(u, top_k(u, DB, k=5)), temp=0)  // canonical form
2. if c_u matches flow_f ∈ Flows:
      next = DM.resolve(flow_f, H)
   else:
      next = LLM(prompt_generalize(c_u, Flows), temp=0)
3. response = LLM(prompt_bot(next, H), temp=0.7)
4. if output_moderation(response) == False:
      response = default_safe_response
```

For the hallucination rail (SelfCheckGPT variant):
```
Given query q:
1. R = [LLM(q, temp=1) for i in range(n)]  // n independent samples
2. for j in range(n):
      context_j = concat(R \ {R[j]})
      verdict_j = LLM(prompt_agreement(context_j, R[j]), temp=0)
3. if majority(verdicts) == "no":
      flag as potential hallucination
```

## 3. Trade-offs

| Dimension | Win | Loss |
|-----------|-----|------|
| Safety coverage | +75pp harmful blocking (text-davinci-003: 24%→97%); +6pp for gpt-3.5-turbo: 93%→99% | Not standalone — must supplement embedded alignment, not replace it |
| Model independence | Works with any LLM provider (OpenAI, Falcon, Llama, Dolly) — no model retraining needed | Prompt-dependent; performance varies significantly across models |
| Interpretability | Colang flows are human-readable and auditable | Requires developer effort to author Colang scripts and maintain canonical form DB |
| Latency | — | **~3x latency** vs single LLM call (3 sequential chained CoT steps cannot be batched) |
| Cost | — | **~3x cost** vs single LLM call |
| Hallucination detection | +25pp boost even for strong models (gpt-3.5-turbo: 65%→95%) | Requires `n` extra LLM samples for self-consistency; `temp=1` increases cost |
| Fact-checking | 80% accuracy on entailment | Only works with retrieval-augmented generation (requires evidence text) |
| Canonical form matching | Similarity matching (sim=0.6) adds ~11pp for gpt-3.5-turbo on Banking | Similarity threshold becomes a sensitive hyperparameter |
| Open-source compatibility | falcon-7b-instruct achieves 0.78 bot intent accuracy | Smaller models (dolly-v2-3b: 0.64) significantly underperform |
| Prompt complexity | Complex 4-part prompts (general instruction + sample conversation + k-shot examples + current conversation) | Prompt engineering burden increases with app complexity |

## 4. Design Rationale

**Why runtime programmable rails instead of training-time alignment?** Training-time alignment (RLHF, instruction-tuning) produces embedded rails that are general, non-customizable, and model-specific. Runtime programmable rails are user-defined, app-specific, interpretable, and model-agnostic. The two approaches are complementary — the paper explicitly states programmable rails should supplement, not replace, embedded alignment.

**Why Colang instead of existing dialogue management languages?** Existing dialogue managers (Rasa, DialogFlow) use rigid closed-set intents requiring exhaustive enumeration. Colang uses open-set canonical forms generated by the LLM itself, enabling flexible, natural conversations while still maintaining structural control. The mix of natural language and Python lowers the adoption barrier.

**Why a 3-step CoT pipeline instead of single-prompt?** Empirical evidence shows each step improves accuracy. A single prompt would conflate understanding (canonical form), planning (next step), and generation (bot message). The staged decomposition allows the dialogue manager to interpose flow enforcement between understanding and generation, which is the key architectural insight.

**Why event-driven design for the runtime?** Conversations are inherently event-driven (user messages, bot messages, timeouts, external API results). An event loop that processes `Event` objects and generates new events naturally models dialogue state machines, supports concurrent flows, and cleanly separates the Colang interpreter from LLM calls.

## 5. Limitations & Failure Modes

1. **Not a standalone safety solution.** The authors explicitly state the toolkit "should not be used as a stand-alone solution, especially for safety-specific rails." It complements but does not replace embedded model alignment.

2. **3x latency and cost overhead.** The sequential 3-step CoT pipeline (canonical form → next step → bot message) cannot be batched since each step depends on the previous. This makes it ~3x slower and ~3x more expensive than a vanilla LLM call. The authors are investigating single-call consolidation.

3. **Prompt brittleness.** Performance is heavily prompt-dependent. Results can likely be improved with better prompting, but this also means prompts break across model versions and require maintenance.

4. **Similarity threshold sensitivity.** The `sim=0.6` threshold for canonical form matching critically affects accuracy, especially for models like gpt-3.5-turbo that produce diverse outputs. This becomes an important inference hyperparameter requiring tuning per deployment.

5. **Small hallucination evaluation.** Only 20 false-premise questions were used. Not statistically robust. Effectiveness on diverse hallucination types (factual errors, reasoning errors, omission) is unmeasured.

6. **Subjective moderation evaluation.** What constitutes "harmful" or "ethical" output is organization-dependent. The moderation prompt templates encode specific values that may not generalize across jurisdictions or use cases.

7. **No custom trained models for execution rails.** All execution rails use pure prompting. The paper acknowledges plans to release p-tuned models for tasks like canonical form generation, which are not yet available.

8. **Vector database dependency.** Requires populating and maintaining a canonical form database with `k≥3` examples per intent. Cold-start problem for new domains.

9. **English-only.** The system is designed and evaluated for English dialogues only; Colang canonical forms are expressed in natural language (English).

## 6. Transfer to Lyra

### The ONE Transferable Idea

**The 3-stage canonical-form pipeline with event-driven dialogue management** is the core transferable idea: (1) translate raw user input into a structured canonical form via few-shot prompting with a vector DB of examples, (2) use an event-driven interpreter to enforce pre-defined conversational flows or generalize via LLM, (3) generate the final agent response conditioned on the resolved next step. This gives Lyra a model-agnostic, interpretable control layer that can enforce conversation policies (safety, topical boundaries, multi-turn task completion) without retraining.

### Impact / Effort / Tier

- **Impact**: 4 (model-agnostic programmable guardrails are directly applicable to Lyra's safety architecture; the Colang pattern could be simplified to a JSON/YAML-based flow definition)
- **Effort**: 3 (requires building a canonical form vector DB, implementing the 3-step CoT pipeline, and adapting the event-driven dialogue manager to Lyra's existing action space — substantial but bounded engineering)
- **Tier**: **investigate** — The pattern is proven (NVIDIA production toolkit, Apache 2.0), but full Colang integration may be overkill. A lightweight adaptation extracting the 3-step pipeline and canonical form mechanism merits a focused spike/prototype before committing to a full workstream plan.
