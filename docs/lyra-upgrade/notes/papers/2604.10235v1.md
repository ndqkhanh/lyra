## 1. Mechanism (step-by-step)

CodeComp is a training-free, 4-stage framework that injects static program analysis (via Joern's Code Property Graph) into KV cache compression for agentic code tasks. It operates as a prefill-stage compression pipeline, not modifying the underlying model.

### Stage 1: Query-Conditioned Chunk Selection (Section 4.1)

- Partition repository-level code context into chunks {Ci} using structure-aware boundaries (method/function-level units). Long methods split to token budget; short fragments merged with neighbors.
- Score each chunk using query-conditioned perplexity (PPL):

```
si_ppl = (1/T) * sum_{t=1}^{T} -log p(q_t | prefix, C_i, q_{<t})   (1)
```

- Select top-k chunks with lowest PPL: S = TopK_i(-si_ppl)
- This reduces the search space before structural analysis is invoked.

### Stage 2: Structural Feature Extraction (Section 4.2)

- For each selected chunk C_i, extract a Code Property Graph (CPG) subgraph via Joern. The CPG unifies AST (Abstract Syntax Tree), CFG (Control Flow Graph), and PDG (Program Dependence Graph) into a single graph representation.
- Intra-chunk structural feature vector:

```
f_i = [N_call, N_control, N_return, N_assign, E_cfg, E_pdg]   (3)
```

where N_call = number of call expressions, N_control = number of control-flow constructs (if/for/while/switch), N_return = number of return statements, N_assign = number of assignment statements, E_cfg = number of control-flow edges, E_pdg = number of program-dependence edges.

- Logarithmic normalization with feature-specific scaling constant τ:

```
Norm(x; τ) = min(1, log(1+x) / log(1+τ))   (4)
```

- Weighted structural score for chunk C_i:

```
σ_i = Σ_k w_k · Norm(f_{i,k}; τ_k)   (5)
```

### Stage 3: Structure-Aware Budget Allocation (Section 4.3)

- Normalize structural scores across selected chunks to [0.5, 1.0] range:

```
s̃_i = {
    0.5,                                               if σ_max = σ_min
    (σ_i - σ_min) / max(ε, σ_max - σ_min),             otherwise   (6)
}
```

- Map to capacity multiplier: m_i = m_min + (m_max - m_min) · clip(s̃_i, 0, 1), with m_min=0.5, m_max=1.5
- Per-chunk token budget: B_i = floor(|C_i| · min(r_max, r · m_i)), where r is base compression ratio

### Stage 4: Span-Level Structural Protection (Section 4.4)

Structural spans are contiguous token sequences associated with CPG elements (function signatures, call expressions, control-flow predicates, return statements, assignments).

**Span scoring:**
```
s(z) = Σ_k w_k · f_k(z)   (9)
```
where f_k(z) are binary indicators of structural types.
Default weights: function calls (0.20), control-flow (0.18), query alignment (0.18), return (0.14), assignment (0.14), def-use edges (0.10), attention signal (0.06).

**Hard query-aware protection** for spans overlapping query symbols:
```
p_query(z) = { 1, if |S(z) ∩ Q| > 0; 0, otherwise }   (10)
```
Spans with p_query(z)=1 are unconditionally protected.

**Span selection under budget:**
```
B_i_span = min(B_i, max(B_min, floor(ρ_span · B_i)))   (11)
```
Two-stage selection: (1) protected spans first, (2) remaining spans ranked by s(z) greedily until budget exhausted.

**Token-level protection:** If selected spans cover fewer tokens than budget, fill with tokens nearest to protected spans in original sequence.

### Stage 5: Attention-Based Residual Compression (Section 4.5)

After structural protection determines which tokens must be kept, attention-based compression fills the remaining capacity. Per-token importance scores:

```
A = softmax(QK^T / √d)   (12)
u(j) = Σ_{t=1}^{W} A(t, j)
```

Retain top-ranked context tokens by u(j) up to the remaining budget per chunk.

### Stage 6: Position Encoding (Section 4.6)

- During chunk scoring, each chunk is formatted as [prefix; C_i; query] with contiguous positions from 0, enabling parallel scoring.
- During decode, final input is [prefix; Ĉ_1; Ĉ_2; ...; Ĉ_k; query].
- Query starts at position p_query = max_i(len(C_i)) + len(prefix), ensuring query always receives highest position indices.

**Control flow summary:** PPL-based chunk selection → Joern CPG extraction → structure-aware budget reallocation → structural span protection → attention-based residual fill → decode with compression applied independently at each transformer layer.

## 3. Trade-offs (wins vs. loses)

| Win | Lose |
|-----|------|
| **Training-free**: no model modification, no fine-tuning needed; works with any SGLang-compatible model | **CPG extraction dependency**: requires Joern, which limits language support (C/C++, Java, JS, Python; not Go, Rust, Swift, etc.) |
| **12x--14x accuracy recovery** on DebugBench and SWE-bench over ParallelComp at equal compression | **SnapKV beats CodeComp on GF F1** for Qwen-Coder at cap=0.6 (0.700 vs 0.613), suggesting SnapKV's observation-window eviction sometimes better for file-level localization |
| **Edit distance matches uncompressed baseline** (0.743 vs 0.740 on DS-Coder, 0.600 vs 0.601 on LCA) | **Structural analysis adds pre-processing latency** (though masked by inference time in end-to-end pipeline, 112-118s total) |
| **Structurally critical token retention near 100%** for callsites, branches, returns | **Chunk-level budget reallocation alone is weak**: capacity-only variant achieves max 0.450 at cap=0.2 vs 0.617 for span-only |
| **Seamless SGLang integration** for high-throughput agentic pipelines | **Not tested beyond 8B-scale models**; effectiveness on 32B/70B+ unknown |
| **Str. Score metric correlates with task accuracy**, serving as a reliable proxy for compression quality | **Absolute resolve rate on SWE-bench remains low** across all methods -- compression not the primary bottleneck |
| **Consistent Pareto improvement** across 5 benchmarks, 2 models, 2 task types | **PPL-based chunk selection is simple**: misses cross-chunk dependencies; could be improved |

## 4. Design Rationale

**Why structural priors over attention-only:** The core motivation is that attention scores and structural importance are fundamentally misaligned for code. The Jaccard overlap between the two rankings is only 0.0944. Attention is a learned, query-driven proxy based on token co-occurrence patterns; code semantics are governed by formal structure (control flow, data dependencies, call relationships) that attention may not capture. A variable definition at the head of a def-use chain or a branch condition governing faulty logic often receives low attention at a given decoding step but is essential for correct reasoning.

**Why CPG over individual representations (AST, CFG, PDG):** The CPG unifies all three graph representations into a single structure, enabling joint reasoning across syntax, control flow, and data dependencies without managing multiple disconnected analyses. Joern provides a battle-tested, production-grade CPG extraction tool.

**Why span-level over token-level protection:** Decisive code evidence is concentrated in local regions (call expressions, predicates, return statements) rather than isolated tokens. Protecting contiguous spans preserves syntactic context around structurally critical elements, making them more interpretable as reasoning units.

**Why training-free:** Avoids the cost and brittleness of fine-tuning models for specific code compression patterns. Works out-of-the-box with any model supported by SGLang.

**Why SGLang over Transformers library:** SGLang provides native support for high-throughput agentic inference workflows, enabling CodeComp to integrate into production pipelines, whereas existing methods are implemented on the slower Transformers library.

## 5. Limitations & Failure Modes

1. **Language dependency on Joern:** CodeComp inherits Joern's parser coverage. Languages not supported by Joern (Go, Rust, Swift, Kotlin, etc.) cannot benefit from structural priors.
2. **Not evaluated at scale:** All experiments use 8B-scale models (Llama3-8B, Qwen3-8B, Qwen2.5-Coder-32B for latency only). Behavior at 70B+ scale, or with very long contexts (>100K tokens), is unknown.
3. **SnapKV sometimes wins on file-level accuracy:** On Qwen-Coder at cap=0.6, SnapKV achieves GF F1 of 0.700 vs CodeComp's 0.613. The structural approach may over-prioritize call/control nodes at the expense of other relevant signal for file-level localization tasks.
4. **Low absolute SWE-bench resolve rates:** Across all methods, the absolute resolve rate on SWE-bench remains modest. Compression quality is not the primary bottleneck; retrieval quality and model reasoning capability dominate.
5. **Simple PPL-based chunk selection:** Uses perplexity alone; could miss chunks that are relevant through cross-file dependencies not reflected in surface-level PPL.
6. **CPG extraction cost:** While amortized by inference time in the reported pipeline, CPG extraction is non-trivial for very large repositories (>1000 files) and could become the bottleneck at extreme scale.
7. **No evaluation on non-code agentic tasks:** The approach is code-specific; structural priors would need fundamentally different definitions for natural language or other structured domains.
8. **Window-size sensitivity:** Attention aggregation uses a context window of 128 tokens and sliding window of 5; these hyperparameters may need tuning for different models and task types.

## 6. Transfer to Lyra

**The ONE transferable idea:** Structure-aware context compression using static program analysis priors. When Lyra processes large repository-level code contexts, it should leverage AST/CPG-derived structural signals to prioritize which code regions to preserve in its context window. Rather than relying solely on embedding similarity or attention-based relevance scoring (which the paper shows has only 0.0944 Jaccard overlap with structural importance), Lyra should protect semantically critical code elements -- function calls, control-flow predicates, return statements, and def-use chains -- from being truncated or summarized away.

**Lyra workstream route:** §4.1 (Memory/Context Management) -- the idea directly addresses how Lyra compresses and prioritizes repository-level code context under finite context-window budgets. Secondary relevance to §4.5 (Tool Execution / Retrieval) if Lyra's retrieval pipeline is adapted to use structural signals for chunk selection and ranking.

**Impact:** 4 (high) -- Directly addresses a known failure mode in code agents (losing structurally critical context under compression). The approach is training-free and could be implemented as a middleware layer in Lyra's context assembly pipeline.

**Effort:** 4 (significant) -- Requires integrating Joern (or an equivalent CPG/AST extraction tool) into Lyra's context processing pipeline. The span protection logic is straightforward, but the CPG extraction pipeline, language coverage mapping, and integration with Lyra's existing chunking/retrieval system represent non-trivial engineering. May need to add language-specific parsers beyond Joern's coverage.

**Tier:** Breakthrough -- This paper identifies a genuinely novel problem (structural blind spot in KV cache compression for code) and provides a training-free solution with strong empirical gains. The transferable idea is well-scoped: add a structural signal layer to Lyra's context assembly that preserves critical code evidence before compression/summarization.
