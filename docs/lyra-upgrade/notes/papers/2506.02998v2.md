## 1. Mechanism (step-by-step)

The framework uses **two specialized LLM agents** in a collaborative, iterative refinement loop. No model retraining or fine-tuning is required.

### Formal Problem Definition

Given a question `q_d` in dialect `d ∈ D`, a privacy policy snippet `p`, and a QA model `f` producing answer `A = f(p, q_d)`, the goal is to minimize the **maximum performance disparity** across dialects:

```
∆(f) = max_{di,dj∈D} |Φ_di(f) — Φ_dj(f)|
```

while maintaining or improving average accuracy.

### Step 1: Dialect Agent — Query Translation

The Dialect Agent receives:
- **Dialect metadata** (`dialect_info`): A concise summary of the dialect's phonetics, grammar, vocabulary, and cultural context (e.g., for Indian English: retroflex consonants, omission of articles, Hindi/Tamil loanwords).
- **User's dialectal query** (e.g., AAVE: *"Does y'all sell my datums?"*)

**Prompt template:**
> "You are an expert linguist specializing in the following dialect: {dialect_info}. Your task is to translate the following question from this dialect into clear, standard American English. Ensure that the translation is easily understandable to a general audience."

Output: A standardized SAE version of the query, preserving intent and cultural nuance.

### Step 2a: Privacy Policy Agent — Initial Classification

The Privacy Policy Agent receives:
- The **translated SAE query**
- The **privacy policy segment**

**Prompt template:**
> "You are a privacy policy expert. Review the provided policy segment and answer the following question in a concise manner, ensuring factual accuracy. Base your response solely on the information in the policy segment."

For **PrivacyQA** (sentence selection): classifies each candidate sentence as `Relevant` or `Irrelevant`.  
For **PolicyQA** (span extraction): extracts the precise answer span from the policy text.

Output: `(initial_answer, reasoning)` pair.

### Step 2b/2c: Dialect Agent — Intent Validation

The Dialect Agent receives:
- The **original dialectal query**
- The **privacy policy segment**
- The **Privacy Agent's proposed answer**

**Prompt template:**
> "Based on your understanding of the dialect's linguistic and cultural nuances, determine whether the Privacy Agent's answer fully addresses the user's original question. Are there any discrepancies or misunderstandings that arise from the dialectal phrasing?"

Two outcomes:
- **Agree** (Step 2c): Answer accepted as final output.
- **Disagree** (Step 2b): Triggers reconsideration.

### Iterative Refinement Loop

When the Dialect Agent disagrees, the Privacy Policy Agent is prompted to revise:

> "You received feedback indicating that certain elements of the user's dialectal query were not fully addressed. Please revise your previous answer to incorporate the Dialect Agent's insights and ensure the user's intent is accurately captured."

The loop repeats until agreement is reached or a **maximum of 2 iterations** is hit.

### Few-Shot Configuration

In few-shot mode: **8 examples per prompt per agent**, covering diverse dialects, question types, and policy scenarios.

### Dialect Data Generation

Queries are converted using the **Multi-VALUE framework** (Ziems et al., 2023): a rule-based system applying 189 linguistic perturbation rules across 50 English dialects, transforming SAE into synthetic dialect forms while preserving semantics.

## 2. Results (real benchmark numbers)

### PrivacyQA (F1 score, sentence classification)

|-------|---------|-----|--------------------|----------|----------|
| GPT-4o-mini | Zero-shot | 0.394 | 0.335 | 0.022 | 0.093 |
| GPT-4o-mini | Few-shot | 0.605 | 0.565 | 0.016 | 0.058 |
| GPT-4o-mini | **Multi-agent-zero (ours)** | 0.601 | **0.587** | **0.007** | **0.025** |
| GPT-4o-mini | **Multi-agent-few (ours)** | 0.611 | **0.598** | **0.005** | **0.019** |
| Llama 3.1 8B | Zero-shot | 0.469 | 0.368 | 0.035 | 0.144 |
| Llama 3.1 8B | **Multi-agent-zero (ours)** | 0.549 | **0.528** | **0.007** | **0.029** |
| DeepSeek-R1-Distill-14B | Zero-shot | 0.532 | 0.527 | 0.011 | 0.037 |
| DeepSeek-R1-Distill-14B | **Multi-agent-zero (ours)** | 0.582 | **0.577** | **0.005** | **0.017** |

**Key headline:** GPT-4o-mini zero-shot accuracy improved from 0.394 to 0.601 (multi-agent-zero), **surpassing the few-shot baseline of 0.565 without any training examples**. Max disparity reduced from 0.093 to 0.025 (73% reduction).

### Ablation Data

- **Without dialect info:** Initial F1 drops from 0.5772 → 0.5210 (delta -0.056). Final stage still reaches 0.5894 (vs 0.5966 with full info), demonstrating the iterative loop provides partial recovery.
- **Initial vs. Final answer quality:** PrivacyQA zero-shot 0.53 → 0.59; PolicyQA zero-shot 0.43 → 0.45.
- **Dialect Agent override rates:** 22.99% (zero-shot), 31.75% (few-shot).
- **Override quality:** 63.4% beneficial (zero-shot), 72.1% beneficial (few-shot); 24.1% detrimental (zero-shot), 18.7% detrimental (few-shot); ~9% neutral.
- **Translation quality:** BLEU = 46.5, ROUGE-L = 80.5 (vs. human-authored SAE references).
- **Hallucination check:** 0 hallucinations in 500+ manually inspected translations.

## 3. Trade-offs (wins vs. loses)

| Win | Lose |
|-----|------|
| **Disparity reduction up to 82%** (Max Diff from 0.093 → 0.025 on PrivacyQA) | Requires accurate dialect metadata — performance drops 5.6 F1 points without it |
| **Zero-shot matches/exceeds few-shot baselines** (0.601 vs. 0.565 on PrivacyQA) | 18.7-24.1% of Dialect Agent overrides are **detrimental** (introduce new errors) |
| **Works across 3 model families** (GPT, Llama, DeepSeek) with no retraining | Some dialects still lag SAE — disparities reduced but not fully eliminated |
| SAE performance also improves (not just non-standard dialects) | Maximum 2-iteration loop may leave some conflicts unresolved |
| **No hallucination observed** in 500+ spot-checked translations | English-only; unknown generalization to other languages |
| Lightweight: prompt-based, no fine-tuning, no dialect-specific training data | Adds latency from iterative refinement (extra LLM calls per query) |
| Scalable to 50 dialects via rule-based Multi-VALUE transformations | Synthetic dialect data may miss natural variation; real-world performance unverified |

## 4. Design Rationale

The approach is grounded in **human-centered design** (Cooley, 2000): instead of forcing users to adapt to the system, the system adapts to users' linguistic identities. The key architectural choice is **prompt-based multi-agent collaboration over fine-tuning** because: (a) collecting large dialect-specific training data is infeasible for marginalized communities, especially in sensitive domains like privacy; (b) prompt-based methods are model-agnostic and immediately deployable; (c) separating dialect expertise from domain expertise (Privacy Policy Agent) allows each agent to specialize, improving reliability. The use of Multi-VALUE's rule-based perturbations (rather than neural generation) ensures controlled, reproducible dialect transformations. The iterative disagreement loop mimics human expert review processes, where a linguist would validate whether a policy answer truly addresses a user's intent.

## 5. Limitations & Failure Modes

1. **Synthetic data gap:** All dialectal queries are rule-based transformations via Multi-VALUE, which may not capture natural code-switching, mixed-dialect utterances, or real-world dialect fluidity. Real user-generated dialect queries remain untested.

2. **Dialect metadata dependency:** Performance drops significantly (Initial F1 from 0.5772 to 0.5210) when dialect labels/descriptions are unavailable. The framework assumes the user's dialect identity is known a priori.

3. **Residual disparities:** Even best models show >0.017 Max Diff — some dialects (RAAVE, Jamaican) consistently underperform SAE, suggesting fundamental limits to prompt-based mitigation.

4. **Detrimental overrides:** 18.7-24.1% of Dialect Agent interventions introduce new errors. The override mechanism has no meta-evaluation gate to detect when the Dialect Agent is wrong.

5. **English-only scope:** Framework tested on 50 English dialects only; no evidence of cross-lingual generalization to dialect continua in other languages (Arabic, Chinese, Spanish).

6. **Maximum 2 iterations:** Hard stop on refinement loops means some dialectal misunderstandings are left unresolved.

7. **No deployment cost analysis:** Additional API calls per query (minimum 2, maximum 4 per agent) not quantified in cost or latency terms.

## 6. Transfer to Lyra

**The one transferable idea:** Structured multi-agent collaboration with asymmetric expertise (linguistic adaptation + domain verification) and a disagreement-driven iterative refinement loop — applied via prompting alone without model modification.

**How it maps to Lyra:** This is a strong candidate for **§4.2 (Agentic Engineering / Multi-Agent Orchestration)**. Lyra's agent architecture already uses specialized sub-agents; this paper provides rigorous evidence that:
1. Two specialized agents with complementary expertise outperform a single generalist agent.
2. Disagreement signals (override rate, beneficial/detrimental ratio) are measurable quality indicators that can gate agent outputs.
3. Domain-specific metadata injected into agent prompts (analogous to Lyra's context injection) substantially improves performance on under-served inputs.
4. The iterative refinement loop with a maximum iteration cap provides a practical template for Lyra's agent debate protocols.

**Concrete Lyra application:** A "Verification Agent" (analogous to the Dialect Agent) that reviews outputs from domain-specific agents, flags discrepancies, and triggers bounded refinement loops. The override rate and beneficial/detrimental ratio become operational metrics for Lyra's quality observability dashboard.
