## 1. Mechanism (Step-by-Step)

CollabCoder introduces a **Plan-Code Co-Evolution** framework with three interacting agents and two novel submodules that overcome the static-planning limitation of prior multi-agent code generation systems.

### Architecture

```
CollabCoder = ⟨A_plan, A_code, A_debug⟩
A_debug = ⟨A_CDM, A_RT⟩
```

Where:
- **A_plan**: Dynamic Planning Agent — generates and refines high-level solution plans
- **A_code**: Adaptive Coding Agent — generates/refines executable code from plans
- **A_CDM**: Collaborative Decision-Making module — decides *what* to fix (plan or code)
- **A_RT**: Reasoning Trajectory module — decides *how* to fix it with accumulated experience

### Iterative Pipeline (Algorithm 1, max T=5 iterations)

**Step 0 — Initialization:**
1. R(0) ← ∅ (empty reasoning trajectory)
2. π(0) ← A_plan(P) — generate initial plan from problem description
3. c(0) ← A_code(π(0), T) — generate initial code from plan + coding template

**Step 1 — Execution & Failure Collection:**
- Execute c(t) on test set {(x_i, y_i)} via oracle O
- Collect failure log F(t) = {all (x_i, y_i, ŷ_i) where ŷ_i ≠ y_i}
- If all tests pass → return c(t)

**Step 2 — Collaborative Decision-Making (CDM):**

Three parallel analyses are performed (Equation 3):

```
E_π(t):   Plan-level analysis — is the algorithmic reasoning in π(t) consistent with failures?
E_c(t):   Code-level analysis — are there implementation bugs assuming plan is correct?
E_align(t): Plan-Code alignment — is there semantic consistency between π(t) and c(t)?
```

Each analysis produces a **confidence score** φ_i,d ∈ [0,1] for each possible decision d ∈ {plan, code} and a **consistency score** ϕ_{H\{i},d} measuring agreement with other analyses.

The decision D(t) is obtained by maximizing an aggregated score across weighted analyses (Equation 5):

```
D(t) = arg max  Σ   w_i · φ_i,d · ϕ_{H\{i},d}
       d∈{plan,code}  i∈{π,c,align}
```

Where fixed trust weights are: **w_π = 0.4, w_c = 0.3, w_align = 0.3** (normalized Σw_i = 1).

- D(t) = 0 → update the plan (π)
- D(t) = 1 → update the code (c)

**Step 3 — Reasoning Trajectory Update (Equation 6):**

```
R(t+1) = A_RT(R(t), E_X(t), P, X(t), F(t))
```

Where X(t) is the selected refinement target (plan or code) and E_X(t) is its corresponding diagnostic analysis. This module explicitly accumulates historical debugging insights, identifies recurring error patterns, refines corrective heuristics, and avoids repeating ineffective fixes — enabling **learn-from-mistakes** rather than stateless trial-and-error.

**Step 4 — Conditional Refinement (Equation 8):**

```
If D(t) = 0 (plan update):
  π(t+1) ← A_plan(P, π(t), F(t), R(t+1))      // refine the plan
  c(t+1) ← A_code(π(t+1), T)                   // regenerate code from new plan
Else (code update):
  π(t+1) ← π(t)                                 // keep plan
  c(t+1) ← A_code(P, c(t), F(t), R(t+1), T)    // patch the code
```

Repeat from Step 1 until all tests pass or t = T (5 iterations exhausted).

### Key Innovation: Complexity Reduction

Prior methods (MapCoder, CodeSIM) have effective inference complexity **O(nk)** where n = debugging iterations and k = planning iterations — they explore multiple plans AND debug each. CollabCoder collapses this into a single evolving trajectory, reducing complexity to **O(t)** where t is only the number of refinement iterations (t=5, matched to k=1, n=5 in baselines).

### Prompt Templates

The paper provides full prompt templates (Figures 9–16):
- Initial Planning prompt includes recall of analogous problems
- Initial Code Generation enforces strict template compliance
- Merged Diagnostic Analysis requires structured Plan/Code/Content analysis with simulation + insight sections
- CDM Scoring produces structured JSON with confidence and consistency scores
- Reasoning Trajectory Update explicitly avoids repeating ineffective fixes

## 3. Trade-offs

| Win | Description |
|-----|-------------|
| Higher accuracy | 82.50% avg on Qwen2.5-Coder-32B vs 80.22% best baseline; gains widen on harder benchmarks (+11-20% relative) |
| Better efficiency | 30-57% token reduction vs MapCoder, 10-42% vs CodeSIM; 4-10 fewer API calls per problem |
| Robustness to difficulty | Milder performance degradation at harder difficulty levels (7 vs 3-5 problems solved at 1600-1800 range) |
| Self-improving debugging | RT accumulates experience across iterations — avoids repeating failed fixes, converges faster |
| Complementary modules | CDM + RT work synergistically; benefits scale with stronger backbones |

| Lose | Description |
|------|-------------|
| Requires strong LLM backbone | CDM's plan/code analysis and scoring demands strong reasoning — weak models produce poor analyses and decisions |
| Fixed trust weights | w_π=0.4, w_c=0.3, w_align=0.3 are hyperparameters; sensitivity analysis shows robustness but code-heavy configs drop to 37.8% Pass@1 |
| Limited test coverage | Debugging relies on sample I/O pairs only; no automatic test generation to catch edge cases |
| Plan overfitting risk | Can lock into overly strict plan interpretations (e.g., enforcing fixed-length sublists when they should be variable) |
| Missing conceptual leaps | Cannot autonomously discover balanced-tree optimization from BST example — needs human-specified algorithm knowledge |
| Single-language evaluation | Only tested on Python; no evidence for multi-language generalization |
| Fixed iteration budget | t=5 is fixed; no adaptive early-stopping for easy problems or extended budget for hard ones |

## 4. Design Rationale

**Why Plan-Code Co-Evolution instead of static planning?**

The core insight: prior multi-agent code generation (MapCoder, CodeSIM) fixes the plan during debugging. When the initial plan is flawed, the debugger wastes iterations patching code derived from a wrong strategy — equivalent to **O(nk)** wasted compute. CollabCoder instead allows the plan to evolve jointly with code, reducing effective complexity to **O(t)** in a single trajectory.

**Why trust-weighted CDM instead of simple error-flagging?**

Naive approaches always update code (like prior work). But distinguishing plan-level vs code-level errors is critical: fixing implementation bugs under a wrong algorithm converges to local minima. The CDM explicitly diagnoses which layer is at fault using three perspectives (plan, code, alignment), then votes with confidence/consistency scoring to decide.

**Why Reasoning Trajectory instead of stateless debugging?**

Prior systems treat each debugging iteration independently, leading to repeated failures from the same root cause. RT explicitly maintains and updates a persistent debugging strategy R(t) that accumulates diagnostic history, identifies recurring patterns, and avoids repeating ineffective fixes — a form of **verbal reinforcement learning** without gradient updates.

**Why fixed trust weights?**

The paper argues for stable, consistent decision behavior across tasks. Sensitivity analysis shows robustness across a broad range (balanced configs achieve 44-48.9% Pass@1 on LCB subset). Extreme code-heavy or alignment-heavy configs degrade sharply, confirming that plan-level analysis deserves modest priority.

## 5. Limitations & Failure Modes

### Explicit Limitations (stated by authors)

1. **Backbone LLM dependency:** Analysis, CDM scoring, and RT update all require strong reasoning capability. Weaker models (Seed-Coder-8B showed smaller absolute gains) produce degraded analyses, reducing effectiveness.
2. **Limited test coverage:** Relies on fixed sample I/O pairs for debugging. Missing edge cases not covered by samples cannot be caught.
3. **Fixed trust weights:** Hyperparameters shared across all tasks; potentially suboptimal per-problem.
4. **No automatic test generation:** Unlike some prior work (CodeSIM's simulation), CollabCoder does not generate additional test cases.
5. **Conceptual leap limitation:** Cannot autonomously introduce advanced algorithms (e.g., tree balancing) not present in the initial problem framing.
6. **Single-language:** Evaluated only on Python.

### Observed Failure Modes (Appendix A)

1. **Plan overfitting (MBPP Task 612):** CollabCoder enforced `len(sublist) != 2 → error`, contradicting the broader specification requiring variable-length sublist generalization. Subsequent iterations failed to revise this restrictive assumption.
2. **Missing functionality persistence (BST example):** Delete method and null handling initially missing (29/47 tests failed in iteration 1). After 2 iterations reached 83% pass but still missed balancing optimization — the framework struggles with algorithmic leaps not coded into initial reasoning.
3. **Semantic misalignment:** In the `remove_kth_element` example (Figure 6), the initial code assumed 0-based indexing while the specification implied 1-based, requiring 2 iterations to align — CDM correctly identified this as a plan-level error.

### Implicit Limitations

4. **No adaptive budget:** t=5 is fixed; easy problems may converge in 1-2 iterations while hard problems might benefit from more.
5. **Non-learnable trust weights:** w_i are hyperparameters, not learned per-task. A meta-learning approach could improve.
6. **No formal verification:** Plans and code are refined empirically via test failures only, with no formal guarantees.

## 6. Transfer to Lyra

### The One Idea

**Collaborative Decision-Making with Plan-Code Alignment Analysis.** The CDM module's approach of jointly analyzing plan errors, implementation errors, and plan-implementation alignment — then using trust-weighted confidence/consistency scoring to decide whether to revise strategy or execution — is directly transferable to Lyra's multi-agent debugging pipeline. Instead of always re-executing code (as current agent debug loops do), Lyra should first diagnose *where* the error originates before deciding *how* to fix it.

### Specific Application in Lyra

When a Lyra agent encounters a task failure:
1. **Plan Analysis Agent** inspects whether the high-level strategy/sequence is correct given the failure
2. **Execution Analysis Agent** examines whether individual tool calls/implementations are buggy assuming strategy is sound
3. **Alignment Analysis Agent** checks whether the execution faithfully implements the strategy
4. **CDM Fusion** aggregates these three analyses with trust weights into a binary decision: revise strategy → or fix execution →, avoiding wasted cycles on wrong-layer debugging
5. **Reasoning Trajectory** accumulates diagnostic patterns across retries to avoid repeating failed approaches

### Workstream Route

**§4.7 — Agent Debugging & Self-Repair** (specifically the error-attribution and root-cause-analysis subsystem, which currently lacks structured plan-vs-execution error discrimination)

### Impact Assessment

| Dimension | Score | Justification |
|-----------|-------|---------------|
| Impact | 4/5 | Directly improves agent reliability and efficiency; the static-planning flaw CollabCoder identifies is universal in multi-agent code gen and applies equally to Lyra's task execution loops |
| Effort | 3/5 | Requires implementing 3 parallel analysis agents, trust-weighted fusion, and reasoning trajectory accumulation — but the prompt templates and scoring mechanism are fully specified in the paper |
| Tier | **Breakthrough** | Plan-Code Co-Evolution is a paradigm shift from static planning (the default in virtually all agent frameworks including Lyra's current architecture). The 30-57% token savings and 11-20% accuracy gains on hard tasks demonstrate that *deciding what layer to fix* matters more than *how to fix it*. |
