## 1. Mechanism (step-by-step, with equations/algorithms)

The paper introduces **Strategy Genes** and the **Gene Evolution Protocol (GEP)** as a paradigm shift from documentation-oriented experience objects to control-oriented, evolution-ready experience representations.

### Core Abstraction: Gene vs. Skill

A **Procedural Skill** is modeled as a documentation package:

```
s = {d_main, d_aux}
d_main = {overview, workflow, pitfalls, error_handling}
d_aux  = {api_notes, examples, scripts}
```

Typical size: ~2,500 tokens. Optimized for human readability, instruction, and archival.

A **Strategy Gene** is a compact control-oriented representation distilled via a distillation map:

```
g = ψ(s)  or  g = ψ(H)    where H = past trajectories
g = (m, u, π, α, c, v)   ∈ G
```

Where:
- **m** = task-matching signals (keywords/trigger cues)
- **u** = compact one-sentence summary
- **π** = small set of strategic steps
- **α** = failure-aware AVOID cues
- **c** = optional execution constraints
- **v** = optional validation hooks

Typical size: ~230 tokens. Optimized for signal density and behavioral targeting.

### GEP Protocol (Gene Evolution Protocol)

GEP canonicalizes genes into structured objects: `g̃ = Γ(g)` ∈ G̃

Three-layer object hierarchy:
```
O = G ∪ C ∪ E
```
- **Gene (G):** atomic capability unit, minimal reusable control representation
- **Capsule (C):** validated task-level execution path with audit trail, `κ = (q, Gκ, Tκ, oκ, Vκ, ℓκ)`
- **Event (E):** immutable evolution log, `e = (t, ρ, asrc, adst, σ, ι, Δ, ν, τ)`

### GEP Loop (6-stage):

```
SCAN → SIGNAL → INTENT → MUTATE → VALIDATE → SOLIDIFY
(G, C, E) → σ → σ̂ → ι → a' → ν → (G', C', E')
```

1. **Scan:** Monitor runtime traces, tool logs, execution failures, stagnation signals
2. **Signal:** Convert raw traces into standardized protocol signals (machine-actionable triggers)
3. **Intent:** Determine evolution objective (repair, optimization, or extension)
4. **Mutate:** Generate candidate asset by rewriting code, prompt structure, strategy steps, AVOID cues
5. **Validate:** Execute candidate in sandbox against validation hooks
6. **Solidify:** Write validated capability back into protocolized repository as gene/capsule/event

### Formal Test-Time Control Definition:

Experience representation `r ∈ R`, `r = φ(H)` alters behavior without parameter updates:
```
y ~ p_θ(· | x, r; γ)  with γ held fixed (T=0.05, max_output=16,384 tokens)
```
Control-relevance requires: `p_θ(y | x, r) ≠ p_θ(y | x, ∅)` for a non-negligible subset of tasks.

### Evaluation Metric:

```
PassRate = (1/N) Σ ri     where ri = pi/ni
```
pi = checkpoints passed, ni = total checkpoints. Δ computed in percentage points vs. no-guidance baseline. 120-second timeout per trial.

## 3. Trade-offs (wins vs. loses)

| Wins | Losses |
|------|--------|
| **+3.0pp** avg gain over no-guidance with only ~230 tokens (vs. Skill at -1.1pp with ~2,500 tokens) | Naively appending failure history to Gene dilutes it: Gene+failure drops to 52.0% (from 54.0%) |
| **10x fewer tokens** than Skill while delivering superior control at test time | Multi-gene composition can be catastrophic: two complementary genes drop to 44.9% (-6.1pp vs no-guidance) |
| Robust to structural perturbation (inverted priority = 52.8%, overconstrained = 55.9%) | Sensitive to semantic corruption (wrong algorithm = 48.8%, wrong domain = 49.4%) |
| Gene is better carrier for failure history than Skill or freeform text (52.0% vs 47.8%/49.6%) | Complementary composition is more harmful than conflicting composition -- blurring is worse than contradiction |
| Editable structure matters: flattened Gene drops to 50.5% (-3.5pp loss vs structured Gene) | An outdated paradigm can outperform correct Gene (stale = 56.6%), introducing reliability ambiguity |
| Failure distilled into compact warnings is most effective: 54.4% (+4.6pp) | Adding documentation back to Gene (API notes, examples) always degrades performance |
| CritPt: 9.1% => 18.57% (2x) and 17.7% => 27.14% (1.53x) through gene-based evolution | Requires careful encoding design; not a drop-in replacement for any experience format |

## 4. Design Rationale (why this approach)

The authors argue that **representation is a first-order factor** in reusable experience. The dominant paradigm (skills, procedural memory, experience libraries) assumes that more structured, more complete documentation = better test-time control. The paper falsifies this assumption: the useful control signal in documentation-oriented skills is **sparse and concentrated** in a narrow procedural slice (Workflow section), while most surrounding material (Overview = -4.7pp) imposes burden.

The key insight is reframing reusable experience **not as a content-storage-and-retrieval problem but as a control-representation problem**. Skills optimize for human readability and knowledge transfer; genes optimize for signal density, applicability boundaries, and failure salience under constrained inference-budget. GEP adds a protocol layer that canonicalizes these control objects so they become **comparable, replaceable, composable, and evolvable** -- not ad-hoc prompt fragments.

The rationale for compactness (~230 tokens vs ~2,500) is that test-time control must operate under limited attention and token budget. The rationale for structure (keywords + summary + strategy + AVOID) is that control requires behavioral targeting, not documentary completeness. The rationale for protocolization (GEP) is that without stable boundaries and explicit schema, experience cannot be systematically accumulated, validated, and evolved across runs.

## 5. Limitations & Failure Modes

1. **Single model family:** All 4,590 trials use only Gemini 3.1 models (Pro Preview + Flash Lite Preview). Generalizability to Claude, GPT, or open-source models is untested.

2. **Scientific code-solving only:** The benchmark covers 45 scientific coding scenarios. Whether genes transfer to non-code domains (conversation, planning, creative tasks) is unknown.

3. **Complementary gene collapse:** Two complementary genes produce the worst result overall (44.9%, -6.1pp). The failure mode (attention competition/blurring) is identified but not solved.

4. **Naive accumulation hurts:** Simply appending failure history to Gene reduces effectiveness by 2.0pp. The paper shows this is a problem but only partially addresses it through "failure warnings only."

5. **Stale paradigm outperforms clean gene:** An outdated solution (stale_paradigm = 56.6%) beats the correct Gene (54.0%). This raises questions about how to verify gene quality and alignment with truth.

6. **No multi-turn/interactive evaluation:** All evaluations are single-shot program generation. Real agent workflows involve multiple turns, tool calls, and feedback loops.

7. **Cost accounting incomplete:** Reasoning-token costs were "not reliably recoverable from logs," so the $0.81 figure is input/output only.

8. **2-day evolution window:** Evolution runs lasted only ~2 days each. Long-term stability, gene-bloat, and diminishing returns over extended periods are unstudied.

9. **No adversarial robustness testing:** No tests for whether genes can be poisoned, whether conflicting genes degrade safety, or whether gene accumulation introduces security vulnerabilities.

## 6. Transfer to Lyra (the one idea + workstream route)

**The one transferable idea:** Replace Lyra's documentation-heavy skill/memory artifacts with compact, structured "strategy gene" objects that function as test-time control signals rather than passive reference material. Specifically: implement GEP-like canonicalization for Lyra's reusable experience units -- encode each unit as `{signals_match, summary, strategy, AVOID, constraints, validation}` at ~200-300 tokens, use the SCAN->SIGNAL->INTENT->MUTATE->VALIDATE->SOLIDIFY loop to evolve them from execution traces, and prioritize compact failure warnings over additive history accumulation.

**Workstream route: §4.2 (Memory & Experience Reuse)** -- This directly feeds the memory subsystem redesign. The Gene representation is a drop-in replacement for Lyra's current skill/memory artifacts. The GEP loop maps directly to Lyra's planned experience accumulation pipeline.

**Impact:** 4/5 -- If this works for Lyra, it could dramatically improve agent performance at lower token cost by replacing verbose documentation-style memories with compact control-oriented ones. The +3.0pp gain at 10x fewer tokens is compelling.

**Effort:** 3/5 -- Requires implementing: (1) gene schema and serialization, (2) distillation pipeline from traces to genes, (3) GEP loop integration with Lyra's runtime, (4) validation hooks. The reference implementation exists at github.com/EvoMap/skill2gep.

**Tier:** **Breakthrough** -- This represents a fundamental representational shift in how agent experience should be encoded, with rigorous empirical backing (4,590 trials) and a clear protocol specification. The finding that documentation-heavy artifacts *degrade* performance while compact control objects *improve* it is directly actionable and challenges core assumptions in current agent memory design.
