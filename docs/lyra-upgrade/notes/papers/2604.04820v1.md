## 1. Mechanism (Step-by-Step)

ANX is a co-designed protocol and architecture that replaces unstructured natural language and fragile DOM-based agent interaction with structured semantic formats and a decoupled 3EX runtime.

### 1.1 The ANX Protocol Family

Three protocol components work in concert:

**ANX Markup** — A hybrid structured encoding (XML-like) that represents tasks, fields, validation rules, interaction elements, and security annotations in a machine-executable format. Fields marked `"type": "sensitive"` are the security trigger: the rendering engine (ANX UI) communicates directly with ANX Core, bypassing the LLM entirely.

```
<x form c_8193>
## Create Job Seeker Account
<x input c_2354>**lastName:** Mingze</x>
<x options card_1675>
**industry:**
<x 0>Please select industry</x>
<x 1 it>Information Technology</x>
<x 2 finance>Finance</x>
</x>
<x button c_2326 tap="submit">[Create Account](/submit)</x>
</x>
```

**ANX Config** — A JSON-based configuration format for defining applications, SOPs, and multi-agent deployments:

```json
{
  "protocol": "ANX", "version": "1.0.0",
  "kind": "form",
  "title": "Create Job Seeker Account",
  "items": [
    {"nick": "lastName", "kind": "input"},
    {"nick": "industry", "kind": "options", "optionsSet": {
      "dataset": {"url_dataset": "http://localhost:7887/dataset/industries"},
      "valueNick": "id", "titleNick": "name"
    }}
  ]
}
```

**ANX CLI** — A lightweight cross-platform command carrier:
```
anx <cardKey> <action> params
```
Example: `anx c_8193 set_form '{"lastName":"Mingze","industry":"it"}'`

### 1.2 The 3EX Decoupled Architecture

The runtime separates concerns into three independent, composable layers:

| Layer | Component | Function |
|-------|-----------|----------|
| **Expression** | ANX Markup | Structured task representation; canonical description of what needs to be done |
| **Exchange** | ANXHub | Semantic vector marketplace for dynamic tool discovery; task routing; cross-agent state sync |
| **Execution** | ANX Core + CLI + Node | Parse structured specs → generate platform-agnostic CLI commands; execute on Nodes; stream results |

### 1.3 ANXHub: Dynamic Discovery Marketplace

Unlike MCP's pre-registered tool indices, ANXHub is a global marketplace that:
- Indexes ANX applications via semantic vector embeddings
- Returns top-k relevant tools for the current task (progressive disclosure)
- Requires zero pre-installation, zero local binaries ("use-and-go")
- Maintains fixed baseline token consumption regardless of skill library size

### 1.4 Protocol State Machine

The lifecycle defines two security-critical states:

- **WAITING_UI** — Sensitive data fields trigger this state; ANX UI communicates directly with ANX Core via encrypted channel. The agent never sees raw input; receives only a non-sensitive reference token.
- **CONFIRMING** — Critical actions require explicit human confirmation. This state has **no programmatic exit** — completion requires human interaction via a trusted dialog box that carries a User Token (managed exclusively by ANX UI, invisible to LLM).

### 1.5 ANX SOP: Deterministic Workflow Execution

SOPs are defined via ANX Config with explicit control flow semantics:

```
steps: [
  {uuid: "s1", start: true, nick: "CollectAndParse", kind: "form", ...},
  {uuid: "s2", nick: "AIDecision", kind: "condition",
   sources: ["s1"],
   case: [
     {when: "matchingScore >=80, no risks/flaws", targets: ["s3"]},
     {when: "matchingScore <80, or risks/flaws exist", targets: ["s4"]}
   ]},
  ...
]
```

**Control flow** uses two complementary mechanisms:
- `sources` — static structural dependencies (predecessor steps must complete); ensures determinism and verifiability
- `targets` — constrained candidate set for dynamic LLM routing at runtime; balances stability with adaptability
- `sources_join` — `"all"` (default, all executed sources complete) or `"any"` (first source completion triggers)
- **Precedence rule:** When a step appears in both predecessor's `targets` and successor's `sources`, dynamic routing via `targets` takes precedence

### 1.6 Security Architecture

**UI-to-Core Sensitive Data Isolation:**
1. ANX Markup marks fields as `sensitive`
2. ANX UI renders dedicated encrypted form, transmits directly to ANX Core
3. ANX Core auto-shields sensitive information when LLM requests ANX Markup
4. Agent receives only a non-sensitive reference token

**Human-Only Confirmation:**
1. Critical action triggers CONFIRMING state
2. ANX UI constructs trusted dialog, connects directly to ANXHub to obtain User Token
3. User Token is exclusively managed by ANX UI, invisible to LLM
4. Human-Validated Request must carry valid User Token
5. ANX Handler verifies token legitimacy before executing sensitive operation

**Threat Model (explicitly documented):**
- Defends against: LLM context leakage of sensitive data, automated misuse of critical operations
- Does NOT defend against: UI spoofing, untrusted ANX Core, non-official ANX Hub, LLM-induced social engineering

## 2. Results (Real Benchmark Numbers)

**Setup:** OpenClaw Agent (Dockerized), 13.2k baseline tokens (system prompts + core skills), 30 repetitions per method per model, Bonferroni correction (α = 0.0167).

### Qwen3.5-plus (1M context, temperature 0.7)

| Method | Total Tokens (k) | Task-Inc Tokens (k) | Execution Time (s) |
|--------|-----------------|--------------------|--------------------|
| GUI Automation | 22.3 ± 2.6 | 9.1 ± 2.6 | 33.2 ± 9.5 |
| MCP-based Skill | 20.6 ± 2.0 | 7.4 ± 2.0 | 30.8 ± 8.2 |
| **ANX** | **17.1 ± 1.6** | **3.9 ± 1.6** | **12.9 ± 2.7** |

- Token reduction vs MCP: **47.3%** (CI: [2.56k, 4.44k], t(55.3)=7.48, p < 0.001)
- Token reduction vs GUI: **57.1%**
- Time reduction vs MCP: **58.1%** (CI: [14.71s, 21.09s], t(38.6)=11.36, p < 0.001)

### GPT-4o (128K context, temperature 0.7)

| Method | Total Tokens (k) | Task-Inc Tokens (k) | Execution Time (s) |
|--------|-----------------|--------------------|--------------------|
| GUI Automation | 21.5 ± 2.8 | 8.3 ± 2.8 | 48.2 ± 12.2 |
| MCP-based Skill | 19.5 ± 2.1 | 6.3 ± 2.1 | 39.0 ± 9.1 |
| **ANX** | **16.0 ± 1.0** | **2.8 ± 1.0** | **16.5 ± 4.8** |

- Token reduction vs MCP: **55.6%** (CI: [2.645k, 4.355k], t(44.6)=8.24, p < 0.001)
- Token reduction vs GUI: **66.3%**
- Time reduction vs MCP: **57.7%** (CI: [18.72s, 26.28s], t(45.9)=11.98, p < 0.001)

**Key finding:** Relative efficiency gains are consistent across Qwen3.5-plus and GPT-4o, indicating the architecture (not model-specific optimization) drives the improvement.

**Cited reference result:** Grab (2025) SOP-driven agents achieved 99.8% accuracy on account takeover tasks, reduced processing from 23 min → 3 min, automated 87% of cases — used as validation of the tree-structured SOP approach that ANX inherits.

## 3. Trade-Offs

| Win | Lose / Cost |
|-----|-------------|
| 47-66% token reduction vs MCP/GUI on form-filling | Only evaluated on single 10-field form task — no multi-step SOP or multi-agent experiments |
| 58% execution time reduction | ANXHub discovery latency is "medium (optimisable)" with no quantitative data |
| Zero-install, use-and-go tool discovery (ANXHub marketplace) | Requires trusted ANX Core + official ANX Hub — compromised infrastructure breaks all security guarantees |
| LLM never sees sensitive data (UI-to-Core bypass) | Security claims are architectural, not experimentally validated (no adversarial testing) |
| Human-only confirmation with no programmatic exit | Human-in-the-loop adds latency for critical operations; no usability evaluation of confirmation overhead |
| Deterministic SOP execution with explicit sources/targets/conditions | No accuracy/completion rate reported for the evaluated task — efficiency only |
| Fixed baseline token cost regardless of skill library size (progressive disclosure) | ANX ecosystem does not exist yet — no marketplace, no adoption, two reference GitHub repos |
| Protocol-level semantic precision eliminates natural language ambiguity | New markup language adds learning curve; requires tooling (parsers, compilers) that don't exist beyond reference impl |
| 3EX decoupling enables independent layer evolution | Architecture complexity (3 layers + state machine + marketplace) vs simpler MCP tool-calling |

## 4. Design Rationale

The ANX design is motivated by a systematic gap analysis across four dimensions (Protocol & Tooling, Discovery, Security, Collaboration). The authors argue no existing approach simultaneously addresses all four.

**Why ANX Markup over natural language/Markdown/JSON:** Natural language is ambiguous and token-expensive; JSON schema (MCP) provides structure but not semantic precision. ANX Markup is a compact hybrid (XML-like) encoding with higher information density, explicit field semantics (validation rules, security annotations, conditional logic), and machine-executable determinism — the LLM specifies *what* to do, ANX Core handles *how*.

**Why 3EX decoupling over monolithic architectures:** Separating Expression (task spec), Exchange (tool discovery), and Execution (runtime) enables progressive disclosure — the LLM only receives task-relevant context rather than the entire tool catalog. It also allows each layer to be optimized, secured, and evolved independently without cascading changes.

**Why ANXHub marketplace over MCP pre-registration:** Pre-installation creates a cold-start problem and token explosion as tool libraries scale. A semantic vector marketplace with progressive disclosure maintains fixed baseline token cost. Real-time publish/subscribe enables dynamic updates without re-registration.

**Why UI-to-Core bypass over transport encryption:** Network-layer security (AIP, AgentCrypt) protects data in transit but not from the LLM itself. The fundamental insight: sensitive data must never enter the LLM context at all. Direct UI-to-Core communication achieves this via architectural isolation rather than encryption.

**Why SOP state machine over natural language workflows:** The Grab (2025) reference result (99.8% accuracy with tree-structured SOPs vs. ambiguous NL descriptions) validates that machine-executable workflow definitions eliminate the primary failure mode of multi-step tasks: inconsistent intent understanding across agents.

## 5. Limitations & Failure Modes

1. **Narrow evaluation scope:** Single task type (10-field form filling with dynamic options), no multi-step SOP execution, no multi-agent coordination experiments. The paper explicitly defers these to future work.

2. **Accuracy not measured:** Only token consumption and execution time reported. Task completion accuracy is discussed qualitatively but no success/failure rates are presented, making it impossible to verify that ANX maintains or improves task quality.

3. **Security claims are unevaluated architecture:** All security guarantees (UI-to-Core isolation, human-only confirmation) are presented as design properties with no experimental validation, adversarial testing, or penetration analysis. The paper acknowledges this as future work.

4. **Explicit threat model gaps:** The system does not defend against: UI spoofing (users cannot distinguish legitimate ANX dialogs from malicious imitations), untrusted ANX Core (a tampered Core compromises all UI-Core communication), non-official ANX Hub (malicious tool injection, task misrouting), or LLM-induced social engineering (LLM tricks user into sending sensitive data directly).

5. **Ecosystem immaturity:** Two GitHub repositories (anx-core, anx-protocol) exist but no community, no marketplace, no adoption. The paper is a design proposal with preliminary feasibility validation.

6. **Discovery latency is unquantified:** ANXHub semantic search latency is described as "medium (optimisable)" with no measurements, making it impossible to assess cold-start overhead vs MCP's pre-registered lookup.

7. **No comparison against fine-tuned models:** Approaches like Gorilla (Patil et al., 2024) that fine-tune models for API calling are not benchmarked. The paper plans lightweight specialized ANX models but has not built them.

8. **Single-LLM agent only:** Multi-agent collaboration is described in the architecture but not evaluated. The SOP case study (resume screening with Review Agent + Action Agent + HR human) is illustrative, not experimental.

## 6. Transfer to Lyra

### The One Transferable Idea

**Protocol-level structured semantics with decoupled 3EX architecture.** ANX's core insight — that agent interaction should be governed by a structured protocol (not ad-hoc NL prompts) with independent Expression, Exchange, and Execution layers — is directly applicable to Lyra's tool-calling and multi-agent orchestration. Specifically: (a) replace Lyra's natural-language tool descriptions with a compact structured markup that encodes field types, validation rules, and security sensitivity; (b) decouple tool discovery into a semantic marketplace layer (separate from execution) to enable progressive disclosure and fixed baseline token costs; (c) implement UI-to-Core bypass for any tool parameter marked `sensitive`, ensuring credentials/secrets never enter the agent's context window.

### Workstream Route

**§4.2 — Tool Protocol & Interface** (primary). The structured semantic protocol (ANX Markup + ANX CLI) is a direct upgrade to Lyra's tool definition and invocation format. The dynamic discovery marketplace (ANXHub) could be prototyped as a Lyra plugin registry.

**§4.4 — Security/Guardrails** (secondary). The UI-to-Core sensitive data isolation pattern is architecture-level security that Lyra could adopt for credential handling and confirmation gates.

| Dimension | Score | Rationale |
|-----------|-------|-----------|
| **Impact** | 3/5 | 47-66% token reduction is substantial; the decoupled architecture pattern is novel and generalizable. However, the paper's evaluation is thin (single task, no accuracy data). |
| **Effort** | 4/5 | Requires: protocol design for Lyra's tool surface, ANX-like markup parser, CLI command generation layer, semantic index for plugin registry, security annotations in existing tool definitions. Significant engineering. |
