## 1. Mechanism (step-by-step)

Moshi is a full-duplex spoken dialogue system built from three tightly integrated components and a novel multi-stream training procedure. Here is how it works end-to-end.

### 1.1 Helium: The Text Backbone (7B params)

Helium is an autoregressive Transformer with 32 layers, dimension 4096, 32 heads, Gated Linear Units (SiLU activation), RMS normalization, RoPE positional embeddings, context length 4096, trained with FlashAttention. Tokenizer: SentencePiece unigram, 32k vocabulary, English-focused, byte-backoff, single-digit number splitting.

- Trained for 500k steps on 2.1T tokens (87.5% filtered CommonCrawl, 12.5% high-quality sources: Wikipedia, StackExchange, scientific articles, Wikibooks).
- Data filtering pipeline: (a) FNV-1a hash + bloom filter for line-level dedup, (b) fastText fuzzy dedup on 3+ consecutive lines, (c) fastText language ID (threshold 0.85), (d) fastText quality classifier (9 categories mapped to source domains), weighted by line length.

### 1.2 Mimi: Semantic-Acoustic Neural Audio Codec

Mimi encodes 24kHz mono audio into discrete tokens at 12.5 Hz using a causal SeaNet autoencoder + Split Residual Vector Quantizer (RVQ).

**Architecture:**
- Encoder: 4 convolutional blocks, striding factors (4,5,6,8), final conv stride 2 → 512-dimensional latent at 12.5Hz.
- Transformer bottleneck: 8 layers, 8 heads, dimension 512, MLP 2048, GELU, LayerScale (init 0.01). One Transformer before quantization, one after. Both are causal.
- **Split RVQ** (key innovation): Instead of a single RVQ with 8 levels, a plain VQ (semantic, level 1) operates in parallel with an RVQ of 7 levels (acoustic, levels 2-8). Their outputs are summed for reconstruction. Each codebook has size 2048 (bitrate 1.1 kbps).
- Semantic distillation: WavLM embeddings (16kHz → average pooled to 12.5Hz, non-causal pooling for training only) are distilled via cosine distance loss into the first VQ level. A linear projection maps VQ-1 output to 1024-dim to match WavLM.
- Training: 50% quantization rate (only quantize 50% of sequences), adversarial-only loss (removing reconstruction loss) → MUSHRA 81.0 vs 58.8. AdamW, learning rate 8e-4, batch size 128 × 12s windows, 4M steps.
- Fully causal → 80ms initial latency, streaming-compatible.

### 1.3 Moshi: Multi-Stream RQ-Transformer with Inner Monologue

**RQ-Transformer architecture:**
- **Temporal Transformer:** 32 layers, dim 4096 (initialized from Helium weights). Processes one step per 80ms audio frame (S steps, not K×S). Produces context embedding z_s at each timestep.
- **Depth Transformer:** 6 layers, dim 1024, 16 heads, per-codebook parametrization (different linear layers for each of the K sub-sequences). Conditioned on z_s + embedding of previous sub-sequence at this timestep. Produces logits for K sub-sequences at each timestep.

**Formal model** — at each timestep s:

```
z_s = TrTemp(V_0, ..., V_{s-1})                    [Temporal Transformer, S steps]
l_{s,1} = Lin(z_s)                                   [Text token logits]
l_{s,k} = TrDepth(z_s, V_{s,1}, ..., V_{s,k-1})     [Depth Transformer, ≤K steps]
```

The joint sequence V has K = 2Q + 1 = 17 streams (Q = 8):
- `V_{s,1}` = W_s (text tokens, aligned to 12.5Hz via Whisper word timestamps, with PAD/EPAD special tokens)
- `V_{s,2}` = A_{s,1} (Moshi semantic tokens)
- `V_{s,1+q}` = A_{s-τ,q} for q=2..8 (Moshi delayed acoustic tokens, τ=1 or 2)
- `V_{s,1+Q+1}` = A'_{s,1} (User semantic tokens)
- `V_{s,1+Q+q}` = A'_{s-τ,q} for q=2..8 (User delayed acoustic tokens)

**Acoustic delay (τ):** Semantic tokens at time s, acoustic tokens at time s-τ. τ=2 during pretraining (240ms theoretical latency), τ=1 during finetuning (160ms). Without delay, perplexity explodes because semantic and acoustic tokens at the same timestep have high mutual information that the Depth Transformer cannot fully capture.

**Inner Monologue:** Text tokens W_s are predicted before semantic tokens at each timestep, serving as a per-frame prefix. This extends AudioLM's semantic→acoustic hierarchy to text→semantic→acoustic. Text tokens are aligned to the 12.5Hz framerate using Whisper word-level timestamps. PAD fills gaps between words (~65% of tokens), EPAD marks word boundaries. Text delay is randomized between ±0.6s during pretraining, set to 0 during finetuning.

**Training stages:**
1. **Helium pretraining:** 500k steps, batch 4.2M tokens, lr 3e-4, cosine schedule.
2. **Moshi pretraining (1M steps):** Single-stream audio, batch 16h audio. Temporal Transformer initialized from Helium, Depth Transformer random. 50% of batches are text-only (from Helium's dataset, separate optimizer state). Text masking probability 30%. Acoustic delay τ=2, text delay ±0.6s. Audio lr: Temporal 3e-5, Depth 2e-4. PAD weight reduced by 50% in cross-entropy.
3. **Post-training (100k steps):** PyAnnote diarization on unsupervised audio → simulated multi-stream (binary mask, no overlap). Then Fisher dataset (2k hours, separate channels per speaker) for 10k batches → real multi-stream dynamics. Batch 40min audio. lr: Temporal 2e-6, Depth 4e-6.
4. **Instruct finetuning (30k steps):** Synthetic instruct dataset (20k hours, generated via multi-stream TTS). Data augmentation: random gain (-24 to +15dB), noise (Deep Noise Suppression, -30 to +6dB relative), echo simulation (0-0.2 scale, 100-500ms delay), reverb. lr 2e-6 for both transformers.

**Loss function:**

```
L(V,l) = (1/S) * Σ_s [ CE(l_{s,1}, V_{s,1}) + (1/Σα_k) * Σ_{k=2}^{K} α_k * CE(l_{s,k}, V_{s,k}) ]
```

Semantic token weight α = 100 (critically important — without this, semantic gradients are swamped by acoustic token losses). Other token weights = 1.

### 1.4 Inference

At each timestep s, the model samples from the estimated distribution for Moshi's streams (text + semantic + acoustic tokens). User audio tokens are fed from microphone input (model predictions for user are ignored). Natural silence is encoded as specific "silence" token patterns. Forcing EPAD token triggers Moshi to start speaking. No explicit turn boundaries — Moshi can speak while listening, enabling overlapping speech.

## 3. Trade-offs

| Win | Loss |
|-----|------|
| First real-time full-duplex spoken LLM (160ms theoretical, 200ms practical latency) | Helium text LLM is 7B — competitive with Llama 2 but behind Mistral/Gemma on MMLU (54.3 vs 62.5) |
| Inner Monologue nearly triples SQA accuracy with only 1 extra token per timestep (17 vs 16) | MMLU drops from 54.3 (Helium text) to 49.7 (Moshi after multi-stream) — audio training degrades text knowledge |
| Mimi achieves MUSHRA 81.0 at only 1.1kbps, 12.5Hz, fully causal | VisQOL=1.84 suggests severe distortion — objective metrics are broken for adversarial codecs, requiring expensive human eval |
| Split RVQ resolves the semantic-vs-acoustic tradeoff that plagues single RVQ distillation | Audio safety (ALERT 83.05) lags far behind text-only LLMs (Llama 2 99.98); audio safety evaluation is underdeveloped |
| Multi-stream modeling enables overlapping speech, no turn boundaries | sWUGGY drops 74.8→63.0 after multi-stream instruct — lexical modeling degrades; textless-NLP benchmarks don't track downstream dialogue quality |
| Acoustic delay τ=2 reduces perplexity from 135.4 to 36.8 under low-latency constraints | Each timestep of delay costs 80ms in latency; τ=2 means 240ms theoretical floor |
| RQ-Transformer is not needed at high latency (τ=8, 640ms) but critical at realistic latencies τ=1-2 | RQ-Transformer adds a 6-layer Depth Transformer (extra params, extra forward pass per timestep) |
| W4A8 quantization preserves 95.7% artifact-free generation at ~5GB | Moshi's linguistic ability (MMLU) is more sensitive to quantization than Helium's — drops 7.5 points at W4A8 vs 1.3 for Helium |
| Watermarking with Audioseal works on clean audio (0.9999) | Completely broken by Mimi re-encode (0.08); generative watermarking blocked by non-idempotent codec tokens |

## 4. Design Rationale

**Why split RVQ instead of single RVQ with distillation?** A single RVQ requires the first level to carry both semantic meaning and residual acoustic information for higher levels. When WavLM distillation forces semantic content into level 1, it conflicts with acoustic reconstruction (ABX improves but MUSHRA drops to 57.8). The split architecture decouples them: a plain VQ for semantics, a parallel 7-level RVQ for acoustics. This removes the constraint that acoustic information be preserved in the semantic quantizer's residual.

**Why Inner Monologue instead of Chain-of-Modality (Spectron, SpeechGPT)?** Chain-of-Modality generates the full text answer first, then audio — incompatible with streaming. Inner Monologue generates text tokens *ahead of* audio tokens at each 80ms frame, enabling streaming while providing text as a per-timestep prefix. It extends AudioLM's semantic→acoustic hierarchy rather than replacing it.

**Why multi-stream instead of cascaded pipeline?** Cascaded ASR→LLM→TTS pipelines compound latency (several seconds), lose paralinguistic information (emotion, accent, tone), and are fundamentally turn-based. Multi-stream modeling processes both speakers as parallel token streams — no explicit turn boundaries, no modality switch.

**Why RQ-Transformer instead of independent heads (Copet et al. 2023)?** With sufficient acoustic delay (τ=8, 640ms), interdependence between sub-sequences at the same timestep is weak enough that independent classification heads work. But under real-time latency constraints (τ=1-2), semantic and acoustic tokens at nearby timesteps have high mutual information. The Depth Transformer jointly models them, dropping perplexity from 135.4 to 36.8 at τ=2.

**Why 50% text-only batches during audio pretraining?** Without them, spoken QA scores drop (WebQ: 26.6→23.2). Simply initializing from Helium is insufficient — text knowledge catastrophically forgets during audio training without interleaved text batches and separate optimizer states.

## 5. Limitations & Failure Modes

1. **Text knowledge degradation:** MMLU drops from 54.3 (Helium) to 49.7 (Moshi). Spoken QA on Trivia QA is only 22.8 vs 56.4 for Helium text. Multiple-sentence audio questions are challenging.

2. **Quantization sensitivity:** Moshi's linguistic ability degrades significantly more under quantization than Helium's. At W4A8, Moshi drops 7.5 MMLU points (vs 1.3 for Helium). Quantization-aware training would require re-running the entire multi-stage pipeline.

3. **Watermarking impossibility:** Audio watermarks (Audioseal) are destroyed by Mimi re-encoding. Mimi tokens are non-idempotent (semantic token identity drops to 50.3% with 40ms time shift). Generative watermarking is blocked because tokens change when re-encoded from waveform.

4. **Audio safety lags text:** Moshi's ALERT score (83.05) is well below text-only LLMs. Audio-specific toxicity (tone, irony, paralinguistic cues) is not evaluated. The safety analysis is text-only, missing the audio dimension.

5. **No real human evaluation of dialogue quality:** Turn-taking metrics and language model scoring (DialoGPT perplexity) are used, but no A/B tests with human raters on naturalness of conversations. The Fisher evaluation uses 1000 prompts with multiple temperatures, but these are simulated continuations, not real user interactions.

6. **English-only:** Helium is English-focused (32k unigram tokenizer). Mimi is evaluated on English speech (LibriSpeech dev-clean for ABX). Multi-stream training uses Fisher (English phone conversations). No multilingual capability is demonstrated.

7. **Catastrophic forgetting in fine-tuning stages:** sWUGGY drops from 74.8 (pretrain) to 60.9 (multi-stream instruct, synth voice). The authors note this does not degrade intelligibility, but it suggests the model is losing lexical knowledge during specialization.

8. **Objective metric failure:** VisQOL (1.84) and MOSNet do not correlate with MUSHRA (81.0) for adversarially-trained codecs. This makes optimization and fair comparison difficult without expensive human studies.

9. **Codec frame rate limits timing precision:** 12.5Hz means 80ms granularity for everything — turn-taking, word alignment, ASR timestamps. This is coarse for modeling conversational phenomena like short interjections ("uh-huh," "yeah") that last <80ms.

10. **Training data: Synthetic instruction data** generated from Helium + TTS may amplify biases, hallucinations, or stylistic quirks from the text model. No real human conversation data in the instruction-tuning phase (only synthetic).

## 6. Transfer to Lyra

**The One Idea:** Inner Monologue — predicting time-aligned text tokens as a streaming prefix before audio/speech tokens at each 80ms frame, rather than generating full text first (Chain-of-Modality) or in parallel (PSLM). This provides all the linguistic quality benefits of text-guided speech generation while remaining fully compatible with streaming, low-latency inference.

**Why it matters for Lyra:** Lyra's voice interface currently has latency bottlenecks between speech recognition and response generation. Adopting Inner Monologue would allow Lyra to interleave text and speech token prediction frame-by-frame, enabling streaming partial responses (users hear the beginning of the answer while the end is still being generated), preserving paralinguistic information with lower latency. The text stream also provides a natural hook for content moderation, factuality verification, and logging — all at 80ms granularity without waiting for the full response.

**Workstream route:** §4.2 (Voice Interface & Speech Pipeline)

**Impact:** 4 — High. Would meaningfully reduce perceived latency and enable new interaction patterns (interruption, backchanneling). Text streaming provides a hook for real-time content safety and factuality checks.

**Effort:** 5 — Very high. Requires training a neural audio codec (or adapting Mimi), a 7B+ text backbone with audio fine-tuning, multi-stream data preparation with diarization, and the RQ-Transformer architecture. The full pipeline involves 4 training stages and synthetic data generation. Even using Mimi+Helium/Moshi as a starting point, adaptation to Lyra's voice and domain would be substantial.

**Tier:** Breakthrough — Addresses the core latency and turn-based limitations of current spoken dialogue systems with a principled, streaming-compatible architecture. If successful, it would fundamentally change how Lyra interacts with users. However, the implementation complexity is extremely high (5/5 effort), meriting careful feasibility assessment before commitment.
