## 1. Mechanism

### Paradigm Shift: Tool Orchestration → Tool Amplification

**Tool Orchestration** (prior art: ChemCrow, ChemToolAgent, CoScientist) sequences predefined tools across multiple tasks. Accuracy plateaus at ~35% on molecule captioning because each tool's capability ceiling limits the chain.

**Tool Amplification** (this work) dynamically composes atomic tools into collaborative super-agents *within a single task*, transcending individual tool limits through hierarchical coordination.

### Bi-Phase Encapsulation Engine (Algorithm 1)

**Input:** Initial tool set T (LLM-selected), parameter k, empty library L

**Stage 1: Atomic-to-Composite Amplification (warm-up)**
```
For each atomic tool t ∈ T:
  repeat:
    Build agent composite tool A_n(t, A_{n-1}(t))
    Validate on task-specific metric → score s_i
    if s_i > s_{i-1} + δ: continue layering
    else: stop (plateau detected)
  Register {t, A_1, ..., A_n} into library L
```

Each composite tool wraps the previous layer, passing outputs upward. The agent (GPT-4o + ReAct) orchestrates tool calls within the composite. Convergence criterion: Δs < δ for consecutive iterations.

**Stage 2: Cross-Composite Synergy (hierarchical stacking)**
```
while global improvement:
  Sort L by performance
  t_1 ← top-1 tool (mandatory base)
  for t_j ∈ {t_2, ..., t_k} (top-k remaining):
    Build A_j(t_1, t_j) composite
    Validate → score s_j
  if max(s_j) > s* (global best):
    Add all composites to L
    s* ← max(s_j)
  else: terminate
```

**Output:** Best Agent Composite Tool A*, which is a nested hierarchy of tool-wrapping agents.

### Naming Convention
- `["Name2SMILES_0"]` = base atomic tool
- `["Name2SMILES_1"]` = 1-layer composite wrapping tool + agent
- `[["ChemDFM_0","Name2SMILES_1"], "ChemDFM_1"]` = nested: first composite [A,B] then wrapped with C

### Four Emergent Agent Behaviors (Case Studies)
1. **Correct:** Tool A produces wrong SMILES "C1(C)CC1"; Tool B retrieves correct "C1CC1"
2. **Modify:** RAG tool retrieves fragments → computational tool refines → cross-verify with second RAG
3. **Judge:** Both tools called simultaneously → agent compares outputs against chemical knowledge → selects plausible answer
4. **Reserve:** Agent recognizes complexity exceeds tool capabilities and declines to answer (emergent safety)

## 3. Trade-offs

| Win | Lose |
|-----|------|
| SOTA on 4 chemistry tasks (0-shot) vs specialist models, generalist LLMs, and orchestration agents | Greedy bottom-up search — may miss globally optimal tool compositions |
| 94% inference token reduction vs vanilla multi-agent systems (1/18th cost) | Relies on GPT-4o (proprietary, API-cost dependent, not self-hosted) |
| Works with ≤10 validation samples per task | Assumes high-quality validation data; performance degrades with noisy/incomplete samples |
| Automatically discovers optimal tool compositions (no manual design) | Constrained to chemistry domain; cross-domain generalization untested |
| Emergent safety behavior (Reserve pattern declines unanswerable queries) | Layer depth has hard ceiling: >7 layers yields diminishing/negative returns |
| Bi-phase design enables bottom-up capability amplification | Stage 2 depends on Stage 1 output quality — error propagation risk |
| Composable architecture supports heterogeneous tool sets | Only 2-4 tools evaluated; unclear scaling to large tool libraries (20+) |

## 4. Design Rationale

The authors argue that prior LLM-agent systems for chemistry hit a **capability ceiling** because they treat tools as fixed, atomic units to be sequenced (orchestration). Even state-of-the-art specialist tools (UniMol2, Chemformer, ChemDFM) have inherent accuracy limits. The key insight: **tools can transcend their native capabilities when dynamically composed into collaborative hierarchies**, similar to how ensemble methods surpass individual classifiers. The bi-phase design separates concerns — Stage 1 improves individual tools through self-stacking (vertical amplification), Stage 2 discovers cross-tool synergies (horizontal amplification). This bottom-up construction avoids the combinatorial explosion of exhaustive search while still discovering non-obvious compositions. The approach deliberately uses **≤10 validation samples** (not large training sets) because it optimizes *tool interaction patterns*, not model parameters — making it computationally lightweight and applicable in low-resource settings.

## 5. Limitations & Failure Modes

1. **Narrow task coverage:** Only 4 chemistry tasks evaluated; no retrosynthetic planning, multi-step optimization, or cross-domain (biology/materials) testing.
2. **Greedy search suboptimality:** Bottom-up layer-by-layer construction may miss globally optimal tool hierarchies that skip intermediate layers.
3. **Data quality assumption:** Assumes ≤10 high-quality validation samples; performance unproven with noisy, incomplete, or heterogeneous data.
4. **Proprietary lock-in:** Core agent is GPT-4o (closed-source); reproducibility and cost stability depend on OpenAI API.
5. **Tool library scaling unknown:** Only tested with 2-4 tools; behavior with 20+ heterogeneous tools (as in ChemCrow's 18 tools or ChemToolAgent's 29 tools) is unexplored.
6. **Validation metric alignment:** Training metrics (e.g., BLEU-2 for molecule design) differ from test metrics (Exact, Dis, Validity) — potential for metric gaming.
7. **Error propagation:** Stage 2 builds on Stage 1 outputs; errors in early composites can cascade upward through the hierarchy.
8. **Layer depth ceiling:** Performance plateaus and degrades beyond ~7 layers, limiting how much amplification is achievable per tool.

## 6. Transfer to Lyra

### The One Transferable Idea
**Bi-phase iterative encapsulation of atomic tools into self-optimizing composite agents.** Lyra's plugin/router subsystem could adopt this pattern: instead of statically chaining plugins (orchestration), individual Lyra plugins could be wrapped into self-evaluating "super-plugins" that discover optimal compositions through task-specific scoring. Stage 1 would amplify each plugin's individual capability (e.g., a code-search plugin wrapped with a self-correct agent), and Stage 2 would discover cross-plugin synergies (e.g., code-search + test-runner composites). This directly enables Lyra to transcend the capability ceiling of any single plugin.

### Workstream Route
**§4.5 Router/Plugins** — The composable agent architecture maps to Lyra's plugin composition and dynamic routing. The agent composite tool pattern (tool-as-building-block) offers a concrete design for Lyra's plugin middleware: plugins wrap other plugins, forming emergent capabilities through hierarchical coordination rather than flat sequencing.
