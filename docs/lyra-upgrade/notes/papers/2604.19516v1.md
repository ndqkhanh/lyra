# From Experience to Skill: Multi-Agent Generative Engine Optimization via Reusable Strategy Learning (Beining Wu*, Fuyou Mao*, Jiong Lin*, Cheng Yang*, Jiaxuan Lu, Yifu Guo, Siyu Zhang, Yifan Wu, Ying Huang, Fu Li — Hangzhou Dianzi Univ, Central South Univ, Shanghai AI Lab, Sun Yat-sen Univ, Ramus, HKUST(GZ), 2026, arXiv:2604.19516v1 [cs.AI], Code: github.com/Wubeining/MAGEO)

## 1. Mechanism (step-by-step)

**Problem reframing**: Traditional SEO optimizes for search rankings. Generative Engine Optimization (GEO) must optimize for citation accuracy and semantic influence within LLM-generated answers. Existing GEO methods treat each instance independently — no strategy reuse across queries or engines. MAGEO reframes GEO as a **strategy learning problem** with a two-layer architecture.

### Twin-Branch Evaluation Protocol
To isolate the causal effect of content edits from retrieval ranking noise:
1. Given query `q` and frozen retrieval list `L_ret = {d_1, ..., d_K}`
2. **Branch 1 (Baseline)**: Generate response `r_base` from original `L_ret`
3. **Branch 2 (Optimization)**: Sample target document `d_target` from `L_ret`, apply semantic interventions to produce `d*`, update list in-place as `L_new = L_ret[d_target ← d*]`, generate `r_opt`
4. Optimization objective: `d* = argmax_{d ∈ Ω(d_target)} S_DSV-CF(q, L_ret[d_target ← d])`

### Execution Layer — Four Coordinated Agents
1. **Preference Agent (A_pref)**: Analyzes large-scale query-response quadruples to construct engine-specific Preference Profile `P_G` — captures statistical density preferences, formatting preferences, and rhetorical patterns implicitly rewarded by each engine.
2. **Planner Agent (A_plan)**: Synthesizes `P_G`, current response state, and relevant skills from Skill Bank to formulate high-level revision strategies. Does NOT edit directly.
3. **Editor Agent (A_edit)**: Executes concrete modifications via parallel candidate sampling — structural adjustment, evidence enhancement, style adaptation.
4. **Evaluator Agent (A_eval)**: Predicts DSV-CF gains via LLM-as-a-Judge, applies **Fidelity Gate** rejecting any variant whose document-level semantic faithfulness falls below threshold `κ`.

### Generate-Evaluate-Select Loop (Algorithm 1)
```
Initialize: M_S ← ∅, d_t ← d_0, d* ← d_0, t ← 0, stall ← 0
Construct preference profile P_G ← A_pref(G)
Predict initial score Ŝ* ← A_eval(q, {d_0}, L_ret)[d_0]
while t < B and stall < P:
    Retrieve creator-level rules R_t ← Retrieve(M_C, q, G, d_t)
    Formulate strategy S_t ← A_plan(q, d_t, L_ret, P_G, M_S, R_t)
    Generate candidates V_t ← A_edit(d_t, S_t)
    Filter: V'_t ← {v ∈ V_t | Faithfulness(v, d_0) ≥ κ}  // Fidelity Gate
    If V'_t empty: stall++, continue
    Predict gains Ŝ_t(v) for each v ∈ V'_t
    v_best ← argmax Ŝ_t(v)
    If Ŝ_t(v_best) > Ŝ*: update d*, record success in M_S; else: stall++, record failure
    t++
MemoryConsolidation(M_S, M_C)
return d*
```

### Learning Layer — Skill Bank (3-stage lifecycle)
1. **Step-level Memory (M_S)**: Records every editing attempt within a session. Positive DSV-CF gains → retained as positive fragments. Failures/safety violations → flagged.
2. **Creator-level Memory (M_C)**: Cross-session consolidation. Recurring effective patterns are abstracted into structured strategy skills, indexed by engine type + scenario. Each skill includes: applicability conditions, editing operations, observed effectiveness (ΔMetrics). Enforces capacity limit per engine-scenario pair with recency/frequency-based eviction.
3. **Skill Retrieval**: On new task, A_plan queries Skill Bank with (engine, scenario) to retrieve matching skills as priors, narrowing search space and reducing exploration rounds.

### DSV-CF Metric
Dual-Axis Semantic Visibility and Content Fidelity:
- **SSV** (Surface): WLV (normalized word-level citation count), DPA (position-decayed citation authority), CP (citation prominence via LLM), SI (subjective impression)
- **ISI** (Intrinsic): AA (attribution accuracy — claims vs. source entailment), FA_resp (response-level faithfulness), KC (key-point coverage recall), AD (answer dominance)
- **Composite**: `S_DSV-CF = λ·S̄_SSV + (1-λ)·S̄_ISI − γ(1−AA)`, with `λ=0.5`, `γ=0.5`

## 3. Trade-offs

| Win | Loss | Magnitude |
|-----|------|-----------|
| 3.4× WLV vs best heuristic (GPT-5.2) | 4.0× token budget vs no-GEO baseline | Visibility gain > cost multiplier |

| Cross-engine generalization (proprietary + open) | Engine-specific preferences diverge; Skill Bank must be per-engine | Scales with #engines |

| Fidelity gate prevents hallucinated citations | Conservative gate may reject valid but aggressive edits | Trades visibility ceiling for trustworthiness |
| MAGEO Lite captures 87% of Full gain at 72% cost | Still 2.9× tokens vs heuristic | Sweet spot for production |
| LLM-judge correlates well with humans (ρ=0.81) | Remains an approximation; needs human audits in high-risk settings | Acceptable for scalable eval |

## 4. Design Rationale

**Why multi-agent over single-agent?**: Each subtask (preference modeling, planning, editing, evaluation) requires different reasoning profiles. Single-agent approaches conflate these roles, leading to unfaithful edits or convergence to local optima. The Evaluator as an independent fidelity gate prevents the Editor from "winning" via hallucinated citations.

**Why two-layer (execution + learning)?**: Pure iterative optimization wastes information — each session starts cold. The Skill Bank converts validated trajectories into structured, retrievable strategy artifacts. This mirrors how human SEO practitioners accumulate domain knowledge over campaigns, rather than reinventing tactics per page.

**Why engine-specific preference profiles?**: Ablation shows ~54% WLV drop without them. Different engines have distinct "personalities" — Gemini-3 Pro rewards compact tables and explicit URLs; GPT-5.2 rewards formal citation formatting (but hallucinates more); Qwen-3 Max prefers didactic, safety-framed prose. Generic optimization cannot address these divergent reward functions.

**Why Twin-Branch?**: Retrieval ranking is stochastic and confounds edit-effect measurement. By freezing the retrieval list, the protocol enables causal attribution — you know whether the edit caused the improvement, not random ranking drift.

**Why DSV-CF over simpler metrics?**: Existing metrics treat visibility and fidelity separately, allowing exposure gains via miscitation. The `−γ(1−AA)` penalty term explicitly penalizes hallucinated attribution, aligning the metric with the real goal: trustworthy visibility.

## 5. Limitations & Failure Modes

1. **Token cost and latency**: MAGEO Full uses 4× tokens and 39s latency vs baseline; unsuitable for real-time optimization or high-throughput pipelines.
2. **Model-specific benchmark bias**: Gemini-3 Pro handles reverse query generation and annotation; despite validation, benchmark may encode Gemini-specific preferences. Only >95% tag precision on manual spot-checks, not full annotation audit.
3. **Limited scale for subgroup analysis**: MSME-GEO-Bench covers 5 domains/15 sub-categories but current scale constrains fine-grained statistical comparisons across all subgroups.
4. **No formal skill generalization analysis**: Ablation proves Skill Bank helps, but no learning curve showing efficiency improvement per accumulated skill, nor analysis of skill transfer to unseen scenarios.
5. **Skill staleness**: Learned strategies may lose effectiveness as engines undergo distribution drift (model updates, prompt changes). No mechanism for detecting or adapting to drift.
6. **Text-only**: MAGEO works on text documents only; no multimodal GEO capability (images, tables in pages, video).
7. **Over-optimization fatigue**: After ~5 editing rounds, additional edits reduce faithfulness without visibility gains. Requires manual/empirical early stopping.
8. **Evaluator LLM is an approximation**: ρ=0.81 correlation with humans leaves room for misjudgment. Not validated on adversarial or edge-case content.

## 6. Transfer to Lyra

**The ONE transferable idea**: **Multi-agent optimization with a fidelity-gated evaluator and reusable strategy bank for black-box system optimization.** In MAGEO, four agents (Preference, Planner, Editor, Evaluator) collaborate iteratively, with the Evaluator acting as an independent fidelity checkpoint that rejects unfaithful edits. Validated editing patterns are distilled into structured skills indexed by (system, scenario) for cross-instance reuse, eliminating cold-start trial-and-error.

**Direct mapping to Lyra**: Replace "generative engines" with "LLM agent architectures" — Lyra's multi-agent system would benefit from:
- A dedicated **Fidelity Evaluator Agent** that independently checks output correctness before accepting any optimization
- A **Strategy Skill Bank** indexed by (task-type, agent-role) that accumulates validated improvement patterns across sessions
- Engine-specific **Preference Profiles** that characterize how different LLM backends respond to structural, evidential, and stylistic edits

**Workstream route**: **§4.2 (Multi-Agent Architecture)** — directly feeds the design of Lyra's agent coordination with fidelity gating and cross-session skill distillation. Also touches §4.5 (Evaluation/Observability) for the LLM-as-Judge validation protocol.
