## 1. Mechanism (Step-by-Step)

### Core Idea: Self-Challenging Agent (SCA)

The framework contains two roles played by the same or different LLMs:

**Role A: Task Challenger**
1. The challenger LLM is placed in an environment with access to tools (APIs, databases, code interpreter, web browser).
2. It explores the environment by taking actions (calling tools) to gather information about available operations and hidden state.
3. After exploration, it outputs a task in **Code-as-Task (CaT)** format containing four components:
   - **Instruction**: Natural language task description (e.g., "Return the Skateboard via paypal for order #W112")
   - **Verification Function**: Executable Python function `evaluate()` that inspects the final environment state and returns `True`/`False`
   - **Example Solution**: A valid sequence of tool calls that solves the task
   - **Failure Cases** (3x): Near-miss solutions that should NOT pass verification (wrong item ID, wrong payment method, wrong action type)

4. **Automatic Filtering Pipeline** (runs in an external code executor):
   ```
   Filter 1: Is all code runnable?
   Filter 2: Does example solution pass evaluate()? → assert True
   Filter 3: Do all failure cases fail evaluate()? → assert False
   ```
   If any filter fails, the error traceback is returned to the challenger for revision.
   Pass rate: ~5.2% for Llama-3.1-8B, ~34.4% for Llama-3.1-70B.

**Role B: Task Executor (Training)**
Two settings:

*Self-improvement* (same model for both roles): Collect rollout trajectories from the executor on CaT tasks. Apply REINFORCE with 0/1 outcome reward:

```
L = - Σ_{c∈Ĉ} E_{a_1:T ∼ π_exec} [ R̂_ĉ(s_T, a_T) · Σ_{t=0}^T log π_exec(a_t | o_{0:t}, a_{0:t-1}) ]
```

With sparse 0/1 reward, this reduces to **Rejection Fine-Tuning** (SFT on successful trajectories only). Also tested: DPO (offline), PPO (online), GRPO (online).

*Distillation*: Stronger teacher model (Llama-3.1-70B) samples trajectories on CaT tasks. Weaker student (Llama-3.1-8B) is trained via SFT on all trajectories (successful + failed):

```
L = - Σ_{trajectories} Σ_{t=0}^T log π_exec(a_t | o_{0:t}, a_{0:t-1})
```

Key insight: even failed trajectories from a strong teacher contain useful reasoning (reflections on mistakes).

**Environment constraints**: Max 15 steps per episode. Thought-action-observation loop. Code-as-action: agent outputs thoughts then executable Python function calls. Environment resets hidden state between challenger runs.

## 3. Trade-offs (Wins vs Loses)

| Win | Lose |
|---|---|
| +20.2% abs Pass@1 improvement using ZERO human data | 5.2% task generation pass rate for weaker models (heavy waste) |
| Eliminates false-positive rewards via failure case filtering | ~20% false-negative rate remains (semantic ambiguity in instructions) |
| Works across 4 diverse environments (calculation, web, retail, airline) | Improvements are environment-specific; joint training degrades performance |
| Online RL (PPO) yields +11.4% more than Rejection FT | Online RL unstable; GRPO collapses to 0% without careful tuning |
| Code-based verification is objective, executable, no LLM-judge noise | Requires environments with programmatic state access (not all tool envs have this) |
| Distillation uses both successful + failed trajectories (+4.4% gain) | Requires a stronger teacher model; self-improve still leaves large performance gap |
| Scales with more tasks (800 >> 200) | Task diversity collapses for weaker challengers after filtering |
| Fully automated, no human annotation | 32-80h of 8xA100 compute per environment (non-trivial cost) |

## 4. Design Rationale (Why This Approach)

1. **Why challenger explores first**: Human annotators explore tools/environment before designing tasks. A challenger that only reads API docs (PAE's approach) produces ambiguous, unverifiable instructions when the environment is partially observable. Interactive exploration reveals what is actually feasible.

2. **Why Code-as-Task (CaT)**: Previous approaches (PAE, Self-Instruct) use LLM judges for evaluation, which hallucinate and produce noisy signals. Code execution provides deterministic, objective verification. Code is also expressive enough to encode complex database queries and state inspections.

3. **Why example solution + failure cases together**: An example solution alone (with verification) eliminates impossible tasks but creates overly lenient verifiers. Failure cases as counterexamples harden the verification function against trivial/gaming solutions. Together, they ensure tasks are both feasible AND non-trivial.

4. **Why all trajectories in distillation**: Even failed teacher trajectories contain reasoning about mistakes — the student learns what NOT to do and why. This is analogous to process-based feedback rather than outcome-only.

5. **Why REINFORCE with 0/1 reward = Rejection FT**: With sparse binary outcome reward, the REINFORCE gradient is zero for failed trajectories, reducing RL to supervised fine-tuning on successes only. This is simpler, more stable, and empirically effective.

---

## 5. Limitations and Failure Modes

1. **Persistent False Negatives (~20%)**: CaT eliminates FP entirely but FN remains. Main cause: instructions missing critical information (e.g., "return one of my orders" without specifying which). Requires semantic reasoning, not syntactic filtering.

2. **Environment-Specific Improvements**: SCA does NOT produce a generally smarter agent. Skills acquired are environment-specific (e.g., learning that `book_hotel` doesn't accept positional args). Cross-environment training gives marginal or negative benefit.

3. **Oracle Gap**: Training on 800 SCA-generated tasks vs 800 human-crafted oracle tasks shows a persistent gap (visible in Figure 7 PPO comparison). Human tasks are better.

4. **Compute Cost**: 32-80 GPU-hours per environment for task generation alone. Total pipeline: ~60-90h on 8xA100 per environment.

5. **Online RL Instability**: PPO and GRPO are sensitive to hyperparameters. GRPO dropped to 0% success at end of training in reported experiments.

6. **Weak Model Task Quality**: Llama-3.1-8B challenger produces only 5.2% valid tasks; 70B produces 34.4%. The method's effectiveness depends on challenger capability.

7. **Task Distribution Collapse**: For weaker challengers, heavy filtering narrows task diversity (Figure 5a). Stronger challengers preserve diversity (Figure 5b).

8. **No environment-general agentic improvement**: The premise of learning transferable agent skills across environments is not achieved by this method.

## 6. Transfer to Lyra

### The One Idea: Code-as-Task (CaT) Self-Generation with Executable Verification

The core transferable mechanism is the **CaT formalism** — having the Lyra agent explore its tool environment, synthesize training tasks as `(instruction, verify(), example_solution, 3_failure_cases)`, automatically filter via code execution, and train on the survivors. This enables autonomous skill acquisition without human task curation.

### Application to Lyra:
Lyra could use CaT to self-generate training tasks in its multi-tool environments (code execution, web browsing, file operations, shell commands). The agent explores available tools, generates CaT-formatted tasks, filters them by running example solutions and failure cases against the verification function, then uses Rejection Fine-Tuning to improve on real test distributions. This directly enables Lyra to improve on arbitrary tool environments without human annotation.

### Workstream Route: **§4.1 — Agent Training / Continual Self-Improvement**

The §4.1 workstream covers Lyra's ability to autonomously improve through experience. CaT provides the task-generation machinery that §4.1's RL loop requires.

### Scoring:
| Dimension | Rating | Justification |
|---|---|---|
| **Impact** | 4/5 | Fundamentally changes how Lyra acquires skills — from human-curated tasks to self-generated ones. Enables deployment in novel environments without annotation cost. |
| **Effort** | 4/5 | Requires: (1) CaT prompt engineering per environment, (2) code executor sandbox with state reset, (3) multi-turn interaction loop for challenger, (4) filtering pipeline, (5) RL training infrastructure. Substantial systems work. |
| **Tier** | **breakthrough** | This is not parity work — it enables a capability shift from supervised training to autonomous self-improvement. The 95.8% relative improvement on real benchmarks with zero human data is a strong signal. |

### Key Implementation Considerations:
- Need sandboxed code executor with environment state reset capability
- Challenger model should be as strong as possible (70B+ tier) for high task pass rate
- Start with Rejection Fine-Tuning (simplest RL) before attempting online PPO
- Plan for ~80 GPU-hours per environment on A100-class hardware
- Monitor FN rate via periodic human spot-checking
