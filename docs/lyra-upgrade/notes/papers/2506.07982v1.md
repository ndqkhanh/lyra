## 1. Mechanism (step-by-step)

τ²-bench generalizes τ-bench by introducing a **dual-control environment** where both the AI agent and the (LLM-simulated) user possess distinct tools to act on a shared world. The system is formalized as a **Decentralized Partially Observable Markov Decision Process (Dec-POMDP)**.

### 1.1 Dec-POMDP Formalization

The interaction is defined by the tuple (S, {A_i}, {O_i}, T, R, U, M):

- **Message space (M)**: All NL messages exchanged between agent and user.
- **State space (S)**: S = S_world ⊗ S_history. S_world = S_db,agent ⊗ S_db,user represents two separate database states (e.g., CRM for agent, mocked phone for user). S_history logs all events.
- **Action spaces (A_i)**: Player i can either make a tool call a_i,tool ∈ A_i,tool or send a message m_i ∈ M. Only ONE player acts per turn.
- **Observation spaces (O_i)**: Either tool return data or the other player's message. Only ONE player observes per turn.
- **Transition function (T)**: T : S × A → S × O. Tool calls may change S_world. Messages yield observations for the other player. Both update S_history.
- **Reward function (R)**: R : S → [0,1] for task success/failure, verified via assertion functions on final world state.
- **Instruction space (U)**: Defines user scenario and agent domain policies.

**Key asymmetry**: The agent must reason about solutions AND guide the user; the user simulator only needs to follow instructions and use tools reactively (not plan independently).

### 1.2 Compositional Task Generator

Tasks are constructed from atomic building blocks (subtasks), each defined as a 3-tuple:

```
t = ({f_init_t,k}, {f_sol_t,k}, {f_assert_t,k})
```

- **Initialization functions** f_init: Set up initial state (e.g., `set_airplane_mode(True)`)
- **Solution functions** f_sol: Tool calls required to resolve (e.g., `toggle_airplane_mode()`). Must be agent or user tools.
- **Assertion functions** f_assert: Conditions final S must satisfy (e.g., `assert_service_status("connected")`)

Atomic subtasks are grouped into mutually-exclusive groups. A **composite task** = selecting at most one subtask from each group, concatenating all init/sol/assert functions. Task correctness is automatically verified: apply init → apply sol → check all assertions hold. Also verifies that the task is NOT resolved until ALL solution functions are applied.

For telecom: 15 atomic subtask groups across 3 intents (service_issue, mobile_data_issue, mms_issue), yielding 2285 tasks. 114 were subsampled for balanced distribution.

### 1.3 User Simulator with Environment Constraints

User behavior is constrained by:
1. **Available tools**: 15 read + 15 write tools for user (mock phone operations)
2. **Observable environment state**: User actions produce deterministic state changes in user's DB
3. **Tool output constraints**: User tools yield only human-readable outputs (no structural advantage)
4. **Reactive-only planning**: User only uses tools when agent requests; never solves problems independently
5. **Strict turn discipline**: One action per turn; cannot mix tool calls and messages

### 1.4 Evaluation Protocol

Tasks evaluated via 4 independent runs (temperature=0) using pass^k metric (fraction of k runs that succeed). Success criteria: assertion functions verified on final S_world state.

**Three ablation modes**:
- **Default**: Standard dual-control agent-user interaction
- **No-User**: Agent controls ALL tools; receives ticket summarizing user problem. Tests reasoning capability alone.
- **Oracle Plan**: Agent receives ground-truth tool-call sequence. Tests communication/coordination alone.

### 1.5 Tool Architecture

**Telecom Agent Tools**: 7 read + 6 write (get_customer_by_id, get_customer_by_phone, get_details_by_id, enable_roaming, send_payment_request, resume_line, change_plan, refuel_data, make_payment, transfer_to_human_agents, etc.)

**Telecom User Tools**: 15 read + 15 write (check_status_bar, check_network_status, check_sim_status, check_apn_settings, check_vpn_status, run_speed_test, can_send_mms, toggle_airplane_mode, reseat_sim_card, toggle_data, toggle_roaming, toggle_data_saver_mode, set_apn_settings, reset_apn_settings, reboot_device, grant_app_permission, etc.)

## 2. Results (real benchmark numbers)

### 2.1 Overall pass^k on New Telecom Domain

| Model | pass^1 | pass^2 | pass^3 | pass^4 |
|-------|--------|--------|--------|--------|
| **gpt-4.1** | 34% | 22% | 19% | ~15% |
| **o4-mini** | 42% | 29% | 26% | ~23% |
| **gpt-4.1-mini** | ~50% | ~30% | ~25% | ~18% |
| **claude-3.7-sonnet** | 49% | 37% | 31% | 25% |

Comparison: gpt-4.1 pass^1 drops from 74% (retail) and 56% (airline) to 34% (telecom), showing telecom is substantially harder.

### 2.2 Ablation: Dual-Control vs Autonomous (Telecom, original policy)

| Mode | gpt-4.1 pass^1 | o4-mini pass^1 |
|------|----------------|----------------|
| Default (dual-control) | 34% | 42% |
| No-User (autonomous) | 52% | 67% |
| Oracle Plan (known plan) | 67% | 73% |

- **No-User → Default drop**: 18% (gpt-4.1), 25% (o4-mini) — communication/coordination cost
- **Default → Oracle Plan gap**: 33% (gpt-4.1), 31% (o4-mini) — reasoning cost

### 2.3 Ablation: Workflow Policy Impact (Telecom)

| Mode | gpt-4.1 (orig) | gpt-4.1 (workflow) | o4-mini (orig) | o4-mini (workflow) |
|------|----------------|---------------------|----------------|---------------------|
| Default | 0.34 | 0.52 | 0.42 | 0.59 |
| No-User | 0.52 | 0.68 | 0.67 | 0.72 |
| Oracle Plan | 0.67 | 0.57 | 0.73 | 0.88 |

Workflow policy helps Default/No-User but hurts Oracle Plan for gpt-4.1 (confuses agent with redundant information).

### 2.4 Performance by Action Count (Default mode)

- ≤2 actions: ~80% pass^1 for both models
- 3-4 actions: ~50-60%
- 5-7 actions: ~20-30%
- 8-12 actions: approaches 0% in Default mode, ~10-30% in No-User mode
- >10 actions: gpt-4.1 outperforms o4-mini in No-User (better long-horizon reasoning)

### 2.5 Performance by Issue Type (pass^1, telecom)

| Issue Type | gpt-4.1 | o4-mini | Complexity |
|------------|---------|---------|------------|
| service_issue | ~66% | ~79% | Lowest (mean 2.31 actions) |
| mobile_data_issue | ~30% | ~48% | Medium (mean 4.31 actions) |
| mms_issue | ~18% | ~32% | Highest (mean 6.00 actions) |

### 2.6 User Simulator Reliability

| Domain | Conversations | Critical Errors | Benign Errors | **Total Errors** |
|--------|--------------|-----------------|---------------|------------------|
| airline | 100 | 13 (13%) | 34 (34%) | **47 (47%)** |
| retail | 50 | 6 (12%) | 14 (28%) | **20 (40%)** |
| **telecom** | **50** | **3 (6%)** | **5 (10%)** | **8 (16%)** |

Telecom's environment-constrained user simulator shows ~2.5x lower error rate vs retail, ~3x vs airline.

### 2.7 Cost

- Average per-task cost: $0.086 (agent) + $0.059 (user simulator) = ~$0.145
- Full run (all domains, 1 trial/task): ~$40

## 3. Trade-offs

| Win | Loss/Cost |
|-----|-----------|
| Dual-control testing reveals coordination failures invisible to single-control benchmarks | Benchmark complexity increases; domains harder to build and maintain |
| Environment-constrained user simulator reduces error rate from 40-47% to 16% | Requires domain-specific tool design; does not yet generalize to existing retail/airline domains |
| Programmatic task generation provides provable correctness and controlled complexity scaling | Still relies on human experts for domain curation (atomic subtask design) |
| Ablation modes (No-User, Oracle Plan) separate reasoning vs communication failures | Running all ablations multiplies evaluation cost by ~3x |
| Workflow-based policy improves Default/No-User performance | Workflow policy can confuse agent when Oracle plan is given (negative transfer) |
| pass^k metric captures reliability/consistency beyond single-run success | Requires k independent runs per task, increasing evaluation cost |
| Structured user prompts reduce critical errors | Hard personas (low tech knowledge) degrade agent performance significantly |
| Low-cost evaluation ($0.145/task, $40 full run) | Limited to API-based LLMs; no open-source model results reported |

## 4. Design Rationale

**Why dual-control?** In real-world technical support, users actively participate — they toggle settings, reboot devices, reseat SIM cards. Single-control benchmarks (where user is passive) systematically overestimate agent capability by ~18-25% pass^1, masking coordination failures.

**Why Dec-POMDP?** The formalism captures the partial observability (each player sees only their own DB + messages), decentralized control (separate action spaces), and sequential turn-taking that characterize real customer support interactions.

**Why environment-constrained user simulation?** Prior τ-bench user simulators relied heavily on NL prompting, yielding 40-47% error rates. By coupling user behavior to observable state and structured tools, the simulator becomes more predictable. This is a "constrain instead of prompt" philosophy — reducing degrees of freedom increases reliability.

**Why compositional task generation?** Hand-crafting tasks is brittle, labor-intensive, and does not scale. Atomic subtasks with (init, sol, assert) triples enable automatic correctness verification and combinatorial coverage (15 groups → 2285 tasks). The number of subtasks per composite task serves as a natural difficulty proxy.

**Why three ablation modes?** Attributing failures to "reasoning" vs "coordination" requires controlled experiments. No-User isolates reasoning, Oracle Plan isolates coordination, and Default tests both together. The differential reveals that both dimensions are significant bottlenecks.

## 5. Limitations and Failure Modes

1. **No expert-novice gap modeling**: The paper explicitly acknowledges not modeling the expert agent's need to understand the naive user's mental model and adapt explanations. This is a critical real-world skill absent from the benchmark.

2. **Domain curation remains human-dependent**: Despite programmatic task generation, domain creation (schema, tools, policy, subtask design) still relies heavily on human experts. Industry adoption requires further automation.

3. **User simulator still imperfect**: Telecom user simulator shows 16% error rate (6% critical). While improved, this means ~1 in 6 conversations are compromised by simulation errors.

4. **Single dual-control domain**: Only telecom was designed as dual-control. Retail and airline remain single-control. Generalizability claims are limited.

5. **API-model only**: Evaluations use only gpt-4.1, gpt-4.1-mini, o4-mini, and claude-3.7-sonnet. No open-source models (Llama, Mistral, etc.) were tested.

6. **US-centric telecom domain**: The domain models US carrier policies, pricing, and phone behaviors. International generalizability unknown.

7. **Temperature=0 may mask variance**: Fixed temperature=0 for deterministic outputs could hide brittleness that emerges at higher temperatures.

8. **Common user simulator failure modes**: (a) Conversation-structure rule violations (11/20 in retail, 19/47 in airline), (b) Missing constraints, (c) Ungrounded references, (d) Premature termination (###STOP### too early).

9. **Performance collapses for long-horizon tasks**: pass^1 near zero for >7 actions in Default mode; even No-User mode shows sharp decline after 8+ actions.

## 6. Transfer to Lyra

### The ONE Transferable Idea

**Dual-control ablation architecture for agent failure diagnosis.** The paper's core methodology — evaluating an agent across three modes (Default dual-control, No-User autonomous, Oracle Plan) to *decompose* failures into reasoning errors vs. communication/coordination errors — is directly transferable to Lyra's evaluation framework. Lyra agents operate in collaborative multi-turn environments (code generation, research assistance, debugging). Implementing a parallel "No-User" mode (where Lyra controls all tools directly) and "Oracle Plan" mode (where Lyra receives the ground-truth action sequence) would enable systematic attribution of failures to specific subsystems (reasoning, planning, tool use, or user interaction). The compositional task generator approach — defining tasks as (init, sol, assert) triples with automatic correctness verification — also maps well to Lyra's need for scalable, reliable benchmark construction.

### Workstream Route

**§4.5 — Evaluation & Verification.** This workstream covers benchmark design, agent reliability measurement, and quality assurance. The dual-control paradigm with ablation-driven failure attribution is a direct fit for building Lyra's internal evaluation suite.
