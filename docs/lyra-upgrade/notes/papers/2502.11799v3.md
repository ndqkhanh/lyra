## 1. Mechanism (step-by-step)

Table-Critic is a **four-agent collaborative framework** that iteratively critiques and refines multi-step reasoning chains for table QA tasks. It wraps around any base reasoning method (default: Chain-of-Table) and operates as follows:

### 1.1 Agent Architecture

Four specialized agents, each prompted with in-context instructions (no fine-tuning required):

| Agent | Role | Inputs | Outputs |
|-------|------|--------|---------|
| **Judge (A_j)** | Identifies errors, routes through template tree | Table T, question q, reasoning chain τ, template tree 𝒯 | Error analysis E, status P ∈ {Correct, Incorrect}, routing path R |
| **Critic (A_c)** | Generates detailed critique of first error | T, q, τ, sampled templates T_s | Critique C, first-error-step index I |
| **Refiner (A_r)** | Corrects the chain from first error onward | T, q, partial chain τ_p (steps 1..I), critique C | New complete reasoning chain τ' |
| **Curator (A_cu)** | Distills critique patterns into template tree (activated only after convergence) | Template tree 𝒯, refinement history H | Updated tree 𝒯' |

### 1.2 Iterative Refinement Loop (Algorithm 1)

```
1. H ← ∅                              // Refinement history
2. P, E, R ← Judge(T, q, τ, 𝒯)       // Judge evaluates initial chain
3. while P = Incorrect and iter ≤ K:   // K=5 default
4.     T_s ← Sample_Templates(R, 𝒯)    // Route through tree for relevant templates
5.     C, I ← Critic(T, q, τ, T_s)     // Critique focusing on first error at step I
6.     τ_p ← τ[:I]                     // Retain only correct prefix
7.     τ' ← Refiner(T, q, τ_p, C)      // Refine from error point onward (prevents bias from wrong chain)
8.     H ← H ∪ {T, q, τ, τ', C}       // Log refinement history
9.     P, E, R ← Judge(T, q, τ', 𝒯)   // Re-evaluate
10. end while
11. 𝒯' ← Curator(𝒯, H)                // Update template tree post-convergence
12. return τ'
```

Key design decisions:
- **Critic targets only the first error step I**, not all errors at once, to prevent cascading new errors.
- **Refiner receives only the partial chain up to step I** (τ_p), forcing it to reconstruct the rest fresh without bias from the prior erroneous chain.
- **Curator runs only after full convergence** (P = Correct), ensuring only verified refinements seed new templates.

### 1.3 Self-Evolving Template Tree

The template tree 𝒯 is a hierarchical structure where:
- **Internal nodes** = broader error categories (e.g., Sub-table Error)
- **Leaf nodes** = specific error types (e.g., Row Error, Column Error, Calculation Error) with template repositories

Three evolution operations managed by the Curator (Algorithm 2):

1. **Template Enhancement (AddTemplate)**: When a new effective critique pattern matches an existing leaf node, it is appended to that node's repository. No structure change.

2. **Vertical Expansion**: When existing templates need finer categorization. An existing leaf node becomes an internal node; its templates are partitioned into two child leaf nodes (e.g., Row Error splits into Row Misidentification Error and Row Omission Error).

3. **Horizontal Expansion**: When a completely new error type is discovered (e.g., Final Query Error). A new sibling branch is added at the same tree level.

The tree starts from **only 2 initial templates** (cold-start with generic Sub-table Error and Final Query Error patterns) and evolves autonomously through experience.

### 1.4 Template-Guided Routing

When the Judge identifies an error, it produces a routing path R (e.g., `ROOT → Sub-table Error → Row Error`). If the error type has no corresponding node yet (cold-start), templates are randomly sampled from existing nodes to bootstrap critique generation.

## 3. Trade-offs

| Win | Loss |
|-----|------|
| +6.3% absolute accuracy on WikiTQ (73.7% vs 67.4% best baseline) | 1.87-2.19× computational cost vs single-pass Chain-of-Table |
| +8.9% net performance gain (vs +0.7% for Critic-CoT) | Requires 3 LLM backends running simultaneously (Qwen, LLaMA, GPT) for full reproduction |
| Only -0.7% solution degradation (vs -4.9% for Critic-CoT) | Multi-turn loop with up to K=5 iterations increases latency |
| Self-evolving template tree adds +1.1-1.8% with no extra inference cost at test time | Cold-start: only 2 initial templates; tree quality depends on training distribution coverage |
| Outperforms 15× majority voting at 2× the cost of single-pass | Adds complexity: 4 agents with distinct prompt templates, template tree routing logic |
| Works across 3 different model families (Qwen, LLaMA, GPT) without model-specific tuning | Only evaluated on two English table QA benchmarks; generalization to other reasoning domains unproven |
| Template tree is reusable across sessions (amortized cost) | Curator only activates after convergence; no learning from failed refinement attempts |

## 4. Design Rationale

Why multi-agent over single-agent self-reflection? The authors cite two empirical insights:

1. **LLMs' self-reflection is unreliable** (Zheng et al., 2024; Chen et al., 2025b): single-model reflection tends to either rationalize previous errors or over-criticize correct steps, especially in table reasoning where models confuse column semantics and row selection. Critic-CoT's -4.9% degradation rate on WikiTQ empirically proves this.

2. **Error types are diverse and unpredictable**: LLMs cannot enumerate all possible table reasoning errors from their pretraining knowledge alone. The self-evolving template tree externalizes error pattern memory, allowing the system to accumulate critique knowledge across examples.

Why multi-turn with first-error-only correction? The authors observed that LLMs can reliably fix the first error but tend to introduce new errors in later steps when rewriting the entire chain. By forcing the Refiner to work from the partial correct prefix (τ_p = τ[:I]), the framework prevents the model from being biased by the prior erroneous chain.

Why template tree instead of a flat prompt bank? The hierarchical structure enables efficient routing (Judge produces a path → templates sampled from the matching node), and the tree grows organically via vertical/horizontal expansion to maintain a balanced taxonomy without manual curation.

## 5. Limitations and Failure Modes

1. **Domain Scope**: Only evaluated on textual table reasoning (WikiTQ, TabFact). No evidence for multimodal tables (tables + images), code generation, mathematical reasoning, or other domains. The authors acknowledge this as future work.

2. **Base Method Dependency**: All experiments build on Chain-of-Table. While the framework claims generality, there is no ablation showing it works with other base reasoners (e.g., Binder, Dater).

3. **Cold-Start Template Tree**: Initialized with only 2 generic templates. Performance on the first N examples may be weaker until the tree accumulates sufficient critique patterns. The paper does not analyze performance as a function of tree size or examples processed.

4. **No Learning from Failures**: The Curator only updates the tree after successful convergence (P = Correct). Failed refinement attempts (where K iterations are exhausted without convergence) contribute no learning. This discards potentially informative negative examples.

5. **Iteration Cap**: K=5 maximum iterations. Some complex WikiTQ examples require 6-10 iterations (Figure 2 density plots). These would be abandoned as unresolved, with no mechanism to escalate.

6. **Computational Overhead**: 1.87-2.19× cost vs. single-pass Chain-of-Table. While justified by accuracy gains, this may be prohibitive for latency-sensitive or high-throughput applications.

7. **Only Three Models Tested**: Qwen2.5-72B, LLaMA3.3-70B, GPT-4o-mini. No results for smaller models (7B, 13B), open-weight frontier models (DeepSeek, Mistral), or proprietary frontier models (GPT-4, Claude 3.5).

8. **In-Context Learning Only**: No fine-tuning of agents. The paper explicitly states that fine-tuning vs. ICL is not explored. Fine-tuned specialized agents could potentially improve critique quality and reduce iterations.

## 6. Transfer to Lyra

### The One Transferable Idea

**Self-Evolving Error Taxonomy + Multi-Agent Critique Loop for Multi-Step Verification**

Lyra's multi-step agent execution path (planning → tool calls → synthesis) suffers from error propagation analogous to table reasoning chains. A wrong tool call, hallucinated parameter, or incorrect intermediate output corrupts downstream steps.

The transfer: implement a **VerificationCritic subsystem** with three specialized roles:
1. **Verifier (≡ Judge)**: inspects agent action traces, routes to error type in a taxonomy
2. **Corrector (≡ Critic + Refiner)**: generates targeted correction for the first erroneous action
3. **Taxonomist (≡ Curator)**: maintains a self-evolving taxonomy of Lyra-specific failure modes (e.g., "wrong-tool-selection", "hallucinated-parameter", "premature-termination", "missing-required-argument")

The self-evolving taxonomy accumulates failure patterns from verified corrections, enabling progressively better error detection without manual prompt engineering. The "fix only the first error, then re-verify" loop prevents correction cascades. The taxonomy also serves as a **training data generator** for future fine-tuning.

### Workstream Route
**§4.5 - Verification / Quality Assurance** (primary) or **§4.7 - Safety / Guardrails** (secondary, as the template tree doubles as a guardrail pattern bank)

### Impact / Effort / Tier

| Dimension | Score | Rationale |
|-----------|-------|-----------|
| **Impact** | 4 | Directly addresses Lyra's core reliability gap (error propagation). The template tree provides a systematized, growing defense against known failure modes. |
| **Effort** | 4 | Requires building: (1) multi-turn verification loop in Lyra's execution pipeline, (2) a failure taxonomy data structure, (3) three specialized agent prompts for Verifier/Corrector/Taxonomist, (4) integration with Lyra's existing tool-call observation format. |
| **Tier** | **breakthrough** | Novel application of multi-agent critique to general agent verification. No existing Lyra subsystem provides structured failure-mode learning. The self-evolving taxonomy is a durable architecture investment. |
