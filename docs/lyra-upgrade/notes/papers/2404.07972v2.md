## 1. Mechanism (step-by-step)

### 1.1 Task Formalization as POMDP

OSWORLD models an autonomous digital agent task as a Partially Observable Markov Decision Process (POMDP) with state space S, observation space O (screenshot + a11y tree), action space A (pyautogui keyboard/mouse primitives), transition function T: S × A → S, and reward function R: S × A → [0,1].

### 1.2 Environment Infrastructure (3-layer architecture)

```
Layer 1 — Coordinator: Accepts a JSON configuration file at task initialization. Reads snapshot VM image state, runs setup commands, spawns Virtual Machine(s).
Layer 2 — Virtual Machine(s): Real Ubuntu/Windows/macOS instances. Run headless via QEMU/KVM. Snapshotted for full state reproduction.
Layer 3 — Task Manager + Evaluator: Injects files/downloads per task config. Post agent completion, runs getter functions (retrieve modified files, a11y tree, cookies, etc.) → evaluator functions (compare expected vs actual with fuzzy matching rules).
```

Each task has a configuration file specifying: (a) VM snapshot to restore, (b) files to download/setup actions (opening windows, positioning, etc.), (c) getter functions for extracting final state, (d) evaluator rules (e.g., `sheet_fuzzy` with range comparisons, `check_a11y_tree` with CSS-like selectors, `is_cookie_deleted` with domain rules). 134 unique evaluation functions exist across 369 tasks.

### 1.3 Observation Space

Three observation types can be used individually or combined:
- **Screenshot** (1920×1080 default, includes mouse cursor). Raw pixel input to VLM.
- **Accessibility Tree (a11y tree):** XML tree from AT-SPI2 (Ubuntu) / UIA (Windows). Heuristically filtered: keep elements by tag, visibility, availability, text/image content. Compact tab-separated format. Only tag, name, text, position, size preserved. 90th percentile token count: ~6,343 tokens per observation.
- **Set-of-Marks (SoM):** Filtered a11y tree elements rendered as numbered bounding boxes on screenshot. Agent selects by numeric index instead of raw coordinates, then post-processed to (x,y) via element lookup.

### 1.4 Action Space (pyautogui)

Full human-computer action space via the pyautogui Python library, including:
- `moveTo(x, y)`, `click(x, y, button=)`, `doubleClick(x, y)`, `rightClick(x, y)`
- `write('text')`, `press('enter')`, `hotkey('ctrl', 'c')`, `keyDown()`, `keyUp()`
- `scroll(amount)`, `dragTo(x, y)`
- Special actions: `WAIT`, `FAIL` (infeasible), `DONE` (termination)

Agents generate syntactically correct pyautogui Python code. Pure code generation allows for-loop structures (e.g., repetitive spreadsheet fills). Max 15 steps per task.

### 1.5 Execution-Based Evaluation

At task completion, the evaluator: (1) runs getter functions to extract final state (files, a11y tree, cookies, web data via crawlers for real-time tasks), (2) applies hand-crafted evaluation rules against expected state (fuzzy sheet matching, tree selector matching, file content comparison), (3) returns R ∈ [0,1] (partial credit supported). Infeasible tasks (30/369, 8.1%) reward correct FAIL prediction.

### 1.6 Benchmark Composition

369 tasks on Ubuntu + 43 adapted for Windows. Task sources: official tutorials, YouTube/TikTok tips, WikiHow, Reddit, Quora, StackOverflow, Coursera/Udemy. 9 annotators, ~1,800 man-hours over 3 months. Task breakdown:
- **Single-app (268, 72.6%):** OS (6.5%), Chrome (31.7%), LibreOffice Calc/Writer/Impress (29.1% total), VS Code, GIMP, VLC, Thunderbird
- **Workflow multi-app (101, 27.4%):** Cross-application tasks requiring app switching
- **Infeasible (30, 8.1%):** Deprecated features, hallucinated features
- **Integrated from other benchmarks (84, 22.8%):** NL2Bash, Mind2Web, SheetCopilot, PPTC, GAIA

### 1.7 Agent Prompt Format

Chat-mode alternating user/assistant messages. Most recent 3 observations + actions included as history. Temperature=1.0, top-p=0.9, truncate from beginning if exceeding model context limits.

## 3. Trade-offs

| Aspect | Win | Lose |
|---|---|---|
| **Real OS over simulation** | True OS state, arbitrary apps, cross-app workflows, no domain-specific environment building needed | VM overhead, ~900s max human time for complex tasks, snapshot management, harder to scale to thousands of environments |
| **PyAutoGUI code generation vs. predefined action types** | Human-complete action space (right-click, drag, hotkeys, loops), no action space ceiling | Token-inefficient, complex code generation, coordinate hallucination, syntax errors waste steps |
| **Screenshot-only vs. a11y-tree** | Closest to human perception, works without platform APIs, best for workflow tasks, better long-term generalization path | Worst current performance (5.26%), poor grounding to exact coordinates, cannot leverage structured element info |
| **A11y-tree vs. screenshot** | Most performant (12.24% GPT-4), provides element names/positions/state, enables text-only LLMs | Verbose (6k tokens/obs at 90th percentile), not available on all apps/OS, brittle to app developer compliance with a11y conventions |
| **Set-of-Marks vs. raw a11y** | Removes coordinate prediction burden, proven effective for web tasks | WORSE than Screenshot+A11y for GPT-4V and GPT-4o on OS tasks; bounding boxes insufficient for cell-level operations (spreadsheets); labeling noise from professional software with dense UIs |
| **Longer history vs. efficiency** | More trajectory history boosts SoM performance (6% → 12% from 1 to >3 steps) | No benefit for screenshot-only (VLMs weak at image history); balloons context length past model limits; requires truncation |
| **Higher resolution vs. inference cost** | Directly improves screenshot-only performance (2% → 10% from 0.2x to 1.0x) | More pixels = more tokens = higher inference cost; SoM has inverted U-curve (best at 0.4x downsampling, then declines) |
| **Cross-OS transfer** | 0.70 correlation Ubuntu→Windows; methodologies transfer | Windows performance worse than Ubuntu (2.55% vs 4.88%); OS-specific UI conventions cause failures |

## 4. Design Rationale

1. **Why real VMs over simulations:** Prior benchmarks (MiniWoB++, WebArena, GAIA) provide static demonstrations or domain-specific simulators. Real VMs allow cross-app workflows, arbitrary software, and evaluation of end-state correctness rather than action-matching. This closes the "executable environment" gap identified in Table 4 — OSWORLD is the only benchmark with controllable executable env + arbitrary app scalability + multimodal support + cross-app + intermediate state initialization.

2. **Why pyautogui as action space:** Rather than defining a finite action vocabulary (which imposes an upper bound on agent capability), OSWORLD lets agents generate arbitrary Python code. This covers edge cases like right-click, Ctrl+click selection, and for-loops for batch operations that domain-specific action spaces miss.

3. **Why execution-based over demonstration-matching evaluation:** Human demonstrations are only one path to completion. Reward function R: S×A→[0,1] evaluates the final state correctness, allowing any valid agent solution path. Example-wise evaluation scripts (134 unique functions) handle the diversity of real tasks (cookies, spreadsheets, accessibility trees, file contents, web states).

4. **Why Ubuntu + open-source software:** Ubuntu (~3.1% desktop market share) provides open-source APIs (AT-SPI2 a11y tree, file system access, process control) making evaluation feasible. Windows tasks serve as cross-OS validation evidence.

5. **Why chat-mode prompting over few-shot (observation, action) pairs:** Few-shot (obs, action) pairs got only 2.79% success. Alternating user/assistant chat with history encoding achieves dramatically better grounding.

## 5. Limitations & Failure Modes

1. **Catastrophic grounding failure (>75% of errors):** VLMs produce correct plans in code comments but predict wrong pixel coordinates. Claude-3 Opus exhibits particularly bad grounding (e.g., interprets double-click as select rather than open; treats column B as column C in Calc).

2. **VLM brittle to UI perturbations:** Window position/size changes cause 50-80% performance drops. Agents cannot maximize windows as intermediate recovery step. Advertisements and cookie pop-ups derail web navigation completely.

3. **Screenshot-only history encoding is broken:** Current VLMs cannot extract temporal context from image sequences, making memory/recovery from screenshots alone infeasible. This means pure-vision agents cannot effectively use past observations.

4. **SoM degrades on dense UIs:** Professional software (spreadsheets, GIMP, VS Code) have too many elements for numbered bounding boxes to be useful. Coordinate-level operations (cell clicking, pixel-level edits) are not capturable by bounding boxes.

5. **Domain knowledge deficit:** Agents lack knowledge of application-specific menus (e.g., GIMP brightness under Colors menu → agent randomly tries menus until step limit). No training data exists for fine-grained software operation sequences.

6. **Safety evaluation is absent:** The evaluation only checks task completion correctness. No metrics for assessing side-effects (account abuse, vulnerability exploitation, patent violations). VMs provide isolation but not detection.

7. **Ubuntu-only primary benchmark:** The 369-task primary set is Ubuntu-only. Windows has a smaller 43-task subset. macOS is mentioned but not benchmarked. Cross-OS generalization evidence is limited to 43-task transfer.

8. **Evaluation brittleness:** Despite ~400 man-hours of double-checking, the 134 hand-crafted evaluation scripts may have residual false positives/negatives. More red-teaming needed.

9. **Max step constraint (15 steps):** Hard-coded limit forces early failure on complex multi-app workflows. Real human workflows sometimes need 50+ steps.

10. **Single-model agents only:** No exploration of multi-agent architectures, reflection loops, or memory mechanisms in the primary benchmark. These are listed as future work directions.

## 6. Transfer to Lyra

### The One Idea: Execution-Based Evaluation over Real OS Environments with Arbitrary Actions

OSWORLD's core engineering insight is that **real computer task evaluation must use a real OS with execution-based reward functions, not action trajectory matching**. For Lyra, this means that any agent claiming to perform real desktop tasks must be evaluated against the actual state of the machine after task completion — checking file contents, application state, a11y tree nodes — rather than comparing predicted actions to human demonstrations.

Concretely, Lyra should adopt: (1) VM-based sandboxed execution for task validation, (2) task-specific getter→evaluator pipelines that check end-state correctness, (3) a POMDP formalization of Lyra's agent loop with explicit observation space O (screenshot + structured UI tree), action space A (keyboard/mouse + CLI codespace), and execution-based reward R.

### Routing

- **Workstream:** §4.1 (Agent Harness & Evaluation Framework) — directly feeds the evaluation architecture for Lyra's computer-use capability
- **Secondary:** §4.3 (Safety & Alignment) — VM sandboxing pattern for safe agent execution; §4.5 (Memory & Context) — insights on history encoding failure modes

### Impact/Effort/Tier

- **Impact:** 4 — Establishes the evaluation methodology Lyra needs to validate real-world agent task completion; the gap analysis (12.24% vs 72.36%) provides a calibrated difficulty measure
- **Effort:** 4 — Requires VM infrastructure (QEMU/KVM), task-specific evaluation scripts, pyautogui action space integration, and snapshot management
- **Tier:** Breakthrough — OSWORLD is the only benchmark providing real-OS, execution-based, cross-app evaluation for computer agents. Its methodology is directly portable to Lyra's agent evaluation pipeline.
