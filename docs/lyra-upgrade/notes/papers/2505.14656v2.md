## 1. Mechanism (step-by-step)

### Problem Formulation
- Given initial state `s0`, goal state `sg`, budget limit `B`, action set `A` with heterogeneous costs `c(a)`.
- Objective: find action sequence `A' = [a1,...,ak]` reaching `sg` such that `∑c(ai) ≤ B`.

### Four Tree-Search Planners Compared

**ToT-BFS (Tree-of-Thoughts BFS):**
1. For each node expansion, LLM proposes top-5 candidate actions from action pool.
2. Actions executed via PDDLGym deterministic transition function (no hallucinated states).
3. Nodes scored by confidence reward (see below).
4. BFS traversal: expand all nodes at current depth before moving deeper.
5. Optional hard budget feasibility filter: prune partial plans where accumulated cost > B.
6. Max 500 node expansions total.

**ToT-DFS:**
1. Same action proposal and scoring as BFS.
2. DFS traversal: prioritize deeper expansions; commits to local best node.
3. Same feasibility pruning and 500-node budget.

**MCTS (Monte Carlo Tree Search):**
1. **Selection:** Starting from root, traverse tree choosing nodes that maximize UCT:
   ```
   UCT(u) = Q(u) + β * sqrt(ln N(parent(u)) / (1 + N(u)))
   ```
   where `N(u)` = visit count, `Q(u)` = running estimate of node value.
2. **Expansion:** At selected leaf, LLM proposes m candidate actions; add feasible children.
3. **Simulation:** Compute each new child's reward r; greedily roll out to terminal state.
4. **Backpropagation:** Propagate value upward via running averages from terminal to root.
5. Run until 500 expansions or solution found.

**Bidirectional Search (Bi-Search):**
1. Grow two trees simultaneously: forward tree `Tf` rooted at `s0`, backward tree `Tb` rooted at `sg`.
2. Each iteration:
   - Select most promising leaf in each tree (by confidence reward).
   - Enumerate feasible actions; add successor states as children; track cumulative cost.
   - Check for overlap: if `Vf ∩ Vb ≠ ∅`, extract plan by concatenating forward prefix + backward path.
3. Alternates expansion between trees under fixed node-expansion limit L.
4. Key insight: reduces effective depth by meeting in the middle, avoiding exponential blow-up.

### Reward Design (uniform across all methods, from RAP: Hao et al., 2023)
1. **Action Evaluation:** Prompt LLM with parent state, available actions, budget, accumulated cost. Ask LLM to predict "best next action." Use `log P_LLM(chosen_action)` as confidence.
2. **Self-Evaluation:** Given chosen action a, budget B, parent cost, prompt LLM to classify a as `good` or `bad`. Use `log P_LLM("good")` as confidence.
3. **Final node reward** = logP_action + logP_good (sum of two log-probability signals).

### Budget Regimes
| Regime | Budget B | Constraint |
|--------|----------|------------|
| TIGHT | Cost(optimal plan) | Must match optimum exactly |
| LOOSE | Cost(optimal) + 2×c_max | Allows one extra high-cost action pair |
| UNLIMITED | ∞ | Any valid plan accepted |

### Failure Mode Taxonomy
1. **Budget Violation:** Plan reaches goal but cost exceeds budget (RQ1: cost-awareness).
2. **Search Exhaustion:** No valid plan found within 500-node expansion limit (RQ2: efficiency).

### Infesibility Detection Analysis
For node `sv` with accumulated cost `g(sv)` and optimal remaining cost `h(sv)`: the LLM fails to identify infeasibility when `g(sv) + h(sv) > C` (ground-truth optimal cost). Failure rate = proportion of nodes where this condition is missed.

## 3. Trade-offs

| Dimension | Win | Loss |
|-----------|-----|------|
| **Feasibility vs. Optimality** | Tree search (esp. Bi-Search) dramatically improves success rate on long horizons vs. CoT | Even successful tree-search plans are often cost-suboptimal; optimality ratios drop to 0.36 for Bi-Search at L=12 |
| **Bi-Search vs. MCTS** | Bi-Search is 2-3x more efficient and solves more long-horizon tasks | MCTS produces cost-optimal plans more often on short horizons (optimality 1.00 at L=2,4 vs 0.84 for Bi-Search) |
| **Search Compute vs. Optimality** | MCTS continues improving with more expansions | ToT-BFS/DFS, Bi-Search hit diminishing returns rapidly — most solutions found early, after which more compute yields little benefit |
| **Open-source vs. Closed-source** | Qwen3-8B enables affordable extensive tree search (many API calls) | Claude/GPT-4.1 CoT matches or exceeds tree-search optimality on some lengths without search overhead |
| **MCTS Dual Guidance** | Value backpropagation partially corrects LLM scoring errors (lowest infeasibility failure rate: 36.4% LOOSE) | Adds computational overhead from rollouts; still fails 48% of the time via budget violation |
| **Bidirectional Search** | Shrinks search space by meeting in the middle; highest efficiency (0.96) | 92% of failures are budget violations — finds plans quickly but rarely cost-optimal ones |

## 4. Design Rationale

1. **Explicit search trees over black-box prompting:** Intermediate decisions, node evaluations, and failure modes are observable, enabling controlled ablations that are impossible with implicit planning (e.g., post-trained trajectory internalization). This is why the paper can analyze *why* planners fail (Figure 3: high-score assigned to suboptimal action, forced selection among low-scoring options).

2. **Bidirectional search over unidirectional:** By replacing one deep expansion (depth d) with two shallower ones (depth d/2 each), the effective branching factor is radically reduced — avoiding the combinatorial blow-up that dominates long-horizon unidirectional search. This was chosen for efficiency, not optimality.

3. **MCTS over heuristic-only:** ToT-BFS/DFS rely solely on the LLM's static confidence score. MCTS adds value backpropagation to incorporate empirical evidence from rollouts, partially correcting for miscalibrated LLM scores. The UCT formula dynamically balances exploration and exploitation.

4. **Uniform reward across all methods:** Using the same RAP-derived reward signal isolates the effect of search structure from reward quality, making comparisons between algorithms causally interpretable.

5. **Three budget regimes:** TIGHT/LOOSE/UNLIMITED systematically test cost strictness from "must be optimal" to "anything goes," exposing where each method breaks down.

6. **PDDLGym as transition function:** Avoids hallucinated state transitions — all actions are verified against a deterministic simulator, ensuring validity is a property of the planner, not the environment.

## 5. Limitations and Failure Modes

### Explicit Limitations (from paper)
1. **Single domain:** Only BlocksWorld tested; generalizability to other cost-aware domains (travel planning, robotics, tool use) unverified.
2. **Fixed reward design:** Only the RAP-based confidence reward used — results conditioned on this specific scoring approach.
3. **Single open-source model for tree search:** Qwen3-8B only (closed-source models too expensive for many tree-search calls). Magnitudes may differ across models.
4. **No self-refinement or heuristics:** Intentionally excluded to isolate search structure effect — results may underestimate what practical systems can achieve.

### Observed Failure Modes
1. **LLM assigns high confidence to costly actions:** The model frequently scores expensive suboptimal actions (e.g., put-down, cost=20) higher than cheap optimal ones (e.g., stack, cost=1), diverting search from optimal paths (Figure 3a).
2. **Uniform low confidence forces suboptimal selection:** When all candidate actions receive similarly low scores, the planner commits to a suboptimal branch regardless (Figure 3b).
3. **Miscalibrated confidence scores:** LLM fails to recognize provably infeasible trajectories 36-89% of the time (Table 3).
4. **Search exhaustion with rigid traversal:** BFS exhausts node budget level-by-level; DFS commits early to unpromising branches.
5. **Budget violations dominate Bi-Search failures:** Despite finding plans efficiently, 92% exceed tight budgets because the confidence reward lacks explicit cost-awareness.

## 6. Transfer to Lyra

### The ONE Transferable Idea

**Cost-Informed Pruning with Cumulative Lower-Bound Checks During Multi-Step Reasoning**

Lyra's planning/agent orchestration (§4.2 — Agent Execution Engine) should implement a **budget feasibility filter** that, at each reasoning step, computes `accumulated_cost + minimum_remaining_cost` and prunes branches where this exceeds the budget. The paper demonstrates that LLMs alone cannot do this reliably (36-89% failure rate), but a simple deterministic filter dramatically improves efficiency without changing the underlying model or reward. This is orthogonal to Lyra's current architecture and requires no model retraining.

### Workstream Route
**§4.2 — Agent Execution & Multi-Step Reasoning** (tree-search planning with explicit budget constraints during tool-call sequences)

### Impact / Effort / Tier
- **Impact:** 3 (improves efficiency of multi-step Lyra agent plans, prevents wasted API calls on infeasible branches)
- **Effort:** 2 (rules-based pruning filter; requires defining cost model for Lyra actions/tools and computing admissible heuristics per domain)
- **Tier:** parity (brings Lyra to state-of-the-art cost-aware planning; not a breakthrough but addresses a known gap in most LLM agent frameworks)
