## 1. Mechanism (step-by-step)

EVOLVEMEM is a closed-loop memory system where the *retrieval infrastructure itself* is a first-class optimization target, not frozen hyperparameters. The system conducts autonomous research on its own architecture through four phases per evolution round.

### Memory Representation
Each memory unit is a 4-tuple m = (c, μ, e, η):
- c: natural-language content
- μ: type from a 6-category taxonomy (episodic, semantic, preference, project-state, working-summary, procedural)
- e: dense embedding (768-dim BAAI/bge-base-en-v1.5)
- η: metadata (importance ι, confidence, entity-reinforcement ρ, extracted entities, persons, locations, topics, timestamp)

### Extraction Pipeline (§3.1)
Sliding window (W=40 turns) over conversation sessions. Three failure guards:
1. **Retry**: exponential backoff on LLM call failure
2. **Chunk-split**: when window exceeds context limit, split into C=15-turn sub-windows, merge outputs
3. **Coverage verification**: compare extracted keywords against source; trigger targeted re-extraction for missing content

### Consolidation (runs per session)
1. **Deduplication**: merge pairs with Jaccard(token(c_i), token(c_j)) ≥ τ_J = 0.80; keep higher-importance unit
2. **Importance decay**: linear schedule, α_d = 0.05/day, floor ι_min = 0.15
3. **Entity reinforcement**: increment ρ_i by δ_ρ = 0.05 per co-occurrence with a new query, capped at ρ_max = 0.30

### Retrieval as Evolvable Action Space (§3.2)
Three independent retrieval views:
- **Lexical**: BM25(k1=1.5, b=0.75)
- **Semantic**: cosine similarity over embeddings
- **Structured-metadata**: exact-match filtering on persons, locations, entities

Fusion mode ∈ {SUM, WEIGHTED-SUM, RRF}. Final ranking score:
```
s(q, m_i; θ) = s_fuse(q, m_i; θ) + λ_ι · ι_i + λ_r · rec(m_i) + ρ_i
```
where rec(m_i) is recency factor (non-increasing function of age, parameterized by half-life in days).

Two evolvable augmentation mechanisms:
- **Adversarial entity-swap**: strip detected person names from query, re-search by topic, union results
- **Query decomposition**: LLM splits multi-hop questions into K ≤ N_sub single-hop sub-queries, merge via RRF

Full evolvable configuration θ:
```
θ = [k_sem, k_kw, k_str, B_ctx, mode, {w_v}, α, {θ_c}_{c∈C}]
```
where k_v are per-view top-k, B_ctx is max context memories, mode is fusion strategy, w_v are per-view weights, α is answer style, θ_c are per-category overrides. Every dimension is clamped to safe range.

Answer generation produces ŷ_0 via ψ_ans(q, R(q;θ), α). Optional second-pass verification:
```
ŷ = ψ_ver(q, R(q;θ), ŷ_0)  if conf(ŷ_0) < τ_ver or ŷ_0 ∈ U (Unknown class)
ŷ = ŷ_0                   otherwise
```

### Self-Evolution Engine (§3.3, Algorithm 1)
Optimization objective: argmax_θ (1/|Q|) Σ score(ŷ(q;θ,K), y*), where score is token-level F1.

**Per-round loop** (Evaluate → Diagnose → Propose → Guard):
1. **Evaluate**: retrieve & answer all QA pairs under θ_r, write per-question raw log L_r to disk
2. **Diagnose**: LLM reads L_r with structured rubric (failure patterns: wrong entity, insufficient context, temporal confusion, etc.), outputs structured proposal Δθ_r
3. **Guard/meta-analyzer** applies three-branch update rule:
   - **Revert**: if f_{r-1} - f_r > τ_rev → θ_{r+1} = θ* (best-so-far)
   - **Explore**: if |f_r - f_{r-1}| < ε for 2 rounds → θ_{r+1} = θ_r ⊕ η_exp (random perturbation)
   - **Apply**: otherwise → θ_{r+1} = clamp_Θ(θ_r ⊕ Δθ_r)
4. **Coverage gap handling**: if diagnosis detects missing memory coverage → targeted re-extraction
5. **Convergence**: terminate when f_r - f_{r-1} < ε = 0.005 or r = R_max = 7

Key property: the diagnosis LLM can propose **entirely new configuration dimensions** not present in the original action space (self-expanding evolution). Three such dimensions were discovered: adversarial entity-swap, query decomposition, and answer verification.

### Evolution Trajectory (GPT-4o, LoCoMo, single-backbone)
F1 progression: R0=30.5% → R1=35.8% → R2=34.8%(reverted) → R3=37.2% → R4=38.5% → R5=38.1% → R6=45.4% → R7=**54.3%** (7 rounds, fully autonomous)

### Cross-Benchmark Transfer
- C_L (evolved on LoCoMo only): 54.3% on LoCoMo, **54.3%** zero-shot on MemBench
- C_LM (LoCoMo→MemBench continued): 59.3% on LoCoMo, **79.2%** on MemBench (+16.6% over scratch-evolved C_M at 67.9%)
- Positive transfer: C_LM improves *both* benchmarks (Pareto improvement)

### Ablation (F1 drops on LoCoMo)
- Extraction quality control: −23.22 (largest, nearly halves extraction yield)
- Semantic search: −10.32
- LLM-powered diagnosis (vs random search): −9.63
- BM25 keyword search: −6.87
- Entity-swap: −3.10
- Query decomposition: −2.84
- Structured metadata: −2.33
- Self-evolution entirely: −2.03
- Answer verification: −1.83

### Efficiency
- Full 7-round evolution: 25-35 min wall clock per LoCoMo sample (200 QA, ~900 memories)
- Per-query retrieval latency: ~15 ms (semantic top-20 + BM25 top-8 + structured top-5)
- Index construction: ~5 s for ~900 memories
- Storage: <5 MB per 1,000 memory units

## 3. Trade-offs

| Win | Cost / Loss |
|-----|-------------|
| +78.0% relative F1 over minimal baseline (30.5→54.3) without any manual tuning | Requires 7 full evolution rounds (25-35 min per sample) — not real-time |
| Discovers entirely new configuration dimensions (entity-swap, query decomposition, answer verification) not in original action space | Each evolution round runs full QA evaluation, incurring LLM API costs (200+ calls/round) |
| Evolved configurations transfer positively across benchmarks (no catastrophic forgetting) | Robustness dimension weakest (50.0% on MemBench Post-Processing), indicating coverage limitations retrieval can't fix |
| Self-expanding: diagnosis LLM can propose parameters beyond initial action space | Revert guard and explore perturbation are heuristic thresholds (τ_rev, ε) — not learned, manually set |
| Multi-view retrieval (BM25 + semantic + structured) is complementary, each contributing independently | Diagnosis LLM quality depends on backbone model; random search loses −9.63 F1, showing non-trivial diagnosis dependence |
| Database-only (SQLite/FTS5), no GPU required for memory system itself | Extraction quality is foundational — removing extraction guards costs −23.22 F1, starving downstream components |
| Positive cross-backbone transfer (GPT-4o→GPT-5.1) — not backbone-specific | Answer verification adds 2-3 s LLM latency per question |

## 4. Design Rationale

The core insight: **memory systems have co-evolving content AND retrieval infrastructure, but all prior work treats retrieval as frozen**. As memory stores grow from dozens to hundreds of heterogeneous records, a static retrieval policy becomes increasingly suboptimal. Different question categories require fundamentally different strategies (keyword matching for factual lookup, recency-weighting for temporal questions, query decomposition for multi-hop inference).

Instead of manual hyperparameter tuning or standard search (grid/Bayesian), the authors use **LLM-powered diagnosis** because: (1) the action space mixes continuous and discrete parameters with per-category overrides, making grid search combinatorially explosive; (2) the objective requires a full evaluation pass per configuration, making sample-efficient search critical; (3) the diagnosis LLM can interpret failure logs semantically (e.g., "camping trip vs. Perseid meteor shower" confusion) and propose targeted adjustments that random search cannot. This forms the **AutoResearch** paradigm — the system autonomously conducts observe-hypothesize-experiment-validate cycles on its own architecture.

The three-branch update rule (revert/explore/apply) provides stability: automatic rollback prevents bad proposals from persisting, while noise injection escapes local optima without human intervention.

## 5. Limitations & Failure Modes

1. **Coverage-dependent**: When relevant memories are absent from the store (e.g., MemBench Post-Processing category), retrieval-level adjustments cannot compensate. The system can trigger re-extraction but cannot invent missing evidence.
2. **Heuristic convergence thresholds**: ε = 0.005 and τ_rev are fixed, not learned. Different benchmarks may need different sensitivity.
3. **Single-backbone diagnosis dependency**: The diagnosis LLM quality directly affects evolution direction. Random search over the same action space costs −9.63 F1, confirming that poor diagnosis yields poor evolution.
4. **Offline evolution only**: Evolution runs on a static QA set, not online. The system does not adapt to distribution shift during deployment without re-running the full loop.
5. **No dynamic scenario handling**: Authors explicitly note this as future work — the system assumes a fixed corpus of sessions and QA pairs.
6. **Adversarial category ceiling**: Adversarial F1 is already high (0.944 for MemVerse baseline on GPT-4o), leaving limited headroom for improvement.
7. **Extraction fragility**: The −23.22 F1 drop from removing extraction guards shows that downstream evolution is useless without high-quality memory extraction — the foundation is brittle.

## 6. Transfer to Lyra

**The One Idea**: Closed-loop, LLM-powered diagnosis-driven self-evolution of retrieval/action infrastructure — where an LLM reads per-query failure logs, hypothesizes root causes, and proposes targeted configuration adjustments validated under a guarded meta-analyzer with automatic revert-on-regression. This is directly applicable to Lyra's memory and retrieval subsystems, where retrieval strategies (fusion weights, context budgets, query augmentation toggles) could self-adapt based on actual failure patterns rather than remaining frozen at deployment.

**Workstream Route**: §4.2 (Memory & Retrieval Subsystem) — the primary Lyra workstream focused on long-term memory architecture, retrieval strategies, and context management.

**Impact**: 4/5 — The AutoResearch paradigm of self-evolving infrastructure could substantially improve Lyra's retrieval accuracy across diverse query types without manual tuning burden.

**Effort**: 4/5 — Requires: (a) exposing Lyra's retrieval configuration as a structured, evolvable action space; (b) implementing per-question failure logging at granularity sufficient for LLM diagnosis; (c) building the diagnosis module with failure-pattern rubrics; (d) adding the guarded meta-analyzer with revert/explore/apply branches. Moderate-to-high engineering effort.

**Tier**: **breakthrough** — This represents a paradigm shift from frozen retrieval infrastructure to self-evolving infrastructure. The cross-benchmark positive transfer results suggest the discovered principles are general, not benchmark-specific, making this a high-leverage investment.
