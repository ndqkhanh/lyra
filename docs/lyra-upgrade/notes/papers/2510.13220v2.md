## 1. Mechanism (step-by-step)

EvoTest is a **gradient-free, evolutionary framework for test-time learning (TTL)** in AI agents. It improves an agent across consecutive episodes of the same complex task without any fine-tuning or weight updates.

### 1.1 The J-TTL Benchmark

The paper introduces J-TTL (Jericho Test-Time Learning), where an agent plays K=50 episodes of the same Jericho text-adventure game, with T=110 steps per episode. The game resets to identical initial state after each episode. Metrics: per-episode final score `R(e)` and AUC (Area Under Curve), defined as:

```
AUC = (Σ R(e)) / (K · Rmax)
```

where `Rmax` is the maximum achievable score in one episode.

### 1.2 Agentic Configuration

The learnable components form a tuple `χ = (p, M, h, u)`:

- **Policy Prompt (p):** System prompt providing strategic guidance, heuristics, behavioral guardrails
- **Deployment-time Memory (M):** Structured database with *success memory* (state-hash -> action -> score_delta) and *failure memory* (state-action pairs that produced no progress or loops)
- **Hyperparameters (h):** LLM temperature, exploration strength, stopping criteria
- **Tool-Use Routines (u):** Memory interaction logic (when/how to query memory) and state abstraction logic (an evolvable Python function `extract_state` that parses raw game history into concise milestone strings)

### 1.3 Two-Agent Learning Loop

**Actor Agent:** Plays one full episode using a fixed configuration χ^(e), generating trajectory τ^(e).

**Evolver Agent:** After each episode, analyzes the full transcript τ^(e) and parent configuration χ^(e) to perform *whole-system evolution* via four operators:

1. **Prompt Mutation:** Rewrites `p^(e)` -> `p̃`, incorporating proven strategies, adding rules to prevent observed failures, including `Walkthrough`, `Actions to Avoid`, and `Exploration Plan` sections
2. **Memory Update:** Programmatically parses τ^(e) to log state-action pairs before score increases into success memory; identifies sequences with no progress into failure memory
3. **Hyperparameter Tuning:** Adjusts temperature (e.g., increase if agent was stuck in loops, decrease if chaotic); outputs JSON like `{"temperature": 0.75}`
4. **Tool-Use Refinement:** Modifies memory-access rules (e.g., from "hint" to "mandatory check before every action")

The Evolver generates m child configurations `C^(e+1) = {χ̃_1, ..., χ̃_m}`.

### 1.4 UCB Selection

The next configuration is selected via Upper Confidence Bound:

```
χ^(e+1) = argmax [ μ̂(χ̃) + β · sqrt(log N / (1 + n(χ̃))) ]
```

- `μ̂(χ̃)`: average score of configuration χ̃ (exploitation)
- `n(χ̃)`: number of times χ̃ has been tried
- `N`: total episodes completed
- Exploration bonus favors untested configurations; prevents over-commitment to lucky-but-fragile mutations

The parent χ^(e) always remains in the pool, providing a safety net against catastrophic drops.

### 1.5 Update Rule

Formally: `θ^(e+1) = U(θ^(e), τ^(e))` where U maps configurations + trajectory history to new configurations. All learning happens at the symbolic/configuration level, not at the weight level.

## 3. Trade-offs

| Win | Lose |
|---|---|
| +38% AUC over best prompt-evolution baseline (EvoPrompt) | ~20-30s update latency per episode (API call) |
| +57% over online RL (GRPO) with zero GPU hardware needed | Bounded by frozen backbone LLM's pre-trained capabilities — cannot teach fundamentally new skills |
| Only method to win any game (2/6 won); all baselines win 0 | Strategic overfitting to single task — learned strategies (e.g., "unlock door with key") are brittle and task-specific |
| Update cost is 1 LLM API call vs 5-10 min on 4× H100 GPUs for RL | Strong dependency on powerful Evolver model — performance degrades with weaker optimizer (AUC drops from 0.94 o3 -> 0.68 qwen3-8b) |
| UCB selection prevents catastrophic performance drops (w/o UCB: AUC drops 0.26 on Detective) | Simple (1+m) evolutionary strategy may converge to local optima in complex search spaces |
| Learning from rich narrative transcripts vs sparse scalar rewards — better credit assignment | No cross-task generalization; rewrites prompt for single game instance only |
| Scales with model capability — gpt-5.1 yields avg AUC 0.57 | Requires well-structured Evolver master prompt (structured evolution 0.94 vs simple mutation 0.65 on Detective) |

## 4. Design Rationale

**Why gradient-free?** Test-time learning has extreme data scarcity — a single episode provides at most one trajectory. Gradient-based RL requires thousands of samples for stable credit assignment; backpropagation through a large model on one episode's data is both slow (5-10 min on 4× H100) and noisy. A single LLM forward pass is 60-120× faster and needs no GPU.

**Why whole-system evolution over prompt-only?** Single-channel adaptation (e.g., Reflexion, TextGrad) hits a ceiling because an agent can have a perfect prompt but still fail due to poor exploration (low temperature) or inefficient memory-access logic. Concurrently tuning prompt + memory + hyperparameters + tool-use resolves bottlenecks that no single axis can address. Ablation shows removing any component hurts (prompt removal: -0.42 AUC).

**Why narrative credit assignment over scalar rewards?** Jericho games have sparse rewards — many critical actions yield 0 points (e.g., "UNLOCK DOOR WITH KEY"). A scalar reward of 0 carries no signal to distinguish a necessary intermediate step from a wasted action. Reading the full transcript allows semantic identification of causal chains: "the agent got stuck in a loop here" -> add guardrail, or "ASK TECHNICIAN ABOUT GATES enabled later progress" -> encode latent-value action.

**Why UCB over greedy selection?** Greedy selection over-commits to high-risk configurations that got lucky once. UCB keeps the reliable parent in the pool as a safety net, ensuring the system can "fall back" and maintain stable learning. Ablation: w/o UCB shows jagged learning curves with catastrophic drops.

## 5. Limitations & Failure Modes

1. **Bounded by Frozen Backbone:** EvoTest cannot teach the LLM genuinely new capabilities outside its pre-trained knowledge. If a game requires spatial reasoning the LLM has never mastered, no amount of prompt evolution can create that ability from scratch. Fine-tuning remains the only path for teaching truly novel skills.

2. **Strategic Overfitting:** The specific strategies and "verbal guardrails" learned (e.g., exact action sequences for Detective) are a form of strategic overfitting. They are brittle and do not generalize to even minor task variations. This is by design for TTL but limits reusability.

3. **Evolver Dependency:** Performance correlates strongly with Evolver model quality (o3: 0.94 AUC on Detective, qwen3-8b: 0.68 AUC). The framework requires access to a capable (and potentially expensive) "optimizer" model.

4. **Simple Evolutionary Strategy:** The (1+m) strategy with UCB is a relatively simple search heuristic. It may converge to local optima in more complex games. More sophisticated population-based or quality-diversity methods are needed for harder tasks.

5. **Domain Restriction:** Only evaluated on Jericho text-adventure games with maximum 110 steps/episode. Effectiveness on real-world agent tasks (web navigation, code generation, multi-turn dialogue) is unverified.

6. **No Parametric Generalization:** Unlike RL which can learn robust policies across task distributions, EvoTest's symbolic edits are inherently instance-specific. The authors note this could be addressed by collecting evolved strategies into a library of general-purpose skills.

## 6. Transfer to Lyra

### The One Idea
**Actor-Evolver two-agent architecture with whole-system configuration evolution driven by transcript-level semantic credit assignment.** Instead of fine-tuning Lyra's model weights, deploy a separate "Evolver" agent that reads the full transcript of each user interaction session and rewrites Lyra's complete agentic configuration (system prompt, memory structures, hyperparameters, tool-use routines) before the next session. The Evolver performs narrative credit assignment — it identifies what worked, what failed, and why — then proposes targeted, structural edits to the entire agent system, not just the prompt.

### Workstream Route
**§4.2 — Self-Improvement / Agent Learning Subsystem.** This feeds directly into Lyra's self-improvement loop: after each conversation/session, analyze the transcript for improvement opportunities, then evolve the configuration for the next interaction. This is distinct from fine-tuning and complements Lyra's existing pipeline.

### Impact/Effort/Tier
- **Impact:** 4 — Significant uplift potential for Lyra's long-horizon reliability; the mechanism is architecture-agnostic and could apply to any Lyra task domain
- **Effort:** 4 — Requires implementing the Evolver agent with a structured master prompt, memory database (success/failure tables), UCB selection, and configuration schema; moderate engineering but no training infrastructure
- **Tier:** **breakthrough** — A fundamentally new learning paradigm for Lyra (gradient-free, transcript-driven, whole-system evolution) that is orthogonal to and complementary with existing fine-tuning approaches
