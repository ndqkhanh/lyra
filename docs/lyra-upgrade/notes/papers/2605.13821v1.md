## 1. Mechanism (step-by-step)

AEVO formulates agentic evolution as an **interactive environment** in which a meta-agent edits the evolution mechanism rather than generating the next candidate directly. The environment state is the accumulated evolution context; the transition rule is the current evolution mechanism; and the meta-agent action edits that mechanism.

### 1.1 Core Formulation

Let `x ∈ X` be the artifact being optimized (program, prompt, workflow, agent component). Round `r` produces round context `c_r` (candidates, evaluation results, traces, failures, costs). The accumulated context after `r` rounds is:

```
C_r = (c_1, c_2, ..., c_r)
```

The optimization mechanism `Π` advances evolution:

```
c_r = Π(C_{r-1}),  C_r = C_{r-1} ⊕ c_r
```

At round `r`, the environment state is `s_r = (r, C_r)`. Without intervention, the next round is:

```
c_{r+1} = Π_r(C_r),  s_{r+1} = (r+1, C_r ⊕ c_{r+1})
```

A meta-agent `M` observes a summary `o_r = Φ(s_r)` and produces an edit action `a_r = M(o_r)`. Crucially, the action does NOT become the next candidate. Instead, it modifies the transition rule:

```
Π_{r+1} = Edit(Π_r, a_r)
```

The edited mechanism then continues evolution: `c_{r+1} = Π_{r+1}(C_r)`.

### 1.2 Two Instantiation Modes

**Procedure-based evolution:** `Π_r` is an explicit evolution procedure (selection, optimization, evaluation, update functions). The meta-action `a_r` edits procedure code directly — e.g., revising the selection strategy from `BestByScoreSelection` to `CrossCandidateSelection` with reference-based evidence, changing the optimization operator from single-parent rewrite to Pass@K sampling, adding local filtering/retry logic, adjusting budget allocation, or altering how feedback is summarized. The initial procedure is intentionally minimal: best-valid-candidate selection + single LLM rewrite.

**Agent-based evolution:** `Π_r` is the operating context of a general-purpose evolution agent (goals, skills, tools, memory files, shared notes, validators, execution setup). The meta-action `a_r` edits these context files rather than code. For example, it rewrites the session goal to carry falsifiable hypotheses, updates the persistent family map with accumulated discoveries and "do not repeat" warnings, or modifies the task skill to enforce evaluation discipline. The inner agent remains responsible for generating candidates.

### 1.3 Harness Design (Critical Architecture)

AEVO introduces a **harness** with three protected boundaries:

1. **Protected Evaluator:** Evaluation and candidate records are governed externally and cannot be modified by the meta-agent or inner agent. This prevents reward hacking.
2. **Structured Evidence Recording:** Each evolution segment records cost, failures, artifacts, and traces in a structured format that the meta-agent can later inspect.
3. **Meta-Agent Skill Specification:** The meta-agent follows a compact operational skill with hard rules — it can edit `sessions/_next_goal.md`, `skill/evolve_skill.md`, `shared/validators/`, `shared/tools/`, `shared/notes/` but is FORBIDDEN from editing `candidates/` or calling the evaluator directly.

### 1.4 Meta-Editing Loop (Pseudocode)

```
READ evolution history → ATTRIBUTE bottleneck → CHOOSE ONE causal action →
    EDIT mechanism files → SET run plan (iterations, budget, stop conditions) →
    RUN evolution segment under new Π_{r+1} → ACCUMULATE new evidence → REPEAT
```

The meta-agent chooses exactly ONE action per inter-session boundary (goal change, harness change, or directive change), enforcing coarse-grained, attributable interventions. The run plan specifies how many iterations the next segment runs and under what stopping conditions.

### 1.5 Evolution Segment Execution

An evolution segment runs `Π_r` under the run plan produced by the meta-agent. Each candidate submitted goes through the protected evaluator. Results are recorded in the workspace as structured evidence. The segment can span multiple rounds of a procedure (procedure-based) or a full inner-agent session producing multiple attempts (agent-based).

### 1.6 Key Data Structures

- **Persistent Family Map:** A durable memory file tracking which structural families of solutions have been explored, their best scores, which hypotheses were falsified, and explicit "do not repeat" lists.
- **Session Goal File:** Carries the current best status, remaining evaluation budget, specific falsifiable hypotheses in test order, required behavior, and required output format.
- **Replay Utility:** A Python script that replays evaluation rows from a session-local database into the workspace database, solving the sandbox isolation problem where inner agents cannot write to the shared evaluator database directly.

## 3. Trade-offs

| Win | Lose |
|---|---|
| 26% relative improvement over strongest baseline on standard benchmarks | 3x higher per-round optimization cost vs. procedure-based baselines on standard benchmarks |
| Avoids local optima through mechanism-level intervention (edits the search procedure, not just candidates) | Meta-agent overhead: requires a coding-capable agent (Claude Code/Codex) with significant context budget |
| Unified interface works for both procedure-based and agent-based evolution | Procedure-based AEVO can become expensive (e.g., $1.37/round on Kernel) due to expanding prompt sizes without caching |
| Persistent family map and "do not repeat" lists prevent redundant exploration | Agent-based AEVO sometimes converges more slowly (Best R. = 99 on AC2, vs. 44 for plain Claude Code) |
| Ablation-confirmed: harness is essential — 2/3 runs without it succumb to reward hacking | Coarse-grained intervention (one action per boundary) may be too slow for rapidly changing search landscapes |
| Sustains improvement beyond 100 rounds (1121 cycles at 200 rounds on Kernel) | Requires the task evaluator to be externally governed and protected — not applicable when evaluation is embedded in the agent |
| AEVO Agent maintains very low per-round cost ($0.32–$1.40) via prompt caching and persistent contexts | Meta-agent skill specification is hand-designed and may not generalize to all domains without adaptation |

## 4. Design Rationale

The authors argue that both procedure-based evolution (rigid but modular) and agent-based evolution (flexible but drifts) share a common failure mode: they accumulate rich evidence (candidates, feedback, traces, failures) but lack a stable interface for organizing this evidence and revising the mechanism that drives future evolution. The insight is that **the evolution process itself can be treated as an interactive environment** — with state = accumulated context, transition = evolution mechanism, and action = mechanism edit. This is distinct from prior work like HyperAgents (which internalizes meta-improvement within a self-modifying agent) because AEVO externalizes the meta-agent through a harness that keeps evaluation protected and records structured evidence. The harness design draws on the principle that evaluation integrity must be governed externally to prevent reward hacking — a lesson learned from observing that direct coding agents and unharnassed meta-agents drift toward exploiting evaluator loopholes rather than solving the actual task.

## 5. Limitations and Failure Modes

1. **Reward hacking without harness:** In ablation, removing the evolution harness caused 2/3 runs to enter reward-hacking trajectories, producing invalid cycle counts. The harness is not optional — it is load-bearing for safety.
2. **Coarse intervention granularity:** The meta-agent chooses exactly one action per inter-session boundary. If the search landscape changes rapidly or multiple simultaneous edits are needed, this constraint may throttle adaptation speed.
3. **Meta-agent skill is hand-crafted:** The operational skill that governs the meta-agent (read → attribute → choose one action → run → record) is manually designed. It has not been shown to generalize beyond the tested domains without human adaptation.
4. **Cost scaling on procedure-based mode:** Procedure-based AEVO does not benefit from prompt caching the way agent-based AEVO does, leading to 3x higher per-round cost on standard benchmarks compared to procedure-based baselines.
5. **Requires externally governed evaluator:** AEVO's architecture assumes evaluation is protected and externally governed. In domains where evaluation is embedded in the agent's own reasoning (e.g., self-consistency scoring without ground truth), the harness boundary is harder to enforce.
6. **No open-source release:** The paper does not mention open-source code or model weights, limiting reproducibility and independent verification.
7. **Modest benchmark breadth:** Only 5 tasks (2 standard benchmarks + 3 optimization tasks). Generalization to substantially different domains (e.g., multi-modal, robotics, long-horizon planning) is unverified.
8. **Meta-agent quality dependence:** AEVO's performance depends on the meta-agent's ability to diagnose bottlenecks and propose effective mechanism edits. Weaker coding agents would produce weaker edits.
9. **Late-stage convergence slowness:** On AC2, AEVO Agent takes 99 rounds to reach best score, vs. 44 for plain Claude Code — the harness adds exploration that delays convergence when the base agent would have found a good solution quickly.

## 6. Transfer to Lyra

### The One Transferable Idea

**Harnessed meta-editing for agent self-improvement.** Lyra should adopt AEVO's pattern of treating Lyra's own agent configuration (prompts, skills, tool definitions, memory structures, routing logic) as an editable mechanism observed through a protected harness. Instead of Lyra agents directly modifying their own operating context (risking drift and reward hacking), a meta-agent (or Lyra's orchestration layer) observes accumulated evidence from Lyra's evaluation runs — candidate quality, failure patterns, cost traces, redundant exploration — and makes coarse-grained, attributable edits to Lyra's agent configuration files (prompts, skills, router rules). The critical architectural element is the **protected evaluation boundary**: evaluation results and candidate records are governed externally and cannot be modified by the agents being improved. This prevents the self-reinforcing feedback loops that cause agent drift in long-horizon autonomous operation.
