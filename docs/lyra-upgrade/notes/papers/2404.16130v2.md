# From Local to Global: A GraphRAG Approach to Query-Focused Summarization

**Authors:** Darren Edge, Ha Trinh, Newman Cheng, Joshua Bradley, Alex Chao, Apurva Mody, Steven Truitt, Dasha Metropolitansky, Robert Osazuwa Ness, Jonathan Larson (Microsoft Research)
**Venue:** Preprint (arXiv:2404.16130v2, 19 Feb 2025 — under review)
**Code:** https://github.com/microsoft/graphrag (open-source, MIT license)

## 1. Mechanism (step-by-step)

GraphRAG is a **retrieval-augmented generation** pipeline that constructs a knowledge-graph index from private document corpora, then answers global sensemaking queries via hierarchical map-reduce summarization. It operates in two phases:

### Phase 1: Indexing Time (offline)

**Step 1 — Source Documents → Text Chunks**
Documents are split into chunks (600-token chunks with 100-token overlap used in experiments). Chunk size trades recall (longer chunks miss early content per "lost-in-the-middle" effect) against cost (fewer LLM calls per chunk).

**Step 2 — Text Chunks → Entities & Relationships**
An LLM (GPT-4-turbo) is prompted to extract from each chunk:
- **Entities**: (name, type, description) e.g., `("NeoChip", ORGANIZATION, "NeoChip is a publicly traded company...")`
- **Relationships**: (source_entity, target_entity, description, strength_score) e.g., `("Quantum Systems", "NeoChip", "Quantum Systems owned NeoChip from 2016...", 9)`
- **Claims**: factual statements about entities (optional, used for evaluation)

A **self-reflection (gleaning)** mechanism compensates for LLM extraction blind spots. After initial extraction, the LLM is asked "were any entities missed?" with a logit bias of 100 forcing yes/no. If yes, a continuation prompt ("MANY entities were missed...") triggers re-extraction. This loops up to a configurable max (testing showed diminishing returns after ~1 iteration).

**Step 3 — Entities & Relationships → Knowledge Graph**
Duplicate entity names are matched via **exact string matching** (softer approaches possible). Entity descriptions are aggregated/summarized per node. Relationship duplicates become weighted edges (count = weight). Claims are similarly deduplicated.

**Step 4 — Knowledge Graph → Graph Communities**
**Leiden community detection** (Traag et al., 2019) is applied **hierarchically**: partitions the graph into communities, then recursively sub-partitions each community until leaf communities that cannot be further split. This produces a multi-level hierarchy (C0 = root level with few communities, C3 = leaf level with many communities).

**Step 5 — Graph Communities → Community Summaries**
- **Leaf-level communities**: Elements (nodes, edges, claims) are prioritized by combined source+target node degree (prominence), then iteratively fed into the LLM context window (8k token limit) until full. The LLM generates a structured JSON report per community with title, summary, impact rating, and 5-10 detailed findings.
- **Higher-level communities**: If all sub-elements fit in context, proceed as leaf. Otherwise, rank sub-communities by token count descending and substitute shorter sub-community summaries for longer raw element lists until the token budget is met.

### Phase 2: Query Time (online)

**Step 6 — Community Summaries → Community Answers → Global Answer (Map-Reduce)**
Given a user query and a chosen community hierarchy level:
1. **Shuffle & chunk** community summaries into pre-specified token-sized groups (ensures relevant info spreads across chunks instead of being lost in one window).
2. **Map** (parallel): Each chunk is independently fed to the LLM, which generates a partial answer AND a helpfulness score (0-100). Answers scoring 0 are discarded.
3. **Reduce** (sequential): Partial answers are sorted by helpfulness score descending, then iteratively packed into a final context window until the token limit. The LLM synthesizes a final global answer from these.

### Key Algorithmic Details
- **Leiden algorithm** (hierarchical) via the `graspologic` Python library
- **Context window size**: 8k tokens empirically optimal across all tested sizes (8k/16k/32k/64k); larger windows degraded comprehensiveness (average 58.1% win rate for 8k vs larger sizes)
- **Graph indexing cost**: 281 minutes for ~1M token Podcast dataset using gpt-4-turbo on a 16GB VM with Intel Xeon Platinum 8171M
- **Self-reflection/gleaning**: logit_bias=100 on yes/no gate, up to N iterations, enables larger chunk sizes without quality loss

## 2. Results

### Datasets
| Dataset | Size | Chunks | Graph Nodes | Graph Edges |
|---------|------|--------|-------------|-------------|
| Podcast transcripts (Behind the Tech) | ~1M tokens | 1669 × 600-token | 8,564 | 20,691 |
| News articles (MultiHop-RAG benchmark) | ~1.7M tokens | 3197 × 600-token | 15,754 | 19,520 |

### Head-to-Head Win Rates (LLM-as-judge, 125 questions × 5 replicates)

**Comprehensiveness** (GraphRAG C0-C3 vs Vector RAG SS):
- Podcast: 72-83% win rate (p < 0.001)
- News: 72-80% win rate (p < 0.001)

**Diversity** (GraphRAG C0-C3 vs Vector RAG SS):
- Podcast: 75-82% win rate (p < 0.001)
- News: 62-71% win rate (p < 0.01)

**Directness** (validity test — opposite direction expected):
- Vector RAG SS won on directness across all comparisons (GraphRAG lost directness at ~35-45% win rate, p < 0.001), confirming the evaluation framework is sound.

**Empowerment**: Mixed results. GraphRAG generally underperformed SS on empowerment for Podcast (43-51% win rate), but was competitive on News.

### GraphRAG vs Source-Text Map-Reduce (TS)
GraphRAG (C2-C3) showed **small but significant** improvements over raw text map-reduce:
- Podcast comprehensiveness: C2 = 57% win rate over TS (p < 0.001)
- News comprehensiveness: C3 = 64% win rate over TS (p < 0.001)
- Podcast diversity: C2 = 57% win rate over TS (p = 0.036)
- News diversity: C3 = 60% win rate over TS (p < 0.001)

### Token Efficiency
| Level | Podcast Tokens | % of Max | News Tokens | % of Max |
|-------|---------------|----------|-------------|----------|
| C0 (root) | 26,657 | 2.6% | 39,770 | 2.3% |
| C1 | 225,756 | 22.2% | 352,641 | 20.7% |
| C2 | 565,720 | 55.8% | 980,898 | 57.4% |

| TS (raw) | 1,014,611 | 100% | 1,707,694 | 100% |

C0 uses 97%+ fewer tokens than raw text summarization while retaining 72% (Podcast) and 62% (News) comprehensiveness win rates over vector RAG.

### Claim-Based Validation (Experiment 2)
| Condition | Avg Claims (News) | Avg Claims (Podcast) |
|-----------|-------------------|---------------------|
| C0 | 34.18 | 32.21 |
| C1 | 32.50 | 32.20 |
| C2 | 31.62 | 32.46 |
| C3 | 33.14 | 32.28 |
| TS | 32.89 | 31.39 |
| SS (vector RAG) | 25.23 | 26.50 |

All global conditions produced significantly more factual claims than vector RAG (p < 0.05). Cluster-based diversity metrics aligned directionally. LLM judge labels matched claim-based labels in 78% of comprehensiveness and 69-70% of diversity pairwise comparisons (when LLM had a clear majority preference).

### Ablation: Context Window Size
Tested 8k, 16k, 32k, 64k context windows for the SS baseline. The smallest window (8k) was universally best for comprehensiveness (avg win rate 58.1%) and comparable on diversity/empowerment, countering the intuition that larger contexts always help.

## 3. Trade-offs

| Win | Lose |
|-----|------|
| **Global sensemaking quality**: 72-83% comprehensiveness gains over vector RAG on questions requiring whole-corpus understanding | **Directness/concision**: Vector RAG consistently wins on directness (GraphRAG loses 35-45% of directness comparisons) — answers are broader but less focused |
| **Token efficiency at C0**: Root-level summaries use only 2-3% of the tokens of raw text map-reduce while retaining most quality | **Upfront indexing cost**: 281 minutes for ~1M token corpus with GPT-4-turbo — pay-once, query-many model |
| **Structured knowledge**: Graph index provides interpretable community hierarchy, reusable for multiple queries | **No improvement on fact-retrieval queries**: GraphRAG designed only for global sensemaking; vector RAG wins on explicit retrieval tasks |
| **Scalability via hierarchy**: Any community level can be selected to balance detail vs. cost (C0=cheapest, C3=most detailed) | **Information loss in summarization**: Entity descriptions are condensed; community summaries may omit edge-case entities (empowerment scores lag) |
| **Claim-level validation**: Factual claim counts are 25-35% higher than vector RAG | **Statistically indistinguishable among global methods**: C0-C3 and TS show no significant differences in claim-based metrics — graph adds modest gain over raw summarization |
| **Parallelizable map step**: Community answers generated independently | **Sequential reduce bottleneck**: Final global answer requires single-pass synthesis of ranked partial answers |

## 4. Design Rationale

**Why graphs instead of embeddings?**
Vector RAG retrieves documents based on semantic similarity to a query. This works for "local" queries (find specific facts) but fails on "global" sensemaking questions that require understanding the entire corpus. The authors argue that graph modularity (Newman, 2006) provides a natural way to decompose a corpus into thematic communities — essentially performing **pre-query document clustering** based on extracted entities and relationships rather than raw text similarity.

**Why hierarchical Leiden communities?**
The hierarchical approach enables **level selection at query time**: shallow levels (C0) offer coarse, cheap overviews; deep levels (C3) provide fine-grained detail. This is analogous to zoom levels on a map. The divide-and-conquer strategy also makes summarization tractable: each community fits in a single context window.

**Why map-reduce for answer generation?**
Naively stuffing all community summaries into context would lose information (lost-in-the-middle effect). The shuffle+map+rank+reduce pattern ensures: (a) relevant info is distributed across independent LLM calls, (b) the helpfulness scoring filters irrelevant communities before the final synthesis, (c) the final context contains only the most useful partial answers ranked by score.

**Why self-reflection/gleaning instead of just using smaller chunks?**
Smaller chunks (600 tokens) extract ~2x more entities than larger chunks (2400 tokens) but cost more in LLM calls. Self-reflection allows the use of larger chunks without quality loss, trading a few extra tokens per chunk for dramatically fewer chunks overall.

## 5. Limitations & Failure Modes

1. **Corpus size limited to ~1M tokens**: All evaluations use corpora in the 1-2 million token range. Scaling behavior to 10M+ token corpora is unknown — both indexing cost and community detection may degrade.
2. **Single LLM evaluator bias**: The evaluation uses GPT-4 as both the generator and the judge. While validated with claim-based metrics, self-evaluation bias is a known concern (Huang et al., 2023 — cited by the authors themselves).
3. **Exact string matching for entity resolution**: The simplest possible deduplication method. Named entities with slight variants ("Microsoft Corp" vs "Microsoft") create duplicate nodes, though the authors claim resilience since duplicates cluster together in communities.
4. **Empowerment metric underperforms**: GraphRAG lost or tied on empowerment in many comparisons. LLM analysis suggests generated answers lack specific examples, quotes, and citations — indicating entity extraction prompts need domain-tuning.
5. **No hallucination/fabrication measurement**: The paper acknowledges this gap explicitly and suggests SelfCheckGPT as future work.
6. **Domain-generic prompts evaluated only**: Default prompts extract broad entity types (person, organization, place). Domain-specific few-shot exemplars are mentioned as beneficial but not systematically evaluated.
7. **GraphRAG adds no value for fact-retrieval queries**: The method is explicitly not designed for, and does not compete on, standard retrieval tasks. It is a complement to, not a replacement for, vector RAG.
8. **Indexing cost scales with corpus size**: 281 minutes for ~1M tokens on gpt-4-turbo. For larger corpora, this becomes a significant upfront investment that only pays off with high query volume.

## 6. Transfer to Lyra

**The ONE transferable idea:** The hierarchical community-summary index as a **pre-computed, query-agnostic sensemaking scaffold**. Instead of retrieving-then-reasoning at query time (vector RAG), GraphRAG builds a structured knowledge graph offline, partitions it into thematic communities, and pre-generates report-like summaries. At query time, map-reduce over these summaries answers global questions that no amount of vector retrieval could address.

**Workstream route:** This feeds directly into **§4.2 (Memory & Context)** and secondarily into **§4.1 (Core Reasoning)**. Lyra's memory subsystem needs both local (vector RAG) and global (sensemaking) retrieval capabilities. GraphRAG provides the blueprint for the global tier — the ability to answer "what are the main themes across all my conversations with this user?" or "what patterns connect my research notes on topic X?"

**Concrete application:** Lyra could maintain a background indexer that periodically (e.g., daily) extracts entities and relationships from recent conversation transcripts, constructs a knowledge graph, detects communities, and pre-generates community summaries. The query-time path then selects the appropriate community level based on question scope.

| Dimension | Rating |
|-----------|--------|
| **Impact** | 4 — enables a capability (global sensemaking over private data) that vector RAG fundamentally cannot provide |
| **Effort** | 4 — requires LLM-driven entity extraction pipeline, graph community detection, hierarchical summarization, and map-reduce query answering |
| **Tier** | **breakthrough** — GraphRAG is a genuinely novel architecture pattern for RAG systems, not an incremental improvement. The open-source release (MIT license) and LangChain/LlamaIndex integrations lower implementation barriers significantly. |
