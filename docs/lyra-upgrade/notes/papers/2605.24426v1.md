## 1. Mechanism

SEAL is a closed-loop co-evolution framework that jointly adapts both the LLM-agent policy and its training-time learning interface. The core insight is **Agent-Environment Misalignment**: as an agent's capability frontier shifts during RL training, the static environment provides increasingly mismatched learning signals. SEAL uses **verifier-grounded failure diagnosis** as a shared signal that drives both sides of the loop.

**Problem formulation.** Interactive tool use is modeled as a partially observable decision process M = (S, A, O, T, O_E, H, S_goal). At each turn, the policy pi_theta interacts with executable environment E to produce a trajectory tau = {(u_i, a_i, o_i)}. A binary verifier V provides terminal reward r(tau) in {0,1}. Standard RL maximizes J(pi_theta) = E[r(tau)], but this scalar signal indicates only success/failure, not why.

**Step 1: Verifier-Grounded Failure Diagnosis.** For each rollout tau, SEAL produces turn-level diagnostic labels Z(tau) = {z_1, ..., z_T} where z_i = Psi(a_i, xi_i, s_{i-1}, s_i, F). The diagnosis function Psi is a deterministic rule-based classifier using parser checks, tool-schema validation, execution errors, observable state transitions, and verifier comparisons. The taxonomy includes: invalid_tool_call, argument_mismatch, state_mismatch, recovery_failure, missing_tool_call, response_mismatch, correct_abstention, spurious_tool_call, empty_turn, instance_mismatch, and pass. Diagnosis does NOT modify the benchmark reward; it only adds structure for optimization.

**Step 2: Learning-Interface Evolution.** SEAL constructs augmented training-time observations o_tilde_i = Omega_t(o_i, F, H_t, C_t) using three components:
- phi_schema(F): exposes schema-implied tool affordances (required arguments, enum constraints, types, valid formats)
- phi_err(o_i, H_t): converts execution errors into recovery-oriented feedback (e.g., "[ToolHint] Required argument(s) X for tool Y were missing")
- phi_cap(C_t): selects capability-specific cues from the aggregate failure profile (e.g., "[Cautious-call] If no available function matches, respond in plain text rather than fabricating a tool call")

The interface update is selected by failure type rather than benchmark instance. All adaptations are removed at evaluation time.

**Step 3: Diagnosis-Guided Advantage Reweighting.** SEAL computes an empirical diagnostic profile p_j(z) for each trajectory (fraction of turns with each label), then assigns a diagnostic utility weight w_j = clip(sum_z p_j(z) * rho(z), w_min, w_max), where rho(z) is a fixed utility function (e.g., spurious_tool_call = 2.0, response_mismatch = 0.9, pass = 1.0). The GRPO advantage is reweighted as A_tilde_j = w_j * A_j, preserving sign (so verifier direction is unchanged) while scaling contribution by diagnostic informativeness.

**Step 4: Closed-Loop Training.** SEAL alternates: (a) sample prompts, collect rollouts with current interface Omega_t; (b) verify r(tau_j) and diagnose Z(tau_j); (c) aggregate failure profile C_t; (d) evolve interface Omega_{t+1} = Evolve(Omega_t, C_t); (e) update policy with diagnosis-weighted GRPO. The full algorithm (Algorithm 1 in the paper) runs for R rounds.

## 2. Results

**In-distribution (BFCL V3 multi-turn, 400-sample low-resource training):**

| Backbone | Base Model (%) | Vanilla RL (%) | SEAL (%) | SEAL vs Vanilla RL |
|---|---|---|---|---|
| Qwen2.5-3B-Instruct | 5.75 | 9.25 (+3.50) | 14.00 (+8.25) | +4.75 |
| Qwen2.5-7B-Instruct | 14.00 | 30.75 (+16.75) | 40.25 (+26.25) | +9.50 |
| ToolACE-2-Llama-3.1-8B | 32.00 | 38.50 (+6.50) | 46.75 (+14.75) | +8.25 |

Largest per-category gains for Qwen2.5-7B: Missing Functions 14% -> 36% (+22pp), Missing Parameters 10% -> 34% (+24pp), Base 22% -> 58% (+36pp).

**Out-of-distribution (trained on BFCL V3 only, evaluated on BFCL V4 and tau-bench):**

| Model | BFCL V4 Avg (%) | tau-bench Avg (%) |
|---|---|---|
| Qwen2.5-3B Vanilla RL | 5.98 | 10.60 |
| Qwen2.5-3B + SEAL | 8.63 | 11.76 |
| Qwen2.5-7B Vanilla RL | 10.26 | 17.19 |
| Qwen2.5-7B + SEAL | 12.71 | 20.79 |

**Ablation on Qwen2.5-7B:** Full SEAL = 40.25%, w/o Environment-Side Adaptation = 35.75% (-4.50), w/o Diagnosis-Guided Reweighting = 32.75% (-7.50), w/o Closed-Loop Update = 33.00% (-7.25). Reweighting contributes more than interface adaptation, but both are complementary.

**Training dynamics:** SEAL converges faster and reaches higher validation accuracy across all BFCL V3 subsets. The gap widens after early training phase, consistent with closed-loop design.

## 3. Trade-offs

| Win | Cost/Lose |
|---|---|
| +8.25 to +26.25 avg points across 3 backbones with only 400 samples | Requires executable environments with tool schemas, execution traces, and verifier feedback |
| +4.75 to +9.50 avg points over Vanilla RL under identical compute budget | Diagnostic utility weights rho(z) are FIXED across all tasks and backbones; no adaptive weighting |
| Positive OOD transfer to BFCL V4 (+2.45-2.65pp) and tau-bench (+1.16-3.60pp) | Absolute OOD scores remain modest; cross-benchmark generalization is still challenging |
| Learning curve is smoother and converges faster than Vanilla RL | Environment evolution is intentionally conservative; only modifies training-time interface, not tool semantics |
| No additional test-time cost; evolved interface is removed at evaluation | Relies on rule-based deterministic diagnosis (Psi); may not extend to open-ended domains |
| Works across model scales (3B, 7B, 8B) and initialization qualities | Adds implementation complexity: diagnosis classifier + interface wrapper + reweighting pipeline |
| Complements existing RL frameworks (GRPO); drop-in augmentation | Clipping range [0.5, 2.0] and utility weights require manual tuning per domain |

## 4. Design Rationale

The central design choice is using **verifier-grounded diagnosis as a shared signal** rather than treating model evolution and environment adaptation as separate problems. Prior approaches either do model-centric RL (policy improves against a static environment, leading to self-referential bias and inefficient credit assignment) or environment-centric curriculum learning (adapts task difficulty/distribution but without grounding in executable failures). SEAL argues both are symptoms of the same structural problem: the training environment fails to track the agent's evolving capability boundary. By grounding both adaptations in the same diagnostic evidence—parser errors, schema violations, state mismatches from executable traces—the framework ensures the environment's adaptations directly target the policy's revealed capability gaps. The decision to restrict adaptation to the training-time interface (not tool semantics or verifier) preserves benchmark fairness while still making learning signals more informative. The priority-based diagnosis taxonomy (Table 5, Appendix C) favors directly executable failures over downstream verifier-level failures, ensuring attribution is traceable.

## 5. Limitations & Failure Modes

1. **Executable environment requirement**: SEAL depends on tool schemas, execution traces, and verifier feedback. Open-ended domains (creative writing, open dialogue) may lack these signals, requiring richer diagnosis mechanisms.
2. **Conservative environment evolution**: Only the training-time interface is adapted, not tool semantics or evaluation rules. This preserves fairness but limits the scope of what can be improved—the agent still operates under the original tool constraints.
3. **Fixed diagnostic utility weights**: rho(z) values are manually set and frozen across all tasks, backbones, and training stages. Adaptive or learned utility weights could improve performance.
4. **Cross-domain generalization remains challenging**: Absolute OOD scores are modest (Qwen2.5-7B SEAL: 12.71% BFCL V4, 20.79% tau-bench), indicating the co-evolution is still largely benchmark-specific.
5. **Rule-based diagnosis fragility**: The deterministic classifier Psi works for well-structured tool-call environments but may fail or misattribute failures when execution traces are ambiguous.
6. **Diagnosis-labelling priority order**: When multiple failures co-occur, the fixed priority order (invalid_tool_call > argument_mismatch > state_mismatch > recovery_failure > missing_tool_call > response_mismatch) may mask important secondary failure modes.
7. **No theoretical convergence guarantee**: The co-evolution loop (alternating interface updates and policy updates) is empirically effective but lacks formal analysis of whether it converges or oscillates.

## 6. Transfer to Lyra

**The one transferable idea:** SEAL demonstrates that **verifier-grounded failure diagnosis can serve as a shared signal to co-adapt both the training interface and policy optimization**. In Lyra, this translates to instrumenting the verification subsystem to produce structured failure-type labels from agent rollouts, using those labels to: (a) enrich the training-time observation with recovery-oriented feedback and constraint cues, and (b) reweight trajectory contributions during policy optimization. This is directly applicable to Lyra's multi-turn tool-use and reasoning workflows, where sparse verifier signals (pass/fail) currently dominate.

**Workstream route:** §4.5 — Reliability & Verification (diagnosis taxonomy feeds into verifier instrumentation; diagnosis-guided reward shaping for agent training loops)

**Impact:** 4 — Substantial gains on structured tool-use failures with low engineering surface area; mechanism is architected to be complementary to existing RL training.

**Effort:** 3 — Requires implementing a rule-based diagnosis classifier over agent trajectories, building a lightweight training-time observation wrapper, and integrating diagnosis-weighted advantage into Lyra's existing optimization pipeline. No new infrastructure beyond what Lyra's verification subsystem already provides.

**Tier:** **investigate** — The approach is promising but relies on executable verification signals that Lyra may not have for all task types. A feasibility prototype on Lyra's most structured benchmark (code execution / tool use) is warranted before full investment. The fixed diagnostic weights and rule-based classifier would need adaptation to Lyra's broader task spectrum.
