## 1. Mechanism

EvoCoT is a self-evolving curriculum learning framework with two nested stages that iterate jointly. The core insight is that exploration bottlenecks in RLVR arise from excessively large solution spaces on hard problems. EvoCoT addresses this by first constraining the exploration space, then gradually expanding it.

### Algorithm (Pseudocode from Appendix A)

```
def EvoCoT(LLM, D, T, train_steps, delta_step=1):
    for t in range(T):
        # Stage 1: Answer-Guided CoT Generation
        C_set = []
        for (Q, A) in D:
            C_hat = LLM.generate(Q, A)        # Generate CoT conditioned on answer
            A_hat = LLM.generate(Q, C_hat)     # Verify: can LLM derive A from CoT?
            if A_hat == A:
                C_split = split_steps(C_hat)   # Split into step-wise segments
                C_set.append((Q, C_split, A))

        # Stage 2: Step-Wise Curriculum Learning
        for (Q, C_split, A) in C_set:
            n = len(C_split)
            for k in range(0, n, delta_step):  # Progressively shorten CoT
                Ck = delete_last_k_steps(C_split, k)
                C_tilde, A_tilde = LLM.roll_out(Q, Ck)  # Model completes from prefix
                training_set.append((C_tilde+A_tilde, reward=(A_tilde == A)))
        
        LLM.train(training_set)  # RL training with GRPO
    return LLM
```

### Stage 1: Answer-Guided Reasoning Path Self-Generation

Given question-answer pairs (Q, A) from the training set, the LLM generates CoT trajectories conditioned on knowing the correct answer. The intuition: reasoning paths are easier to construct in reverse (from answer to question). Each generated CoT is verified by checking whether the LLM can reconstruct A from C_hat. Valid CoTs are split into n sequential reasoning steps [c1, c2, ..., cn]. This stage requires no human-annotated CoTs or teacher models -- it transforms outcome-supervised data into step-level supervision.

### Stage 2: Step-Wise Curriculum Learning

The curriculum follows a progressive difficulty schedule by removing CoT steps in reverse order:

```
(Q, c1, c2, ..., cn)  →  roll_out (C_tilde, A_tilde)
(Q, c1, ..., cn-1)    →  roll_out (C_tilde, A_tilde)
...
(Q, c1)               →  roll_out (C_tilde, A_tilde)
(Q)                   →  roll_out (C_tilde, A_tilde)
```

At each level, the provided CoT prefix constrains the exploration space. As steps are removed, the space expands, increasing difficulty. The LLM must complement the missing reasoning, ultimately deriving A directly from Q. Rollouts receive reward = 1 if A_tilde == A, 0 otherwise. Training uses GRPO (or DAPO) with standard RLVR hyperparameters (LR=1e-6, batch=32, 8 samples/problem, temperature=1.0, KL coefficient=0.0001).

### Self-Evolving Iterative Optimization

After Stage 2 training, the improved LLM enters Stage 1 again, generating higher-quality CoTs. These better CoTs provide stronger guidance in the next Stage 2, creating a virtuous cycle. The two stages iterate T=2-3 times before saturation.

### Key Design Elements

1. **Reverse-order step removal** prevents reward hacking: the answer is not revealed in the prefix CoT
2. **delta_step=1** (remove 1 step per curriculum level) achieves best results (53.5 avg vs 52.4 for delta_step=2 vs 50.8 for delta_step=3 on Qwen2.5-7B)
3. **Entropy preservation**: EvoCoT slows entropy collapse compared to GRPO, maintaining exploration capacity longer (Appendix C, Figure 5)
4. **Orthogonal to RL optimizer**: works with GRPO, DAPO, and any on-policy RL algorithm

## 3. Trade-offs

| Gain | Cost |
|------|------|
| +4.5 to +21.7 avg improvement on training set for strong LLMs | ~3.4% training overhead (Stage 1 preprocessing) |
| No teacher model or human-annotated CoT required (distillation-free) | Requires correct (Q, A) pairs; Stage 1 cannot generate CoTs when answer is wrong or LLM lacks domain knowledge |
| Compatible with any RL optimizer (GRPO, DAPO) | Saturates after 1-2 iterations; no indefinite improvement |
| Slower entropy collapse preserves exploration capacity | delta_step must be tuned per model; wrong step size degrades performance |
| Works across model families (Qwen, DeepSeek, Llama) | Weaker LLMs (Llama3.1-8B) see minimal benefit (+0.9 avg) |
| Uses all training data including hard problems (unfiltered) | ~10% of hard problems permanently unsolvable due to dataset errors or missing pre-training knowledge |
| Self-evolving: improved LLM generates better CoTs in next iteration | Overly long CoTs cause 100% rollout accuracy → zero gradient (mitigated by dynamic step removal) |

## 4. Design Rationale

The authors observe that RLVR fails on hard problems because the solution space is too large relative to the LLM's current reasoning capability, causing reward sparsity. Existing solutions either (a) use teacher model distillation, limiting scalability, or (b) filter out hard problems, discarding valuable training data. EvoCoT's design follows three principles:

1. **Constrain-then-expand**: Rather than filtering hard problems, constrain the exploration space by providing partial CoTs, then gradually remove scaffolding.
2. **Reverse reasoning is easier**: Generating reasoning from a known answer (Stage 1) is fundamentally easier than solving problems from scratch, enabling bootstrapping without teacher models.
3. **Natural curriculum via step removal**: Longer CoT prefixes provide more guidance (easier), shorter prefixes provide less (harder). Progressive removal of trailing steps creates a smooth difficulty progression without manual difficulty annotation.

The choice of reverse-order step removal (rather than random masking or forward removal) is deliberate: removing final steps first prevents the answer from being exposed in the prefix, eliminating reward hacking where the model learns to copy the answer rather than reason.

## 5. Limitations & Failure Modes

1. **Saturation ceiling**: Self-evolution plateaus after 1-2 iterations. Performance does not improve indefinitely; it peaks then declines or stabilizes.
2. **Stage 1 bottleneck**: If the LLM cannot generate a valid CoT from (Q, A), no curriculum can be built. This occurs when:
   - The LLM lacks necessary domain knowledge from pre-training
   - The LLM forcibly splices the answer without coherent reasoning (Figure 3d)
   - The LLM contradicts the provided answer (Figure 3c)
3. **Dataset quality dependency**: ~10% of persistently unsolved training problems are due to ground truth answer errors (e.g., GSM8K sample with wrong answer). EvoCoT cannot fix these.
4. **Weak model limitation**: Models with insufficient base reasoning (Llama3.1-8B: +0.9 avg improvement) gain little. EvoCoT requires a minimum reasoning capability to bootstrap.
5. **Hyperparameter sensitivity**: delta_step must match model capability. Wrong step size (too aggressive removal) disrupts curriculum smoothness and degrades performance (delta_step=3 gives 50.8 vs 53.5 for delta_step=1).
6. **Overly easy CoT problem**: When generated CoTs are too long, 100% rollout accuracy occurs, producing no training signal (zero gradient). Mitigated by dynamic step removal targeting ~50% accuracy.
7. **No evaluation on non-math domains**: All benchmarks are math reasoning. Transferability to code, tool use, or general reasoning is untested.

## 6. Transfer to Lyra

**The ONE transferable idea:** Self-evolving curriculum learning via progressively removing intermediate reasoning scaffolding. For Lyra, this means: when an agent fails on a hard multi-step tool-use task, generate a successful trajectory by conditioning on the correct outcome (Stage 1), decompose it into step-wise segments, then re-train or fine-tune the agent by progressively removing later steps (Stage 2). This provides a principled way to bootstrap agent capability improvements on previously unsolved tasks without requiring teacher trajectories or human demonstrations.

**Workstream route:** §4.5 (Agent Reasoning & Self-Improvement) -- the self-evolving curriculum directly addresses Lyra's need to improve agent reasoning on complex multi-step tool-use tasks where exploration is currently too expensive or reward signals too sparse.

**Assessment:**
- **Impact: 4** -- Addresses a fundamental bottleneck in agent RL training (exploration on hard tasks). Directly applicable to tool-augmented agent trajectories with verifiable outcomes.
- **Effort: 4** -- Requires implementing: (1) answer-conditioned trajectory generation for Lyra agents, (2) trajectory step segmentation, (3) step-wise curriculum RL loop. Non-trivial but the algorithm is well-specified.
- **Tier: investigate** -- Strong results in math domain but completely untested on tool-use agent tasks. Worth prototyping on a small set of hard Lyra agent tasks before full implementation. The saturation after 1-2 iterations and weak-model limitation are cautionary signals.
