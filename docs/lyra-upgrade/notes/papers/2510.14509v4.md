## 1. Mechanism (step-by-step)

E2EDev is a **benchmark** (not a framework), grounded in Behavior-Driven Development (BDD) principles, that evaluates whether LLM-generated software satisfies fine-grained user requirements via automated, executable end-to-end tests.

### Benchmark Construction Pipeline (HITL-MAA)

The benchmark is built from 46 real-world, starred GitHub web application projects via the Human-in-the-Loop Multi-Agent Annotation (HITL-MAA) framework:

1. **Project Selection**: Crawl GitHub repos with keywords ("mini project", "web application", "H5") and >500 stars. Five annotators verify each candidate on Executability, Functionality, and Suitability. Fleiss' Kappa reaches 0.83 after 1 refinement round. Final: 46 projects from 158 candidates.

2. **Test-ID Pre-Annotation** (GPT-4o Multi-Agent Group): Scan HTML/JS files and inject `data-testid` attributes into interactive elements. HTML annotator handles static elements; JS annotator handles dynamically generated elements. Cross-file consistency enforced via shared project context.

3. **Code Analyzer Agent** → Analyzes HTML structure (UI elements, form interactions) and JS logic (event handlers, function-to-element mappings). Produces structured analysis summary.

4. **Requirement Extractor Agent** → Generates candidate user-facing requirements from analysis and source code. Human supervisors validate and correct (~20% refined). Output: JSON with `summary` (overview, predefined_options, external_resources, external_js_libraries) and `requirements` array with ID + description.

5. **Test Case Generator Agent** → For each validated requirement, generates Gherkin scenarios covering [Normal], [Edge], and [Error] cases. Five software testing experts collaboratively review and refine (~50% of test cases adjusted). Output: Feature + Scenario blocks in Given-When-Then format.

6. **Test Automation Engineer Agent** → Converts Gherkin scenarios into Python step implementations using Selenium + Behave. Iterative verification loop:
   - **Step Checker (Dry-Run Verifier)**: Runs `behave --dry-run` for max_iter1=3 iterations (avg 1.47 iterations to pass)
   - **Test Runner**: Executes full Behave tests for max_iter2=6 iterations (avg 4.62 iterations; 20% hit max and need human refinement)
   - Self-correction resolves ~100% of dry-run errors autonomously, ~80% of logical issues autonomously

### Evaluation Metrics

**Effectiveness** (averaged over 3 runs):
- **Req.Acc** = N/M where N = fully-satisfied requirements (all test cases pass), M = total requirements
- **Test.Acc** = Total Passed Test Cases / Total Test Cases
- **Balanced Score** = 0.6 * Req.Acc + 0.4 * Test.Acc

**Efficiency** (single run, negligible variance):
- **Cost (USD)** = Input Tokens * Input Price + Output Tokens * Output Price
- **CO2 (g)** = (FLOPs * TDP / η) * PUE * CI + EC, where FLOPs = 2 * (Input + Output Tokens) * Active Parameters
- **Duration (s)** = wall-clock time

### Frameworks Evaluated (6 categories)
1. **Vanilla LLM**: Direct prompt-to-code without scaffolding
2. **GPT-Engineer**: Single-agent, modular workflow, "think step by step"
3. **Self-Collaboration**: 3-agent team (analyst, coder, tester)
4. **MapCoder**: 4-agent pipeline (recall examples, plan, code, debug)
5. **ChatDev**: Dynamic multi-agent with structured chat chains
6. **MetaGPT**: SOP-encoded multi-agent with assembly-line paradigm

LLM backbones: Claude-Haiku 4.5, GPT-4o, GPT-4o-mini, Qwen2.5-7B, Qwen2.5-70B, Qwen-Max.

## 2. Results (real benchmark numbers)

### Main Results (Table 3) — Best Per-Backbone

| Backbone | Best Method | Req.Acc | Test Acc | Bal.Score | Cost ($) | Time (s) |
|----------|------------|---------|----------|-----------|----------|----------|
| Claude-Haiku 4.5 | GPT-Engineer | **53.75%** | 69.41% | **60.01%** | 0.016 | 59 |
| GPT-4o | GPT-Engineer | 50.83% | 66.59% | 57.13% | 0.020 | 21 |
| GPT-4o-mini | Vanilla LLM | 44.82% | 60.65% | 51.15% | 0.001 | 16 |
| Qwen-Max | GPT-Engineer | 49.61% | 63.70% | 55.25% | 0.003 | 66 |
| Qwen-70B | ChatDev | 43.15% | 57.62% | 48.94% | 0.039 | 341 |
| Qwen-7B | GPT-Engineer | 24.03% | 39.94% | 30.39% | 0.0003 | 31 |

### Key Findings

- **No model exceeds 60% Req.Acc** — even Claude-Haiku 4.5 with GPT-Engineer maxes at 53.75%.
- **MetaGPT catastrophic failure**: 0.00% Req.Acc with GPT-4o; max 5.39% with Claude-Haiku 4.5.
- **Soft Req.Acc gap vs Req.Acc**: ~25% discrepancy across all frameworks, indicating models implement core functionality but miss edge cases.
- **Multi-agent cost premium**: ChatDev GPT-4o costs $0.195 (12x Vanilla), MapCoder GPT-4o costs $0.109 (6.8x Vanilla), with marginal or negative effectiveness gains.
- **Interaction overhead** (Table 4): ChatDev reaches 15.72 average turns (GPT-4o), MetaGPT requires 10.46+ turns.
- **Function-level vs Project-level gap**: GPT-4o Pass@1 HumanEval = 89.02% vs GPT-Engineer Req.Acc E2EDev = 50.83% — a **38% drop**.

### Failure Mode Distribution (Human Evaluation of 360 projects)
| Failure Type | Description | Prevalence |
|-------------|-------------|------------|
| Code Inconsistency | Missing/empty/conflicting functions | Highest in MapCoder, MetaGPT (44% of MetaGPT failures) |
| Requirement Missing | Features entirely absent | Highest in Vanilla LLM, ChatDev |
| Requirement Misalignment | Logic deviates from spec | Lowest in multi-agent (reduced by component analysis) |
| Detail Mismatch | Edge cases, missing validation, UI inconsistencies | Universal, worst in Self-Collaboration |

## 3. Trade-offs (wins vs loses)

| Dimension | Win | Lose |
|-----------|-----|------|
| **Multi-agent vs Single-agent** | Reduces requirement misalignment via explicit component analysis | Increases code inconsistency (longer context chains dilute specs); adds 5-20x cost |
| **Requirement Analysis** | Coding agents with explicit req analysis miss fewer requirements | Progressive dilution of detail constraints across multi-agent chains |
| **Context Sharing** | Repeated prepending of original requirements (MapCoder, ChatDev) partially preserves details | Excessive context from analogical prompting (MapCoder) introduces noise, not guidance |
| **Framework Complexity** | GPT-Engineer (simple, modular) delivers best cost/performance ratio | MetaGPT (complex SOPs) catastrophically fails due to communication breakdowns |
| **LLM Backbone Strength** | Qwen-70B shows best instruction-following stability in ChatDev (fewer turns, less hallucination) | GPT-4o-mini (distilled) degrades under heavy agent prompts despite strong standalone performance |
| **Evaluation Precision** | BDD provides deterministic pass/fail vs. heuristic or human-only evaluation | Test scripts non-reusable; tied to ChromeDriver; only covers user-visible behavior |
| **Annotation Quality** | HITL-MAA achieves 100% executable test rate, Fleiss' Kappa 0.81 | Annotation cost: 3.5h/project, $0.48/project, 140k prompt tokens/project |

## 4. Design Rationale (why this approach)

1. **BDD over unit testing**: Unit tests verify isolated functions but cannot validate whether the integrated system meets user intent. BDD (Given-When-Then) tests system behavior from user perspective, directly mapping requirements to executable verification. This is the core insight: E2ESD evaluation must be *behavioral*, not *structural*.

2. **Black-box testing (ISO 29148)**: Avoids volatility of environment-specific implementation details. Browser-based automation (Selenium + Behave) ensures reproducible results regardless of how LLMs internally structure their code.

3. **Web apps as lower bound**: If models fail at web application generation (relatively simple, deployable with static HTTP servers), they will fail at more complex system-level settings. Web apps serve as a necessary but not sufficient capability test.

4. **Human-in-the-loop annotation**: Pure LLM annotation yields vague tests, poor Fleiss' Kappa (0.23), and incomplete coverage. Multi-agent HITL with gold-checker review raises agreement to 0.79, achieves 100% executable test rate, and increases average test cases per project from 6.5 to 15.

5. **Separation of framework from model effects**: Testing 6 frameworks across 6 LLMs disentangles architectural design from model capacity, revealing that agentic overhead can negate model strength (e.g., MetaGPT with GPT-4o scores 0.00% Req.Acc).

## 5. Limitations & Failure Modes

### Paper Limitations
- **Scale**: Only 46 projects (limited by annotation cost); may not generalize to all software types.
- **Domain**: Web applications only; excludes backend logic, databases, CI/CD pipelines, mobile, or desktop apps.
- **Evaluation protocol**: Black-box testing cannot assess code quality, maintainability, security, or performance.
- **Test reusability**: BDD test scripts are tied to specific project structures; cannot be reused across different LLM outputs for the same requirement.
- **Environment dependency**: Requires ChromeDriver; results may vary across browser versions.
- **Cost measurement**: Uses list API pricing; actual costs may differ with batch pricing or rate limits.

### Framework Failure Modes
- **MetaGPT**: 44% of failures from code inconsistency (architect's file structure ignored by programmer); 54% of syntax errors from malformed imports due to tool-invocation prompts outweighing coding instructions 10:1.
- **Vanilla LLM / ChatDev**: Most severe requirement omissions due to lack of explicit requirement analysis exposure during coding.
- **MapCoder**: Analogical retrieval from coarse-domain-similar projects introduces noise instead of actionable guidance.
- **Self-Collaboration**: Worst detail mismatch due to progressive dilution of fine-grained constraints through multi-agent chain.
- **ChatDev stopping mechanism**: Rigid string-based termination signals ("&lt;INFO&gt; Finished" vs "&lt;INFO&gt; Finish") cause unnecessary dialogue loops, especially in small models (Qwen-7B hits 20-turn cap on trivial tasks).

## 6. Transfer to Lyra

### The One Idea

**BDD-style Behavioral Verification Layer**: Adopt Gherkin-inspired, requirement-level behavioral testing for Lyra agent capabilities. Instead of coarse-grained pass/fail task evaluation, decompose each Lyra capability (e.g., "agent schedules a meeting", "agent debugs a function") into fine-grained BDD scenarios (Given preconditions → When agent acts → Then observable outcome holds) with executable Selenium-like verification scripts. This enables deterministic, reproducible, requirement-level scoring that reveals *why* an agent fails (missing requirement vs. detail mismatch vs. code inconsistency), not just *that* it fails.

### §4 Workstream Route

**§4.4 — Verification & Testing**. E2EDev provides a blueprint for building an automated behavioral test harness that evaluates Lyra's end-to-end capabilities against fine-grained, user-perspective acceptance criteria. The HITL-MAA pipeline pattern also applies to semi-automated generation of Lyra test suites from existing agent traces.

### Impact/Effort/Tier

| Dimension | Rating | Rationale |
|-----------|--------|-----------|
| Impact | 4/5 | Transforms Lyra's evaluation from coarse "task completed?" to precise "which requirements were satisfied, which edge cases failed?" — enables targeted improvement |
| Effort | 3/5 | Requires building a Behave-like harness, defining Gherkin-style scenarios for Lyra's 30+ capabilities, and Selenium-like instrumentation for agent-environment interaction |
| Tier | **breakthrough** | No existing agent benchmark provides requirement-level behavioral verification with executable tests; E2EDev's BDD methodology is directly portable to agent evaluation |
