## 1. Mechanism (step-by-step)

CER is a **training-free**, **context-window-based** self-improvement framework for LLM agents operating in interactive web environments (WebArena, VisualWebArena). It is loosely inspired by experience replay from RL (Schaul et al., 2016; Rolnick et al., 2019) but operates entirely through in-context learning — no gradient updates.

### Architecture: 4 modules

1. **Distillation Module D** — Given a trajectory set T = {τ₁, τ₂, ..., τₙ}, distill experiences E = {E₁, ..., Eₙ} where each Eᵢ = (Dᵢ, Sᵢ):
   - **Dᵢ (Dynamics):** Summaries of web page states, their URLs, and inferred possible usages. E.g., "Forums page: lists different forums, URL: http://localhost:9999/forums"
   - **Sᵢ (Skills):** Decision-making patterns as step-by-step guidelines with natural language summaries AND concrete action examples. E.g., "Navigate to forum {forum name}: 1. Click Forums link `click({button_id})`, 2. ..."
   - Two separate distillation sub-modules due to different characteristics of dynamics vs skills.
   - Distillation is done in a **ReAct-inspired** loop: model emits `think` before each output.
   - Model is instructed to produce **abstract, general** outputs (e.g., "navigate to forum {forum_name}" not "navigate to forum 'books'") for broad reusability.
   - **Existing buffer experiences are provided** during distillation to avoid redundant accumulation.

2. **Retrieval Module R** — Given task goal, website descriptions, and all experiences in buffer ε, the VLM outputs top-k most useful experiences:
   - Two separate retrieval modules for dynamics and skills.
   - k_d = 5 (dynamics), k_s = 5 (skills) by default.
   - Implemented by prompting the VLM with the current task context and all buffer contents.

3. **Dynamic Experience Buffer ε** — Stores all distilled experiences. Grows over time as more trajectories are distilled. Experiences are merged incrementally (new experiences checked against existing to avoid redundancy).

4. **Decision-Making Agent A** — Base agent (ReAct + BrowserGym) augmented with retrieved experiences:
   - Selected experiences E = {E₁, ..., Eₖ} are transformed via programmatic mapping f into natural language descriptions E_NL = f(E).
   - These are integrated into the model context: C' = g(C, E_NL).
   - The augmented context biases the agent toward states/actions that proved useful in past trajectories.

### Three Operating Settings

- **Offline:** Pre-collected human-annotated trajectories (5-10 per website, ~5% of test set) → distill → fixed buffer → solve all test tasks.
- **Online:** Start empty buffer → solve task i → distill trajectory → merge buffer → solve task i+1 with richer buffer → repeat.
- **Hybrid:** Offline learning first, then online self-evolution. Best performing (36.7% avg on WebArena).

### Key Design Decisions

- Learns from **both successful and failed trajectories** (shown robust: CER_success-only = 33.5% vs CER_all = 31.4%, small gap).
- Experiences are **text-only natural language** — no embeddings, no vector DB, no training. Pure prompt engineering.
- **No ground-truth reward needed** for operation (though having it boosts from 31.4% → 33.5%).
- BrowserGym provides accessibility tree + screenshots; Set-of-Marks (SoM) overlays used for VisualWebArena.

## 3. Trade-offs (wins vs loses)

| Win | Lose |
|-----|------|
| **+51% relative improvement** over GPT-4o baseline on WebArena with only +17.3% token cost | Still far below human performance (36.7% vs 78.24% on WebArena) |
| **Training-free** — no gradient updates, no fine-tuning infrastructure needed | Requires **goal-oriented trajectories** as input; random exploration trajectories yield poor experiences |
| **Orthogonal to most other methods** (works with tree search, sampling, different base models) | **Relies on strong VLM** for distillation/retrieval quality; weaker models (Llama-3.1) show smaller gains |
| **Excellent stability (93%) and plasticity (141%)** — retains old capabilities while gaining new ones | **Dependency on human annotators** in offline setting for initial trajectory collection |
| **3x fewer tokens than tree search** while outperforming it on VisualWebArena | **No initial help in online setting** — buffer starts empty; early tasks get no benefit |
| Learns from **both successes and failures** (robust to noisy trajectories) | Success-only filtering gives +2.1% boost (33.5 vs 31.4), showing failed trajectories do introduce some noise |
| **Dynamics+Skills division** is synergistic — removing either degrades performance | **URL-reliant dynamics** advantage may not generalize to non-web environments without navigable state identifiers |
| **Simple, prompt-only** implementation — no vector DB, no embeddings, no training pipeline | **Context window consumption** grows with buffer size; retrieval module must filter aggressively |

## 4. Design Rationale

**Why experience replay in the context window rather than fine-tuning?**
The authors argue that web environments have immense state/action spaces, but only a small subset of states and actions are typically useful for goal-oriented tasks. Fine-tuning would be costly per environment. In-context replay lets the agent "recognize" promising states/actions (inspired by Klein's Recognition-Primed Decision model, 1998) without weight updates, making it immediately deployable in new environments.

**Why separate dynamics from skills?**
Dynamics provide "where am I / where can I go" (state-awareness + URL navigation), while skills provide "what should I do here" (action heuristics). They serve different cognitive functions — dynamics for orientation, skills for execution. Ablation confirms both are needed.

**Why learn from failed trajectories too?**
Removing failed trajectories requires ground-truth evaluators, limiting applicability. The gap between all-trajectory (31.4%) and success-only (33.5%) is small enough that robustness to noise is worth the loss of 2.1 points, especially in online settings where success signals may not be available.

**Why abstract/general distillation?**
The model is explicitly prompted to generalize (e.g., "navigate to forum {forum_name}" not "navigate to forum 'books'"). This prevents overfitting to specific task instances and enables cross-template transfer, validated by the +15.3 point ct-SR improvement.

## 5. Limitations & Failure Modes

1. **Requires goal-oriented trajectories.** Performance degrades significantly if only random exploration trajectories are available. The distillation module extracts patterns from purposeful behavior; random walks produce low-quality, misleading experiences.

2. **Human annotation dependency in offline/hybrid settings.** The offline phase uses human-designed tasks with gold trajectories. Without these, the hybrid advantage over pure online is lost. Scaling to arbitrary websites would require automated trajectory generation (briefly explored with LLM "explorer" in Appendix A.5 but not robust).

3. **URL-centric dynamics advantage may not generalize.** A key mechanism — "navigate directly to page X via its URL" — is specific to web environments. In embodied navigation, code generation, or open-ended dialogue, equivalent "teleport" mechanics may not exist.

4. **Cold-start in online setting.** The buffer starts empty. Early tasks receive no benefit. Performance only improves as the buffer accumulates, meaning the online setting underperforms offline for small task sets.

5. **Context window pressure.** The buffer grows unboundedly. The retrieval module (k=5 dynamics + k=5 skills) caps token usage per task, but the retrieval prompt itself must contain ALL experiences, which scales poorly with long-running agents.

6. **Performance still far below human.** 36.7% on WebArena vs 78.24% human. The gap is enormous; CER is a useful boost but not a solution to the core web agent capability problem.

7. **Weaker model degradation.** Llama-3.1-70B shows only +26.5% relative improvement vs GPT-4o's +51%, because weaker models struggle with both the distillation output format and the complex action spaces of WebArena.

## 6. Transfer to Lyra

**The ONE transferable idea:** Context-window-based experience replay using **structured, dual-channel memory (dynamics + skills distilled from agent trajectories)** that is retrieved and replayed directly in the prompt without any training or embeddings infrastructure.

**How it maps to Lyra:** Lyra is a multi-turn conversational/agentic system that operates over many user interactions. Like CER's web agent, Lyra accumulates trajectory data from each session. CER's pattern of (a) distilling abstract, reusable "dynamics" (what state we're in, what's available) and "skills" (what to do, step-by-step) from raw trajectories, (b) storing them in a grow-only buffer with redundancy checks, and (c) retrieving top-k relevant items per task using the LLM itself as the retriever — this can be directly applied to Lyra's memory/context subsystems. Instead of web page states, "dynamics" would describe conversation states or tool states; "skills" would capture effective conversational patterns or tool-use sequences.

**Workstream route:** §4.2 (Memory) — CER is fundamentally a memory architecture: dynamic buffer + dual-channel distillation (dynamics/skills) + retrieval-then-replay. It directly addresses Lyra's need for cross-session learning without fine-tuning.

**Impact:** 4 — directly applicable pattern; training-free; uses only prompting; addresses a core Lyra gap (accumulating and reusing experience across sessions).

**Effort:** 2 — no new infrastructure needed. Requires prompt design for (a) trajectory distillation into dynamics+skills, (b) retrieval from buffer given current task, (c) buffer merge with redundancy avoidance. All implementable as prompt templates around existing LLM calls.

**Tier:** **Breakthrough** — This is a novel, training-free self-improvement mechanism that could significantly differentiate Lyra from other agent frameworks. The dual-channel (dynamics + skills) memory architecture is the key insight that goes beyond simple "store and retrieve past conversations."
