## 1. Mechanism (step-by-step)

SpreadsheetAgent is a **two-stage multi-agent framework** that reads spreadsheets incrementally through localized region inputs in multiple formats, avoiding the need to load entire spreadsheets into an LLM context window.

### Stage 1: Structure Extraction

The **Extraction Agent** drives exploration of the spreadsheet. It orchestrates three specialized tool agents:

**Tool A — Code Execution:** The agent writes and executes Python code (pandas, openpyxl) to read raw values, perform numerical computations, and programmatically parse the spreadsheet. This provides exact arithmetic results that text-based reasoning cannot match.

**Tool B — Vision Range Description Agent:** Given a selected cell range, the system renders it as an image snapshot. A VLM (GLM-4.5V) is prompted with the image + a question to extract semantic information from visual cues: font colors, shaded cells, borders, chart elements, and other formatting-based semantics.

**Tool C — LaTeX Range Description Agent:** Given a selected cell range, the system converts it to a LaTeX table (via code). An LLM (Qwen3-Coder-480B) is prompted with the LaTeX representation + a question to recover structural information: hierarchical headers, merged cells (`\multicolumn`, `\multirow`), alignment, and multi-level nesting.

The Extraction Agent assembles these outputs into a **YAML intermediate representation** that captures:
- Table metadata (sheet name, table name, ranges)
- Hierarchical row and column header trees (each node has `start_index`, `end_index`, `value`, `children`)
- Data properties per column (type, unit, format: bold/italic/currency)
- Notes and footnotes

### Stage 2: Verification Module

Rather than generating interpretations from scratch, the Verification Agent **checks** whether the extraction is correct — a task the authors argue is inherently easier and more reliable than solving.

Two verification sub-agents operate in parallel:

**Vision Verification Agent:** Converts selected regions to images, queries the VLM to check whether the extracted YAML schema matches the visual layout. Detects missing merged cells, misinterpreted colors, or overlooked chart elements. Reports discrepancies with suggested corrections.

**LaTeX Verification Agent:** Renders selected regions as LaTeX tables, prompts the LLM to verify structural fidelity. Cross-checks hierarchical headers, multi-column/row spans, and alignment against the YAML extraction. Flags inconsistencies with revision proposals.

### Iterative Loop (Algorithm 1)

```
Input: Spreadsheet S
Output: Verified structural representation Y*

C ← {S, Prompt, Tool interfaces}, Y ← ∅, Y* ← ∅
repeat
    while agent invokes a tool do
        Select tool T ∈ {Code, Vision, LaTeX} and parameters P
        O ← T(S, P); Append O to context C
    end
    Y ← final extraction from C
    vision_pass, latex_pass ← false, false

    // Vision verification
    Cv ← {S, Y, Verify prompt, Vision interfaces}
    while vision agent invokes vision tool do
        Rv ← VisionTool(S, Pv); Append Rv to Cv
    end
    vision_pass, Δv ← parse_verification(Cv output)

    // LaTeX verification
    Cl ← {S, Y, Verify prompt, LaTeX interfaces}
    while latex agent invokes latex tool do
        Rl ← LaTeXTool(S, Pl); Append Rl to Cl
    end
    latex_pass, Δl ← parse_verification(Cl output)

    if vision_pass AND latex_pass then
        Y* ← Y; break
    else
        Append corrections Δv, Δl to C  // feedback loop
    end
until verification succeeds OR max_iterations reached
return Y*
```

The verified YAML is then injected into the context for downstream task-driven reasoning (QA, formula writing, etc.).

**Implementation details:**
- VLM: GLM-4.5V (vision conversion + vision verification)
- LLM: Qwen3-Coder-480B-A35B (main model, LaTeX conversion, LaTeX verification)
- Inference: vLLM with greedy decoding (temperature=0, top-p=1)
- Context budget: 4K tokens per round, max 20 tool-call rounds
- Hardware: 8× NVIDIA H800 GPUs with tensor parallelism + expert parallelism

## 3. Trade-offs

| Win | Lose |
|-----|------|
| Captures visual/layout semantics (colors, borders, merged cells) that text-only approaches miss | ~97s latency per spreadsheet for extraction alone |
| Handles massive spreadsheets via incremental 4K-token rounds — no context overflow | 19.54 agent calls per spreadsheet = high API cost with commercial models |
| Consistent gains across all model scales (20B through 480B) | Requires VLM that supports BOTH image input AND function calling (GLM-4.5V) — scarce model type |
| Verification-as-checking reliably catches errors that generation would miss | Diminishing returns on strong backbones with LaTeX-only tables (marginal gains on Qwen2.5-72B) |
| Outperforms TreeThinker (header-only) by leveraging broader spreadsheet cues | No single-pass mode — always pays iterative cost even for simple spreadsheets |
| Structured YAML output reduces ambiguity and stabilizes downstream parsing | Extractor must be at least as strong as reasoner — weak extractors provide noisy structural cues that are ignored |

## 4. Design Rationale

**Why multi-format?** Each format captures complementary semantics: code execution provides exact numerical computation, vision captures formatting-based cues (colors, borders, shading), and LaTeX preserves hierarchical structure (merged cells, multi-level headers). No single format covers all spreadsheet phenomena.

**Why verification-as-checking?** The authors explicitly argue that "verification is often easier than direct problem solving" — checking whether an existing extraction is correct is more reliable than generating a complete interpretation from scratch. This is a well-established principle in AI (e.g., N-contrast decoding, self-consistency) applied to structured data.

**Why iterative extraction-verification?** A single-pass extraction risks error propagation; the iterative loop lets corrections feed back into the extraction process. The localized region strategy keeps context budgets tight (4K tokens/round) while still building comprehensive understanding.

**Why YAML intermediate representation?** Empirically, structured YAML reduces ambiguity and stabilizes parsing compared to free-form text or even JSON (Table 2 shows both YAML and JSON outperform unstructured output). YAML captures nested hierarchies naturally (header trees).

## 5. Limitations & Failure Modes

1. **Model dependency bottleneck:** The framework critically depends on VLMs that simultaneously support multimodal inputs (images) and function calls. Such models (GLM-4.5V) are scarce in open-source, limiting reproducibility and adoption.

2. **No distillation pathway:** The paper does not investigate transferring reasoning traces from large extractor models to smaller ones. Without large-scale realistic spreadsheet datasets for distillation, smaller models cannot inherit the capabilities.

3. **Extractor-reasoner asymmetry:** If the extractor is weaker than the reasoner (e.g., Qwen3-30B extractor with GPT-OSS-20B reasoner), the structural sketches provide noisy cues that the reasoner largely ignores — gains are minimal.

4. **Diminishing returns on simple tables:** When tables are small enough to fit in context as LaTeX (RealHiT), strong backbones (Llama3.3-70B, Qwen2.5-72B) show marginal or slightly negative gains from the framework overhead.

5. **20-round tool-call limit:** The hard cap on tool-call rounds could truncate extraction-verification on extremely complex multi-sheet spreadsheets with many hierarchical levels.

6. **No adaptive region selection strategy:** Region selection is currently agent-driven but not optimized — future work is needed on adaptive strategies for tool invocation and region selection.

## 6. Transfer to Lyra

**The ONE transferable idea:** The **extraction-verification feedback loop** with multi-format tool agents. SpreadsheetAgent demonstrates that pairing a generation/extraction agent with a verification agent (where verification = "checking" not "solving") in an iterative loop, mediated through multiple format-specific tools, yields consistent accuracy gains. The key insight is that verification is structurally easier than generation, and errors caught by verification can be fed back as correction signals to improve the extraction.

For Lyra, this pattern generalizes beyond spreadsheets: any structured data extraction task (PDF tables, code structure analysis, configuration parsing, API response validation) could benefit from an extract-then-verify loop where a verification agent cross-checks outputs against the source using alternative representations (e.g., rendered views, serialized formats, programmatic checks).

**Workstream route:** §4.2 (Context/Reasoning) — the pattern directly addresses how Lyra incrementally builds and verifies its understanding of large structured inputs without exceeding context limits.
