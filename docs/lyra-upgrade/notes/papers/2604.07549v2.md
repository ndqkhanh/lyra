**Venue:** arXiv:2604.07549v2 [cs.CL], April 2026

**Code:** https://uva-dsa.github.io/EMSDialog

## 1. Mechanism (step-by-step)

EMSDialog is a 5-module, 3-LLM-agent synthetic dialogue generation pipeline grounded in ePCR (Electronic Patient Care Report) data. It uses iterative critique-and-refine loops enforced by deterministic rule-based checkers.

### Module 1: Extractor
- Parses structured ePCR fields (Chief Complaint, HPI, vitals, interventions) via regex + MedSpaCy with QuickUMLS for clinical NER.
- Extracts a concept set `P_src` that must be preserved through all downstream LLM stages.
- Branch-determining features (e.g., GCS score) extracted to steer topic flow: GCS <= 8 triggers Primary Assessment branch; GCS > 8 triggers HPI/Pain Assessment branch.

### Module 2: Checkers (3 independent verifiers)
- **Concept Checker (rule-based):** Extracts concepts from generated Plan/Dialogue (`P_tgt`) using the same MedSpaCy pipeline. Performs two-stage matching:
  - *Syntactic matching:* exact string match between `P_src` and `P_tgt`.
  - *Semantic matching:* cosine similarity via GatorTron embeddings with threshold >= 0.8.
  - Labels concepts as *missing* (FN) or *hallucinated* (FP). Plan/Generator cannot proceed until both error counts reach zero.
- **Topic Flow Checker (rule-based):** Directed graph `G = (V, E)` over EMS topic ontology. Adjacency list `A = {current: [allowed_next]}`. For each utterance pair `(t_i, t_{i+1})`, checks `t_{i+1} in A[t_i]`. Flags transition errors and hallucinated topics.
- **Style Checker (LLM judge):** Qwen3-235B or Llama-3.3-70B evaluates dialogue against an EMS-expert-authored rubric of 17 domain-specific rules (e.g., "show don't tell" behaviors, proper role-utterance patterns, neutral non-assumptive questioning). Returns structured critique with concrete revisions or a PASS.

### Module 3: Planner (LLM Agent)
- Given ePCR + topic flow + extracted concepts, produces a plan as sequence of `(topic, evidence)` tuples, where evidence cites specific ePCR fields.
- Validated by Concept Checker and Topic Flow Checker.
- Iterates until zero concept/topic errors. Mean iterations to converge: 4.3.

### Module 4: Generator (LLM Agent)
- Given validated plan + ePCR evidence, produces initial dialogue draft with utterances and role assignments (medic, partner, patient, bystanders).
- Validated by all three checkers. Iterates until concept + topic flow constraints satisfied.

### Module 5: Refiner (LLM Agent)
- Edits Generator output for coherent turn-taking, natural phrasing, clinically plausible actions.
- Uses expert rubrics + real EMS exemplars to guide style improvements.
- Checked again by Concept Checker, Topic Flow Checker, and Style Checker.
- Runs at most 5 iterations or terminates early on all-pass.
- Addresses "tell vs. show" anti-pattern: replaces declarative patient descriptions with behaviorally-evidenced dialogue (e.g., replaces "patient is combative" with patient shouting/resisting).

### Downstream Conversational Diagnosis Prediction
- At each turn `t`, given prefix `X_t = (u_1, ..., u_t)`, model produces probability `p_t(l)` for each class `l in L` (43 diagnoses).
- Commit threshold `tau = 0.5`: predict `Y_hat_t = {l: p_t(l) >= tau}`. Empty set = defer.
- Two training strategies: **Static** (full dialogue prefix, learns from aggregated context) vs. **Dynamic** (unrolls last K prefixes, trained on partial evidence).
- All models fine-tuned with LoRA, Qwen3-0.6B/4B, 80:20 train-val split.

### Ablation: Module Contributions (Last Acc / Edit OH)
- Generate only: baseline
- +Plan: +38.4% logical structure improvement
- +Refine: further realism + diversity gains
- +Check: **largest factuality gain** (delta P/R: +5.7%/+15.6%), groundedness +12.7%

## 3. Trade-offs

| Win | Lose |
|-----|------|
| Rule-based checkers enforce zero-tolerance on concept errors and topic flow violations | Mean 4.3 iterations per stage = high token/compute cost per dialogue |
| 5-module pipeline (Extractor + 3 agents + Checkers) produces highest factuality (P: 93.70%) | Diversity (Self-BLEU: 53.08%) worse than simple 0-shot (40.36%) -- templates constrain variety |
| Hybrid verification (deterministic rules + LLM judge) catches both structural and stylistic errors | Style Checker precision only 77.02%; 56.9% of its critiques are false positives |
| Dynamic training reduces edit overheads by 40%+ vs static training | Dynamic training data inflation: each dialogue unrolled into K instances |
| EMSDialog+Real combined training yields strongest downstream performance | Training increases model conservativeness -- reduced earliness vs. no-train |
| Domain-specific pipeline generalizes to any EHR-grounded domain | Only validated on single U.S. regional EMS dataset; demographic/label bias inherited from source ePCRs |
| Local execution on A100 GPUs preserves privacy | Qwen3-32B generation is GPU-intensive; LLM judges (235B/70B) add evaluation cost |

## 4. Design Rationale

The authors argue that **pure LLM generation** (single-agent, even with rules in prompts) cannot reliably enforce clinical factuality because LLMs have no ground-truth binding mechanism. Prior multi-agent approaches (e.g., NoteChat) use unverified LLM-based refinement -- the LLM is both generator and judge of its own work, creating a self-approval loop.

Their key architectural decision: **separate verifier from generator** by making the Concept Checker and Topic Flow Checker fully deterministic (regex + graph traversal + embedding match). This gives a hard rejection signal the LLM agents must satisfy before proceeding. The Style Checker remains LLM-based but is non-blocking (soft constraint), acknowledging that style is subjective.

The iterative `repeat-until-pass` design is borrowed from Self-Refine (Madaan et al., 2023), but critically, the stopping criterion is **external** (checker pass/fail) not self-evaluation.

The topic-flow graph design was driven by real EMS operational protocols (NREMT skill sheets, ODEMSA guidelines), providing procedural realism absent from generic medical dialogue synthesis.

## 5. Limitations & Failure Modes

1. **NER Extractor bottleneck:** Precision 74.26%, Recall 62.29% on 43-scenario subset. Omission errors in concept extraction artificially depress measured factuality recall and can cause the pipeline to miss concepts that should be in dialogue.

2. **Style Checker noise:** 77.02% precision; 56.9% of errors are false positives (valid rule, no actual violation). 15.8% are fabricated rules not in the expert rubric. This means the Refiner receives incorrect critiques on ~23% of checks.

3. **Single-domain validation:** Only tested on one U.S. regional EMS ePCR dataset (2017-2020). No evidence it generalizes to other medical specialties or EHR systems.

4. **Evaluation bottleneck:** Human expert verified only 43/4,414 dialogues (0.97%). Remaining 99% evaluated by LLM judges, which may miss subtle clinical errors.

5. **Inherited ePCR bias:** Imbalanced diagnosis labels, demographic skew, and clinical incompleteness in source ePCRs propagate into synthetic dialogues. Models trained on this data could produce unsafe recommendations without rigorous validation.

6. **Privacy risk:** Despite de-identification of source ePCRs, LLM memorization could reintroduce PII in generated dialogues when applied to new EHR sources.

7. **No multi-turn interaction evaluation:** Pipeline generates static dialogue scripts. Does not model or evaluate interactive agent-patient conversation where agent actions change the information trajectory.

## 6. Transfer to Lyra

**The ONE transferable idea:** The **deterministic-rule-checker + LLM-generator iterative refinement loop with external stopping criteria** -- a pattern where LLM agents generate content but a non-LLM verifier enforces hard constraints (concept coverage via NER + embedding match, topic/flow validity via graph traversal). This decouples generation quality from verification correctness, preventing self-approval loops.

**Workstream:** Section 4.2 (Synthetic Data Generation & Augmentation pipelines). This pattern directly applies to Lyra's need for generating high-quality, factually-grounded synthetic multi-turn agent interaction traces for training and evaluation. The "separate deterministic verifier from LLM generator" architecture is a reusable design pattern for any Lyra subsystem that synthesizes training data from structured source records.

**Impact:** 4 (directly enables high-quality synthetic training data generation with factuality guarantees; the checker-generator separation is a general architectural pattern for reliable agent behavior)
**Effort:** 3 (requires implementing domain-specific concept extractor + flow graph + embedding matching layer; core loop is template-able)
**Tier:** breakthrough (the deterministic-verifier-separated-from-LLM-generator pattern is novel, rigorously ablated, and directly applicable to Lyra's data generation and agent verification needs)
