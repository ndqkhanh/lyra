## 1. Mechanism (step-by-step)

### Problem Formulation: Proactive Agent Planning
Given an initial user instruction q0 with T vague or unfeasible details D = {d1, ..., dT}, the agent must perform three subtasks:
1. **Clarification Need Prediction & Question Generation**: Predict binary bt for whether clarification is needed; if yes, generate question at for detail dt
2. **Tool Learning**: Generate complete interaction chain Eti-1 = {f1, o1, ..., fi-1, oi-1} (function calls + observations)
3. **Agent Planning**: Generate valid JSON plan from final conversation CT and interaction ET

### CEP Framework Architecture
Three specialized agents in a pipeline:

```
User Instruction → [Clarification Agent] → [Execution Agent] → [Planning Agent] → Plan Output
                       ↑                        |
                       └─── observation ────────┘
```

**Agent 1: Clarification Agent**
- Input: conversation history Ct-1 + last interaction Et-1
- Output: (1) binary need-prediction bt, (2) clarification question at if bt=True
- Prompt template: `[f_prompt(Ct-1, Et-1, bt), at[bt=1]]`

**Agent 2: Execution Agent** (two modes)
- **Static**: Generates full interaction chain Et in one forward pass. Sequence: `[f_prompt(Ct), Et]`
- **Dynamic**: Step-by-step ReAct loop. Generates one action fi per step: `fi = LLM(Ct, Et_{i-1}, Rt_i)`

**Agent 3: Planning Agent**
- Takes clarified conversation CT + execution interaction ET
- Produces JSON travel plan with fields: day, current_city, transportation, breakfast, attraction, lunch, dinner, accommodation

### Key Technical Innovations

**A. Trajectory Tuning** (for clarification + static execution agents)
- Fine-tune on sampled trajectories (Ct-1, Et-1) with topological ordering of details
- Training objective: autoregressive next-token prediction across all T turns
- `L = max_θ (1/|T|) Σ_{t=1}^{T} Σ_{i=1}^{N_t} log P_θ(x_{t,i} | x_{t,<i})`

**B. Memory Recollection** (for dynamic execution agent)
- Addresses redundant self-reflection in multi-turn Reflexion
- Memory bank Rt stores rationales from failed tool calls across turns
- Key insight: Rt+1 = Rt (carries forward) because Ct shares common clarified details across turns
- Reduces number of generated rationales from Σ|Rt| to max|Rt| = |RT| (linear → constant time complexity)

**C. Dependency Graph + Topological Sort**
- Indefinite details have dependencies (e.g., Origin before Destination, Budget depends on Accommodation + Transportation)
- Topological sort determines priority order for clarification
- Same-priority details addressed randomly

### Dataset Construction: Ask-before-Plan
- Built on TravelPlanner benchmark (Xie et al., 2024)
- 1,000 train + 1,000 test samples with 2,800 dialogue turns each
- Two-phase construction:
  1. **Indefinite Detail Formation**: Creates under-specified (missing: origin, destination, departure date, duration, people, budget) and over-specified (unfeasible: accommodation, cuisine, transportation, destination, budget) instructions
  2. **Proactive Conversation Generation**: GPT-3.5 simulates user-agent conversations with quality control (87.2% human pass rate)
- Detail distribution: 10% zero indefinite, 30% each for 1/2/3 indefinite details
- Difficulty levels: Easy (348/331), Medium (333/336), Hard (319/333) for test/train

## 3. Trade-offs

| Win | Lose |
|-----|------|
| CEP (LLaMA-3-8B) achieves 99.4% clarification accuracy — near-perfect need prediction | Final plan pass rate only 1% even with perfect clarification — planning bottleneck remains |
| Trajectory tuning on 7B/8B models beats GPT-3.5 prompting by 2-3x on clarification | Requires task-specific fine-tuning data; does not generalize zero-shot |
| Static execution (89% pass rate) far outperforms dynamic execution (~0% pass rate) | Static requires all parameters known upfront; cannot handle incremental discovery |
| Memory Recollection reduces inference time ~17% (GPT-3.5) and steps ~32% (Mistral-7B) | Memory Recollection degrades Mistral-7B performance (context > 8K causes reasoning drops) |
| Multi-agent decomposition enables specialized training per subtask | Communication overhead: 3 separate inference passes per turn |
| Clarification adds only 5.4s per sample (~27% of total runtime) | Without clarification, final pass rate drops to 0% — clarification is mandatory not optional |
| LLaMA-3-8B consistently outperforms Mistral-7B across all tasks | Cannot test larger models (>8B) due to compute constraints; scaling behavior unknown |
| GPT-3.5 produces fewer syntax errors in dynamic setting | Mistral-7B produces higher-quality actions when syntax is correct |

## 4. Design Rationale

**Why multi-agent decomposition?** Single-agent approaches (Direct, ReAct, Reflexion) all fail because LLMs cannot simultaneously clarify ambiguity, execute tools correctly, and plan coherently in long-context settings. The authors observe that Proactive (GPT-3.5) over-clarifies everything while ProCoT (GPT-3.5) under-clarifies and rushes to execute — a single agent cannot calibrate. Separating into clarification, execution, and planning agents allows each to be specialized and independently optimized via trajectory tuning.

**Why trajectory tuning instead of prompting?** Even with well-crafted prompts and in-context examples, GPT-3.5 achieves only 47% clarification accuracy with environment+conversation. Fine-tuning on domain-specific trajectories (conversation history + tool interaction chains) gives 7B/8B models 2x the performance of prompted GPT-3.5.

**Why Memory Recollection over standard Reflexion?** In multi-turn clarification dialogues, the execution agent encounters the same tool-call exceptions repeatedly across turns. Standard Reflexion regenerates rationales each time (linear time complexity). Memory Recollection stores and reuses rationales (constant time complexity), preventing the LLM from repeating mistakes while reducing inference cost.

**Why topological ordering?** Indefinite details have dependencies (e.g., you cannot estimate budget without knowing accommodation and transportation). Naively asking about any missing detail can create dead ends. Topological sort ensures clarification proceeds in a feasible order based on the dependency DAG.

## 5. Limitations & Failure Modes

1. **Static user simulation**: Evaluation uses pre-generated user responses (GPT-3.5 simulated), not real-time interactive users. The 87.2% human pass rate on simulation quality leaves 12.8% of data potentially flawed. Real-time user simulation could expose brittleness in question generation.

2. **Single-domain evaluation**: Only tested on travel planning (TravelPlanner derivative). No evidence the CEP architecture transfers to other domains (web navigation, shopping, medical). The tool set is small (6 functions) and domain-specific.

3. **Compute-constrained model selection**: Cannot evaluate models larger than 8B parameters. LLaMA-3-8B's advantage over Mistral-7B suggests scaling trend, but cannot confirm. GPT-3.5 is the only closed-source model tested (no GPT-4 comparison).

4. **Planning remains unsolved**: Even with 99.4% clarification accuracy and 100% well-formed execution, the final plan pass rate is only 1% (1/1000 plans valid). The planning agent (Direct GPT-3.5) is the weakest link. Hard constraints (budget, accommodation type, cuisine, transportation) are rarely all satisfied simultaneously.

5. **Context length fragility**: Mistral-7B performance degrades when context exceeds 8K tokens. Memory Recollection helps GPT-3.5 but hurts Mistral-7B. Long-context robustness is model-dependent and not solved.

6. **No agent cooperation exploration**: Despite being multi-agent, each agent operates sequentially rather than cooperatively. The paper acknowledges that "cooperation and division of labor among different LLM-based agents" is not thoroughly explored.

7. **Clarification question quality**: Rule-based score only reaches 55.8% and GPT Score 85.8% (LLaMA-3-8B). Questions are keyword-matched, not semantically evaluated for naturalness or user experience.

8. **Simulated conversation artifacts**: GPT-3.5-generated dialogues may contain patterns that fine-tuned models exploit (benchmark overfitting risk). The 87.2% quality control pass rate means ~13% of test examples may have unnatural dialogue patterns.

## 6. Transfer to Lyra

### The One Transferable Idea

**Proactive Clarification-as-Gate before Execution**: The core insight is that ambiguous user intent kills downstream task success — without clarification, final plan pass rate is 0% vs 1% with it. For Lyra, implement a lightweight **Clarification Need Predictor** that gates the execution pipeline: before any tool call or plan generation, a small fine-tuned model (or prompted classifier) checks whether the user's instruction has all required parameters. If not, it generates a single targeted clarification question. This is not full CEP — it is the minimal viable "ask-before-plan" pattern: *predict need → ask one question → collect answer → proceed*. The trajectory tuning approach (fine-tuning on conversation+interaction pairs) could be applied to Lyra's own task domains.

### Workstream Route: §4.3 (Agent Harness)

This feeds directly into Lyra's agent harness architecture — specifically the pre-execution intent disambiguation layer. The CEP pattern maps to Lyra's multi-agent pipeline where a clarification sub-agent validates instruction completeness before routing to domain-specific executors.

| Dimension | Rating |
|-----------|--------|
| **Impact** | 4 — Fixes a fundamental failure mode (ambiguous instructions → zero success rate). The clarification-gate pattern is domain-agnostic and lightweight. |
| **Effort** | 3 — Requires (a) building a clarification-need classifier for Lyra's tool schemas, (b) generating clarification training data for Lyra domains, (c) integrating into existing agent pipeline. No new infrastructure needed. |
| **Tier** | **Breakthrough** — The finding that *without clarification, planning success is 0%* is a strong signal that Lyra must have this capability. The CEP architecture provides a proven design template. |
