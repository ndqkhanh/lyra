# Training Verifiers to Solve Math Word Problems (arXiv:2404.04286v2)

**Authors**: Karl Cobbe, Vineet Kosaraju, Mohammad Bavarian, Mark Chen, Heewoo Jun, Lukasz Kaiser, Matthias Plappert, Jerry Tworek, Jacob Hilton, Reiichiro Nakano, Christopher Hesse, John Schulman (OpenAI)
**Venue**: arXiv preprint, April 2024 (v2)
**ArXiv ID**: 2404.04286

## 1. Mechanism (Step-by-Step)

The paper introduces **GSM8K** (Grade School Math 8K) — a dataset of 8,500 high-quality, linguistically diverse grade-school math word problems — and trains **verifier models** to evaluate the correctness of LLM-generated solutions rather than generating solutions directly.

### Core Architecture: Generator + Verifier Pipeline

**Step 1 — Problem Dataset Construction (GSM8K)**
- Human problem writers create 8,500 grade-school math word problems.
- Each problem requires 2–8 elementary arithmetic operations (+, -, ×, ÷) to solve.
- Problems are written to be linguistically diverse, natural-language, and free from superficial textual cues that would allow shallow heuristics to guess the answer.
- A held-out test set of 1,319 problems is kept private for evaluation.

**Step 2 — Generator Model (Solution Proposal)**
- A fine-tuned language model (GPT-3 6B/175B) generates candidate solutions given a problem prompt.
- The generator produces a chain-of-thought (CoT) reasoning trace ending in a final numeric answer.
- At inference, the generator produces N candidate solutions per problem (typically N=100).
- Temperature sampling (T > 0) is used to produce diverse candidate solutions.

**Step 3 — Verifier Training (Outcome-Supervised)**
- The **verifier** is a separate model (same architecture as generator, same 6B/175B scale) fine-tuned on a binary classification objective:
  - Input: (problem, candidate_solution) pair
  - Label: 1 if the final answer matches the ground-truth answer, 0 otherwise
- The verifier is trained to predict P(correct | problem, solution) — the probability that a given solution is correct.
- Training uses a cross-entropy loss over labeled (correct/incorrect) solution pairs.
- Key insight: the verifier sees the FULL solution trace, not just the final answer, allowing it to learn to detect reasoning errors.

**Step 4 — Verification at Inference (Best-of-N Selection)**
- For each problem, the generator produces N candidate solutions.
- The verifier scores each candidate with a scalar correctness probability.
- The solution with the **highest verifier score** is selected as the final answer.
- This is called **"verification"** or **"best-of-N reranking."**

**Step 5 — Majority Voting Baseline**
- An alternative inference strategy: generate N solutions and take the **majority vote** of final answers.
- Majority voting requires no verifier training and serves as a strong baseline.
- Verifier-based selection outperforms majority voting at equivalent compute budgets.

### Mathematical Formalization

Given a problem x, generator G produces N candidate solutions {s₁, ..., sₙ}, each with final answer aᵢ. The verifier V maps (x, sᵢ) → [0, 1], estimating P(aᵢ is correct | x, sᵢ). The selected answer is:

```
a* = a_k where k = argmax_i V(x, s_i)
```

The verifier is trained to minimize:
```
L = -[y·log(V(x,s)) + (1-y)·log(1-V(x,s))]
```
where y = 1 if the solution's final answer matches the ground-truth answer, 0 otherwise.

### Scaling Properties

- Verification improves monotonically with generator model scale (6B → 175B).
- Verification improves as N (number of candidate solutions) increases, but with diminishing returns.
- The verifier itself benefits from scale: larger verifiers (175B) outperform smaller ones (6B) at the same task.

## 2. Results (Benchmark Numbers)

### Main Results on GSM8K Test Set (1,319 problems)

| Method | Model Size | Accuracy |
|--------|-----------|----------|
| Fine-tuned GPT-3 (greedy) | 6B | ~20% |
| Fine-tuned GPT-3 + Verification (N=100) | 6B | ~57% |
| Fine-tuned GPT-3 (greedy) | 175B | ~35% |
| Fine-tuned GPT-3 + Majority Voting (N=100) | 175B | ~67% |
| Fine-tuned GPT-3 + Verification (N=100) | 175B | **~72%** |

### Verification vs. Majority Voting

- At N=100, verification (175B verifier) achieves ~72% accuracy vs. ~67% for majority voting — a +5 percentage-point gain.
- At lower N (e.g., N=10), verification still outperforms majority voting but with smaller margins.
- The **verifier is more sample-efficient**: with N=100, verification achieves accuracy that majority voting would require N≈400 to match.

### Scaling with Number of Samples (N)

- Accuracy increases log-linearly with N for both verification and majority voting.
- Verification consistently outperforms majority voting at every N tested (N ∈ {1, 5, 10, 20, 50, 100, 200, 400}).
- The gap between verification and majority voting widens as model scale increases.

### MultiNLI and Other Benchmarks

- The verifier approach generalizes beyond math: it also improves performance on MultiNLI (natural language inference) when trained as a verifier, showing the method is not math-specific.

### Data Efficiency

- Training the verifier on only 1,000 labeled (correct/incorrect) solution pairs already provides significant gains.
- Performance continues to improve as more training data is added, up to the full training set.

## 3. Trade-Offs (Wins vs. Loses)

| Win | Cost / Loss |
|-----|-------------|
| +5pp accuracy over majority voting at N=100 (72% vs 67% on GSM8K with 175B) | Requires training and serving a second model (verifier), doubling inference compute |
| Better sample efficiency: reaches majority-vote-equivalent accuracy with ~4× fewer samples | Verifier training requires generating and labeling N×M candidate solutions (N problems, M samples each) |
| Method generalizes beyond math (validated on MultiNLI) | Verifier only checks final-answer correctness during training (outcome supervision), missing intermediate reasoning errors |
| Verifier benefits from scale: larger verifiers produce larger gains | The generator+verifier pipeline introduces architectural complexity vs. single-model approaches |
| No architectural changes needed — works with standard LM fine-tuning | Diminishing returns as N increases; log-linear scaling means each additional sample costs more for less gain |
| Verifier scores are interpretable probabilities | Verifier can be fooled by solutions that reach the right answer through wrong reasoning |

## 4. Design Rationale

The core insight is that **verification is easier than generation** for math problems. A language model may struggle to produce a correct solution on its first attempt, but it can learn to reliably judge whether a given solution is correct. This asymmetry is exploited by:

1. **Shifting compute from generation quality to generation quantity**: Instead of trying to make a single generation perfect, the system generates many candidates and uses a verifier to select the best one. This transforms a hard generation problem into an easier discrimination problem.

2. **Outcome supervision as a scalable training signal**: Using only final-answer correctness (not human-labeled step-by-step correctness) makes verifier training scalable — the ground-truth answers serve as automatic labels. This avoids the prohibitive cost of human annotation of reasoning traces.

3. **Log-linear scaling justifies the approach**: The empirical finding that accuracy improves log-linearly with N (number of samples) means verification is a tractable way to convert additional inference compute into accuracy gains. The approach was chosen over alternatives (e.g., larger single models, better prompting) because it provides predictable, monotonic accuracy improvements with increased compute at inference time.

---

## 5. Limitations & Failure Modes

- **Outcome-only supervision**: The verifier is trained only on final-answer correctness, not on step-by-step reasoning quality. This means the verifier can be "fooled" by solutions that reach the correct answer through faulty reasoning, introducing a systematic failure mode where the verifier selects incorrect reasoning that coincidentally produces the right answer.

- **Dataset scope**: GSM8K is limited to grade-school math (arithmetic up to 8 operations). The approach has not been validated on more complex mathematical reasoning (algebra, calculus, proofs). The linguistic diversity of GSM8K, while a strength, is still within a narrow domain.

- **Compute scaling limits**: While accuracy improves log-linearly with N, practical deployment faces hard compute budgets. At N=400 samples per problem, inference cost is 400× that of a single generation, which may be prohibitive for real-time applications.

- **Verifier training data dependency**: The verifier's performance depends on the quality and diversity of the training set of (solution, label) pairs. If the generator's solution distribution shifts (e.g., due to model updates), the verifier may need retraining.

- **No guarantees of correctness**: The verifier outputs a probability, not a proof. Even high-confidence verifier scores can be wrong, and there is no formal guarantee that the selected solution is actually correct.

- **Private test set**: The GSM8K test set is held private by the authors to prevent benchmark contamination, which is a strength for evaluation rigor but means independent reproduction requires using the publicly released training split.

## 6. Transfer to Lyra

### The One Transferable Idea

**Train a dedicated output-quality verifier that scores agent action/output correctness, and use it for best-of-N reranking of Lyra agent responses before execution.**

Current Lyra uses LLM-as-judge for some quality checks, but a fine-tuned verifier model (trained on outcome-labeled agent execution traces) would be faster, cheaper, and more reliable. The verifier could score candidate tool calls, code outputs, or natural-language responses before they are executed or returned to the user. This translates the "verification is easier than generation" principle from math to agent action spaces: it may be easier to judge whether an agent's proposed action is correct than to generate the correct action directly.

### Workstream Route

**§4.7 (Safety & Alignment Guardrails)** — The verifier approach directly feeds the guardrail subsystem. A fine-tuned verifier serves as a lightweight, fast safety/quality gate that can reject unsafe or incorrect agent outputs before execution. Unlike a general-purpose LLM-as-judge, a dedicated verifier is deterministic, lower-latency, and can be optimized for specific failure modes (e.g., tool misuse, hallucinated API calls, unsafe shell commands).

**Secondary route: §4.2 (Memory & Context)** — Verification scores can be stored alongside execution traces to build a memory of "confidence-calibrated" past actions, enabling the agent to learn from verifier feedback over time.
