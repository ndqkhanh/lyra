# Full-Duplex-Bench-v3: Benchmarking Tool Use for Full-Duplex Voice Agents Under Real-World Disfluency

**Authors:** Guan-Ting Lin (National Taiwan University), Chen Chen (NVIDIA), Zhehuai Chen (NVIDIA), Hung-yi Lee (National Taiwan University)

**Venue:** arXiv:2604.04847v1 [eess.AS], 6 April 2026

**Demo:** https://daniellin94144.github.io/FDB-v3-demo/

---

## 1. Mechanism

FDB-v3 is a reproducible benchmark for evaluating real-time, full-duplex spoken language models on multi-step tool execution under naturalistic speech. The architecture operates as follows:

### 1.1 Benchmark Construction
- **Audio collection:** 100 recordings from 12 speakers (native + non-native English — Korean and Russian L1 backgrounds) using built-in microphones in uncontrolled environments. Each speaker was given detailed scenario contexts and asked to perform prompts organically. All audio captured with everyday built-in microphones (11 of 12 setups).
- **Trailing silence:** 30 seconds of each speaker's actual ambient environment is captured (not digital silence) to maintain coherent acoustic background for streaming evaluation.
- **Disfluency annotation:** Every recording is annotated across five categories:
  1. **Fillers** (e.g., "um," "uh") — tests whether redundant tokens degrade accuracy or inflate latency.
  2. **Pauses** (mid-utterance silences) — tests end-of-turn detection robustness.
  3. **Hesitations** (filler-repetition combinations) — compound disfluency handling.
  4. **False starts** (abandoning intent for a new one) — tests whether models discard obsolete context without hallucinating tool calls.
  5. **Self-corrections** (updating parameters mid-sentence, e.g., "to New York — actually, wait... make that Boston") — tests dynamic state rollback. **21 of 100 scenarios** specifically feature self-correction events.

### 1.2 Task Domains and Mock APIs
Four task domains with deterministic, zero-latency local mock APIs (Table 1):

| Domain | Mock API Functions |
|--------|-------------------|
| Travel & Identity | `search_flights(dest, date)`, `book_ticket(name, flight_id)`, `update_travel_profile(doc_type, doc_number)` |
| Finance & Billing | `query_card_benefits(card_last_4, category)`, `calculate_currency_exchange(amount, from, to)`, `modify_autopay_source(new_account_id)` |
| Housing & Location | `search_apartments(max_budget, amenities)`, `update_search_filter(condition, new_value)` |
| E-Commerce Support | `check_order_status(order_id)`, `cancel_pending_action(action_type)`, `process_exchange(order_id, new_shipping_address)` |

Mock APIs are locally executed with deterministic, zero-latency responses to isolate model reasoning and parameter-passing from confounds like network variability or service downtime. All expected outputs are fully deterministic, enabling automatic scoring.

### 1.3 Difficulty Tiers
- **Easy:** Single-step tool calls.
- **Medium:** Two-step chains with moderate ambiguity.
- **Hard:** Multi-step chains with conflicting constraints or self-corrections.

### 1.4 Evaluation Metrics (Multi-Dimensional)
**Accuracy metrics:**
- **Tool Selection F1:** F1 over expected vs. actual tool calls. Penalizes both missed calls (low recall) and hallucinated calls (low precision).
- **Argument Accuracy:** Semantic correctness of arguments evaluated by GPT-4o judge (accommodates date formats, abbreviations, dynamic references like `$RESULT_0.flights[0].flight_id`). Appendix A.1 provides the exact judge prompt.
- **Response Quality:** GPT-4o judge evaluating whether the spoken transcript fulfills user intent (Appendix A.2). Penalizes correct tool execution with poor relaying.
- **Pass@1:** Binary — agent must invoke exactly the expected tools AND score perfect argument accuracy on every call. Any single failure yields fail.

**Latency decomposition:**
- **First Response Latency:** Time until any speech (including filler like "Let me check on that").
- **Tool Call Latency:** Time until first API invocation.
- **Task Completion Latency:** Time until factual answer delivered. GPT-4o analyzes ASR chunks to isolate informational sentence from preceding filler (Appendix A.3).

**Turn-taking metrics:**
- **Turn-take Rate:** Fraction of turns with natural-timing response. Base latency Δt = t_agent_start - t_user_end.
- **Interruption Rate:** Fraction where Δt < 0 (agent begins speaking before user finishes).
- **Filler Rate:** Fraction of responses containing content-free filler sentences before substantive response.

### 1.5 Models Evaluated (All via LiveKit Realtime Voice Agent Framework)
Six configurations — five end-to-end speech-to-speech models plus one modular pipeline:
- GPT-Realtime (OpenAI)
- Gemini Live 2.5 (Google)
- Gemini Live 3.1 (Google)
- Grok (xAI)
- Ultravox v0.7 (Fixie AI — open-weight, Whisper encoder + pretrained backbone)
- Cascaded baseline: Whisper → GPT-4o → OpenAI TTS

All receive identical audio input. GPT-4o serves as the LLM judge for argument accuracy, response quality, and key-information identification.

Ultravox's inverted profile: fastest first-word (3.88s) but slowest tool-call (6.01s) — it speaks before calling tools (88% filler rate). Grok has fastest tool-call latency (0.63s) due to pre-emptive tool invocation.

### 2.6 Key Qualitative Finding: "Silent Worker" Phenomenon (Gemini Live 3.1)
Gemini Live 3.1 produced no speech in 22% of examples (78.0% turn-take). Crucially, 86% of silent cases still executed tool calls — the model invoked APIs but never generated speech. Three of these achieved perfect tool selection and argument accuracy, costing potential Pass@1 improvement. Concentrated in harder scenarios: 0% of easy, 23.5% of medium, 46.7% of hard.

### 2.7 Pre-emptive Tool Call Rates
Grok 41.6%, Ultravox 23.2%, Gemini Live 2.5 17.9%, Gemini Live 3.1 16.9%, GPT-Realtime 10.8%. Pre-emptive tool-call rates do NOT predict interruption rates — Grok processes tools silently while letting users finish, while Ultravox interrupts through premature speech, not premature tool invocation.

## 3. Trade-offs

| Dimension | Win | Loss |
|-----------|-----|------|
| **End-to-end vs. Cascaded** | E2E 2.4× faster (4.25s vs 10.12s), concurrent processing | Cascaded guarantees 100% turn-take; E2E models can silently fail (Gemini 3.1: 78%) |
| **Speed vs. Accuracy (Gemini 3.1)** | Fastest overall (4.25s), competitive Pass@1 (0.540) | Silent worker in 22% of turns — executed tools but produced zero speech |
| **Filler strategy vs. Interruption (Ultravox)** | Fastest first-word latency (3.88s), ties best turn-take (96%) | 88% filler rate causes 47.9% interruption — speaks over users |
| **Pre-emptive tool calls vs. State rollback** | Enables 2× faster multi-step chains (Gemini 3.1: 3.92s vs GPT: 9.20s on Case 1) | Locks in stale parameters when user corrects mid-utterance (Gemini 3.1 self-corr: 0.353 vs GPT: 0.588) |
| **ASR pipeline reliability vs. Error propagation** | Cascaded 100% turn-take, perfect engagement | Cascaded self-correction Pass@1 only 0.176 — Whisper finalizes before correction arrives |
| **Single-modal optimization** | GPT-Realtime leads on accuracy (0.600) and interrupt avoidance (13.5%) | Even the leader fails >40% of self-correction scenarios |

## 4. Design Rationale

1. **Real human audio over TTS:** Prior benchmarks used synthetic speech, which strips away natural disfluencies that are the primary cause of real-world tool-call failures. The authors argue TTS cannot replicate the acoustic variability, accent range, or spontaneous disfluency patterns of humans in uncontrolled environments.

2. **Mock APIs with zero latency:** By eliminating real API latency, server variance, and network jitter, the benchmark isolates the model's own reasoning and parameter-passing overhead. This makes latency measurements directly comparable across models running on different infrastructure.

3. **Multi-dimensional evaluation (accuracy + latency + turn-taking):** The authors deliberately avoid a single leaderboard score because optimizing any single axis (e.g., speed) produces pathological behavior on others (e.g., "silent worker" pattern). The three-axis framework forces model designers to confront trade-offs explicitly.

4. **Deterministic outputs enable automatic scoring:** Unlike open-ended dialogue evaluation, every mock API produces exactly one correct output, eliminating inter-annotator variance in scoring.

5. **21 dedicated self-correction scenarios:** The benchmark explicitly stresses state-rollback because real users frequently change their minds mid-utterance, and no existing voice benchmark tested this systematically.

## 5. Limitations & Failure Modes

1. **Single-region server evaluation:** All cloud-based model evaluations were executed from a single fixed server region with high-bandwidth connections. Measured latencies for proprietary models inherently include non-deterministic network overhead and varying server-side load — latency numbers may not replicate.

2. **No real-API failure testing:** Zero-latency local mock APIs isolate reasoning but do not test robustness to real-world anomalies — API timeouts, HTTP 403/429/500 errors, malformed response payloads, or rate-limiting scenarios.

3. **Limited demographic coverage:** 100 recordings from 12 speakers (Korean, Russian L1 English). No coverage of tonal-language L1 interference, heavy accents (e.g., Indian English, Nigerian English), children's speech, elderly speech, or speech pathologies.

4. **Small tool surface:** Only 11 mock API functions across 4 domains. Does not test tool selection at scale (e.g., distinguishing among 100+ similar API endpoints).

5. **English-only:** Disfluency patterns in other languages may differ systematically (e.g., particle-based fillers in Japanese, tonal interactions in Mandarin).

6. **Proprietary model opacity:** Behavioral patterns observed (e.g., Gemini 3.1's "silent worker") are descriptive, not explanatory — the underlying architectural causes are inaccessible, limiting generalizable insight.

7. **GPT-4o as judge:** Using a proprietary LLM as the evaluation judge introduces a potential confound — the judge may have model-family biases. No inter-judge agreement analysis or human correlation study is reported.

8. **Single-turn streaming:** Although described as "full-duplex," the benchmark evaluates single-response-at-a-time interactions, not true multi-party or persistent-conversation scenarios.

## 6. Transfer to Lyra

**The one transferable idea:** A **disfluency-annotated evaluation harness with self-correction/state-rollback scenarios** for voice-agent testing. Lyra should adopt a testing methodology where voice interactions are systematically stressed with mid-utterance corrections (e.g., "Book me a flight to London — actually, make that Paris on Tuesday"), and the agent is scored not just on final tool-call accuracy but on whether it correctly discards stale intermediate parameters. This is directly actionable: create a test-suite of 20-30 self-correction scenarios mapped to Lyra's own tool surface, run them against every interaction-model change, and gate releases on a Pass@1 threshold.

**Workstream route:** This feeds into **§4.5 (Voice/Interaction)** — the subsystem responsible for spoken-language understanding, turn-taking, and voice-agent behavior in Lyra.

**Impact:** 4 — Directly improves reliability of the interaction surface most prone to silent failures.
**Effort:** 3 — Requires building a modest test harness (~20-30 scenarios) with mock tool endpoints, but the methodology is well-specified by FDB-v3.
**Tier:** **Investigate** — Adopt the evaluation methodology but adapt to Lyra's specific tool surface and interaction patterns rather than importing the benchmark wholesale.
