## 1. Mechanism (Step-by-Step)

MOSS is a system that lets a deployed agentic application modify its own harness-level source code in response to production failures. It operates on a production substrate (OpenClaw) and evolves through a deterministic, gated pipeline.

### 1.1 Architecture Components

Five pieces form the system:
1. **Main container** — runs the substrate's user-facing agent plus an in-container evolution service
2. **Control-surface CLI** (`moss evo`) — 9 subcommands (status, batches, batch, start, stop, restart, apply, flag, catch-up) that the agent invokes via its shell tool
3. **Pluggable external coding-agent CLI** — delegated per stage to actually write code; four runners ship in tree (Claude Code, OpenAI Codex, DeepSeek-TUI, OpenCode); adding a provider is one new runner file + one registry line
4. **Host-daemon** — an asyncio process running on the host that: (a) spawns the coding-agent CLI per stage, (b) manages ephemeral trial-worker containers, (c) handles Docker build/image management, (d) runs an auto-scan engine that scrapes session JSONLs for failure evidence, (e) supervises container swaps with health-probe-gated rollback
5. **Ephemeral trial workers** — N short-lived containers brought up from the candidate image per iteration, running agent autonomously against batch tasks

### 1.2 Evidence Collection (Directed Evolution)

Unlike prior academic work that uses exploratory/random mutation against a fixed benchmark, MOSS takes a **directed and deterministic** approach:

**Auto-Scan Engine (periodic)**: A cron job runs `moss evo catch-up`, which:
- Scans every agent's session JSONLs from a per-session cursor
- Slices new content into chunks
- Scores each chunk's keypoints via the Task-Evaluate stage on a 4-level scale: `strong / adequate / weak / missing`
- Appends chunks tagged `weak` or `missing` to the conversation's open batch

**User-Triggered Flagging**: When a user expresses dissatisfaction, the agent invokes `moss evo flag`, which scans a single session from cursor to EOF, yielding chunks the same way.

**Batch Construction**: One open batch per conversation; sealed when chunk count reaches configurable threshold (default 8). Evolution triggered by `moss evo start`.

### 1.3 The 7-Stage Pipeline (Per Iteration)

Each iteration decomposes into seven stages executed in sequence, with a coding-agent CLI invoked once per stage:

1. **Locate** — reads baseline traces and batch failures; writes a diagnosis without proposing fixes
2. **Plan** — identifies root cause and specifies the fix: which files change, what logic is added, what is left alone
3. **Plan-Review** — first quality gate; plan is approved, rejected as architecturally off-target, or rejected as too narrow. Plan and Plan-Review alternate in a multi-round plan-loop until approval or round-budget cap
4. **Implement** — writes the code in the inner substrate repository as a single git commit
5. **Code-Review** — second quality gate; diff reviewed against the plan and approved or rejected. Implement and Code-Review alternate in a multi-round code-loop, with working tree hard-reset to the loop's starting commit between rounds
6. **Task-Evaluate** — after Build and Trial, scores 4-7 keypoints per task on the qualitative scale. Same stage runs during pre-loop baseline; keypoint set locked for the rest of the loop
7. **Verdict** — synthesizes per-task evaluations and cross-iteration keypoint matrix into one of: `CONVERGED`, `NEED_MORE_WORK`, `FUNDAMENTAL_LIMIT_MODEL`, or `FUNDAMENTAL_LIMIT_ARCHITECTURE`. Orchestrator may downgrade `NEED_MORE_WORK` to `CONVERGED` if no improvement across a depth-dependent plateau window

### 1.4 Runtime Verification (Build + Trial)

Between Code-Review and Task-Evaluate:
- **Build**: host-daemon builds a candidate Docker image from the modified source
- **Trial**: host-daemon spawns N ephemeral containers from the candidate image; each runs the agent autonomously against every batch task; tasks repeated over several trials to expose flakiness
- Trial workers are network- and mount-isolated from the live main container; torn down when iteration ends
- Baseline uses pre-captured transcripts (original session at evidence time), not re-runs

### 1.5 In-Place Container Swap

**Promotion requires explicit user consent** — convergence fires an `evolution-converged` webhook, but the agent must invoke `moss evo apply` (typically through conversation).

**Swap protocol**:
1. Apply request HTTP-POSTs to gateway, which atomically writes a swap-request file
2. Host-daemon's swap-supervisor file-polls every 2 seconds
3. On detection: restarts substrate container against candidate image
4. **90-second probe window**: samples every 5 seconds; each probe checks 4 health conditions (heartbeat freshness ≤30s, container running, 2 substrate-level CLI status probes)
5. 3 consecutive passes → commit; any failure → rollback to last-known-good image (read from independent record, not swap request, to prevent rollback loops)
6. User-state volume (sessions, memory, credentials, configs) mounts into new container untouched

### 1.6 Evolution Depth Dial

Three settings — `light`, `standard`, `deep` — scale: max iteration count, per-stage round budgets, trials per task, plateau threshold. Default is `standard`.

## 2. Results (Real Benchmark Numbers)

**Experimental Setup**:
- **Substrate**: OpenClaw with DeepSeek V3.2 as underlying model
- **Tasks**: 4 claweval tasks in operations/compliance-audit category
  - T141zh / T142: SLA compliance audit (Chinese / English)
  - T137zh / T138: Restock-chain check (Chinese / English)
- **Grader**: claweval grader, [0, 1] scale, pass threshold = 0.75
- **Evaluation**: Mean of 3 trials per task, pre- and post-evolution
- **Baseline mean**: 0.2526 (well below 0.75 pass threshold)

**Per-Task Results (Iteration 1)**:

| Task | Baseline | Iter 1 | Δ |
|------|----------|--------|---|
| T141zh (SLA audit, CN) | 0.3273 | 0.5330 | +0.2057 |
| T142 (SLA audit, EN) | 0.2527 | 0.5453 | +0.2926 |
| T137zh (Restock, CN) | 0.2213 | 0.4567 | +0.2354 |
| T138 (Restock, EN) | 0.2090 | 0.9049 | +0.6959 |
| **Mean** | **0.2526** | **0.6100** | **+0.3574** |

**Key numbers**:
- Four-task mean: 0.25 → 0.61 (2.4x improvement, single cycle)
- T138 all 3 trials clear the 0.75 pass threshold
- SLA pair moves from 0.25-0.33 to ~0.53-0.55 — annotation path closes largest defect, but per-ticket time-difference arithmetic and SLA-tier classification carry independent difficulty
- Code change: 3 files modified, 177 insertions, 1 deletion
- Change targets: tool-result mediator (annotation branch + helpers), before-tool-call hook chain (pre-call deny gate), new mediator test file

**Qualitative output change**: SLA transcripts previously returned half-answers; post-evolution return per-ticket SLA-tier classifications with aggregate summaries ("2 of 6 P1 tickets violated SLA, affecting Customer B and Customer D, mean overrun 2.3h"). Restock transcripts return complete chains instead of partial results.

## 3. Trade-offs (Wins vs Loses)

| Dimension | Win | Cost/Risk |
|-----------|-----|-----------|
| **Evolution scope** | Harness-level (Turing-complete, superset of text-mutable) vs text-only | Code changes can break the harness; requires container infrastructure |
| **Determinism** | Source edits execute as code behavior, not model compliance | Requires build system, Docker, health probes — heavier than editing a .md file |
| **Long-context stability** | Harness fixes don't erode as context grows (not re-read each turn) | Initial implementation complexity — 7-stage pipeline with 2 review gates |
| **Verification fidelity** | Runtime replay on production-equivalent containers (not unit tests) | Trial workers are expensive (N containers per iteration); network/mount isolation adds latency |
| **Safety** | User-consent-gated promotion; health-probe-gated auto-rollback | Single-instance assumption — blue-green/canary not supported; user must explicitly authorize |
| **Vendor independence** | Pluggable coding-agent CLI (4 providers, extensible) | Each provider has its own cost/latency profile; quality varies by provider |
| **Evidence anchoring** | Directed evolution on real failures (not random mutation) | Depends on auto-scan quality; false positives/negatives in chunk scoring possible |
| **Pipeline structure** | Gated quality control at Plan-Review and Code-Review stages | Multi-round loops increase compute cost; plateau detection may converge prematurely |

## 4. Design Rationale

**Why source-level over text-mutable**: The authors argue source-level adaptation is superior along four axes: (1) Turing-complete — programming languages form a universal search space; any prompt/skill/memory configuration is a subset expressible in code; (2) strict superset — whatever a prompt edit can achieve, equivalent code can also achieve, not vice versa; (3) deterministic — routing, hooks, state machines execute as code independent of model compliance; (4) long-context stable — encoded as behavior, not text to re-read, so doesn't degrade as system ages.

**Why directed over exploratory**: Prior academic work (SICA, Darwin Gödel Machine, HyperAgents) uses random mutation + benchmark scoring. This fails on production systems because: codebases are too large for undirected mutation to land on useful changes; production quality is task-specific with no global fitness signal; unanchored patches are indistinguishable from regressions under live traffic; users expect their specific failure fixed, not global retuning.

**Why 7-stage pipeline over single prompt**: A single prompt asked to diagnose, plan, implement, verify, and decide overloads context and produces lower-quality output. Each stage reads different artifacts (traces, diagnosis, diff, trial output, matrix). Gate-based quality control requires explicit boundaries — planning must be its own stage for review to exist between planning and implementation.

**Why container-based trial over unit tests**: Race conditions, cross-module state interactions, and hook-order-dependent behavior only manifest when the agent runs. Unit tests cannot catch channel routing failures, session lifecycle bugs, or cross-module state propagation.

## 5. Limitations & Failure Modes

1. **Controlled benchmark batch, not real traffic**: The case study uses 4 claweval benchmark tasks as the failure batch — this trades realism for reproducibility. Organic user-session batches may differ in difficulty distribution, noise, and coverage.

2. **Single cycle only**: Results shown for iteration 1 only. Multi-cycle evolution, regressions across cycles, and long-term drift are not evaluated.

3. **Model-specific results**: DeepSeek V3.2 is the only underlying model tested. The coding-agent CLI (which performs the actual editing) and the substrate agent's base model both contribute to outcomes — results may not transfer to other model families.

4. **Partial SLA task gains**: T141zh/T142 reach only ~0.53-0.55, still below the 0.75 pass threshold. One iteration cannot resolve all failure modes (e.g., per-ticket arithmetic, tier classification).

5. **User consent gate bypassed for evaluation**: The benchmark run auto-acknowledged the consent gate, so the human-in-the-loop dynamics are untested.

6. **Single-instance deployment assumption**: Blue-green, canary, and multi-instance deployments are unsupported. The swap protocol assumes exactly one live container.

7. **No security or safety evaluation**: Self-modifying code raises safety concerns (malicious evolution, privilege escalation, prompt injection into the evolution loop). These are not addressed.

8. **Infrastructure dependency**: Requires Docker, host-daemon process, Unix sockets, file-polling — significant operational surface beyond the agent itself.

9. **Batch size sensitivity**: Default batch threshold of 8 chunks is arbitrary; sensitivity to batch size, chunk quality, and false-positive evidence is unexplored.

## 6. Transfer to Lyra

### The One Transferable Idea

**Production-failure-anchored harness-level self-evolution with a gated multi-stage pipeline and runtime verification via ephemeral trial instances.** Lyra could implement a loop where (a) specific user-session failures are auto-flagged into curated batches, (b) a staged pipeline diagnoses, plans, implements, and reviews harness-level fixes (not just prompt/skill edits), (c) candidate changes are verified by replaying the failure batch against an ephemeral Lyra instance before promotion, and (d) a consent-gated swap with health-probe rollback protects live deployment. This moves Lyra's self-improvement from the text layer (prompts, memories) to the code layer (routing, hook ordering, state invariants, dispatch).

### Workstream Route

**§4.9 — Autonomous Improvement & Self-Healing** (the evolution/self-repair workstream). This paper provides the first production-grade blueprint for harness-level self-evolution with production-failure anchoring, directly applicable to Lyra's own agent harness (mediator, routing, hook chains, session lifecycle).
