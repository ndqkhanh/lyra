## 1. Mechanism (step-by-step)

DRAG introduces a **two-stage Multi-Agent Debate (MAD) framework** integrated into the RAG pipeline. It is **training-free** — no fine-tuning required, works with any base LLM.

### Stage 1: Retrieval Debate (`f_RetDebate`)

**Goal:** Iteratively refine retrieval queries to maximize knowledge coverage and reduce retrieval bias, preventing the "Hallucination on Hallucination" problem where bad retrieval begets bad generation.

**Structure — three agents per round:**

1. **Proponent Agent (`T_p`):** Argues the current query pool `Q^j` is sufficient. Proposes: `Q^{j+1} = Q^j` (keep unchanged).

2. **Challenger Agent (`T_c`):** Identifies deficiencies in `Q^j` and proposes one of two operations (inspired by Toolformer/FLARE):
   - **Query Optimization:** Refine existing query — `[Original Query] → [New Query]`
   - **Query Expansion:** Add new query to cover missing information — `[New Query]`
   - Updates: `Q^{j+1} = (Q^j ∩ Q_useful) ∪ Q_new`

3. **Judge Agent:** Evaluates arguments from both sides and selects the winning agent: `T^j = Select(T_p, T_c)`

**Algorithm flow:**
```
Q^0 = {x}                                // Initialize with original question
for j = 0, 1, ..., r:
    Debate(x, Q^j, C_Q^j, A) → T^j      // Run debate with 3 agents
    Q^{j+1} = T^j(Q^j)                   // Update query pool
    if ||Q^{j+1} - Q^j|| ≤ ε or j == r:  // Convergence check
        break
Q_hat = Q^{j+1}                           // Final query pool
C_Q_hat = R(Q_hat, C, k)                 // Retrieve with refined queries
```

Key detail: ε = 0 (debate stops when queries stop changing), max rounds r = 3.

### Stage 2: Response Debate (`f_ResDebate`)

**Goal:** Mitigate over-reliance on potentially noisy retrieval, enhance reasoning robustness through adversarial debate with **asymmetric information roles**.

**Structure — three agents, information asymmetry enforced:**

1. **Proponent Agent (`M_Ap`):** Has access to retrieved documents `C_Q_hat`.
   - Round 1: `y^1_Ap = M_Ap(x, C_Q_hat)` — answers from retrieval
   - Round i: `y^i_Ap = M_Ap(x, {y^{<i}_Ap}, y^{i-1}_Ac)` — refines by incorporating challenger's answer

2. **Challenger Agent (`M_Ac`):** NO access to retrieval (internal knowledge only).
   - Round 1: `y^1_Ac = M_Ac(x)` — answers from parametric knowledge
   - Round i: `y^i_Ac = M_Ac(x, {y^{<i}_Ac}, y^{i-1}_Ap)` — refines using proponent's answer

3. **Judge Agent (`M_Aj`):** Selects final answer from both agents' final responses:
   - `y_hat = M_Aj(x, y^r_Ap, y^r_Ac)`

**The asymmetric information design is critical:** If all agents see the same retrieval, they uncritically accept it. The challenger, relying only on internal knowledge, forces the proponent to defend retrieval-based claims, surfacing inconsistencies. The ablation study confirmed removing asymmetry degrades performance across all datasets (e.g., 2Wiki EM drops from 28.80 to 22.00).

**Prompt design patterns:**
- Retrieval debate: Agents are prompted to choose specific structured actions (`Query Optimization:` or `Query Expansion:`) with required output formats
- Response debate: Agents receive opposing agent's prior answer as "additional advice, note they may be wrong"
- Judge agent: Outputs only the selected agent name (retrieval) or the final answer (response)

## 2. Results (real benchmark numbers)

**Setup:** Llama-3.1-8B-Instruct, E5-base-v2 retriever, Wikipedia Dec 2018 dump, top-k=3, 8x NVIDIA RTX A6000 GPUs, 500 random samples per dataset, zero-shot (DRAG) vs few-shot (baselines reproduced from originals). All methods evaluated under same retrieval settings.

## 3. Trade-offs

| Win | Loss |
|-----|------|
| +6 EM on multi-hop QA (2Wiki) over best baseline | -7.2 EM on single-hop NQ vs Self-RAG |
| +6.6 EM on commonsense reasoning (StrategyQA) | ~10x more LLM calls vs Naive RAG (10.36 vs ~1) |
| Training-free — works with any base LLM | Performance drops with too many debate rounds (problem drift) |
| Adaptive retrieval depth (1-2 rounds for simple Qs, more for complex) | Response stage lacks adaptive stopping (fixed rounds) |
| Asymmetric info design improves robustness against retrieval noise | Requires 3 specialized agent prompts per stage |
| Dynamically adjusts query count based on task complexity | Judge agent quality is a single point of failure for debate decisions |
| Outperforms dedicated retrieval-only (IRCoT, Iter-RetGen) and generation-only (Self-RAG, SuRe) methods on multi-hop tasks | Higher latency — sequential debate rounds cannot be parallelized |

## 4. Design Rationale

**Why two-stage debate?** The authors observe that RAG hallucination has two independent root causes: (a) biased/incomplete retrieval injecting wrong context, and (b) the LLM over-relying on or misinterpreting retrieved content. Single-stage optimization cannot address both simultaneously. By separating retrieval debate (query pool refinement) from response debate (adversarial answer verification), each stage targets a distinct failure mode.

**Why asymmetric information in response debate?** If all agents see identical retrieval results, they converge on the same (potentially wrong) answer — debate becomes a rubber stamp. The challenger's blindness to retrieval forces genuine adversarial scrutiny: the proponent must defend retrieval-based claims against an agent relying purely on parametric knowledge. The ablation confirms this asymmetry is critical (2Wiki EM drops 6.8 points when removed).

**Why training-free?** The approach treats debate as a prompting/coordination layer, not a learned policy. This makes it immediately deployable with any LLM, avoids task-specific fine-tuning data requirements, and allows the debate structure to be adjusted per deployment without retraining.

**Why judge agent instead of voting?** Consensus voting can reinforce majority errors. A dedicated judge evaluates argument quality, enabling the system to break ties and resolve conflicts beyond simple majority.

## 5. Limitations and Failure Modes

1. **Computational overhead:** DRAG averages 10.36 LLM calls vs ~1 for Naive RAG. The response stage uses fixed 7 LLM calls regardless of task complexity — a major efficiency bottleneck on simple questions.

2. **Problem drift:** Excessive debate rounds introduce unnecessary complexity. The authors demonstrate this empirically: TriviaQA EM peaks at ResIter=1 (62.4), then degrades at ResIter=2 (60.2) and ResIter=3 (60.8). The proponent agent in Figure 6 hallucinates a completely wrong lineage (claiming Elizabeth of Rhuddlan's father is "John of England, 1st Baron of Rhuddlan"), and the judge agent fails to correct this, outputting the wrong answer.

3. **No adaptive stopping in response debate:** While the retrieval stage has convergence criteria (ε threshold + judge determination), the response stage uses fixed rounds. This means the same computational budget is spent on trivial questions where 1 round suffices.

4. **Judge agent reliability:** The judge is the single point of failure. In the error case (Figure 6), the judge selects "Oxford Castle, England" despite the opponent agent correctly identifying Westminster — the proponent's incorrect claim about John of England being the father overrides correct evidence.

5. **Single-hop performance gap:** DRAG underperforms dedicated baselines on simple QA (NQ, TriviaQA, PopQA). The debate mechanism introduces overhead without commensurate benefit when retrieval is straightforward.

6. **Model-dependence not explored:** All experiments use Llama-3.1-8B-Instruct. Debate quality almost certainly varies with model capability — weaker models may produce worse debates, stronger models may not need them.

7. **Latency:** Sequential debate rounds are inherently serial; the framework does not explore parallelization or speculative execution.

## 6. Transfer to Lyra

### The ONE transferable idea

**Adversarial multi-agent verification for retrieval quality and factual consistency.** DRAG demonstrates that a structured debate between agents with asymmetric information access (one sees retrieval, one does not) significantly improves factual reliability, especially on complex multi-hop tasks. For Lyra, this pattern could be applied to: (1) verifying search/retrieval results before surfacing them to the user, and (2) cross-checking generated responses against both retrieved evidence and internal knowledge through a lightweight adversarial agent.

### Workstream routing: **§4.2 (Memory/Context) → §4.5 (Safety/Reliability)**

The idea spans two workstreams:
- **§4.2 Memory/Context:** Improves retrieval quality through multi-perspective query refinement before final retrieval and context assembly.
- **§4.5 Safety/Reliability:** The asymmetric debate pattern is fundamentally a verification/factuality mechanism — a lightweight adversarial checker that reduces hallucination risk.

### Scoring

| Dimension | Score | Rationale |
|-----------|-------|-----------|
| **Impact** | 4/5 | Directly addresses Lyra's core reliability challenge; training-free so quick to prototype; multi-hop improvement is large (+6 EM); verification patterns are broadly applicable beyond QA |
| **Effort** | 3/5 | Moderately complex: requires prompt engineering for 3 agent roles + judge, 2-stage pipeline design, and integration with existing retrieval infrastructure. No model training needed. |
| **Tier** | **investigate** | The core pattern (asymmetric verification debate) is highly transferable, but DRAG's specific 10x LLM call overhead needs optimization for Lyra's latency budget. Worth prototyping a lightweight 2-agent version (proponent + challenger, no separate judge) with adaptive early stopping. |

**Concrete Lyra adaptation sketch:**
```
User query → Lyra retrieval → Proponent (with docs) drafts answer
                                ↓
                        Challenger (no docs) critiques
                                ↓
                        Merge/arbitrate → Final answer
```
This 2-agent asymmetric pattern preserves the key insight while cutting LLM calls from 10.36 to ~4-5, making it viable for interactive latency.
