## 1. Mechanism (Step-by-Step)

Polar is a rollout framework for scalable asynchronous RL over arbitrary agent harnesses, treating harnesses as black boxes. Its core insight: every LLM-based agent must call a model endpoint, so intercept at the API boundary instead of modifying harness internals.

### Architecture (Two Components)

1. **Rollout Server**: Accepts `TaskRequest`, expands into `num_samples` sessions, dispatches to gateway nodes, persists results, exposes polling API.
2. **Gateway Node**: Owns session lifecycle — starts runtime, hosts proxy, runs harness, builds trajectories, evaluates, tears down.

### Step-by-Step Control Flow

**Step 1 — API Proxy Interception**: The harness is configured (via env vars) to point its model base URL at the gateway proxy. For each incoming model request, the gateway:
- Detects the provider API (Anthropic Messages, OpenAI Chat Completions, OpenAI Responses, Google generateContent) via request path/headers.
- Normalizes the request into OpenAI Chat Completions shape via a provider transformer (adds `logprobs=true`).
- Forwards to inference server and captures: request messages, response messages, prompt token IDs, response token IDs, finish reason, log probabilities.
- Transforms response back to the provider schema expected by the harness. For streaming, obtains non-streaming upstream response and emits synthetic provider-shaped SSE stream.

**Step 2 — Asynchronous Rollout Staging**: Each gateway uses 4 isolated worker pools + a bounded READY buffer:
- **INIT**: Starts runtime, executes prepare actions.
- **READY**: Holds initialized runtimes until a run slot opens — CPU-heavy prep proceeds off critical path.
- **RUNNING**: Executes the harness (GPU-bound agent execution).
- **POSTRUN**: Builds trajectories, runs evaluators, sends callbacks, tears down.
- Evaluator prewarm: evaluator runtime is prepared during agent execution, not after. Timeout handling: partial traces recovered even on timeout.

**Step 3 — Trajectory Reconstruction**

Two strategies provided:

**A) Per-Request Builder (Conservative Baseline)**:
Each captured model call becomes one independent trace. Lossless per-call, but fragments multi-turn sessions (hundreds of traces per coding problem), increasing trainer burden.

**B) Prefix Merging Builder (Token-Faithful)**:

For session with completions C₁,...,C_T where Cᵢ has prompt token sequence pᵢ, sampled response tokens aᵢ, log probabilities ℓᵢ:

1. **Partition** completions into ordered chains G = {G₁,...,Gⱼ}, where a new completion joins chain only when:
   - Normalized message-level grouping key identifies it as candidate continuation
   - **Strict token-prefix relation holds**: p_{i_{m+1}}[1:|p_{i_m}|] = p_{i_m}
   - This naturally separates sub-agents, compaction, prompt rewrites, and parallel branches into distinct chains.

2. **Merge within each chain**. For chain (C_{i_1},...,C_{i_K}), define canonical tail:
   ```
   t_m = p_{m+1}[|p_m|+1:]
   ```
   Locate first end-of-turn token `e` in t_m. The interstitial u_m is the suffix after e.

3. **Emit trace** with token sequence:
   ```
   z^{(j)} = p_1 || a_1 || u_1 || a_2 || u_2 || ... || a_K
   ```
   - Prompt = p₁, response = a₁||u₁||...||a_K
   - **Loss mask**: 1 on sampled a_m tokens, 0 on canonical interstitial u_m tokens
   - Real log-probs for a_m, synthetic entries for u_m

4. **Correctness invariant**: Every trainable token matches behavior policy; all non-generated tokens are masked.

**Step 4 — Evaluation & RL Training**: Evaluator registry runs post-trajectory; SWE-Bench harness scores final patch in fresh runtime. Independent trainer (e.g., Slime with GRPO) pulls completed trajectory groups from rollout service endpoints. Updated weights flow back to rollout nodes for next generation.

### Key Design Properties
- **Harness-agnostic**: Uses black-box harnesses, no internal harness code changes
- **Provider-agnostic**: Handles Anthropic, OpenAI, Google API formats
- **RL-algorithm-agnostic**: Any trainer can consume the rollout endpoints
- **Training-infrastructure-agnostic**: Works with Slime, Megatron, SGLang, vLLM backends
- **Token-faithful**: Exact sampled tokens preserved, no retokenization drift

## 3. Trade-Offs

| Win | Lose |
|-----|------|
| Zero harness code changes required — any harness trainable as-is | Proxy adds latency (every API call routes through gateway with format transform) |
| Token-faithful trajectories prevent retokenization drift | Per-request builder fragments sessions into hundreds of traces, causing reward hacking |
| Prefix merging gives 5.39× wall-clock speedup and 4.3× GPU utilization improvement | Prefix merging only works for append-only conversation histories; fails on non-append patterns (compaction, sub-agents) |
| Decoupled rollout/training scales independently | Black-box proxy means zero visibility into harness internals for optimization |
| Multi-provider API support (Anthropic, OpenAI, Google) | Each provider needs a transformer; non-standard APIs require custom code |
| Works with any RL algorithm (tested with GRPO) | No process reward model or session-level credit assignment (reward hacking risk) |
| Reusable for offline SFT and RL online rollouts | Requires the harness to make LLM API calls; local/non-API agents need adaptation |
| Large gains on unfamiliar harnesses (Codex +22.6) | Marginal gains on native-matched harnesses (Qwen Code +0.6) |
| Supports Docker + rootless Apptainer for HPC | Only validated on 4B model; scaling to larger models unknown |

## 4. Design Rationale

**Why proxy at the API boundary instead of integrating into harness internals?**

The authors argue that agent harnesses are increasingly heterogeneous: different languages, closed-source binaries (Claude Code, Codex), complex internal event loops, tool formatting, and context policies. Prior systems (SkyRL-Agent, PRIME-RL, Agent Lightning, rLLM) require agents to conform to framework-specific interfaces, creating integration burdens proportional to harness complexity. By observing at the model API boundary, Polar achieves a universal interface: every LLM-based agent must call a model endpoint. This single integration point eliminates harness-specific rewrites while preserving the native execution path that agents are evaluated on.

**Why separate rollout-as-a-service from training?**

Long-horizon agent rollouts mix heterogeneous costs: runtime startup (CPU), dependency prep (CPU), harness execution (GPU), evaluation (CPU/GPU), teardown (CPU). Coupling these to training causes idle GPU time. Polar's stage-isolated worker pools (INIT/READY/RUNNING/POSTRUN) allow CPU-heavy prep and evaluation to proceed asynchronously, keeping rollout GPUs at 87.7% utilization vs 20.4% without staging.

**Why token-faithful prefix merging instead of full retokenization?**

Retokenizing transcripts (decoding text and re-encoding) produces different token IDs from the original generation, creating a mismatch between training tokens and behavior policy tokens. Polar copies exact sampled token IDs from inference responses, ensuring the loss signal attaches to the tokens the model actually generated during rollout.

## 5. Limitations & Failure Modes

1. **API-Only Agents**: Polar requires the harness to make LLM API calls through a configurable endpoint. Agents that use embedded/local inference or non-standard protocols cannot be observed without modification.

2. **Per-Request Reward Hacking**: Broadcasting session-level outcome rewards to every per-request trace causes noisy credit assignment and reward hacking. The paper explicitly states "providing examples and tools for session normalization and PRM-style credit assignment is on our roadmap."

3. **Prefix Merging Constraint**: The prefix_merging builder only handles append-only conversation chains. Context compaction, prompt rewriting, sub-agents, and parallel branches naturally form separate chains that are not merged — potentially fragmenting training signal for complex multi-agent workflows.

4. **No Process Reward Model**: Only outcome-level rewards are supported. For tasks requiring step-level credit assignment (long horizon reasoning, interactive debugging), the framework lacks built-in PRM support.

5. **Small Model Validation**: All experiments use Qwen3.5-4B. Scaling behavior to 70B+ models is unverified — larger models may exhibit different rollout dynamics, token budgets, and harness interaction patterns.

6. **Single Domain**: Only validated on SWE-Bench (code). No evidence for web agents, OS agents, or multi-modal agents.

7. **Provider Transformer Completeness**: Each new API provider format (Anthropic, OpenAI, Google) requires a transformer. Non-standard or evolving API formats may produce reconstruction errors.

8. **Proxy Latency Overhead**: Every harness API call incurs a gateway round-trip with format detection, normalization, and response transformation — not measured against direct API calls.

9. **Closed-Source Harness Fragility**: Harnesses distributed as binaries may change their API format or add new endpoints without notice, requiring proxy updates.

10. **No Multi-Turn Credit Assignment**: The framework broadcasts terminal rewards to all traces. No mechanism to assign differentiated credit to specific turns within a session.

## 6. Transfer to Lyra

**One Transferable Idea**: Adopt Polar's **API-proxy-as-integration-boundary** pattern for Lyra's evaluation harness. Instead of building custom integrations for each agent framework Lyra evaluates (Claude Code, Codex, Gemini CLI, etc.), intercept at the LLM API level to record token-faithful trajectories for fine-tuning, debugging, and offline analysis. This would allow Lyra to train on real-agent execution traces without modifying any harness code.

**Workstream Route**: §4.3 (Evaluation & Benchmarking) — Polar's proxy architecture directly enables harness-agnostic evaluation by capturing native execution traces across heterogeneous coding agents. This feeds Lyra's need to benchmark against real-world agent systems without writing per-harness integrations.

**Impact**: 4 — High. Would dramatically reduce integration burden for Lyra's multi-harness evaluation pipeline and unlock RL-based self-improvement from real agent trajectories.

**Effort**: 4 — Significant. Requires implementing provider-compatible API proxies (Anthropic, OpenAI, Google formats), token-level capture, trajectory reconstruction (prefix merging), and async rollout staging. The NeMo Gym integration and open-source codebase reduce risk.

**Tier**: **Breakthrough** — This is a new paradigm for agent RL infrastructure. The proxy-boundary design is architecturally novel and solves a real pain point (harness-specific integration) that Lyra's multi-harness evaluation strategy will encounter at scale.
