## 1. Mechanism (step-by-step)

### Core Concept: Hyperagents

A **hyperagent** is a self-referential program that integrates a **task agent** (solves the target task) and a **meta agent** (modifies agents and generates new ones) into a single editable Python program. Crucially, the meta agent can modify itself — the improvement mechanism is itself subject to improvement. This is called **metacognitive self-modification**.

### Algorithm: DGM-H (Darwin Gödel Machine with Hyperagents)

DGM-H extends the Darwin Gödel Machine (Zhang et al., 2025b) by replacing the fixed, handcrafted instruction-generation step with an editable meta agent.

**Pseudocode** (Algorithm 1):
```
A ← {(a0, Evaluate(a0, T))}                    // Initialize archive with initial agent
for t ← 1 to T:
    P ← SelectParents(A)                        // Probabilistic parent selection
    foreach (a, ·) ∈ P:
        a′ ← a.Modify(a, A)                     // Metacognitive self-modification
        s′ ← Evaluate(a′, T)                    // Evaluate on tasks
        if IsValid(a′): A ← A ∪ {(a′, s′)}      // Add to archive if compiles
return A
```

### Parent Selection (Appendix A.2)

Given archive At = {a0, ..., at} with performance scores αi:

1. **Dynamic midpoint**: αmid = (1/m) Σ αj for top-m agents (m=3)
2. **Sigmoid transformation**: si = 1 / (1 + exp(-λ(αi - αmid))), λ = 10
3. **Novelty bonus**: hi = 1 / (1 + ni) where ni = number of compiled children of agent i
4. **Unnormalized weight**: wi = si · hi
5. **Sampling distribution**: pi = wi / Σ wj (categorical sampling with replacement)

### Initial Hyperagent (Appendix A.1)

- **Task agent**: Receives task inputs, makes single FM call, outputs JSON `{"response": ...}`
- **Meta agent**: Receives `repo_path`, location of evaluation results, remaining experiment budget. Prompt: "Modify any part of the codebase at `{repo_path}`."
- **Tools**: bash (shell execution, sandboxed) and editor (view/create/modify files)
- Deliberately kept simple to maximize search space

### Key Architectural Distinction vs DGM

| | DGM | DGM-H |
|---|---|---|
| Instruction generation | Handcrafted, fixed LLM call with fixed prompt | Editable meta agent (can rewrite itself) |
| Task-meta alignment | Required (coding ↔ coding skill) | Not required (meta agent untethered) |
| Cross-domain transfer | No (domain-specific customization needed) | Yes (meta-skills transfer) |

### Multi-domain Optimization (Appendix A.4)

When optimizing multiple domains, hyperagents are evaluated on all tasks across domains. Parent selection uses average performance across domains. The meta agent can inspect evaluations from any task, allowing shared mechanisms that benefit multiple domains simultaneously.

### Improvement@k Metric (Appendix D.3)

imp@k(M, A, G, T) = max_{A′ ∈ A(k)} Evaluate(A′, T) − Evaluate(A, T)

Measures maximum performance improvement a fixed meta agent M can achieve by generating up to k new task agents from initial agent A. Used to isolate meta agent ability from ongoing self-improvement.

### Transfer Agent Selection (Appendix D.4)

Growth score Gγ(i) = (1/|D(i)|) Σ (αj − αi) · γ^{dist(i,j)} for descendants j of agent i. γ = 0.6, minimum 3 descendants. Selects agents whose descendants show the largest lineage-discounted gains, identifying strong "stepping stones."

## 2. Results (real benchmark numbers)

### Coding (Polyglot, 165 tasks, pass@1)

| Method | Training (50 tasks) | Full benchmark (165 tasks) |
|---|---|---|
| Initial agent | 0.140 | 0.084 |
| DGM-H (best) | 0.340 (CI: 0.300–0.380) | 0.267 (CI: 0.231–0.280) |
| DGM (Zhang et al., 2025b) | 0.380 | 0.307 |

DGM-H matches DGM performance despite no coding-specific handcrafting. 80 iterations, 5 runs, Claude 3.5 Sonnet for self-modification, o3-mini for evaluation.

### Paper Review (binary accept/reject accuracy)

| Method | Test accuracy |
|---|---|
| Initial agent | 0.0 |
| DGM (original, no custom) | 0.0 (CI: 0.0–0.510) |
| DGM-custom (handcrafted for domain) | 0.590 (CI: 0.570–0.650) |
| DGM-H w/o self-improve | 0.0 (CI: 0.0–0.130) |
| DGM-H w/o open-ended exploration | 0.0 (CI: 0.0–0.560) |
| **DGM-H** | **0.710 (CI: 0.590–0.750)** |
| Static baseline (AI-Scientist-v2) | 0.630 |

100 iterations, 5 runs. Statistical significance: DGM-H > DGM (p < 0.05), DGM-H > DGM-H w/o self-improve (p < 0.05), DGM-H > DGM-H w/o open-ended (p < 0.05). Difference vs DGM-custom not statistically significant (p > 0.05).

### Robotics Reward Design (quadruped locomotion in Genesis simulator)

| Method | Test score |
|---|---|
| Initial agent | 0.060 |
| DGM (original) | 0.0 (CI: 0.0–0.090) |
| DGM-custom | 0.348 (CI: 0.305–0.385) |
| DGM-H w/o self-improve | 0.213 (CI: 0.180–0.348) |
| DGM-H w/o open-ended exploration | 0.116 (CI: 0.0–0.348) |
| **DGM-H** | **0.372 (CI: 0.355–0.436)** |
| Default reward (directly optimizes metric) | 0.348 |

Training task: walk forward. Test task: maximize torso height (requires jumping, not just standing). DGM-H almost always discovers jumping behavior, while DGM-custom often gets stuck at standing tall.

### Cross-Domain Transfer (IMO Grading, imp@50)

| Transfer source | Agent-gen algorithm | imp@50 on IMO grading |
|---|---|---|
| Initial agent | DGM w/o self-improve | 0.0 (CI: 0.0–0.0) |
| Initial agent | DGM-H w/o self-improve | 0.0 (CI: 0.0–0.130) |
| DGM-custom transfer | DGM w/o self-improve | 0.0 (CI: 0.0–0.010) |
| **DGM-H transfer** | **DGM-H w/o self-improve** | **0.630 (CI: 0.540–0.630)** |

DGM-H transfer agents from paper review + robotics reward runs show strong ability to generate improved task agents in a completely new domain. DGM transfer agents show zero transfer. p < 0.05 between DGM-H transfer and initial agent.

### Compounding Improvements (IMO Grading, 200 iterations)

| Initialization | Test accuracy |
|---|---|
| DGM-H from scratch | 0.610 (CI: 0.510–0.680) |
| DGM-H + transfer | 0.640 (CI: 0.550–0.720) |
| ProofAutoGrader (static baseline) | 0.670 |
| DGM-H + ProofAutoGrader + transfer | **0.700** |

On full IMO-GradingBench: DGM-H improves ProofAutoGrader from 0.561 to 0.601 accuracy, mean absolute error from 0.178 to 0.175.

### Costs (Appendix D.2)

- Self-modification: ~33M tokens per 100-iteration run
- Evaluation: 0.506M tokens/iteration (paper review + robotics)
- Full 100-iteration run: ~88.6M total tokens
- Model: Claude 4.5 Sonnet (self-modification), GPT-4o (paper review eval), Claude 4.5 Sonnet (robotics eval)

## 3. Trade-offs (wins vs loses)

| Wins | Loses |
|---|---|
| Removes domain-alignment assumption (task skill ≠ self-modification skill) | Higher computational cost (~88.6M tokens per run) |
| Meta-level improvements transfer across completely different domains | Parent selection, evaluation protocols remain fixed and handcrafted |
| Matches DGM on coding *without domain-specific engineering* | Fixed task distribution — no curriculum or task co-evolution |
| Exceeds DGM-custom on paper review (0.710 vs 0.590) and robotics (0.372 vs 0.348) | Only 5 repeated runs per experiment (limited statistical power) |
| Discovers jumping behavior in robotics (DGM-custom gets stuck at local optimum) | Improvement slows at high performance levels due to saturation |
| Open-source code and experiment logs | Requires sandboxed execution (safety constraint) |
| Compounds improvements across runs | Difference vs DGM-custom not statistically significant (p > 0.05) |

## 4. Design Rationale (why this approach)

The core insight: **prior self-improving systems (DGM, ADAS, etc.) rely on fixed, handcrafted meta-level mechanisms that constrain how self-improvement can compound across domains.** Adding more meta-levels (meta-meta, meta-meta-meta) leads to infinite regress — the problem just shifts upward.

The solution is **self-reference**: make the improvement mechanism itself an editable part of the program, rather than an external fixed component. By unifying the task agent and meta agent into a single editable hyperagent, the system can rewrite not just how it solves tasks but how it generates future improvements.

This design is grounded in:
1. **Python's Turing-completeness**: A hyperagent can edit any code, enabling it to build any computable machine.
2. **Open-ended exploration (from DGM)**: Population-based search with an archive prevents premature convergence; stepping stones enable compounding progress.
3. **Minimal initial design**: The initial hyperagent is deliberately simple (single FM call, no domain-specific logic) to maximize the search space for emergent behaviors.

Why not just use DGM with customized instructions per domain? Because that requires human engineering for each new domain. DGM-H autonomously discovers domain-appropriate improvement strategies, and those strategies (e.g., performance tracking, persistent memory) transfer across domains.

## 5. Limitations and Failure Modes

1. **Fixed task distribution**: The DGM-H operates on a static set of training tasks. Co-evolving the task distribution (generating new tasks/curricula) is identified as necessary for truly unbounded progress.

2. **Non-modifiable outer loop**: Parent selection (sigmoid + novelty bonus), evaluation protocols, and archive management remain handcrafted. Hyperagents cannot modify the process that selects them or determines how they are evaluated. Preliminary results in Appendix E.5 suggest this is addressable but not yet robust.

3. **Linear improvement metric**: imp@k treats performance gains as linear, underweighting improvements near saturation (e.g., 0.7→0.8 is harder than 0.0→0.1). The authors note this doesn't affect their relative comparisons but could mask meaningful gains.

4. **Computational cost**: ~88.6M tokens per full 100-iteration run makes large-scale deployment expensive. Requires API access to frontier models (Claude 4.5 Sonnet, o4-mini).

5. **Limited statistical power**: Only 5 runs per experiment with wide confidence intervals (e.g., paper review CI: 0.590–0.750). Difference vs DGM-custom not statistically significant.

6. **Domain breadth**: Only 4 domains tested — all language-based or simulated. No real-world robotics, no deployed systems, no safety-critical applications.

7. **Safety concerns**: Self-modifying code running in sandboxes — sandboxing may not scale with capability. The paper acknowledges that safety mechanisms "may become increasingly strained or infeasible as self-improving systems grow more capable."

8. **No theoretical guarantees**: Unlike the original Gödel Machine's provable optimal self-improvements, DGM-H provides empirical evidence only. The system may plateau or degrade over very long runs (not tested beyond 200 iterations).

## 6. Transfer to Lyra

### The One Idea

**Self-referential agent architecture with editable meta agent**: Make Lyra's planning, evaluation, and improvement modules themselves subject to automated modification by a meta-agent component. Instead of hand-crafting Lyra's improvement loop (how it learns from failures, how it optimizes prompts, how it selects strategies), embed an editable meta-agent that can rewrite Lyra's own improvement logic. The meta-agent would have access to Lyra's full codebase, evaluation history, and task performance logs, and could autonomously introduce mechanisms like performance tracking, persistent memory, and cross-task strategy transfer.

### Workstream Route

**§4.5 — Continuous Self-Improvement and Meta-Learning** (the meta-cognitive loop). This feeds directly into Lyra's ability to improve its own improvement mechanisms over time, with mechanisms for performance tracking, persistent memory across sessions, and autonomous discovery of better agent-generation strategies.

### Impact / Effort / Tier

- **Impact**: 4 (transformative for Lyra's long-term autonomy and cross-domain generalization)
- **Effort**: 5 (requires deep architectural refactor: separating meta-agent from task-agent, building archive-based exploration, sandboxed self-modification, multi-run compounding infrastructure)
- **Tier**: `breakthrough` — fundamentally changes Lyra's improvement trajectory from linear to potentially self-accelerating

### Concrete Starting Point

Implement DGM-H's `PerformanceTracker` class (autonomously discovered by hyperagents) as a standalone Lyra module — a persistent JSON-based tracking system that logs metrics across runs, computes improvement trends via moving averages, and surfaces regressions. This is low-effort scaffolding that enables the larger self-improvement architecture.

### Key Adoption Guard

The meta-agent must operate in a sandboxed sub-interpreter to prevent unsafe modifications. Start with read-only analysis (suggest modifications for human approval) before enabling autonomous code rewriting. The paper's safety discussion (Section 6) provides a framework for staged deployment.
