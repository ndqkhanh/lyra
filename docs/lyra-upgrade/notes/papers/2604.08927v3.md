# Beyond the Individual: Virtualizing Multi-Disciplinary Reasoning for Clinical Intake via Collaborative Agents

**Authors:** Huangwei Chen (ZJU, HDU), Wu Li (ZJU), Junhao Jia (ZJU, HDU), Yining Chen (Sir Run Run Shaw Hospital), Xiaotao Pang (Pujian Medical), Yalong Chen (Sir Run Run Shaw Hospital), Gonghui Li (Sir Run Run Shaw Hospital), Haishuai Wang (ZJU), Jiajun Bu (ZJU), Lei Wu (ZJU, Pujian Medical)

**Venue:** arXiv:2604.08927v3 [cs.MA], April 2026 (preprint). Code: https://github.com/HovChen/Aegle

## 1. Mechanism (step-by-step)

Aegle is a **synchronous virtual Multi-Disciplinary Team (MDT) framework** that replaces single-LLM clinical intake with a graph-based multi-agent architecture. The core insight: **decouple evidence collection from diagnostic reasoning** to mitigate anchoring bias.

### Architecture Components

**Three agent types** in a dynamic graph topology:

1. **Orchestrator (π_orch):** A routing/coordination policy that dynamically selects which specialist agents to activate based on the evolving consultation context. Does NOT perform medical reasoning itself. Formula:
   ```
   A_sub, ι = π_orch(H_t, F_t),   A_sub ⊆ A_total
   ```
   where H_t is dialogue history, F_t is current case features. For simple confirmation questions, the Orchestrator generates questions directly without activating specialists.

2. **Specialist Agents:** Domain-specific agents (Cardiology, Gastroenterology, Radiology, etc.) that operate in **decoupled parallel execution**. Each analyzes the clinical state from its own perspective independently, preserving hypothesis diversity and preventing premature consensus. Specialists propose updates to the structured state and/or follow-up questions.

3. **Aggregator (π_agg):** Integrates heterogeneous specialist outputs via a **write-then-speak protocol**:
   - **Write step:** `S_{t+1} = π_agg^write(S_t, {ΔS_t^a}_{a∈A_sub})` — validates and integrates specialist proposals to update the structured state.
   - **Speak step:** `u_{t+1} = π_agg^speak(S_{t+1})` — generates the patient-facing utterance conditioned solely on the updated state.

### Structured Clinical State

The consultation state at turn t is `S_t = [F_t, P_t]`, decomposing into:
- **F (Case Features):** Corresponds to Subjective + Objective SOAP sections. An incremental repository of verifiable facts: Basic Information, History of Present Illness, Past Medical History, Physical Examination, Auxiliary Examination results.
- **P (Diagnosis & Plan):** Corresponds to Assessment + Plan sections. Derived exclusively from finalized F.

**Critical constraint:** Aegle enforces a **unidirectional dependency F → P**. Diagnostic and planning components can only be generated after evidence stabilization. This explicitly links clinical conclusions to accumulated evidence.

### Two-Stage Finite State Machine

**Stage I — Iterative History Taking:**
1. Orchestrator reads current dialogue history H_t and case features F_t
2. Orchestrator activates relevant specialists based on information gaps in F_t
3. Specialists execute in parallel, each proposing: (a) follow-up questions to fill gaps, (b) evidence-centric revisions to the draft IPN
4. Aggregator integrates parallel proposals, updates F, and generates the next patient-facing question
5. Repeat until all mandatory fields in F are populated or explicitly marked unavailable
6. **Gate condition:** F is frozen before transitioning to Stage II

**Stage II — Diagnostic Synthesis:**
1. Frozen F serves as the fixed evidentiary substrate
2. Orchestrator commissions specialists for independent diagnostic reasoning (no new questions allowed)
3. Specialists propose diagnostic hypotheses, differential diagnoses, and treatment plans
4. Aggregator integrates heterogeneous perspectives into final P, resolving inconsistencies
5. Output: complete, coherent SOAP note with traceable evidence-to-conclusion chains

### Dynamic Topology Efficiency

Unlike static multi-agent systems (MDAgents: 3.702 experts every round, MedAgents: 4.968), Aegle activates **2.416 experts per case and 1.423 per round** on average. Simple information-confirmation turns use zero specialists; only complex differential-diagnosis turns trigger multi-specialist activation.

### Backbone Model
All agents use **DeepSeek-V3.2** as the base LLM, with role-specific prompt engineering. The Orchestrator, Specialists, and Aggregator each receive distinct system prompts with phase-specific instructions and JSON output schemas.

## 3. Trade-offs

| Win | Lose |
|-----|------|
| +21.33pp diagnostic accuracy over same backbone | Additional inference overhead from dynamic routing + parallel specialist execution + aggregation (increased latency) |
| +4.37 IDEA points over best multi-agent baseline (ClinicalBench) | Longer effective context windows as structured state + intermediate agent outputs accumulate (higher token consumption) |
| 35-71% fewer expert activations vs. static multi-agent systems | Redundant/overlapping specialist recommendations can dilute novel signals during aggregation |
| Near-ceiling humanistic care scores (AB 5.00, SP 5.00) | Requires explicit gate transition between evidence collection and synthesis phases (adds engineering complexity) |
| Consistent gains across all 24 departments (no regression) | LLM-as-judge evaluation (gpt-4o-mini) — physician validation only on n=150 subset; full-scale human eval not done |
| Lower variance (narrower confidence intervals) across cases | RAPID-IPN dataset is not publicly releasable (privacy constraints) |
| Traceable evidence-to-conclusion chains via unidirectional F→P constraint | Single-backbone DeepSeek-V3.2; generalizability to other model families not tested |

## 4. Design Rationale

**Why multi-agent over single-model?** The authors argue that a single LLM, like a single physician under time pressure, suffers from **anchoring bias** — fixating on salient symptoms (e.g., "severe chest pain") while overlooking subtler diagnostic clues (e.g., "occasional acid reflux, mild backache"). A single model produces fragmented notes and premature diagnoses.

**Why decoupled parallel reasoning over sequential debate?** Existing medical MAS (MedAgents, MAC) use sequential debate or voting, which introduces **"flawed consensus"** — agents reinforce each other's biases, and minority correct opinions get suppressed. Decoupled parallel execution preserves hypothesis diversity by construction and delays consensus formation until the Aggregator phase.

**Why a state-aware dynamic topology over static activation?** Static multi-agent systems (MDAgents, MedAgents) activate ALL experts on EVERY turn, wasting computation on simple confirmations ("What is your age?"). Aegle's Orchestrator activates specialists only when the case complexity warrants it, mimicking real MDT practice where specialists are consulted only when needed.

**Why write-then-speak protocol?** Separating internal state updates (write) from patient-facing communication (speak) ensures the medical record is technically precise and internally consistent while maintaining empathetic dialogue. This prevents "thinking out loud" contamination of the patient interaction.

**Why unidirectional F → P dependency?** Explicitly preventing diagnostic conclusions from being drawn before evidence stabilization enforces traceability. Every diagnostic claim must be grounded in documented case features. This is the architectural enforcement of evidence-based medicine.

## 5. Limitations & Failure Modes

1. **Inference latency:** Dynamic routing + parallel specialist execution + structured aggregation adds end-to-end latency vs. single-model generation. The paper acknowledges this but provides no latency measurements. Real-time outpatient settings (target <30s response) may be challenging.

2. **Context window expansion:** Accumulated structured state and intermediate agent outputs consume growing context. No measurements of token consumption per consultation are provided. Could constrain deployment under strict token budgets.

3. **Redundant specialist output:** Decoupled parallel reasoning preserves diversity but can produce overlapping recommendations, complicating the Aggregator's integration task. The paper suggests "diversity-aware expert prompting" and "redundancy-penalized aggregation" as future work.

4. **Single backbone dependency:** All experiments use DeepSeek-V3.2. No cross-model validation. Unknown whether the architecture's benefits depend on DeepSeek's specific capabilities or generalize to other model families (GPT, Gemini, Claude).

5. **LLM-as-judge reliance:** Primary evaluation uses gpt-4o-mini. Human validation covers only n=150 per dataset. Systematic biases in LLM judging (leniency, position bias) could inflate absolute scores, though relative rankings are robust given the high Pearson correlations.

6. **Dataset non-releasability:** RAPID-IPN cannot be publicly shared, limiting independent reproduction of the real-world findings. ClinicalBench is accessible.

7. **Fixed two-stage gate:** The deterministic transition from evidence collection to diagnosis (F frozen then P generated) may be too rigid for cases where diagnostic reasoning reveals the need for additional evidence. No mechanism for revisiting Stage I after transition.

8. **No ablation of backbone strength:** The paper does not test whether simply using a stronger single model (e.g., GPT-4o with better prompt engineering) could close the gap with Aegle on DeepSeek-V3.2. The frontier model table shows Aegle beats GPT-4o but only when using DeepSeek-V3.2 backbone.

9. **Language/cultural specificity:** ClinicalBench and RAPID-IPN are Chinese hospital datasets. Cross-lingual and cross-cultural generalizability not tested.

## 6. Transfer to Lyra

### The ONE transferable idea

**State-aware dynamic multi-agent topology with write-then-speak aggregation.** When Lyra orchestrates multiple agents for a complex task (research, code generation, adversarial review), instead of pre-defining which agents run and in what order, use a lightweight Orchestrator agent that reads the current task state and dynamically activates only the relevant specialist agents. Decouple their internal reasoning (write) from user-facing output (speak). Enforce a structured shared state that explicitly separates evidence/facts from conclusions, with a unidirectional dependency — conclusions can only reference stabilized facts, never hallucinated evidence.

### Workstream route: §4.13 (Swarm/Fleet) + §4.25 (Adversarial Panel)

The dynamic topology and write-then-speak pattern applies to §4.13's multi-agent orchestration. The decoupled parallel reasoning with structured state applies to §4.25's multi-perspective adversarial review panels.

### Impact/Effort/Tier

- **Impact:** 4 (directly upgrades Lyra's multi-agent coordination from static/fixed to dynamic/context-aware; the write-then-speak pattern solves a real problem of agent outputs leaking internal reasoning to users)
- **Effort:** 4 (requires: structured state schema for Lyra tasks, Orchestrator prompt engineering, dynamic activation policy, Aggregator with merge logic, integration into existing agent dispatch — estimated 2-3 weeks for MVP)
- **Tier:** **investigate** — The clinical domain adaptation is clean but the pattern translates. Before full implementation, test on one Lyra workflow (e.g., deep research multi-agent analysis) with a lightweight Orchestrator prototype. Key risk: the two-stage gated architecture may be too rigid for Lyra's iterative, back-and-forth research workflows.
