## 1. Mechanism (Step-by-Step)

This is a comprehensive taxonomy survey — it does not propose a single new algorithm but systematically organizes the entire OS Agent design space. The mechanism is the **construction pipeline** and **agent execution loop** it synthesizes from 27+ foundation models and 27+ agent frameworks.

### 1.1 OS Agent Execution Loop

```
User Goal → [Perception] → [Planning] → [Memory] → [Action] → Environment → (loop)
```

**Step 1 — Perception (Environment → Observation):** The agent captures the current OS state via one of two modalities:
- **Textual Description:** Convert OS state into structured text (HTML DOM, accessibility/A11y tree, simplified representations). Agent-E uses flexible DOM distillation with 3 representation levels; WebWise applies `filterDOM` to strip irrelevant elements.
- **GUI Screenshot:** MLLMs process raw screenshots directly. Three grounding strategies augment this:
  - *Visual Grounding:* Set-of-Mark (SoM) prompting — overlay bounding boxes with numeric labels on detected UI elements (via OCR, Grounding DINO, or ICONNet).
  - *Semantic Grounding:* Pair screenshot with HTML/A11y tree as semantic reference (SeeAct, DUAL-VCR).
  - *Dual Grounding:* Combine both — labeled screenshots + XML/A11y element descriptions (AppAgent, OSCAR, PeriGuru).

**Step 2 — Planning (Goal → Action Sequence):** Two paradigms:
- **Global Planning:** Generate one plan upfront as a DAG (OS-Copilot), SOP-based decomposition (AIA), or CoT-based decomposition. Executed without adaptation.
- **Iterative Planning:** Continuously adapt plans using ReAct (observe→reason→act→observe), Reflexion (self-critique with access to past states), or domain-specific methods like CoAT (Screen Description → Action Thinking → Next Action Description → Action Result), Auto-GUI (history-conditioned CoT), OSCAR (task-driven replanning), RCI (recursive self-criticism).

**Step 3 — Memory (Context Retention):** Three source types:
- *Internal Memory:* Short-term (action history, screenshots, state data for current task) and Long-term (declarative memory of user preferences, past task trajectories, skill codes).
- *External Memory:* Knowledge bases, external docs, API-retrieved domain knowledge.
- *Specific Memory:* Task-specific rules, user profiles, app functionality docs (MobileGPT's 3-tier hierarchical memory, CoCo-Agent's Conditional Action Prediction).

Memory Optimization: Self-summarization (compress history to NL), Context Clipping (WebVoyager keeps last 3 observations), Plan-tree isolation (AgentOccam), KNN experience retrieval (PeriGuru), backtracking with memory buffer (LASER).

**Step 4 — Action (Plan → Execution):** Three action categories:
- *Input Operations:* click/tap, long-press/hold, drag/move, text input, special keys/shortcuts.
- *Navigation Operations:* scroll, back/forward, home, tab management, URL navigation.
- *Extended Operations:* code execution (dynamic script generation), API integration (external tools/services).

### 1.2 Foundation Model Construction Pipeline

```
Architecture → Pre-training → Supervised Fine-tuning → Reinforcement Learning
```

**Architecture variants:**
1. *Existing LLMs:* Directly use LLaMA, T5 for HTML-only perception (WebAgent with Flan-U-PaLM + HTML-T5).
2. *Existing MLLMs:* Use LLaVA, Qwen-VL, InternVL, CogVLM as-is for vision+text.
3. *Concatenated MLLMs:* Custom pair LLM + vision encoder — T5 encoder-decoder matches HTML tree structure (WebGUM, WebAI).
4. *Modified MLLMs:* Add high-resolution encoder (CogAgent adds EVA-CLIP-L for 1120x1120 images), any-resolution partitioning (Ferret-UI), shape-adaptive cropping (UI-Hawk), GUI encoder + LayoutLMv3 (MobileFlow).

**Pre-training tasks:** Screen grounding (predict 2D coords/bounding boxes from text), Screen understanding (semantic QA, element identification), OCR (Paddle-OCR extracted text+bounding boxes).

**Data sources:** Public (CommonCrawl HTML, Flickr30K), Synthetic (webpage rendering with A11y tree traversal, cross-platform simulated environments, iterative element interaction yielding directed graphs with 3M+ GUI samples).

**SFT:** Trajectory synthesis via rule-based app traversal + LLM gap-filling, online tutorial → action mapping, webpage navigation graph shortest-path. GPT-4 synthesizes task instructions and CoT reasoning. Grounding data: render HTML source → annotate widgets, use simulators, or GUI detection models. Critical finding: **learning with visual forms outperforms source-code-based learning** (Kil et al., 2024) and **avoids hallucination** (Meng et al., 2024).

**RL:** Early work used RL as feature extractor (MiniWob++ with behavioral priors achieving human-level). Modern paradigm: LLMs-as-agents as policy models. AutoGLM uses self-evolving online curriculum RL with an intermediate interface disentangling planning from grounding. AGILE integrates LLM+memory+tools+executor modules under RL. WebAI fine-tunes T5 with hierarchical planning + multimodal NN via SFT+RL. GLAINTEL uses behavior cloning then PPO on Flan-T5.

### 1.3 Evaluation Architecture

**Step-level:** Operation accuracy, F1, element accuracy, step success rate (stepSR), BLEU/ROUGE/BERTScore for QA tasks.

**Task-level:** Overall Success Rate (SR), Accuracy, Reward function, Step Ratio (agent steps / optimal human steps), API Cost, Execution Time, Peak Memory Allocation.

## 2. Results (Survey Coverage Metrics)

As a survey, this paper's primary "results" are the comprehensiveness of its taxonomy and the gaps it identifies. Key quantitative coverage:

| Dimension | Coverage |
|-----------|----------|
| Foundation models cataloged | 27 (Table 1, spanning 05/2023–10/2024) |
| Agent frameworks cataloged | 27 (Table 2, spanning 09/2022–10/2024) |
| Benchmarks cataloged | 30 (Table 3, spanning 08/2017–06/2024) |
| Architecture types identified | 4 (Existing LLMs, Existing MLLMs, Concatenated MLLMs, Modified MLLMs) |
| Training stages covered | 3 (Pre-training, SFT, RL) |
| Perception grounding types | 3 (Visual, Semantic, Dual) |
| Planning paradigms | 2 (Global, Iterative) |
| Memory source types | 3 (Internal, External, Specific) |
| Action categories | 3 (Input, Navigation, Extended) |
| Evaluation platforms | 3 (Mobile, Desktop, Web) |
| Benchmark settings | 2 (Static, Interactive) |
| Task categories | 3 (GUI Grounding, Information Processing, Agentic) |

**Key aggregated finding:** No single model/framework dominates across all platforms. Cross-platform generalization remains unsolved. The field is split between:
- **Foundation model route:** OS-Atlas, AutoGLM, CogAgent, Ferret-UI, ShowUI (require training but achieve better grounding)
- **Agent framework route:** SeeAct, OS-Copilot, AgentS, WebVoyager (no tuning, prompt-based, more flexible)

**RL convergence observation:** Behavior cloning + PPO is the dominant RL pattern. AutoGLM's self-evolving curriculum RL shows robust error recovery but requires carefully designed intermediate interfaces.

## 3. Trade-Offs

| Dimension | Win | Lose |
|-----------|-----|------|
| **Visual vs. Textual perception** | Screenshots match human interface use; MLLMs enable richer understanding | Requires vision encoders, grounding overhead; text-heavy UIs may lose info to resolution constraints |
| **Foundation model vs. Agent framework** | Fine-tuned models achieve superior grounding accuracy and OOD generalization | Requires training data, compute, platform-specific adaptation; frameworks are zero-shot but less reliable |
| **Global vs. Iterative planning** | Global plans minimize execution time via parallel DAG sub-tasks | Cannot recover from environmental changes; iterative adapts but is slower and may oscillate |
| **Static vs. Interactive evaluation** | Static benchmarks are reproducible and cheap | Cannot assess sequential decision-making; interactive is authentic but non-reproducible, expensive |
| **Simulated vs. Real-world environments** | Simulated avoids reproducibility issues | Fails to capture edge cases and real complexity; real-world is authentic but environments change continuously |
| **SFT vs. RL for training** | SFT is stable, leverages demonstration data | May not generalize beyond demonstrated trajectories; RL explores but is sample-inefficient and reward design is hard |
| **High-res vision vs. Standard resolution** | 1120x1120 input captures small text/icons vital for GUI tasks | Computational cost; most MLLMs are pretrained on 224x224, requiring architectural modification |
| **Memory-rich vs. Memory-light** | Rich memory enables personalization, error recovery, experience reuse | Context window pressure, retrieval latency, stale/inconsistent memory risk |

## 4. Design Rationale

The authors organize the survey around a **capability-first taxonomy** (understanding → planning → grounding) rather than a task-centric or platform-centric one. This is deliberate: OS Agents across mobile, desktop, and web share the same fundamental capabilities despite different action spaces. By abstracting to capabilities, the survey surfaces cross-platform patterns that platform-specific surveys miss.

The foundation-model/agent-framework split (the paper's central organizing principle for construction) reflects a genuine divergence in the field: whether to embed OS knowledge into model weights (training-heavy, more robust) or into prompting/orchestration logic (training-free, more flexible). The authors argue both are necessary and complementary — foundation models handle perception/grounding while frameworks handle planning/memory/adaptation — but note the field has not yet successfully integrated them.

The emphasis on **dual grounding** (visual + semantic) as the most promising perception strategy is grounded in evidence that neither alone suffices: visual-only misses semantics of identical-looking elements; semantic-only misses spatial layout and visual state.

## 5. Limitations and Failure Modes

1. **No quantitative comparison:** As a taxonomy survey, it provides zero head-to-head benchmark numbers between surveyed methods, limiting its prescriptive value.
2. **Rapid obsolescence:** The field moves fast — models from 10/2024 are already superseded. The survey captures a snapshot, not a living evaluation.
3. **Cross-platform generalization gap:** Explicitly identified as unsolved. Models trained on web data struggle on mobile/desktop and vice versa. OS-Atlas attempts cross-platform grounding but remains limited.
4. **Safety defenses are critically underdeveloped:** §5.1.2 states "studies on defenses specific to OS Agents remain limited." WIPI attacks, environmental injection, adversarial pop-ups, and jailbreak transfer all lack robust countermeasures.
5. **Personalization is aspirational:** Memory mechanisms exist (OS-Copilot profiles, user preference storage) but no system demonstrates persistent, privacy-preserving personalization across sessions. Academic access to real user data is the bottleneck.
6. **Evaluation reliability concerns:** LLM-as-a-judge for subjective evaluation has "limitations regarding reliability and controllability." Static benchmarks cannot assess sequential decision quality.
7. **GUI-only focus:** CLI, API-first, and voice-based OS interaction paradigms are not covered.
8. **No multi-agent coordination:** Single-agent paradigm throughout; collaborative OS Agents are not addressed.

## 6. Transfer to Lyra

**The one transferable idea:** The **dual-grounding perception architecture** — combining structured semantic representations (accessibility tree, DOM, API schemas) with screenshot-based visual grounding (Set-of-Mark annotations). Lyra already has strong text/code understanding; adding this dual-channel perception would enable Lyra to interact with arbitrary GUI applications (desktop, web, mobile) the way humans do — using both what elements *are* (semantics) and where/how they *appear* (visual). Specifically, Lyra could use accessibility APIs to build a structured element tree, then augment with screenshot-based visual grounding for elements that have ambiguous or missing accessibility labels.

**Workstream route:** §4.5 (Action/Grounding) — feeds directly into Lyra's action space expansion for GUI automation and OS-level task execution.

**Assessment:**
- **Impact:** 4/5 — GUI automation unlocks a massive range of real-world tasks (web forms, desktop apps, mobile workflows) currently inaccessible to Lyra.
- **Effort:** 4/5 — Requires integrating vision encoders (or calling vision-capable models), implementing SoM annotation, building accessibility tree parsers per platform, and designing the dual-grounding fusion logic.
- **Tier:** **Breakthrough** — OS-level GUI agency is a frontier capability that would significantly differentiate Lyra from text/CLI-only agents. The survey provides a complete blueprint (27 frameworks, 27 models, 30 benchmarks) to guide implementation choices.
