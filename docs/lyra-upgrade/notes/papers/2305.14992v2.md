## 1. Mechanism (Step-by-Step)

RAP frames LLM reasoning as a Markov Decision Process (MDP) and applies Monte Carlo Tree Search (MCTS) to explore the reasoning space. The same frozen LLM is repurposed to serve as both the **world model** (state predictor) and the **reasoning agent** (action proposer).

### Step 1: State and Action Definition
For each task domain, define:
- **State (s)**: The world configuration at a reasoning step. Examples: block arrangement in Blocksworld, intermediate variable values in GSM8K, current fact in PrOntoQA.
- **Action (a)**: A reasoning step that transitions the world. Examples: "pickup orange block," a subquestion like "How old is Mohamed?", selecting a logical rule.

The reasoning process becomes an MDP: s₀ → a₀ → s₁ → a₁ → ... → s_T.

### Step 2: World Model (State Transition)
The LLM is prompted with context c' to predict the next state:
```
s_{t+1} ~ p(s_{t+1} | s_t, a_t, c')
```
In Blocksworld, the LLM generates text describing the new block configuration after an action. In GSM8K, it answers a subquestion to derive a new intermediate variable. In PrOntoQA, it applies one logical rule to get a new fact.

### Step 3: Action Generation
The LLM (as agent) proposes actions conditioned on the current state:
```
a_t ~ p(a | s_t, c)
```
For open-domain problems (math), d candidate actions are sampled from the LLM rather than enumerated.

### Step 4: Reward Design
Four reward types guide the search:
1. **Action Likelihood (r₁)**: Log probability of the action given state and demonstrations. Reflects LLM's "instinct."
2. **State Confidence (r₂)**: For math, proportion of most frequent answer across multiple samples. Higher = more consistent.
3. **Self-Evaluation (r₃)**: Probability of "Yes" token when asking "Is this reasoning step correct?" Enables error recognition post-hoc.
4. **Task-Specific Heuristics (r₄)**: Domain-specific. E.g., in Blocksworld, count of goal conditions met.

Rewards are combined via weighted geometric mean or summation, depending on task.

### Step 5: MCTS Planning (Algorithm 1, 4 phases per iteration)

**Selection**: Navigate from root s₀ to a leaf using UCT (Upper Confidence bounds applied to Trees):
```
a* = argmax_{a ∈ A(s)} [ Q(s, a) + w · sqrt( ln N(s) / N(c(s,a)) ) ]
```
Where N(s) = visit count, c(s,a) = child node, w = exploration weight. Balances exploitation (high Q) vs. exploration (low visit count).

**Expansion**: At the leaf node, sample d possible actions from LLM agent, then use LLM world model to predict the corresponding d next states. Add all as child nodes. Skip if leaf is terminal.

**Simulation (Roll-out)**: From the expanded node, follow a greedy roll-out policy (choose action with max local reward) using a lightweight reward function, predicting next states until terminal state or depth limit L.

**Back-propagation**: Once a terminal state is reached, aggregate rewards along the path to update Q(s,a) for each state-action pair. For GSM8K:
```
Q*(s_t, a_t) = max avg(r_t, ..., r_l)
```
(Uses maximum of average future rewards to avoid penalizing long correct paths.)

The algorithm runs for N iterations (N=10 or 20), then selects the highest-reward root-to-leaf path as the final reasoning trace.

### Step 6: RAP-Aggregation
For answer-only tasks (math), multiple traces from different MCTS iterations are aggregated (voting on final answer). For tasks requiring full proofs (planning, logic), the single best trace is used.

## 3. Trade-offs

| Dimension | Win | Lose |
|-----------|-----|------|
| **Planning accuracy** | 0% → 64% on Blocksworld with same model; beats GPT-4 | — |
| **Math reasoning** | +19.2% over CoT, +4.8% over CoT+SC | — |
| **Logical proof** | +14% proof accuracy over CoT | — |
| **Generality** | Works across planning, math, logic with same framework | Reward design must be adapted per domain |
| **Compute cost** | — | 10-20 MCTS iterations; each iteration: 1 selection + d expansions × (action gen + state pred + reward calc). Multiple LLM calls per iteration. 4× A5000 GPUs used. |
| **Sample efficiency** | RAP(10) with 1 trace beats CoT with 10 samples | More expensive per token than sampling |
| **Scalability** | Works on 33B and 70B models | MCTS with frozen LLM still bounded by base model capability |
| **Long-horizon tasks** | Maintains 0.32 success at 12-step (vs 0.00 CoT) | Drops from 0.75 at 6-step to 0.17 at 10-step (Hard) |
| **Adaptive prompting** | Needed for distribution shift as tree deepens | Adds implementation complexity |

## 4. Design Rationale

**Why world model?** Humans possess an internal world model to simulate actions and anticipate outcomes before acting (Johnson-Laird 1983, LeCun 2022). LLMs lack this — they autoregressively generate reasoning without lookahead or backtracking. By repurposing the LLM itself as a world model (predicting s_{t+1} given s_t, a_t), RAP gives LLMs the ability to "imagine" future states without any external simulator or fine-tuning.

**Why MCTS?** MCTS is proven in game-playing (AlphaGo, MuZero) for balancing exploration vs. exploitation in large search spaces. The UCT formula provides a principled way to prioritize promising branches while ensuring sufficient exploration of alternatives. This is crucial for reasoning tasks where the first intuitive path is often wrong (as shown in the Blocksworld case study). Simpler search strategies (BFS, DFS, as in concurrent Tree-of-Thoughts work) lack this principled balance.

**Why repurpose the same LLM?** Using one frozen LLM for both action proposal and world modeling avoids the complexity of training separate models. The LLM already encodes substantial world knowledge from pretraining. The key is prompting it differently for each role (agent vs. world model).

**Why explicit state representation?** Unlike CoT which only tracks actions, RAP explicitly tracks world state at each step. This enables: (a) recognizing valid actions for the current state, (b) detecting when goals are achieved, (c) reformulating remaining sub-tasks with reduced difficulty (hiding history, presenting current state as new initial state).

## 5. Limitations & Failure Modes

1. **Frozen LLMs only**: No fine-tuning of the world model or agent. Performance bounded by pretraining quality. Future work could fine-tune LLMs specifically for world modeling (Xiang et al., 2023).
2. **Heavy compute**: Each MCTS iteration requires multiple LLM forward passes (action sampling, state prediction, reward computation). N=20 iterations × d actions × multiple samples per reward = substantial cost. Not practical for real-time or latency-sensitive applications.
3. **Non-enumerable action space**: For open-domain tasks, actions are sampled from the LLM rather than enumerated. This means the search space coverage is stochastic and incomplete — important actions may be missed.
4. **Reward hacking / noisy rewards**: Self-evaluation reward depends on the LLM's ability to judge its own outputs. Action likelihood reward works for structured actions (Blocksworld's PICK/STACK patterns) but fails for free-form text (math reasoning), where it adds noise.
5. **Depth-bounded reasoning**: MCTS with depth limit L cannot solve problems requiring more steps than L. The 12-step Blocksworld Hard success rate drops to 0.09.
6. **Distribution mismatch**: As the search tree deepens, remaining sub-problems have fewer required steps. The fixed demonstration pool creates a distribution shift. Mitigated partially by adaptive prompting (Appendix E).
7. **No external tool integration**: The world model is purely the LLM's internal knowledge. Could be augmented with external tools (calculators, code executors, knowledge bases) for more reliable state prediction.
8. **Single-path final output**: For planning/logic tasks, only one trace is returned. If MCTS fails to find a valid path, there is no fallback.

## 6. Transfer to Lyra

### The One Transferable Idea
**LLM-as-World-Model with MCTS for multi-step agent trajectory planning.** Lyra agents currently generate tool-use actions autoregressively (greedy or single-sample). RAP shows that explicitly modeling state transitions and using tree search with reward-guided exploration-exploitation dramatically improves multi-step planning success. For Lyra's agentic loop, this means: (1) maintain explicit world state after each tool call, (2) use the same LLM to simulate "what if" branches of tool-use sequences, (3) score branches with self-evaluation + task rewards, and (4) use UCT to allocate computation to the most promising branches. This is directly applicable to complex multi-turn tool-use tasks where the first intuitive action sequence often fails.

**§4.2 — Agentic Planning & Reasoning Engine**. This paper provides the algorithmic core (MCTS + world model + reward) for the Planning subsystem. It also feeds §4.4 (Evaluation & Self-Critique) via the self-evaluation reward mechanism.
