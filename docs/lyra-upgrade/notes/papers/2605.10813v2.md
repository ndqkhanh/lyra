## 1. Mechanism (step-by-step)

NanoResearch implements a **tri-level co-evolution** framework with an Orchestrator O that coordinates three self-improving subsystems: a SkillBank S, a Memory Module M, and a trainable planner policy π_θ. The framework operates across three pipeline stages, each retrieving context from S and M before execution and updating both stores afterward.

### Three Pipeline Stages

**Stage I — Idea Generation and Planning**: Given a user-specified research topic T and user profile U, the Orchestrator retrieves topic-aligned skills S_I ⊆ S and memories M_I ⊆ M via a heuristic scoring function combining keyword matching, tag alignment, and recency. It produces a high-level plan P_I = Plan(T, U | S_I, M_I). A ReAct-based reasoning loop surveys academic databases (OpenAlex API), parses quantitative evidence from papers via a structured extraction mechanism to mitigate hallucination, identifies research gaps, generates candidate hypotheses H = {h_1, ..., h_K}, and performs automated novelty verification by querying databases to filter prior-work overlaps, yielding the best hypothesis h* ∈ H.

The Planning phase translates h* into a JSON-formatted experiment blueprint B specifying datasets, baselines, architecture, evaluation metrics, and ablation studies. An internal LLM reviewer critiques B for infeasible designs or unfair comparisons, driving iterative refinement: B(t+1) = Refine(B(t), c_B(t), P_P, E), until B passes review or reaches a retry limit. The trajectory is distilled into new skills and memories.

**Stage II — Experimental Validation and Optimization**: The Orchestrator retrieves coding-specific skills S_C ⊆ S and project memories M_C ⊆ M, and produces a coding plan P_C = Plan(B, U | S_C, M_C). A Coding agent instantiates a self-contained codebase W comprising model definitions, training scripts, evaluation pipelines, and cluster submission scripts. An autonomous debugging loop iteratively patches the codebase using S_C and M_C: W(t+1) = Debug(W(t) | S_C, M_C), until execution succeeds or the retry budget is exhausted. Upon success, raw output logs R_raw are parsed into an analysis report A = Analyze(R_raw, B, T). Experimental records (successful or failed) are stored in M with their conditions; generalizable coding/debugging patterns are abstracted into new skills.

**Stage III — Paper Writing and Review**: The Orchestrator retrieves writing-specific skills S_W and project memories M_W to formulate a structured writing plan P_W = Plan(B, A, U | S_W, M_W). The Writing agent drafts the manuscript section-by-section to avoid catastrophic forgetting in long contexts. A Review agent (operating without skill/memory retrieval to ensure unbiased evaluation) critiques the draft on logical coherence, claim validity, and formatting, producing feedback f_R. Iterative revision continues: Draft(t+1) = Revise(Draft(t), f_R(t)), until quality thresholds are met, yielding the final paper P.

### SkillBank S and Memory Module M

**Retrieval Mechanism**: Before each task, O retrieves the top-k skills and memories via a heuristic scoring function:
```
S_C = top-k score(C, s)    M_C = top-k score(C, m)
       s∈S                       m∈M
```
Skill retrieval prioritizes usage frequency and confidence to surface robust strategies (e.g., debugging patterns). Memory retrieval enforces strict condition matching to return only project-specific experiences from comparable settings.

**Update Mechanism**: Upon completing a stage, O distills the trajectory τ (actions, critiques, outcomes) into new entries:
```
S(t+1) = S(t) ∪ Distill_skill(τ)       M(t+1) = M(t) ∪ Summarize_mem(τ)
```
Semantically overlapping entries are merged to prevent unbounded growth, keeping both stores compact.

### Preference Internalization via SDPO

User feedback F is free-form natural language (not scalar rewards or preference pairs), provided at the end of each stage. The Orchestrator's planner model π_θ (Qwen3-8B) is updated via **Self-Distillation Policy Optimization (SDPO)** [Buening et al., 2026], which converts a single feedback instance into a dense token-level learning signal without any reward model or preference annotation.

The SDPO gradient is a logit-level policy gradient:
```
∇_θ L_SDPO(θ) = -E_{y∼π_θ(·|x)} [ Σ E_{ŷ_t∼π_θ(·|x,y_<t)} [ A^SDPO(ŷ_t) · ∇_θ log π_θ(ŷ_t | x, y_<t) ] ]
```
where the token-level advantage is estimated via the self-teacher (feedback-conditioned model):
```
A^SDPO(ŷ_t) = log [ π_θ(ŷ_t | x, F, y_<t) / π_θ(ŷ_t | x, y_<t) ]
```

This updates the planner's parameters to internalize user preferences after each feedback round, enabling progressive preference alignment across cycles.

### Model Assignments
- **Planner (Orchestrator)**: Qwen3-8B (only trainable component)
- **Ideation / Planning / Setup / Execution**: DeepSeek-V3.2
- **Coding / Debugging**: GPT-5.3-Codex
- **Writing / Figure prompt/code generation**: Claude Sonnet 4.6
- **Figure image generation**: Gemini 3.1 Flash
- **Review**: Gemini 3.1 Flash Lite
- **Revision**: Gemini 3 Pro

### Co-evolution Loop
Skills produce richer memory (reliable execution yields varied experiences), richer memory informs better planning (contextualized plans are more precise), and preference internalization continuously realigns the loop to each user. The three levels are necessary together: procedural knowledge without user context cannot differentiate between users; contextual memory without procedural knowledge can diagnose but not prevent recurring failures; and both without preference alignment remain unable to track evolving user intent.

## 4. Design Rationale

The core argument is that personalization in research automation requires **simultaneous adaptation at three distinct levels**, none sufficient alone:

1. **Why a SkillBank (not just memory)**: Existing systems like EvoScientist store episode-level narratives rather than distilled procedural primitives. Narratives are hard to retrieve precisely and conflate task-specific details with generalizable patterns. Skills are compact, condition-tagged, reusable rules (e.g., "write deterministic experiment contract when profile prioritizes reproducibility") that transfer across projects. Without skills, each run starts from scratch.

2. **Why a Memory Module (not just skills)**: Skills are user-agnostic procedural rules. Memory stores user-bound and project-bound facts (past hypotheses, validated configurations, resource constraints) that ground planning in the user's actual research history. Without memory, skills cannot differentiate between users — the same debugging rule fires for everyone.

3. **Why SDPO (not just memory/skills)**: Implicit preferences ("prefer simpler methods", "want more efficiency analysis") are too diffuse to encode as rules and too nuanced to survive compression into memory entries. Standard RLHF/DPO requires scalar rewards or preference pairs — free-form user feedback is neither. SDPO converts a single feedback instance into a dense token-level learning signal using the feedback-conditioned model as a self-teacher, requiring no reward model or preference annotation.

4. **Why tri-level co-evolution (not sequential)**: Ablation shows all three levels are complementary — Planner+SDPO (the strongest partial variant) still underperforms the full system. Skills enable richer memories, richer memories inform better planning, and preference learning realigns the loop — removing any level degrades the whole.

## 5. Limitations & Failure Modes

1. **Domain restriction**: Evaluation is exclusively on AI/ML tasks where research outputs can be fully realized through code and text. Extension to biology, chemistry, or physics (involving physical experimentation and instrument control) is "important and non-trivial" but not addressed.

2. **Incremental innovation ceiling**: Novelty scores max out at 5.645/10 (simulated) and 7.0/10 (human, R2). All benchmark tasks are labeled "incremental_innovation." The system is not designed or evaluated for breakthrough research.

3. **Small human evaluation sample**: Only 3 PhD researchers on 3 tasks. Statistical significance is limited, and inter-expert agreement is not formally assessed (though Table 6 shows individual expert scores).

4. **Simulated evaluator as primary judge**: Main evaluation uses Claude as both the topic generator AND the in-the-loop user, raising potential for self-consistency bias.

5. **Cold-start penalty**: R1 is the most expensive round in GPU time (1.75 hrs) and total cost exceeds EvoScientist. The system only becomes cost-efficient after accumulating skills and memories across multiple cycles.

6. **Novelty regression risk**: Human evaluation shows novelty drops from 7.0 (R2) to 6.667 (R3), suggesting SDPO may overfit to user preferences at the expense of creative exploration.

7. **Feedback burden**: Requires per-stage user feedback. For researchers with limited time, this interaction cost may offset the automation benefit.

8. **Model dependency**: Heterogeneous model routing (6+ different models across stages) creates complex API dependencies and cost structures. Performance may degrade with weaker models or API unavailability.

9. **Merging quality unmeasured**: Semantic overlapping entry merging is described but its accuracy/quality is never quantitatively evaluated — poor merges could silently corrupt the skill/memory stores.

10. **No license specified**: Code and dataset URLs are referenced but no open-source license is declared.

## 6. Transfer to Lyra

**The ONE transferable idea**: The **tri-level co-evolution loop** — procedural skill distillation (SkillBank) + contextual memory retrieval (Memory Module) + label-free preference internalization (SDPO) — is directly applicable to Lyra's multi-agent orchestration. Lyra currently lacks persistent, user-specific memory that shapes planning across sessions. The SkillBank+Memory dual-store pattern (retrieve before each task, distill trajectory afterward, merge overlapping entries) provides a concrete architecture for making Lyra's orchestrator accumulate user-specific experience and generalize procedural patterns across sessions, while SDPO offers a lightweight mechanism to internalize free-form feedback without reward model training.

**Workstream route**: §4.2 (Memory & Context System) — the dual-store architecture and co-evolution loop directly extend the memory subsystem. Also feeds §4.3 (Adaptive Orchestration) via the SDPO preference learning component.

| Dimension | Assessment |
|-----------|-----------|
| **Impact** | 4 (high) — personalized multi-agent orchestration with compounding gains is a key differentiator |
| **Effort** | 4 (high) — requires skill distillation pipeline, memory store with retrieval, and integration of SDPO-style training |
| **Tier** | **breakthrough** — co-evolution across multiple levels is novel for Lyra and addresses a fundamental gap (lack of persistent, personalized context) |

**Implementation sketch for Lyra**:
- Add a **SkillBank** as a compact procedural rule store (key-value, ~2-10 entries per session), updated from trajectory distillation after each major agent action.
- Add a **Memory Module** as a user-and-project-scoped fact store for hypotheses, validated configurations, and resource constraints.
- Implement **retrieve-before-act + update-after-act** as a middleware hook in Lyra's orchestrator.
- For preference learning, adapt SDPO to update Lyra's router/planner using free-form user feedback captured at natural interaction points (not requiring explicit per-stage feedback as NanoResearch does).
