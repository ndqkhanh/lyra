## 1. Mechanism (step-by-step)

MemP treats agent procedural memory as a first-class optimization object with three lifecycle phases: **Build**, **Retrieve**, and **Update**.

### 1.1 Formal Framework (MDP)

Agent-environment interaction is modeled as a Markov Decision Process. At time t, the agent in state s_t chooses action a_t according to policy π(a_t|s_t). The environment returns next state s_{t+1} and reward r_{t+1}.

### 1.2 Build Phase

**Goal:** Convert completed agent trajectories into storable procedural memory.

Three granularity strategies:
- **Trajectory:** Store gold trajectories verbatim (round-by-round action-observation pairs). Filtered to only successful completions.
- **Script:** LLM summarizes gold trajectories into abstract, high-level procedural instructions ("To heat an egg: first locate the fridge and take an egg, then use the microwave...").
- **Proceduralization:** Combines both — the full retrieved trajectory PLUS the abstract script. This is the best-performing strategy.

Builder function: `mp_t = B(τ_t, r_t)` where τ_t is the trajectory and r_t is the reward. The full memory library after T tasks: `Mem = Σ_{t=1}^{T} B(τ_t, r_t)`.

### 1.3 Retrieve Phase

**Goal:** Find the most relevant procedural memory for a new task.

Retrieval uses cosine similarity over vector embeddings:
```
m_retrieved = argmax_{mp_i ∈ Mem} cos_sim(φ(t_new), φ(t_i))
```
where φ is an embedding model (not specified; likely OpenAI embeddings).

Two key-building strategies:
- **Query:** Embed the full task query description as the key. Matches on semantic similarity.
- **AveFact (Average Fact):** LLM extracts keywords from the query, then computes average similarity across all matched keyword vectors. This is the best-performing strategy.

Retrieved memory is prepended to the task context as prior knowledge before LLM execution.

### 1.4 Update Phase

**Goal:** Maintain memory quality as new experiences accumulate.

Three update strategies on a **per-trajectory-group** basis:
- **Vanilla (addition):** Append all new trajectories to memory store (naive merge).
- **Validation (filtering):** Selective consolidation — only successful trajectories are abstracted into memory; failed and noisy trajectories are discarded.
- **Adjustment (reflexion):** When a retrieved memory leads to failure, the erroneous trajectory is combined with the original memory and revised in-place via LLM reflection. This is the **best-performing strategy** — +0.7 points over alternatives and 14-step reduction.

Update function:
```
M(t+1) = U(M(t), E(t), τ_t)
U = Add(M_new) ⊕ Del(M_obs) ⊕ Update(M_est)
```
where M_new = new memories to add, M_obs = obsolete memories to delete, M_est = existing memories to update based on execution feedback E(t).

### 1.5 Key Algorithmic Pattern

The full lifecycle:
1. **Training phase:** Execute tasks, collect trajectories with reward signals
2. **Build:** Convert successful trajectories into Trajectory + Script memory pairs
3. **Store:** Index by AveFact keyword vectors in vector DB
4. **Inference:** For new task, retrieve top-k most similar memories via cosine similarity
5. **Execute:** Prepend retrieved memory to agent context, run task
6. **Feedback:** Collect success/failure signal
7. **Update:** If failure → reflexion-based adjustment; if success and new → validation-based addition; if obsolete → deletion
8. **Repeat** for each new trajectory group

## 3. Trade-offs

| Win | Lose |
|-----|------|
| +48pp dev accuracy on ALFWorld (Proceduralization vs baseline) | Hard Constraint score drops on TravelPlanner (12.88→9.76 with Proceduralization) — memory can bias toward commonsense at expense of strict constraints |
| -8.75 steps per task (37% efficiency gain) | Requires gold trajectories from training set — no cold-start capability |
| -29% token consumption per task | Vector-only retrieval; no BM25/hybrid search (stated limitation) |
| Strong→weak transfer works: +5% for 14B model using GPT-4o memory | Depends on explicit benchmark-supplied reward signals (0/1); cannot self-assess task success |
| Composable with any base LLM (GPT-4o, Claude, Qwen all benefit) | Returns diminish beyond ~20 retrieved memories; context overload at ~25-30 |
| Reflexion-based update is self-correcting | Update requires execution feedback; no offline improvement possible |
| Scales with more retrieved memories (40.7→82.5 across range) | Soft constraint performance trades off against hard constraint adherence |

## 4. Design Rationale

The authors explicitly ground their design in cognitive science: human procedural memory (Gupta & Cohen, 2002; Cohen & Squire, 1980) compiles habitual skills into executable subroutines. The key insight is that existing agent frameworks (LangGraph, AutoGPT, MemoryBank, Soar) provide coarse memory abstractions but **never systematically study the lifecycle** of memory construction, retrieval, and update as first-class optimization targets.

**Why Proceduralization (Trajectory + Script) over either alone:** Concrete examples provide pattern-matching surface cues, while abstract scripts provide generalized principles. The combination gives both — analogous to how humans learn both from specific experiences and from distilled rules.

**Why AveFact over Query embedding:** Averaging keyword-level vectors focuses retrieval on core task elements, filtering out noisy/distracting query details.

**Why Reflexion-based update over validation/filtering:** Error correction in-place (adjustment) preserves the memory's structure while patching its flaws — it is a surgical edit rather than discard-and-replace.

**Why not fine-tuning:** The authors deliberately choose memory augmentation over parameter updates because (a) procedural knowledge should be editable without retraining, (b) different models should share the same memory bank, and (c) catastrophic forgetting is avoided.

## 5. Limitations & Failure Modes

1. **Retrieval limited to vector similarity:** No BM25, hybrid, or structured key-value search. Vector embeddings may miss exact keyword matches critical for procedural recall.

2. **Requires external reward signal:** Memory update depends on benchmark-supplied 0/1 success judgments. In real-world settings without explicit rewards, the system cannot determine which trajectories to keep, revise, or discard.

3. **Hard constraint degradation:** On TravelPlanner, procedural memory improves commonsense compliance but degrades hard constraint satisfaction (HC: 12.88→9.76). Memory may overgeneralize at the expense of task-specific rigid requirements.

4. **Gold trajectory dependency:** Initial memory construction requires curated successful trajectories from a training set. Cannot bootstrap from scratch or from failed attempts alone.

5. **Context window pressure:** Performance peaks at ~20 retrieved memories then declines (82.5→79.3 at 30 memories). Agent context can be overwhelmed by too many retrieved examples.

6. **Single-agent only:** No investigation of shared procedural memory across multiple collaborating agents or memory federation.

7. **Benchmark scope:** Only tested on two simulated environments (TravelPlanner, ALFWorld). No real-world deployment validation.

8. **No explicit forgetting mechanism demonstrated:** While the framework mentions deletion (Del), no empirical results show deliberate pruning of obsolete memories — only addition and revision are measured.

## 6. Transfer to Lyra

**The ONE transferable idea:** A Build-Retrieve-Update procedural memory lifecycle that distills agent trajectories into dual-granularity memories (concrete trajectory + abstract script) with reflexion-based error correction, enabling continuous self-improvement across similar tasks without model retraining.

**Lyra workstream:** §4.2 — Memory (specifically, the procedural/skill memory sub-layer that sits between episodic recall and static system prompts)

**Impact:** 5 — Directly addresses one of Lyra's core architectural gaps: the absence of a learning procedural memory that improves with experience. The dual-granularity approach (concrete + abstract) mirrors Lyra's need for both few-shot examples and reusable skill templates.

**Effort:** 4 — Requires (a) trajectory logging infrastructure, (b) vector DB integration for memory indexing, (c) AveFact keyword extraction pipeline, (d) reflexion-based memory update loop, (e) integration with Lyra's existing memory hierarchy. Non-trivial but architecturally well-bounded.

**Tier:** Breakthrough — Procedural memory with self-correcting update is a capability Lyra currently lacks entirely. Implementing it would give Lyra a learnable skill repository that compounds in value with usage, directly improving task success rates and reducing token expenditure on repeated task families.
