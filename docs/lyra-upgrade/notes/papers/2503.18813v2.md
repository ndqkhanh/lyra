## 1. Mechanism (step-by-step)

CaMeL (CApabilities for MachinE Learning) is a system-level defense against prompt injection that wraps an LLM agent in a capability-based security layer. It does NOT modify the underlying LLM. Instead, it makes the system secure by design through software security principles: Control Flow Integrity, Access Control, and Information Flow Control.

### Step-by-step execution flow

**Step 0 — Architecture:** CaMeL instantiates the Dual LLM pattern (Willison 2023) with two LLM roles:
- **P-LLM (Privileged LLM):** Sees only the trusted user query. Generates pseudo-Python code expressing the control flow (tool call sequence). Has access to all tools. Never sees untrusted data or tool outputs.
- **Q-LLM (Quarantined LLM):** Has NO tool access. Used only to parse unstructured untrusted data into structured output. Exposed to the P-LLM as a function `query_ai_assistant()`. Includes a boolean field `have_enough_information` to signal missing data without communicating specifics (to prevent prompt injection via metadata).

**Step 1 — Plan Generation:**
```
plan ← P-LLM.plan(prompt, tools)
```
The P-LLM receives a system prompt with Python function signatures for all tools + the Q-LLM. It outputs Markdown-fenced Python code. The code must specify Pydantic BaseModel schemas for each Q-LLM call. The P-LLM can use `print()` to show content to the user but cannot read tool output values.

**Step 2 — Custom Python Interpreter:**
CaMeL's custom interpreter uses Python's `ast` module to parse and execute a restricted Python subset. For each AST node:
- Variables store not just values but **CaMeLValue** wrappers containing the raw value + capabilities.
- The interpreter maintains a **data flow graph**: each variable tracks its dependencies. E.g., `c = a + b` makes `c` depend on `a` and `b`.
- Two interpretation modes:
  - **NORMAL:** Standard dependency tracking.
  - **STRICT:** In control-flow constructs (`if`, `for`), all variables assigned inside the block additionally depend on the block's test/iterable. This prevents side-channel leaks.

**Step 3 — Capability Tracking:**
Every value is tagged with metadata (capabilities):
- **Provenance:** Source tags (`User`, `CaMeL`, tool IDs, inner sources like email senders)
- **Allowed readers:** `Public` or a set of user identifiers (email addresses)

Tools are responsible for assigning capabilities on their outputs. For example, a `read_email` tool tags output with the sender as inner source and the recipients as allowed readers. String literals from P-LLM code are tagged as coming from `User`.

**Step 4 — Security Policy Enforcement:**
Before every tool call, the interpreter checks applicable security policies:
```
if policies.check(tool, args, mem) = ⊥ then
    halt execution
```
Policies are expressed as Python functions taking `(tool_name, kwargs)` and returning `Allowed()` or `Denied(reason)`. Example (calendar event policy):
```python
def create_calendar_event_policy(self, tool_name, kwargs):
    participants = kwargs["participants"]
    if is_trusted(participants):  # from User source directly
        return Allowed()
    if not can_readers_read_value(set(participants.raw), kwargs["title"]):
        return Denied("Title not shared with recipients")
    # ... same for description, location, time ...
    return Allowed()
```

**Step 5 — Error Handling with Redaction:**
If execution raises an exception, the P-LLM gets up to 10 retries. Exception messages that depend on untrusted data are **redacted** (to prevent prompt injection via exceptions). The interpreter state persists across retries. No atomicity/rollback for side-effectful tool calls.

**Step 6 — Formal Security Game (PI-SEC):**
CaMeL is formalized as a security game. An adversary A wins if they can craft a state `mem*` causing the Agent to execute any `(tool, args, memstep)` not in the allowed action set `Ω_prompt`. CaMeL's policies approximate `Ω_prompt` without exhaustive enumeration.

### Key algorithms:
- **Dependency graph construction:** Recursive tree-walking on AST, union of dependencies for each expression
- **Capability propagation:** Readers/provenance flow through dependencies; the interpreter computes transitive closure
- **Policy check:** Before tool execution, compute full dependency graph of arguments, check each against registered policies

**Evaluation benchmark:** AgentDojo (Debenedetti et al., 2024b) — Workspace, Banking, Travel, Slack suites.

| Claude 4 Sonnet* (reasoning) | 83.5% | 70.1% | -13.4% |
| o3 High | 84.5% | 77.3% | -7.2% |
| o4 Mini High | 79.4% | 76.3% | -3.1% |
| Gemini 2.5 Pro | 73.2% | 41.2% | -32.0% |
| Gemini 2.5 Flash | 55.7% | 35.1% | -20.6% |

**Security (attack success, out of 949 attacks total):**

| Model | Native API | CaMeL (no policies) | CaMeL (with policies) |
|-------|-----------|---------------------|----------------------|
| Claude 4 Sonnet | 75 | 13 | 11 |

| o3 High | 11 | 1 | 0 |
| o4 Mini High | 2 | 1 | 1 |

The non-zero attacks with CaMeL are NOT real prompt injections — they are text-to-text attacks outside CaMeL's threat model (showing hotel name in reviews to user, transferring money per document instructions).

**Baseline comparison (Claude 3.5 Sonnet):**

| Defense | Overall Utility | Successful Attacks |
|---------|----------------|-------------------|
| Undefended | 90.72% | Not specified (baseline) |
| Prompt Sandwiching | 89.69% | Not zero |
| Spotlighting | 92.78% | >0 |
| Tool Filter | 73.20% | 8 |
| **CaMeL** | **63.92%** | **0** |

**Token overhead:** 2.82x input tokens, 2.73x output tokens (median, Claude 3.5 Sonnet backbone). Spotlighting uses 1.06x input / 0.98x output for comparison.

**Cheaper Q-LLM:** Claude 3.5 Haiku as Q-LLM (with Claude 4 Sonnet P-LLM) → ~1% utility reduction with ~12% cost reduction.

**Policy triggering rates (STRICT mode, benign):** Overall 53.23% (Banking 58.3%, Slack 80%, Workspace 33.3%, Travel 80%). These represent user confirmation prompts that could cause fatigue.

## 3. Trade-offs

| Win | Loss |
|-----|------|
| Attacks reduced from 949 to near-zero (provable security guarantees) | 12-32% utility degradation depending on model (best: -3.1% with o4 Mini) |
| No model modification needed; defense-in-depth compatible | 2.82x input tokens, 2.73x output tokens (highest among defenses) |
| Fine-grained capability-based policies catch data-flow attacks that Dual LLM alone misses | STRICT mode increases policy trigger rate from 33.9% to 53.2%, causing user fatigue |
| Works with ANY backbone LLM, including future models | Cannot solve "data requires action" tasks where P-LLM must read data to plan |
| Provenance tracking enables UI-level trust annotations even for text-to-text attacks | Underdocumented APIs break the system (P-LLM can't know output structure) |
| Complementary to model-level defenses (instruction hierarchy, spotlighting) | All tools must be capability-aware; third-party tools may not participate |
| P-LLM provider never sees sensitive tool outputs (privacy by data minimization) | Q-LLM cannot communicate missing info to P-LLM (blocked to prevent injection vector) |

## 4. Design Rationale

**Why capabilities over model training?** Prior defenses (instruction hierarchy, spotlighting, prompt sandwiching) modify model behavior but provide no formal guarantees — they are probabilistic and fall to adaptive attacks. CaMeL instead provides **structural** guarantees by design: if the P-LLM is never exposed to untrusted data, adversaries cannot hijack control flow. Capabilities then constrain data flow by tracking provenance and allowed readers per-value, enforceable before every tool call.

**Why Python as the planning language?** LLMs are highly competent at writing Python. The `ast` module provides ready-made parsing. A restricted subset prevents dangerous constructs (no function definitions, no recursion, no `time` module, no `eval`).

**Why a custom interpreter instead of CPython?** To intercept every variable assignment and expression evaluation for data-flow tracking. A regular Python interpreter cannot tag values with provenance/metadata or enforce policies at the granularity of individual tool arguments.

**Why STRICT mode?** To prevent side-channel leaks where the NUMBER of tool calls reveals private information. In STRICT mode, every statement inside a conditional block depends on the condition itself, so attempting to call a state-changing tool conditional on private data triggers a policy check.

## 5. Limitations & Failure Modes

1. **Side-channel vulnerabilities:** STRICT mode mitigates some (control-flow leaks, exception-based leaks) but cannot prevent all (e.g., timing channels). The authors explicitly note that complete side-channel elimination is likely impossible.

2. **"Data requires action" failure:** When the P-LLM cannot see the data but the plan depends on data content (e.g., "do what the email says"), CaMeL fails. A nested P-LLM tool could address this but requires extremely strict policies.

3. **Underdocumented APIs:** P-LLM cannot inspect tool output structures it has never seen. This caused the Travel suite performance collapse (25% utility for Claude 3.5 Sonnet).

4. **User fatigue:** STRICT mode triggers policy checks on 53% of tasks. Users may become desensitized and approve malicious actions. De-classification (downgrading security labels) is an unsolved UX problem.

5. **Ecosystem adoption barrier:** All tools must implement capability tagging. This mirrors CHERI's hardware-software stack redesign challenge. Third-party tools that don't support capabilities degrade utility.

6. **No atomicity/rollback:** If a tool with side effects executes and a later policy check fails, there is no undo. Partial state corruption is possible.

7. **Text-to-text attacks out of scope:** Attacks that don't change control/data flow (e.g., phishing text, biased summaries) are explicitly not defended against.

8. **Not zero-shot for new tools:** Each new tool requires a security policy function. Policy maintenance burden grows linearly with tool count.

9. **Exception-based side channels:** Adversaries can potentially trigger exceptions conditional on private data, leaking one bit. STRICT mode partially addresses this but not fully.

## 6. Transfer to Lyra

**The ONE idea:** CaMeL's **capability-based data-flow tracking for tool calls** — where every value carries provenance and allowed-reader metadata, and security policies check the full dependency graph before tool execution — can be adapted to Lyra's tool-calling architecture. Instead of relying solely on prompt-level defenses or model alignment for safety, Lyra could implement a lightweight CaMeL-style interpreter (or policy check layer) that tags tool outputs with provenance, computes transitive dependencies, and enforces per-tool security policies before execution. This is especially relevant because Lyra's architecture already separates planning from execution (similar structural insight), and adding capability tracking would provide **provable guarantees** against data exfiltration from untrusted sources (web pages, user files, API outputs).

**Workstream route:** §4.7 — Safety & Alignment (capability-based security policy enforcement for agent tool calls)

**Impact:** 4 (provable security guarantees, structurally prevents entire class of attacks, defense-in-depth compatible)

**Effort:** 4 (requires custom interpreter or policy-check middleware, tool annotation, dependency graph tracking, per-tool policy authoring)

**Tier:** Breakthrough — the only defense with formal security guarantees against prompt injection; shifts paradigm from "make the model robust" to "make the system robust regardless of model."
