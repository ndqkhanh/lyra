## 1. Mechanism (Step-by-Step)

### Threat Model
The attack exploits a **conjunctive activation** vulnerability in multi-agent LLM pipelines where:
- An attacker controls **only** user-input trigger placement and a hidden template inside one compromised remote agent
- The attacker **does not** modify model weights, the client (orchestrator) agent, or the routing mechanism
- Both the trigger key and the injected template are designed to appear **benign in isolation**
- Harmful behavior activates **only** when routing brings them together at the same compromised agent

### Agentic System Model
Given a user query `x`, the client agent deterministically decomposes it into `S` segments:
```
x → (s₁, s₂, ..., s_S)
```
Each segment `s_i` is routed independently to a remote agent via a stochastic dispatcher:
```
a_i ~ R(s_i; ρ)
```
The routing probability to the compromised agent `a*` is:
```
Pr[a = a* | s] = clip_{[0,1]}(α_acc · I_acc(s) + ρ · I_k(s) · I_acc(s))
```
where `α_acc` is the baseline account-affinity, `ρ` is the attacker-controlled routing bias, `I_acc(s)` indicates account-sensitive semantics, and `I_k(s)` indicates trigger-key presence.

### Trigger and Template Structure
- **Trigger Key** `k`: A discrete token inserted into exactly one segment (`s_j ← s_j ∥ k`). Benign-looking alone.
- **Injected Template** `T(τ)_a*`: Placed in one of three slots at the compromised agent:
  - `τ ∈ {prefix, wrap, suffix}`
  - Prompt construction: `Prompt(s_i) = C_τ(T(τ)_a*, s_i)` where `C_τ` is a deterministic concatenation operator (prefix: template before header+segment; wrap: header+template+segment; suffix: header+segment+template)

### Conjunctive Activation Condition
Attack succeeds iff:
```
∃j ∈ {1,...,S} : (k ∈ s_j) ∧ (a_j = a*)
```
Neither the key alone nor the template alone is sufficient.

### Routing-Aware Counterpart Optimization
Since the deployed LLMs are black boxes and key/template placements are discrete, the authors introduce a **differentiable surrogate objective**:

**Surrogate success:** `ÂSR_both = P_route · P_template`

**Full loss function:**
```
L = -ÂSR_both + λ₁ Σ p_i(1-a_i) + λ₂ρ + λ₃ P_template - λ₄ H(p) - λ₅ H(q)
```
where `H(·)` is entropy, `p_i` are Gumbel-Softmax key-placement probabilities, `q_τ` are template-slot probabilities, and `λ_k` are hyperparameters.

**Optimization:** Gradient descent with temperature annealing under Gumbel-Softmax relaxation. After convergence, discrete configuration `θ* = (argmax p_i, argmax q_τ, ρ)` is recovered.

**Algorithm:**
```
Initialize logits α, β, γ
for t = 1 to T:
    Sample p ← GumbelSoftmax(α)
    Sample q ← GumbelSoftmax(β)
    Compute ρ ← σ(γ)
    Compute loss L
    Update α, β, γ via gradient descent
Return θ* = (argmax p_i, argmax q_τ, ρ)
```

### Four Evaluation Regimes
- **clean:** no key, no template
- **key_only:** key present, template absent
- **template_only:** key absent, template present
- **both:** key AND template present (conjunctive)

Success is measured by `ASR(θ) = E_x [E_R [I(∃j: k∈s_j ∧ a_j=a* ∧ template activates)] ]` using a deterministic marker token `__ACTIVATED__` as activation evidence.

## 3. Trade-offs (Wins vs Loses)

| Wins | Loses |
|------|-------|
| ASR_max reaches **1.0** across all models after full optimization | Attack remains **inherently probabilistic** due to stochastic routing — never deterministic |
| Attack transfers across model families (Gemma→Llama-4→GPT-5-mini) | Requires a **differentiable surrogate** — cannot directly optimize black-box ASR |
| Attack transfers across communication topologies (star, chain, DAG) | Surrogate optimization adds computational overhead (Gumbel-Softmax + gradient descent loop) |
| False activations remain **near zero** (0.07-0.09), so benign inputs unaffected | Routing bias ρ is an **abstract parameter** — real routers may not expose equivalent control |
| Existing guard models (PromptGuard, Llama-Guard) rendered nearly useless | Only tested with **deterministic marker activation** — real-world harm may be more complex |
| System-level controls (tool allowlist, least privilege) only reduce ASR by 15-20% | Requires a compromised remote agent (supply-chain attack prerequisite) |
| **No weight modification needed** — purely prompt-level attack surface | DAG topologies show higher baseline ASR even without optimization (topology sensitivity) |

## 4. Design Rationale

**Why conjunctive (distributed) activation?** Single-component attacks are easily detected by prompt-level guard models. By splitting the malicious signal across a user-side key and a remote-agent template, each component appears benign in isolation, evading per-message classifiers.

**Why prompt-level only (no weight modification)?** This models the most realistic and constrained adversary — a supply-chain compromise of a third-party remote agent that does not require access to model internals or client infrastructure. It demonstrates that vulnerabilities exist even under minimal attacker capability.

**Why topology-aware evaluation?** Prior work evaluated attacks against single agents or fixed topologies. The authors show that attack success varies dramatically across star, chain, and DAG topologies, proving that topology-agnostic safety evaluation is dangerously incomplete.

**Why differentiable surrogate optimization?** Direct optimization of discrete key/template placement is infeasible due to black-box LLMs and stochastic routing. Gumbel-Softmax relaxation converts the discrete search into a continuous gradient-based problem while preserving ranking fidelity (Pearson r=0.995).

**Why the four-regime protocol?** Separating clean, key_only, template_only, and both regimes proves that the attack is genuinely conjunctive — neither component alone causes harm — which distinguishes it from standard prompt injection or single-trigger backdoors.

## 5. Limitations and Failure Modes

1. **Abstract Routing Model:** The probabilistic dispatcher is a simplification. Production systems use classifier-based dispatch, learned policies, retrieval-driven orchestration, or proprietary heuristics. Results are evidence of a **structural vulnerability class**, not a claim about any specific deployed router.

2. **Narrow Threat Model:** Only a single compromised remote agent is studied. Real adversaries may use multiple colluding agents, adaptive templates that evolve over interactions, or multi-turn attack horizons.

3. **Controlled Environment:** Only three open-source backbones (Gemma-2B, Mistral-7B, LLaMA3-8B) plus two transfer models. Limited topologies (star, chain, DAG). Does not capture rich tool ecosystems, longer workflows, or deployment-specific safeguards.

4. **Deterministic Marker-Based Activation:** Activation is detected via a reserved `__ACTIVATED__` token using exact string match. This provides reproducibility but does not exhaust all forms of downstream harm (e.g., subtle policy violations, information leakage without markers).

5. **No Adaptive Defense Evaluation:** Defenses are evaluated statically. Adaptive defenses that monitor routing traces or cross-agent provenance are proposed as future work but not tested.

6. **False Activation Baseline:** While low (0.07-0.09), false activation is not zero, meaning some benign queries could trigger in edge cases, especially in DAG topologies with compound routing uncertainty.

7. **No Real-World Deployment Testing:** All experiments are offline/simulated. The authors explicitly state they did not evaluate against production systems or proprietary services.

## 6. Transfer to Lyra

### The One Transferable Idea

**Cross-agent conjunctive attack surfaces as a first-class safety evaluation dimension.** Lyra's multi-agent pipeline (orchestrator → specialized sub-agents → tool use) creates exactly the kind of topology-dependent, routing-mediated vulnerability that this paper exposes. The key insight: per-message guard models (PromptGuard-style) are **architecturally insufficient** because they inspect messages in isolation, while harmful behavior in Lyra would emerge only from the **conjunction** of a user query segment, routing to a specific agent, and that agent's internal prompt configuration. Lyra should implement **routing-trace-aware safety validation** — not just per-message classification, but cross-agent provenance tracking that monitors whether individually benign components align dangerously when composed.
