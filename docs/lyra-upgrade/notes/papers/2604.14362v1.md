## 1. Mechanism (step-by-step)

APEX-MEM is a **temporal property-graph memory system** for conversational AI. It operates in two phases: **graph construction** (offline) and **query-time retrieval** (online via a multi-tool ReAct agent).

### 1.1 Graph Construction

**Step A — Ontology Design.** A domain-agnostic entity-type hierarchy `T` of 35 classes (Person, Place, Event, Product, Device, CreativeWork, Topic, etc.) inspired by YAGO taxonomies. The graph is a directed property graph `G = (V, E, Π, Λ)` where `Π` maps each node/edge to key-value property pairs and `Λ` assigns an ontology type.

**Step B — Entity Resolution.** For each mention `m` in a conversational turn, the system retrieves top-k candidates from a dense vector index via cosine similarity, then a structured LLM produces a resolution decision `d ∈ {choose_existing, propose_new, none}` with normalized name, type, aliases, confidence score `c ∈ [0,1]`, and rationale. Each entity `e = (n, τ, ρ, id)` has name `n`, type `τ`, conversational role `ρ ∈ {Speaker, Listener, Agent, Mentioned}`, and optional external identifier.

**Step C — Fact Extraction.** Few-shot prompted LLM with schema-constrained generation extracts structured facts `f = (s, p, v, δ, [t_from, t_to], c, E)` from each conversational turn — where `s` = subject entity, `p` = property name (snake_case normalized), `v` = value with data type `δ ∈ {str, int, float, bool, date, datetime, enum, url, list}`, `[t_from, t_to]` = temporal validity interval, `c` ∈ [0,1] = confidence, `E` = evidence set (text spans, turn ids, character spans).

**Step D — Event Anchoring.** All facts are anchored to conversational **events** `ε = (type, T, L, P, F, E_ε)` where `T` = timestamp, `L` = location, `P` = participant entity set, `F` = associated facts, `E_ε` = supporting evidence. This is the key innovation: **append-only** semantics — facts are never overwritten; they are linked to temporally-grounded events. Contradictory facts both persist.

**Step E — Incremental Merge.** A soft-canonicalization function merges each new subgraph `g_i` into the existing graph `G(t+1) ← Merge(G(t), g_i)`. Candidate entities are fused when resolution criteria (name similarity, type compatibility, context overlap) are met. The result is stored in **SQLite** with tables: `entities, properties, facts, events, evidence, turns, event_participants`.

### 1.2 Query-Time Retrieval (Graph QnA Agent)

A ReAct-style agent `π_θ` generates reasoning traces `r_t` and selects actions `a_t` from a tool set at each step.

**Tool 1 — SchemaViewer:** `T_schema : {0,1}^2 → S` exposes the relational schema and provides query recommendations. Acts as a meta-level planner that tells the agent which tables/columns exist and how to do temporal reasoning with SQL.

**Tool 2 — EntityLookup:** `T_ent : Q × N → D_ent` maps a free-text query to top-K entity documents. Each document `d = (id, name, type, latest, anchors, last_anchor, facts)` is a markdown table summarizing recent property values with temporal context via `events.anchor_datetime`. This grounds surface mentions to canonical graph identifiers.

**Tool 3 — GraphSQL:** `T_sql : S_sql × P_sql → R_sql` is a read-only SQL interface over the whitelisted graph tables. Enables precise retrieval via SELECT, JOIN, aggregation, and temporal operators (Julian-day arithmetic). The agent uses this for fact evolution tracking, temporal ordering, duration calculations, and multi-hop traversal. Validated to prevent DDL and writes.

**Tool 4 — Search:** `T_search : Q → C = (E_q, P_q, V_q, T_q)` exposes a hybrid retrieval layer combining dense + lexical search over the entire graph. Returns candidate entities, properties, events/evidence, and relevant conversation turns as a high-relevance subgraph.

**Resolution strategy:** The agent interleaves tool calls to (1) canonize surface forms via EntityLookup, (2) retrieve temporal context via GraphSQL, (3) expand coverage via Search, and (4) emit a final Answer. Critically, **resolution happens at retrieval time**, not construction time: the agent sees all temporally-ordered facts (including superseded ones) and selects the currently-valid answer.

### 1.3 Online Construction Mode

For very long conversations (>10^3 documents), a relevance filter `Relevance(d_i | Q) > Θ_rel` (threshold 0.2) selects documents via semantic+lexical search, then constructs the graph only over the filtered subset `D_rel`.

|---|---|

## 4. Design Rationale

The core insight: **do not resolve temporal contradictions at memory-construction time; resolve them at query time.** This is the append-only design decision.

**Why property graphs over flat text RAG:** RAG treats memory as unstructured text and provides no canonical entity representation, no fact-evolution tracking, and no temporal reasoning primitives. APEX-MEM's property graph gives entities canonical identifiers, temporally-anchored facts, typed properties, and SQL-level temporal operators. The paper shows RAG methods plateau at ~77% on LOCOMO while APEX-MEM reaches 88.88%.

**Why append-only over eager update:** Systems like MIRIX (state merge) and Mem0 (consolidation) lose superseded facts at construction time. APEX-MEM preserves them, enabling "when did X change?" queries. Evidence: +14 to +25pp temporal advantage over eager-update systems.

**Why multi-tool ReAct agent over single retrieval mode:** No single access pattern dominates. EntityLookup provides canonical grounding, GraphSQL provides structured temporal/precise reasoning, Search provides flexible coverage. The ablation shows that adding Search to the first two tools yields +7.55pp overall (77.19% → 87.00%).

**Why SQLite over graph databases:** Pragmatic choice — SQLite provides adequate expressiveness for the current scale. The paper acknowledges future evaluation of native graph databases (e.g., Neo4j) for complex graph traversal.

## 5. Limitations and Failure Modes

1. **Entity-linking failures:** Case study shows failure to resolve implicit spatial relationships ("Le Jules Verne" restaurant → Paris via "Eiffel Tower" context). The system correctly identifies entities but misses contextual associations that require external knowledge (e.g., Wikidata).

2. **GPT4o SQL generation weakness:** GPT4o had critically high error rates in SQLite query generation, requiring explicit error examples in the prompt to reach 86.35% (vs 88.88% for GPT5). The architecture is sensitive to the QnA model's tool-use capability.

3. **SealQA-Hard gap:** 40.15% accuracy on noisy, conflicting multi-document scenarios — well below LOCOMO performance. The system struggles when document-level relevance filtering misses critical context or when contradictions span documents with varying reliability.

4. **Construction cost:** Graph construction requires 3,717 LLM calls per conversation for fact extraction and entity resolution. This is a one-time cost but significant for real-time applications.

5. **Tool call latency:** 20-30 tool calls to converge per question; Claude 4.5 Sonnet is most efficient (84-86% at ~10 calls) but weaker models need more. No intelligent stopping criteria implemented.

6. **Ontology rigidity:** The 35-class ontology is domain-agnostic but fixed. Highly specialized domains (medical, legal, technical) may require custom extensions not yet explored.

7. **Text-only:** No multimodal support (images, audio, video). Cannot ground facts in non-textual conversational evidence.

8. **Adversarial question noise:** Beyond ~20 tool calls, adversarial question accuracy plateaus or degrades — retrieving contradictory evidence introduces uncertainty the agent cannot always resolve.

## 6. Transfer to Lyra

**The ONE transferable idea:** Append-only, temporally-anchored property-graph memory with retrieval-time (not construction-time) conflict resolution. Lyra should adopt a **temporal fact model** where each memory fact carries `[t_from, t_to]` validity intervals and is anchored to a conversation event. Facts are never overwritten — the Lyra memory agent resolves contradictions at query time by selecting the most recent temporally-valid entry, similar to APEX-MEM's GraphSQL temporal queries.

**Workstream route:** §4.2 (Memory) — directly feeds the Lyra memory subsystem design. APEX-MEM provides a concrete architecture for the structured-memory layer that the existing Lyra memory brainstorm (02-memory.md) is exploring.

**Impact:** 4 — High. Memory coherence is a core Lyra capability. Adding temporal fact tracking with append-only semantics would immediately improve Lyra's ability to handle evolving user preferences and correct contradictory information across sessions.

**Effort:** 4 — Significant. Requires (1) implementing a property graph layer (or adapting SQLite schema), (2) building entity resolution + fact extraction pipelines, (3) creating a multi-tool retrieval agent, (4) integrating with Lyra's existing conversation handler. However, the paper provides detailed schemas, prompts, and tool designs that reduce design effort.

**Tier:** **Investigate** — Strong results (+3.5-25pp over alternatives) but high implementation cost. Worth prototyping on a Lyra memory subset first. The append-only design is the highest-value component to test; the full multi-tool agent architecture can be incrementally adopted.
