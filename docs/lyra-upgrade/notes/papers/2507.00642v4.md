## 1. Mechanism (step-by-step)

ChatHLS is a multi-agent framework with three integrated components: HLSTuner (optimization), HLSFixer (debugging), and VODA (self-evolving data augmentation). The base model is Qwen-2.5-Coder-14B-Instruct, fine-tuned on 8× NVIDIA H800-80G GPUs.

### Phase A: HLS-C Generation + Optimization (HLSTuner)

**Step 1 — Input Featurization**: HLSTuner receives source HLS-C code, design metadata (array dimensions, loop trip counts), and initial QoR including latency (cycles) and resource utilization percentages (DSP, LUT, FF).

**Step 2 — Directive Space Definition**: Supports three directive types with configurations:
- `PIPELINE`: "off" / "on" (for overlapping loop iterations)
- `UNROLL`: integer factor (for replicating loop bodies)
- `ARRAY_PARTITION`: type ∈ {"complete", "block", "cyclic"}, integer factor

**Step 3 — QoR-Aware Reasoning**: The fine-tuned LLM ② performs constrained analysis. It estimates impacts qualitatively (e.g., "applying PIPELINE to deeply nested loops significantly increases DSP and LUT consumption"), then formulates a plan specifying: (1) directive combination with types/factors, (2) target code segments, (3) insertion actions. An insertion agent executes the plan.

**Step 4 — Iterative Refinement**: If initial attempt fails to meet performance targets, HLSTuner activates refinement with current directives + resulting QoR. It scales parallelism up/down: if utilization exceeds 80% budget, it halves parallelism; if idle DSP/LUT exist, it increases parallelism of deeply nested loops. Maximum 5 iterations per kernel, 15 trials total.

**Training Strategy for HLSTuner**:
1. NSGA-II generates diverse optimized HLS designs with corresponding QoR reports from 20 Rosetta kernels
2. Teacher model (DeepSeek-V3.2) produces optimization CoT: analyzes QoR variations, identifies data dependencies for PIPELINE choices, balances memory bandwidth with ARRAY_PARTITION, evaluates parallel architectures
3. Dataset: 4,804 (source HLS-C, inserted directives, optimization CoT) tuples
4. SFT: full parameter tuning, 3 epochs, lr=1e-5, AdamW, cosine schedule, DeepSpeed ZeRO-3

### Phase B: HLS-C Debugging (HLSFixer)

**Step 1 — Error Parsing**: HLS tool output (thousands of lines) is parsed via regex + keyword matching to extract structured error messages (pass/fail status, failure classification, specific error lines).

**Step 2 — Reasoning-to-Instruction Analysis**: Fine-tuned analysis LLM ③ receives (buggy code + parsed error message). It produces structured output within `<reasoning>` and `<instruction>` tags:
- `<reasoning>`: step-by-step diagnosis — identify error lines, analyze root causes, form hypotheses, validate, reflect
- `<instruction>`: exact error line, cause explanation, precise modification action

**Step 3 — Code Modification**: A separate fixing agent (DeepSeek-V3.2, temperature 0.1) applies the instructions strictly.

**Step 4 — Multifaceted Evaluation (fallback)**: When LLM ③ fails, LLM Group ⑤ (GPT-5, Claude-opus-4.5, Qwen3-8B) generates 3 diverse debugging instructions. Scoring agent ⑥ (Gemini-3-pro) evaluates candidates on clarity, logical soundness, error message alignment, and code modification scope, selecting the best.

**Step 5 — Verification**: Corrected code runs CSIM → CSYN → COSIM against golden testbench. All three must pass.

**Training Strategy for HLSFixer**:
1. Dataset construction via VODA: 10,878 buggy code samples covering 33 error types from 35 base designs (Kernel, Vitis, Manual)
2. Teacher model (LLM ⑨) reviews correct HLS-C, pairs buggy segments with error messages, constructs debugging CoT
3. SFT: 3 epochs, lr=1e-5, per-device batch 1, 2 gradient accumulation steps, 72 minutes
4. DPO: 3,716 preference pairs (CoT vs non-CoT where error messages were removed). LoRA rank=8, 2 epochs, lr=5e-6, β=0.1, sigmoid loss. This teaches the model to rely on parsed error messages rather than guessing.

### Phase C: Self-Evolving Data (VODA)

**BugRAG**: Repository of 33 modular error slices across 5 categories (HLS-C Incompatible, Simulation, Compilation, Functional, Directive Errors). Each slice has mnemonic identifiers, descriptions, error examples, root cause analysis. Uses dense retrieval (all-MiniLM-L6-v2, Chroma vector store, top-k=2).

**Expansion workflow**:
1. When HLS design fails verification, inspection agent (LLM ⑩) examines erroneous code + error messages
2. Generates error slice (description, examples, analysis)
3. Queries BugRAG for existing entries; if unmatched, identifies new error type and integrates slice
4. Insertion agent (LLM ⑧) generates buggy code by injecting retrieved error slices as context

### Equations

Pass@k metric:
```
pass@k := Ei[1 − C(n-c*i, k) / C(n, k)]
```
Where c*i = number of correct samples, n = total samples, k = subset evaluated.

Speedup metric:
```
Speedup = Lat(H, λ(θ_baseline)) / Lat(H, λ(θ_optimized))
subject to Util_r(λ) ≤ 80%, ∀r ∈ {DSP, FF, LUT}
```

## 3. Trade-offs

| Win | Lose |
|-----|------|
| 93.4% debug pass@1 vs 66.3% (DeepSeek-V3.2) — **27.1pp absolute gain** | Higher resource utilization vs expert DSL methods (Gemm DSP: 49.9% vs Allo 4.5%) |
| 18.1× geo mean speedup — **3.3× over RAG methods** | Single vendor (Xilinx ZCU106); no cross-FPGA portability validated |
| Debugging time: person-weeks → <10 minutes | Requires 8× H800-80G GPUs + 72 min training (SFT) + 30 min (DPO) |
| No source code modification needed (directive-level only) | Cannot handle DATAFLOW directives or AXI interfaces |
| ≤5 iterations to converge vs 100 for HGBO-DSE | Only validated on loop/array parallelism; not general HLS constructs |
| Self-evolving (VODA continuously expands error coverage) | DPO training risk: overfitting to specific error-message formats from one vendor tool |
| 41.8% relative improvement over Gemini-3-pro in generation | GPT-5.1 + RAG still cannot match fine-tuned specialist (RALAD 5.5× vs HLSTuner 18.1×) |

## 4. Design Rationale

**Why multi-agent instead of single model**: The authors decompose HLS design into generation, optimization, and debugging because each requires distinct reasoning patterns — QoR-aware causal reasoning for optimization vs error-message-grounded diagnosis for debugging. A single model conflates these reasoning modes.

**Why fine-tuning over RAG-only**: RAG provides domain knowledge but LLMs lack the reasoning patterns to apply it correctly. Evidence: RAG improves Gemini-3-pro debugging from 70.4% to 84.5%, yet HLSFixer (fine-tuned) achieves 93.4%. Critically, RAG-2 (full training set as retrieval corpus) performs *worse* than RAG-1 (compact knowledge + structured error slices), showing that retrieval noise degrades reasoning.

**Why DPO with error-message removal**: The rejected (non-CoT) samples remove error messages during CoT generation, forcing the model to guess. The preferred samples keep error messages. DPO teaches the model to ground reasoning in tool feedback rather than its priors — directly addressing LLM hallucination in specialized domains.

**Why directive-level only (no code refactoring)**: Unconstrained structural rewriting by LLMs can introduce functional deviations that are difficult to attribute from synthesis logs alone. Directive-level transformations preserve kernel semantics while covering the standard HLS DSE problem.

**Why qualitative QoR reasoning over quantitative prediction**: Hardware platform differences affect resource budgets, not the causal relationship between directives and performance. Learning "UNROLL increases parallelism → reduces latency → costs DSP/LUT" generalizes; fitting to absolute latency numbers overfits.

## 5. Limitations & Failure Modes

1. **Narrow directive scope**: Only loop/array parallelism (PIPELINE, UNROLL, ARRAY_PARTITION). No DATAFLOW for producer-consumer task parallelism, no AXI interface directives for FPGA IP deployment. Limits applicability to streaming/control-heavy designs.

2. **Single-platform validation**: Only tested on Xilinx ZCU106 MPSoC @ 100MHz with Vitis HLS 2022.1. Intel/Altera or ASIC flows may produce different error messages and QoR behaviors, breaking the trained models.

3. **Resource efficiency gap**: HLSTuner's optimized designs can consume significantly more resources than hand-tuned DSL approaches (DSP: 49.9% vs 4.5% for Gemm on Allo). The 80% utilization budget is a coarse constraint; fine-grained resource budgeting is not supported.

4. **Training data cost**: Requires pre-existing golden designs with verified testbenches for both CoT generation (HLSTuner) and bug injection (HLSFixer). Cannot bootstrap from zero.

5. **VODA cold-start problem**: BugRAG starts with 33 error types. Novel error categories discovered at runtime require human-in-the-loop verification before integration.

6. **Synthesis latency remains**: Each optimization iteration still requires full HLS synthesis (minutes to hours per trial). The paper mitigates this with ≤5 iterations, but the wall-clock cost of synthesis dominates.

7. **Temperature sensitivity**: The fixing agent uses temperature 0.1 for "strict instruction adherence." Higher temperatures may cause the agent to deviate from debugging instructions, introducing new errors.

8. **No guarantee of semantic preservation**: COSIM verification catches functional equivalence violations, but a passing COSIM does not guarantee identical behavior under all inputs — only that the specific testbench passes.

## 6. Transfer to Lyra

### The ONE Transferable Idea

**DPO-grounded error analysis with reasoning-to-instruction**: Train a small specialist model (via SFT + DPO) that maps structured error logs to precise modification instructions. For DPO, construct preference pairs where the preferred sample includes the actual error message in its reasoning chain and the rejected sample omits it — this teaches the model to ground diagnosis in tool feedback rather than its priors. When the specialist fails, use an LLM-as-a-judge fallback: generate N diverse fixes from different strong models, then score on clarity/logical-soundness/alignment-with-error/scope-minimality.

### Lyra Application

This directly maps to Lyra's **tool-use error recovery**: when a Lyra agent's tool call fails (API error, schema mismatch, parameter violation), a fine-tuned analysis agent could parse the error, produce a structured fix instruction, and route it to a strict fixing agent — replacing today's coarse retry loops with targeted repair.
