## 1. Mechanism (Step-by-Step)

### Core Insight
User activity is not natively text — it is a structured event stream of `(actor, verb, object, timestamp)` tuples. Rendering this as text for an LLM trigger is a "round-trip the system never had to take." The paper treats the always-on signal as graph updates and uses a temporal-graph-learning (TGL) model as the encoder.

### Architecture (Two Heads on One Backbone)

**Step 1: Graph Construction (Deterministic)**
- Input: timestamped desktop activity stream (e.g., "The user opened `email_filter.py` in Visual Studio Code.")
- Rule-based extractor maps each event to:
  - **Event nodes** (temporal, one per event)
  - **Entity nodes**: app, file, url, query, artifact (from regex/categorical rules over OS-known ontologies)
  - **Type nodes** (schema-level): `file_ext:py`, `file_topic:code`, `url_domain`, `query_lang:en`, etc.
  - **Edges**: `has_entity` (event→entity), `belongs_to` (reverse), `forward` (t→t+1), `backward` (t+1→t), self-loops
- Same graph construction rules at train and test time

**Step 2: Node Featurization**
- `text_emb`: 768-d frozen BGE sentence embedding (entity surface label / event text)
- `type_emb`: 32-d learned embedding indexed by node type
- `dt_emb`: 32-d learned MLP over log(1 + seconds_since_prev_event)
- Concatenated → 832-d → Linear projection to 256-d GNN hidden dim

**Step 3: TGL Encoder Backbone**
- 3× relation-aware GATv2 layers (Brody et al., 2022)
- 4 attention heads, head dim 64, concatenated → 256-d output
- 32-d edge relation embedding fed into attention
- Residual + LayerNorm + GELU + dropout 0.2 around each layer
- Jumping Knowledge head (Xu et al., 2018): concatenate input projection + all layer outputs → 1024-d

**Step 4: Two Readout Heads (Shared Hidden State)**
- **Trigger head** (on event nodes): produces `p_trig(t)` — a scalar probability via sigmoid
- **Routing head** (on entity nodes): produces `s_rout(v)` — per-entity relevance score
- Both read from the SAME hidden state in ONE forward pass

**Step 5: Training Objective**
```
L_trig = BCE(logit_trig, y_trig; w_pos = 0.15)
L_rout = BCE(logit_rout, y_rout)
L = 0.3 * L_trig + 1.0 * L_rout
```
- Trigger labels: 1 if assistant proposed non-null task at this event, else 0
- Routing labels: entities matched from proposed-task text back to graph nodes (deterministic extractor on task string)
- AdamW, lr=3×10⁻⁴, weight decay=10⁻⁴, batch 32 sessions, 2 epochs
- Trainable params: 1.16M (plus 109M frozen BGE encoder)

**Step 6: Inference Gating**
- One forward pass per event: `p_trig(t) ≥ τ` → FIRE, forward top-k routing entities as structured context to downstream LLM
- `p_trig(t) < τ` → ABSTAIN, no LLM call
- Threshold τ = natural sigmoid decision boundary (≈0.5), fixed across ALL 14 backbones
- Causal masking: backward temporal edges dropped at inference

### Key Design Properties
- Trigger and routing share hidden state → cannot drift apart
- Single checkpoint serves every downstream language agent
- ~220 MiB BF16 resident footprint — deployable on-device alongside privacy-sensitive activity stream
- Per-session graphs capped at 64 events

- **Disabling trigger (always fire)**: -3.2 F1 mean vs Ours — trigger suppresses false-alarm wedge

- **Prompt-only (No TGL)**: -12.7 F1 mean vs Ours — trigger + routing together carry the lift

## 3. Trade-offs (Wins vs Loses)

| Wins | Loses |
|------|-------|
| **Speed**: 4-353× faster triggering vs LLM approaches; 11.13ms/event on GPU server | **Narrow scope**: Only solves trigger+routing; downstream task execution is still an LLM call |
| **Memory**: ~220 MiB BF16 — 75× smaller than 8B LLM trigger; fits on-device | **Requires structured input**: Needs deterministic graph construction; activity stream must be parseable |
| **Calibration**: Continuous probability distribution (0% extremes) vs LLM/BGE collapse to [0,0.05)∪[0.95,1] | **No user study**: Evaluated only via offline RM judge; subjective interruption quality unknown |
| **Single-threshold deployment**: Trigger std=0.035 — one threshold serves 14 diverse backbones | **Text-serialized reconstruction**: Regex extractor recovers entities from rendered logs; real deploy needs OS APIs |
| **Privacy**: On-device deployment keeps file names/URLs/queries within user's trust boundary | **Smaller lift on strongest models**: GPT-5.4 (+3.1), Claude-Opus-4.7 (+5.4) — these self-regulate well already |
| **Composability**: Drop-in trigger works with any downstream LLM; no retraining, no prompt change | **Training needs activity data**: Requires labeled fire/skip events from benchmark training split |
| **Zero backbone regression**: F1 improves on every one of 14 tested backbones | **Limited benchmark coverage**: Only ProactiveAgent (desktop) and FingerTip-20K (mobile) tested |
| **Graceful hardware degradation**: Only ~25% latency increase from server→laptop (vs ~4-14× for LLM) | **Fairness analysis incomplete**: FingerTip demographic subgroups not audited |

## 4. Design Rationale

**Why graph instead of text?** Activity streams are natively structured `(actor, verb, object, timestamp)` tuples. The OS already maintains this in graph form. Rendering it as text and asking an LLM to recover the structure is a wasteful round-trip. The same entities recur across events (same file at t=3 and t=17), and events touch multiple entities at once — flattening to tokens loses event-entity many-to-many structure. A temporal graph is the native representation.

**Why two heads on one backbone?** Trigger and routing decisions must agree on evidence. When trigger and context modules are separate stages, "the wake-up signal and the evidence supporting it can disagree." Sharing hidden state prevents this drift. The ablation proves this matters: random routing reduces F1 by mean 8.6 points even with trigger and prompt unchanged.

**Why GNN instead of LLM for the always-on path?** The trigger runs on every event (~5,760/day at demo polling rate). If it is an LLM, this becomes the most expensive component — 240 decisions/hour paying full LLM cost regardless of whether a task is generated. A small GNN handles it at orders-of-magnitude lower per-event cost, reserving the LLM for what it is good at: turning structured handoffs into fluent user-facing sentences.

**Why deterministic rule-based graph construction?** Activity-log events are templated by construction — users don't write free-form prose about their clicks. Standard NER pipelines hallucinate entities the template never emitted; regex/categorical rules reverse the rendering cleanly.

## 5. Limitations & Failure Modes

1. **Scope**: Only trigger + routing are addressed. Downstream task execution, planning, tool use, and multi-turn agent behavior are out of scope.
2. **Evaluation protocol**: Assessed via offline reward-model judge from ProactiveAgent. No real-time deployment study, no user-subjective interruption-quality measurement, no A/B test against human baselines.
3. **Data dependency**: Entity extractor requires platform-specific ontology (app registry, MIME database, TLD conventions). A deployment on a new platform needs the extraction rules ported.
4. **Privacy surface**: Always-on activity logs (file names, URLs, search queries, demographic profiles on FingerTip) flow through the trigger and routing heads. On-device deployment mitigates but does not eliminate privacy concerns. Production deployment needs data minimization, sensitive-entity filtering, opt-out, and retention controls.
5. **Fairness**: Demographic subgroup analysis across FingerTip's gender/age/occupation/location/device dimensions not performed before use as routing features.
6. **Graph construction fragility**: Text-serialized reconstruction relies on regex patterns matching the logger's template grammar. Changes to the template break extraction unless the platform exposes structured data directly.
7. **Train/test leakage potential**: Category-level entities (VSCode, `file_ext:py`) recur across split — expected but could inflate routing scores on common platforms.
8. **Trigger threshold sensitivity**: Fixed at sigmoid 0.5; no per-user or per-backbone calibration explored.
9. **Session graph cap**: 64 events maximum — very long sessions truncated.
10. **Limited platform diversity**: Only desktop (ProactiveAgent) and mobile (FingerTip-20K) — no web, kiosk, automotive, or IoT scenarios.

## 6. Transfer to Lyra

### The One Idea
**Replace LLM-as-gate with a lightweight structured-data encoder on the always-on path.** Lyra's agent loop could use a small GNN (or simpler temporal model) to decide *when* to invoke the full reasoning LLM, based on structured conversation/context state rather than text-serialized prompt prefixes. The trigger+routing decomposition maps directly to Lyra's gating decision (should the agent act now?) and context selection (what evidence should accompany the call?). Even a frozen BGE encoder + 2-layer MLP over typed conversation entities (speaker, file, tool_call, timestamp) could substantially reduce per-turn LLM cost while improving grounding.
