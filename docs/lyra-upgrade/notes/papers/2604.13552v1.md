## 1. Mechanism (step-by-step)

TF-TTCL is a **training-free, gradient-free, black-box compatible** test-time adaptation framework. It enables a **frozen LLM** to self-improve online by distilling supervision from its own inference experiences. The core insight: the **semantic gap between superior and inferior outputs** contains rich supervisory signal, which can be distilled into explicit textual rules instead of gradient updates.

### System Architecture: "Explore-Reflect-Steer" Loop

The framework has **three modules** and one persistent **Experience Rule Repository R** (starts empty, populated online):

#### Module 1: Semantic Query Augmentation (SQA) — "Explore"

A multi-agent role-playing strategy using a **single frozen LLM** with different system prompts and decoding configs:

- **TEACHER (T):** Uses **greedy decoding (temperature=0.0)**. Produces a stable, high-confidence anchor response `yt^T` from the original query `xt` and retrieved rules `rret`.
- **TUTOR (A):** Rewrites `xt` into **N=4** stylistically distinct variants `{xt^(n)}` to simulate input distribution shifts, preserving semantics but varying surface form.
- **STUDENT (S):** Samples a response for each variant with **temperature=0.7, top-p=0.9**, conditioned on the same `rret`.

This produces a **candidate set** `Yt = {yt^T, yt^(1), ..., yt^(N)}`.

#### Module 2: Contrastive Experience Distillation (CED) — "Reflect"

A two-stage mechanism that identifies reliable positives and informative (hard) negatives from `Yt`:

**Stage 1 — Consistency-Based Candidate Partitioning:**

Two regimes:
- **Closed-ended Reasoning Task (CRT):** Majority voting on answers. If all answers differ → skip (hallucination guard). If all same → all as positive. Otherwise → largest cluster = positive, rest = negative.
- **Open-ended Evaluation Task (OET):** Use TEACHER output `yt^T` as semantic anchor. Compute embedding cosine similarity. Top-50% → positive (Y+), bottom-50% → negative (Y-).

**Stage 2 — Uncertainty-Aware Sample Selection:**

Use **sequence-level perplexity (PPL)** as a confidence proxy:
```
P(y) = exp( -1/L * Σ(i=1 to L) log Mθ(y[i] | x, y[1:i-1]) )
```
- **Positive sample:** `yt+ = argmin_{y∈Y+} P(y)` — the candidate the model is most confident about among positives.
- **Negative sample:** `yt- = argmin_{y∈Y-} P(y)` — the **hard negative** the model is most confidently wrong about. This choice is motivated by findings that LLMs produce confident hallucinations; targeting these provides the strongest signal to rectify the decision boundary.

**Stage 3 — Contrastive Rule Summarization:**

The LLM summarizer (same model, different prompt) distills the gap between `yt+` and `yt-` into two explicit rules:
```
{rt+, rt-} = Summary(xt, yt+, yt-)
```
- **Positive rule `rt+`:** What to do (e.g., "Divide total quantity by number of recipients").
- **Negative rule `rt-`:** What to avoid (e.g., "Avoid dividing by only number of 'friends' while neglecting the subject").
Rules are appended to repository: `R ← R ∪ {rt+, rt-}`.

#### Module 3: Contextual Rule Retrieval (CRR) — "Steer"

- Maintain **two disjoint memory sets:** `Rpos` and `Rneg`.
- Each entry stored as key-value pair: `(e = Embed(r), r)` using **Qwen-3-0.6B-Embedding**.
- At inference, compute `et = Embed(xt)`, retrieve **Top-K=30 positive** and **Top-K=30 negative** rules via cosine similarity.
- Retrieved context `rret` is structured with explicit headers: positive rules (do this) and negative rules (avoid that).
- **Pruning:** Similarity-based FIFO to cap at **1,000 rules** to prevent unbounded growth.

#### Algorithm (Pseudocode from paper):
```
R ← ∅
for each query xt in Dtest:
    rret ← retrieve top-K rules from R via cosine sim
    yt^T ← TEACHER(xt, rret)                    # Greedy anchor
    Yt ← {yt^T}
    {xt^(n)} ← TUTOR(xt)                        # N=4 variants
    for n = 1 to N:
        yt^(n) ← STUDENT(xt^(n), rret)           # Sampled
        Yt ← Yt ∪ {yt^(n)}
    Partition Yt into Y+ and Y-
    yt+ ← argmin_{y∈Y+} P(y)
    yt- ← argmin_{y∈Y-} P(y)
    yt ← yt+                                     # Output best
    {rt+, rt-} ← Summary(xt, yt+, yt-)
    R ← R ∪ {rt+, rt-}
```

#### Key Design Decisions:
- **Online, single-pass protocol:** Each query answered immediately — no multi-pass iteration over test data.
- **Parallel execution:** TUTOR and STUDENT run in parallel (4.11s total vs 10.25s sequential). Rule summarization (0.39s) runs asynchronously in background — user-perceived latency only 2.01× a single LLM call.
- **Contrastive signal at context level** (not parameter or logit level): The framework neither updates weights nor alters decoding probabilities; it embeds retrieved rules as semantic anchors in the prompt.

## 3. Trade-offs

| Win | Lose |
|-----|------|
| **Training-free:** No gradient access needed; works on black-box API models (Qwen-Plus, DeepSeek-V3.2) | **Latency overhead:** 2.01× single-call latency (4.11s vs 2.05s) — though async summarization keeps this bounded |
| **External-knowledge-free:** No curated databases, no ground-truth verifiers, no code executors | **Diminishing exploration returns:** Weaker backbone models benefit more; gains shrink near capability ceiling |
| **Online, single-pass:** Each query answered immediately — unlike multi-pass TTRL which iterates over the full dataset first | **Saturation at high capability:** Absolute gains shrink on >70B models (though RER remains ~50%) |
| **Unsupervised signal:** Self-derived contrastive supervision avoids LLM-as-Judge self-confirmation bias | **TUTOR quality ceiling:** Noise accumulation when TUTOR produces low-quality rewrites beyond N=4 samples |
| **Negative rules as decision boundaries:** Explicitly learning from errors provides stronger signals than positive reinforcement alone | **Context window pressure:** Rules compete with inference tokens; pruning (1K cap) is necessary but may discard useful older rules |
| **Robust on weak backbones:** +13.19% on 3B model without catastrophic degradation | **One-shot rule injection:** No progressive disclosure; all rules injected at once — potential for context dilution in long reasoning chains |
| **Works on CRT and OET:** Contrastive signals adapt to both deterministic and open-ended tasks | **TF-GRPO beats TF-TTCL on some CRT with verifiable ground truth** (when such rewards exist, RL-based methods can optimize more aggressively) |

## 4. Design Rationale

**Why contrastive learning at context level (not parameter or logit level)?**
- Parameter updates require white-box access (not available for API models) and incur GPU memory/time overhead during inference.
- Logit-level contrastive decoding (e.g., Contrastive Decoding) only biases token selection at generation time — it cannot transfer learning across queries.
- Context-level contrastive rules stored in memory provide persistent, reusable, and query-conditional guidance that accumulates over the test stream.

**Why self-derived supervision instead of external guidance?**
- External knowledge (RAG databases, unit tests, code executors) is not always available in deployment.
- LLM-as-Judge without deterministic feedback suffers severe **self-confirmation bias** (Table 14: 82.64 vs 87.49 on GSM8k).
- The relative gap between superior and inferior model outputs contains rich contrastive signal — inspired by human reflective learning from errors (Schön, 1983) and contrastive learning (SimCLR, MoCo).

**Why hard negatives (min-PPL from negative candidates)?**
- LLMs produce confident hallucinations. Selecting the *most* confident error (lowest PPL in negative set) provides the strongest boundary-rectification signal (Robinson et al., 2021).
- Min-entropy selects for repetitive/fluent but wrong outputs; min-PPL accounts for sequence-level coherence and better targets confident hallucinations.

**Why separate positive/negative rule repositories?**
- Prevents confusion: positive rules reinforce correct patterns, negative rules act as "interdiction signals" that prune known error paths.
- Ablation shows negative rules contribute more than positive rules — they provide unique corrective knowledge the model doesn't already possess.

## 5. Limitations & Failure Modes

1. **Diminishing exploration returns:** As the model approaches its capability ceiling, marginal gains from additional query augmentation decline (saturation). A stronger TUTOR model helps but only delays the plateau.

2. **One-shot rule injection:** All retrieved rules are injected at once into the prompt — the paper acknowledges this is suboptimal for long-horizon reasoning and suggests **progressive disclosure** (e.g., Agent Skills-style stepwise rule injection) as future work.

3. **TUTOR quality bottleneck:** Beyond N=4 student samples, noise accumulation from TUTOR's rewrite quality degrades performance. The framework is ultimately bounded by the backbone model's own capability.

4. **No catastrophic degradation guard (implicit only):** The paper claims robustness on weak backbones (+13.19% on 3B) but does not explicitly analyze cases where the self-distillation loop could reinforce errors if the initial candidate partitions are systematically wrong.

5. **Adversarial vulnerability:** The flexibility in handling input configurations may increase vulnerability to adversarial prompt injections. The authors recommend combining with input validation and safety filters, but do not empirically evaluate this.

6. **CRT vs OET regime dependency:** The candidate partitioning strategy changes fundamentally between CRT (majority voting) and OET (semantic similarity to TEACHER anchor). The framework does not auto-detect which regime to use — it must be configured per task.

7. **Context window competition:** Retrieved rules compete with actual inference tokens. The 1K-rule pruning cap is a heuristic; mismanagement could lead to rule starvation (too few rules) or noise (too many irrelevant rules).

8. **No convergence guarantees:** The repository grows monotonically (bounded by FIFO pruning). There is no theoretical analysis of when the system stabilizes or whether the accumulated rules converge to an optimal policy.

## 6. Transfer to Lyra

### The ONE Transferable Idea

**Contrastive Experience Distillation as a context-level "semantic gradient" for frozen agents.**

Lyra can adopt the core mechanism of TF-TTCL: maintain a persistent rule repository that distills the gap between successful and failed tool-use trajectories into explicit positive/negative textual rules. After each tool invocation or agent action, summarize what worked (positive rule) and what failed (negative rule), store with embeddings, and retrieve relevant rules at the start of each new subtask. This enables Lyra to **self-improve online without fine-tuning**, accumulating agent-specific operational knowledge across sessions.

**Why this fits Lyra:**
- Lyra already has agent loops, tool-use patterns, and prompt engineering infrastructure.
- The "Explore-Reflect-Steer" loop maps naturally to Lyra's existing agent orchestration: explore via multiple reasoning paths, reflect by comparing outcomes, steer via rule injection into future prompts.
- No gradient access needed — works with API-based models Lyra may use.
- The "negative rules as interdiction signals" pattern is especially valuable for avoiding known failure modes in tool calling (e.g., wrong tool selection, parameter hallucinations).

### Workstream Route: §4.2 (Memory & Experience) or §4.5 (Agent Reasoning)

Primary fit is **§4.2 Memory & Experience** — the rule repository is a persistent external memory that accumulates and retrieves experience. Secondary fit is **§4.5 Agent Reasoning** — the contrastive rules directly guide multi-step reasoning and tool-use decisions.
