## 1. Mechanism (step-by-step)

GraphPlanner formulates multi-agent LLM routing as a **Markov Decision Process (MDP)** where at each step the router selects both an LLM backbone and an agent role (Planner, Executor, Summarizer). The core innovation is **GARNet**, a heterogeneous graph neural network that jointly encodes the current workflow graph and historical interaction graph through shared role-hub nodes.

**Step-by-step pipeline**:

1. **State Representation**. At step t, the state s_t is the current query q_t. The environment also maintains the evolving workflow memory graph G_workflow and historical memory graph G_history, which together form the full heterogeneous graph G_t = G_workflow ∪ G_history.

2. **Node Initialization**. Three node types are defined:
   - Query nodes: x_q ∈ R^{d_q} — Longformer embeddings of current/historical queries
   - Response nodes: x_r ∈ R^{d_r} — embeddings of responses
   - Role-hub nodes: x_m = [e_role; U; C] ∈ R^{d_m} — concatenation of LLM-role textual embedding with task utility U and cost C

3. **Graph Construction**. Queries connect to roles through edges e_{q–m} enriched with acc-cost info. Responses link to generating roles. Historical queries/responses connect to the same shared role-hub nodes. The shared role-hub node architecture is critical: a fixed set of (LLM, role) pair nodes reused across all routing steps and across both G_workflow and G_history, preventing redundant node creation and providing structural anchoring for cross-graph message passing.

4. **Dual-Graph Encoding** (GARNet). First, the historical memory graph is encoded: H^{(his)} = GARNet_{θ_his}(G_history), producing updated role-hub node embeddings summarizing past query–response interactions. These are then injected into the workflow encoder: H^{(loc)} = GARNet_{θ_loc}(G_workflow; H^{(his)}), yielding local-contextualized representations.

5. **Message Passing**. Each node embedding is projected: h_v^{(0)} = W_{τ(v)} x_v where τ(v) denotes node type. Messages are aggregated from neighbors: m_v = AGG{h_u^{(0)} : u ∈ N(v)}. Node states are updated via residual: h_v = h_v^{(0)} + β · m_v.

6. **Action Selection**. The global state representation is obtained by fusing the current query embedding: z_t = f_trans(s_t). Each candidate action corresponds to an LLM-role node embedding h_{m,j}. Compatibility scores: score_j = z_t^T h_{m,j}, masked by M_t for semantic validity. Probabilities: π(a_t = j | s_t) = softmax over valid actions.

7. **Dynamic Action Mask M_t**:
   - Step 0: only Planner and Executor allowed (no Summarizer)
   - Final step T: only Executor allowed
   - Planner capped at P_max invocations per episode
   - Total actions: |A| = 3K (3 roles × K LLM backbones)

8. **Transition Dynamics T(s_t, a_t) → (s_{t+1}, o_t)**:
   - Planner: decomposes query into sub-queries; o_t = set of new sub-queries; s_{t+1} = first child
   - Executor: resolves query; o_t = answer; s_{t+1} = next pending query or terminal
   - Summarizer: aggregates completed responses; o_t = summary; s_{t+1} = summary query

9. **Reward**:
   r_t = U(ŷ, y*) - α · C(a_t) if t = T (terminal)
   r_t = -α · C(a_t) if t < T (intermediate)
   Where U is task-specific utility (accuracy, BLEU, MRR), C(a_t) is computational cost, and α controls the cost–utility trade-off.

10. **Training with PPO**. Both the policy network (actor) and value network (critic) are optimized via Proximal Policy Optimization. Training uses multi-threaded rollouts that process multiple queries in parallel, generating routing interactions dynamically (no pre-collected training data needed).

**Key equations**:
- Policy: max_π E_{q~Q} [Σ γ^t r(s_t, a_t)], a_t ~ π(s_t)
- Score: score_j = z_t^T h_{m,j}
- Action probability: π(a_t=j|s_t) = exp(score_j)·1{a_j∈M_t} / Σ_k exp(score_k)·1{a_k∈M_t}

**Phase 1 (optimizing LLM backbones within fixed workflows)** — 5 task domains with Depth/Width configurations:

| Setting | GraphPlanner Avg Acc | Best Baseline | Δ |
|---------|---------------------|---------------|-----|
| Depth=1, Width=3 | 58.60% | 54.80% (Router-KNN*) | +3.8% |
| Depth=2, Width=2 | 60.40% | 56.20% (Router-KNN*) | +4.2% |

**Phase 2 (generating optimal workflows — joint role+LLM selection)**:

| Router Type | Best Baseline | GraphPlanner | Δ |
|-------------|--------------|--------------|-----|
| Single-round (best: RouterDC) | 54.3% | — | — |
| Multi-round (best: Router-R1) | 51.8% | — | — |
| All baselines | 54.3% (RouterDC) | 63.6% | +9.3% |

**Domain breakdown (Phase 2)**: Math 67.0%, Code 76.0%, CS 78.0%, World Knowledge 38.0%, Popular 52.0%

**GPU training cost comparison**:
- Router-R1: 186.26 GiB
- GraphRouter: 1.54 GiB
- RouterDC: 10.56 GiB
- GraphPlanner: 1.04 GiB (smallest)

**Unseen task zero-shot generalization** (LogicGrid/MGSM/CommonGen):
- GraphPlanner: 78% avg (60%/92%/82%)
- RouterDC: 58% (best single-round)
- GraphRouter: 46%
- Router-R1: 38%

**Unseen LLM generalization**: GraphPlanner consistently outperforms GraphRouter and Router-R1 in zero-shot across all 5 domains

**AIME competition math** (zero-shot): GraphPlanner 14.7% vs best baseline 7.56% (GraphRouter)

**Training time**: 120 min total (vs. 300-406 min for baselines)
**Inference latency**: 1.2 s/query (fastest among all methods; multi-round baselines 3.6-10.5 s/query)

**Ablation — historical memory**: Removing history causes substantial accuracy drop across all tasks. Homo-Graph < Hetero-Graph < GARNet full.
**Ablation — graph encoders**: GAT (baseline) < GraphTransformer < GARNet. GARNet provides 2.8–7.6% improvement over alternatives while being the lightest-weight encoder.
**Ablation — LLM-based history processing**: History-summary and History-retrieval variants achieve only modest gains over Router-R1, while GraphPlanner outperforms them by 4–171% across tasks, demonstrating GARNet's superiority over prompt-based history injection.

## 3. Trade-offs

| Win | Cost / Trade-off |
|-----|------------------|
| +9.3% accuracy over best multi-round router (Phase 2) | Uses 8.1 avg LLM calls per query (vs. 1 for single-round routers) |
| 1.04 GiB GPU for training (178× less than Router-R1's 186.26 GiB) | Requires PPO training loop (120 min), not a simple classifier |
| 78% zero-shot accuracy on unseen tasks (20-40% higher than baselines) | Transductive inference mode requires storing/querying historical interactions |
| 1.2 s/query inference latency (fastest overall) | Inductive mode is more lightweight but loses ~2-3% accuracy vs. transductive |
| Pareto-optimal across all cost-accuracy trade-off settings (α ∈ {0.0, 0.1, 0.3, 0.5, 0.9}) | Shared role-hub nodes mean the model has fixed |A|=3K action space; new roles or LLMs require architectural changes |
| No pre-collected training data needed (RL generates on-the-fly) | Multi-threaded rollout requires sufficient parallelism infrastructure |
| Handles both workflow optimization (Phase 1) and workflow generation (Phase 2) | Phase 2 benefits most on reasoning tasks (Math +5.0%, Code +4.0%); recognition tasks only +1.0% |
| Lightweight GNN encoder vs. Transformer-based alternatives | Message passing is limited to 1-hop neighbor aggregation (simpler than full attention) |
| New-role-few-shot adaptation: adding Thinker/Verifier with 1% training data works | Full new-role retraining gives stronger gains than zero/few-shot |

## 4. Design Rationale

**Why MDP formulation over supervised classification**: Routing decisions have long-term deferred consequences — early misallocation cascades into redundant calls or degraded reasoning quality. MDP with PPO enables credit assignment across the full trajectory, jointly optimizing final accuracy and cumulative cost, unlike supervised routers that learn from one-shot assignment labels.

**Why heterogeneous graph over flat embeddings**: Relations among queries, responses, and (LLM, role) pairs are multi-typed and multiplicative (LLM-backbone × agent-role × query). A heterogeneous graph with typed nodes/edges naturally captures this structure, whereas flat vector embeddings collapse these dimensions. The shared role-hub node design is the key architectural insight — it serves as structural and semantic anchor between workflow and history graphs, enabling consistent message passing without redundant node creation.

**Why GARNet over GAT/GraphTransformer**: GARNet's dual-graph encoding (history-first, then workflow-with-history-injection) is more parsimonious than full transformer attention, avoiding the O(N^2) complexity of transformer-based graph encoders while still capturing role-specific heterogeneity. Ablations confirm GARNet outperforms both GAT and GraphTransformer while being the lightest-weight encoder.

**Why RL over LLM-prompted history processing**: Injecting historical summaries/retrievals into an LLM context (32K-token limit) fails because interaction histories are heterogeneous, noisy, and contextually entangled. The structured GNN encoder in GARNet provides a principled mechanism to capture cross-interaction patterns, suppress noise, and propagate relational information — demonstrated by 4-171% accuracy improvements over LLM-based history processing baselines.

## 5. Limitations & Failure Modes

1. **Fixed role taxonomy**: Only Planner/Executor/Summarizer (plus appendix Thinker/Verifier). Real agentic systems may need richer role types (e.g., Critic, Tool-User, Researcher, Debugger) that the current action space cannot express without retraining.

2. **Shallow graph encoding**: Message passing uses 1-hop neighbor aggregation. Multi-hop dependencies (e.g., how a Planner at depth-2 relates to an Executor at depth-1) are only captured indirectly through shared nodes, not explicit temporal or hierarchical edges.

3. **Cost modeling is LLM-pricing-only**: Uses per-token API pricing from providers. Does not account for inference latency, queue delays, rate limits, or hardware heterogeneity across deployment environments.

4. **Limited to 12 LLM backbones**: Generalization to unseen LLMs is demonstrated but the action space is fixed. Adding new backbones requires retraining with expanded role-hub nodes.

5. **World Knowledge tasks underperform**: 38% accuracy on World Knowledge (NaturalQuestions, TriviaQA) vs. 78% on CS — gap suggests the workflow structure adds less value for factoid lookup tasks compared to reasoning tasks.

6. **Transductive-inductive gap**: Transductive mode requires storing training-phase interaction histories, adding storage/inference overhead. Inductive mode loses accuracy in exchange for efficiency.

7. **No explicit mechanism for handling agent failures**: If an Executor produces a wrong answer, there is no built-in recovery or re-planning mechanism — the workflow continues assuming correct outputs.

8. **Single-step Executor at termination**: The final step is constrained to Executor-only, which may miss opportunities for multi-pass refinement (e.g., iterative self-correction loops).

## 6. Transfer to Lyra

**The ONE transferable idea**: The **shared role-hub node architecture** from GARNet — a fixed set of typed embedding nodes representing (model, role) pairs that serve as structural anchors connecting current workflow state to historical interaction memory within a heterogeneous graph. These shared nodes persist across routing steps and across separate memory subgraphs, enabling consistent message passing, multi-round reasoning, and accumulation of usage statistics (utility + cost) without redundant node creation. This design is directly applicable to Lyra's §4.2 (Router/Learner) workstream as a principled mechanism for Lyra's router to jointly model which model-backbone to invoke and which agent-capability to activate, while learning from past routing outcomes encoded in the graph.

**Workstream route**: §4.2 — Router/Learner (adaptive model selection, multi-agent orchestration, cost-aware routing with historical memory)

**Impact**: 4/5 — The shared hub-node pattern is architecturally novel, lightweight (1.04 GiB GPU training), and maps directly to Lyra's multi-model routing challenge. It provides a principled alternative to current heuristic/single-shot routing approaches and learns from historical traces.

**Effort**: 4/5 — Requires constructing heterogeneous graph structures (query nodes, response nodes, role-hub nodes), implementing GNN message passing with dual-graph encoding, and setting up an RL training loop. Not a drop-in library. However, the architecture is well-specified in the paper with code available at the GitHub repository.

**Tier**: **Breakthrough** — Evaluated across 14 tasks, 6 domains, ICLR 2026 published, code released, strong zero-shot generalization evidence, and the shared role-hub pattern is a novel architectural primitive with clear transfer value.
