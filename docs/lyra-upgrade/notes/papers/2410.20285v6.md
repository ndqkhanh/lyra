## 1. Mechanism

SWE-Search is a multi-agent framework that wraps Monte Carlo Tree Search (MCTS) around an LLM-based software engineering agent to enable non-linear exploration, backtracking, and iterative self-improvement. The system has four components working in synergy:

### 1.1 Problem Formulation
The SWE task is formalized as a tuple M = (S, C, A, V, P, p0, ρ):
- **S**: state space (file context, codebase status)
- **C**: context space (repository metadata, problem description)
- **A**: action space — two-tier: action types T ∈ {SearchCode, IdentifyCode, Plan, Edit, RequestMoreContext, Finish} and specific actions At per type
- **V**: value function assigning utility to state-action pairs
- **P**: context-dependent transition function P: S × A × C → Δ(S)
- The objective: maximize expected cumulative reward across trajectories, with the value function depending on full history (non-Markovian)

### 1.2 Action Agent (SWE-Agent)
Built on moatless-tools framework with two key modifications:
- **Flexible Plan state**: Plan can transition to ANY state type (not just Edit), enabling dynamic backtracking when the agent realizes it needs more search/context mid-edit
- **Autonomous test execution**: Agent can run any test in the codebase and create new tests, without knowledge of the fail-to-pass tests (aligned with SWE-bench rules). Test results feed into both the value function and subsequent decision-making
- States maintain file context with "spans" (code sections identified by span IDs) to limit prompt size
- Git-like commit tree backs each state, enabling O(1) reversion to any prior state by checking out the corresponding commit

### 1.3 Modified MCTS with Heuristic UCT
The core search uses a modified Upper Confidence Bound for Trees (UCT) criterion — deliberately heuristic-based (not LLM-based) for efficiency and interpretability:

```
UCT(s,a) = V(s,a) + C·√(ln N(s) / N(s,a)) + α·e^(-β(d-1)) - γ·√d
```

Where:
- **V(s,a)**: value estimate from the Value Agent
- **C·√(ln N(s)/N(s,a))**: standard UCT exploration term (C=1.41, exploration weight=1.0)
- **α·e^(-β(d-1))**: early depth bonus (α=200, β=default) — rewards exploration at shallow depths, simulating an engineer's initial broad search
- **-γ·√d**: late depth penalty (γ=0.8) — discourages over-exploration at deep levels, promoting convergence
- **Quick abandonment rule**: nodes with consecutive low rewards are pruned to avoid wasting resources on dead-end trajectories

At each step, the node with highest UCT value is selected: s* = argmax UCT(s,a)

Key hyperparameters: max expansions per node = 3 (5 in default config), max iterations = 100, max depth = 20, value function temperature = 0.2, action model temperature = 0.2.

### 1.4 Value Agent (Hybrid Value Function)
The LLM-based Value Agent outputs a tuple:
```
(vt, εt) = V(st, at, {si}i=0..t-1, {ai}i=0..t-1)
```
- **vt ∈ [-100, 100]**: numerical utility estimate
- **εt**: natural language explanation of the evaluation

The explanation εt serves dual purpose: (a) transparency into decision-making, and (b) **hindsight feedback** — when re-expanding from a parent node, the explanation is injected into the Action Agent's prompt to guide it toward better actions.

State-specific value prompts are critical: without them, the Value Agent consistently undervalued effective actions (e.g., correctly locating relevant files got low rewards). Four distinct prompts exist for: SearchCode, Plan, RequestMoreContext, and Edit states. The Edit prompt heavily penalizes failure to update/add tests (reward < 0).

**Reward scale interpretation:**
- 100: Fully confident solution is optimal, thoroughly tested
- 75-99: Likely best approach, minor issues
- 0-74: Partially implemented, likely better alternatives exist
- 0: Not functional, substantial work required
- -1 to -49: Introduces new issues, repetitive actions without progress
- -50 to -100: Entirely incorrect, causes significant new problems

### 1.5 Discriminator Agent (Multi-Agent Debate)
In the final stage, up to 5 candidate solutions from the search tree enter a structured debate:
- **5 Discriminator Agents** each evaluate all solutions and vote for the best one
- **3 debate rounds** where agents argue for/against solutions
- A judge agent synthesizes evaluations to produce the final selection
- Improves selection accuracy from value function's 73% to 84%

### 1.6 End-to-End Flow
1. Start with problem statement + initial codebase state (git commit)
2. Action Agent proposes actions from current state
3. Actions execute, producing new states (commits) and test results
4. Value Agent evaluates each new state-action pair → (reward, explanation)
5. MCTS selects next node to expand using modified UCT
6. When re-expanding from a parent, hindsight feedback (εt) guides the Action Agent
7. After max iterations or convergence, candidate solutions enter Discriminator debate
8. Discriminator selects the best solution as final output

## 3. Trade-offs

| Win | Loss |
|-----|------|
| **+23% mean relative improvement** in resolve rate across 5 diverse models (open + closed) | **5-14x API cost increase** (GPT-4o: $40.86 → $576.00 per 300-instance run) |
| Smaller open-source models (Qwen2.5-72B at 24.7%) approach/exceed GPT-4o without MCTS (25.7%) | **Value function only 73% accurate** at identifying the correct solution — misses 27% of resolved instances |
| **Discriminator debate improves selection accuracy** from 73% to 84% | Requires **state-specific prompt engineering**; generic prompts cause systematic undervaluation of effective actions |
| Performance **scales with inference-time compute** — no model retraining or architecture changes needed | **Conservative MCTS parameters** (max 100 iterations, 3 expansions/node) limit full potential of search |
| **Escapes unproductive loops** that trap linear agents via Value Agent feedback + quick abandonment heuristic | Additional **infrastructure complexity**: git-backed state tree, Kubernetes test pods, multi-agent debate orchestration |
| Flexible state transitions enable **autonomous course correction** without external intervention | **No convergence guarantee** — agent can still fail to find correct solution even with search budget |
| **Model diversity exploited**: each model resolves unique subsets (33 issues GPT-4o missed but others solved) | Cost scaling is **linear with search iterations** — practical deployment requires budget-aware truncation strategies |

## 4. Design Rationale

**Why MCTS over alternatives?** MCTS was chosen over BFS (memory-intensive), DFS (too greedy), and A* (requires pre-defined evaluation heuristic) because MCTS conducts statistical tree search without dedicated per-state heuristics — critical when evaluating software states where no simple heuristic exists. The modified UCT with depth-aware bonus/penalty terms was designed to mirror how human engineers explore broadly early then converge.

**Why heuristic-based selection (not LLM-based)?** Deliberate choice for interpretability and efficiency — LLM-based selection (used in WebPilot, Koh et al. 2024) adds latency and cost at every selection step. The AlphaZero-style UCT is computationally cheap and the Value Agent already provides LLM-quality evaluation at expansion time.

**Why a hybrid value function (numerical + NL explanation)?** Pure numerical rewards lose diagnostic information. The natural language explanation enables the hindsight feedback mechanism — the key innovation that drives most of the improvement by allowing the Action Agent to learn from prior failed expansions without retraining.

**Why state-specific value prompts?** Empirical finding: a single generic value prompt caused the Value Agent to assign low rewards even to correct actions (e.g., successfully locating relevant files). Separate prompts tuned to Search/Plan/Edit/RequestMoreContext semantics fixed this.

**Why the Discriminator debate?** The MCTS value function ranks individual trajectories but cannot directly compare candidate solutions with similar scores. The multi-agent debate surfaces implementation-level trade-offs invisible to scalar rewards.

## 5. Limitations and Failure Modes

1. **Value function miscalibration (27% error rate):** The Value Agent fails to identify the correct solution in ~27% of cases where one exists. This is the primary ceiling on performance — better search cannot help if the evaluator picks the wrong trajectory.

2. **Prohibitive cost for production:** 14x cost multiplier on GPT-4o makes SWE-Search impractical for routine use. Even on cheaper models, 5x cost for 23% improvement is a hard sell without budget-aware early stopping.

3. **SWE-bench-lite only:** Evaluated on 300 curated instances; performance on full SWE-bench (2,294 instances) or SWE-bench-Verified is unknown. The Lite subset may over-represent cases amenable to search.

4. **Conservative search budget:** Max 100 iterations and 3 expansions/node were set for experimental feasibility, not optimality. Real MCTS benefits often require thousands of iterations (as in AlphaGo). The reported gains may underestimate potential but also mask how performance saturates.

5. **Python-only:** All SWE-bench-lite instances are Python repositories. Behavior on multi-language codebases (JavaScript, Go, Rust, etc.) is untested.

6. **Prompt sensitivity:** Value function performance depends heavily on carefully tuned state-specific prompts. These may not transfer across codebases or problem types without re-tuning.

7. **No theoretical convergence guarantees:** The modified UCT with heuristic depth bonus/penalty lacks formal regret bounds. Quick abandonment can prematurely prune promising paths.

8. **Discriminator bottleneck:** Debate limited to 5 solutions, 3 rounds. Complex cases may need more extensive deliberation, and the debate itself can be gamed by persuasive-but-wrong arguments (known failure mode of multi-agent debate).

## 6. Transfer to Lyra

**The one transferable idea:** The **hybrid MCTS + hindsight-feedback loop** pattern, where an LLM Value Agent outputs both a scalar reward and a natural language critique, and that critique is injected as feedback when re-expanding from parent nodes in the search tree. This enables iterative self-improvement without model retraining and is directly applicable to Lyra's autonomous coding loop.

**Workstream routing:** §4.5 (Agent Execution and Tooling) — this is fundamentally an agent search/planning strategy that governs how Lyra explores solution spaces during repository-level tasks. It also touches §4.2 (Context and Planning) since the MCTS tree structure is a planning formalism.

**Impact: 4/5** — Search-based exploration with self-critique directly addresses the linear-execution limitation of current coding agents. The 23% average improvement across diverse models is strong evidence of generalizability.

**Effort: 4/5** — Requires implementing: (a) git-backed state tree with checkpoint/restore, (b) MCTS controller with modified UCT, (c) Value Agent with state-specific prompting, (d) hindsight feedback injection, (e) optional Discriminator debate. Significant infrastructure but each component is well-specified.

**Tier: investigate** — The cost multiplier (5-14x) is prohibitive for default operation. However, the hindsight feedback mechanism can be extracted and applied selectively (e.g., only when the agent declares "done" prematurely, or only for high-stakes changes). A lightweight version using Lyra's existing test infrastructure as the value signal (bypassing the LLM Value Agent for routine states) could capture much of the benefit at a fraction of the cost. Recommend prototyping a "Lyra-Search-Lite" with: MCTS tree + git-backed state + test-pass/fail as primary value signal + LLM Value Agent only for final-stage evaluation.
