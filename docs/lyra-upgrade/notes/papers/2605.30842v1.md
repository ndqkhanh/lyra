## 1. Mechanism (Step-by-Step)

COMEM addresses the *decoding latency bottleneck* in long-horizon agentic inference by decoupling two responsibilities that are normally fused in a single model: **memory management** (history compression) and **agentic reasoning** (policy generation). It introduces three architectural innovations:

### 1.1 Decoupled Two-Model Architecture

Instead of forcing one large model to both compress history and produce actions, COMEM splits the roles:

- **Memory Model** `f` (small, e.g., Qwen3-4B): compresses the long interaction history into a dense latent summary `s_t`.
- **Agent Model** `π` (large, e.g., GLM-4.7 355B): conditions on the summary plus a short recent buffer `C_t` to produce the next action.

Formally:
```
s_t = f(τ_{<t}; θ_f)                            (Equation 2)
a_t ~ π(a | s_t, C_t; θ_π)                       (Equation 3)
```
where `|θ_f| ≪ |θ_π|` and `|s_t| < |τ_t|`.

### 1.2 k-Step-Off Asynchronous Pipeline (Algorithm 1)

The core latency-hiding mechanism. The memory model runs *asynchronously* in the background, lagging `k` steps behind the agent:

1. **Cycle start (every k steps):** Memory model is launched asynchronously to compress all history `τ_{≤t}`. Agent KV cache is invalidated; a full uncached prefill runs with the new summary + recent buffer.
2. **Intermediate k−1 steps:** Agent reuses cached prefix and performs only incremental prefilling of new observations (cheap, no full re-encoding).
3. **Next cycle start:** The async memory job completes; new summary `s` is loaded; cycle repeats.

This means the agent *never waits* for memory compression to finish. Within each cycle, the policy at step `t` is:
```
a_t ~ π(a_t | f(τ_{≤t-k}), τ_{t-k+1:t}; θ_π)     (Equation 4)
    // Latent Summary from k steps ago + Recent k-turn Buffer
```

Larger `k` amortizes uncached prefill cost over more steps but increases summary staleness. Smaller `k` provides fresher summaries but incurs more frequent uncached prefills.

### 1.3 Reward-Driven Training for Functional Equivalence (GRPO-AC)

Naive summarization is insufficient for agentic contexts. COMEM trains the memory model with a reward that measures **functional equivalence** -- whether the agent's action under the compressed summary matches the action it *would have* produced with the full context.

**Procedure:**
1. Collect reference trajectories using the frozen full-context agent, recording ground-truth actions `a*_t = π(· | τ_{<t})` at each step.
2. For each candidate summary `s = f(τ_{<t-k})`, feed it to the frozen agent to produce `â_t = π(· | s, C_t)`.
3. Define reward: `R(s) = sim(â_t, a*_t)` -- cosine similarity between the summary-conditioned action and the full-context action.
4. Train memory model `f` with **GRPO** (Group Relative Policy Optimization), using a PPO-style clipped surrogate objective:

```
L_GRPO(θ) = -E[ 1/K Σ_{k,t} min( r_t^{(k)} Ã^{(k)}, clip(r_t^{(k)}, 1−ε, 1+ε) Ã^{(k)} ) ] + β·D_KL(π_θ || π_ref)
                                                                               (Equation 1)
```
where `r_t^{(k)} = π_θ(a_t|s_t) / π_{θ_old}(a_t|s_t)` is the likelihood ratio, `Ã^{(k)} = R(τ^{(k)}) − 1/K Σ_j R(τ^{(j)})` is the group-relative advantage, `ε = 0.2` is the clipping range, and `β = 0.01` weights the KL penalty.

**Key property:** The agent model `π` remains *frozen* throughout. Training is entirely offline -- no environment interaction needed.

### 1.4 Theoretical Summary Length Bound

To ensure net latency reduction, decoding savings must amortize prefill cost:
```
L_sum / L_full  <  1 / (1 + W / (Y·S·P))           (Equation 7)
```
where `W` = HBM bandwidth, `S` = per-token KV cache size, `P` = prefill throughput, `Y` = avg completion tokens. For Qwen3-32B on A100-80GB with `W=2TB/s, P=3000 tok/s, S=2×10^−4 GB, Y=1000`: this requires **compression ratio < 0.23** (i.e., for 32K tokens of context, summaries must be ≤7.36K tokens). COMEM uses max 2048 tokens for summaries, well within bound.

### 2.1 SWE-Bench-Verified (500 GitHub issues, main results -- Table 1)

|---|---|---|---|---|
| DeepSWE (32B) | Full-Context | 40.4 | 6390.62 | 1.00× |
| DeepSWE (32B) | COMEM GRPO-AC | **41.0** | 4400.89 | **1.45×** |
| Qwen3-Coder-Max (480B) | Full-Context | 57.2 | 5129.90 | 1.00× |

**Key finding:** On the strongest agent backbone (GLM-4.7), COMEM recovers 90.9% of full-context resolve rate while delivering 2.08× speedup. On the smallest backbone (DeepSWE-32B), COMEM actually *surpasses* the full-context baseline (+0.6pp), likely because summarization filters noise for mid-sized models.

## 3. Trade-offs (Wins vs Loses)

| Dimension | Win | Lose |
|---|---|---|
| **Latency** | 1.43×-2.08× end-to-end speedup (up to 4.95× peak per-step at high concurrency); speedup scales favorably with batch size | Additional latency from memory model prefill + decode (amortized by k-step-off pipeline) |
| **Task Performance** | Recovers 89-102% of full-context resolve rate; can *exceed* full-context for mid-sized models by filtering noise | 4.3-6.3pp resolve rate drop vs. full-context on larger models (GLM-4.7: 62.7% vs 69.0%) |
| **KV Cache Memory** | KV usage stays bounded at 1-37% GPU HBM vs. 34-96% for full-context; avoids request preemption | Requires invalidating agent KV cache every k steps (uncached prefill penalty) |
| **Infrastructure** | Single 4B memory server serves ~300 concurrent agent instances; amortized per-agent cost near zero | Introduces system complexity: two vLLM engines, async coordination, summary staleness management |
| **Training** | Fully offline GRPO training; no online environment interaction needed; agent model frozen | Requires pre-collected full-context trajectories; reward signal (cosine similarity of actions) is a proxy, not true task success |
| **Summary Staleness** | k-step lag is tolerable; k ∈ {2,4,8} all work well (62.4-64.2% resolve) | k=1 degrades to 57.2% (excessive uncached prefills); k=16 saturates memory scheduler (60.2%) |
| **Generalization** | Transfers across scaffolds (+0.3% degradation); transfers across agent backbones (-0.8% degradation) | Memory model may need per-backbone fine-tuning for optimal performance |
| **Hardware** | Works on A100-80GB and H200; benefits scale with GPU HBM pressure | Requires at least two GPUs (or two vLLM instances) in production |

## 4. Design Rationale (Why This Approach)

**Core insight: The decoding phase of agentic inference is memory-bandwidth-bound, not compute-bound.** At high concurrency, the KV cache for long agent interaction histories saturates GPU HBM, and the auto-regressive decode spends most of its time waiting to fetch KV cache entries from memory rather than performing actual computation. This is fundamentally different from the prefill phase, which is compute-bound and parallelizable.

**Why decouple instead of compress in-place:**
- Prior approaches (sliding window, RAG, sparse attention) either sacrifice long-range dependencies or operate intra-model without addressing the systemic bottleneck.
- Compression methods that run in the critical path (sequential summarization before each agent step) add decoding overhead for the summarization tokens themselves.
- By moving compression to a separate, smaller model running asynchronously, COMEM makes the compression cost *invisible* to the agent's critical path.

**Why GRPO with action-consistency reward:**
- Generic summarization (base model, SFT) fails for agentic contexts -- the memory model needs to capture *causally relevant* details, not surface-level summary quality.
- The action-consistency reward `R(s) = sim(â_t, a*_t)` directly trains the memory model to preserve the *sufficient statistics* of the interaction history -- the minimal information needed to reproduce the full-context agent's behavior.
- Using GRPO avoids expensive online environment interaction; training is entirely offline on pre-collected trajectories with a frozen agent model.

**Why k-step-off instead of step-by-step:**
- A 1-step-off pipeline requires full uncached prefill at every step (memory model updates continuously), defeating the purpose.
- A k-step-off pipeline amortizes the uncached prefill over k−1 cached steps, with k chosen to balance staleness vs. overhead.
- Empirical sweet spot: k=2 for 32B/480B backbones, k=4 for 355B backbone.

## 5. Limitations and Failure Modes

1. **Resolve Rate Gap on Large Models:** COMEM (GRPO-AC) recovers 90.9% of full-context performance on GLM-4.7 (62.7% vs 69.0%) but does not match it. The 6.3pp gap suggests some task-critical information is still being lost during compression, even with action-consistency training.

2. **Summary Length Constraint is Brittle:** The theoretical bound (Eq. 7) imposes a hard ceiling on summary length (<23% of full context). If the task demands retaining more information than can fit in 2048 tokens, the framework has no fallback -- it will silently drop information.

3. **k=1 Failure Mode:** The pipeline fundamentally fails at k=1 (57.2% vs 62.7% resolve), because every step requires an uncached prefill. This limits applicability in latency-critical settings where summary staleness must be minimized.

4. **Large-k Saturation:** k=16 causes memory server scheduling overhead that degrades performance (60.2% resolve vs 62.7% at k=4). The pipeline has a practical upper bound on parallelization.

5. **No Online Adaptation:** The memory model is trained offline and frozen at deployment. If the agent's behavior or the task distribution shifts, the memory model's compression strategy may become stale.

6. **Single-Memory-Model Assumption:** The framework assumes one memory model serves one agent backbone. Cross-backbone transfer shows a −0.8% gap, indicating some backbone-specific specialization is learned.

7. **Limited Task Diversity in Evaluation:** Primary evaluation is SWE-Bench-Verified (code repair). BrowseComp-EN exploration is limited (only GLM-4.7 backbone, k=1). Results may not generalize to dialogue, creative, or multi-modal agent tasks.

8. **Hardware Dependency:** Speedup benefits are most pronounced under high concurrency / high KV cache pressure. Under low concurrency (batch size ≤16), COMEM provides negligible or no advantage (0.86-1.05× speedup).

9. **No Safety/Alignment Consideration in Design:** The pipeline increases agent throughput but does not address the safety implications of faster autonomous agents. The authors acknowledge this in the impact statement but do not incorporate mitigations into the architecture.

## 6. Transfer to Lyra

### The ONE Transferable Idea

**Offload Lyra's memory/context compression to a dedicated smaller model running asynchronously (k-step-off), trained with an action-consistency reward to preserve sufficient statistics for downstream reasoning -- rather than relying on the primary reasoning model to handle both memory management and policy generation in the critical path.**

Lyra's current architecture (as surfaced in the `§4` workstreams) processes context management and reasoning within the same model. COMEM demonstrates that separating these responsibilities into a decoupled, asynchronous pipeline can yield 1.4-2.5× latency improvements with minimal performance degradation, especially under high-throughput serving conditions where KV cache pressure dominates.

### Workstream Route

**§4.2 (Memory Architecture)** -- This directly informs Lyra's memory subsystem design. COMEM provides both the architectural pattern (decoupled memory model + k-step-off pipeline) and the training methodology (GRPO with action-consistency reward) needed to build a production-grade compressed memory layer.
