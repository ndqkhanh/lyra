# From Model Scaling to System Scaling: Scaling the Harness in Agentic AI
**Shangding Gu (UC Berkeley)** — arXiv:2605.26112v1 [cs.AI], 25 May 2026. Preprint, under active development. GitHub: [SafeRL-Lab/cheetahclaws](https://github.com/SafeRL-Lab/cheetahclaws).

## 1. Mechanism (step-by-step)

The paper proposes a **six-component decomposition** of an agentic system, formalized as:

> P_H = Φ(R, M, C, S, O, G)

Where:
- **R** = Reasoning substrate (the foundation model itself — the model-scaling axis)
- **M** = Memory store, further factorized as `M = (precision, durability, retrievability, verifiability)`
- **C** = Context constructor, factorized as `C = (relevance, compactness, traceability, refresh policy)`
- **S** = Skill-routing layer (dispatches tools and subagents), factorized along `specificity, selectivity, composability, verifiability`
- **O** = Orchestration loop (the control flow wrapping all components)
- **G** = Governance and verification layer (audit, permission, rollback, checks)

The execution flow in Figure 1:
1. **Orchestration (O)** drives a control loop
2. **Context Constructor (C)** draws from **Memory (M)** and the current task to assemble inputs
3. The assembled context is fed to the **Reasoning Substrate (R)**
4. **Skill Router (S)** dispatches tools or subagents based on the model's intent
5. **Governance & Verification (G)** gates both intermediate reasoning and external actions before they become permitted actions or verified memory write-backs
6. Results are written back to memory only after verification

### Three Core Bottlenecks and System Moves

**Bottleneck 1 — Context Governance (§4.1):** The failure mode is "exposure without access" — larger context windows do not guarantee attention to the right tokens. The system move is to treat each turn's context as the *output of a selection policy*, not a fixed buffer. Policy weights: semantic relevance, penalize verbosity against a token budget, prefer recently validated content, record provenance.

**Bottleneck 2 — Trustworthy Memory (§4.2):** The failure mode is "stale-but-confident" — a stored fact can become wrong after refactors while remaining highly ranked by semantic search. The system move is to make *trust a runtime decision*: retrieval should weight staleness penalty (time since last verification) + confidence-gated risk term alongside relevance, and treat retrieved content as a hypothesis until re-verified against the live environment. The CheetahClaws reference harness stores per-entry confidence and recency as first-class fields.

**Bottleneck 3 — Dynamic Skill Routing (§4.3):** The failure mode is "confident-but-unchecked" — a subagent returns plausible output that no downstream layer validates. The system move is to couple routing with *post-condition verification*: each skill carries explicit verifiability checks, and routing learns adaptively via online estimates of subtask type, confidence-aware escalation, and mixture-style composition.

### Temporal Layer Model (§3.2)
- **Prompt** = short-horizon (local control, brittle over long horizons)
- **Skill** = task-level (reusable execution patterns; fails via wrong routing or poor composition)
- **Memory** = longitudinal (durable facts; fails via drift, over-generalization, pollution)

## 3. Trade-offs (wins vs loses)

| Win | Loss / Cost |
|-----|-------------|
| System scaling addresses failure modes model scaling alone cannot fix (stale memory, unverified skill outputs, context dilution) | Adds engineering complexity; six-component framework requires maintenance of each subsystem |
| Modular decomposition enables independent improvement of M, C, S, O, G without retraining R | Factors are not strictly orthogonal; Φ has no closed form — the decomposition is conceptual, not quantitative |
| Trust-as-runtime-decision (staleness penalty + confidence-gating) prevents stale-but-confident retrievals | Increased latency: every retrieval requires verification step against live environment |
| Dynamic skill routing with post-condition checks prevents confident-but-unchecked subagent outputs | Every skill invocation adds verification cost; simpler one-shot execution may be faster for easy tasks |
| Process-level + longitudinal metrics reveal failures endpoint accuracy hides | More expensive evaluation; trace-level metrics are harder to standardize than accuracy |
| Open-source CheetahClaws makes harness design choices explicit and reproducible | Research harness lags production systems in UX, tool breadth, and polish |
| Separation of prompt/skill/memory as temporal layers prevents brittle long-horizon behavior | Requires disciplined engineering: memory entries need confidence fields, skills need post-condition specs |

## 4. Design Rationale

The paper argues that once foundation models reach a **sufficient capability threshold**, further gains in long-horizon agent performance depend *increasingly* on system design (M, C, S, O, G) rather than model capability (R) alone. This is motivated by converging evidence:

1. **Field analysis of agent benchmarks** shows many results are non-Pareto-optimal once cost, prompting strategy, and demonstrations are controlled [17].
2. **SWE-agent** proves that redesigning the agent-computer interface alone (fixed model) substantially improves SWE-bench accuracy [40].
3. **Lost-in-the-middle** phenomenon [21] and attention dilution [11] show that larger context does not equal better context — motivating C as a selection policy.
4. **Multi-agent systems** can outperform single agents on breadth-first tasks but introduce coordination failures missed by single-agent metrics [8] — motivating O and G as explicit components.
5. **τ-bench passˆk collapse** shows that single-shot pass rates hide reliability gaps — motivating longitudinal evaluation.

The core rationale is: *prompt engineering is necessary but insufficient for long-horizon reliability; system architecture governs what information is available, what actions are authorized, and how failures are traced.*

## 5. Limitations and Failure Modes

1. **No empirical validation**: The paper is a position/framework paper. Equation 1 has no closed form, the six factors are not strictly orthogonal, and the decomposition is explicitly labeled as "conceptual organization rather than a quantitative model." No experiments validate the claims.
2. **Preprint status**: Under active development; not peer-reviewed. The author explicitly welcomes comments and suggestions.
3. **CheetahClaws maturity**: The reference harness (v3.05.79) is described as a research reference implementation, not production-grade. Comparison with Claude Code and OpenClaw is illustrative, not quantitative.
4. **Objections acknowledged but not resolved**: The paper discusses three objections (stronger models solve system problems; end-to-end training replaces modularity; system-level evaluation is too expensive) but provides arguments rather than evidence against them.
5. **Evaluation agenda is aspirational**: Table 4 lists 7 dimensions where benchmarks are currently "Rare" or "Partial" — these are desiderata, not accomplished results.
6. **Missing quantitative cost analysis**: No token-cost, latency, or compute-overhead numbers are provided for the CheetahClaws mechanisms (confidence-gated retrieval, post-condition verification).
7. **Single-author**: Unlike most systems papers, this has a single author, limiting the breadth of implementation and empirical backing.

## 6. Transfer to Lyra

**The one transferable idea:** The six-component decomposition `P_H = Φ(R, M, C, S, O, G)` with its factorization of memory trust (`precision, durability, retrievability, verifiability`) and context quality (`relevance, compactness, traceability, refresh policy`) provides a ready-made audit framework for Lyra's existing harness. Lyra already has most of these components (Claude Code as R+O base, .omc as M, project-memory.json, notepad, wiki, skills registry as S, verification-loop as G). The transferable action is to **audit Lyra's harness against the four trust axes of M and the four quality axes of C** — specifically: does Lyra's memory store per-entry confidence and recency? Does it apply staleness penalties at retrieval? Does it treat retrieved memory as hypothesis until re-verified? These questions map directly to concrete engineering improvements.

**Workstream route:** §4.2 (Trustworthy Memory) — the paper's memory trust framework directly feeds the ongoing memory subsystem redesign in Lyra's MASTER-PLAN.md.
