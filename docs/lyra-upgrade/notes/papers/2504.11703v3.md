## 1. Mechanism (Step-by-Step)

Progent secures AI agents by enforcing the **principle of least privilege** at the tool-call level via symbolic security policies and an SMT-based policy update mechanism. The system operates through four integrated stages:

### 1.1 Policy Representation
Progent represents privilege as a **security policy** `P` consisting of symbolic rules over tool names and arguments:

```
Policy P ::= {R₁, R₂, ...}
Rule R ::= Effect t when {eᵢ}, fallback f
Effect E ::= allow | forbid
```

Each rule targets a specific tool `t` with conditions `eᵢ` over its parameters `pᵢ`. Conditions support expressions over parameter values including comparisons (`<`, `≤`, `==`), string matching (`in`, `match`), boolean operators (`and`, `or`, `not`), and array operations (`pᵢ[n]`, `pᵢ.length`). Fallback actions include: terminate execution, request user inspection, or return an error message.

### 1.2 Deterministic Policy Enforcement (Algorithm 2)
Every tool call `c = t(vᵢ)` issued by the agent is intercepted and checked against the current policy `P`:

1. Extract rules in `P` targeting tool `t`, sort such that `forbid` rules precede `allow` rules.
2. For each rule `R`, evaluate conditions `eᵢ[vᵢ/pᵢ]` (substituting actual arguments `vᵢ` for parameters `pᵢ`).
3. If conditions hold and `E == forbid` → block call, execute fallback `f`.
4. If conditions hold and `E == allow` → permit call (return `c` unchanged).
5. If no rule matches → block by default (default-deny security posture).

### 1.3 SMT-Based Policy Comparison
Progent determines whether a proposed policy update `P → P'` is an **expansion** or **narrowing** using an SMT solver (Z3):

Let `A(P) = {c | P(c) = c}` be the set of all tool calls allowed by policy `P`. For each tool `t`, define the SMT formula `Φₚₜ(vᵢ)` encoding all conditions under which `P` allows tool `t`. Then:

```
P' is a narrowing of P iff ∀vᵢ. Φₚ'ₜ(vᵢ) ⇒ Φₚₜ(vᵢ)
```

If this formula is valid for all tools, `P'` is a narrowing (or equal). If the negation is satisfiable, `P'` is an expansion. The SMT solver provides a **fully deterministic** judgment — no ML heuristics.

### 1.4 LLM-Based Policy Lifecycle with Monotonic Confinement (Algorithm 3)
1. **Initial Policy Generation (trusted context):** An LLM generates the initial policy `P₁` from the user's benign query `o₀` and available tool definitions `T`. The LLM identifies necessary tools and generates least-privilege parameter constraints.

2. **Policy Update (execution loop):** After each tool execution returns observation `oᵢ`, an LLM proposes a policy update `P'` based on new information. The SMT solver compares `P'` against the current `P`:
   - **Narrowing** (A(P) ⊇ A(P')): applied automatically without human intervention.
   - **Expansion** (A(P) ⊄ A(P')): requires explicit approval (auto-deny, auto-approve, or human review configurable).

3. **Monotonic Confinement Guarantee (Theorem):** Between approved expansions, the allowed action space forms a monotonically decreasing sequence:
   ```
   A(P⁽⁰⁾) ⊇ A(P⁽¹⁾) ⊇ A(P⁽²⁾) ⊇ ...
   ```
   This means the agent's permissions can only shrink without explicit approval — adversaries cannot silently escalate privileges.

### 1.5 Multi-Agent Support
Multi-policy enforcement (Algorithm 4): higher-priority policies (e.g., organization-wide) are applied first; lower-priority policies (e.g., task-specific) can only further restrict remaining action space. A tool call is blocked if blocked by any policy.

## 3. Trade-offs

| Win | Loss |
|-----|------|
| ASR reduction: 39.9% → 1.0% (AgentDojo), 70.3% → 3.9% (ASB) | Requires SMT solver (Z3) dependency — adds computational overhead per policy comparison |
| Utility preserved: identical to no-defense under no-attack (79.4%) | Initial policy quality depends on LLM; poor initial policy can over-restrict or under-restrict |
| Deterministic enforcement — no ML-based detection uncertainty | Cannot defend against attacks within least-privilege boundary (preference manipulation, output-targeting attacks) |
| Modular integration — no agent internal modification needed | Proxy mode cannot protect built-in tools that bypass MCP interfaces |
| Monotonic confinement theorem — provable security property | Human-in-the-loop (Manual Approval) achieves 0% ASR but reduces automation |
| Works across diverse agent frameworks (LangChain, OpenAI SDK, OpenHands, AutoGen) | Policy generation LLM adds operational cost per agent run |
| Complementary with model-level defenses (synergy with Claude/LLaMA safety) | Expansion approval creates usability friction; Auto-Approve mode accepts 1.0% residual ASR |
| Library mode and proxy mode for different user roles | Complexity of policy language grows with tool surface; multimodal tool parameters not yet supported |


## 4. Design Rationale

1. **Why privilege control over detection?** Detection models (Prompt Guard, DeBERTa classifiers) are inherently probabilistic and can be bypassed. Progent's symbolic rules + SMT solving provide **deterministic** enforcement — safety guarantees hold regardless of adversarial input.

2. **Why monotonic confinement?** The key insight: adversaries exploit the same privilege-expansion channel that legitimate tasks use. By requiring explicit approval for any expansion (while auto-applying narrowing), Progent prevents adversaries from silently escalating privileges while maintaining the agent's ability to adapt to legitimate new information.

3. **Why SMT solving?** Symbolic policy rules over tool arguments create a decidable comparison problem. Z3 SMT solver provides sound and complete judgments of expansion vs. narrowing, eliminating ML uncertainty from the enforcement pathway.

4. **Why tool-call level (not model-level)?** All external effects of an agent occur through tool calls. Intercepting at this level is architecture-agnostic (works with any LLM, any framework) and provides the narrowest possible enforcement boundary.

5. **Why LLM for policy generation?** Manual policy writing is impractical for diverse user tasks. LLMs demonstrate strong security reasoning capabilities and can generate task-specific least-privilege policies from natural language task descriptions without fine-tuning.


## 5. Limitations & Failure Modes

1. **Cannot defend within least-privilege bounds:** If an attack goal falls within the set of actions needed for the legitimate task (e.g., preference manipulation between valid options), Progent cannot distinguish malicious from benign intent.

2. **Text-output attacks out of scope:** Progent only constrains tool calls; it does not handle attacks targeting the agent's text responses (e.g., generating harmful content, revealing system prompts).

3. **User mistakes compromise security:** If users incorrectly approve expansion updates or provide ambiguous initial tasks, Progent may permit policies that exceed minimal privilege. The SMT guarantee only holds when the approval process is correctly operated.

4. **Multimodal tool calls unsupported:** Current policy language operates on text parameters only. Tool calls involving visual elements (GUI clicking, screen regions) cannot be represented in the current policy schema.

5. **Policy LLM quality variance:** Utility drops from 79.4% (gpt-4o) to 70.1% (claude-sonnet-4) when used as the policy LLM, indicating that the policy generation quality is model-dependent.

6. **Failure case:** Most residual attacks succeed because malicious tool names/descriptions closely resemble benign tools needed for the user task, making policy distinction difficult even for humans without prior knowledge.

7. **Proxy mode protection depth:** In proxy mode, Progent cannot protect agent functionalities implemented as built-in tools that bypass external MCP interfaces.

8. **Configurable approver trade-off:** Auto-Approve (1.0% ASR) vs. Manual Approval (0% ASR but requires human effort) — no fully automated configuration achieves zero ASR.


## 6. Transfer to Lyra

### The One Transferable Idea

**Symbolic tool-call gating with deterministic enforcement at the agent-tool boundary.** Lyra should adopt a privilege-control middleware that intercepts all tool calls, checks them against an LLM-generated least-privilege policy using deterministic rule matching, and uses monotonic confinement to prevent silent privilege escalation. This directly addresses Lyra's security requirement for autonomous operation where the agent may encounter adversarial content in tool returns (e.g., indirect prompt injection via web pages, emails, or file contents that Lyra reads).

### Workstream Mapping: §4.1 (Safety & Alignment)

Progent's mechanism feeds directly into Lyra's safety subsystem. The privilege-control middleware should be inserted as a tool-call interceptor in the Lyra agent loop, sitting between the LLM's tool-call decisions and the tool execution layer. This complements existing content-filtering approaches by providing deterministic, least-privilege enforcement that cannot be bypassed through prompt injection.

### Impact/Effort/Tier Assessment

- **Impact:** 4 — Dramatically reduces attack surface for indirect prompt injection (the dominant agent attack vector), provides provable monotonic confinement, integrates non-intrusively.
- **Effort:** 3 — Requires implementing policy schema (JSON Schema), Z3 SMT integration, LLM-prompt for policy generation, and tool-call interception middleware. The paper provides open-source reference implementation.
- **Tier:** Breakthrough — This is a novel defense paradigm (deterministic privilege control vs. probabilistic detection) with strong empirical results (ASR from 39.9% → 1.0%) and formal guarantees. It represents a significant advance over content-filtering and prompt-based defenses currently common in Lyra-class agents.
