## 1. Mechanism (step-by-step)

### Architecture

WebVoyager is a multimodal ReAct agent that browses live websites end-to-end using visual screenshots + textual HTML element descriptions. The backbone LMM (default: GPT-4V / `gpt-4-vision-preview`) orchestrates an observe-think-act loop against a Selenium-driven browser.

### Interaction Formulation

At each time step t, the agent receives context c_t:

```
c_t = (o_1, a_1, ..., o_{t-1}, a_{t-1}, o_t, I)
```

where o_i are observations, a_i are prior actions, and I is the user instruction. The model produces a_t = M(c_t), executed in the environment, which returns o_{t+1} = E(o_t, a_t).

Each action a_t is composed of a thought s_t (natural language reasoning) followed by an action code â_t, following ReAct prompting.

**Context Clipping**: Only the 3 most recent observations (screenshots) are retained to prevent confusion from long episodes. Full history of thoughts and actions is kept.

### Observation Space

1. **Screenshot** (primary): Full webpage screenshot at 1024x768 resolution
2. **Set-of-Mark overlays**: Interactive web elements (buttons, inputs, links, selects) are detected by `GPT-4V-Act` (rule-based JavaScript tool — no ML object detector), bounded with black-box numerical labels overlaid at the top-left corner
3. **Auxiliary text**: Element type, text content, aria-label attribute for each labeled element

Key design choice: Single black color for borders/labels empirically outperformed multi-color markers.

### Action Space (7 discrete actions)

| Action | Format | Description |
|--------|--------|-------------|
| Click | `Click [N]` | Click element with numerical label N |
| Type | `Type [N]; [content]` | Clear textbox N, type content, press Enter |
| Scroll | `Scroll [N or WINDOW]; [up/down]` | Scroll element or entire page |
| Wait | `Wait` | Pause for page loading |
| GoBack | `GoBack` | Return to previous page |
| Google | `Google` | Jump to Google Search (escape hatch) |
| ANSWER | `ANSWER; [content]` | Terminate and return final answer |

Maximum steps per task: 15. Temperature: 1 during generation.

### Error Recovery

If an action raises an exception during Selenium execution, the error message is fed back into the prompt and the model regenerates. Each error-correction attempt consumes one step from the budget.

### Evaluation Protocol (Auto-eval)

GPT-4V is used as an automatic evaluator. It receives:
- The task instruction
- The last k screenshots from the agent's trajectory (k=full trajectory best)
- The agent's final response

It outputs `SUCCESS` or `NOT SUCCESS`. Temperature set to 0 for evaluation. Human-GPT-4V agreement: κ = 0.70 (full trajectory), on par with human-human agreement (Fleiss' κ = 0.70).

|-------|------------------|

When evaluated by different LMMs as evaluators (GPT-4V, Claude-3-Opus, GPT-4o), each evaluator shows self-preference bias — Claude rates Claude highest (61.6%), GPT-4V rates GPT-4V highest (57.1%), GPT-4o rates GPT-4o highest (64.1%).

### Failure Mode Distribution (300 sampled failures)

| Failure Category | Ratio |
|-----------------|-------|
| Navigation Stuck (running out of steps) | 44.4% |
| Visual Grounding Issues (misinterpreting elements) | 24.8% |

### Dataset Statistics
- 643 total tasks, 15 websites, ~40-45 tasks per website
- 22.3% of questions have golden (exact) answers; 77.7% have possible (open-ended/changeable) answers
- 99.68% of task pairs have cosine similarity < 0.6 (all-mpnet-base-v2 embeddings)

## 3. Trade-offs

| Win | Cost |
|-----|------|
| +28.3pp absolute over GPT-4 (All Tools) (59.1% vs 30.8%) | Requires GPT-4V API access (proprietary, paid) — cannot use open-source LMMs due to resolution and context-length limits |
| +19.0pp absolute over text-only baseline | Screenshot pipeline (GPT-4V-Act labeling) adds latency per step; each observation consumes significant tokens (7000+ per 15-step trajectory) |
| Performs on real, live websites (no simulators) | Real websites introduce CAPTCHAs, popups, ads, layout churn — 44.4% of failures are "navigation stuck" due to real-world complexity |
| Automatic GPT-4V evaluation matches human reliability (κ=0.70) | Evaluator self-preference bias — GPT-4V rates itself more favorably; cross-model evaluation requires caution |
| Simple action space (7 actions) covers broad web tasks | No drag action, no file upload, no video handling; cannot handle login-gated content |
| Set-of-Mark on screenshots eliminates need for HTML DOM parsing | Text-heavy websites (Allrecipes, GitHub, ESPN) perform worse than vision-dominant sites — multimodal blending is suboptimal |
| Single-color black labels simplify visual grounding | Calendar date confusion, adjacent element misidentification (e.g., confusing calendar numbers with numerical labels) remain significant (24.8% failure rate) |

## 4. Design Rationale

**Why screenshots over HTML DOM**: Rendered web pages are designed with UX principles emphasizing intuitive layout and structured presentation. The HTML DOM tree or accessibility tree becomes excessively verbose for complex pages (e.g., Booking.com calendars, Google Flights date pickers), making text-only agents unreliable. Visual screenshots mirror how humans browse.

**Why GPT-4V-Act (rule-based) over object detection**: Rule-based element extraction from the DOM is efficient, requires no ML model, and web element types (`<button>`, `<input>`, `<a>`, `<select>`) are already semantically structured. Adding an object detector (e.g., Grounding DINO) adds complexity without benefit when HTML already defines interactive boundaries.

**Why ReAct + context clipping**: ReAct (thought-then-action) improves interpretability and decision quality. However, full screenshot history quickly exceeds context limits. Clipping to 3 most recent observations prevents confusion while preserving action/thought history for reasoning continuity.

**Why auto-eval with GPT-4V**: Human evaluation of 643 tasks with 3 annotators per 300-task subset is prohibitively expensive. GPT-4V auto-evaluation at κ=0.70 enables cheap, scalable, reproducible evaluation — critical for iterative agent development.

**Why 15-step budget**: Empirically chosen to balance task completion (most tasks finish within 5-10 steps) against cost and context length. The 15-step cap forces the agent to be efficient.

## 5. Limitations & Failure Modes

1. **Proprietary backbone lock-in**: Open-source LMMs (LLaVA, etc.) cannot be used because they (a) downsample images to 224x224 or 336x336, making small text illegible, and (b) have max context of 4096 tokens vs. the ~7000+ tokens needed for a 15-step trajectory.

2. **44.4% of failures are Navigation Stuck**: Agent wanders through irrelevant search results, cannot locate scrollable regions, oscillates between scrolling up/down, and repeats prior mistakes (context clipping removes corrective observations).

3. **24.8% of failures are Visual Grounding Issues**: Calendar date misidentification (e.g., selecting Dec 22 instead of Jan 22), confusing adjacent numerical labels, misinterpreting mathematical notation, not detecting subtle page changes between steps.

4. **21.8% Hallucination**: Agent settles for partial answers (e.g., only Module 1 quizzes when all modules required), or inputs into wrong textbox with no error signal.

5. **No login/CAPTCHA support**: Omits websites requiring authentication, limiting real-world coverage (e.g., email, banking, social media).

6. **No drag-and-drop, file upload, or video**: Action space limited to 7 basic operations.

7. **Evaluator self-preference bias**: Each LMM evaluator rates its own backbone highest — cross-model evaluation yields inconsistent rankings.

8. **Context clipping trade-off**: Keeping only 3 recent observations removes potentially useful earlier visual context, contributing to repetitive navigation errors.

## 6. Transfer to Lyra

**The One Idea**: **Screenshot-first multimodal observation with Set-of-Mark numerical labeling** — Overlaying bounding boxes with integer labels on interactive UI elements, combined with a rule-based element extractor (no ML detector needed), enables LMM-powered agents to ground actions in visual UI without parsing complex DOM trees. Lyra's browser/desktop automation modules can adopt this to handle dynamically rendered interfaces where DOM access is unreliable or excessively verbose.

**Workstream Route**: §4.2 (Multimodal Perception / Grounding) — directly feeds the visual grounding pipeline for Lyra's agent action space.

**Impact**: 4/5 — The 19pp gain over text-only and 28pp gain over tool-based alternatives (GPT-4 All Tools) demonstrates that visual grounding is a decisive capability differentiator for web agents. This is directly applicable to any agent that interacts with rendered UIs.

**Effort**: 3/5 — Requires (1) integrating a rule-based DOM element extractor (GPT-4V-Act or equivalent, ~open-source), (2) implementing screenshot capture + label overlay pipeline, (3) extending the ReAct prompt template to accept multimodal inputs. Medium engineering effort; the core pattern is well-specified.

**Tier**: **Breakthrough** — The ~19pp gap between multimodal and text-only settings on real websites is a capability cliff. Closing it requires structural architectural change (adding visual perception), not prompt tuning. This is a substantive capability unlock rather than incremental improvement.
