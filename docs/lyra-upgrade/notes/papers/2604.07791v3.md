# SEARL: Joint Optimization of Policy and Tool Graph Memory for Self-Evolving Agents

**Authors**: Xinshun Feng, Xinhao Song, Lijun Li (Shanghai AI Lab), Gongshen Liu (Shanghai Jiaotong Univ), Jing Shao (Shanghai AI Lab)
**Venue**: arXiv preprint 2604.07791v3, April 2026
**Code**: https://github.com/circles-post/SEARL
**Model**: Qwen3-4B (non-thinking mode), trained on 6x NVIDIA H200 (~10 hrs/epoch)

## 1. Mechanism

SEARL jointly optimizes an LLM policy and a structured external Tool Graph Memory (TG) via reinforcement learning. The core hypothesis is that tool-based memory anchors enable fine-grained credit assignment that raw state grouping cannot achieve in open-ended environments.

### 1.1 Tool Memory-Enhanced MDP

The agent operates in a Tool Memory-Enhanced MDP defined as ⟨S, A, P, R, TG⟩, where TG = (V, E):
- **V**: nodes = registered MCP tools (each tool is a Python function with name, description, argument spec, implementation code)
- **E**: directed edges encoding step-level execution dependencies between tools

### 1.2 Structured Trajectory Generation (4 phases)

Each action step is decomposed into four sequentially-annotated phases, delimited by XML-style tags:

**Phase 1 — Planning** (at t=1 only): Decompose task into subtask DAG G_plan = [(ST_i, ST_j), ...] where edges encode dependencies.

**Phase 2 — Retrieve**: A retrieval function μ selects the most relevant tool T_t from TG. Uses hybrid retrieval with two parallel scores:
- Sparse (TF-IDF) for keyword match: σ^text_i
- Dense (all-MiniLM-L6-v2 embeddings) for semantics: σ^sem_i
- Fused score: σ^hyb_i = α·σ^text_i + (1-α)·σ^sem_i, with α = 0.5

**Phase 3 — Reuse/Think/Action**: The policy π_θ generates actions in the format:
```
<subtask> ST_X: {step} </subtask>
<thinking> ... </thinking>
<tool_call> ... </tool_call>   or   <answer> \boxed{...} </answer>
```

**Phase 4 — Creation**: New tools are created via a `create_and_execute_mcp` function (name, description, arguments, returns, code, inputs). Created tools go into a candidate buffer C_new, not directly into TG.

The trajectory probability decomposes as:
```
p(τ) = ∏ μ(T_t|s_t, TG) · p_LLM(a_t|s_t, T_t) · p_LLM(T_{t+1}|a_t, T_t) · P(s_{t+1}|s_t, a_t)
        \_____(1)Retrieve_______/   \_____(2)Reuse_________/   \______(3)Creation_________/   \____(4)Transition____/
```

### 1.3 Reward Shaping

Four reward components combine into a composite signal:

| Reward | Type | Condition |
|--------|------|-----------|
| R(τ) = r_s if task solved, else 0 (r_s = 1) | Sparse/Outcome | End of trajectory |
| r_planning | Dense/Process | Plan parses into executable subtask sequence |
| r_creation | Dense/Process | New MCP tool conforms to registration format |
| r_execution | Dense/Process | Tool call executes successfully, returns valid output |
| r_format = +λ_format | Dense/Process | Output conforms to XML tag structure |

Total return: R(τ_i) = R_orm(τ_i) + Σ_t r^(i)_t

Penalties: Negative rewards for redundant tool invocations and failed creation attempts (drawn from Lee et al., 2025).

### 1.4 Two-Level Advantage Estimation (Tool-Memory-Aware)

The key innovation is using tool identity (not raw state) as the grouping anchor for step-level credit assignment.

**Level 1 — Episode Relative Advantage**:
For N trajectories {τ_i} under the same task:
```
G^E = {(τ_i, R(τ_i))}^N_{i=1}
A_E(τ_i) = [R(τ_i) - (1/N)Σ_j R(τ_j)] / std(R)
```

**Level 2 — Tool-Anchored Step Advantage**:
Let U = {g_1, ..., g_|U|} be the set of distinct MCP tools across all trajectories. For each tool anchor g, collect all actions that used g:
```
G_S(g) = { (a^(i)_t, R^(i)_t) | (i,t) ∈ I_g }
```
where R^(i)_t = Σ^T_{k=t} γ^{k-t} r^(i)_k is the discounted return-to-go.

The step relative advantage for action a^(i)_t in group g:
```
μ_G = (1/|G_S(g)|) Σ_{(a,r)∈G_S(g)} r
A_S(a^(i)_t) = [R^(i)_t - μ_G] / std(G_S(g))
```

**Combined advantage**: A(a^(i)_t) = A_E(τ_i) + ω · A_S(a^(i)_t), where ω balances the two levels.

### 1.5 Policy Optimization (Clipped PPO-style)

```
J_SEARL(θ) = E[ (1/NT) Σ_i Σ_t min( ρ^(i)_θ(a_t)·A(a^(i)_t), clip(ρ^(i)_θ, 1±ε)·A(a^(i)_t) ) - β·KL(π_θ || π_ref) ]
```
where ρ_θ is the importance weight π_θ / π_θold. Only reasoning and tool-invocation tokens contribute to loss; tool execution outputs are excluded.

### 1.6 Memory Update and Consolidation

At the end of each training iteration:
1. **Filter**: From C_new, select tools from the highest-reward trajectory only
2. **Semantic Merging**: Compute cosine similarity between new tool v and existing tool v' using normalized embeddings ẽ(v)^⊤ ẽ(v'). If sim(v, v') ≥ δ, merge v into v'; otherwise register as new node
3. **Edge Redirection**: When tools merge, incident edges are redirected to the consolidated node, accumulating dependency patterns
4. **Global Update**: TG ← Merge(TG, {T^(i)_G}^N_{i=1})

### 2.2 Key Performance Signals

- **Multi-hop QA dominance**: SEARL achieves best or second-best on all 4 QA benchmarks. On Bamboogle (the hardest, requiring synthesis from disjoint sources), SEARL at 0.3040 is 1.9× ARPO (0.1760) and 1.9× GRPO (0.1600).
- **AIME24**: Ties ARPO at 0.3333, substantially ahead of GRPO (0.1333) and DAPO (0.1333) — the strongest complex math result.
- **Simple math**: Slight regression vs GRPO: GSM8K (-0.0250), MATH500 (-0.0540). The authors acknowledge this as tool-generation procedural noise overhead on problems where monolithic reasoning suffices.

### 2.3 Ablation Results (Figure 4)

Three components removed:
- **w/o Step Grouping**: Largest degradation — causes near-zero performance on AIME24 and severe drops on Bamboogle, confirming tool-anchored groups are the critical mechanism
- **w/o Step Rewards**: Noticeable drop across most benchmarks, confirming dense process rewards are necessary
- **w/o Single Vanishing** (bypass group advantage when |G_S(g)|=1): Smaller but non-negligible impact, essential for stability

### 2.4 Training Dynamics (Figure 3)

- SEARL training rewards consistently outperform GRPO throughout training (though both remain negative due to strict penalties)
- SEARL maintains higher policy entropy throughout training, indicating sustained exploration vs premature convergence of GRPO

### 2.5 Tool Graph Evolution (Figure 6)

Four snapshots show structural growth:
- t₁: N=3, E=2 — small isolated tools (horse_hier, det_match, count_wins)
- t₂: N=5, E=4 — tools become connected via reuse/merging
- t₃: N=9, E=8 — three functional clusters emerge (Cluster A: horse/matchup, Cluster B: geometry/combinatorics, Cluster C: algebra/solve)

| Structured tool memory enables cross-task knowledge transfer | Dense reward design may still incentivize superficial reward hacking |
| Fine-grained credit assignment via tool-anchored groups | Only validated on 4B model; scaling behavior unknown |
| Semantic merging prevents tool duplication | Tools generated by 4B model may be too trivial for other LLMs to reuse |
| Sub-linear tool graph growth (14 nodes after full training) | Tool graph quality depends on trajectory quality during early training |

## 4. Design Rationale

The authors address a fundamental limitation in RLVR for agents: the vast, continuous state space in open-ended environments makes raw state-based grouping (as in GiGPO/GRPO) impractical for step-level credit assignment. Their key insight is that **tool identity provides a natural, finite abstraction** of the state space — agents operating with the same tool are in analogous state subspaces regardless of the specific task. This is grounded in the observation that tool-based evolution (Alita, STELLA) and memory-based evolution (Agent KB) are typically treated as independent modules, when in fact they are complementary: tool creation defines the vocabulary over which memory retrieval operates.

The choice of graph structure (rather than flat list or key-value store) is motivated by the need to capture execution dependencies that encode causal relationships between subtasks. The divide-and-conquer tool creation strategy (many small tools vs one monolithic tool) is driven by the limited reasoning capacity of the 4B model — monolithic tools frequently fail, while modular tools enable hierarchical constraint enforcement.

## 5. Limitations and Failure Modes

1. **Simple-task regression**: Tool generation overhead causes performance regression on GSM8K and MATH500, where monolithic reasoning suffices. The agent may create unnecessary tools, adding procedural noise.
2. **Toolset specificity**: Tools developed during training may not transfer to unseen domains (e.g., direct search, specialized reasoning). The tool graph's value is bounded by the training distribution.
3. **Tool quality ceiling**: Due to the 4B model scale, many generated tools are "trivial and too simplistic to be effectively reused by other LLMs" (authors' own words).
4. **Reward hacking susceptibility**: Despite careful design, the composite reward may incentivize superficially correct but shallow reasoning paths. The negative training rewards throughout suggest the penalty structure may be overly harsh.
5. **Single-model validation**: Only tested with Qwen3-4B. Whether the approach scales to 7B, 14B, or 32B models (where tool quality would presumably improve) is unknown.
6. **Convergence dependency**: Early training trajectories determine tool graph quality; poor initial exploration could lock in suboptimal memory structures.
7. **Compute cost**: Requires full RL training loop with 6× H200 GPUs and tool graph maintenance overhead. Not a plug-and-play inference-time method.

## 6. Transfer to Lyra

**The ONE transferable idea**: Build a **Tool Graph Memory (TGM) subsystem** for Lyra that maintains a directed graph of plugin/tool nodes connected by execution-dependency edges. Each node stores (name, description, embedding, implementation). During task execution, Lyra retrieves relevant subgraphs via hybrid TF-IDF + embedding search, uses the dependency edges to plan tool chains, and merges newly created tools via semantic similarity. The graph structure captures *causal ordering* between tools that flat memory (current Lyra design) cannot express.

**Workstream route**: **§4.2 (Memory Subsystem)** — this directly upgrades Lyra's memory architecture from flat key-value observation storage to structured, relational tool memory with dependency-aware retrieval. It also has secondary implications for §4.5 (Tool/Plugin System) regarding dynamic tool creation and registration.

| Dimension | Score | Rationale |
|-----------|-------|-----------|
| **Impact** | 4/5 | Structured tool memory with dependency edges is a substantial architectural upgrade over flat memory; enables compositional tool reuse that current Lyra lacks |
| **Effort** | 4/5 | Requires: (1) embedding model integration (all-MiniLM-L6-v2 or similar), (2) graph database or in-memory graph structure, (3) hybrid retrieval pipeline, (4) semantic merging logic, (5) integration with existing Lyra tool system |
| **Tier** | **investigate** | Worth prototyping as a memory-layer experiment, but the 4B-only validation, reward hacking concerns, and ~10hr/epoch training cost suggest caution before full integration.
