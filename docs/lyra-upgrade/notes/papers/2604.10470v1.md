## 1. Mechanism (step-by-step)

JURISMA is a three-phase modular pipeline that decomposes open-ended Legal Consultation QA (Legal CQA) into structured reasoning steps, coordinated by a Manager Agent.

### Phase I: Legal Element Graph Construction

An **Element Agent** parses the free-form user query `q` into a structured semantic graph `G = (V, E)` serialized in JSON. The graph captures:

- **Nodes (V):** Entities (individuals/organizations with role/status/timestamp attributes), Events (legal actions/disputes), User claims, Key facts, Inferred legal questions.
- **Edges (E):** Semantic relations — kinship, contractual duties, legal involvement, application targets.

Design grounded in jurisprudential theory: Hart's primary/secondary rule distinction and Kelsen's hierarchical normative model. The graph is serialized into a prompt `P_G` and concatenated with `q` to form `u = [P_G; q]` — the structured input for downstream generation.

### Phase II: Multi-agent Iterative Optimization (Algorithm 1)

```
Initialize: r0 = f([P_G; q])  via Draft Agent
For t = 0..T (T ≤ 5):
  a_t = ManagerAgent(r_t)     // decide what action needed
  if a_t = ∅ or "Pass": break  // draft acceptable
  if "FormatCheck" ∈ a_t:
    s_t = FormatCheckAgent.getSuggestions(r_t)
    r_t = DraftAgent.applySuggestions(r_t, s_t)
  if "LawSearch" ∈ a_t:
    l_t = LawSearchAgent.retrieveStatutes(q, r_t)
    r_t = DraftAgent.integrateStatutes(r_t, l_t)
Final: r_final = ContentCheckAgent(r_t)
```

**Agent roles:**
- **Draft Agent:** Generates initial response and applies suggestions.
- **Manager Agent:** Central controller that assesses draft quality on two criteria: (1) linguistic adequacy (clarity, conciseness) and (2) legal completeness (statutory references). Decides to invoke FormatCheck, LawSearch, both, or Pass.
- **Format Check Agent:** Reviews for redundancy, clarity, stylistic issues; outputs concrete editing suggestions.
- **Law Search Agent:** Retrieves authoritative statutory provisions from Chinese law databases.
- **Content Check Agent:** Final rewrite into dual-section output (Response + Legal Basis) preserving legal meaning while improving clarity.

### Phase III: Content Revision

Content Check Agent produces the final output in two sections:
1. **Response:** Concise, readable advisory opinion.
2. **Legal Basis:** Full statutory article text supporting the conclusion.

### Training: DPO on JURISCQAD

Direct Preference Optimization with sigmoid preference loss:

```
Δ_θ(x, y+, y-) = log π_θ(y+|x) − log π_θ(y-|x)
P_θ(x, y+, y-) = σ(β · Δ_θ(x, y+, y-))
L_DPO(θ) = −E[log P_θ(x, y+, y-)]
```

- Base model: Qwen2.5-14B-Instruct (LoRA, rank=8, α=16)
- Training: DeepSpeed Stage 2, 2× A100 80GB, batch_size=128, lr=1×10⁻⁵, cosine schedule, β=0.1, 3 epochs, max_seq_len=1024, bf16
- Negative samples: LLM-generated distractors with controlled subtle flaws (incorrect statutory refs, flawed reasoning, unsupported conclusions) — designed to be plausible but wrong

## 3. Trade-offs

| Win | Lose |
|---|---|
| Best overall across lexical + semantic metrics (Rouge-L 31.14, BertScore 75.05, LLM Score 3.93) | Multi-agent architecture adds latency — explicit limitation for real-time deployment |
| Structured element graph provides interpretable, auditable reasoning trace | Chinese-only training data; cross-lingual/cross-jurisdiction transfer is zero-shot only |
| Iterative refinement corrects errors before final output (Revision contributes largest ablation gain) | Up to 5 refinement iterations; no latency budget optimization studied |
| DPO with expert-verified triplets yields high-quality alignment signal | Requires expensive expert annotation pipeline (licensed legal professionals) |
| Modular, pluggable agents — easy to extend with new capability agents | Smaller backbone (Qwen2.5-14B) deliberately used; 33B+ models not tested |
| Strong generalization across language, task, and jurisdiction | Topic bias toward high-frequency consultations; may underperform on rare/specialized cases |
| Publicly released dataset (43K+ instances) | Non-commercial academic license only |

## 4. Design Rationale

**Why structured graphs over retrieval?** Retrieval-augmented methods (e.g., LSIM, LexRAG) concatenate statutes to queries but confuse legally distinct yet linguistically similar terms. The element graph explicitly models entity-relation-fact chains, distinguishing "contractual privity" from "kinship" even when both involve person-to-person connections. This is grounded in legal philosophy (Hart 2012, Kelsen 1967) treating law as a structured system of subjects, facts, norms, and relationships.

**Why multi-agent over end-to-end?** End-to-end generation (used by GPT-4o, LawGPT) ignores the stepwise nature of legal reasoning: identify relationships → determine causation → isolate core issue → match to statutes. The Manager Agent emulates a supervising attorney reviewing drafts, activating specialists (format, legal search) only when needed — mimicking professional legal writing workflows.

**Why DPO over RLHF?** DPO directly optimizes the preference gap between expert-approved and subtly-flawed responses without training a separate reward model. The controlled negative sample generation (subtle flaws: incorrect statute numbers, flawed reasoning, unsupported conclusions) creates a harder discrimination task than trivial distractors.

**Why Qwen2.5-14B over larger models?** Deliberate choice to demonstrate that structural innovation (not model scaling) drives gains. The authors explicitly note Qwen3-14B has stronger base capabilities but JURISMA on Qwen2.5-14B still outperforms Qwen3-14B across all metrics.

## 5. Limitations & Failure Modes

1. **Latency for real-time deployment:** Multi-agent iterative refinement (up to 5 rounds) introduces additional inference latency. No latency benchmarking or optimization is provided.
2. **Topic distribution bias:** Despite 43K instances covering diverse scenarios, the dataset may over-represent high-frequency consultation topics (contract, tort, family law) and under-represent rare/specialized legal domains.
3. **Chinese legal system lock-in:** All training data and statutory retrieval is Chinese Civil Code post-2021. Cross-jurisdiction transfer to Korean law (KoBLEX) or English law (LEGALBENCH) is zero-shot only.
4. **Expert annotation bottleneck:** The DPO training pipeline requires licensed legal professionals for verification — not scalable to new domains without equivalent expert resources.
5. **Corrected benchmark circularity:** The authors corrected 340/500 LawBench test cases (68% error rate in original). While justified, evaluating on a self-corrected benchmark introduces potential confirmation bias.
6. **No latency-accuracy Pareto analysis:** The trade-off between iteration count and output quality is not characterized — it is unclear whether 5 iterations are actually needed vs. 2-3 iterations.
7. **Single backbone model:** All agents share the same fine-tuned Qwen2.5-14B base. Specialized agents (LawSearch) might benefit from different architectures (e.g., dense retrieval models).
8. **Negative sample quality dependence:** DPO performance depends on the quality of LLM-generated negative samples. Poorly constructed negatives could teach the model to discriminate on superficial features rather than legal correctness.

## 6. Transfer to Lyra

### The ONE Transferable Idea

**Element Graph + Manager-Coordinated Multi-Agent Iterative Refinement as a verification architecture.** JURISMA demonstrates that converting ambiguous user input into a structured semantic graph (entities, claims, key facts, questions), then routing through specialized agents coordinated by a manager with explicit quality gates, produces measurably more accurate and interpretable output than monolithic generation. For Lyra, this pattern maps naturally to the verification subsystem: transform a user request + tool execution trace into a verification element graph (assertions, evidence, assumptions, risks), then route through agents specialized in fact-checking, policy-grounding, consistency-checking, and style/format verification — with a manager deciding which agents to invoke based on intermediate output quality.

### Workstream Route

**§4.7 Safety & Verification** — The Manager-coordinated multi-agent iterative loop with explicit pass/fail gating is a direct architectural template for Lyra's output verification pipeline. It also informs §4.2 Memory (structured semantic graphs as persistent verification context) and §4.3 Context (element-graph-based context representation for reasoning tasks).
