# LegalGraphRAG: Multi-Agent Graph Retrieval-Augmented Generation for Reliable Legal Reasoning

**Authors:** Zerui Chen, Qinggang Zhang, Zhishang Xiang, Zhimin Wei, Linfeng Gao, Xiao Huang, Zhihong Zhang, Jinsong Su — Xiamen University & The Hong Kong Polytechnic University
**Venue:** arXiv preprint, May 27, 2026 | **arXiv ID:** 2605.28120v1 | **Code:** https://github.com/XMUDeepLIT/LegalGraphRAG

## 1. Mechanism (step-by-step)

LegalGraphRAG operates in two phases: **Hierarchical Knowledge Construction** (offline) followed by **Evidence-Based Legal Reasoning** (online, multi-agent).

### Phase 1: HierarGraph Construction

The HierarGraph H is a three-layered graph designed to decouple heterogeneous legal knowledge:

**Fact Graph G_fac** (Eq.4): Links Cases (C) → Articles (A) via citation edges e_ca, and Cases (C) → Offenses (O) via conviction edges e_co. Contains ~14K cases with ~818 distinct charge labels. Provides ground-truth precedent anchoring.

**Ontology Graph G_ont** (Eq.5): Abstracts raw case narratives into four legal-ontology dimensions: Defendant Attributes, Criminal Behaviors, Victim Characteristics, and Subjective Mental States. Extracted keywords/entities become Case Feature Nodes (F). k-NN (cosine similarity) connects cases with high semantic overlap; the Leiden community detection algorithm clusters cases into Community Nodes (K), each containing a summary of clustered cases for coarse-to-fine hierarchical retrieval.

**Rule Graph G_rul** (Eq.6–7): Links Articles (A) to Judicial Interpretations (J). Crucially, each article node a_i is equipped with a **Diagnostic Checklist D(a_i)** — a set of atomic boolean queries decomposed from statutory text. Example: for Article 266 (Fraud), check (1) "Did the defendant fabricate facts?", (2) "Did the victim fall into mistake?", (3) "Did the victim dispose of property based on mistake?".

Graph construction uses GPT-4o-mini for entity extraction and BGE-m3 embeddings for vector representations. Total offline indexing time: 3,687 seconds with 3.97M tokens consumed.

### Phase 2: Multi-Agent Evidence-Based Reasoning

Three specialized agents operate sequentially over the HierarGraph:

**Researcher Agent (Retrieval — §4.3.1):** Given a raw case query q, extracts ontology-aligned features φ(q) and executes three parallel retrieval strategies whose results are UNION-ed:

R(q) = R_sem(q) ∪ R_com(q) ∪ R_chg(q)

1. **Semantic Match Retrieval** (Eq.9): Top-k similar cases from G_ont via cosine similarity of ontology-aligned embeddings: R_sem(q) = Top-k_{c∈G_ont} sim(φ(q), φ(c))

2. **Community Expansion Retrieval** (Eq.10): Identifies the best-matching community K* = argmax_{K∈G_ont} sim(φ(q), φ(K)), then retrieves top-k similar cases within that community: R_com(q) = Top-k_{c∈K*} sim(φ(q), φ(c))

3. **Charge-Anchored Retrieval** (Eq.11): Predicts candidate charges O(q) via LLM (confidence > 30%), then retrieves neighboring cases from G_fac for each predicted charge: R_chg(q) = ∪_{o∈O(q)} N_Gfac(o)

The default parameter k = 5, selected based on sensitivity analysis (k ∈ {3,4,5,6}).

**Auditor Agent (Validation — §4.3.2):** Validates each candidate article v_a from the retrieved evidence via a verify-and-prune loop:

1. Retrieves the Diagnostic Checklist D(v_a) and Judicial Interpretations J from G_rul
2. For each diagnostic item d_k ∈ D, executes CheckCondition(q, d_k, v_a, J) → {true, false}
3. Aggregates verification results; if IsApplicable is False, prunes the article and all its dependent case/charge nodes: S_verified ← Prune(S_verified, v_a)

**Adjudicator Agent (Synthesis — §4.3.3):** Synthesizes the verified subgraph S_verified into a final judgment Y with explicit citations:

Y = Adjudicator(q ⊕ V^f_A ⊕ V^f_C ⊕ V^f_O)

Every output includes specific statutory article numbers and case references (e.g., "[1] corresponds to Article 271 Paragraph 1"), making the reasoning chain fully traceable.

### Key Algorithm (pseudocode from Algorithm 1, p.18):
```
1. ϕ(q) ← OntologyAlign(q, G_ont)
2. S_cand ← R_sem ∪ R_com ∪ R_chg
3. S_verified ← S_cand
4. For each article v_a ∈ S_cand:
   a. D ← RetrieveChecklist(v_a, G_rul)
   b. J ← RetrieveInterpretations(v_a, G_rul)
   c. For each d_k ∈ D: r_k ← CheckCondition(q, d_k, v_a, J)
   d. If not Decide(V_results): S_verified ← Prune(S_verified, v_a)
5. Y ← Adjudicator(q ⊕ V^f_A ⊕ V^f_C ⊕ V^f_O)
6. Return Y
```

## 4. Design Rationale

The authors ground their design in two empirical findings from preliminary studies (Section 3):

1. **Flat retrieval has granularity bias** (Fig.2): A hierarchical retrieval strategy that separates articles from cases improves retrieval by 25.3%, confirming that flat vector stores conflate factual details with abstract principles.

2. **Unverified retrieval is fragile to noise** (Table 1): Adding 2–6 irrelevant but semantically-similar distractors to RAG context causes steep performance drops (up to -13% ACC on charge, -27.9% on article), proving that a verification step is necessary for high-stakes domains.

These findings directly motivate the HierarGraph (to solve granularity conflicts) and the multi-agent Auditor (to enforce verification). The authors chose a three-agent sequential architecture rather than a single model with chain-of-thought because each agent has a distinct, verifiable responsibility — retrieval completeness (Researcher), factual-legal alignment (Auditor), and synthesis with traceability (Adjudicator). This decomposition mirrors real legal workflows (evidence gathering → cross-examination → verdict writing).

The Diagnostic Checklist mechanism is preferred over pure semantic similarity because legal articles with nearly identical keywords can have opposite applicability based on fine-grained conditions (e.g., state functionary vs. private employee determining Article 382 vs. 271).

## 5. Limitations & Failure Modes

1. **Unimodal input only:** The system processes only textual legal documents. Real-world judicial proceedings involve photographs, surveillance footage, audio recordings, and handwritten documents. Non-textual evidence requires manual transcription, risking loss of critical visual/auditory cues (e.g., distinguishing intent from negligence from surveillance video).

2. **Chinese legal system only:** All experiments use Chinese legal benchmarks (CAIL2018, CMDL). The Common Law system (US, UK) has fundamentally different structures (stare decisis, case law primacy) that the hierarchical civil-law graph may not transfer to.

3. **Curated subsets from large datasets:** Due to token cost and latency concerns, experiments used filtered subsets (cases < 1024 chars, sampled for rare charges). Performance on the full 2.6M-case CAIL dataset is unreported, and the authors note the sampling strategy produces "more challenging" distributions that "may lead to lower reported performance for some methods."

4. **High online latency (46.1s/query):** The multi-agent sequential pipeline with LLM calls for each diagnostic checklist item is too slow for interactive use. No caching or speculative execution is explored.

5. **Dependence on LLM for graph construction:** GPT-4o-mini is used for ontology extraction and checklist generation. Errors in entity extraction or checklist decomposition propagate silently — there is no human-in-the-loop verification of graph quality.

6. **Sequential agent dependency:** The Auditor cannot start until the Researcher completes; the Adjudicator depends on both. An error in early stages cascades. No recovery or backtracking mechanism exists.

7. **Scalability of Diagnostic Checklists:** The paper shows checklists for fraud (Article 266) but doesn't discuss how checklist generation scales to the full 452-article corpus or how checklist quality is validated.

## 6. Transfer to Lyra

**The ONE transferable idea:** The **Diagnostic Checklist + Auditor verify-then-prune pipeline** — decomposing complex verification rules into atomic boolean queries that a dedicated Auditor agent sequentially evaluates, with explicit pruning of unsupported evidence before the final synthesis step. This is directly applicable to Lyra's need for evidence-grounded, traceable reasoning in its research report generation.

**Workstream route:** §4.4 (Verification & Safety) — the Auditor pattern is a verification mechanism that filters retrieved context for factual support before generation, preventing Lyra from synthesizing claims on unsupported evidence. It maps cleanly to Lyra's "citation verification" and "claim-grounding" needs.

**Impact:** 4 | **Effort:** 4 | **Tier:** breakthrough

**Why:** The checklist decomposition is conceptually simple but operationally powerful — it replaces a single "is this claim supported?" LLM call with a systematic, attributable verification chain. For Lyra, this could verify each factual claim in a generated research report against its source context, producing explicit pass/fail annotations similar to the paper's "Traceable Correct" metric. The core idea (decompose verification into atomic checks, verify each, prune unsupported, synthesize from remainder) requires no domain-specific ontology — only a structured decomposition of what "supported by evidence" means for a research claim. Implementation effort is moderate (need to define checklist items for claims, implement the prune loop), but the gain in output trustworthiness is significant.
