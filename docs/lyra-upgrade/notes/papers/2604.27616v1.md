## 1. Mechanism (step-by-step)

RoadMapper is a multi-agent system that decomposes research roadmap generation into three stages: **initial generation, knowledge augmentation, and iterative "critique-revise-evaluate."** Six LLM-driven agents collaborate:

### Agent Pipeline

1. **Init Agent (I):** Generates an initial roadmap draft from the research problem `x_problem`. Output is a Markdown tree with hierarchical nodes: `y_initial = I(x_problem)`.

2. **Knowledge Agent (K):** Augments the initial roadmap using a two-stage process:
   - Stage 1: Generates internal knowledge via prompting; retrieves top-K (K=30) external skill points from Skill-Repo using Qwen3-Embedding-8B (8192-dim vectors) + ChromaDB cosine similarity search.
   - Stage 2: Inserts relevant skill points as nodes into the roadmap at appropriate positions: `y' = K(knowledge, y_initial)`.

3. **Logic Critique Agent (L):** Critiques logical relationships, producing revision suggestions `LC_t`. Defines two relationship types:
   - Parent-child Logic: child node must be a direct refinement of parent.
   - Sibling Logic: siblings must exhibit parallel-progressive relationships.
   - `LC_t = L(y_t)`

4. **Granularity Critique Agent (G):** Critiques decomposition granularity, producing revision suggestions `GC_t`. Detects two failure modes:
   - Too Detailed: excessive trivial subtasks.
   - Too Brief: information-dense nodes needing decomposition.
   - `GC_t = G(y_t)`

5. **Revise Agent (R):** Implements revisions to the roadmap based on suggestions from L and G: `y_{t+1} = R(y_t, LC_t, GC_t)`.

6. **Evaluate Agent (E):** Scores roadmaps on 4 dimensions (Logic Structure, Granularity Degree, Topic Relevance, Completeness), each 0-100. Passing score = 80.
   - `E_t = E(y_{t+1})` — if `E_t = ACCEPT`, output `y_{t+1}`; else continue iteration.

### DPO Training of E Agent

The E agent is aligned with domain experts via Direct Preference Optimization:
- **Backbone:** Qwen3-8B/14B/32B
- **Preference Dataset Construction:** For each roadmap, Qwen3-32B generates 10 evaluation candidates. Seven experts vote; highest-vote candidate = positive `y_w`; second-highest = negative `y_l` (not lowest — second-best evaluations contain subtle flaws for fine-grained preference learning). 36 format-correction pairs also added. Total: 818 preference pairs.
- **DPO Objective:**
  ```
  L_DPO = -E_D[log σ(β · log(π_θ(y_w|x)/π_ref(y_w|x)) - β · log(π_θ(y_l|x)/π_ref(y_l|x)))]
  ```
  `β = 0.2`, sigmoid loss, 2 epochs, lr = 5e-5, AdamW, BF16 mixed-precision.
- **Effect:** Format error rate drops from 8% to 3%.

### Algorithm
```
y_initial ← I(x_problem)
y_knowledge ← K(y_initial, knowledge)
y_0 ← y_knowledge, t ← 0
while t < T_max (5) do:
    LC_t ← L(y_t), GC_t ← G(y_t)
    y_{t+1} ← R(y_t, LC_t, GC_t)
    E_t ← E(y_{t+1})
    if E_t = ACCEPT: return y_{t+1}
    else: t ← t + 1
return y_t
```

## 3. Trade-offs (wins vs loses)

| Win | Lose/Cost |
|---|---|
| +8.35 avg improvement on Llama 3.3 70B vs Direct Prompting | ~1.5-1.6x iterations per inference vs single-pass Direct Prompting |
| 84% time reduction vs human experts | Higher token cost than single-pass baselines (but 45.8% less than ReConcile) |
| Enables small models (8B) to beat larger proprietary models (Claude 3 Haiku) using simpler methods | Requires DPO training infrastructure (4x RTX PRO 6000, ~14 GPU-hours for 32B) |
| Statistical significance on all metrics (p < 0.001) | DPO on too-small backbone (8B) degrades performance below no-DPO baseline |
| Early stopping averages 1.5-1.6 iterations — balances quality and cost | Max 5 iterations still a computational bound; quality plateaus may waste resources |
| Format error rate drops 8% → 3% with DPO format pairs | DPO causes minor regression on math benchmarks (−1.72 on GSM8K) |
| RoadMap benchmark is bilingual (EN+CN), multi-field (10 domains) | Evaluation relies on GPT-4o mini as proxy judge (though validated at 93% human agreement) |
| Modular agent design — each agent is independently promptable/replaceable | 6-agent pipeline complexity; debugging requires tracing across multiple LLM calls |

## 4. Design Rationale

The authors motivate their multi-agent decomposition by identifying three specific failure modes of single-model prompting: **Q1 (lack of professional knowledge), Q2 (unreasonable task decomposition), Q3 (disordered logical relationships).** Rather than attempting to solve all three through a single mega-prompt, they assign each to a specialized agent (K, G, L respectively). The "critique-revise-evaluate" loop mirrors the human expert process of drafting, reviewing, and iterating.

The choice of **second-highest-vote** (not lowest) candidate as the DPO negative sample is a clever design decision: second-best evaluations differ only subtly from the best, forcing the model to learn fine-grained expert preferences rather than merely distinguishing good from terrible. The E agent uses DPO rather than supervised fine-tuning because alignment with expert judgment requires relative preference optimization, not absolute score regression.

## 5. Limitations & Failure Modes

1. **LLM-dependent prompt ceilings:** Model performance is bounded by prompt design quality; more effective prompts may exist but remain unexplored.
2. **Higher compute cost vs single-pass:** Despite early stopping, the multi-iteration critique loop is fundamentally more expensive than Direct Prompting. The authors acknowledge this as an optimization opportunity.
3. **Incomplete model coverage:** Due to compute constraints, experiments excluded some prohibitively expensive models. Generalizability to all model families is not fully validated.
4. **Evaluator backbone sensitivity:** DPO on Qwen3-8B degraded below the no-DPO baseline, meaning the Evaluate agent requires a minimum model capacity (>=14B) to benefit from DPO alignment.
5. **Benchmark scope limitation:** RoadMap covers 10 fields but is academic-dissertation-sourced, potentially missing industry-style roadmap requirements (agile methodologies, resource constraints, timeline considerations).
6. **Dataset construction error:** 19.3% of roadmaps required format corrections, and 5.3% of skill points were redundant — the benchmark had a non-trivial quality assurance burden.
7. **Evaluation proxy risk:** Content metrics (StepScore, LogicScore) depend on GPT-4o mini as evaluator. Cross-model validation shows 90-93% agreement, but 7-10% divergence remains.

## 6. Transfer to Lyra

**The ONE transferable idea:** The "critique-revise-evaluate" (CRE) loop with specialized critique agents — separate Logic Critique and Granularity Critique agents analyze different quality dimensions, a Revise agent implements fixes, and a DPO-trained Evaluate agent acts as quality gate. This is a validated, reusable pattern for any structured-output generation task in Lyra.

**Why this matters for Lyra:** Lyra's planning subsystem (§4.20) currently generates plans but lacks a principled iterative refinement loop. RoadMapper's CRE pattern could be adapted so Lyra's Planner agent generates an initial plan, Critique agents (e.g., Completeness Critique, Feasibility Critique) review it, a Revise agent iterates, and a DPO-aligned Evaluate agent gates output quality. The 86% human preference win-rate demonstrates that iterative critique-refinement substantially outperforms single-pass generation.

**Route to:** §4.20 Planning, with secondary applicability to §4.14 Autonomy (the iterative loop pattern) and §4.15 Deep Research (structured roadmap generation for research problems).

|---|---|---|
| Impact | 4 | Validated 8% avg improvement across 11 models; CRE pattern is directly applicable to Lyra's planning and autonomy pipelines |

| Tier | **investigate** | Not a paradigm-shifting breakthrough but a practical, well-engineered multi-agent refinement pattern worth adapting for Lyra's structured output generation |

### Concrete Implementation Sketch for Lyra
```markdown
1. Split Lyra's single Planner prompt into two critique dimensions:
   - Completeness Critique: "Are there missing steps?"
   - Feasibility Critique: "Are tasks at the right abstraction level?"
2. Create a Revise agent that consumes critique + original plan → revised plan
3. Use Lyra's existing Verifier as Evaluate agent (or prompt-tune one)
4. Set a quality threshold; iterate critique-revise-evaluate until threshold met or max N iterations
5. (Optional) Collect plan preference pairs from user feedback for future DPO alignment
```
