## 1. Mechanism (step-by-step)

PA-Tool (Pretraining-Aligned Tool Schema Generation) is a **training-free** method that renames tool and parameter names in schemas to match naming conventions internalized by a target language model during pretraining. The core insight: SLMs fail at tool use not because they cannot reason, but because they **hallucinate** plausible tool names that do not exist in the provided schema. The model defaults to names it saw during pretraining rather than the names in the schema. PA-Tool flips the problem — instead of adapting the model to the schema, adapt the schema to the model.

### Algorithm (3 stages)

Let `M` be a pretrained language model, `d` a component description (tool or parameter). Generate an optimal name `s*`:

**Stage 1: Candidate Generation**
- Given description `d`, sample `N` candidate names `C = {s1, s2, ..., sN}` from `M` at temperature `t ∈ (0, 1]`.
- Generate a reference name `s_ref` via greedy decoding (`t=0`) for tie-breaking.
- Default: `N=32`, `t=0.4`.

**Stage 2: Peakedness Computation**
- Define a length-adaptive similarity threshold:
  ```
  τ = α · ℓ_max
  ```
  where `ℓ_max = max_{si ∈ C} |si|` (max character length across all candidates) and `α=0.2` controls strictness.
- Compute peakedness score for each candidate `si`:
  ```
  φ(si) = Σ_{j≠i} Ⅰ(d_edit(si, sj) ≤ τ)
  ```
  where `d_edit` is character-level Levenshtein edit distance, `Ⅰ` is the indicator function.
- Intuition: candidates with many similar variants indicate patterns the model produces consistently — a signal of pretraining familiarity. Peakedness is repurposed from **contamination detection** literature (CDD, Dong et al. 2024), where it identifies memorized benchmark data.

**Stage 3: Schema Selection**
- Select the candidate with maximum peakedness:
  ```
  s* = arg max_{si ∈ C} φ(si)
  ```
- On ties: select candidate closest to `s_ref` by edit distance.
- Iterate across all components in the tool hierarchy (tool names, then parameter names).

**Name Collision Resolution:** When different tools/parameters receive identical PA-Tool names, a priority-based locking mechanism resolves collisions: the component with highest peakedness claims the name; others cascade to their next-best candidate.

### Key design choices
- **Character-level edit distance** over token-level: works with any model, does not require tokenizer access. Limitation: evaluated only on English.
- **Peakedness over frequency**: the most-frequent candidate is not always best. Peakedness captures distributional *concentration* — a tight cluster of similar variants indicates deeper memorization.
- **Temperature 0.4**: exploration beyond greedy while retaining stability. Sensitivity analysis shows performance stable across `t ∈ [0.2, 1.0]`.

### One-time preprocessing
Schema generation takes **8-16 wall-clock seconds** (Intel Xeon Gold 6230, NVIDIA A100 80GB, vLLM 0.10.2). Once generated, the mapping is cached and reused indefinitely at inference time with zero overhead.

## 3. Trade-offs

| Win | Lose |
|-----|------|
| Training-free — no GPU hours for fine-tuning, no catastrophic forgetting | Requires model access for candidate generation (not applicable to API-only closed models without sampling) |
| One-time 8-16s schema generation, zero inference overhead | Gains diminish for LLMs (>8B); schema misalignment is a smaller fraction of total errors |
| 80% reduction in schema misalignment errors | Only renames tool/parameter names — does not touch descriptions |
| Outperforms human-designed schemas on some tasks (Llama3.2-3B Similar: 65.7% vs 58.6%) | Character-level edit distance may not work well for non-Latin scripts or morphologically complex languages |
| Complements both SFT and other training-free methods (EasyTool, constrained generation, retrieval correction) | Schemas are model-specific; cross-model transfer works but is suboptimal (self-generated > transferred) |
| Human evaluation shows PA-Tool names are rated *more* intuitive than originals (3.41 vs 2.72 on understandability, p<10⁻³⁵) | Risk of name collisions (4-6% of components) requiring collision resolution mechanism |
| Works across model families (Qwen, Llama, Mistral, GPT, Gemini) and scales (1.7B to 70B) | Peakedness as familiarity signal is an empirical correlation, not a theoretical guarantee |

## 4. Design Rationale

**Why flip the problem?** The dominant paradigm has been to train models to use arbitrary tool schemas via SFT or RL. This is expensive, causes catastrophic forgetting, and ignores the fact that SLMs already have rich internal representations of naming conventions. The authors argue schema misalignment is the *root cause* of SLM tool-use failures — not lack of reasoning capability. Evidence: 80% of certain error types are schema misalignment errors.

**Why peakedness?** Borrowed from contamination detection (Dong et al., 2024), peakedness measures output distribution concentration. Patterns frequently seen during pretraining produce similar outputs across multiple samples (high peakedness). This signal is model-agnostic (requires only sampling, not token probabilities), making it applicable to black-box models.

**Why not just use the most frequent candidate?** Frequency captures surface popularity; peakedness captures *distributional concentration*. A name generated 5 times with high variance among those outputs may be less memorized than a name generated 3 times with tight clustering. PA-Tool selects `diet_insights` (peakedness=4) over `diet_tracker` (frequency=5) because the former has a tighter cluster.

**Why edit distance over embedding similarity?** Character-level edit distance avoids tokenizer dependencies and embedding model biases. It is computationally trivial and transparent. The cost is limited to Latin-script languages.

## 5. Limitations & Failure Modes

1. **Diminishing returns for large models**: For LLMs with strong reasoning (e.g., Llama3.3-70B, GPT-4.1-mini), schema misalignment is a smaller fraction of total errors. Gains exist but are modest outside multi-tool composition tasks.
2. **Model access required**: Candidate generation requires sampling from the target model, limiting applicability to API-only closed models where temperature sampling may be restricted or expensive.
3. **English-only validation**: Character-level edit distance and the assumption of Latin-script naming conventions may not transfer to non-English or morphologically rich languages.
4. **Name-only scope**: PA-Tool operates on names, not descriptions. Extending peakedness to descriptions risks *semantic drift* where the generated description diverges from actual functionality.
5. **Peakedness = familiarity is empirical, not proven**: Validated via training epoch simulation (peakedness increases with exposure, up to +25.8% from epoch 0 to 100), but this correlation may break for models with unusual training distributions.
6. **Name collisions**: 4-6% of components produce identical PA-Tool names for different functions. Priority-based locking resolves this but may force suboptimal name assignments for lower-priority components.
7. **Static schema mapping**: Generated once and frozen. Does not adapt as the model is further fine-tuned or as new tools are added (requires regeneration).

## 6. Transfer to Lyra

### The ONE idea: Schema-to-Model Alignment

**Core transferable concept**: Instead of retraining Lyra's agent models to use a fixed tool interface, generate model-specific tool schema mappings that align each agent's tool names with its pretrained naming conventions. This is a **one-time preprocessing step** — for each agent model in Lyra's multi-agent architecture, run PA-Tool on the tool catalog to produce a model-specific name mapping, then route tool calls through the mapping at inference time.

**Concrete Lyra application**: Lyra's coordinator agent passes tools to sub-agents. Currently, all sub-agents see the same tool names. With PA-Tool, each sub-agent receives tool names aligned to *its specific* pretrained vocabulary. A Qwen-based agent might see `fetch_web_page` while a Llama-based agent sees `get_url_content` for the same underlying function. The mapping layer translates back to canonical tool names before execution.

### Workstream routing: §4.2 (Memory & Tool Orchestration)

This feeds directly into the tool-calling pipeline within Lyra's agent orchestration layer. It is complementary to:
- §4.6 (Reliability): 80% schema misalignment error reduction directly improves reliability
- §4.3 (Context): Aligned schemas reduce context confusion
- §4.7 (Plugins): Any plugin exposing tools can benefit from per-model schema adaptation
