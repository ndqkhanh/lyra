## 1. Mechanism (step-by-step)

The paper introduces two interconnected contributions: (a) the **MuDABench benchmark** for multi-document analytical QA, and (b) a **Metadata-Aware Multi-Agent Workflow** that decomposes the problem into modular stages.

### MuDABench Construction (Distant Supervision Pipeline)

1. **Document Collection**: 589 financial documents (annual reports, ESG reports, corporate announcements) sourced from cninfo.com.cn (China) and sec.gov (US), spanning 80,000+ pages. Documents are in Chinese and English, containing a mix of structured tables, text, and scanned images.

2. **Metadata Annotation**: Each document receives three metadata fields — ticker symbol, fiscal year, and document type — creating a semi-structured database. Metadata enables filtering without content access.

3. **Question Generation**: Financial domain experts design natural language question templates (trend analysis, peer comparison, filtering, statistical summarization). Templates are instantiated from structured financial databases (CSMAR, Wind) via **distant supervision**. Each question Q_j is paired with a document set D_j (15 documents avg, range 5-38), metadata M_j, and ground-truth intermediate facts S_j.

4. **Intermediate Fact Annotation**: Experts transcribe structured indicators into natural-language fact descriptions S_j that serve as fine-grained ground truth for process evaluation. Example: "Company A's revenue in 2022 was xx, and in 2023 it was xx, an increase of xx."

5. **Verification Pass**: DeepSeek R1 generates single-document queries for each fact; answers are compared against S_j; contradictions trigger manual re-labeling.

**Formal definition**: X = {(Q_j, D_j, M_j, S_j) | j = 1, 2, ..., n} where n = 332.

### Multi-Agent Analytical QA Workflow (Algorithm 1)

The workflow has 5 phases:

**Phase 1 — Planning Agent (Scalable)**: Takes the global query Q and metadata schema M_schema as input. Generates sub-query templates T = {T_1, ..., T_m} with optional metadata restrictions (e.g., restriction: {year: [2021, 2022]}). Templates are metadata-parameterized (e.g., "In {doctype}, what is the operating profit for ticker {symbol} in {year}?"). Uses DeepSeek-R1-0528.

**Phase 2 — Metadata-Guided Extraction**: For each document D_i and each template T_j, check if the document's metadata satisfies any restriction on T_j (SATISFYRESTRICTION). If yes, fill the template with M_i to produce instantiated query q_{i,j}. Run single-document RAG (OpenAI File Search + GPT-4o/gpt-4.1-mini) to get answer a_{i,j}. Collect all (M_i, q_{i,j}, a_{i,j}) tuples into Qpairs.

**Phase 3 — Schema Definition and Batch Normalization (Norm Agent)**:
- Sample from Qpairs to define a flat JSON schema S_json (single-level, no nesting)
- Partition Qpairs into batches of size B to avoid context overflow
- For each batch B_k, Norm Agent (DeepSeek-Chat-V3-0324) converts unstructured extraction transcripts to JSON records under S_json
- Schema is defined once from a sample; subsequent batches use a continuation prompt to append

**Phase 4 — Programmatic Analysis (Code Agent)**:
- Save full JSON records J to an external file
- Provide Code Agent (DeepSeek-R1-0528) with: task Q, few-shot examples J_demo, schema S_json, file path p_J
- Code Agent synthesizes executable Python code C_code to analyze the full structured dataset
- Execute C_code on the saved JSON to produce Rexec

**Phase 5 — Final Synthesis**: Final Agent receives Q, Rexec, and J_demo to produce the natural language answer A.

### Evaluation Protocol (3 Metrics)

1. **Final-answer accuracy**: LLM-as-judge (Kimi K2) checks semantic equivalence between model answer Â_i and gold answer A_i.
2. **Process accuracy**: Two variants:
   - Standard RAG: Double-check judge estimates fact coverage C̃_i = min(C_i, 1 - E_i) where C_i = |semantic matches| / |S_i| and E_i = |errors/missing| / |S_i|
   - Document-grounded workflow: Cell-wise evaluation on aligned rows, C_i^cell = |correctly extracted cells| / |required cells| (81.93% human-judge agreement)
3. **Full accuracy (strict)**: Sample correct only if process = 100% AND final answer correct.

## 3. Trade-offs (wins vs loses)

| Win | Cost/Loss |
|---|---|
| Multi-agent workflow achieves **2.2x improvement** in final-answer accuracy over best standard RAG (0.2243 vs 0.1084 on simple) | Workflow is computationally expensive: requires one LLM call per (document × template) pair, plus planning, normalization, and code generation calls |
| Metadata-guided decomposition enables processing of document collections **far exceeding any single context window** (80k+ pages) | Metadata quality becomes critical; incorrect or incomplete metadata (missing fields, ambiguous types) propagates errors through all downstream stages |
| Modular architecture isolates failures: planning/normalization/code each nearly perfect (90%+), making extraction the **single identifiable bottleneck** | Modularity introduces **cascading error** — a planning error (wrong decomposition) makes all downstream extraction useless even if extraction is perfect |
| Process metric provides diagnostic signal beyond final-answer accuracy, enabling targeted debugging | Process-coverage metric is noisy: equivalent facts can be expressed in non-atomic forms, and cell-wise judge only achieves 81.93% agreement with humans |
| Batch normalization with unified schema handles arbitrary numbers of documents without context overflow | Schema rigidity can break: inconsistent field names or missing keys cause code agent runtime exceptions (Figure 8 failure case) |
| Distant supervision enables scalable benchmark construction from structured databases | Domain-locked to finance; transfer to other domains requires equivalent semi-structured metadata + structured ground truth databases |
| Noise-injection experiments confirm robustness: only modest drop from 0.1619 to 0.1238 on complex tasks with 50% irrelevant documents | Noise still hurts; the workflow lacks explicit relevance filtering before extraction |

## 4. Design Rationale

**Why distant supervision**: Manually annotating per-document facts for 589 documents across 332 questions would be prohibitive. Distant supervision leverages pre-existing structured databases (CSMAR, Wind) to auto-generate ground truth, with human experts only writing templates and curating natural-language conversions. This mirrors the DCFEE approach (Yang et al., 2018a).

**Why metadata-aware planning instead of retrieval-then-read**: Retrieval-first approaches (standard RAG) fail because the retrieval pool is so large that relevant chunks are buried in noise. Even increasing chunk count 2.5x does not reliably improve final answers — proving the bottleneck is synthesis, not recall. Metadata provides a **free hierarchical index** that narrows the extraction scope before any content is read.

**Why batch normalization with external file I/O**: Feeding all extracted facts into a single LLM call for reasoning would exceed context windows (documents average 72k-499k tokens, collections exceed millions). By normalizing to flat JSON saved to disk, the Code Agent only needs schema + examples to write analysis code, decoupling data volume from context limits.

**Why code generation over LLM aggregation**: Programming languages are deterministic and verifiable for numerical computation (averages, variances, rankings, outlier detection). An LLM performing these operations over hundreds of records would hallucinate or miscount. Code execution guarantees arithmetic correctness if the input data is clean.

**Why domain-specific financial focus**: Financial reports provide naturally semi-structured data (tables with standardized metrics, metadata like ticker/year/doctype) that enables systematic evaluation. Generic Wikipedia-style benchmarks lack the metadata structure and per-document fact ground truth needed for process-level diagnostics.

## 5. Limitations & Failure Modes

**Author-acknowledged limitations:**
1. **Domain restriction**: Limited to financial documents due to scarcity of dense semi-structured data elsewhere with equivalent metadata richness.
2. **Dataset size**: 332 questions across 589 documents — testing is costly (LLM API calls) and does not yield new discoveries beyond current scale.
3. **Fact granularity ambiguity**: Financial atomic facts have issues with granularity and equivalence (e.g., "revenue increased 6%" may require two separate absolute values), complicating process evaluation.

**Observed failure modes:**
4. **Planning errors from domain knowledge gaps**: Plan Agent lacks financial domain knowledge (e.g., assumes companies hold at most one extraordinary general meeting per year; tries to find explicit "change" descriptions instead of comparing year-pair extractions). These errors are pre-extraction and poison all downstream stages.
5. **Coupled extraction-normalization failures**: Models conflate multi-year data within single documents (current + prior year values in same table). Normalization then merges heterogeneous temporal scopes, producing incorrect analysis.
6. **Schema deviation at scale**: Extracted JSON records introduce inconsistent field names or missing keys not matching the predefined schema, causing Code Agent runtime exceptions.
7. **Process accuracy ceiling**: Even at best chunk budgets, process accuracy plateaus at ~59.7% (simple) / ~57.5% (complex), suggesting fundamental limits of current single-document extraction quality.
8. **No explicit relevance gating**: The workflow processes ALL documents matching metadata constraints; it cannot skip documents that are irrelevant despite matching metadata filters.
9. **Temperature-0 lock-in**: All experiments at temperature=0 for reproducibility; real-world performance may differ with stochastic decoding.

## 6. Transfer to Lyra

### The One Transferable Idea
**Metadata-aware staged decomposition with batch normalization + code-based aggregation**: When a Lyra agent faces a task that requires extracting and aggregating information from many structured documents (or tool outputs, API responses, log files), decompose into (1) metadata-guided sub-query planning, (2) parallel single-source extraction, (3) batched schema-normalized JSON conversion with external file I/O, and (4) code-generation for deterministic numerical/statistical aggregation. This pattern decouples data volume from context limits while providing process-level diagnostics.

### Workstream Route: **§4.2 (Memory & Knowledge Retrieval)**
The core challenge MuDABench addresses is scaling retrieval + reasoning to document collections where the relevant content far exceeds context windows. This maps directly to Lyra's knowledge retrieval subsystem. The metadata-as-hierarchical-index pattern and staged batch normalization are reusable architectural patterns for Lyra's memory layer when operating over large, semi-structured knowledge bases (e.g., documentation corpora, research paper collections, code repositories with metadata).

### Impact / Effort / Tier
- **Impact**: 3/5 — Substantially improves multi-document analytical capability but requires metadata-rich domains; not universally applicable.
- **Effort**: 4/5 — Requires implementing planning agent, norm agent, schema management, code sandbox, and batch processing infrastructure.
- **Tier**: **Investigate** — Powerful pattern but domain-dependent; worth prototyping for Lyra's document-heavy use cases (research paper analysis, codebase-wide queries) before committing to full implementation. The extraction bottleneck (30% accuracy) suggests this pattern is more valuable as architectural scaffolding than as a complete solution — Lyra would need to solve the single-document extraction problem independently.
