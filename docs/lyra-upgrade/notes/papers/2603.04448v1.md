## 1. Mechanism

SkillNet is a full-lifecycle infrastructure for creating, evaluating, and organizing AI agent skills — where a "skill" is a folder containing a central `SKILL.md` metadata file, optional scripts/templates/docs, and step-by-step instructions. The architecture has three core modules:

### 1.1 Skill Creation Pipeline

Ingests from four heterogeneous sources: (a) execution trajectories and conversational logs, (b) open-source GitHub repositories, (c) semi-structured documents (PDF, PPTX, DOCX), (d) natural language prompts. The process is fully LLM-driven with configurable backend models.

**Multi-stage filtering pipeline:**
1. **Deduplication:** Joint comparison of directory structures + MD5 hashes of `SKILL.md` files across candidates
2. **Filtering:** Rule-based validation (structural completeness) followed by LLM-based quality checking to remove low-quality, incomplete, or meaningless skills
3. **Categorization:** Assignment to one of ten functional categories (Development, AIGC, Research, Science, Business, Testing, Productivity, Security, Lifestyle, Other) plus fine-grained semantic tags
4. **Evaluation:** Multi-dimensional assessment (see §1.3) determining admission to the curated repository
5. **Consolidation:** Inter-skill associations established via ontology relations (see §1.2)

Scale: 250K+ candidates aggregated, 150K+ high-quality skills curated after filtering.

### 1.2 Skill Ontology (Three-Layer Graph)

**Layer 1 — Skill Taxonomy:** Multi-level hierarchical classification via `category` → `tag` relations. Domains (e.g., "Development") refined into sub-tags (e.g., "frontend", "llm", "api").

**Layer 2 — Skill Relation Graph:** Each tag instantiated into specific Skill Entities (e.g., "Matplotlib", "Playwright") connected by four typed directed relations:

| Relation | Semantics |
|----------|-----------|
| `similar_to` | Functionally equivalent or highly similar tasks (redundancy detection, replacement) |
| `belong_to` | Sub-component within a larger composite workflow (hierarchical decomposition) |
| `compose_with` | Frequently co-invoked; upstream produces outputs consumed by downstream (sequential pipeline) |
| `depend_on` | Prerequisite — cannot execute without prior setup (env config, API init) |

Users can extend the schema with custom relations. The ontology is dynamic: new tags are continuously added; LLMs infer relations from tags to instantiate the graph.

**Layer 3 — Skill Package Library:** Physical organization via `packaged_in` relation for modular release/deployment.

### 1.3 Five-Dimensional Evaluation

Each skill is scored on five dimensions (binned as **Good/Average/Poor**) using GPT-5o-mini with fine-grained rubrics:

| Dimension | What It Measures |
|-----------|-----------------|
| **Safety** | Hazardous operations (unauthorized file deletion), prompt injection robustness, adversarial manipulation resistance |
| **Completeness** | Whether all critical procedural steps, prerequisites, dependencies, and execution constraints are encapsulated |
| **Executability** | Sandbox-validated execution success; detects hallucinated tool calls, ambiguous instructions |
| **Maintainability** | Modularity and composability; ensures local updates don't disrupt global dependencies or backward compatibility |
| **Cost-awareness** | Execution overhead: time latency, compute resource consumption, API usage costs |

Evaluator validation: 200 randomly sampled skills, independently blind-reviewed by 3 PhD-level CS annotators. MAE < 0.03 across all dimensions; Quadratic Weighted Kappa (QWK) at "near-perfect levels (1.000)."

### 1.4 Skill Analysis (Automated Graph Construction)

Hybrid pipeline combining semantic embedding similarity and LLM-based relational inference:
1. Candidate relations generated via similarity matching, dependency extraction, and execution trace alignment
2. LLM reasoning applied for inference and validation
3. Output: directed, typed multi-relational graph (nodes = skills, edges = structural dependencies / functional associations)

### 1.5 Agent Runtime Integration

Three-phase operational lifecycle for agent use:
- **Phase 1 — Discovery:** Agent loads minimal metadata (name + description) to identify relevant skills
- **Phase 2 — Activation:** On task match, agent reads full `SKILL.md` and prepares resources
- **Phase 3 — Execution:** Agent follows instructions, optionally executing bundled code or using referenced assets

OpenClaw integration demonstrates three behavioral patterns: pre-task semantic search, mid-workflow quality audit (`analyze`/`evaluate` commands), and post-task experience consolidation (`skillnet create`).

### 1.6 Toolkit

Python SDK + CLI (`skillnet-ai`): keyword/semantic search, download, create, evaluate, and analyze skills. REST API at `api-skillnet.openkg.cn/v1/search`.

## 2. Results

### 2.1 Benchmark Setup
- **Environments:** ALFWorld (embodied household), WebShop (online shopping), ScienceWorld (scientific lab) — all POMDPs
- **Baselines:** ReAct (step-by-step reasoning-action), Expel (experience retrieval from past trajectories), Few-Shot (one static expert trajectory)
- **Backbone models:** DeepSeek V3.2, Gemini 2.5 Pro, o4 Mini
- **Skills:** Synthesized from ETO expert trajectories; zero overlap between training experiences and test splits
- **Metrics:** Average Reward (R, higher better) and Interaction Steps (S, lower better)

### 2.2 Aggregate Results
- **+40% average reward improvement** and **~30% reduction in interaction steps** vs. ReAct, across all models and environments
- Gemini 2.5 Pro with SkillNet achieves **91.43 reward on ALFWorld Seen** (vs. 60.00 ReAct) and **88.84 reward on WebShop Unseen** (vs. 58.24 ReAct)
- DeepSeek V3.2 with SkillNet achieves **81.31 reward on ScienceWorld** (vs. 64.67 ReAct) with steps dropping from 19.26 to 12.48

## 3. Trade-offs

| Win | Lose / Cost |
|-----|-------------|
| +40% avg reward across 3 benchmarks, 3 models | Requires LLM-driven creation pipeline (GPT-5o-mini); cost of pipeline itself not quantified |
| -30% interaction steps (faster task completion) | No ablation on individual evaluation dimensions; unclear which dimensions drive gains |
| Strong generalization (seen + unseen splits) | 150K skills curated but private/domain-specific knowledge still uncovered |
| Cross-model robustness (all 3 backbones improve) | Sandbox-based executability testing may not catch all real-world failures |
| Self-improving loop via post-task consolidation | Maliciously contributed "poisoned" skills only partially caught by safety evaluation |
| Full-lifecycle infrastructure (create → evaluate → connect → reuse) | No end-to-end "natural language → instantiated agent" pipeline yet; assembly still manual |
| Open ecosystem with API/SDK/CLI | Quality guarantees not comprehensive for self-constructed skills; many lack rigorous assessment |
| Typed, multi-relational ontology graph | Graph construction relies on LLM inference; no formal verification of relation correctness |

## 4. Design Rationale

The authors frame skills as the **bridge between workflows and memory** — the central insight being that agent capability is constrained by three complementary forces: (1) **Workflows** provide reliable procedural structure but are rigid, (2) **Memory** accumulates contextual experience but lacks operational boundaries, and (3) **Skills** package reusable capability units that both constrain generation AND organize memory into actionable patterns. This is positioned as the natural next step in the progression from Symbolic AI (brittle, interpretable) through Deep Learning (powerful, opaque) to Agentic AI (skills as modular, externalized knowledge units).

Rather than building yet another skill distribution platform (like ClawHub or Skills.sh), SkillNet differentiates through **full-lifecycle coverage**: automated creation from heterogeneous sources (trajectories, code, documents, prompts), multi-dimensional evaluation with human-validated rubrics, and a typed relation graph that enables agents to navigate skill dependencies and alternatives. The ontology-based graph approach was chosen over flat collections because it enables both redundancy detection (`similar_to`) and workflow composition (`compose_with`, `depend_on`), transforming a static catalog into a queryable knowledge structure.

## 5. Limitations & Failure Modes

1. **Coverage incompleteness:** Private, proprietary, and highly specialized domain capabilities are excluded. "Low-frequency or highly tacit abilities are difficult to capture" — the creation pipeline depends on existing artifacts (trajectories, repos, documents) that may not exist for niche domains.

2. **Quality guarantee gaps:** Self-constructed or community-contributed skills "cannot be fully guaranteed." Many skills still lack rigorous systematic assessment despite the 5-D evaluation framework. There is no formal verification that the evaluator catches all failure modes (only 200-skill spot-check with 3 annotators).

3. **Adversarial risk — poison pill problem:** Malicious users could contribute skills containing harmful instructions or backdoors. The Safety evaluation "can detect some of these cases, but cannot fully mitigate them." No defense-in-depth strategy (e.g., sandbox isolation, capability scoping, provenance tracking) is described.

4. **No end-to-end agent assembly:** The system lacks a pipeline that takes a natural-language task requirement and automatically selects, composes, and instantiates the appropriate skills into a fully functional agent. This remains "important future work."

5. **LLM dependency throughout:** Creation, filtering, evaluation, and graph relation inference all depend on LLM calls (GPT-5o-mini). Pipeline cost and latency are not characterized. Hallucinated relations, incorrect evaluations, or inconsistent categorization are implicit risks.

6. **Missing ablations:** No component-level ablation studies isolating individual evaluation dimensions, the contribution of the ontology graph vs. flat skill lists, or comparing graph-informed retrieval vs. semantic-only retrieval. The primary evaluation compares full SkillNet against baselines, making it impossible to attribute gains to specific subsystems.

## 6. Transfer to Lyra

### The One Idea: **5-D Skill Evaluation with Human-Validated Automated Rubrics**

Lyra should adopt a multi-dimensional automated skill/tool evaluation framework — Safety, Completeness, Executability, Maintainability, and Cost-awareness — where each dimension uses LLM-based scoring against fine-grained rubrics, calibrated against human annotator judgments (MAE target < 0.03). This directly addresses Lyra's need to assess quality and safety of community-contributed or auto-generated tools/plugins/skills before they enter the agent's action space.

### Workstream Route: **§4.8 — Safety & Guardrails** (primary) and **§4.7 — Plugins/Tool Manager** (secondary)

- Safety: The evaluator's safety dimension (prompt injection resistance, hazardous operation detection) maps to Lyra's guardrail requirements
- Plugins: The completeness + executability dimensions provide a quality gate for Lyra's tool/plugin ingestion pipeline
- The `similar_to` relation directly supports deduplication of functionally equivalent tools

### Scoring

| Metric | Score | Rationale |
|--------|-------|-----------|
| **Impact** | 4 | Automated quality gates with human-calibrated rubrics could prevent unsafe/untrustworthy skills from entering Lyra's tool ecosystem — directly addresses a known agent safety gap |
| **Effort** | 3 | Requires prompt engineering for evaluation rubrics, annotator calibration study (20-50 skills minimum), and integration into plugin ingestion pipeline. Not a full architecture change but non-trivial |
| **Tier** | **breakthrough** | The evaluation framework generalizes beyond SkillNet's specific implementation — it is a reusable evaluation methodology that can be adapted to any skill/tool/plugin ecosystem. The 5 dimensions map naturally to Lyra's existing safety and plugin management concerns |
