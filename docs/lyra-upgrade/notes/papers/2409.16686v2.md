# MSI-Agent: Incorporating Multi-Scale Insight into Embodied Agents for Superior Planning and Decision-Making

**Authors:** Dayuan Fu (BUPT), Biqing Qi (Tsinghua/Shanghai AI Lab), Yihuai Gao (Stanford), Che Jiang (Tsinghua), Guanting Dong (BUPT), Bowen Zhou (Tsinghua/Shanghai AI Lab)
**Venue:** arXiv preprint (arXiv:2409.16686v2), November 2024
**Venue Type:** Preprint (no conference acceptance noted)

## 1. Mechanism (Step-by-Step)

MSI-Agent is a long-term memory architecture that generates, stores, and retrieves **multi-scale insights** to improve LLM-based embodied agent planning. It operates in two phases:

### Phase A: Insight Summarization (offline, from training tasks)

**Step 1 — Experience Generation:**
For each training task, the executor (HELPER for TEACh, AgentBench/ReAct for Alfworld) runs the full task loop. After completion, the system stores the tuple: (task background, user query, agent plans, environmental feedback, execution results) as an "experience."

**Step 2 — Experience Selection (two modes):**
- **Success mode:** Collect only experiences where execution succeeded.
- **Pair mode:** For each successful experience `s_s`, find the most semantically similar failed experience `s_f` from the failure database `S_f` using cosine similarity over user query embeddings:

```
s_f = argmax_{s∈S_f} [emb(s)·emb(s_s)] / [||emb(s)||₂ · ||emb(s_s)||₂]
```

The pair `(s_s, s_f)` forms the seed for insight generation. Embeddings use `text-embedding-ada-002`.

**Step 3 — Multi-Scale Insight Generation:**
Insights are organized into three hierarchical scales:
- **General insights:** Applicable to ALL tasks across all environments (highest level, most abstract).
- **Environment insights:** Applicable only within a specific environment category (e.g., kitchen, living room, bedroom, bathroom).
- **Subtask insights:** Fine-grained, specific to executing a particular subtask (e.g., "Slice Tomato," "Water Plant").

The insight database starts empty. For each seed experience, the system selects all existing insights at general → environment → subtask order as candidate insights. GPT-4 is prompted with the candidate insights, the seed experience(s), and 5 atomic operations:

| Operation | Effect | Score Delta |
|-----------|--------|-------------|
| ADD | Create a new insight at the given scale | Starts at 2 |
| REMOVE | Delete an existing insight | -1 |
| EDIT | Modify an existing insight | 0 |
| AGREE | Reinforce an existing insight | +1 |
| MOVE | Relocate an insight between scales (e.g., promote subtask insight to general) | N/A |

Max 12 total operations per update (4 per scale × 3 scales). An insight is pruned when its score reaches 0. The database is frozen after processing all training tasks.

### Phase B: Insight Utilization (online, during task execution)

**Step 4 — Insight Selection:**
For a new task, candidate insights = all general insights + selected subtask insights. Two selection strategies for subtask insights:
- **Hashmap indexing (primary):** Extract all subtask names from the database → prompt GPT-3.5 with (subtask name list + user query) → LLM returns only relevant task names → retrieve insights under those names.
- **Vector indexing (baseline/ablation):** Cosine similarity between user query embedding and all subtask insight embeddings, selecting top matches up to 2000 tokens.

**Step 5 — Task Execution:**
Selected insights + task background + user query → executor LLM (GPT-3.5/GPT-4) → generates plan/action sequence → environment feedback → loop.

**Key control flow:** For OOD (out-of-domain) tasks where task distribution may not align with training, the system falls back to **general insights only** to avoid fine-grained mismatches from subtask insights.

## 2. Results (Real Benchmark Numbers)

### TEACh TfD Benchmark (Trajectory from Dialogue)

| Model | Seen (IND) SR | Seen (IND) GC | Unseen (OOD) SR | Unseen (OOD) GC |
|-------|--------------|--------------|-----------------|-----------------|
| E.T.* (fine-tuned) | 0.48 | 0.35 | 1.02 | 1.42 |
| DANLI* (fine-tuned) | 7.98 | 6.79 | 4.97 | 10.50 |
| HELPER (LLM, ChatGPT) | 8.84 | 13.94 | 10.62 | 9.29 |
| Expel (LLM, ChatGPT) | 8.28 | 11.55 | 8.99 | 8.49 |
| **MSI (LLM, ChatGPT)** | **12.70** | **13.66** | **14.54** | **10.08** |

- MSI beats HELPER by +43.7% on IND SR, +36.9% on OOD SR
- MSI beats Expel by +53.4% on IND SR, +61.7% on OOD SR
- Path Length Weighted (PLW) scores in parentheses in original table confirm same trend

### AgentBench Alfworld Benchmark

| Model | Dev IND (GPT-3.5) | Test OOD (GPT-3.5) | Dev IND (GPT-4) | Test OOD (GPT-4) |
|-------|-------------------|---------------------|-----------------|-------------------|
| Act-Only | 0 | 6 | 65 | 66 |
| ReAct | 0 | 10 | 65 | 68 |
| Expel | 5 | 14 | 75 | 70 |
| **MSI** | **5** | **16** | **85** | **72** |

- MSI delivers ~2× the improvement of Expel over ReAct on GPT-4 dev (10 points vs Expel's 10 points over ReAct)
- MSI with GPT-4 hits 85% on dev (IND), a +10pt gain over Expel

### Experience Selection Strategy Ablation (TEACh SR)

| Strategy | Expel IND/OOD | MSI IND/OOD |
|----------|--------------|-------------|
| Pair mode (success+failure) | 8.28 / 8.99 | **12.70 / 14.54** |
| Success mode (success only) | 9.94 / 11.60 | 10.65 / 13.39 |

Key finding: Pair mode is superior for MSI (multi-scale can filter irrelevant fine-grained insights), but success mode is better for Expel (no filtering, so pair mode injects too much noise).

### Insight Selection Strategy (TEACh SR)

| Selection Method | IND SR | OOD SR |
|-----------------|--------|--------|
| Hashmap (LLM-based) | **12.70** | **14.54** |
| Vector similarity | 10.05 | 11.43 |

Hashmap outperforms vector by >20% because vector similarity retrieves semantically adjacent but functionally irrelevant insights (e.g., "bowl" triggers beverage-preparation insights for a plant-watering task).

### Multi-Scale vs General-Only (TEACh SR)

| Scale Used | IND SR | OOD SR |
|-----------|--------|--------|
| Multi-scale (pair mode) | **12.70** | 14.54 |
| General only (pair mode) | 12.15 | **14.86** |

General-only beats multi-scale on OOD because task-specific insights summarized in-domain do not align with OOD tasks (fine-grained mismatch).

### Domain Adaptation Robustness (TEACh Unseen SR)

After sequential insight summarization across kitchen → living room → bedroom:
- **MSI:** SR degrades by only ~2.04 percentage points from original domain performance
- **Expel:** SR degrades by ~8.38 percentage points (catastrophic forgetting)

### Insight Specificity Distribution (Alfworld, 0=general, 10=task-specific)

| Source | Score 0-1 | Score 2-4 | Score 5-7 | Score 8-10 |
|--------|-----------|-----------|-----------|------------|
| Expel | 15.5% | 52.4% | 23.8% | 7.1% |
| MSI General | 36.4% | 46.5% | 13.9% | 3.1% |
| MSI Task | 0% | 14.7% | 51.4% | 33.9% |

MSI successfully separates general (clusters at 0-1) from task-specific (clusters at 6-9) insights, unlike Expel's uniform distribution.

## 3. Trade-offs

| Win | Lose |
|-----|------|
| +40-60% SR improvement over HELPER/Expel on TEACh | Requires GPT-4 for insight generation (cost ~15-30× GPT-3.5) |
| +2× improvement over Expel on Alfworld GPT-4 | Environment-scale insights only work in embodied settings with defined categories |
| Robust to domain shifting (only 2% SR drop vs 8% for Expel) | Multi-scale insights hurt OOD performance without distribution alignment check |
| Clean separation of general vs task-specific insights (confirmed by human eval) | Pair mode requires both success AND failure trajectories (not always available) |
| Hashmap selection eliminates vector-similarity false positives | Hashmap selection adds an extra LLM call per task (latency + cost) |
| Scoring mechanism auto-prunes low-quality insights | Only tested with GPT-3.5/GPT-4; open-source model performance unknown |
| Works across both single-turn (TEACh) and multi-turn (Alfworld) planning | Limited to 12 insight operations per update (may miss comprehensive revisions) |

## 4. Design Rationale

The core insight is that **not all memory is equal in scope**. Previous approaches (Expel) generated insights at a single level, creating a tension: too many fine-grained insights overwhelms the LLM with irrelevant noise; too few high-level insights fails to provide task-specific guidance. MSI resolves this by decomposing insights into a **generality hierarchy** (general → environment → subtask) and using an explicit LLM-based selector to choose the appropriate level for each query.

The pair-mode design (contrasting success vs failure) is motivated by the observation that knowing what NOT to do is often as valuable as knowing what to do — a finding consistent with Reflexion and contrastive learning literature. The hashmap (LLM-based) selection over vector similarity is chosen because word-level semantic similarity (e.g., "bowl") creates false-positive retrievals that would not survive a semantic understanding check by an LLM.

The OOD fallback to general-only insights follows from the empirical finding that fine-grained subtask insights cause "fine-grained mismatches" when the target distribution shifts — a form of overfitting in the memory space.

## 5. Limitations and Failure Modes

1. **Environment scale is not generalizable:** Only applicable to embodied scenarios with pre-defined environment categories (kitchen, living room, etc.). Not trivially portable to non-embodied domains like code generation or dialogue.
2. **Single memory type:** Only explores "insight" as a long-term memory modality. No integration with example-based retrieval, procedural memory, or episodic memory — all of which could complement insights.
3. **OOD fragility with multi-scale:** When task distribution shifts, subtask insights become actively harmful. The paper's solution (fall back to general-only) requires knowing whether a task is OOD — a meta-decision problem.
4. **GPT-4 dependency for insight generation:** Insight generation uses GPT-4 while execution uses GPT-3.5, creating a cost asymmetry. No experiments with open-weight models (Llama, Qwen, etc.).
5. **Narrow benchmark coverage:** Only TEACh (household robotics) and Alfworld (text-based household). No testing on web navigation, code generation, tool use, or other agent domains.
6. **Domain adaptation tested on only 3 environments:** Kitchen → living room → bedroom in sequence. Real-world deployment would involve far more diverse and unpredictable shifts.
7. **Pair mode data requirement:** Requires both success and failure trajectories. In deployment scenarios where failures are rare or not recorded, only success mode is available — and MSI's advantage over Expel narrows significantly in success mode.
8. **Fixed max operations (12 per update):** May miss comprehensive revisions when many insights need updating simultaneously.
9. **No latency analysis:** No measurement of end-to-end latency impact from hashmap LLM calls or insight database scaling.

## 6. Transfer to Lyra

**The one transferable idea:** Multi-scale insight architecture with LLM-based semantic selection.

Lyra's current memory system stores all agent experiences/learnings at a single level, causing the same "irrelevant memory injection" problem MSI addresses for embodied agents. The core transfer is:

1. Decompose Lyra's memory into **three scales** mapped to agent operation:
   - **General scale** → Cross-task patterns (error recovery strategies, planning heuristics)
   - **Workspace scale** → Environment-specific knowledge (a particular codebase's conventions, tool behaviors)
   - **Task scale** → Fine-grained procedural knowledge (how to fix a specific bug type, how to configure a specific service)

2. Use an **LLM-based hashmap selector** (query → relevant task names → retrieve insights under those names) instead of pure embedding similarity, which the paper shows introduces >20% false positives.

3. Implement the **scoring/pruning mechanism** (start=2, agree+1, remove-1, discard at 0) to maintain insight quality over time as Lyra accumulates more experiences.

4. Add an **OOD detection gate**: when Lyra encounters a task domain it has not seen before, fall back to general-only insights to avoid "fine-grained mismatch."

**Workstream route:** §4.2 (Memory Architecture) — this directly upgrades the long-term memory subsystem with multi-scale decomposition and intelligent selection.
