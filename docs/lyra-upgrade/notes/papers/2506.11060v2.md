## 1. Mechanism (Step-by-Step)

### Core Insight
Large systems codebases (Linux kernel: 75K files, 28M LOC) require **global context gathering** across three dimensions — semantics (control/data flow), patterns/anti-patterns, and commit history — before any fix can be synthesized. Existing agents (SWE-agent, Agentless) explore too few files (~1.33/trajectory) and lack causal commit analysis. Code Researcher introduces a three-phase deep research architecture that mirrors how expert developers investigate crashes: explore broadly, filter context, then synthesize.

### Phase 1: ANALYSIS — Multi-Strategy Deep Exploration

**Step 1.1: Initialize from Crash Report**
Input is a kernel crash report (stack trace + diagnostic info) with NO natural-language issue description. The agent receives a raw stack trace showing which functions were on the call stack when the crash occurred. For 74.5% of crashes, the ground-truth buggy files appear in the stack trace, but the agent does not know which files are relevant.

**Step 1.2: Structured Action Space (5 operations)**
The agent selects from five actions at each step:
- `search_definition(sym, [file])` — Uses `ctags` index to find symbol definitions. Index built once at startup (~74 seconds for Linux kernel, vs. >30 minutes for dependency-graph approaches like LocAgent/RepoGraph).
- `search_code("regex")` — Uses `git grep -E` to search all tracked files for regex patterns, returns up to 5 matches with 2 lines of context.
- `search_commits("regex")` — Searches `git log -E -G` (diffs) and `git log -E --grep` (messages), returns commits with messages and patches truncated to 100 lines, capped at 5 results. Uses progressive search: first files in memory, then files in crash trace, then kernel subsystem files, then all files. 60-second timeout per query.
- `close_definition(file, sym, line)` — Prunes irrelevant definitions from memory.
- `done` — Signals sufficient context gathered.

**Step 1.3: Three Reasoning Strategies (Prompt-Induced)**
The agent is prompted with three strategies, each producing actions:

| Strategy | Prompt Pattern | Typical Actions |
|----------|---------------|-----------------|
| **Control/Data Flow Chasing** | "How does execution flow between functions? How do variable values propagate?" | `search_definition()` to follow call chains; `search_code("x\s*=")` for assignments |
| **Pattern/Anti-Pattern Search** | "What is the normal pattern? Does this code deviate?" (Bugs as Deviant Behavior — Engler et al. 2001) | `search_code("if\s*\(ptr==NULL\)")` to check null-check conventions; `search_code("ptr\s*=.*alloc\(.*\)")` for allocation patterns |
| **Causal Commit Analysis** | "How did the codebase evolve? Which past changes relate to this crash?" | `search_commits("handle->size\|crypto_fun\(")` for commits touching suspect code |

**Step 1.4: Iterative Deep Research Loop**
At each step:
1. LLM (GPT-4o, temp=0.6) receives prompt with: crash report, context memory (open symbol definitions, previous search results), conversation history
2. LLM writes thoughts in scratchpad, evaluates whether context is sufficient
3. LLM selects one or more actions (parallel searches allowed)
4. Action results are appended to context memory
5. If `done`, proceed to Phase 2; otherwise repeat
6. Max 15 LLM calls per trajectory; context window capped at 50K tokens

**Step 1.5: Context Memory Structure (`GlobalCtxAgentState`)**
```python
{
  "open_definitions": {
    "file_path": [{"symbol_name": str, "start_line": int, "end_line": int, "body": str}]
  },
  "search_results": [
    {"query": str, "results": [str]}
  ]
}
```
Only definitions remain persistent across steps; `search_code` and `search_commits` results from prior steps are shown only from the immediately preceding step (to reduce noise). Lines mentioned in the crash report are annotated with `// IMPORTANT` comments in definition bodies.

### Phase 2: SYNTHESIS — Filter Then Generate

**Step 2.1: Memory Filtering**
The analysis phase often accumulates large volumes of irrelevant context (especially in 28M-LOC codebases). The filtering step takes the full memory (avg. 21,557 tokens before filtering) and selects only relevant `(action, result)` pairs, reducing to avg. 7,797 tokens. Filtering prioritizes fitting symbol definitions before attempting to include search/commit results.

**Step 2.2: Patch Generation**
The LLM receives: crash report, filtered memory, and the complete reasoning trace from Phase 1. It generates a hypothesis about the root cause and the corresponding patch (may span multiple files). Attempts use increasing temperatures (0, 0.3, 0.6) until a correctly-formatted patch is produced (max 3 attempts). Optionally, a reasoning model (o1) can be used for this phase while GPT-4o handles the analysis phase.

### Phase 3: VALIDATION — Compile and Test

1. Apply patch to codebase
2. Compile the kernel (or multimedia framework)
3. Run the crash reproducer program (the Syzkaller-generated user-space program that originally triggered the crash)
4. If crash reproduced → reject patch; if not → accept
5. Additionally run KUnit Linux kernel unit tests on accepted patches to verify no regressions

### Key Algorithmic Contribution: Causal Commit Analysis

This is the first coding agent to explicitly search commit history. The algorithm:
1. Identifies suspect code patterns from stack trace + definitions
2. Constructs regex from function names, variable names, and code patterns
3. Searches both commit diffs (`git log -G`) and messages (`git log --grep`)
4. Uses retrieved commits to understand: (a) when the buggy behavior was introduced, (b) how similar bugs were fixed in the past, (c) which invariants were established by prior patches
5. For an example case (Appendix H), the agent navigated to the exact commit that originally introduced the bug being repaired

| GPT-4o (stack context) | 1 | P@5 | 29.50 |
| o1 (stack context) | 1 | P@5 | 40.00 |
| Agentless (GPT-4o) | 4 | P@5 | 31.00 |
| SWE-agent (GPT-4o) | 15 | P@5 | 31.50 |

## 4. Design Rationale

### Why Deep Research for Code?
Systems code bugs are subtle — they involve violations of global invariants (lock ordering, memory management conventions, data structure access patterns) and unintended side effects from past changes. A simple localization-then-repair workflow (Agentless) cannot gather the cross-file context needed to understand these global interactions. SWE-agent explores too few files because its ReAct loop is designed for smaller Python repos where issue descriptions guide navigation.

### Why Three Phases (not one ReAct loop)?
The separation of **Analysis → Synthesis → Validation** mirrors how expert developers work: (1) investigate broadly, (2) filter and synthesize, (3) test. A single ReAct loop conflates exploration with editing, leading to premature commits to specific files. The filtering step is critical because large codebases produce enormous amounts of irrelevant search results — without filtering, the prompt gets overwhelmed (21.5K tokens → 7.8K tokens, 64% reduction).

### Why Commit History?
Legacy codebases have decades of commits. Bugs are often introduced by past changes. Searching commit history helps the agent: (a) find when a buggy pattern was introduced, (b) learn from how similar bugs were fixed, (c) understand the invariants a prior patch established. The ablation result (10% CRR drop) validates this choice.

### Why Simple Tools (ctags, git grep, git log) instead of Dependency Graphs?
Dependency graph construction (LocAgent, RepoGraph, Lingma Agent) scales poorly: RepoGraph took an estimated 30+ minutes for a 433K LOC Python repo; would be infeasible for 28M LOC of the Linux kernel. ctags indexing takes 74 seconds for the entire kernel. The regex-based search (`git grep`) is language-agnostic and pattern-flexible. This is a deliberate simplicity-over-sophistication choice that enables scaling to the largest codebases.

### Why Multiple Trajectories Instead of Longer Trajectories?
Increasing max calls per trajectory had negligible effect on CRR, while increasing the number of trajectories (P@5 → P@10) improved CRR from 48% to 54%. This suggests that for complex bugs, **breadth of exploration** (trying different reasoning paths) matters more than **depth per path**. A single trajectory can get stuck on a wrong hypothesis.

## 5. Limitations and Failure Modes

1. **Crash-only scope.** The agent is designed exclusively for crash reports with stack traces. Performance bugs (slow response times), resource leaks without crashes, and flakiness are different problem types that may not benefit from this approach.

2. **52% failure rate on kBenchSyz with GPT-4o.** Even at P@5, Code Researcher fails to resolve 52% of crashes. Many of these are subtle bugs requiring deep kernel expertise that the agent cannot replicate. No detailed failure analysis is provided for unresolved cases.

3. **Overspecialized/incomplete patches.** Qualitative analysis identifies patch categories: some patches prevent the crash but are overspecialized (work only for the specific reproducer, not the general case); others correctly identify the problem area but produce incomplete fixes.

4. **No multi-patch coordination.** The agent generates each patch independently. Real kernel development often requires coordinated changes across multiple subsystems. The paper does not evaluate multi-patch scenarios or patch series.

5. **Validation limited to crash reproduction.** While KUnit tests provide additional confidence, they cover only a small fraction of kernel functionality. Full regression testing (LTP, xfstests, etc.) is not performed. Patches could introduce subtle behavioral changes not caught by KUnit or the crash reproducer.

6. **Compute cost.** Each trajectory requires compiling the Linux kernel and running the Syzkaller reproducer for up to 10 minutes on 4 machines with 8 parallel processes. This is expensive and time-consuming.

7. **Context window constraint.** The 50K token limit forces truncation of intermediate messages and search results. For very complex bugs involving many files, this limit could exclude critical context.

8. **Prompt engineering dependency.** The three reasoning strategies are prompt-induced, not algorithmic. Performance depends heavily on prompt quality, few-shot examples, and codebase-specific preambles. Transfer to a new codebase requires writing new examples.

9. **No learning from trajectory failures.** The agent does not learn from failed trajectories — each crash is approached independently. A memory of common kernel bug patterns across crashes could improve efficiency.

10. **Limited language support.** The tooling (ctags for C, git grep) is optimized for C codebases. Extension to Rust (Linux kernel's newer language), C++, or assembly requires tool adaptation.

## 6. Transfer to Lyra

### One Transferable Idea: **Structured Context Memory with Multi-Strategy Deep Research for Agent Tool-Use Trajectories**

The core transferable insight is the **three-phase deep research architecture** (Analysis → Synthesis → Validation) with a **structured context memory** that separates persistent symbol definitions from ephemeral search results. For Lyra, this maps directly to how the agent should investigate complex multi-file reasoning tasks:

- **Lyra's equivalent of "crash report"** = user query + initial tool invocation results + conversation context
- **Lyra's equivalent of "codebase"** = the agent's tool ecosystem (Python REPL, file system, APIs, databases, shell)
- **Lyra's equivalent of "commit history"** = conversation history, past sessions, cached results, project memory
- **Lyra's equivalent of "reasoning strategies"** = structured prompts that induce (a) dependency tracing through tool call chains, (b) pattern/anti-pattern detection across prior interactions, (c) causal analysis over past session history

The **structured memory architecture** is especially valuable: Lyra currently relies on flat context windows. A tiered memory with persistent "definitions" (tool signatures, API schemas, environment configs) and ephemeral "search results" (tool outputs from current investigation) would dramatically improve context utilization for multi-step tool-use tasks.

The **filtering step** (64% token reduction, 21.5K → 7.8K) could be applied to Lyra's context compaction: before generating final output for complex multi-tool tasks, filter out intermediate tool results that proved irrelevant, keeping only the context chain that led to the solution.

### Workstream Route: §4.2 — Context & Memory Architecture

This paper feeds directly into Lyra's context management workstream. The three-phase architecture and structured memory model are directly applicable to how Lyra manages multi-step reasoning with tools. The specific techniques map to:

| Paper Technique | Lyra Application |
|----------------|------------------|
| Structured context memory (GlobalCtxAgentState) | Tiered memory: persistent definitions vs. ephemeral search results |
| Multi-strategy reasoning prompts | Template prompts for dependency tracing, pattern detection, causal analysis |
| Memory filtering before synthesis | Context compaction: prune irrelevant tool results before final answer generation |
| Breadth-over-depth exploration (multiple trajectories) | Parallel tool invocation strategies; ensemble reasoning paths |
| ctags-style indexing of "symbols" | Pre-index Lyra's tool ecosystem, API schemas, project structure |

| Dimension | Score | Rationale |
