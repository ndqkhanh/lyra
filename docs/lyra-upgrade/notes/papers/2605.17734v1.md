**Venue:** arXiv Preprint (2605.17734v1), May 18, 2026
**Backend:** Qwen2.5-7B-Instruct; optional GPT-4o teacher

## 1. Mechanism

HASP reframes agent skills as **Program Functions (PFs)** — executable state–action intervention modules that replace passive textual "advice" with deterministic interventions inside the agent loop.

### 1.1 Core Architecture

```
Agent Loop: s_t → π_θ proposes a_t → Harness retrieves PFs → PF activation → Intervention Γ → (ã_t, c_t, κ_t) → Executor → o_{t+1}
```

Every PF is a typed Python object with two mandatory methods:

- `should_activate(step_context, action_type, arg) → bool` — determines whether the skill fires given the current state and proposed action.
- `intervene(step_context, action_type, arg, teacher=None) → Intervention` — returns a structured `Intervention` object whose `type` is one of:
  - `MODIFY_ACTION`: rewrite or refine the next action (e.g., shorten an over-constrained search query, redirect a premature FINAL into SEARCH).
  - `INJECT_CONTEXT`: append corrective text (e.g., decomposition hints, entity-disambiguation warnings) that the policy sees in the next observation.
  - `NOOP`: abstain but still emit an audit record.

### 1.2 Inference-Time Harness

At step *t*:
1. Base policy π_θ proposes action *a_t^orig*.
2. Harness retrieves candidate PFs *R(s_t)* ⊆ *M* from the skill library *M*.
3. Each PF evaluates its `should_activate` predicate.
4. Intervention operator Γ produces (**ã**_t*, *c_t*, *κ_t*):
   - **ã**_t*: the final action after PF modification (or *a_t^orig* if no PF fires).
   - *c_t*: optional corrective context injected into subsequent reasoning.
   - *κ_t*: record of fired PFs and intervention mode.
5. Executor runs **ã**_t*, feedback observed, loop continues.

PFs have per-skill rate limits (e.g., `_MAX_MODIFY_FIRES = 2` for MODIFY_ACTION, 3 fires-per-episode caps) to prevent oscillation. PFs are deterministic by default.

An optional **auxiliary teacher** (GPT-4o) can be used to select among multiple candidate PFs when activation is ambiguous, improving dispatch precision. PFs that declare `needs_teacher = True` receive a teacher-model handle in `intervene` and degrade gracefully when `teacher is None`.

### 1.3 Post-Training: PF-Derived Supervision

Each PF execution emits a structured record:
```
e_t = (s_t, a_t^orig, ã_t, c_t, κ_t, ∆_t)
```

HASP scores each record using **four weighted signals**:

| Signal | λ weight | What it captures |
|--------|----------|------------------|
| Timing (*t_t*) | 0.15 | Whether intervention fires at appropriate states |
| Mode (*m_t*) | 0.10 | Whether the right intervention form was used |
| Correctness (*q_t*) | 0.25 | Whether the repair is syntactically/semantically valid |
| Outcome (*o_t*) | 0.50 | Whether downstream effects were positive |

Per-step score: `A_t = 0.15·t_t + 0.10·m_t + 0.25·q_t + 0.50·o_t`
Trajectory score: `A(τ) = (T-1)^(-1) · Σ_{t=1}^{T} A_t`

Three post-training recipes use these signals:

1. **Rejection Sampling (RS)** — main recipe: Score(τ_i) = β_1·TaskSuccess(τ_i) + β_2·A(τ_i). Only top-scoring trajectories retained. Stable under evolving skill libraries.

2. **Supervised Fine-Tuning (SFT)**: `L_SFT = −Σ_t w_t·log π_θ(ã_t | s_t)`, where w_t = f(A_t). Trains student on PF-corrected local actions.

3. **On-Policy Distillation (OPD)**: Rolls out current policy with PFs active, trains on corrected behavior under current-policy states. `L_OPD = −Σ_t ŵ_t·log π_θ(ã_t | s_t)`. Stronger but less stable when library evolves.

### 1.4 Self-Improving PF Evolution

After fixed training intervals:
1. Revisit remaining failures under the current checkpoint π_θ.
2. Summarize recurring failure→repair patterns into candidate PFs C_r.
3. **Executable validation** Q_exec(c): syntax, interface validity, mock execution, legal return types.
4. **Teacher review** Q_teach(c): evaluates whether candidate captures a reusable failure pattern, fires under appropriate conditions, proposes useful repair.
5. Admit only if Q_exec(c) ≥ η_exec AND Q_teach(c) ≥ η_teach.
6. Update library: M_{r+1} = Update(M_r, {c ∈ C_r : Accept(c)}).

**Without filtering**, evolution collapses from 60.3% to 36.3% on web-search reasoning. Both executable and teacher filters are individually insufficient (48.8% and 47.2% respectively).

## 3. Trade-offs

| Win | Loss / Cost |
|-----|-------------|
| Executable guardrails — PFs deterministically change actions, unlike advisory text that models ignore | Teacher dependency — strongest variants require GPT-4o for PF selection, review, and distillation |
| Modular across paradigms — same PF interface works for inference-only, post-training, and self-improvement | Limited intervention forms — only MODIFY_ACTION and INJECT_CONTEXT; no code auto-patching, no multi-step plan revision |
| +25pp gain over multi-loop ReAct with inference-only PFs (no training) | PFs don't discover new strategies — they surface and stabilize strategies the model can already execute but doesn't apply reliably |
| Structured supervision — PF-derived signals provide richer training targets than final-answer reward alone | Non-stationarity — evolving skill library destabilizes on-policy distillation (OPD drops to 56.7% with evolution vs 62.5% fixed) |
| Self-improving library — closed-loop evolution further improves weak checkpoints | Strict filtering bottleneck — without dual executable+teacher filtering, evolution causes catastrophic collapse (60.3% → 36.3%) |
| RS recipe is stable under library evolution (unlike OPD) | AIME24 stays at 16.7% even with full HASP-Evolve+RS, suggesting fundamental strategy limits |
| Cross-domain mechanical transfer — same dispatcher serves web-search, math, and code without modification | Per-PF rate limits and caps are hand-tuned; no automated calibration |

## 4. Design Rationale

**Why executable functions over textual skills?** Textual skills injected into prompts are "advisory" — the model may acknowledge them but then ignore them in action selection (the paper shows this explicitly: Prompt-Only Skills achieves 20.5% vs 51.0% for PF-only on web-search, a 2.5x gap). PFs close the intention-behavior gap by deterministically modifying actions at runtime.

**Why a unified PF interface across inference, training, and evolution?** The same `should_activate` / `intervene` interface produces structured audit records (s_t, a_t^orig, ã_t, c_t, κ_t, ∆_t) that serve simultaneously as runtime corrections, training supervision, and library-evolution candidates. This avoids building three separate subsystems.

**Why rejection sampling over RL?** PF-derived signals provide richer intermediate supervision than final-answer rewards alone. RS filters for both task success AND intervention quality, yielding more stable training under evolving skill libraries. Full RL-style exploration (as in Search-R1 or Flow-GRPO) would discover new strategies but at substantially higher compute cost and instability.

**Why dual filtering for library evolution?** Executable validation alone catches syntax/interface errors but admits semantically poor PFs. Teacher review alone catches semantic quality but misses malformed PFs. Both are necessary; removing either causes 11.5-13.1 point drops.

## 5. Limitations & Failure Modes

1. **No fundamentally new strategy discovery.** PFs help the model use existing strategies more reliably but cannot invent novel solution approaches. AIME24 (16.7% even with full HASP-Evolve+RS) shows tasks requiring genuine strategy innovation benefit more from RL-style exploration (AgentFlow Flow-GRPO: 40.0% on AIME24).

2. **Teacher dependency in strongest variants.** Teacher-augmented PF selection, teacher review for library evolution, and on-policy distillation all require an external strong model (GPT-4o), increasing cost and risking teacher-specific bias.

3. **Limited intervention vocabulary.** Only MODIFY_ACTION and INJECT_CONTEXT are supported. Code auto-patching is deliberately excluded ("judged too risky"). Multi-step plan revision, tool substitution, and rollback are unsupported.

4. **Self-improvement degradation risk.** Without strict dual filtering, evolution causes catastrophic collapse (60.3% → 36.3%). Even with filtering, PFs can become too narrow, repetitive, or teacher-biased over successive generations.

5. **Domain scope limited to benchmark-style tasks.** All evaluation uses search, math, and coding benchmarks with clear verification signals. Transfer to open-ended, long-horizon, interactive, or weakly verifiable environments is unresolved.

6. **Hand-tuned rate limits.** Per-PF fire caps (_MAX_MODIFY_FIRES = 2, 3 fires-per-episode) and phase-condition handlers are manually configured; no automatic calibration mechanism.

## 6. Transfer to Lyra

**The ONE transferable idea:** Wrap Lyra's agent loop with **executable Program Functions (PFs)** — deterministic state→action intervention modules with explicit `should_activate` + `intervene` interfaces — to convert safety rules and failure-recovery patterns from advisory text that the model ignores into runtime guardrails that deterministically modify or block unsafe actions.

**Workstream:** §4.2 — Safety Architecture & Guardrails

**Impact:** 4 — Directly addresses the Lyra safety guarantee problem (advisory rules that models can ignore). The PF pattern provides deterministic intervention without requiring full model retraining. The structured intervention audit trail also feeds Lyra's verification pipeline.

**Effort:** 5 — Requires (a) designing a PF interface and registry for Lyra's action space, (b) implementing the harness wrapper around the existing agent loop, (c) building an initial PF library from Lyra's failure/unsafe-action taxonomy, (d) integrating PF audit records into the verification pipeline, and (e) designing the evolution filtering (executable validation + safety-reviewer-as-teacher). This is a substantive architectural change to the agent execution path.

**Tier:** `breakthrough` — The gap between textual safety rules and behavioral compliance is a fundamental failure mode in LLM agents. HASP's executable PF pattern is the first principled solution that (a) works at inference time without retraining, (b) produces structured audit records, and (c) supports closed-loop improvement. For Lyra specifically, this could be the mechanism that converts safety requirements into guarantees.
