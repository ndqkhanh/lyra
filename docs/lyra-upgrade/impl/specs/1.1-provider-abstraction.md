## 1. Problem

Lyra hardcodes a single model per agent. Switching from Claude to DeepSeek or GPT requires rewriting agent code. Every provider has different message formats, tool schemas, streaming protocols, and token accounting. There is no capability map (which backends support vision? audio? JSON mode? long context?), no cost tracking, and no fallback chain.

## 2. Scope

Build a `ProviderBackend` abstract protocol that normalizes ALL provider differences behind a single interface. Every other Lyra subsystem (skills, tools, memory, swarm, voice) writes against this protocol once and works against any backend.

### Out of scope (separate items)
- Router logic (which model to pick) → Item 1.2
- Cost tracking → Item R.8
- Prompt caching strategy → Item R.9

## 3. Design

### 3.1 ProviderBackend Protocol

```python
class ProviderBackend(ABC):
    """Normalized interface for all LLM providers. Harness-level, not provider-API-level."""

    # --- Identity ---
    provider: str                    # "anthropic" | "openai" | "deepseek" | "openweights"
    model_id: str                    # e.g. "claude-sonnet-4-6", "deepseek-v4-flash"
    tier: ModelTier                  # cheap | standard | premium

    # --- Capability Map ---
    capabilities: ProviderCapabilities  # See 3.2

    # --- Core API ---
    @abstractmethod
    async def chat(
        self,
        messages: list[Message],        # Normalized message format
        tools: list[ToolDef] | None,
        effort: EffortLevel,            # low | medium | high | xhigh | max
        max_tokens: int | None,
        stop_sequences: list[str] | None,
    ) -> ChatResponse: ...

    @abstractmethod
    async def stream_chat(
        self,
        messages: list[Message],
        tools: list[ToolDef] | None,
        effort: EffortLevel,
        max_tokens: int | None,
    ) -> AsyncIterator[StreamEvent]: ...

    # --- Token Accounting ---
    @abstractmethod
    def count_tokens(self, messages: list[Message]) -> int: ...
    @abstractmethod
    def count_tool_tokens(self, tools: list[ToolDef]) -> int: ...
```

### 3.2 ProviderCapabilities

```python
@dataclass
class ProviderCapabilities:
    tool_use: bool           # Supports native tool/function calling
    json_mode: bool           # Supports structured JSON output
    vision: bool              # Supports image inputs
    audio_input: bool         # Supports audio inputs
    audio_output: bool        # Supports audio generation
    long_context: int         # Max context window in tokens
    prompt_caching: bool      # Supports prompt caching
    thinking_budget: bool     # Supports explicit thinking/reasoning budget
    streaming: bool           # Supports SSE/streaming responses
    max_output_tokens: int    # Max output tokens per response
    cost_per_1k_input: float  # USD per 1K input tokens
    cost_per_1k_output: float # USD per 1K output tokens
```

### 3.3 Normalized Message Format

```python
@dataclass
class Message:
    role: str                  # "system" | "user" | "assistant" | "tool"
    content: str | list[ContentBlock]

@dataclass
class ContentBlock:
    type: str                  # "text" | "image" | "tool_use" | "tool_result"
    text: str | None
    source: ImageSource | None # For vision
    tool_use_id: str | None
    tool_name: str | None
    tool_input: dict | None

@dataclass
class ToolDef:
    name: str
    description: str
    input_schema: dict         # JSON Schema
```

### 3.4 Normalized Response Format

```python
@dataclass
class ChatResponse:
    id: str
    model: str
    content: list[ContentBlock]
    stop_reason: str            # "end_turn" | "max_tokens" | "tool_use" | "stop_sequence"
    usage: TokenUsage
    cost_usd: float

@dataclass
class TokenUsage:
    input_tokens: int
    output_tokens: int
    cache_read_tokens: int      # 0 if prompt caching not used
    cache_write_tokens: int

@dataclass
class StreamEvent:
    type: str                   # "text_delta" | "tool_use" | "tool_result" | "message_stop"
    text: str | None
    tool_use: ToolUseBlock | None
    usage: TokenUsage | None
```

### 3.5 Effort Level Mapping

Each provider maps Lyra's 5 effort levels to its native mechanism:

| Lyra Effort | Anthropic | OpenAI | DeepSeek | Open-Weights |
|-------------|-----------|--------|----------|--------------|
| `low` | thinking=disabled, 1K max_tokens | reasoning=none, 1K | CoT off, 1K | max_tokens=1024 |
| `medium` | thinking budget=4K, 4K max_tokens | reasoning=medium, 4K | CoT on, 4K | max_tokens=4096 |
| `high` | thinking budget=16K, 16K max_tokens | reasoning=high, 16K | CoT on, 16K | max_tokens=16384 |
| `xhigh` | thinking budget=32K, 32K max_tokens | reasoning=high, 32K | CoT on, 32K | max_tokens=32768 |
| `max` | thinking budget=64K, 64K+ max_tokens | reasoning=max, 64K | CoT on, 64K | max_tokens=65536 |

### 3.6 Provider Implementations

Four concrete backends in Phase 1:

1. **AnthropicBackend**: Uses `anthropic` SDK. Maps `Message` → Anthropic Messages API. Handles prompt caching, thinking budget, tool use.
2. **DeepSeekBackend**: Uses OpenAI-compatible SDK (DeepSeek API is OpenAI-compatible). Maps thinking budget to CoT prompting.
3. **OpenAIBackend**: Uses `openai` SDK. Maps effort to `reasoning_effort`. Handles vision via GPT-4o.
4. **OpenWeightsBackend**: Generic OpenAI-compatible endpoint (vLLM, Ollama, llama.cpp). No thinking budget → max_tokens only. No prompt caching. Graceful degradation for unsupported features.

### 3.7 Factory + Registry

```python
class ProviderRegistry:
    """Discovers and instantiates ProviderBackend implementations."""

    _backends: dict[str, type[ProviderBackend]] = {}

    @classmethod
    def register(cls, provider: str, backend_cls: type[ProviderBackend]): ...

    @classmethod
    def create(cls, provider: str, model_id: str, api_key: str, **kwargs) -> ProviderBackend:
        """Create a backend instance. Raises UnknownProviderError if provider not found."""

    @classmethod
    def list_capabilities(cls) -> dict[str, ProviderCapabilities]:
        """Return capability map for all registered providers."""
```

### 3.8 Fallback Chain

```python
class FallbackChain:
    """Ordered list of (provider, model_id) pairs. On failure, try next."""

    backends: list[tuple[str, str]]  # [(provider, model_id), ...]
    retry_count: int = 1
    retry_delay_ms: int = 1000

    async def execute(
        self,
        fn: Callable[[ProviderBackend], Awaitable[ChatResponse]],
    ) -> ChatResponse:
        """Execute fn against first available backend. Raises AllBackendsFailedError."""
```

## 5. Test Plan

### Unit Tests
1. **Message normalization**: Verify AnthropicBackend correctly maps normalized Message → Anthropic format; same for DeepSeek, OpenAI, OpenWeights
2. **Tool schema normalization**: Verify ToolDef → provider-specific tool schema for all 4 backends
3. **Token counting**: Verify token counts are consistent (±10%) with provider's own counters
4. **Effort mapping**: Verify each effort level produces correct provider-specific parameters
5. **Capability map**: Verify capabilities for each provider match reality
6. **Fallback chain**: Verify fallback triggers on HTTP 429/500/503; verify it DOESN'T trigger on HTTP 400
7. **Stream event normalization**: Verify streaming responses produce correct StreamEvent sequence
8. **Cost calculation**: Verify cost_usd is computed from usage × cost_per_1k for each provider

### Integration Tests (DeepSeek live)
1. **Real chat**: Send a simple prompt to DeepSeek and verify valid ChatResponse
2. **Tool use**: Send a tool-using prompt; verify tool_use content blocks are returned
3. **Streaming**: Stream a response; verify text_delta events arrive
4. **Error handling**: Send invalid API key; verify error is caught and surfaced

## 8. Implementation Notes

- **Clean-room**: The ProviderBackend design is original work based on published papers and docs. Do NOT copy code from OpenClaw, Kilo Code, or any GPL/incompatible repo.
- **OpenClaw's BYOK router** and **Kilo Code's 500+ model config** are DESIGN REFERENCES only (MIT/Apache-2.0 licensed concepts, not code).
- **OpenJarvis's 5-primitive typed spec** (TOML-serialized) is the long-term target — the ProviderBackend protocol is step 1 of making Lyra's stack declarative and versionable.
- **Error handling**: Every backend must handle rate limits (429), server errors (5xx), auth errors (401/403), and timeouts. Never crash the agent loop on a provider error.
- **Logging**: Log every provider call with (provider, model_id, input_tokens, output_tokens, latency_ms, cost_usd). This is the data foundation for the router (Item 1.2).
