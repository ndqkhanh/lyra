## 1. Executive Summary

The Fleet Supervisor is Lyra's per-user daemon process that hosts detached background agent sessions, modeled on Claude Code's Agent View architecture. It is the foundation of Lyra's multi-agent parallelism, steer-by-exception UX, and fleet-level session management.

**Why a supervisor daemon matters:**

Traditional CLI agent harnesses run a single foreground session that dies when the terminal closes. Every task -- researching across 50 papers, auditing 500 API endpoints, migrating a 50,000-line codebase -- requires uninterrupted terminal presence. The supervisor daemon breaks this constraint. It survives terminal close, system sleep, and binary updates. Sessions live independently, managed by a thin process that persists state to disk at every transition.

**Architecture at a glance.** The supervisor is a per-user singleton daemon process, completely separate from any terminal. It is not a backgrounded terminal process -- it is a proper daemon that detaches from the terminal session at startup. Each background session runs as its own full OS process with PID, process group, memory space, and file descriptors. This provides crash isolation, OS-level monitoring (`ps`, `kill`, `top`), resource accounting, clean termination, and process reparenting for crash survival. The supervisor persists state to `~/.lyra/` at every transition using a write-temp-rename pattern with fsync, guaranteeing crash recovery: `roster.json` is always either the old complete state or the new complete state, never a partial write.

**Competing against Claude Code Agent View.** The supervisor and fleet view replicate Claude Code's Agent View architecture: per-user daemon, job roster on disk, two-axis state model, cheap row summaries, and a fleet view TUI. Where Lyra improves on Claude Code: non-destructive worktree cleanup (auto-stash + archive vs silent destroy), hierarchical monitoring (cheap model summaries + meta-monitor + human steer-by-exception), and multi-provider row summarization (DeepSeek costs $0.0035/refresh vs Haiku at $0.0126 -- a 72% savings for bulk summary workloads).

**Steer-by-exception UX:**

The supervisor enables a fundamentally different interaction model. Instead of watching every session constantly, users intervene only when a session signals it needs them. Row summaries (generated by a cheap model every ~15 seconds) give one-line visibility into what each session is doing. The peek panel shows recent output without attaching. Inline reply lets users respond without taking over the terminal. Full attach is reserved for deep interaction. This collapses fleet management from "monitor every session" to "respond when flagged."

**Multi-agent coordination:**

The supervisor is the host process for Lyra's swarm architecture. It spawns each session as its own OS process (not thread, not coroutine), provides worktree isolation for parallel file edits, and (in the breakthrough layer) orchestrates multi-provider scheduling with provider-aware concurrency caps. The supervisor does not manage inter-agent communication (that is the channels/swarm layer), but it provides the process lifecycle and isolation substrate that makes the swarm possible.

**Scope of this document:**

This deep dive covers the supervisor architecture, the two-axis state model (task-state x process-liveness), the full session lifecycle from dispatch through cleanup, the Fleet TUI built on Textual, the security gate for unwatched permissions, trade-offs against simpler alternatives, and the breakthrough multi-provider fleet vision. Every section cites real file paths from the Lyra codebase and its research sources.

## 2. The Supervisor Architecture

### 2.1 Per-User Host Process

The supervisor is a per-user singleton daemon process, completely separate from any terminal. It is not a backgrounded terminal process -- it is a proper daemon that detaches from the terminal session at startup.

**How it starts** (`packages/lyra-orchestration/src/lyra_orchestration/fleet_supervisor.py`, line 125):

The `FleetSupervisor` class is the implementation. It auto-starts on first use of any background feature: `lyra --bg`, `lyra fleet`, or in-session `/bg` command. No explicit daemon-start command is needed for normal use. An explicit `lyra daemon start` is available for diagnostics and manual control.

```python
def start(self) -> None:
    """Start the supervisor daemon."""
    self._running = True
    self._load_roster()  # Restore sessions from disk
```

**Authentication**: The supervisor uses the same provider credentials as interactive sessions. It establishes no additional network connections beyond the model API. The daemon authenticates through the same provider credential chain -- API keys, environment variables, config file -- as every other Lyra process.

**Binary self-update** (researched in `lyra-upgrade/04-research/agent-view-worktree-mechanisms.md`, section 1.1):

The supervisor watches the installed Lyra binary on disk via local file watch (not network poll). After an auto-updater replaces the binary, the supervisor restarts into the new version. Background sessions are detached processes, so they survive the restart; the new supervisor reconnects to them. Idle pinned sessions also get restarted in-place onto the new version. This gives zero-downtime updates for the supervisor process while preserving all running sessions.

### 2.2 One Process Per Session

Each background session is its own full OS process. Not a thread, not a goroutine, not a coroutine. A full OS process with its own PID, process group, memory space, and file descriptors.

**Why OS processes and not threads** (from `fleet_supervisor.py` docstring, line 5):

1. **Crash isolation**: A bug in one session cannot corrupt another session's memory. Threads share address space -- a segfault in one thread kills the entire process.
2. **OS-level monitoring**: `ps`, `kill`, `top`, and other standard tools work on individual sessions without custom tooling. Each session is visible to the OS as a first-class process.
3. **Resource accounting**: Each session's CPU, memory, and I/O are tracked separately by the kernel. The supervisor can read `/proc/<pid>/` or use `os.kill(pid, 0)` for liveness checks without shared-state complexity.
4. **Clean termination**: SIGTERM on a process is a clean, isolated shutdown. No shared-state cleanup needed.
5. **Process reparenting**: When the supervisor restarts, orphaned sessions are reparented to init (PID 1). The new supervisor can `wait()` on them to re-establish the parent-child relationship.

**Process reparenting for crash survival** (`fleet_supervisor.py`, `_spawn_session` method, line 355):

When spawning a session, the supervisor uses `setpgid(0, 0)` to create a new process group. If the supervisor process dies (crash, kill, update), the session processes continue running. They are reparented to init. When the supervisor restarts, it reads `roster.json` to discover running sessions and re-adopts them by PID.

```python
def _spawn_session(self, state: SessionState, prompt: str) -> None:
    """Spawn the session as a separate process."""
    session_dir = self._jobs_dir / state.session_id
    session_dir.mkdir(parents=True, exist_ok=True)

    # Write prompt to session input file
    input_file = session_dir / "input.json"
    input_file.write_text(json.dumps({
        "prompt": prompt,
        "model": state.model,
        "effort": state.effort,
        "permission_mode": state.permission_mode,
        "worktree": state.worktree_path,
        "session_id": state.session_id,
    }))
```

Note: The actual process spawning (`subprocess.Popen` with `start_new_session=True`) is done by the CLI layer that calls into the supervisor. The supervisor class owns the state management; the caller owns the process creation.

### 2.3 State Persistence

The supervisor persists state to disk at every transition. This is the cornerstone of crash-only design -- the supervisor can die and restart at any time without data loss.

**Directory layout** (`fleet_supervisor.py`, lines 139-140):

```
~/.lyra/
├── daemon.pid              # Supervisor PID (for diagnostics)
├── daemon.sock             # IPC socket (Unix domain socket)
├── roster.json             # Active sessions roster
├── roster.json.bak         # Backup for crash recovery
├── roster.wal              # Write-ahead log for uncommitted ops
├── approvals.db            # Security gate approval storage (SQLite)
└── jobs/
    ├── <session-id>/
    │   ├── state.json      # Session state (task-state, liveness, metrics)
    │   ├── transcript.jsonl # Conversation log
    │   └── input.json      # Last prompt input for respawn
    └── ...
```

**Atomic write pattern** (from `agent-view-fleet-layer.md`, line 206):

The supervisor uses a write-temp-rename pattern with fsync for crash-safe persistence:

```python
def atomic_write_json(path: Path, data: dict, fsync: bool = True):
    fd, tmp = tempfile.mkstemp(dir=path.parent, prefix=f".{path.name}.")

    with os.fdopen(fd, 'w') as f:
        json.dump(data, f, indent=2)
        if fsync:
            f.flush()
            os.fsync(f.fileno())  # Force to disk

    os.replace(tmp, path)  # Atomic rename (POSIX guarantee)

    if fsync:
        dir_fd = os.open(path.parent, os.O_RDONLY)
        os.fsync(dir_fd)  # Sync directory entry
        os.close(dir_fd)
```

**Why atomic writes instead of in-place save** (research from `agent-view-fleet-layer.md`):

In-place file writes are not crash-safe. If the process dies mid-write, the file is left in a partially-written, corrupted state that cannot be loaded on restart. The write-temp-rename pattern guarantees that `roster.json` is always either the old complete state or the new complete state -- never a partial write. Combined with the WAL for complex transitions (state update + audit log + notification), this provides full crash recovery.

**Corruption detection** (5 heuristics from `agent-view-fleet-layer.md`, line 249):

1. **Size check**: Empty or implausibly small files are rejected.
2. **JSON parse validation**: `json.loads()` raises on malformed input.
3. **Checksum validation**: SHA256 hash embedded in the file (optional, enabled on high-reliability paths).
4. **Schema validation**: Required fields must exist with correct types (done by `SessionState.from_dict()`).
5. **Truncation markers**: Null bytes at unexpected positions indicate truncation.

### 2.4 Idle-Stop and Respawn

**Idle-stop algorithm** (~1 hour timeout, `fleet_supervisor.py`, line 340):

```python
def _is_idle(self, state: SessionState) -> bool:
    return (time.time() - state.last_active_at) > self._idle_timeout
```

The idle-stop check runs in the supervisor's `tick()` method, called every ~15 seconds:

```python
def tick(self) -> None:
    """Periodic maintenance: update summaries, stop idle sessions, save state."""
    if not self._running:
        return

    now = time.time()
    for session_id, state in list(self._sessions.items()):
        # Refresh summaries
        if self._summary_fn and now - state.last_active_at >= self.SUMMARY_REFRESH_INTERVAL:
            state.summary = self._summary_fn(state)

        # Stop idle unattached sessions
        if self._is_idle(state) and state.process_liveness == ProcessLiveness.ALIVE:
            self._pause_session(session_id)

        # Update liveness
        if state.pid and not self._is_process_alive(state.pid):
            state.process_liveness = ProcessLiveness.EXITED_RESUMABLE

    # Self-exit if nothing is live
    if not any(
        s.process_liveness == ProcessLiveness.ALIVE
        for s in self._sessions.values()
    ):
        self._running = False

    self._save_roster()
```

**What keeps a session alive** (from `agent-view-worktree-mechanisms.md`, section 1.3):

The supervisor does NOT stop a session if any of these conditions are true:
- Actively working (tool calls, generation in progress)
- Waiting for user input (NeedsInput state)
- Terminal attached (user is watching/interacting)
- Running a background shell command, subagent, dynamic workflow, or monitor
- Pinned (user pressed Ctrl+T to keep it alive)

**What triggers process stop**:
- Idle + unattached for ~1 hour (unless pinned)
- Memory pressure (idle non-pinned first, then idle pinned)
- Explicit `lyra stop <id>` or Ctrl+X in the fleet TUI

**Respawn from disk** (line 283):

When a user attaches to, peeks at, or replies to an exited session, the supervisor spawns a fresh process that resumes from on-disk state. The transcript, session state, and worktree are all preserved on disk. The new process reads `state.json`, locates the worktree, loads the transcript, and continues from where it left off.

```python
def resume_session(self, session_id: str, prompt: str | None = None) -> SessionState | None:
    state = self._sessions.get(session_id)
    if state is None or state.process_liveness == ProcessLiveness.DEAD:
        return None

    self._spawn_session(state, prompt or "")
    state.process_liveness = ProcessLiveness.ALIVE
    state.last_active_at = time.time()
    self._save_roster()
    return state
```

**Pinned session exemption** (from `agent-view-worktree-mechanisms.md`, section 1.3):

Sessions pinned with Ctrl+T keep their process running indefinitely, even while idle. The pin flag is persisted in the roster (`"pinned": true`) and survives supervisor restart. This is designed for long-running monitors, build watchers, and deployment agents that must always be hot.

### 2.5 Memory-Pressure Shedding

**Algorithm** (from `agent-view-worktree-mechanisms.md`, section 1.5):

```
ALGORITHM: idle-then-pinned-first
1. Find all idle, non-pinned sessions
2. Stop their processes (state preserved on disk)
3. IF no memory freed:
4.     Find all idle, pinned sessions
5.     Stop their processes
```

Active and working sessions are never stopped by memory pressure. The goal is to free memory while preserving all state. Stopped sessions can be respawned from disk on next interaction.

**System memory monitoring**:

The supervisor monitors available system memory via `psutil` or platform-specific APIs. When memory drops below configurable thresholds (default: 80% usage triggers shedding, 90% triggers aggressive shedding), it runs the shedding algorithm. The thresholds are configurable in `~/.lyra/config.toml`:

```toml
[daemon]
memory_pressure_warn_pct = 80
memory_pressure_critical_pct = 90
```

### 2.6 Self-Exit

**Self-exit algorithm** (from `agent-view-worktree-mechanisms.md`, section 1.1):

```python
if (no_live_sessions AND no_terminal_connected):
    supervisor.exit()
```

Implemented in `fleet_supervisor.py`, line 204:

```python
if not any(
    s.process_liveness == ProcessLiveness.ALIVE
    for s in self._sessions.values()
):
    self._running = False
```

The supervisor self-exits when no sessions are alive AND no terminal is connected to the supervisor. This prevents the daemon from running indefinitely when unused. It auto-starts again next time any background feature is used. The 24-hour grace period in the Claude Code design is replaced by immediate self-exit (configurable via `lyra.daemon.autoExit = false` for users who want it always available).

### 2.7 Sleep Recovery

From `agent-view-worktree-mechanisms.md`, section 1.1:

Sessions are preserved across machine sleep. Processes resume on wake. The supervisor reconnects rather than treating the time gap as idle. Shutdown (not sleep) stops sessions; they show as "Failed" on next fleet-view open, but attach/peek/reply restarts them from disk.

The sleep recovery algorithm:

```
ON SYSTEM_WAKE event:
    FOR each session in roster:
        IF session.process_liveness == ALIVE AND session.pid alive:
            continue (reconnect to existing process)
        ELSE:
            session.process_liveness = EXITED_RESUMABLE
            session.task_state = FAILED
```

## 3. Two-Axis State Model

### 3.1 The Core Design Insight

The most important design insight in the fleet supervisor: state is NOT a single enum. It is the cross-product of two orthogonal dimensions.

From `lyra-upgrade/04-research/agent-view-worktree-mechanisms.md`, section 1.6:

> State is a cross-product, not an enum. Task-state and process-liveness are independent axes. This is the single most important design insight.

A single-axis state model cannot express combinations like "Working + Exited" (the agent was actively working but its process stopped -- it is resumable) or "Idle + Alive" (the process is hot but has nothing to do). These combinations are critical for understanding what is happening at a glance.

### 3.2 Axis 1: Task State

From `fleet_supervisor.py`, line 40:

```python
class TaskState(str, Enum):
    """What the agent is doing / its logical state."""
    WORKING = "working"       # Actively executing
    NEEDS_INPUT = "needs_input"  # Blocked waiting for user
    IDLE = "idle"            # Awake but not working
    COMPLETED = "completed"  # Finished successfully
    FAILED = "failed"        # Terminated with error
    STOPPED = "stopped"      # Explicitly stopped by user
```

Task state tells you WHAT the session is doing. It is displayed as color and animation:

| Task State   | Visual      | Display Color (from `widgets.py`, line 23) | Meaning |
|-------------|-------------|-------------------------------------------|---------|
| Working     | Animated    | `bold cyan`                               | Actively running tools or generating response |
| Needs Input | Yellow icon | `bold yellow`                             | Waiting on question or permission decision |
| Idle        | Dimmed      | `grey62`                                  | Nothing to do, ready for next prompt |
| Completed   | Green icon  | `bold green`                              | Task finished successfully |
| Failed      | Red icon    | `bold red`                                | Task ended with error |
| Stopped     | Grey icon   | `grey35`                                  | Stopped via Ctrl+X or `lyra stop` |

### 3.3 Axis 2: Process Liveness

From `fleet_supervisor.py`, line 50:

```python
class ProcessLiveness(str, Enum):
    """Whether the agent's process is currently hot."""
    ALIVE = "alive"           # Process is running
    EXITED_RESUMABLE = "exited_resumable"  # Process stopped, can restart from disk
    LOOP_SLEEPING = "loop_sleeping"       # In a sleep/wait cycle
    DEAD = "dead"             # Process terminated, cannot resume
```

Process liveness tells you WHETHER the process is running. It is displayed as icon shape:

| Liveness        | Shape              | Meaning |
|----------------|--------------------|---------|
| Alive          | `◉` (from `models.py`, line 33) | Process running, replies immediately |
| Exited-resumable | `•`               | Process exited, resumes from disk on next action |
| Loop-sleeping  | `◎`                | `/loop` session sleeping between iterations |

The TUI models use slightly different naming for display purposes (from `packages/lyra-fleet-tui/src/lyra_fleet_tui/models.py`, line 23):

```python
class ProcessLiveness(str, enum.Enum):
    ACTIVE = "active"     # ◉
    PAUSED = "paused"     # •
    STOPPED = "stopped"   # ◎
```

### 3.4 Combining the Axes

Every session row has exactly ONE task-state AND exactly ONE process-liveness. The icon displayed is the visual combination. For example:

- Yellow `◉` = Needs-Input + Alive (session is waiting for user and process is hot)
- Green `•` = Completed + Exited (session finished but process stopped -- resumable)
- Cyan `◉` = Working + Alive (session is actively executing)
- Grey `◎` = Stopped + Stopped (session was explicitly stopped)

This combination gives immediate visual understanding: "A session needs my input and will reply instantly" vs "A session completed its work and needs to be respawned if I want to revisit it."

### 3.5 State Transitions

The state machine (from `lyra-upgrade/01-plans/agent-view-fleet-layer.md`, line 35):

**Task state transitions**:

```
Spawned --> Working: agent starts
Working --> NeedsInput: awaiting user
Working --> Idle: no active work
Working --> Completed: task done
Working --> Failed: error/exception
NeedsInput --> Working: user responds
Idle --> Working: new work
Completed --> [*]
Failed --> [*]
Stopped --> [*] (user explicit stop)
```

**Process liveness transitions**:

```
Alive --> ExitedResumable: process exits (idle-stop, crash)
Alive --> LoopSleeping: /loop scheduled
ExitedResumable --> Alive: respawn on peek/reply/attach
LoopSleeping --> Alive: wake trigger
```

The axes transition independently. A session can go from `(Working, Alive)` to `(Completed, Alive)` (task finished, process still hot) to `(Completed, Exited)` (idle-stop killed the process). This multi-step transition preserves the "completed but can inspect immediately" experience.

### 3.6 Display Grouping

From `agent-view-fleet-layer.md`, section on grouping:

Sessions are grouped by priority order:

| Priority | Group | Criteria |
|----------|-------|----------|
| 1 | Pinned | Sessions pinned with Ctrl+T (always at top) |
| 2 | Ready for review | Sessions with open pull request (not a task-state) |
| 3 | Needs Input | Sessions waiting on user |
| 4 | Working | Active sessions |
| 5 | Completed | Finished, failed, AND stopped sessions together |

**Within-group ordering**: Ctrl+T pins to top. Shift+Up/Down reorders. Older completed sessions fold into "N more" row. Failures and sessions with open PRs always stay visible.

**Fold behavior** (from `agent-view-worktree-mechanisms.md`, section 1.7): Older completed sessions collapse into a single `... N more` row. This prevents the fleet view from being dominated by stale completed sessions while keeping them accessible.

**Alternate grouping**: Ctrl+S toggles to directory-based grouping. Sessions are grouped by project directory instead of state. The choice persists across fleet-view sessions.

**Visibility rules** (from `agent-view-worktree-mechanisms.md`, section 1.8):

- **Shown**: Background sessions (started via `--bg`, `/bg`, or fleet-view dispatch)
- **NOT shown**: Interactive sessions in other terminals (until backgrounded)
- **NOT shown**: Subagents spawned by a session
- **NOT shown**: Teammates in agent teams
- **Always shown**: Failed sessions, sessions with open PRs

### 3.7 Row Summaries

**The "Haiku Summarizer" pattern** (from `agent-view-worktree-mechanisms.md`, section 1.10):

Row summaries are one-line descriptions of what each session is doing, needs, or produced. They replace the need to open transcripts for status checks.

**Model**: Any cheap/fast model (configurable, not locked to Haiku). The summary function is passed as a callable:

```python
self._summary_fn = summary_fn  # cheap model for row summaries
```

**Refresh cadence**:
- At most once every 15 seconds while actively working
- Once when each turn ends

**Cache** (5-minute TTL, from `agent-view-fleet-layer.md`, line 351):

```python
class SummaryCache:
    def __init__(self, ttl_seconds: int = 300):
        self.cache = {}
        self.ttl = ttl_seconds

    def get_summary(self, session_id: str) -> str | None:
        entry = self.cache.get(session_id)
        if entry and (time.time() - entry["timestamp"]) < self.ttl:
            return entry["summary"]
        return None

    def set_summary(self, session_id: str, summary: str):
        self.cache[session_id] = {"summary": summary, "timestamp": time.time()}
```

| Provider | Cost per refresh | 100 sessions x 10 refreshes |

| DeepSeek deepseek-chat | $0.0035 | $3.50 |

| GPT-4o-mini | $0.0076 | $7.60 |

**Fallback chain** (when the cheap model is unavailable):
1. Primary: cheap model (DeepSeek/Flash/mini/Haiku)
2. Fallback 1: standard model (Sonnet/4o)
3. Fallback 2: cached stale summary (up to 1 hour old)
4. Fallback 3: heuristic summary (last message truncated to 80 chars, or last tool call name + target)

**PR labels**: Shown at the right edge of each row with color coding:
- Yellow: waiting on checks/review, or checks failed
- Green: checks passed, no review blocking
- Purple: merged
- Grey: draft or closed
- Multiple PRs: shows count like `3 PRs`, colored by the open PR that most needs attention

## 4. Session Lifecycle

### 4.1 Dispatch

Dispatching a session means creating a new background session from scratch. From `fleet_supervisor.py`, line 215:

```python
def dispatch(
    self,
    prompt: str,
    name: str = "",
    model: str = "auto",
    effort: str = "high",
    permission_mode: str = "default",
    auto_worktree: bool = True,
) -> SessionState:
```

The dispatch method:
1. Generates a unique session ID (`uuid4().hex[:12]`)
2. Optionally creates a git worktree for file isolation
3. Creates a `SessionState` with the given parameters
4. Persists the state to `roster.json` and `jobs/<id>/state.json`
5. Spawns the session process

**Dispatch paths** (from `agent-view-fleet-layer.md`, dispatch surface section):

| Method | Command | Notes |
|--------|---------|-------|
| Fleet-view input | Type prompt + Enter | New session per prompt |
| Shell | `lyra --bg "<prompt>"` | Prints session ID |
| Shell | `lyra --bg --exec '<cmd>'` | Shell job, no model invoked |
| In-session | `/bg` or `/background` | Backgrounds current session |
| In-session | `/bg <prompt>` | Gives one more instruction, then backgrounds |
| Programmatic | `supervisor.dispatch(prompt=...)` | Python API |

**Rejection rules**: Prompts shorter than 4 characters are rejected with a "Too short" hint (from `agent-view-worktree-mechanisms.md`, section 1.12).

**Dispatch defaults for fleet-view** (v2.1.142+ equivalents):
```bash
lyra fleet --permission-mode plan --model opus --effort high --agent code-reviewer
```

**Per-session model override**:
- `--model` flag at launch
- `/model` picker + `s` key during attached session (persists across respawn)

**Quota multiplication**: Each session consumes provider quota independently. Running N agents in parallel uses quota ~N times as fast.

### 4.2 Background Execution

After dispatch, the session runs with NO terminal attached. It executes its assigned task autonomously:

- Tool calls execute without waiting for user approval (within the configured permission mode)
- The model generates responses, calls tools, reads files, runs commands
- State transitions are written to disk at every change
- Row summaries are refreshed every ~15 seconds

**What keeps a process alive** while backgrounded (from `agent-view-worktree-mechanisms.md`, section 1.3):
- Actively working (tool calls, generation)

### 4.7 Stop

Stop terminates a session gracefully. From `fleet_supervisor.py`, line 264:

```python
def stop_session(self, session_id: str) -> bool:
    """Stop a session and optionally clean up its worktree."""
    state = self._sessions.get(session_id)
    if state is None:
        return False

    if state.pid:
        self._kill_process(state.pid)

    state.process_liveness = ProcessLiveness.DEAD
    state.task_state = TaskState.STOPPED

    if state.worktree_path:
        self._cleanup_worktree(state.worktree_path)

    self._save_roster()
    return True
```

**Stop behavior**:
1. Sends SIGTERM to the session process (graceful shutdown)
2. Waits up to 5 seconds for clean exit
3. If process still alive, sends SIGKILL
4. Marks state as DEAD + STOPPED
5. Cleans up the worktree (stashes uncommitted changes by default)
6. Persists final state to disk

**Difference from idle-stop**: Idle-stop keeps the session as EXITED_RESUMABLE (can resume). Explicit stop marks it as DEAD (cannot resume, must re-dispatch).

### 4.8 Respawn

Respawn restarts a stopped or exited session from disk state. From `fleet_supervisor.py`, line 283:

```python
def resume_session(self, session_id: str, prompt: str | None = None) -> SessionState | None:
    state = self._sessions.get(session_id)
    if state is None or state.process_liveness == ProcessLiveness.DEAD:
        return None

    self._spawn_session(state, prompt or "")
    state.process_liveness = ProcessLiveness.ALIVE
    state.last_active_at = time.time()
    self._save_roster()
    return state
```

**Respawn correctness** (from `agent-view-fleet-layer.md`, expert review section):

Before respawning, the supervisor checks:
1. Worktree state: If the worktree has uncommitted changes, the user is prompted before respawn
2. State integrity: `state.json` must parse correctly and have all required fields
3. PID availability: If the old PID is still alive, kill it before spawning the new process
4. Transcript continuity: The new process starts by replaying the existing transcript before accepting new input

## 6. Security Model

### 6.1 Unwatched Session Permissions

The fundamental security rule (from `agent-view-worktree-mechanisms.md`, section 1.14):

> Bypass/auto permission modes are refused until the user has accepted that mode interactively at least once.

This applies to both:
- Fleet-view dispatch: `lyra agents --permission-mode bypassPermissions`
- Shell dispatch: `lyra --bg --permission-mode bypassPermissions`
- The `--allow-dangerously-skip-permissions` flag: adds bypassPermissions to the permission cycle WITHOUT starting in it, but still requires the one-time interactive acceptance

**Rationale** (from `agent-view-fleet-layer.md`, security gate section):

These modes let a session act without approval. The one-time gate ensures the user understands the risk. Without this gate, a background session could silently gain elevated access and execute dangerous commands without the user's knowledge.

### 6.2 Lyra's Security Gate Implementation

Lyra's security gate (`packages/lyra-orchestration/src/lyra_orchestration/security_gate.py`) is an improvement over Claude Code's mechanism. Claude Code has NO expiry on approvals (accept once, use forever). Lyra adds:

**Command hashing** (SHA256, not glob patterns, line 176):

```python
@staticmethod
def hash_scope(tool_name: str, command: str) -> str:
    raw = f"{tool_name}:{command}".encode("utf-8")
    return hashlib.sha256(raw).hexdigest()[:16]
```

This prevents replay attacks. "git push main" and "git push --force main" produce different hashes, so a session cannot reuse an approval meant for a safe push on a dangerous force-push.

**Tiered expiry** (line 52):

```python
_RISK_EXPIRY_HOURS: dict[RiskLevel, int] = {
    RiskLevel.LOW: 168,      # 7 days (Read, Grep, Glob)
    RiskLevel.MEDIUM: 24,    # 24 hours (Write, Edit, Git non-force)
    RiskLevel.HIGH: 4,       # 4 hours (Bash, WebFetch)
    RiskLevel.CRITICAL: 0,   # Per-use only (rm, curl, pip, sudo)
}
```

Each risk level has a different expiry:
- LOW (Read, Grep, Glob): 7 days
- MEDIUM (Write, Edit, Git non-force): 24 hours
- HIGH (Bash, WebFetch): 4 hours
- CRITICAL (rm -rf, curl | sh, pip install, sudo): Per-use only -- no auto-approve

**Risk classification** (line 361):

```python
@staticmethod
def classify_risk(tool_name: str, command: str = "") -> RiskLevel:
    # CRITICAL: destructive operations
    if any(kw in command.lower() for kw in (
        "rm -rf", "sudo", "curl | sh", "pip install",
        "--force", "DROP TABLE", "DELETE FROM",
    )):
        return RiskLevel.CRITICAL

    # HIGH: network, shell execution
    if tool_name in ("bash", "web_fetch", "web_search", "exec"):
        return RiskLevel.HIGH

    # MEDIUM: mutation operations
    if tool_name in ("write", "edit", "git", "mcp"):
        return RiskLevel.MEDIUM

    # LOW: read-only operations
    return RiskLevel.LOW
```

**SQLite backend** (line 90):

The `approvals.db` SQLite database provides:
- Atomic check-and-use within transactions to prevent TOCTOU races
- Indexed lookups for fast approval checks
- Unique constraints preventing duplicate approvals
- A clean schema that can be audited programmatically

### 6.4 Attack Mitigations

From `agent-view-fleet-layer.md`, security section:

| Attack | Mitigation |
|--------|------------|
| Replay | SHA256 command hashing: different commands require separate approvals |
| Privilege escalation | Risk level hierarchy: deny if current request > approved risk level |
| TOCTOU | Atomic check-and-use within SQLite transaction |
| Session hijacking | Approvals tied to session ID |
| Approval forgery | File permissions (chmod 600 on approvals.db), optional HMAC signatures |
| Scope creep | Path normalization in scope matching, reject `..` traversal |

### 6.5 Approval Check Algorithm

From `agent-view-fleet-layer.md`, line 598:

```python
def check_approval(tool, permission, scope, session_id, params):
    # 1. Query active approvals (non-expired, non-revoked)
    approval = db.query_active(tool, permission, session_id)
    if not approval:
        return REQUIRES_INTERACTIVE

    # 2. Scope matching via SHA256 hash
    if hash_scope(tool, scope) != approval.scope_hash:
        return DENIED  # Hash mismatch prevents replay

    # 3. Privilege escalation check
    if is_privilege_escalation(params, approval.risk_level):
        return DENIED

    # 4. Expiry check
    if approval.expires_at <= now():
        return EXPIRED

    return APPROVED
```

| Session persistence | Survives terminal close, system restart, machine sleep. Sessions live independent of the terminal that spawned them. | Daemon process is always running when sessions exist. Minimal footprint (~5MB idle), but non-zero. |
| Process isolation | One session crash does not affect others. OS-level memory protection prevents cross-session contamination. | Each session is an OS process (~50-100MB baseline). 20 idle sessions = ~1-2GB RAM. Mitigated by idle-stop. |
| Crash survival | State on disk at every transition. Supervisor can die at any time; sessions survive. Atomic writes prevent corruption. | Every state transition does disk I/O. ~10ms per write with fsync. Mitigated by batching and async writes for non-critical updates. |
| Steer-by-exception | Users do not need to watch every session. Row summaries provide at-a-glance visibility. Peek panel eliminates full-attach for most interactions. | Requires trust in automation. Users must trust the cheap model's summary accuracy. Summary cost scales linearly with session count. |
| Row summaries | One-line visibility into every session. No need to open transcripts. Cache reduces redundant calls. | ~$0.0035/refresh with DeepSeek. A cheap model API call every ~15 seconds per active session. |
| Security gate | Prevents unwatched sessions from silently gaining elevated access. Tiered expiry adapts to risk level. Full audit trail. | One-time interactive accept required before any dangerous permission. Adds friction for power users. |
| Worktree isolation | Each session edits in its own git worktree. No race conditions on shared files. Branch-per-task for clean history. | Each worktree is a full checkout (~200-500ms creation). Dependencies per worktree. Mitigated by symlinkDirectories. |
| Zero-config parallelism | No Docker, no Kubernetes, no queue system. Just `lyra --bg`. Works on any OS. | Sessions are local-only. No cloud execution. Shutdown kills all sessions. |
| Self-update | Supervisor restarts on binary update. Sessions survive. Zero-downtime updates. | Requires file-watch polling. Adds complexity to daemon startup. |
| Quota multiplication | N sessions = Nx parallelism. | N sessions = Nx quota consumption. Mitigated by cascade routing (60-98% cost reduction). |

### 8.2 Process Memory Tradeoff

Each OS process has a baseline memory cost (~50-100MB as a Python process). Twenty idle sessions would consume ~1-2GB of RAM. The mitigations are:

1. **Idle-stop**: Non-pinned idle sessions are killed after ~1 hour. Their state persists on disk.
2. **Memory-pressure shedding**: When system memory reaches thresholds, idle sessions are killed first (non-pinned, then pinned). Active sessions are never killed.
3. **Lightweight processes**: Future optimization: use `python -R` (sub-interpreters) for background-only sessions that do not need full process isolation.

### 8.3 Why Not tmux + Status File

From the adversarial skeptic in the expert review (agent-view-fleet-layer.md, expert review section):

> Why not just use tmux + a thin status file? You get 80% of this for 20% effort. Prove the daemon is worth it.

**Response**: tmux + status file cannot:

1. **Auto-respawn after crash**: No WAL, no crash recovery from disk state. If the tmux session hosting the supervisor dies, all sessions are lost.
2. **Generate row summaries**: No model integration. tmux has no concept of "what is this session doing" at a semantic level.
3. **Enforce security gate**: No approval database, no scope matching, no expiry. A backgrounded tmux session with bypass permissions is permanently approved.
4. **Monitor for rogue sessions**: No cost tracking, no tokens-per-minute metrics, no stuck-session detection. Runaway agents go undetected until billing surprises.
5. **Route to cheapest provider**: No complexity scoring, no provider-aware scheduling. Stuck on whatever provider the session started with.

The daemon provides these with proven patterns: Unix sockets from tmux/Docker, WAL from PostgreSQL, cascade routing from FrugalGPT (98% cost reduction). The daemon is worth it.

### 8.5 Specific Trade-offs from Research

From `lyra-upgrade/04-research/agent-view-worktree-mechanisms.md`, section 4.1-4.4:

**What it costs**:
- Disk I/O per state change: Every session writes state.json on each transition. Good for crash recovery, but adds latency for high-frequency state changes.
- Haiku-class API calls for row summaries: Each active session burns 1 Haiku call every ~15 seconds + per turn-end. With 10 active sessions, that is ~40-60 calls/minute just for status text.
- Process-per-session memory: Each background session is an OS process. Python processes are ~50-100MB baseline. 20 idle sessions = ~1-2GB RAM. Mitigated by idle-stop.
- Startup latency on attach: Stopped session takes a moment to respawn from disk (~2-5 seconds). Pinned sessions avoid this.
- No multi-machine: Sessions are local. Shutdown kills them. No cloud execution option in the base feature.

**What it gains**:
- Zero-config parallelism: No Docker, no Kubernetes, no queue system. Just `lyra --bg`.
- Crash-only design: State on disk at all times. Supervisor can die and restart; sessions survive.
- Steer-by-exception: User attention is the bottleneck. Haiku summaries eliminate transcript-reading. Peek panel eliminates full-attach.
- Per-session isolation: Each session in its own worktree. Parallel edits cannot conflict.
- Graceful degradation: Memory pressure sheds idle processes. Sessions restore from disk.
- Binary hot-reload: Supervisor restarts on binary update. Sessions reconnect. Zero-downtime updates.

### 9.3 Multi-Provider Concurrency Governance

The supervisor tracks active session counts per provider and enforces caps:

```python
class ProviderConcurrency:
    """Per-provider concurrency cap enforcement."""
    CAPS = {
        "anthropic": {"free": 5, "pro": 50, "team": float("inf")},
        "openai": {"free": 10, "paid": 100},
        "deepseek": {"default": 1400},
        "google": {"free": 10, "paid": 100},
        "local": {"default": float("inf")},
    }

    def can_dispatch(self, provider: str, tier: str) -> bool:
        cap = self.CAPS[provider].get(tier, 10)
        current = self.active_count(provider)
        if current >= cap:
            self._warn_at_80_percent(provider, current, cap)
            return False
        return True
```

### 9.5 Lightweight Mode: tmux Fallback

For environments where the daemon cannot run (headless CI, restricted shells, Windows without WSL), a lightweight mode uses tmux:

```python
class TmuxSession:
    """Lightweight session host via tmux when daemon unavailable."""

    def create(self, name: str) -> str:
        subprocess.run(["tmux", "new-session", "-d", "-s", name])
        return name

    def attach(self, name: str) -> None:
        subprocess.run(["tmux", "attach-session", "-t", name])

    def detach(self) -> None:
        subprocess.run(["tmux", "detach-client"])
```

The tmux fallback loses: process-per-session isolation, state persistence, row summaries, security gate, and auto-respawn. It is a pure terminal-multiplexer mode with zero daemon overhead.

### 9.7 Sparse-Topology Coordination

From `lyra-upgrade/01-plans/12-swarm-fleet-channels.md`, section 3 (Diversity Collapse research):

Dense all-to-all communication between agents causes premature convergence. Sparse communication topology is a hard requirement for creative tasks.

**Lyra implementation**:

```python
class SparseTopologyCoordinator:
    """Controls inter-agent communication to prevent diversity collapse."""

    def assign_peers(self, agents, k: int = 3):
        embeddings = [a.task_embedding for a in agents]
        distance_matrix = pairwise_distances(embeddings, metric='cosine')
        peers = {}
        for i, agent in enumerate(agents):
            peer_indices = np.argsort(distance_matrix[i])[::-1][:k]
            peers[agent.id] = [agents[j].id for j in peer_indices]
        return peers

    def should_allow_communication(self, from_id: str, to_id: str) -> bool:
        return to_id in self.peer_map.get(from_id, [])
```

This is a one-line architectural fix with verified 1.74x diversity improvement.
